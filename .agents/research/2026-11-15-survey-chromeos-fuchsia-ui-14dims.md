## 结论

### 总裁决

两套系统代表 UI 框架光谱的两个极端：ChromeOS 是「平台不做 UI 框架，把整个系统 UI 押在 Web 技术 + 扩展生态上，三应用形态（Web/ARC++/Linux）经 exo Wayland 服务统一进一个 shell」；Fuchsia 是「平台不做 UI 框架，只把合成（Scenic/Flatland）、View 体系、输入管线、IME（text_manager）、无障碍（a11y manager）做成纯 FIDL 协议组件，应用与 shell 一律吃现成框架（Flutter 一等，Chromium 次之）」。对 BerryOS 的总取法：协议面学 Fuchsia（独立组件 + token 语义），产品交付面学两家的共同教训（不自研应用 UI 框架，声明式框架直接选型现成生态），键盘优先与三形态输入统一的工程面学 ChromeOS。

### ChromeOS 十四维

一、声明式与状态管理：系统 Web 应用（System Web Apps）走声明式 Web 栈——`//ash/webui` 收纳「Chrome OS 专用的系统 Web 应用 WebUI」，README 标注已迁往 `//chromeos/ash/experiences`（https://chromium.googlesource.com/chromium/src/+/main/ash/webui/README.md）；组件模型是 Web Components + Lit（Material Web 自述「基于 web components 的库」）；但 Ash shell 主体（窗口管理、shelf、概览）仍是 C++ Views 保留模式 widget 树，非声明式——系统处于「外壳命令式、应用面声明式」的混合态，且迁移以目录整理而非框架统一的方式推进。

二、组件丰富度与质量：桌面原生组件由 Views toolkit 承担（`//ash/wm`、`//ash/system`），WebUI 侧组件库双轨——Google 内部的 cr/iron 系与对外的 `@material/web`（Material 3 web components，npm 发布）；关键负面事实：Material Web 官方 README 声明「MWC is in maintenance mode pending new maintainers」（https://raw.githubusercontent.com/material-components/material-web/main/README.md），材料化 Web 组件生态处于维护模式待接管；Android 形态经 ARC++ 可复用全部 Android 组件，Linux 形态自带 GTK/Qt，三形态组件质量不齐、无统一规范。

三、动画系统：Ash 动画走 ui::Layer + viz 合成器，虚拟桌面切换有专用动画组件 `root_window_desk_switch_animator` 与 `desk_animation_impl`（https://chromium.googlesource.com/chromium/src/+/main/ash/wm/desks/ 目录实抓）；desk 栏滚动时长常量 `kDeskBarScrollDuration = 250ms`（desks_constants.h）；WebUI 动画用 CSS + Material motion token（easing 分 emphasized/standard，https://m3.material.io/styles/motion/overview）；无统一跨形态动画 API，各栈各做。

四、手势与输入：输入栈 Evdev → ui/events → Ash accelerator；触控板滑动切桌面有量化阈值 `kTouchpadSwipeLengthForDeskChange = 420`（desks_constants.h 实抓）；三形态统一在 exo——「Exo 在 Aura Shell 之上实现 display server，用 Wayland 协议与客户端通信」，客户端即 ARC++ 与 Crostini，私有协议 `zaura_shell`（全部客户端）与 `zcr_remote_shell`（仅 ARC++），输入文件族 pointer/touch/keyboard/gamepad + 触控笔代理 pointer_stylus_delegate/touch_stylus_delegate 齐备（https://chromium.googlesource.com/chromium/src/+/main/components/exo/ README 与目录实抓）。

五、输入法框架：统一 IME = Chrome 扩展 API `chrome.input.ime`（现参考页路径 developer.chrome.com/docs/extensions/reference/api/input/ime，标题 browser.input.ime），输入法以扩展形态实现；三形态各设桥——Android 形态在 `chrome/browser/ash/arc/input_method_manager/`：`ArcInputMethodManagerService` + `ArcInputMethodManagerBridgeImpl`（实现 ARC mojom `InputMethodManagerHost`，另有 `arc_input_method_state`、`input_connection_impl`，目录实抓）；Linux 形态在 exo 的 `text_input.{h,cc}`（Wayland text-input 协议）+ `input_method_surface`（候选窗 surface）；Web 形态直接走 Blink 文本栈。统一谓「一套 IME 框架三种桥」，不是一套协议。

六、多窗口与合成：Ash = Aura Shell，窗口管理在 `//ash/wm`；虚拟桌面（Virtual Desks）源码级齐备——`desks_controller`、`desk`、desk 模板（`templates/` 子目录，保存与恢复整桌布局 `desks_restore_util`）、desk 上限常量 `kDeskBarMaxDeskShortcut = 8`（ash/wm/desks/ 目录与 desks_constants.h 实抓）；合成走 viz FrameSink 体系，exo 为 ARC++/Crostini 提供合成路径并自带 occlusion 计算（`desks_window_occlusion_calculator`、exo `window_occlusion_manager`）；多显示器布局由 `ui/display` `DisplayPlacement` 描述（子显示器相对父显示器的边与偏移，display_layout.h 注释实抓）。

七、无障碍：架构三层（Chromium 官方 a11y 文档原文）——renderers（Blink web 内容、ARC++ Android 应用、Aura/Views 系统 UI 树在 Ash 进程内）产出无障碍树并序列化增量更新（`AXNodeData` 稀疏属性数组 + 通用树序列器，offset container + 4×4 矩阵省重序列化）；framework = 扩展 API（公开 `chrome.automation`/`chrome.tts`/`chrome.ttsEngine`，私有 `chrome.accessibilityPrivate`/`chrome.brailleDisplayPrivate`/`chrome.speechRecognitionPrivate`）；feature = 组件扩展（ChromeVox 屏幕阅读器、Switch Access（support.google.com/chromebook/answer/10274137）、语音输入 Dictation（answer/12001244）、字幕（answer/10616170）），系统级 TTS 可执行 googletts 与 espeak-ng、盲文 BRLTTY；关键事实两条：「On Chrome OS, we use our own accessibility API that closely maps to Chrome's internal accessibility API」与「RenderFrameHostImpl 不路由事件到 BrowserAccessibilityManager，因为 Chromium 之外没有平台屏幕阅读器」（https://chromium.googlesource.com/chromium/src/+/lkgr/docs/accessibility/os/how_a11y_works.md 及 overview.md）；ARC++ 无障碍桥在 `chrome/browser/ash/arc/accessibility/`（`arc_accessibility_helper_bridge`、`arc_accessibility_tree_tracker` 把 Android 无障碍树并入 ChromeOS 树，目录实抓）——ChromeOS 无障碍统一是「树统一进 Chromium，AT 全部做成扩展」。

八、主题暗色与动态取色：一手缺位——本轮未定位到 ChromeOS 系统级 dark theme 与壁纸动态取色（Material You dynamic color）的官方一手文档（support.google.com 对应 answer 页未检索到，chromium.org 旧设计文档已 404）；可引的一手仅有 Material 3 体系定义（dynamic color/color roles，https://m3.material.io/develop/web）与 `@material/web` 的 token 化 theming；结论标低置信：机制存在（暗色模式与取色随 Material 3 进入 ChromeOS 设置与 Personalization 面），细则待补一手出处。

九、自适应布局断点折叠多屏：多屏有协议级一手（`DisplayPlacement` 相对布局 + 每显示器独立 mode，ui/display/display_layout.h）；DPI 缩放策略一手缺位（旧版 display scaling 设计文档 404，developer-library 索引为 JS 空页），机制面只能陈述：Wayland 形态经 wl_output scale、ARC++ 经 zcr_remote_shell 的 display metrics 下发缩放，具体 DSF 档位表无官方一手；无折叠屏产品线，自适应=窗口 resize + snap（半屏/四分），断点体系不存在于系统层（Web 应用自担 media query）。

十、国际化与字体：系统 UI 文案走 Chrome i18n（GRIT/.xtb）；输入语言覆盖靠 IME 扩展生态（Google 输入工具）；字体一手缺位——三形态字体栈各不相同（Chrome/Noto、Android/Noto、Linux/fontconfig），系统级字体规范无公开一手，判定为「事实存在、文档缺位」。

十一、性能与掉帧治理：Web/WebUI 走 viz BeginFrame + requestAnimationFrame，DevTools Performance 面板为主治理面（https://developer.chrome.com/docs/devtools）；exo 为 Wayland 客户端自带帧时序治理件——`vsync_timing_manager`（vsync 时序观测）、`frame_timing_history`（客户端帧时延历史）、`event_latency_metrics`（输入延迟度量，components/exo/ 目录实抓）；ARC++/Linux 形态的掉帧治理下沉到各自栈，无跨形态统一帧预算 API。

十二、开发者工具预览热重载调试：Web 形态体验最好——Chrome DevTools 全量可用（live edit、Performance、Lighthouse，developer.chrome.com/docs/devtools 200 实测）；WebUI 是 Web 页面，天然吃 DevTools 与热刷新；扩展（含 IME）调试走 chrome://extensions；键盘优先的开发者文化有官方页背书（键盘总览 support.google.com/chromebook/answer/1047364、快捷键全集 answer/183101、emoji/符号选取器 answer/14156232）；ARC++ 调试沿用 adb 生态，Crostini 直装 Linux 工具链——开发体验以 Web 形态为最优。

十三、设计系统与规范文档：有对外的 Material 3 规范全集（https://m3.material.io：foundation/components/styles/tokens 四部）与 `@material/web` 参考实现；但 ChromeOS 系统 UI（Ash/Views/WebUI）自身无公开设计规范文档，Material 规范与系统实装之间是「参照关系」而非「契约关系」；结合 MWC 维护模式，判定：设计系统文档面强、组件实现面弱。

十四、特色能力：一是三应用形态同 shell——exo 以一个 Wayland display server 把 ARC++ 与 Crostini 都变成 shell 的一等客户端（exo README 原文）；二是虚拟桌面成体系（desk 模板保存/恢复、上限 8、触控板滑切）；三是键盘优先交互文化（Search 键体系、官方快捷键全集页、键盘帮助页）；四是无障碍即扩展（AT 全部组件扩展化，走 automation/tts 私有 API）；五是 Google Play 与 Linux 子系统同机运行。

### Fuchsia 十四维

一、声明式与状态管理：平台不提供 UI 框架——官方 UI 概念页明言「没有单一 UI API，客户端按需实现」（ui-client 文档列出拼装件：`fuchsia.ui.composition.Flatland`、`fuchsia.ui.views.ViewRefFocused`/`Focuser`、`fuchsia.ui.pointer`、`fuchsia.ui.input3.Keyboard`，https://fuchsia.dev/fuchsia-src/concepts/ui/ui-client）；应用层声明式框架 = Flutter（widget 树 + setState 局部刷新，https://docs.flutter.dev/ui/interactivity），无障碍文档原文「view 的客户端 typically Flutter or Chromium」（https://fuchsia.dev/fuchsia-src/concepts/accessibility/accessibility_framework）；Flutter 引擎在 flutter/flutter monorepo 内维护 Fuchsia embedder（engine/src/flutter/shell/platform/fuchsia，https://github.com/flutter/flutter/tree/main/engine/src/flutter/shell/platform/fuchsia，目录 200 实测）。

二、组件丰富度与质量：平台零组件库（concepts/ui 只讲协议，无任何 widget 文档）；组件供给完全来自 Flutter 的 Material/Cupertino 目录；系统 shell（产品化）由产品方用 Flutter 自建；判定：组件丰富度=所绑框架的丰富度，平台自身不背组件质量责任。

三、动画系统：平台侧无服务端动画 API——Flatland 是保留模式场景图，动画在客户端框架（Flutter animation）内插值，平台只保证按 requested_presentation_time 呈现（帧调度机制 present credits/OnNextFrameBegin/latch/squashing 全套见基线 [GUI-05](../../research/GUI-05-微内核OS的GUI架构.md) §1.3 与 [GUI-10](../../research/GUI-10-移动优先渲染深研综合裁决.md)，不重复）；平台级缩放动画能力 = `Flatland.SetScale()`（RFC-0174：浮点缩放、保证无子像素渲染，放大镜即用此，https://fuchsia.dev/fuchsia-src/contribute/governance/rfcs/0174_scale_in_flatland）。

四、手势与输入：输入管线是独立组件 `src/ui/bin/input-pipeline`（src/ui/bin 目录实抓；其作为唯一可直读驱动输入组件、防键盘记录的定位见基线 [GUI-05](../../research/GUI-05-微内核OS的GUI架构.md) §1.6 引 RFC-0096）；指针 API = `fuchsia.ui.pointer`（MouseSource/TouchSource，ui-client 文档列出）；hit test 与焦点链归 Scenic（焦点链机制见基线，焦点语义补一手：focus 概念页——恒有焦点 view、断链失焦父承接、`fuchsia.ui.views.Focuser` 移动焦点、产品自定焦点策略，https://fuchsia.dev/fuchsia-src/concepts/ui/input/focus）；键盘 = `fuchsia.ui.input3.Keyboard.AddListener(view_ref)`，关键语义三条：仅焦点 view 收事件、root→leaf 顺序派发、返回 `KeyEventStatus.HANDLED` 可截断传播，另有 Sync/Cancel 补偿客户端不可用期间的按键状态（keyboard.fidl 实抓，https://fuchsia.googlesource.com/fuchsia/+/refs/heads/main/sdk/fidl/fuchsia.ui.input3/keyboard.fidl）；手势歧义消解在客户端框架（Flutter gesture arena）；a11y manager 自建 gesture arena 拦截手势（见第七维）；输入设备集按产品装配——scene_manager README：structured config 声明 supported_input_devices（产品例 button/touchscreen，测试例 button/keyboard/lightsensor/mouse/touchscreen，https://fuchsia.googlesource.com/fuchsia/+/refs/heads/main/src/ui/bin/scene_manager/ README 实抓）。

五、输入法框架：IME manager 是独立组件 `text_manager`（src/ui/bin/text/README：serves the text editing needs of Fuchsia clients）；对外协议四件——`fuchsia.ui.input.ImeService`（文本消费者第一接触点，`GetInputMethodEditor` 建立双向通道）、`fuchsia.ui.input3.Keyboard`（监听注册）、`fuchsia.ui.input3.KeyEventInjector`（接收 input pipeline 注入的键事件）、`fuchsia.ui.keyboard.focus.Controller`（焦点变化输入）；编辑状态双向协议 = `InputMethodEditor`（manager→消费者，SetKeyboardType/SetState）+ `InputMethodEditorClient`（消费者→manager，DidUpdateState/OnAction），`TextInputState.revision` 序列号防竞态（text_manager.md 与 text_input.fidl 实抓，https://fuchsia.googlesource.com/fuchsia/+/refs/heads/main/src/ui/bin/text/docs/text_manager.md）；负面事实两条：库级标注「DEPRECATED: migration to fuchsia.ui.input3 in progress」（sdk/fidl/fuchsia.ui.input/README.md）与虚拟键盘 `fuchsia.input.virtualkeyboard` 与 ImeService 功能重复待清理（text_manager.md 原文）——平台 IME 框架处于换代未完成态；相关 RFC-0195（text APIs 的位置与区间）在 RFC 索引在列。

六、多窗口与合成：合成器 = Scenic，Gfx（通用 3D 场景图）→ Flatland（2D）重写的动因与协议全套见基线（[GUI-05](../../research/GUI-05-微内核OS的GUI架构.md) §1.1–1.2、[GUI-10](../../research/GUI-10-移动优先渲染深研综合裁决.md)）；View 体系一手补齐——View 是「UI 组织的基本单元」，不经 View 无法上屏，Viewport 承载（常属另一组件的）子 View，全系统一棵全局 View Tree，规则四条：无依赖环、单父、只知自身坐标系、父可经平移/旋转/缩放控制子 viewport 坐标系（https://fuchsia.dev/fuchsia-src/concepts/ui/scenic/views，RFC-0147）；窗口即组件——`fuchsia.element.Manager.ProposeElement()` 提议加元素（session 实现该协议；可挂起不可见元素省资源，FIDL 注释原文），呈现走 `fuchsia.element.GraphicalPresenter.PresentView(ViewSpec)`，ViewSpec 二选一 token：Flatland 视图给 `viewport_creation_token`、Gfx 视图给 `view_holder_token`+`view_ref`，生命周期由 `ViewController.Dismiss()`/`OnPresented()` 事件管理（element_manager.fidl 与 graphical_presenter.fidl 实抓）——窗口管理是产品 session 的事，平台只定 token 语义与提议协议；无虚拟桌面概念。

七、无障碍：a11y manager 是平台独立组件，任何带屏产品都跑（src/ui/a11y/bin/a11y_manager，官方文档原句「Accessibility Manager is a part of the Fuchsia platform and runs on any Fuchsia product with a screen」）；职责面（官方列表）：管理 a11y 设置、实现 semantics API、集成 Scenic 做放大等显示修改、理解 view 与客户端关系、中介输入输出、中介 TTS 等系统服务；语义树协议 = `fuchsia.accessibility.semantics`：运行时注册后以 Update/Delete/Commit 三方法提交语义树，manager 实现服务端；结构性设计：manager 在 view tree 里持有自己的 view（拦截手势、改图、注入输入、参与焦点变化），自建 gesture arena 消解 a11y 手势，「accessibility focus」由 manager 做唯一真相源，高亮由 manager 画；设置经 SetUI 的 `fuchsia.settings.accessibility` 下发并广播给 scenic/运行时；TTS 协议 `fuchsia.accessibility.tts`；特性在列：screen reader、magnifier、color correction/inversion（https://fuchsia.dev/fuchsia-src/concepts/accessibility/accessibility_framework）；Flutter/Chromium 运行时各自把语义树喂给 manager——无障碍与 UI 框架彻底解耦。

八、主题暗色与动态取色：平台无主题系统——fuchsia.dev 概念树无 theme/dark mode/dynamic color 任何页（concepts 索引实抓），色彩仅有的平台事实是 Scenic color spaces（sRGB 等像素格式，https://fuchsia.dev/fuchsia-src/concepts/ui/scenic/color_spaces）；暗色与取色完全是产品 shell（Flutter 侧）的事；判定：此维平台供给为零，BerryOS 若要主题系统必须自建，Fuchsia 无可学。

九、自适应布局断点折叠多屏：DPI 策略一手清晰——RFC-0174 定义逻辑/物理像素术语与 `Flatland.SetScale()`：浮点缩放、保证结果无子像素渲染、Flatland 实例只感知 device pixel ratio（RFC 摘要实抓）；显示度量协议 = `fuchsia.ui.display.singleton.Info`，FIDL 内含 vsync 周期与 VRR 能力类型（`VrrConfig`、`FrameIntervalPowerHint`、`NotifyExpectedPresentConfig`，info.fidl 实抓）——但 singleton 语义面向 Scenic 主显示器，多屏非平台当前重心；无断点/折叠体系，形态适配 = 产品装配期决定输入设备组合（scene_manager structured config）而非运行时断点。

十、国际化与字体：i18n 协议件 = `fuchsia.intl`（`LocaleId` 为 canonicalized BCP-47（含 language/region/script/variant 与 u 扩展），目录含 property_provider/time_zones/calendar，intl.fidl 实抓）+ `fuchsia.fonts.Provider`（`FamilyName`、`TypefaceRequest` 支持关闭 family fallback 与精确样式匹配开关，provider.fidl 实抓）——平台提供「locale 与字体服务」，不提供 UI 层 i18n（无文案框架、无 UI 字体规范，那些属 Flutter/产品）。

十一、性能与掉帧治理：平台帧调度治理全套（present credits 节流、`OnNextFrameBegin` 的 `FuturePresentationInfos` 未来呈现时刻表、latch point、squashing、每 session 独立 dispatcher 的 deadline 渲染线程）见基线不重复（[GUI-05](../../research/GUI-05-微内核OS的GUI架构.md) §1.3、[GUI-10](../../research/GUI-10-移动优先渲染深研综合裁决.md)）；新增一手两件：面板级帧率治理下探——display singleton 暴露 VRR/vsync 周期与功耗提示（info.fidl），观测走 fuchsia.tracing/perfetto（`fuchsia.tracing.perfetto` 在 SDK FIDL 目录在列）；教训面：Gfx→Flatland 重写本身就是性能治理——「API 形态即性能上限」结论见基线 [GUI-10](../../research/GUI-10-移动优先渲染深研综合裁决.md)。

十二、开发者工具预览热重载调试：平台工具面 = ffx 工具族与 Bazel SDK（fuchsia.dev/reference/tools、/reference/bazel_sdk 导航在列）+ 组件级 debug/inspect 诊断体系；输入侧测试一手在 SDK：`fuchsia.ui.test.input`（输入合成）与 `fuchsia.ui.test.scene`（场景装配，SDK FIDL 目录在列）；预览与热重载继承 Flutter 工具链（flutter run 的热重载对 Fuchsia target 的可用性本轮未取得平台一手文档，标待核）；判定：平台原生开发体验面窄，主要红利来自所绑框架的既有工具链。

十三、设计系统与规范文档：无公开设计系统——fuchsia.dev 无任何 design system/token 页；「规范」的形态是协议文档（FIDL 参考、concepts、RFC），即设计契约下沉为协议契约；产品 shell 的设计（如智能屏产品）不公开；对照 ChromeOS（M3 全集对外）与鸿蒙（设计规范官网，见对照系调研），Fuchsia 此维为三家最弱。

十四、特色能力与「选 Flutter 不自研」的教训：特色四件——其一，UI 全栈服务化与能力化：scenic、sysmem、Magma、input-pipeline、text_manager、a11y manager、scene_manager、virtual_keyboard_manager 全是组件，契约全走 FIDL（src/ui/bin 目录与基线 [GUI-05](../../research/GUI-05-微内核OS的GUI架构.md) §1）；其二，分布式全局 View Tree：跨组件 view 嵌合只靠 token 对（`ViewportCreationToken`/`ViewCreationToken`，Gfx 旧制 `ViewHolderToken`/`ViewToken` 并存，glossary 与 views 文档），中心服务不知道内容只管拓扑与 hit test——结构性地防 clickjacking（基线已证）；其三，提议式窗口管理（fuchsia.element 的 ProposeElement/PresentView/annotations，含 persist_element 跨重启持久化标注）；其四，a11y 与 IME 同为平台独立组件、与 UI 框架解耦（第七、五维）。教训三条：第一，Google 在预算无约束的新 OS 上仍未自研应用 UI 框架，而是把 Flutter 立为一等公民（引擎内维护 Fuchsia embedder + 平台文档「typically Flutter or Chromium」）——理由即 ui-client 文档的结构：平台只需把合成/输入/焦点/文本/语义做成协议，框架生态（组件、工具、热重载、设计规范）全部外包给现成框架；第二，平台 API 换代的代价可量化——fuchsia.ui.input → fuchsia.ui.input3 迁移以年计且未收尾（README 的 DEPRECATED 标注与 text_manager 内新旧协议并存是直接证据）；第三，自研「系统 UI 框架/外壳框架」的两波尝试（Modular/session framework 时代的 shell 组件）已收敛为薄件——当前 src/ui/bin 里只剩 scene_manager（`fuchsia.session.scene.Manager`：建场景图、装输入管线、设 root view、聚焦）与 tiling_wm 等极简组件，session 框架 RFC（RFC-0092/0194）仍在索引但概念树已无 session 章节——「shell 交给产品，平台不背 shell 框架」是被执行过的裁决。
