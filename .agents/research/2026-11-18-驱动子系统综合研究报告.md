## 一、现状盘点

### 1.1 总体架构

BerryOS 是微内核路线（ADR #12「驱动用户态为主，启动关键暂留内核」）：virtio 全家族跑在用户态常驻服务进程里，通过 boot 期手铸的 MMIO 窗 VMO 访问设备、用 VMO 机制做 DMA、经 channel RPC 对外提供服务；内核只留 GIC/定时器/UART/console 等 boot 关键件。当前没有统一 bus/device/driver 抽象——设备发现靠驱动自扫 MMIO 槽，启动靠 svcmgr（用户态 init，9017 行）点名拉起（2026-11-20 波 1 补：统一 Driver 生命周期 trait 已落 [berry-driver](../notes/implemented/2026-11-20-berry-driver统一Driver-trait框架crate.md)，bus/device 抽象仍缺，devmgr 仅观察半边 v1 在席——见 §4.2 交付 1.1）；devmgr（DTB 枚举 → 资源池 → 匹配 → 授权 → `/svc` 注册）是 v2 设计，已在 [驱动模型设计-v1.0.md](../../docs/驱动模型设计-v1.0.md)（ADR #46）立法。

`drivers/` 是独立 cargo workspace（2026-10-24 自 `user/` 迁入），成员 5 个；virtio-gpu 驱动另有 1 个住在 `user/bins/guifbd`。`drivers/bins/vgpud` 在库但不在 members、未入产线（见 §4.1）。

**berry-virtio（框架库）**遵循「解析器即产品」纪律：只管内存里的字节长什么样，volatile MMIO 读写一律留驱动本体。内容涵盖 split virtqueue 布局（`RingLayout`：qsize 幂次校验、desc/avail/used 单页内偏移计算，全链 ≤4KiB 的单页承诺）、描述符编码 `put_desc`/发布 `publish`/收割 `used_idx`/`used_ent`（自由运行 u16 idx、环绕 65536）、特性位常量（VERSION_1、INDIRECT_DESC、NET_F_MAC、NET_F_MRG_RXBUF）、virtio-blk 16B 请求头、virtio-mmio v2 寄存器偏移表（0x00–0x100 冻结值）与设备 ID 族（blk=2/net=1/input=18/gpu=16，GPU 数值单源在 berry-gpuproto，跨 crate 断言互证）、input 模块（8B 事件编解码、evdev 常量表冻结自 linux/input-event-codes.h——含 KEY_RIGHTCTRL=97 与 'a' 码域碰撞钉板、136B config 查询区 devids 恰 8B/absinfo 恰 20B 恰长执法、LSB-first 位图）。host 单测 26 个（tests/layout.rs 14 + input 内联 12）。

**vprobe（探针）**扫 32 槽 × 0x200 窗验 magic="virt"、占用槽须 ver=2（拒 legacy）；按设备类计数：block 须恰一，net/input/gpu 合法同席（各由消费者自认领），未知 did 走 loud trap。成功打 `VIRTIO ok did=… slot=N`（smoke 标记）后即退。

**vblk（块设备服务）**实现完整 modern 协商序（STATUS=0 复位回读 → ACK|DRIVER → FEATURES_OK 回读验 → 建队列 → DRIVER_OK）；qsize=16 整环落一页；启动自验 LBA0 魔数读 + LBA1 写读回对拍（`VBLK ok`），随后常驻服务循环（`BLKD ok`）。协议为 berry-blkproto 严格串行 RPC（请求 9B + 1 枚 VMO 随行、应答 1B），数据面 bounce-buffer（client VMO 别名经 vmo_read/vmo_write 搬运）。单设备单主人是 v1 文档化缺口：第二个持窗实例的 STATUS=0 复位会掀翻在役队列，现行靠「窗口能力不出 svcmgr 表」兜底。

**vnet（网络服务）**采用双队列（rx q0 + tx q1）+ rx 单描述符缓冲几何（12B mrg 头 + 帧同缓冲；链式拆分需 32 desc > qsize，单 desc 是几何结论）；协商 MAC+MRG_RXBUF+VERSION_1——MRG_RXBUF 必须：QEMU vnet_hdr 按 12B 剥头，只组 10B 头即帧被斩 2B、SLIRP 静默丢弃（filter-dump 实证）。自验链为 ARP 解网关 → ICMP echo 32B 往返（`NET ok ping=32`）→ DNS 代查（`DNS ok`）→ TCP 回显挥手（`TCP ok echo=64`）→ 服务端会话表 TcpMux（LISTEN/ACCEPT/POLL + hostfwd 回环入站自验 `LSN ok n=7`）。常驻服务走 berry-netdproto 4 op（DNS_QUERY/TCP_OPEN/ROUNDTRIP/CLOSE），rx 缓冲收割即回填。tcp.rs 与 berry-tcp（纯状态机，638 行）分工「IO 归驱动、状态归协议 crate」。

**gui-inputd（输入服务）**按设备类分类认领：指针类（EV_BITS(EV_ABS) 位图 ABS_X+ABS_Y 双位在场 = virtio-tablet）恰一台 + 键盘类（绝对轴缺席 = virtio-keyboard）至多一台；ABS_INFO 读校准域（以设备自述为准，勿硬编 32767）；eventq always-posted 16×8B 预投 + SYN_REPORT 关批泵；lib 侧纯函数面（wire 适配 → 归一化 → PointerPump 状态机：DOWN/MOVE/UP/CANCEL、history 采样配对、SYN_DROPPED 合成取消、键盘 US 布局翻译表）；对外 berry-guiproto INPUT_SUBSCRIBE/INPUT_POLL，并监窗口管理器 wmd 推送通道做命中测试旁注。设备缺席走优雅退出（诊断 + park 不 trap，与 vnet 的 trap 面分工明确）。

**guifbd vgpu 后端（virtio-gpu 2D）**扫窗找 did=16；控制队列 q0（cursor q1 留位）；berry-gpuproto 九命令（GET_DISPLAY_INFO / RESOURCE_CREATE_2D / UNREF / SET_SCANOUT / RESOURCE_FLUSH / TRANSFER_TO_HOST_2D / ATTACH_BACKING / DETACH_BACKING / UPDATE_CURSOR）；INDIRECT 描述符首用——ATTACH_BACKING 的 mem_entry 表可达 8KB，超单页环预算，间接表把链挪出 ring 页；帧提交 = CPU blit 落 fb 后 TRANSFER+FLUSH 钩子；ramfb 红线：无 virtio-gpu 设备时现役行为逐字节不变（fw_cfg `etc/ramfb` 后备）。`FB ok vgpu` 为 smoke 标记。

### 1.4 驱动注册与总线模型

现状（v1）无统一 bus/device/driver 抽象，链路是手搭的三步：其一，内核 boot 期 `Vmo::create_mmio(0x0A00_0000, 0x4000)` 铸出 virtio-mmio 整窗（32 槽 × 0x200）MMIO 窗 VMO，插进 svcmgr handle 表（第 4 插 0x0001_0004，R|W|MAP）；GUI 起再加 fb 窗 VMO + 几何 info VMO；`create_mmio` 是 boot-only 原语（Zircon `zx_vmo_create_physical` 的收紧版，EL0 永不可自造物理窗口）。其二，svcmgr boot 期按 cpio 名单点名预拉驱动：`spawn_rootfs_elf` + `SpawnSpec { mmio_vmo: Some(H_MMIO), mmio_va: VIRTIO_MMIO_VA }` 把窗映进驱动地址空间，同时建 channel_pair，服务端端点随 env 块 gift[2]/extras 迁入驱动。其三，设备发现 = 驱动自己扫 32 槽读 did 按类认领（QEMU 总线排布随 -device 顺序漂移，绑死槽号被明确拒绝）。

终态设计（v2，已立法未实现）：驱动 = 持证应用（同一 .bap 包 + manifest `type=driver` + `[hw] match` 键 DT compatible/PCI ID + `[capabilities] mmio/irq/dma`）；devmgr（svcmgr 家族演化的普通服务）持设备资源池做五件事：枚举（DTB/ACPI）→ 匹配（认领即独占，收口 v1 单设备单主人缺口）→ 授权三铸件（MMIO 窗 VMO / IRQ→channel 转发 / IOMMU DMA 圈）→ 注册 `/svc` 命名空间 → 导出机器可读设备任务书。装卸/崩溃/热换全走 appd 应用链 + DEAD 代号（ADR #28）。现行 boot 手铸窗被官方称作「devmgr 的手工前身」。

### 1.5 中断处理

IRQ 分发 = [trap.rs](../../arch/aarch64/src/trap.rs) 的 `exception_irq` 硬编码 INTID match（无通用 IRQ 注册表，HAL 用函数指针槽把调度/唤醒回调反转给内核）：

```
acknowledge() 读 IAR → match INTID {
  27 (CNTV)      → timer::handle() 重编程（去活电平）→ EOIR → 调度 tick 槽
  33 (PL011 RX)  → uart::rx_irq drain 到 RXFE（去活）→ EOIR → 唤醒则抢占检查点
  40 (UART1 RX)  → 同 33 形
  39 (PL061)     → power_key_irq（ICR 清锁存 pre-EOI）→ EOIR
  SGI 1 (resched)   → EOIR → 计数 → 重调度槽
  SGI 2 (TLB shoot) → EOIR → 本地全量失效 + 回执
  未知 → EOIR + 首 4 个 loud（`irq? id=N`）后静默
}
```

核心纪律（plan Bug 1 教训立法）：ack → 去活电平 → EOIR → dispatch/switch——switch 类工作绝不在 ack↔EOIR 之间，否则 GIC 里中断保持 active、EOIR 饿死（SMP 下被偷核则永久化）；电平触发的三源（CNTV/PL011/PL061）各有 pre-EOI 去活铁序。

用户态驱动零中断：GIC 从不使能任何 virtio SPI；vblk/vnet 轮询 used ring（10s 帽 + 1ms 绝对 deadline 睡步进），gui-inputd 1ms 泵步进 + `wait_many` 心跳重臂（空闲心跳 100ms 量级）；INT_STATUS 读 + ACK 只是整洁面。IRQ→channel 转发原语（Interrupt 对象）v1 未实现，语义设计已在 [IPC设计-v1.0.md](../../docs/IPC设计-v1.0.md) §3 在册——这是用户态驱动「能跑但费电、真机不可接受」的已知头号缺口。

唤醒归因链（PM 刀 1）三层且 host 可测钉板：wakeface（179 行，INTID→唤醒源纯函数）+ wsrcface（294 行，源分类/进环判定）+ wake.rs（137 行，per-CPU 语境 cell + 到达计数）。

### 1.6 设备树（dtbface）

dtbface crate（404 行）是最小 FDT（flattened device tree）walker 纯函数面：原语 `rd32`（大端界检读）、`cstr_at`（NUL 串定位）、`prop_u64`（1/2 cell 值）、4 对齐步进；唯一用途是 `find_initrd`——迭代 walk（不递归防深嵌套炸栈）找根直接子节点 `/chosen` 的 `linux,initrd-start/end` 物理区间；纪律是纯函数零 panic，畸形（坏魔数/越界/截断/未知 token）九态全 `None`，boot 侧降级为「无 initrd」存活。消费方式上 [dtb.rs](../../kernel/src/dtb.rs)（50 行）只留物理臂 `boot_probe`——入口 x0 的 DTB PA 界检 `[RAM_BASE, RAM_TOP)` → 高半直映切片 → find_initrd。重要现实：QEMU 非 Linux ELF `-kernel` 直加载不走 boot 协议（x0=0、RAM 无 DTB），rootfs 实际走 fw_cfg 通道；DTB 路是真机/Linux 协议留位。目前没有用 DTB 做设备枚举——GIC/UART/PL061 的 IRQ 号与触发方式是从 QEMU 自产 DTB（dumpdtb）人工抄录成常量的（gic.rs 注释「DTB 实证」多处可溯），DTB 枚举设备池属于 v2 devmgr 计划。

### 1.7 DMA 与内存

DMA = 纯 VMO 机制，是微内核纪律的完整演示（vblk 为标杆）：其一，`vmo_create(VMO_OPT_CONTIGUOUS | VMO_OPT_PINNED, len)` 物理连续 + 钉死（禁 decommit），F0-4 落地；其二，DMA VMO 从不进任何地址空间——无映射即无清理面，环构造/收割全走 `vmo_read`/`vmo_write`（内核高半直映搬数）；其三，`vmo_get_phys`（syscall 0x1B）查页后备 PA 填描述符——qsize=16 单页几何下无跨页连续性需求（帧分配器无连续保证也无碍）；其四，`vmo_cache_op`（syscall 0x1C）PoC 数据缓存维护，vblk/vnet 已在用（发布前 `VMO_CACHE_OP_CLEAN` 环+缓冲、收割前 `VMO_CACHE_OP_INVALIDATE` used.idx/status/数据）；其五，门铃前 `dmb ish`（berry-virtio `publish()` 调用方契约）。

IOMMU：无。ADR #22 立「IOMMU/SMMU 头等设计」（用户态驱动 DMA 经 SMMU 限定在授权 VMO 区间）但未实现；vblk 头注诚实记录「v1 无 IOMMU 板上 PA 披露 = 已授 MMIO 窗口的设备本可 DMA 全内存，v1 接受并文档化」。MMIO 窗 VMO 本身 commit/read/write 一律拒、只许 volatile 经映射访问（Device-nGnRnE + SH_NONE 属性）。真机缺口（诚实面）：gui-inputd 与 guifbd vgpu 尚未用 `vmo_cache_op`（TCG 无 cache 模型天然一致）；cache 维护 DMA API 的完整收口挂 v2。

### 1.8 电源管理

PM 子系统分四层，成熟度差异极大。第一层内核侧（在役）：tickless idle（空闲核 mask + wfi，无周期中断，「续航第一杠杆 day-one」）；PSCI 探测 + SYSTEM_SUSPEND 深睡 HVC（sim-S3 仿真断言；TCG 返不支持即诚实降级）+ SYSTEM_OFF（syscall `NR_POWER_OFF` 0x88，成功不归）；PL061 电源键无主 IRQ 台账；冻结令牌 `SuspendTok`（`process_suspend` 持有即冻结、close 即解冻、深度嵌套、wake_pending 唤醒即解冻）；唤醒归因链（见 1.5）。第二层用户态策略服务（骨架，大量留窗）：berry-power（7 文件 2325 行，频率帽聚合/充电限流票/EAS 四动作 hint 经 `policy_bind` 提交——真实通道多未接线，当前形态 = 起机自检 + park 常驻）、berry-thermal（946 行，step_wise + 迟滞仲裁引擎纯面已测，输入订阅/三类输出写面全部留窗）、simbattery（204 行，sim 帧通道消费）。第三层设备电源态（suspend/resume per-device）：无——没有驱动级 .suspend/.resume 回调面，「挂起停钟 + SLEPT 双钟」立法在 ADR #66 L2。第四层设计文档：[PM仿真S2断言实施设计](../../docs/PM仿真S2断言实施设计-v1.0.md)、[PM仿真S3断言实施设计](../../docs/PM仿真S3断言实施设计-v1.0.md)、ADR #66–#68 立法三件。

### 1.9 内核接口：userland 怎么访问设备

无 /dev、无 devfs、无 sysfs（fsmgr 里那行 `/dev/root / fat rw 0 0` 是 FAT mtab 的兼容化妆字符串，不是设备树）。设备 = 服务：每个驱动是常驻进程，boot 期 svcmgr 建 channel_pair，端点随 env 块 gift 迁移给驱动/客户端；此后消费方（fsmgr/svcmgr/应用）持 handle 走严格串行 RPC；大块数据不走消息走 VMO 随行迁移（channel inline 帽 256B < 512B 扇区——能力而非拷贝）。协议 crate 家族（L2 层，wire add-only 冻结）：berry-blkproto（块：9B 请求 + VMO 随行）、berry-netdproto（DNS + TCP 三 op）、berry-guiproto（submit/frame_callback/release + INPUT_SUBSCRIBE/POLL，6514 行）、berry-fsproto、berry-pwproto、berry-netproto（以太网/ARP/IP/ICMP/DNS 编解码）。控制台键盘 = 内核 console 服务（P4-5a，v1 留内核任务形态的「首个服务循环」）经 channel 转 bsh；GUI 输入 = gui-inputd。网络衔接链（代码注释自证）：应用（含未修改的 `std::net`）→ berry-libc/src/net.rs POSIX socket 面 → berry-netdproto RPC → vnet 进程内 berry-tcp 状态机 → virtio-net DMA。

syscall 面（[系统调用ABI设计-v1.0.md](../../docs/系统调用ABI设计-v1.0.md)，单源 [abi.toml](../../tools/abi.toml) 生成）：v1 40 号在册、39 号实现（唯 0x85 attest 恒 -ENOTSUP）。与设备相关：handle 三操作（权限在 handle rights 12 位不在对象）、channel send/recv/create、event + `wait_one`/`wait_many`、VMO 十一号（create/commit/decommit/read/write/get_size/get_phys/cache_op/pager 族）、vmar map/protect/unmap、`clock_read`（MONOTONIC/REALTIME）、`thread_sleep`、`power_off`、sched attr/util snapshot；未知编号一律 -ENOTSUP 存活不 panic。`/svc` 命名空间（`/svc/disk/blk0` 形态）= v2 devmgr 设计位；现役等价物 = svcmgr 表里的裸 handle。

## 二、架构对照

### 2.1 三家模型速写

**Linux：单内核 + 动态总线模型（运行时匹配的巨机器）。**核心是 `bus_type`/`device`/`device_driver` 三角：总线下挂设备与驱动两个链表，注册任意一方时用 `bus->match()`（背后是 `of_match_table`（设备树 compatible 串）、`acpi_match_table`、`i2c_device_id`/`pci_device_id` 表）双向撮合，命中即回调 `driver->probe(dev)`，分离时 `remove()`。生命周期由 Kobject/refcount 驱动；`devm_*`（devres）把资源生命周期绑到 device 对象上——probe 里 `devm_ioremap`/`devm_kzalloc`，unbind 时自动逆序释放。`.ko` 模块可运行时加载（`module_init`/`module_device_table`），热插拔链路 = 内核发 uevent（`MODALIAS` 环境变量）→ udevd 收 → `modprobe` 匹配装载 → probe；sysfs 是整棵设备树的只读导出面。弱点正是 BerryOS 设计文档点名的病灶：.ko 与内核版本/符号 CRC 锁死，驱动崩溃 = 整机 oops。

**Zephyr：静态链接 + 描述驱动的编译期模型（[官方 Device Driver Model](https://docs.zephyrproject.org/latest/kernel/drivers/index.html)）。**链路是「devicetree + YAML binding → Kconfig 门控 → 编译期实例化」：板级 DTS 描述硬件，binding 约束属性语法，Kconfig 决定驱动是否编入；构建系统生成 `devicetree.h` 宏，驱动用 `DT_DRV_COMPAT` + `DEVICE_DT_INST_DEFINE(inst, init, pm, data, config, level, prio, api)` 在编译期生成设备实例。`struct device` 四件套：`name`/`config`（ROM，来自 DT 的只读参数：MMIO 地址、IRQ 号）/`api`（函数指针表，子系统多态）/`data`（RAM，每实例运行态）；取实例用 `DEVICE_DT_GET(node_id)`。init 分层定序：`PRE_KERNEL_1`（无依赖、跑在中断栈、可用 IRQ 不可用内核服务）→ `PRE_KERNEL_2` → `POST_KERNEL`（内核主任务上下文）→ `APPLICATION`，层内 0–999 优先级，靠链接段排序静态展开（`west build -t initlevels` 可检查）；`zephyr,deferred-init` 属性可延迟到运行时 `device_init()`。中断静态注册：`IRQ_CONNECT` 展开为 ISR 声明进链接段，`IRQ_DIRECT_CONNECT` 直挂向量表，`irq_connect_dynamic()` 走运行时；多实例驱动靠 per-instance `config_func` 解决 IRQ 参数编译期常量问题。PM（[官方 Device Power Management](https://docs.zephyrproject.org/latest/services/pm/device.html)）是一等公民：驱动注册 `pm_device_action_cb`（SUSPEND/RESUME/TURN_OFF/TURN_ON 四动作），运行时 PM 用引用计数（`pm_device_runtime_get/put`），系统 PM 按初始化逆序挂起设备、`pm_device_busy_set` 保护事务中设备、`wakeup-source` 声明唤醒源、电源域本身也是设备。没有运行时模块加载——整镜像静态链接。

**Redox：微内核 + scheme 模型（[官方 book：Drivers](https://doc.redox-os.org/book/drivers.html) / [Schemes](https://doc.redox-os.org/book/schemes.html)）。**驱动是普通用户态守护进程，每个进程持受限 scheme 命名空间（「驱动看不到别的系统接口」）；scheme 取名自 URI scheme：既是资源类型、又是路径根、又是唯一命名服务——`disk.*`（ided/ahcid/nvmed）、`network`（e1000d/rtl8168d）、`input`（inputd）、`display.vesa`/`display.virtio-gpu`、`file`（redoxfs）。内核只留一小撮 kernel scheme 兜底，其中三个正是「用户态驱动直通硬件」的枢纽：`irq:`（把中断转成消息——驱动 `open("irq:N")` 后 `read` 阻塞等中断到来）、`memory:`（`fmap` 物理地址——MMIO 寄存器与帧缓冲的用户态映射即由此来，DMA 缓冲同理）、`event:`（epoll 式多路等待）。两点诚实面：其一，实际命名是 `disk.*`/`network`/`input`（无尾冒号变体）；其二，Redox 的 DMA/MMIO 直通是软隔离——`memory:` fmap 拿到的是裸物理地址，靠进程命名空间约束而非 IOMMU 硬执法，持有窗口的设备本可 DMA 全内存。PS/2 `serio` 因协议时序问题留在内核，是它自己的「boot 豁免清单」。

### 2.3 BerryOS 的定位判断

先校准定位：仓库实际定位（README/ADR #39）是产品向微内核 OS（省电优先/能力安全/AI 原生，手表 → 手机 → PC），教学是它的第二重可兑付价值；两个定位指向同一结论——BerryOS 已选择且应当坚持 Redox/Fuchsia 同族的用户态驱动模型，与三重属性全部对齐：微内核纪律（no_std 极小内核，内核只留调度/IPC/地址空间/能力派发，驱动进内核就直接违宪 ADR #12，Linux 模型第一个出局）；Rust + no_std 用户空间（驱动即普通 musl 静态二进制，复用全部应用工具链 mkapp/appd/smoke，没有 .ko 式版本地狱，正是 Linux 病根的结构解）；教学定位（三家可教性各有最强项——Zephyr 最适合教「设备描述如何变成实例」、Linux 最适合教动态生态、Redox/BerryOS 最适合教隔离与能力；BerryOS 教第三课且比 Redox 更严谨——能力 handle 而非裸 FD + 命名空间，学生写一个 .bap 就是一个驱动）。

单内核 vs 微内核 vs 混合的回答：BerryOS 目前是纯微内核 + 少量诚实豁免的实用主义形态，不是混合内核——混合内核如 XNU/NT 是把驱动/FS 常驻内核只是 IPC 快；BerryOS 的 GIC/timer/UART/console 豁免是「拉起别人之前就要用的」最小集，且有逐版外提纪律与「只减不增」裁决 Q11。规划中的 SMMUv3 + Interrupt 对象（hal 2.0）若落地，硬件资源授权面将比 Redox 的 `memory:`/`irq:` scheme 更硬（软命名空间隔离 → IOMMU 硬执法）。

### 2.4 适配建议：从每家各借一件，不借什么

**从 Linux 借三件「形状」，不借「住址」**：其一，bus 抽象的极小化身——devmgr v2 的 match 键要同时容纳 DT 与 PCI 两种来源（`dt:`/`pci:` 前缀），这正是 Linux `bus_type` 的存在理由；建议 devmgr 内部把「枚举器（DT walker/未来 PCI 枚举器）→ 统一设备记录 → 匹配表」分层，匹配语义单源，新增总线只扩枚举器。其二，deferred probe 的思想——Linux `-EPROBE_DEFER` 允许驱动因依赖（时钟/GPIO）未就绪而挂起重试；映射到 devmgr：驱动认领设备但依赖服务（如 IOMMU 域）未就绪时，设备回池、驱动挂起待重匹配，避免引入「就绪序」的隐式全局知识。其三，uevent 的「设备事件导出」思想——设备出现/消失/被认领应是可订阅事件（推给 appd、诊断面、AI 活儿清单），实现上是设备任务书导出面的增量，不引入 udev 级用户态策略引擎。不借：.ko 模块格式与运行时模块装载（ADR #46 已立法拒绝，正确——版本锁死与签名面复杂度对教学与安全双输）；sysfs 的全量对象树（`/svc` + 任务书已覆盖教学观察需求）。

**从 Zephyr 借两件「纪律」，不借「形态」**：其一，init 优先级分层 → devmgr 拉起序的显式化——Zephyr 分层本质是「依赖拓扑的静态编码」，BerryOS 的等价物不应是链接段（用户态服务没有共享镜像），而是 manifest 声明的启动层级/依赖：建议给驱动 .bap 定 `level = core/storage/ui` 式三档（console/存储先于输入/显示），把「谁先起来」从 svcmgr 手铸表变成声明式数据，同时是教学叙事增量（启动序可见、可断言）。其二，PM device 四动作 + runtime 引用计数——SUSPEND/RESUME/TURN_OFF/TURN_ON 动作模型与 `pm_device_runtime_get/put` 引用计数是「省电优先」支柱在驱动面的最成熟先例；映射：补齐动作语义（四动词而非仅档位）与消费者侧引用计数（fsmgr 持块设备引用期间不许降档）——`pm_device_busy_set` 的「事务中不许挂起」正是 vblk/FAT 写路径原子性的电源面对应物。不借：编译期静态实例化整套形态（DT 宏展开、链接段排序，成立前提是单镜像固件，与用户态驱动模型相斥）；但 `config(ROM)/data(RAM)` 的「只读参数与运行态分离」值得在驱动 crate 结构里沿用（berry-virtio 纯函数面已是同款纪律）。

**从 Redox 借一件「先例确认」+ 一件「反面教材」**：先例确认——`irq:` scheme（中断→消息）与 `memory:` fmap（MMIO 物理映射）证明「内核只做转发原语、驱动住用户态」在 Rust 全栈可工程化；BerryOS 的 Interrupt 对象 + MMIO 窗 VMO 是同一拓扑的更强版（能力化 + Drop 自愈 + Split-EOI 免中断风暴），hal 2.0 的验收指标（静置 10 秒外设轮询唤醒计数为 0）应保持一等 smoke 断言，这是对 Redox 软隔离路线的代差优势，别在实现中退化回轮询。反面教材——Redox 的 DMA 直通无 IOMMU 执法，隔离停在命名空间层；BerryOS 已用 ADR #22 + SMMUv3 规划避开此坑，要守住「无 IOMMU 板诚实披露」与 cage 隔离档位，不要让「QEMU virt 默认无 SMMU」的便利把披露面变成常态；另外 Redox 的 scheme 名提醒 `/svc` 词表要一次定好层级（`/svc/disk/blk0` 现役形态已比 Redox 扁平名更有结构），避免 Redox 式 `disk.usb-{id}+{port}-scsi` 在名字里编码拓扑。

落到刀序（与既有 v2 计划对齐，不新开方向）：devmgr v2 + 莓核 2.0 hal（Interrupt/SMMUv3）已覆盖上述大半；本对照给出的增量只有四件小刀——match 键的枚举器分层（Linux 形状）、manifest 启动层级声明（Zephyr 形状）、PM 四动作动词 + 消费者引用计数（Zephyr 形状）、设备事件订阅面（Linux uevent 形状），四件都是既有面上的增项，不推翻任何现行 ADR。

## 三、缺口分析

### 3.1 缺口清单（按影响排序）

**P0-1 virtio 中断面整体缺失（全系统 poll 模型）——最大的结构性缺口。**vblk/vnet/gui-inputd 头注均自认「GIC 从不使能 virtio SPI，poll used ring（10s 帽 + 1ms 睡步进）」；gui-inputd 更明确「离散转移零丢的结构性根治 = v2 IRQ 面」。后果有三：输入事件有丢批窗口——eventq 仅 16×8B 预投缓冲，空闲 tick 100ms 内超过 16 事件即被设备静默丢弃（press 送达 release 丢弃 → 接触态滞留）；所有 I/O 延迟下限 = 轮询步进（活跃 1ms/空闲心跳 100ms 量级），CPU 白烧在轮询上；GICv2 驱动和中断框架其实已在内核在役（IRQ27 timer、IRQ33 PL011、IRQ39 PL061），缺的只是「把 virtio SPI 路由给用户态驱动」的机制（如 IRQ→channel 通知桥）。性能课、输入课、交互流畅度全部受制于此，这是「教学 OS」与「真实驱动工程」之间最宽的一条沟。

**P0-2 块设备栈太浅：无分区表解析，FAT12-only，单盘单在途。**无 GPT/MBR：fsmgr/src/fat.rs 的卷定位是约定式探测——在 {LBA0, LBA16} 里试 BPB 签名 + `hidden` 字段对账（mkfat 造的卷恒在 LBA16），报告时点全仓无分区表解析器。**已落地（berry-partition + vblk 启动分区探测，波 1，2026-11-20）**：GPT/MBR 双格式解析器清偿第一断层（no_std 纯函数 crate、读盘闭包注入、18 测，见[单件笔记](../notes/implemented/2026-11-20-berry-partition分区表解析crate.md)）；vblk 启动序已接探测刀——自验后经读盘闭包跑 `berry_partition::parse`，分区布局打一行日志、解析失败或空表按整盘服务不杀链（见[单件笔记](../notes/implemented/2026-11-20-vblk接入berry-partition启动分区探测.md)）；fsmgr `first_lba` 定卷与 vblk 多分区 RPC 暴露留后续刀，FAT12-only 与单盘单在途断层未动。文件系统 = FAT12 only：8.3 大写名 staging；MKDIR/UNLINK 纯 RAM 面（FAT 建删目录「不在 C-0 盒」）；FAT 文件删除明确「留 v2」；ext2/FAT32 无。单盘假设：vblk 扫 32 槽定位唯一 block 设备，只认 did==block 恰一——第二块盘没有消费者。性能形态失真：严格串行 RPC（一请求一应答、单在途）+ bounce-buffer 双拷贝 + qsize=16；smoke 盘 1MiB。学生做不了「分区 → 格式化 → 多文件系统对照」这条最经典的存储实验线，IOPS 数字不代表真实块驱动。

**P0-3 网络栈「单会话回显形」——驱动与协议栈的衔接存在人为天花板。**衔接本身是通的且设计不差（std::net 可直接跑），但 berry-libc/src/net.rs 的「v1 语义裁定」自认硬限制：connect 目标恒钉死 SLIRP 网关 10.0.2.2（协议无出站地址域，`sin_addr` 非网关直接 ENETUNREACH，学生连不了任何真实服务器）；系统同时至多一个客户端会话（session-0 独占，二连 EIO）；无 UDP socket 面（UDP 仅 vnet 内部 DNS 用）、无 IPv6、无 DHCP（guest 地址 10.0.2.15 硬编码）；berry-tcp 本身 MSS=128、固定窗口 1024、Go-Back-N、无滑窗（教学级最小实现，文档已诚实定位）；驱动侧同样单设备假设。所有「真实网络应用」实验（HTTP 客户端、并发下载、UDP 广播）在驱动-协议衔接层就被挡死，只能做宿主回显对拍。

**P0-4 真机验证路径为零，「真机就绪度」缺口已自我立案。**仅支持 QEMU `virt` 板（AArch64 TCG/MTTCG）+ x86_64 最小集冒烟（smoke-x86.sh），无任何真实硬件目标。两项已文档化的真机阻断项（vblk 头注「诚实缺口」）：DMA cache 维护缺失（无 `dc cvac`/`dc ivac`——TCG 无 cache 模型恒绿，真机上设备取陈旧数据，留待 v2 DMA API）；无 IOMMU/SMMU（持 MMIO 窗的设备可 DMA 全部物理内存，ABI 注记自认）。「移植到真机」这门课没有起点；安全模型教学上 IOMMU 缺席是明显反例。

**P1-5 显示：无真 GPU 加速路径，应用渲染全 CPU。**virtio-gpu 后端（guifbd）只用 2D 命令集（GET_DISPLAY_INFO → RESOURCE_CREATE_2D → ATTACH_BACKING → SET_SCANOUT + 全帧 TRANSFER_TO_HOST_2D + FLUSH），无 3D/capset（Venus）、无光标平面；应用侧 berry-gfx 是纯 CPU soft 光栅（fill/line/blit/glyph），设计良好的 WebGPU 式 API 但无硬件后端，VMO-backed 纹理「留位后续刀」；帧缓冲到用户态路径 = 应用经 berry-guiproto（OP_SUBMIT 等）提交给 guifbd 集中 CPU blit 合成——无应用直扫、无 page-flip 原子模式（vblank 面 OP_REG_VBLANK/VBLANK_WAIT 已有）。图形课停在软件渲染；dirty-rect 已有首载体（2026-11-17 波3批B 带合成 v1——surface 六档分类、带缓存、damage 域重放，见[单件笔记](../notes/implemented/2026-11-17-波3批B-guifbd带合成v1与wm面收线.md)），硬件合成/双缓冲仍无载体。

**P1-6 输入：多点触控只有「留位」。**berry-virtio/src/input.rs 已定义 `ABS_MT_SLOT`、`SYN_MT_REPORT` 等常量但注释明言「v1 忽略计数——多点留位」；单指 + 键盘在役；空闲丢批问题（P0-1）在输入面伤害最大。

**P1-7 RTC 无设备驱动（fw_cfg 注入替代）。**kernel/src/rtc.rs 开头自认「本仓无 RTC 设备驱动（QEMU virt 亦未挂 goldfish-rtc）」，现役方案 = 宿主启动时把 epoch 秒经 fw_cfg 具名文件注入，内核单次消费换算 REALTIME。**用户态消费面已落地（berry-rtc，波 2，2026-11-20）**：公共消费 crate——epoch 单源读数经 `CLOCK_REALTIME` + 简化儒略日历法换算 `hhmmss_utc`/`ymd_utc`（Python datetime 对拍 4 测，见[单件笔记](../notes/implemented/2026-11-20-rtc消费面与看门狗骨架双crate.md)），launcher/appshell 自持换算迁单源留后续刀；设备驱动本体（goldfish/PL031）仍未动。时区换算「挂账波二」；精度 = TCG boot 秒级漂移，不注入则 REALTIME 直接 -ENOTSUP。

**P1-8 传感器/电池/热全为模拟通道，无总线驱动。**simbattery（fw_cfg 门控的 UART1 模拟帧 + pwproto）、berry-thermal（输入订阅/三类输出写面全部留窗）、berry-power（真实接线全留窗）——服务框架在、设备面零接线；无 I2C/SPI/GPIO 总线驱动（PL061 仅服务内核电源键且 v1 无消费面），任何真传感器都接不进来。

**P1-9 外部存储总线全空。**USB（xHCI/EHCI）、NVMe、SD/eMMC（SDHCI）、virtio-scsi 均零实现；svcmgr 对 usb-storage 显式拒绝（「EFI 冻结相 usb-storage 非本域即拒」）；U 盘/SD 卡实验无门。

**P1-10 声卡/蓝牙/硬件看门狗完全缺失。**无 virtio-sound/任何声卡；无蓝牙（settings 应用的 Bluetooth 开关是纯 UI 假面）；无硬件看门狗（代码里的 watchdog 一词全是 svcmgr 进程错杀断言语义）——**软件骨架已落地（berry-watchdog，波 2，2026-11-20）**：纯软件超时窗 crate（new/kick/is_expired 三口、单调钟时基、到期即咬，host 假钟 4 测，见[单件笔记](../notes/implemented/2026-11-20-rtc消费面与看门狗骨架双crate.md)），svcmgr 喂狗接线留后续刀，真硬件 WDT 仍缺；顺带 virtio-rng（熵源）也无——密码学实验的熵来自哪里值得补。

**P2-11 设备发现机制原始。**枚举 = virtio-mmio 32 槽固定窗口扫描（vprobe 白名单 did {1,2,16,18}，未知 did = trap）；dtbface 在仓但驱动枚举不走设备树匹配；无 PCIe；设备命名/热插拔/多实例（v1「单设备单主人」仅靠约定文档化）均未立法。

### 3.2 测试与验证：强项与两处盲区

已建成分层验证链（值得肯定）：host 纯函数单测（berry-virtio tests/layout.rs 等各 crate）→ 内核 ktest（串口 PASS/FAIL）→ tools/smoke.sh 1840 行 QEMU e2e（约 187 个标记断言）+ smp/image/lockdep/dpgsoak/x86 分线 → berry CLI 交互回归 + BCTS 兼容套件；「解析器即产品」纪律让协议面在 QEMU 之前就有 host 单测。盲区有二：真设备行为无独立模拟层——驱动的设备侧交互只能靠 QEMU 整机 e2e，没有「设备模型 mock」级单测（改一次收发路径要跑整个 smoke）；无非 QEMU 验证路径——真机/其它模拟器（crosvm/firecracker）零覆盖，驱动里多处「QEMU 实现行为」依赖（如 virtio-input 逐描述符一事件、SLIRP 补零到 64B 帧）未在第二环境对拍过。

### 3.3 教学场景关键短板判定

| 实验课题 | 能否开展 | 阻塞缺口 |
|---|---|---|
| 网络协议分析/真实 HTTP | 否 | P0-3：connect 钉死网关 + 单会话 |
| 并发服务器/客户端 | 否 | P0-3：session-0 独占 |
| UDP/DNS 实验 | 仅 DNS 内部 | P0-3：无 UDP socket |
| 分区/格式化/多文件系统 | 否 | P0-2：无分区解析、FAT12-only |
| 驱动性能调优（中断/批量/DMA） | 否 | P0-1/P0-2：poll + 单在途 + bounce |
| 多点触控/手势 | 否 | P1-6：MT 留位 |
| GPU/硬件加速图形 | 否 | P1-5：2D-only + CPU 光栅 |
| USB/摄像头/声卡外设 | 否 | P1-9/P1-10（camera 应用是程序化模拟景） |
| 真机移植/裸机调试 | 否 | P0-4：cache/IOMMU/板级支持全空 |
| 输入管线/事件系统 | 受限 | P0-1：丢批窗口 |
| 进程调度/内存管理/IPC | 可 | 非驱动域 |

结论：内核本体（调度/SMP/VM/IPC）教学能力扎实，但驱动域目前只能教「virtio 协议编解码 + 用户态驱动架构」这两课；一切「真实外设、真实性能、真实网络」的实验全部被 P0 三项（中断、块栈、网络衔接）挡住。

### 3.4 健壮性审计后续

2026-11-24 复审对 virtio 驱动家族做了一轮死亡面与契约面审计，本节只记清偿进度——事实细节归各单件笔记，行号以当日在册源码为准。

已修四项：其一，vblk 死亡面——认领槽后任一 trap 先 `STATUS=0` 复位设备再自陷（进程死后内核回收 DMA 帧，设备不得仍在途写这些帧），三处 `put_desc` 拒绝与授窗拒绝由静默改 loud，分区行改走 berry-partition `display()` 单源（见[vblk 死亡面加固笔记](../notes/implemented/2026-11-24-vblk死亡面加固与display接线.md)）；其二，berry-hal `BumpDmaAlloc` 配额记账——对齐垫片不再吃授额，单笔 `cap` 必成；其三，devmgr 驱动表六个设备 ID 改引 berry-virtio `mmio::DEVICE_ID_*` 单源，新增 console=3、rng=4 两常量（后两项见[小刀笔记](../notes/implemented/2026-11-24-驱动小刀两件-BumpDmaAlloc配额记账与devmgr设备ID单源.md)）；其四，gui-inputd `normalize_axis` 乘法溢出——中间量 i64 改 u64（钳位后三因子全在 u32 域，乘积上限约 1.8e19 超 `i64::MAX`：极端三元组下 debug panic、release 静默回绕；真实路径 `screen_len` 来自 u16 显示尺寸到不了，属防御面），补 20 万组 i128 参考对拍等三条等价性测试，旧式不溢出域内结果逐位相同（见[inputd 溢出笔记](../notes/implemented/2026-11-24-inputd-normalize_axis乘法溢出修复.md)）。

遗留五项，按影响排序：第一，vnet 与 vgpud 的 trap 不复位设备——两者 `trap()` 仍只自陷（vnet `main.rs` 第 1500—1506 行、vgpud `main.rs` 第 561—566 行），与 vblk 修前同形；第二，`let _ = vio::put_desc` 静默吞拒绝——vgpud 7 处、vnet 3 处、gui-inputd 1 处（vblk 已清零），描述符未落环仍 publish 时设备读到陈旧 desc 行；第三，DMA 缓存维护——内核 `0x1C vmo_cache_op` 在席（F0-4）、vnet 已接入，vblk/vgpud/gui-inputd 零调用（vblk 头注自述留 v2 DMA API；即 §3.1 P0-4 同一条，TCG 无 cache 模型恒绿）；第四，vgpud 显示信息未校验——GET_DISPLAY_INFO 应答头 type 不核对 `RESP_OK_DISPLAY_INFO`（`parse_display_info` 只解不判），display mode 只判 `enabled≠0` 且宽高非零，宽高无上限、不与后备帧幅对账，直接进 RESOURCE_CREATE_2D 与 SET_SCANOUT；第五，vblk 热路径便捷面——blk_op/serve 仍走 `Mmio::read32/write32` 加偏移常量而未换 `VirtioMmio` 便捷面（复审 C 类建议，非缺陷）。归属：涉及 vnet 的部分在并行会话领地，其余归 vgpud、vblk、gui-inputd 的后续刀。

## 四、三波演进路线

### 4.1 现状快照与三个候选裁决

### 4.5 与莓核 2 代的关系

其一，一体两面：裁决六四大件（berry-hal 五窄 Trait、GICv2/v3 双栈、Interrupt 直通、ramoops）全部是驱动底座；莓核 Wave 4 三刀（4.1/4.2/4.3）本质是驱动子系统的内核半边工单，本路线三波是用户态半边。其二，节奏耦合：驱动波 1 与莓核 Wave 0–3 完全并行零冲突（零内核改动），建议立即启动不等莓核；驱动波 2 消费莓核刀 4.1/4.2；驱动波 3 消费刀 4.3；莓核刀序把 Wave 4 排最后是「先止血防破窗」铁律，不构成驱动波 1 的阻塞。其三，互为验收：莓核刀 4.2 的验收标准（三驱动零轮询 + 静置唤醒计数 0）就是驱动波 2.1 的交付物——两份计划共享同一验收面，建议工单合并跟踪。其四，文档治理纪律：docs/驱动模型设计-v1.0.md 是 standard 只写现行态，devmgr 2.0 细节住 plans/soc-peripherals/design.md（spec）；本路线的行动面若立项应建 `.agents/plans/drivers/`（Type: plan，含未完成事项清单），每波收官同批升 docs/ 标准版本号，与莓核五波同款纪律。

## 五、教学路径

### 5.1 核心卖点与前置门槛

核心卖点即驱动模型设计的中心论点——驱动 = 持证应用：学生全程不碰内核、不碰裸 unsafe（MMIO 经窗口 VMO volatile 访问）、崩溃只死自己，「驱动课」从危险内核课变成安全服务课。前置门槛（诚实面）：教学路径在波 1 落地前不可行——今天学生得改 boot 手铸表才能拿到窗口，这不是教学形状；波 1 的 devmgr + 设备任务书导出（`AI工程面设计` §2.1 已设计的机器可读未认领池——AI 消费与教学消费同构）是教学面第一前置。

### 5.2 梯度课程（对应波次交付）

第 0 课·认设备：读 vprobe（135 行，天成样板）——扫槽、验魔数、按 did 分类、打 smoke 标记，最小完整闭环。第 1 课·第一个驱动：virtio-rng（did=4，virtio 规范最简设备：一队列、零状态、无 DMA 复杂度），最小步骤六步——QEMU 挂 `-device virtio-rng-device` → `berry drv-tasks` 查未认领池拿设备任务书 → `cargo new` + berry-drv SDK 模板（`hw.match = ["dt:virtio,mmio"]` + capabilities + `provides = ["/svc/rng"]`）→ 写协议层（抄 blkproto crate 模式）→ `just smoke` 验证 → `.bap` 打包装机。第 2 课·读改真实驱动：vblk（553 行）——块协议、DMA 页后备（`vmo_get_phys`）。第 3 课·中断驱动（波 2 后）：Interrupt 对象 + Port 事件循环，亲手删轮询、看 WAKESRC 归零——性能教学实感强。第 4 课·新总线（波 3 前期）：`dt:` 键匹配的真硬件设备（PL061 GPIO + LED——内核有 PL061 先例，真机上灯亮是最好的课堂反馈）。

### 5.3 配套沉淀与课程叙事

建议同批沉淀一份 `docs/驱动开发指南.md`（对齐现有 [应用开发指南.md](../../docs/应用开发指南.md) 体例），并让 vblk 演进历史（轮询版 → 中断版）作为「前后对照教材」保留。对照研究同时给出课程总叙事：三层递进课程——静态表（现状 boot 手铸）→ 动态匹配（devmgr）→ 能力授权（capability + SMMU），每层都有现役代码可指；三家可教性互补——Zephyr 最适合教「设备描述如何变成实例」、Linux 最适合教动态生态（uevent/udev/热加载）、Redox/BerryOS 最适合教隔离与能力（驱动崩溃不死机、能力表可打印可审计），BerryOS 教第三课且比 Redox 更严谨（能力 handle 而非裸 FD + 命名空间），学生写一个 .bap 就是一个驱动，不需要学内核构建链。

## 六、结论与建议

### 6.1 总判断

BerryOS 驱动栈的地基质量很高：用户态驱动架构（微内核纪律的完整演示）、virtio 协议纯函数层（「解析器即产品」）、分层验证链（host 单测 → ktest → 1840 行 smoke e2e）三件都是强项，且架构选型正确——站在 Redox/Fuchsia 同族的用户态驱动路线上，正确的动作不是换模型，而是把 Linux 的匹配分层、Zephyr 的启动层级与 PM 动作词表、比 Redox 更硬的 IOMMU/中断直通（已在 hal 2.0 图纸上）收进 devmgr v2 的既有刀序。但「中断、分区、网络自由度」三块天花板把它锁死在演示形态——补齐这三项 + DMA cache 面，就能从「能跑的教学内核」升级为「能做真实验的驱动教学平台」。

### 6.2 行动建议

近期做制度（波 1，1-2 月，零内核改动、与莓核 Wave 0–3 并行、建议立即启动）：devmgr 最小面 + 驱动 .bap `type=driver` + 手铸面退役 + MBR/GPT 分区表解析 + virtio-rng 教学样板。中期做纪律（波 2，3-6 月，吃莓核 Wave 4 红利）：三驱动零轮询化（与莓核刀 4.2 共享验收面，工单合并跟踪）、berry-drv SDK 总线抽象、热插拔热重启、PCIe ECAM + MSI-X、cache 维护 DMA API 收口、sensord QMP 注入桥。远期做疆域（波 3，6-12 月，2026-11-20 拆四刀 + 后半程两站，见 §4.4）：USB xHCI 主机栈 QEMU 起步（3.1）与键盘 USB HID（3.2）、GPU 2D 加速面（3.3——3D 线随 gfx/compositor 线并行）、devmgr v2 授权面收口用户态驱动框架（3.4）；SMMUv3 隔离（CI 加 `iommu=smmuv3` 腿）与真机第一站（VMware Fusion → 树莓派级开发板）随莓核 Wave 4 收官解锁。

补缺刀序按「教学价值 ÷ 工程量」排序的要点：virtio IRQ 桥撬动面最大（根治输入丢批 + 砍掉三处 1ms 轮询）；GPT/MBR 解析器纯函数 crate 完全复用 berry-virtio 纪律，两周内可落；网络出站地址域 + 多会话表（OP_TCP_OPEN 携带 dst IP、ARP 查询通用化、会话表扩 N 槽）落地后 std::net 的真实 HTTP/DNS 实验立刻解锁；DMA cache 维护把「真机就绪度」从文档承诺变成可验证断言；goldfish-RTC 或 PL031 驱动小体量、高感知，是「第一个非 virtio 设备驱动」的理想教学样板；其余（多点触控 Type-B、UDP socket + DHCP、FAT16/32 或 ext2 只读、USB xHCI、设备模型 mock 单测层）按波次排队，USB 建议作为高阶课程项目而非内核主线任务。
