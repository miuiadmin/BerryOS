# 模拟器性能分层诊断（2026-11-15 LAN 演示实测归因）

Type: survey
Status: current
Updated: 2026-11-15

一句话说明：LAN 网页桌面演示中「很卡」的分层归因——当晚体感的约七成来自三起叠着的工地事故（HVF 被在制品内核挡死退到 TCG 软件模拟、测试镜像开机全量自测烧 CPU、冷页楔死 bug），约三成来自架构性能上限（客机模拟 CPU 软光栅、ramfb 全帧通路、无合成器——均已在显示体系设计立法有刀序）；结论：不是「系统比业界差」，是「已立法的层未兑现 + 工地事故」，修复钥匙在并行分支回合与既有刀序。

## 第 0 层：TCG 兜底（当晚最大因素，事故）

本机 Apple Silicon 可用 HVF 硬件虚拟化（近原生），但当晚现存内核构建无一能在 HVF 下活到桌面：

| 尝试 | 死因 | 定性 |
|---|---|---|
| 老内核（≤11-12 镜像） | FP 寄存器自检 panic | 老内核无加速键跳过（判例 11-13 才入） |
| 新内核（11-15 构建） | 首个用户进程 EL0 D-abort 不恢复，2s halt | 并行内核线在制品回归 |
| knife6 分支镜像（11:23） | 冷页缺页 pager 楔死（12:30 才修，镜像更老） | 同线已修未回合 |

TCG = 每条指令软件翻译，典型慢 10-50 倍；BerryOS GUI 为 CPU 软光栅，界面速度 ≈ CPU 速度，TCG 下即「卡」。HVF 修复钥匙 = 回合 `wip/boot-events-knife6` 的两笔修复（见 [1080p 会审](2026-11-15-1080p恒黑根因会审.md)）；berry 侧已铺好 GUI 家族 `noktest` fw_cfg 注入（[qemu.rs](../../tools/berry/src/qemu.rs)，六波 owner 裁决落地）。

## 第 1 层：测试镜像开机全量自测（事故）

当晚所有镜像均测试构建：内核 ktest + 上百 rootfs 自测程序（FILE/STD/HEXYL/ECO…）在 TCG 单模拟 CPU 上烧 5-10 分钟，期间桌面与自测抢核——点击延迟的直接来源。实测（TCG、健康镜像）：到 LAUNCH 91-127s，自测流安静需再 5-8 分钟；`noktest` 只免内核 ktest，rootfs 套件仍在（生产模式镜像无此面）。

## 第 2 层：冷页楔死（bug，非速度）

画面在、输入无响应 = 冷页缺页把 pager 挂死（`e58c94ccf` 已修未回合）。同晚 phone 档（480×1000）实测点击有响应、tablet 档两次楔死——楔死与布局触达的冷页相关，与速度无关。

## 第 3 层：架构性能上限（真实「性能」答案，均有立法）

| 缺层 | 业界做法（详见[机制调研](2026-11-15-survey-模拟器1080p显示机制对照.md)） | 代价与边界 |
|---|---|---|
| 像素生产端无宿主 GPU 卸载 | Android/iOS 模拟器渲染直达宿主 GPU | 帧率上限 = 模拟 CPU 吞吐；4K=33MB/帧软光栅判不可行 |
| ramfb 全帧通路（宿主 16ms 全帧 pread + VNC 全帧推） | virtio-gpu 脏矩形 / QEMU 脏页跟踪 | 1080p60 ≈ 0.5GB/s——设计文档判「可承受」但浪费 |
| 无合成器（应用全屏盖状态栏） | Wayland/Android 合成层 | 正确性欠账，非性能 |

三层均已立法有刀序（[显示与加速体系设计-v1.0](../../docs/显示与加速体系设计-v1.0.md)）：virtio-gpu 2D guest 半已落（`FB ok vgpu slot=31`）、宿主 wgpu/Metal 合成、D-Bus 纯 damage 出帧口。

## 结论与验证遗留

当晚「卡」= 三事故叠加；架构上限决定的是 4K/高帧率天花板，不决定当晚。待办：回合两修复后实测 HVF 档全链数字（开机时长/点击延迟/1080p 帧率）补进本文——当晚 HVF 无一颗健康内核可测（各死因见第 0 层表），此为如实登记的未验证面。
