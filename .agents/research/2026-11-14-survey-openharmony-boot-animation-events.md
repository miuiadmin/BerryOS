# OpenHarmony/HarmonyOS 开机动画与启动事件体系调研（BerryOS 引导视觉设计弹药）

Type: survey
Status: current
Updated: 2026-11-14

一句话说明：为 BerryOS「统一模拟器入口 + 引导视觉（verbose 滚动日志 / 图形 logo 遮罩 + 真实事件驱动进度条）」设计，对 OpenHarmony 标准系统 bootanimation 服务与 init bootevent 体系做的一手源码级调研，含 LiteOS-M 差异、进度折算机制、调试等价物与可直接抄的机制清单。

## 问题

BerryOS 要设计两种引导视觉模式：verbose 模式（详细滚动启动日志，滚完进桌面）与图形模式（logo 遮罩 + 进度条，进度映射真实启动事件，粒度越细越好）。本调研回答：OpenHarmony 怎么做开机动画（谁拉起、Surface 时序、退出条件）、动画资源长什么样、init 侧有多少启动事件点可用、事件如何折算进度、小设备与标准系统路径差异、以及调试模式下有没有等价 verbose。只取一手材料（gitee 源码与官方 docs），逐条带出处。

## 方法与来源

web_search 通道上游认证失败不可用，全部改走 gitee OpenAPI 与 raw 直抓（curl -L），并对 startup_init、startup_bootstrap_lite、manifest 三个仓库做 shallow clone 后本地 rg。核心源：graphic_graphic_2d 仓库 frameworks/bootanimation 全目录（master，2026-11 抓取）与 OpenHarmony-v3.0-LTS / v3.1-Release / v3.2-Release 历史版本、startup_init 仓库 services/modules/bootevent、services/init/standard、services/param/watcher、官方文档 docs/zh-cn/device-dev/subsystems 下启动子系统全套。历史版本用于追「Unable to」文字阶段（结论见适用边界）。补验轮（同日）：再浅克隆 window_window_manager 与 ability_ability_runtime 两仓补齐 wms.fullscreen.ready / appfwk.ready 置位者；关键源码断言（CheckExitAnimation 闸门、bootevent.c 记账、init.c 主序列、changefreq 折算、compile_progress 数字）逐一 curl raw 复核；检索通道换 Sogou（可用）与 Bing（返回无关结果弃用）拿华为一手页面。

## 结论

### bootanimation 服务：谁拉起、Surface 时序、退出条件

源码位置：foundation/graphic/graphic_2d 仓库 frameworks/bootanimation/，可执行目标 ohos_executable("bootanimation") 安装为 /system/bin/bootanimation。master 版目录：src/ 12 个文件（controller/operation/strategy 分层 + picture/video/sound 三种 player + compile_progress）、include/ 16 头文件、etc/bootanimation.para、data/ 四个默认资源、bootanimation.cfg。

拉起方式：bootanimation.cfg 声明服务（path=/system/bin/bootanimation，once=1，uid=graphics，importance=-20，bootevents=[bootevent.bootanimation.started, bootevent.bootanimation.finished]），cfg 安装到 /system/etc/init 由 init 统一扫描。服务未配 start-mode，按默认 normal 组在 post-init 阶段被 TriggerServices(START_MODE_NORMAL) 与其他 normal 服务并行拉起（init.c:355-357：pre-init job → init job → boot 组 → post-init job → normal 组）。

启动内部时序（BootAnimationController::Start）：先 WaitRenderServiceInit 轮询（30ms 间隔）SystemAbilityManager 的 RENDER_SERVICE SA 存在且系统参数 bootevent.renderservice.ready 为 true；再读配置 json（失败进 COMPATIBLE 兼容策略，默认单屏 screenId=0）；按配置选策略——COMPATIBLE（单屏，支持折叠屏 hinge 状态选视频）/ INDEPENDENT（多屏各自独立动画）/ ASSOCIATIVE（多屏共用一路操作）。每屏 SetScreenPowerStatus(ON) 后建 RSDisplayNode（全屏黑底 0xFF000000）+ RSSurfaceNode（名 BootAnimationNode / 副屏 BootAnimationNodeExtra，类型 SELF_DRAWING_WINDOW_NODE，isSync=false，SetBootAnimation(true) 特权标记，SetPositionZ(MAX_ZORDER=100000) 置顶）；surfaceNode 建成即 SetParameter("bootevent.bootanimation.ready","true")。视频路径直接把 surface 给播放器；图片路径 PlayPicture 时置 bootevent.bootanimation.started=true。

帧驱动：图片播放器走 VSyncReceiver（rsClient.CreateVSyncReceiver("BootAnimation")），SetVSyncRate 降频系数 changefreq = (1000/freq)/16，即按目标帧率对 60Hz vsync 抽帧；每回调 RequestFrame → CPU 绘制（先整屏黑矩形再按正方形居中画当前帧，边长取 min(宽,高)）→ FlushFrame 提交，buffer fence 由 RSSurface 层携带。帧序列按 zip 内文件名排序，播到最后一帧 Stop。动画线程 join 后，若判定为 OTA 升级首启则进入 BootCompileProgress 阶段（见下节），最后主循环 while(!CheckExitAnimation()) usleep(30ms) 轮询退出。

退出条件（CheckExitAnimation）：动画自身播完时先 SetParameter("bootevent.bootanimation.finished","true")，然后等 bootevent.boot.completed 为 true 才退出进程——即退出 = 动画播完 && 全系统启动事件集齐，桌面就绪由 init 的 bootevent 记账代理，动画只做消费方。另有 duration 秒定时器兜底（cust.bootanimation.duration，PostTask 延时 duration*1000ms 强制 StopBootAnimation）与视频播完回调。历史对照：v3.0-LTS 旧实现直接用 WindowManagerService 的窗口列表回调 OnWindowCreate 监听 com.ohos.launcher / com.ohos.systemui 进程建窗即 exit，另有 15 秒兜底——「桌面窗口出现」曾是显式退出信号，后来统一换成 bootevent.boot.completed。Surface/SyncFence 细节：master 的 rsSurfaceNodeConfig.isSync=false（动画 buffer 不做同步事务），而 OTA 编译进度的 BootCompileProgressNode 用 isSync=true 且 Z=MAX_ZORDER+1（压过动画层）。

反向依赖（补验轮实证）：bootanimation 的 ready 事件不止给 init 记账，还直接门控桌面启动——ability_ability_runtime 的 AbilityManagerService::WaitBootAnimationStart（ability_manager_service.cpp:13221）在启动 LAUNCHER 前调用（:7491，注释原句 "wait BOOT_ANIMATION_STARTED to start LAUNCHER"）：WaitParameter("bootevent.bootanimation.ready","true",timeout)，旧参数缺失时回落等 bootevent.bootanimation.started；timeout 默认 5（ams_configuration_parameter.h:176 bootAnimationTime_{5}），可由 service_config.json 的 boot_animation_timeout_time 覆盖。即官方用「动画首帧参数」当跨服务同步点：先保证遮罩上屏，再放行桌面进程，防止桌面先画穿帮。

### 动画资源：格式、分辨率、帧率与「Unable to」文字阶段

默认资源三件套（BUILD.gn ohos_prebuilt_etc 安装到 /system/etc/graphic/）：bootpic.zip（帧序列）、bootsound.wav、bootvideo.mp4。配置解析顺序：bootanimation_custom_config.json（etc/bootanimation/bootanimation_custom_config.json，键 cust.bootanimation.pics / cust.bootanimation.sounds / cust.bootanimation.video，指向 /sys_prod/etc/bootanimation/cust_bootpic.zip 等运营商/产品定制资源；企业设备另支持 /data/service/el1/public/edm/config/system/all/graphic/bootanimation/ 下的下发配置）。资源选择逻辑 IsBootVideoEnabled：视频路径存在则播视频（支持 videoExtPath 按折叠屏 hinge 状态选片），否则图片 + 可选声音；图片路径不存在回落默认 /system/etc/graphic/bootpic.zip。

帧包格式：zip 内含 config.json（{"FrameRate": N}，FrameRateConfig 默认 30）与任意命名的图片序列（ReadZipFile 全量解压进内存，SortZipFile 按文件名排序定序）；帧率校验 CheckFrameRateValid 只接受 30 或 60，其他值告警后维持默认。分辨率不自适应缩放素材：取屏幕短边为正方形边长居中绘制（InitPicCoordinates），背景涂黑。声音开关 const.bootanimation.bootsound（v3.2 为 persist.graphic.bootsound.enabled，默认开）。「Unable to」文字阶段：在 v2.0-Canary、v3.0-LTS、v3.1-Release、v3.2-Release 与 master 五个版本的 bootanimation 源码中全文检索均无 "Unable" 字样，该描述未证实属于 OpenHarmony 开源实现；开源侧最接近的「文字阶段」是 OTA 优化进度层（见下）与 LOGE 日志，若指 Android bootanimation 的缺资源占位文字则属 Android 行为，BerryOS 不应照抄此结论。

### OTA 编译进度：进度条如何折算真实事件（最直接可抄的样板）

BootCompileProgress（boot_compile_progress.cpp）只在 OTA 升级后首启显示（IsOtaUpdate：persist.dupdate_engine.update_type 为 manual/night，或 persist.update.hmos_to_next_flag=1），时机在开机动画播完之后、退出轮询之前。驱动是混合模型：目标事件 bootevent.bms.main.bundles.ready（BMS 主包扫描/优化完成）；时间预算 persist.bms.optimizing_apps.timing 默认 240 秒。事件未到时 progress = (now - start) / (timeLimit * 1000ms) * 100，纯线性时间推进；事件到达后改为每帧 progress_++（vsync 降频 4、约 30fps，最多约 3.3 秒从当前值平滑冲到 100），到 100 置 isUpdateOptEnd_ 收尾。即「时间线性兜底 + 事件确认后快速补完」，天然避免进度回跳与长时间卡死。视觉：白色文字「正在优化应用 XX%」（海外 Optimizing Apps，文案可由 const.bms.optimizing_apps.display_info 覆盖），字体 HarmonyOS Sans SC，字号 phone 12vp / 其他设备 24vp（TranslateVp2Pixel 按 360/800 基准宽折算像素），下方三个半径 3vp（wearable 5vp）白点做透明度循环：30 帧一周期、每 10 帧一阶段、透明度经三次贝塞尔 (0.33,0)-(0.67,1) 插值，三点相位错开。布局常量：进度区高 max(宽,高)*0.05、距底 20%，全可被 BootAnimationProgressConfig（progressScreenId/Height/FrameHeight/Offset/FontSize/RadiusSize/Degree）按屏覆写。

### init 启动事件体系：job 阶段、param 触发器、bootevent 记账、可用的进度事件点

job 阶段链（官方 jobs 文档 + init.cfg 实物）：pre-init（ueventd/watchdog/data 挂载）→ init（大命令批 + boot 组服务并行）→ post-init（trigger early-fs / fs / post-fs / late-fs / post-fs-data / early-boot / boot + normal 组服务并行）。条件 job 以 param 前缀命名 + condition 字段（支持 && || 与 * 通配，如 "param:sys.boot.completed=*" 或 "boot && const.debuggable=1"），参数一变即触发；同名 job 跨 cfg 合并执行。小型系统只支持基本 job（无 trigger 无条件 job）。

服务并行与依赖：start-mode 三档（boot=init 阶段并行首批 / normal=post-init 阶段并行默认 / condition=等 start 命令），另有 on-start/on-stop/on-restart 服务钩子 job 与 end-mode（pre-fork/after-fork/after-exec/ready）标定服务完成时机——声明 bootevents 的服务即以收到 bootevent 为「完成」。boot 组实证：samgr（samgr_standard.cfg，bootevent.samgr.ready，critical [1,1,60]）、appspawn（appspawn.cfg，bootevent.appspawn.started）、param_watcher（param_watcher.cfg，bootevent.param_watcher.started）；normal 组实证：render_service（graphic.cfg，bootevent.renderservice.ready）、bootanimation。

bootevent 记账机制（bootevent.c 全文）：init 解析各 cfg 的 "bootevents" 字段（字符串或数组）建链表并计数 g_bootEventNum，fork 服务时记 CLOCK_MONOTONIC 时间戳[BOOTEVENT_FORK]；服务初始化完成后自己 SystemSetParameter("bootevent.xxx.yyy","true")，init 的 param_hook 前缀表（param_hook.c GetOtherSpecial：{"bootevent.", "bootevent.", "bootevent"}）把 bootevent.* 参数变更路由到 DoBootEventCmd → BootEventParaFireByName：记 [BOOTEVENT_READY] 时间戳、写 ohos.boot.time.<事件名>=<uptime 微秒> 系统参数、计数减一；归零时 SystemWriteParam("bootevent.boot.completed","true") + SetBootCompleted + 写 /data/log/startup/bootup.trace（Chrome trace JSON 格式，pid=服务 pid、dur=ready-fork，persist.init.bootuptrace.enable 开关）+ 上报 sysevent（persist.init.bootevent.enable，begetctl bootevent enable/disable 命令控制）+ 100ms 定时器后执行 INIT_BOOT_COMPLETE hook + 清链表。init 自身也打点：ohos.boot.time.kernel（内核 uptime）、ohos.boot.time.init，job 型事件 init.prepare / init.ParseCfg，超过 100ms（SAVEINITBOOTEVENTMSEC）的 init 命令也单独入 trace；另有 etc/init/priv_app.bootevents 文件机制把应用级事件预注册进链表。unset_bootevent 命令可撤销事件（boot.completed 回落 false）。

事件粒度盘点（已证实清单）：机器可数的事件点 = 服务 bootevents（已实证 10 个：samgr.ready、appspawn.started、param_watcher.started、renderservice.ready、bootanimation.ready、bootanimation.started、bootanimation.finished、appfwk.ready（appfwk.para 声明，aafwk abilitymgr 置位）、wms.ready、wms.fullscreen.ready（wms.para 声明）、bms.main.bundles.ready（compile progress 消费）——即 11 个）+ init 自身 4 个（kernel/init/prepare/ParseCfg）+ 每个事件一条 ohos.boot.time.* 时间戳参数 + 慢命令 trace 条目；标准系统整机总数未盘点全（audio/wifi/telephony 等仓库未逐一核，未证实）。桌面首帧的代理事件：bootevent.boot.completed（bootanimation 的退出闸门）与 bootevent.wms.fullscreen.ready；v3.0 历史实现则直接以 launcher/systemui 建窗为号。

两个关键事件的置位者（补验轮读源确认）：其一 bootevent.wms.ready 在 WindowManagerService 构造函数里置位（window_manager_service.cpp:110），语义 = WMS SA 服务对象初始化完成。其二 bootevent.wms.fullscreen.ready 有两条置位路径——旧架构 wmserver/src/window_controller.cpp:932 StopBootAnimationIfNeed（在每次 AddWindowNode 加窗后调用，:358）：遍历默认屏全部已显示窗口（跳过 WINDOW_TYPE_BOOT_ANIMATION 类型），求窗口矩形并集，当并集完整覆盖默认屏（差集为空）时打日志 "stop boot animation"、置 bootevent.wms.fullscreen.ready=true 并经 HiSysEvent 上报 boot animation done duration(s)——这是「像素覆盖」语义的桌面就绪判定：除动画层外的可见窗口盖满全屏即桌面首帧就绪；新架构（sceneboard）window_scene/session_manager/src/scene_session_manager.cpp:1626 在 CreateRootSceneSession() 一进门即置位——根场景会话建立即视为全屏就绪。appfwk.ready 置位点 = AbilityManagerService::OnStart 发布 SA 成功后（ability_manager_service.cpp:386）。对 BerryOS 的直接启示：桌面首帧就绪可用「launcher 窗口与遮挡窗口的并集覆盖全屏」这一几何判据，不必等主观「桌面画完」。

### 真机鸿蒙开机视觉（华为 logo → 动画 → 桌面）

一手公开资料（补验轮经 Sogou 检索通道取得两类）：其一华为开发者官网 HarmonyOS 设计规范（设备控制设计 → 视觉风格 → 开机画面，V1 归档版，更新时间 2024-04-11）给出一手定义与硬规范：开机画面 =「设备接通电源并打开屏幕后、显示设备主界面（桌面）前显示的界面」；结构强制两段式——第一段必选静态画面，含厂商 logo + 固定的 "Powered by OpenHarmony" logo（厂商不可自行设计，深底用白 #FFFFFF、浅底用黑 #000000 两色模式，屏幕底部居中、设 logo 高为 x 则底边距屏底 2x），第二段可选厂商 logo 动画；背景必须纯色、禁图片与纹理填充；厂商 logo 横向居中、纵向视觉居中；圆形屏另有专门位置图。其二华为消费者支持站的故障排查用语坐实真机链路词汇：「开机卡在 HUAWEI Logo 界面」（BIOS/引导段）、「重启后尝试进入桌面」（桌面段）、「HarmonyOS 开机向导」（桌面后的首启设置段）分属三段。加上 bootanimation 源码里的商用痕迹——企业设备 EDM 下发动画路径、/sys_prod/etc/bootanimation/ 产品定制层（cust_bootpic.zip/cust_bootsound.wav/cust_bootvideo.mp4）、字体常量 "HarmonyOS Sans SC"、升级参数 persist.update.hmos_to_next_flag（HMOS 升级到 NEXT 的首启编译进度场景）、分区文案按 const.cust.region=cn 区分「正在优化应用 / Optimizing Apps」。综合可证链 = 固件/bootloader 华为 logo（内核起来前）→ init 拉起 bootanimation 黑底视频/帧动画（视频优先）→ bootevent.boot.completed 集齐动画退出 → sceneboard/launcher 桌面 → 首启开机向导；华为手机本体（HarmonyOS 4/NEXT）开机动画的逐帧视觉描述仍无官方一手文档（第三方 Bilibili 视频可佐证存在，未作证据），标注未证实。

### LiteOS-M 小设备与 standard 的启动路径差异

轻量系统（mini，≥128KB，Hi3861 类）：无 init 进程、无 cfg、无 param 服务、无开机动画组件（manifest 全仓清单确认 foundation/graphic 下 lite 侧只有 surface_lite 与 graphic_utils_lite）。路径：内核 los_KernelInit 后调 OHOS_SystemInit（startup_bootstrap_lite/services/source/system_init.c）：MODULE_INIT(bsp) → MODULE_INIT(device) → MODULE_INIT(core) → SYS_INIT(service) → SYS_INIT(feature) → MODULE_INIT(run) → SAMGR_Bootstrap() → LiteParamService()。实现靠链接脚本 zinitcall 段（.zinitcall.sys.service0.init 等，IAR 下每类还有 level 0-4 两级分层），SYS_SERVICE_INIT/SYS_FEATURE_INIT/APP_SERVICE_INIT/APP_FEATURE_INIT 宏把初始化函数钉进段内，启动即顺序遍历调用——启动顺序 = 段布局，编译期定死，无运行时事件。小型系统（small，≥1MB，LiteOS-A）：init lite 顺序 DoJob(pre-init) → DoJob(init) → DoJob(post-init)，无 trigger/条件 job（官方 jobs 文档约束），同样无开机动画。结论：事件体系与动画是 standard 独有的运行时能力，lite 靠编译期段序；BerryOS 若做单二进制可选内核态等价 zinitcall。

### 调试模式有没有等价 verbose

无「图形/文字双模式切换」机制，也无 verbose boot 模式开关。等价物分层：其一 init 日志五级（INIT_DEBUG/INFO/WARN/ERROR/FATAL），由 persist.init.debug.loglevel 参数（0-4）控制，begetctl setloglevel N 运行时立即生效、重启后经 load_persist_params 恢复；其二 hilog 全系统日志（bootanimation 的 LOGI 全进 hilog，串口或 hdc shell hilog 实时看，即事实上的 verbose 通道）；其三启动事件观测——param 工具实时读 ohos.boot.time.*（每个事件的微秒时间戳）与 bootevent.boot.completed，begetctl bootevent enable 开 sysevent 上报，/data/log/startup/bootup.trace 出 Chrome trace 可视化（perfetto 直接打开）；其四 bootchart（pre-init 里 "bootchart start"）做 CPU 级启动分析。对 BerryOS 的启示：verbose 与图形两种模式可共用同一事件流，verbose 即把事件流以日志形式滚动打印（OpenHarmony 的 hilog 本来就是滚动文本），图形即把同一事件流折算进度。

## 适用边界

其一，「Unable to」文字阶段与华为手机本体（HarmonyOS 4/NEXT）开机动画逐帧视觉均未证实：前者在五个版本的 bootanimation 源码检索为空；后者官方仅给出结构规范（两段式）与故障排查词汇，无逐帧描述。其二，标准系统整机 bootevent 事件总数未盘点全（audio/wifi/telephony 等仓库未核），给出的是已实证的 11 个服务事件 + init 4 个自打点；bootanimation.ready 未列入 bootanimation.cfg 的 bootevents 数组（cfg 只列 started/finished），ready 主要作为 aafwk 的跨服务门控参数被消费，init 是否为其单独记账取决于 cfg 声明。其三，结论基于 master（2026-11）与 v3.0/v3.1/v3.2 三个 Release tag，OpenHarmony 迭代快，fork 或商用版本（含 HarmonyOS NEXT 闭源部分）行为可能不同；bootanimation 在 master 已重构为 controller/operation/strategy 分层，旧版单文件实现仅作机制演变参考；华为设计规范页为 V1 归档版（官网已推荐 NEXT 版，NEXT 版对应页未在本次取证范围内）。其四，本文只调研不改代码，BerryOS 侧的落地设计属后续 plans。
