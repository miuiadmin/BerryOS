## 问题

BerryOS 现役模拟器显示链（ramfb + guifbd blit-at-SUBMIT + 宿主轮询读客机 RAM）在 1080×1920 档恒黑（串口全绿、帧缓冲物理区 md5 不变），而 480×1000 与 800×1280 同链正常。要回答：别人的系统靠什么机制使分辨率不成为瓶颈；BerryOS 缺的是哪些层（host GPU 卸载？脏矩形协议？独立显示设备模型？还是只是内部表尺寸）；哪些是架构级差距、哪些只是实现细节未扩容。任务书给定 BerryOS 侧事实：TCG + HVF 双档复现、三镜像同病、buddy 分配器帽与 TextureDesc 校验已排除、guifbd 是 blit-at-SUBMIT 无合成架构、svcmgr 有 128KiB 平像帽（六波计划风险列表原话）。

## 逐系统机制细节与证据

### Android Emulator：API 转发 + 宿主 GPU + 矩形出屏

四件证据拼出完整链路。其一，GPU-EMULATION.TXT 定义 hw.gpu.mode：`host` 模式用 translator 库把 guest EGL/GLES 命令译成宿主桌面 GL，`mesa` 为宿主软件 GL 兜底，guest 软渲染仅 GLES 1.x 极慢备胎；官方开发者文档列出 `-gpu host/software/swiftshader/swangle/lavapipe` 档位（host 模式 macOS 可用 MoltenVK 加速 Vulkan）。其二，emugl DESIGN 文档给出全链：guest 侧系统库实现同款 EGL/GLES ABI，函数调用被 emugen 生成的 encoder 序列化为字节流，经 QEMU Pipe（guest 内核驱动 + `hw/android/goldfish/pipe.c` 虚拟设备）送到宿主 renderer 进程，renderer 解码后交 translator 打到宿主 GL——QEMU 进程本身只当「哑代理」不解析协议流。其三，ANDROID-QEMU-PIPE.TXT 证实 `opengles` 是 pipe 服务名（等价 tcp:22468）、通道按页粒度读写且「从 guest 视角读写近乎瞬时」。其四，ANDROID-FRAMEBUFFER.TXT 证实软件合成路的出屏机制：goldfish fb 的物理页在客机连续、宿主机随机分布，`goldfish_fb_update_display()` 检查 fb 物理页 dirty bits，算出自上次以来的像素更新 bounding rectangle，经 `qframebuffer_update(fb, x, y, w, h)` 只把矩形推给 clients（皮肤 UI 窗/VNC），刷新节拍 1/60。现代演进是 gfxstream（virtio spec 的 capset 3 GfxStream）：官方 README 自述「代码生成器，把图形 API 调用从一个地方序列化转发到另一个地方——VM guest 到 host、进程到进程、机器到机器」，cuttlefish 的 `--gpu_mode=gfxstream_guest_angle_host_swiftshader` 即 guest-ANGLE-宿主-SwiftShader 的组合后端。分辨率在这套体系里几乎不是变量：像素生产在宿主 GPU、像素搬运按矩形、guest 只送命令流。

### HarmonyOS DevEco 模拟器：QEMU 基座 + 翻译层 + 共享内存帧流

官方文档四页给出机制骨架。「模拟器与真机的差异」页明确「模拟器是运行在 Mac 或 Windows 电脑上的虚拟机应用，会使用电脑的硬件资源，包括 CPU、内存和网络连接等」；图形接口差异清单（不支持 GLES 3.1/3.2，Vulkan 自 6.1.0 Beta2 支持但缺 vkGetSwapchainGrallocUsageOHOS/vkAcquireImageOHOS/vkQueueSignalReleaseImageOHOS 三个 gralloc 交换链接口，DMA buffer 仅 RGBA）是宿主 GPU 翻译层的典型缺口签名——与 Android emugl 同构思路，渲染落在宿主 GPU。基座是 QEMU 的铁证在「获取模拟器实时画面数据」页：`param get | grep hvd` 出 `ohos.qemu.hvd.name = Mate 90 RS`（ohos.qemu.* 前缀参数），hdc 走 127.0.0.1:5555，设备类型页要求 x86 模拟器编译 x86_64 so。该页还给出帧出口机制：`-streamOutput` 启动参数把主屏幕画面帧实时写入命名共享内存 `emu-shm-frame-<hdc端口>`，Header 带 magic/ready/frame_index/timestamp/width/height/format(RGBA8888)/encode(raw)/payload_size，读取方轮询 ready、按 frame_index 去重、校验 payload==w×h×4——即宿主侧有独立帧合成出口，帧序号单调递增，payload 尺寸无上限字段，1080×2340 级手机面板为常规档。分辨率支撑面：设备类型含 Phone/折叠/Tablet/2in1/TV/Car，官方差异页只谈色域与锯齿，不设分辨率帽。

### iOS Simulator：没有模拟层，宿主原生进程

Apple 官方 Simulator User Guide（archive 版）的表述直接了当：Simulator「是跑在 Mac 上的 app」「直接使用计算机的资源，包括 CPU、内存和网络连接，这些都可能比真机快」，因此「不适合测性能，UI 在 Simulator 上可能比真机更快更平滑」；OpenGL ES 差异节确认 Simulator 提供 GLES 1.1/2.0/3.0 的完整实现（能力近似 A7 GPU），但「不用 tile-based 延迟渲染」「与真机 GPU 无像素级一致」「渲染性能与真机无关」。也就是说模拟器 app 二进制就是宿主架构原生代码，渲染直连 Mac GPU（现代版 Metal 亦然），显示就是普通 Mac 窗口——分辨率对它只是窗口尺寸，所谓瓶颈只剩「与真机不一致」这一种。这与 BerryOS 类比意义有限（BerryOS 是真指令级客机内核），但它是「分辨率不成问题」的极端参照：当渲染与出屏都在宿主、guest 只贡献程序逻辑时，分辨率天然退化为窗口缩放问题。

### 通用 QEMU：三条路径三种协议

_std VGA / bochs VBE_：帧产生 = guest CPU 直接写 VRAM（LFB 模式映射为 BAR）；出屏 = vga.c 的 `vga_draw_graphic` 每刷新 tick 先 `memory_region_snapshot_and_clear_dirty(&s->vram, ...)`（KVM/HVF 下脏页由硬件二级页表跟踪），逐扫描线用 `memory_region_snapshot_get_dirty` 判脏，脏行重画、连续脏行合并成 `qemu_console_update(con, 0, y_start, disp_width, y-y_start)` 矩形上报——脏矩形协议在设备侧自动完成，guest 无感。尺寸校验在 `vbe_fixup_regs`：XRES/YRES 钳到 VBE_DISPI_MAX_XRES/YRES（16000/12000），YRES 还受 `maxy = vbe_size / linelength` 钳制（VRAM 容量），1080p×32bpp 需 8.3MiB，默认 16MiB VRAM 无压力。

_virtio-gpu 2D_：协议即 UAPI。RESOURCE_CREATE_2D 建 resource，RESOURCE_ATTACH_BACKING 把 guest RAM 页表挂为后备，SET_SCANOUT 把 resource 矩形绑到 scanout，TRANSFER_TO_HOST_2D(rect, offset) 只把脏矩形从 guest RAM 拷到宿主 resource，RESOURCE_FLUSH(rect) 声明「这块该出屏了」。内核驱动侧 virtgpu_plane.c 是活教材：`drm_atomic_helper_damage_merged(old_state, plane->state, &rect)` 合并 damage，`bo->dumb` 时 `virtio_gpu_update_dumb_bo()` 只对 rect 发 TRANSFER_TO_HOST_2D，随后 `virtio_gpu_resource_flush()` 带 fence 发 RESOURCE_FLUSH；`drm_plane_enable_fb_damage_clips()` 把用户态 damage hint 接进来。virgl（capset 1/2）与 venus（capset 4）再把 3D 命令流交给宿主渲染器，与 Android host 模式同构。

_ramfb_：ramfb.c 的事实——guest 写 fw_cfg 具名文件 `etc/ramfb` 的 RAMFBCfg{addr, fourcc, flags, width, height, stride}（要求 fw_cfg 开 DMA），QEMU `ramfb_create_display_surface` 校验 16 ≤ width ≤ 16000、16 ≤ height ≤ 12000 后 `physical_memory_map` 直接映射客机 RAM 建 DisplaySurface（零拷贝），`ramfb_display_update` 永远 `qemu_console_update_full(con)`——整帧刷新、无脏矩形、无 guest→宿主事件通道（guest 想通知只能重写 cfg）。这就是 BerryOS 现役链的宿主端：机制上 1080×1920 远在许可域内（宽度 1080 ≥ 16、高度 1920 ≤ 12000、8.3MiB 连续区映射无碍），QEMU 侧不存在拒绝或降级 1080p 的代码路径。

### 典型 Linux 桌面：为什么 QEMU 里 1080p 没问题

把上面三件拼起来：Wayland 合成器把各 surface 合成到 dumb buffer（CPU 写线性 RAM）或 virgl resource；每次 atomic commit 内核驱动对 dumb buffer 只发 TRANSFER_TO_HOST_2D(damage 矩形) + RESOURCE_FLUSH，QEMU 只拷脏区；std-vga 路径则连协议都不需要，guest 直接写 VRAM，KVM 脏页跟踪自动框出脏区。分辨率变大时，每帧成本只随「实际变化的像素」走（光标移动帧每帧几十 KB），全帧变化帧才回到线性；而全帧 8.3MiB×60 ≈ 0.5GB/s 的宿主带宽在现代桌面是零头。damage 合并在内核（drm_atomic_helper_damage_merged）、脏页跟踪在硬件（EPT/NPT）、出屏在设备侧矩形上报——三层叠加使 1080p 在「没有 GPU 加速的 QEMU」里也只是普通负载。

## 通用结论：别人靠什么使分辨率不成为瓶颈

五家系统殊途同归，靠的是三条机制，缺一就退化为「分辨率敏感」：

1. 渲染卸载到宿主 GPU（像素生产端）：iOS 极致化为宿主原生进程；Android/DevEco 用 API 翻译转发（emugl translator / gfxstream / 类似翻译层）；QEMU 用 virgl/venus。像素不经过 guest CPU 软光栅，分辨率只是宿主 GPU 的常规负载。
2. 脏矩形/增量出屏协议（像素搬运端）：virtio-gpu 的 TRANSFER_TO_HOST_2D(rect)+RESOURCE_FLUSH(rect)、std-vga 的脏页快照+按行合并矩形、goldfish fb 的 dirty bits+bounding rect、DevEco 的 frame_index 增量帧流。每帧搬运量 = 变化量，不是全帧。
3. 显示几何与渲染解耦（配置端）：EDID/显示信息协商、SET_SCANOUT 动态换绑、宿主窗口任意缩放永不回灌 guest 分辨率（BerryOS 体系设计不变量①引用的 Android/QEMU GTK 双先例）。

ramfb 是唯一「三条全无」的路径——guest 软光栅 + 整帧轮询 + 静态几何——它仍然跑得动 1080p（0.5GB/s 量级），但每帧成本恒为全帧，这是 BerryOS 现役链「慢」的根因（体系设计裁一的定量：每变化帧 ≥4 次全帧级 CPU 遍历），却不是「黑屏」的机制来源。

## BerryOS 现状对照与差距分级

BerryOS 现役链（任务书与体系设计文档：ramfb 轮询 pread 现役、guifbd blit-at-SUBMIT 无合成、svcmgr 128KiB 平像帽、宿主全帧读）与五家对照后的差距分级：

**架构级差距（缺层，但均已在体系设计立法、属「已规划未兑现」）**：

1. 缺 damage/脏矩形出屏协议。别人家家都有（见通用结论第 2 条）；BerryOS 现役 ramfb 链宿主侧整帧轮询「先读后验」。已立法：virtio-gpu 2D 档 TRANSFER_TO_HOST_2D 行循环 + FLUSH∩scanout 求交（体系设计 §2 虚拟化层契约），兑现线在刀 3/5。
2. 缺宿主 GPU 卸载/合成层。guest CPU 软光栅 + 宿主 CPU 标量转换与合成；别人像素生产在宿主 GPU（Android/DevEco/virgl/iOS）。已立法：宿主 wgpu/Metal 单 pass 采样缩放合成（裁四案 β），兑现线在刀 6/8。
3. 缺独立显示设备模型（动态几何与事件通道）。ramfb 是「fw_cfg 描述的 RAM 区」，不是设备：无 EDID、无 config events、无 scanout 协商，分辨率两相位只能全静态、换档要重启。已立法：virtio-gpu SET_SCANOUT/events_read+CONFIG_GEN+EDID（裁七），兑现线在刀 7。
4. （小一号的架构项）静默失败可观测性缺口：launcher VMO create/commit/map 有 fail 消息面，但像素搬运下游（blit/SUBMIT 路径）没有等价的失败回显——本次恒黑「串口一条 fail 都没有」正是这个缺口的直接体现。别人设备模型里协议每步有应答（virtio-gpu 每个 cmd 有响应、ramfb cfg 重写有边界校验），错误能定位到层。

**实现细节未扩容（bug/参数类，不是缺层）**：

5. 1080×1920 恒黑本身。机制排除法：QEMU 侧无障碍（ramfb 上限 16000×12000、连续区映射、尺寸校验域远盖 1080p，串口 `FB ok`/`FBW ok`/`LAUNCH ok` 证明 guest 侧 fb 与窗口域建立成功）；宿主带宽非瓶颈（体系设计裁一：59.6GB/s 对 0.5GB/s 占 0.83%）；buddy 帽与 TextureDesc 校验已排除。嫌疑收敛到 guest 内部「像素搬运路径的尺寸相关静默失败」，头号嫌疑 = svcmgr 128KiB 平像帽（六波计划风险列表现成条目）：1080×1920×4 = 8,294,400 字节 = 63.3 个 128KiB 块（向上取整 64 块），而正常的 800×1280×4 = 4,096,000 字节 = 31.25 块（32 块）——两档恰好跨过 32 与 64 两个幂次块数边界，若分块计数器/数组按 ≤64 块（或 6 位宽度、64 项数组）设计且溢出路径静默丢弃，症状就完全吻合：几何全建立、无失败消息、fb 内容恒黑。此为机制推演假说（本调研权限止于机制对照），定谳归属 = 现场 grep svcmgr 平像分块代码的块数上限与溢出分支；配套修法是给分块路径补 fail 消息面（堵上第 4 条缺口）。注意：即便此假说不中，结论也不变——问题在 guest 某张内部表/计数器的尺寸边界，而不是任何显示架构层缺失，因为同链 800×1280 正常、更老构建出过 1080p 截图（out/berry-desktop-fullhd.png），证明现架构容纳过 1080p。
6. 「128KiB 平像帽」若确认为根因，扩帽属实现细节；但「扩帽后要不要分块上限告警」应随第 4 条一起补。

一句话总评：BerryOS 缺的架构层（damage 协议、宿主 GPU 合成、显示设备模型）全部已被体系设计 v1.0 立法并有刀序，本次 1080p 恒黑不在其中任何一层——它是现链上一张尺寸敏感的内部表（最可能 svcmgr 平像分块）加上静默失败可观测性缺口叠加出来的回归，属「实现细节未扩容」档。
