# 应用点开不出窗与窗口自消失诊断（r7 两次起机）

Type: survey
Status: current
Updated: 2026-11-24

一句话说明：desktop 机上五个现役 app（BROWSER / CONTACTS / PHOTOS / SETTINGS / TERMINAL）「点开不出窗、第二击无动作、出窗后窗口自消失」三类现象的根因诊断。两次起机（原始镜像 + 五个 manifest 临时改 `console = true` 的诊断镜像）定谳为四颗彼此独立的雷加一个设计面：应用启动期 RELEASE_WAIT 单趟撞 wmd presarb 快答 ST_BUSY 即 park；gfxdemo 退场不销窗留下全屏幽灵窗吞掉第二击；PHOTOS 样张 slab 超 berry-libc 默认 1 MiB 堆；TERMINAL 自检对 fs 礼物再 dup 被内核拒 -EACCES；窗口自消失无人移除窗，是 launcher 整帧重绘（分钟换字与任意 tap）盖掉共享 fb 上的 app 像素。

## 问题

- 点应用图标后 `eco: app <ID> it 03` 出现但长时间无窗、无退出行（BROWSER 181 s、CONTACTS / TERMINAL 120 s），PHOTOS 约 10 s 后 `exit code`。
- 同一应用第二次点击串口零动作。
- 偶尔出窗的（SETTINGS、重拉的 BROWSER）不操作几十秒后窗口自己消失，进程仍活着。
- 附带四问：`intent: hop budget cap (send)` 是谁打的、是不是错误；svcmgr 的 recycle 是不是「杀掉重拉」；系统栏导航带 / 状态带在应用窗开着时是什么颜色。

## 方法与来源

- 基线：origin/main `9649244496f6cb088d3cd457e1c90521e496ced6`（worktree `/tmp/r7-apps`，HEAD 同值）。
- boot1 = 原始产线镜像，run 目录 `1795485398-477457000-37113-host`。boot2 = 诊断镜像，仅把五个 app manifest 的 `console = false` 临时改为 `true`（worktree 已删、未入库），run 目录 `1795488200-087785000-1139-host`。改 `console` 的理由：原始构建里 `console=false` 的 app 的 stdout / stderr 走 svcmgr 私有对，被 `app_supervise` 的 drain 原样丢弃（[svcmgr main.rs](../../user/bins/svcmgr/src/main.rs) 9676-9704 行），串口上永远看不到 app 自己说了什么；boot2 让 app 的 `eprintln!` 上串口，拿到 `boot release bad st=3`、`memory allocation of 2764800 bytes failed`、`fs gift dup failed` 三条直证。
- 两次起机参考值全部在席：`VBLK ok cap=2048 slot=31`（boot1 第 119 行）、`BLKD ok n=512`（第 205 行）、`GFX ok`（第 203 行）、`err=-13` 0 行、`LAUNCH ok`（第 306 行，起机约 219 s）。
- 出窗判据：tap 前截基线桌面，tap 后每 5 s 截图，与基线做线索区 x[100,990) y[300,1500) 的像素变化比例（逐通道差 >16 计变化）；比例 ≥ 阈值即出窗。色值用同一工具在固定坐标采样。
- 证据目录 `/tmp/r7-apps-evidence/`（`key-serial-excerpts.txt` 是串口摘录总表）；两台设备均 `berry device stop --run` 收尾。下文 `boot1:N` / `boot2:N` 指各 run 目录 `serial.log` 的行号。

## 链路各环与各应用断点

- 点击分发：inputd → launcher 泵（pump.rs 440-558 收 INPUT_POLL）→ `pump_input_at` → `on_msgs`（frameloop.rs 395-433）。
- APP_SPAWN 请求：`on_click`（1261-1273）→ `queue_spawn`（641-659，置 pending + 点灯）→ 下一拍 `flush_pending_spawn`（666-690）→ `spawn_by_id_inner`（1045-1100，阻塞 RPC）。
- svcmgr 拉起：`app_serve_spawn`（svcmgr 8900-9092）→ `app_launch`（7257-7600：守卫 → fs dup → per-app wm 对 + `wm_attach_rpc` → `spawn_rootfs_elf`，gifts `[rootfs, fs, wm_cli]` 或 `[wm_cli]`）。
- 应用连窗口服务：各 app `main()` 取 `wm_present_h()` / `wm_cli_h()`（[io.rs](../../user/berry-libc/src/io.rs) 309 / 448，GIFT_H 由 crt0 io.rs 118-141 落种）→ `WM_GETINFO` 握手（browser 1257-1262）。
- 建窗：五个 app 都不建窗——全仓 `encode_wm_create_req` 调用点只有 launcher（main.rs 183 / 205）、已不在产线的 `*-app` 旧 crate 与 gfxdemo；五 app 的 SUBMIT 全是 `surface_id: 0`（browser 1614、settings 956、photos 1360、contacts 1325、berry-term 1196）→ guifbd `classify_surface`（[guifbd lib.rs](../../user/bins/guifbd/src/lib.rs) 370-390）归 AppCompat。
- 首帧提交 → 上屏：app 自带帧循环 SUBMIT → wmd `on_wm`（gui-wmd main.rs 325-371）presarb 闸 → relay → guifbd `submit`（guest.rs 1614-1744）→ `blit_and_sample`（1751-1844，AppCompat 裁带 + 带重放）。
- 断点分布：BROWSER / CONTACTS / SETTINGS 在「连窗口服务」后的启动期 RELEASE_WAIT（撞 BUSY 即 park）；PHOTOS 在建树前的堆分配；TERMINAL 在建树前的 fs 礼物再 dup；成功出窗的（SETTINGS、重拉的 BROWSER）死在「上屏之后被 launcher 盖掉」。

## hop budget cap、第二击与 recycle

- `intent: hop budget cap (send)` 的打印者是内核（syscall.rs 3753-3759）：channel send 快照发送者 intent 时 `SnapOut::Capped` 打 trace + `telemetry::intent_budget_capped()`。预算 `INTENT_HOP_BUDGET_NS` = 50 ms（[intface lib.rs](../../intface/src/lib.rs) 67），判定在 144-153：借入方（effective < declared，即被交互消息提了权的任务）持有超过 50 ms 后再 send 即降级不传播。它是调度遥测 trace，不是错误——消息照发，只是不再把交互优先级传给下一跳。BROWSER 首开 4 s 内出现 3 行（boot1:421-422、r6:397-400）是因为 svcmgr → wmd attach → spawn 这条链在 TCG 下每跳都超 50 ms；r7 所有成功 / 失败路径都伴随它，与是否出窗无因果。
- 第二击无动作：`spawn_ok ≥ 1` 后点击先过 `on_covered_tap`（frameloop.rs 424-426），gfxdemo 遗留窗（id=1，在 launcher 之前建：`WM ok` boot1:128 早于 `LAUNCH v=1` 208；launcher 的 self_wins=[2,3]）命中 `covering_app_win`（812-824）→ DESTROY + 吞击。不是「已在表里被当成前台」——那条路（svcmgr 回 err=3 `alive`）在 r7 两次 boot 都没走到，因为 `app_alive_win_present` 的 ≥2 判据此刻恰好只数到桌面一窗。
- recycle 是「杀掉重拉」：`app_spawn_recycle`（svcmgr 8860-8877）`terminate(9)`（内核打 `TERM: killed 'user_child'`）→ `app_reap_tail(killed=true)` 打 `killed` → `wm_detach_rpc` → `cbox_death_flush` 打 `cbox rec` → 回到 `app_launch` 重 spawn 打 `it 03`。重拉实例很快出窗是时序：recycle 链让 launcher 的 APP_SPAWN RPC 阻塞 6-7 s，新实例到达 RELEASE_WAIT 时 launcher 没有 in-flight present 事务，presarb 放行（boot2:707-715，`it 03` → `first frame` 7 行内完成）。

## 窗口自消失是谁移除的

没有人「移除窗」——wmd 表里本来就没有这五个 app 的窗（它们不 CREATE），进程也没退出。是 launcher 把整屏桌面重新画了一遍：触发条件 = frameloop.rs 378-392 时钟分钟换字（`set_text` 在 berry-ui A 面走 `mark_ancestors_dirty`，lib.rs 1464-1481 → layout.rs 691-746 对 Root 及全部子节点 `dmg_clip_add` 新旧界 = 整视口），周期 = 分钟沿 + ≤ `IDLE_CAP_NS` = 10 s（pump.rs:94）；以及任何 tap 的首 MOVE 事件（damage 空集 → `wake` 置 FULL，lib.rs 2613-2615）。不是窗口服务空闲策略（wmd 没有 idle 回收，`WMD_IDLE_CAP_NS` 只是 wait 帽），不是启动器回收（`app_spawn_recycle` 只在再次点击同 id 时发生，会打 recycle 行）。

## PHOTOS、SETTINGS、TERMINAL、CONTACTS 逐问

## 未定位点

1. app 的 SUBMIT / FRAME_CALLBACK 阶段同样没有 ST_BUSY 重试（browser 1626-1630 `parse_submit_ack` 失败即 fail；「settings 镜像」同形），理论上出窗后下一次与 launcher 事务撞车也会 park——r7 两次 boot 的成功实例都没撞上，是否会在更长运行里发生未证实。状态：已修（2026-11-24，三处 rpc 点均包成 ST_BUSY 重试环，见「修复状态」）。
2. launcher 呼吸灯在 boot1 的亮灭节拍与 `covered_by_app()` 1 Hz 查表不完全对齐（有连亮 10 帧、连灭 5 帧的段），按 P2 入途帧的呈现延迟解释，未证实；不影响结论（亮过 = 幽灵窗曾在表）。
3. 需 owner 裁决：五个现役 app 不建 wmd 窗（surface_id=0 AppCompat），而 launcher / svcmgr 的「重开 = 聚焦」「back 键 DESTROY」「已活判据 ≥2」「覆盖态收盖」全建立在「每个 [ui] app 一枚 APP 层窗」之上（svcmgr 5965-5967 注释明文）。要么让五 app 补 `WM_CREATE`（照 gfxdemo 442-457 形，surface_id 用返回的 wid → guifbd 走 WinApp 档不裁带），要么把这些判据改成按 apps 通道属主而非窗表——这是设计题。
4. 需 owner 裁决：v1 共享 fb 下 launcher 任何整帧（分钟换字、任意 tap）都会盖掉 app 像素。短修可在 frameloop.rs:378 时钟换字前加 `if self.covered_by_app() { 跳过 }`（603 `on_key` 已有同款门），但前提是第 3 条先让 app 真有窗；或给 launcher 开 berry-ui `s7` 特性让 `set_text` 走 ChangeMask 增量（lib.rs 1426-1463 B 面）——两者都在并行会话领地，本诊断只给指针。

## 适用边界

- 基于提交 `9649244496f6cb088d3cd457e1c90521e496ced6`（origin/main）；desktop 机（`berry device` desktop profile，QEMU TCG，256 MiB，1080x1920），宿主同时有 1-2 个并行 QEMU，TCG 时序（5 s 租约、分钟沿存活）随宿主负载漂移。
