# 并行双机下内核致命异常符号化诊断（8c76e042，desktop 机双 VM 并行）

Type: survey
Status: current
Updated: 2026-11-24

一句话说明：desktop 机双 VM 并行时一台的内核打出 `=== EXCEPTION: sync (current-EL SPx) ===` 致命异常并 halt，桌面起不来。用同提交重建内核加 256 MiB `ram.bin` 转储把 PC `0xffffff8040094190` 符号化到 `exc_sync_el0+0x84`（恢复用户态现场的 `ldp x0, x1, [sp]`），定谳成因（机制置信度高）：`probe_el0` 的 `klock_exit` 无条件开中断，使 EL0 返回 stub 在写完 ELR / SPSR 之后、`eret` 之前被 IRQ 打断，ELR 被覆写成 stub 内地址，`eret` 后 SP 每轮 +0x120 爬升 325,120 轮直到撞上 RAM 顶无映射地址——受害线程是一个 std 用户进程（最像 berry-launcher，未证实）。并行是放大器不是必要条件。

## 问题

双 VM 并行起机，一台串口出现致命异常转储后 `-> fatal, halt`，桌面起不来；另一台正常。需要把 PC / FAR 符号化，判断成因、与并行的关系、修法在哪。

- 运行目录 `~/berry-live/run/1795465141-471989000-53415-host/`：serial.log 508 行、`ram.bin` 256 MiB（物理内存转储）、meta.json（desktop profile、256 MiB、镜像 `/tmp/r6-final-base.img`）。
- 本路未起任何 QEMU（复现未执行）；worktree 与隔离 target 已删。
- 总审复核：转储 38 行与该 run 目录 serial.log 第 290-327 行逐字一致；抽检 13 处 kernel / arch / linker / svcmgr 文件行号在 `8c76e042` 与 `96492444`（origin/main）两处内容相同。

### 对任务前提的更正

- `pressure p1` 只出现在异常之后（第 328、378 行），之前没有；它是 svcmgr 主循环的压力沿观测行（[svcmgr main.rs](../../user/bins/svcmgr/src/main.rs) 589），不是崩溃前的内存压力证据。
- `-> fatal, halt` 之后系统没有停：`SCHED picks` 计数继续增长（第 329 行 UNSPEC=32994 → 文件末行 UNSPEC=73538，总审按现存 508 行文件核出；诊断报告记的是「→ 第 509 行 72724」，与其读取时的行数略有出入），说明 halt 没有真正停机（成因见下文第 5 步）。

### 次生异常

第 336-375 行：`user_child`（x9=`0x50475044` = "DPGP"）在 PC=0x102c 读 0x6000 缺页，等供给 30 s 超时（第 334 行 `dpg: pager watchdog fired`，[dpg.rs](../../kernel/src/dpg.rs) 252 `PAGER_WATCHDOG_SECS`=30）后被杀。它与主异常的关系未证实。崩溃前 svcmgr 两条自检已是降级行（第 283 行 `eco: dpgs dmap` = svcmgr main.rs 4026 vmar_map 失败；第 284 行 `eco: dpgn sp3` = 4217 第三子 spawn 失败），降级路径本就泄漏子进程，孤立子无人供给同样会 30 s 后被杀。

## 地址换算

- 内核高半基 `KERNEL_VA_BASE = 0xFFFFFF8000000000`（[linker-aarch64.ld](../../tools/linker-aarch64.ld) 11；`nm` 显示 `ffffff8000000000 A KERNEL_VA_BASE`）；链接脚本约定高半 VMA = 基 + LMA。
- 程序头实证（`objdump -p`）：高半 r-x 段 `vaddr 0xffffff804000d000 / paddr 0x4000d000 / filesz 0x955b4` → vaddr − paddr = 0xffffff8000000000。
- 所以 `PC 0xffffff8040094190` 的 ELF 地址就是它本身（LMA 0x40094190），落在 .text 的 r-x 段内。
- `SP/FAR 0xffffff8050000000` → PA 0x50000000 = `RAM_TOP`（[lib.rs](../../arch/aarch64/src/lib.rs) 45）；内核直映循环 `while pa < RAM_TOP`（[mmu.rs](../../arch/aarch64/src/mmu.rs) 165）半开，所以 0x50000000 是第一个无映射地址。ISS=0x6 → DFSC=0b000110 = L2 翻译缺页，与「整块 2 MiB 无 L2 描述符」吻合。

## 符号化结果

| 地址 | 结果 | 证据 |

| 调用者 | 该 stub 由向量 0x400（lower-EL, AArch64, Sync）`b exc_sync_el0` 进入（trap.rs 156）；此刻已经从处理函数返回，正在恢复用户态现场 | trap.rs 303-308 |

## ram.bin 交叉验证

1. 栈顶帧与串口逐字一致：PA 0x4ffffee0–0x4ffffff0 正是 `exc_sync_spx` 的 288 字节帧，x0…x30、esr=0x96000006、far、elr=0x…94190、spsr=0x345、sp=0x…50000000 全部对上。
2. 受害线程的真正内核栈不在这里：扫描全 RAM 83 个带合法 `ctx.lr` 的 Task 记录，唯一一个 `ctx.sp` 落在自身 16 KiB kstack 之外的：PA 0x4a6ad000，`name="user_child"`，`kstack=[0x4a6b0000,+0x4000)`，`ctx.lr = sched::on_irq_tick+0x8ac`，`ctx.sp = 0xffffff804ffffc80`（`STACK_SIZE`=16 KiB：[task.rs](../../sched/src/task.rs) 29）。
3. 它真正的 EL0 异常帧完好地留在自己栈顶 PA [0x4a6b3ee0, 0x4a6b4000)：`esr=0x92000047`（EC 0x24 D-abort(lower)，DFSC 7 = L3 翻译缺页）、`far=0x8f7000`、`elr=0x7a7e3c`、`spsr=0x2000000`（EL0t）、`sp=0xc05070`，x19 / x26 / x27 = 0x8f06f0 / 0xbf4000 / 0xc309a0（用户堆指针）。即一个 std 用户进程首触匿名页 VA 0x8f7000，走了内核按需缺页探针。
4. halt 不是真停机：紧贴栈顶帧之下的帧 [0x4ffffd80, 0x4ffffea0) `elr = 0xffffff8040099f14 = exception_sync+0x404`，反汇编是 `0x99f10 wfi; 0x99f14 b 0x99f10`（内联的 `halt()` 环）。致命异常后该线程在 wfi 环里被 IRQ 反复唤醒，IRQ 帧被压到 RAM 顶部。
5. SP 爬升算术精确吻合：从该线程真实栈顶 V=0x4a6b4000 到 0x50000000 的差 `0x594c000` 恰好 = 325,120 × 0x120（整除；V mod 0x120 = 0x50000000 mod 0x120 = 0xe0），所以最终 FAR = SP = 0x50000000 一字不差。
6. "mmap" 的家：PA 0x4ffff000 起是用户态链表节点，64 字节一条：`{"mmap", next, prev, (n<<32)|1, lo, hi, 0, 8}`，lo / hi 是 RAM 物理段（如 0x4fe20000–0x4feaffff）。致命帧及之后的 IRQ 帧正盖在这页上（0x4ffffb70 以上已被踩）。

## 成因判断与置信度

机制置信度：高。

`load_frame_el0`（trap.rs 258-282）的出口序是：先把帧里的 ELR_EL1 / SPSR_EL1 / SP_EL0 写回（0x94178–0x9418c），再取 x0–x30、`add sp, sp, #288`、`eret`（0x941d4）。从 `msr elr_el1` 到 `eret` 共 22 条指令，期间 PSTATE.I 是开的（致命 SPSR=0x345 → I=0）。I 之所以开着，是 EL0 缺页探针 `probe_el0`（dpg.rs 267）用裸 `klock_enter()`（279）配对 `klock_exit()`（ZFOD 快路径 316、等页醒来后 441），而 `klock_exit` 无条件 `enable_irq()`（[kern_lock.rs](../../arch/aarch64/src/kern_lock.rs) 214-217 → lib.rs 449 `daifclr #2`），回到 stub 时 I 仍为 0。

时序：

1. 线程在 EL0 首触 0x8f7000 → L3 翻译缺页 → `exc_sync_el0`，SP_EL1 = 自身栈顶 0x4a6b4000，帧落 [0x4a6b3ee0, 0x4a6b4000)。
2. `exception_sync_el0` → `demand_fault_probe_el0` → `probe_el0` 处理完，`klock_exit` 开 I，返回 true。
3. stub 写完 ELR / SPSR / SP_EL0 之后、`eret` 之前（PC ∈ [0x94190, 0x941d0]），IRQ 落入（I 开着）。IRQ 入口硬件把 ELR_EL1 / SPSR_EL1 覆写为（stub 内 PC, 0x345）；`exc_irq_spx` 的 `load_frame` 原样恢复的也是这对值，用户的 ELR / SPSR 从此丢失。
4. `eret` 回到 stub 内 PC、EL1h、SP=0x4a6b4000 → 再跑一遍 `ldp…; add sp,#0x120; eret` → 又回到同一 PC，SP 每轮 +0x120。循环 325,120 轮（约 7.8M 条指令，毫秒级），沿途只读不写，直到 [0x50000000] 无映射 → 本次致命异常。寄存器里的 "mmap" / 0x48000000 / 0x48ff6fff 等就是最后一轮从 RAM 顶页读出的用户数据（x0 / x1 像地址范围——像，但它们是 RAM 顶页里的记录内容，不是函数参数）。
5. `exception_sync` 走 fatal（`cbox_record` + dump + `halt()`，trap.rs 400-403）。`halt()` 是裸 `wfi` 环（lib.rs 482-487）且 I 仍为 0 → 被 tick 反复唤醒，调度器继续跑别的任务，而本线程的 IRQ 帧持续压在 RAM 顶页上，踩坏上节第 6 点那页用户数据。

同一类竞态仓库里已有档案：`user_entry_trampoline` 注释原话「`msr elr_el1` 与 `eret` 退役之间开 IRQ 窗：IRQ 入口把 ELR_EL1 覆写为本 trampoline 内返回地址……屏蔽态写 ELR / SPSR 后 eret 原子落地，窗口消灭」（[task.rs](../../arch/aarch64/src/task.rs) 332-337）；`KlockIrqSaveGuard` / `klock_enter_irqsave` 文档写明「同步异常探针 `dpg::probe` / `probe_el0` 专用」（kern_lock.rs 322-346）——但 `8c76e042` 与 `96492444` 两个提交上两个探针都没换上，该守卫全仓只有 [ktest.rs](../../kernel/src/ktest.rs) 13807 自测在用。`probe`（EL1 臂，dpg.rs 149 / 198）同样裸用，`exc_sync_spx` 的 `load_frame`（trap.rs 202-224）是同样的窗口。

受害线程是谁：Task 名是通用名 `user_child`（[syscall.rs](../../kernel/src/syscall.rs) 2248），无进程名。用户态 PC=0x7a7e3c、堆 0x8f06f0–0xc309a0，是大镜像 std 进程做堆首触（典型是 Vec 扩容）。按串口邻接，崩溃前最后一行活动是 `launcher: icon decode BadMagic { got: [0, 0, 0, 0] }`（第 285 行，[icons.rs](../../user/bins/berry-launcher/src/icons.rs) 332 / 336），最像 berry-launcher 主线程——未证实。它死后 svcmgr 监督看不到退出事件，桌面自然起不来；svcmgr 主循环本身还活着（之后仍打 `pressure p1`）。

为什么只在两台并行时出现（置信度：中）：窗口单机也存在，命中是概率事件——每个经探针返回的 EL0 缺页都有约 22 条指令的敞口。`berry device` 在 macOS 上默认加速器 auto → HVF（[qemu.rs](../../tools/berry/src/qemu.rs) 57-61）；meta.json 未记 accel，所用加速器未证实。HVF 下虚拟定时器可在任意指令边界打断。双 VM 并行时宿主争抢让「每单位客户机工作对应的墙钟 tick 数」上升，且堆增长带来的首触缺页更多，命中概率随之上升。并行是放大器，不是必要条件。`launcher: icon decode BadMagic` 与本异常无关（图标魔数是 "BYI1"，[icon.rs](../../user/berry-gfx/src/icon.rs) 120，全零 blob 是另一回事）。

## 修法指针

`kernel/` 与 `arch/` 属并行会话领地，只报告。诊断报告的修法指针只到达本路第 1 条，原样转写：

1. 结构性堵窗（首选）：trap.rs 的 `load_frame`（202-224）与 `load_frame_el0`（258-282）在写 `ELR_EL1` / `SPSR_EL1` 之前先 `msr daifset, #2`，屏蔽态下写完再 `eret`（eret 弹 SPSR 原子恢复）。

## 复现结果

复现未执行：诊断路未起任何 QEMU，总审路也未起针对本异常的复现机（两次起机均为应用出窗端到端，各自 `EXCEPTION` 0 行）。复现条件（双 VM 并行 + 特定提交）下的再触发概率未量化。

## 适用边界

- 基于 `8c76e042`（运行内核）与同提交重建内核；`96492444`（origin/main）上 `kernel/src/dpg.rs` 两个探针同形，结论对两者都适用，抽检行号两处相同。
- desktop 机（`berry device` desktop profile，256 MiB），双 VM 并行；加速器未证实。
- ram.bin 只有一份、一个受害线程，成因链的第 3 步（IRQ 落入的精确时刻）由 SP 爬升算术与帧内容反推，没有直接 trace。
- 次生异常与主异常的关系、受害线程的进程名、并行放大系数三项均未证实。
