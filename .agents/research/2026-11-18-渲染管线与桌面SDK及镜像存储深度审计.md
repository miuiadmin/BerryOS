# BerryOS 渲染管线、模拟器、桌面窗口、SDK 与镜像存储全栈深度审计

Type: survey
Status: current
Updated: 2026-11-18

一句话说明：基于 2026-11-18 工作树实存源码，对模拟器呈现壳、客机 2D 图形光栅引擎、GPU 加速协议边界、窗口合成器、声明式 UI 与应用 SDK、桌面交互系统以及镜像与文件系统产线进行全量源码级缺陷取证，与 [莓核全核深度体检报告](2026-11-18-莓核全核深度体检报告.md) 共同构成全栈零妥协重构的完整证据基座。

## 问题

在微内核、IPC 与基础调度器之外，决定开发者与终端用户直观体验及系统上限的上半栈面临五个核心拷问：

1. 模拟器窗口与远程桌面为何存在局部更新丢帧、帧率卡死 33fps、跨平台 GPU 合成退化与屏幕旋转销毁会话等顽疾？
2. 客机图形渲染引擎 `berry-gfx` 与显示服务 `guifbd` 为何在架构上无法呈现抗锯齿圆角、柔和阴影、实时背景毛玻璃、平滑矢量文字以及真多窗口重叠过渡动画？
3. 现役 `virtio-gpu 2D` 加速路径真实卸载了什么、什么仍然 100% 压在客机 CPU 上，以及为何每应用独立全屏像素 VMO 模型在 128MiB 至 512MiB 端侧设备上存在物理内存死胡同？
4. 应用开发者使用现行 SDK（`berry-ui`、`berry-appshell`、`berry-libc`）构建真实交互应用时，为何仍面临千行级样板代码、64 字节文本上限、256KiB 静态堆耗尽、中文输入法空白与同步 I/O 卡死帧循环等障碍？
5. 全量内存驻留 `rootfs.cpio`、9 文件上限 RAM-fs、根目录 8.3 大写 FAT12 与超长串行构建脚本如何制约冷启动速度、存储可靠性与工程迭代效率？

## 方法与来源

本审计以 2026-11-18 工作树源码与现行设计标准为直接样本，执行三层核验：

1. **现行规范与历史调研状态核验**：核查 [显示与加速体系设计](../../docs/显示与加速体系设计-v1.1.md)、[刷新率体系规范](../../docs/刷新率体系规范-v1.0.md)、`docs/桌面沉浸式设计规范-v1.0.md`、[显示管线调度集成指南](../../docs/显示管线调度集成指南-v1.0.md)、[GUI 渲染调研](../../docs/GUI渲染调研-2026-10-v1.0.md)、[应用 API 全景](../../docs/应用API全景-v1.0.md)、[UI 组件清单与实施规划](../../docs/UI组件清单与实施规划-v1.0.md) 与 [模拟器方案规划](../plans/2026-11-14-模拟器方案规划.md) 的头块状态及未闭合条款。
2. **全链路源码逐模块直读**：逐行核查宿主模拟器壳 `tools/berry/src/`、图形引擎 `user/berry-gfx/src/`、GPU 协议 `user/berry-gpuproto/src/`、显示合成服务 `user/bins/guifbd/src/`、窗口管理守护 `user/bins/gui-wmd/src/`、UI 框架 `user/berry-ui/src/`、应用壳 `user/berry-appshell/src/`、桌面启动器 `user/bins/berry-launcher/src/`、现役系统应用 `user/bins/{settings,browser,files,photos,contacts,messages,camera,berry-term}/` 与 `user/bins/{settings-app,browser-app}/`、C 运行时 `user/berry-libc/src/`、文件系统服务 `user/bins/fsmgr/src/`、调度运行队列 `sched/src/` 以及根构建脚本 [justfile](../../justfile)。
3. **像素带宽、内存足迹与复杂度定量核算**：以 1080×1920 BGRA8/RGBX8 单帧 `8,294,400B`（7.91MiB）及 60Hz/120Hz 帧预算（16.67ms / 8.33ms）为基准核算内存、拷贝遍数与扫描复杂度。

## 结论

1. **模拟器渲染处于分裂过渡态**：共享内存扫描路径存在高概率漏帧缺陷且每变化帧在 CPU 执行双循环逐像素转换与 8.29MB 堆分配；VNC 路径受 QEMU 服务端 30ms 定时器硬顶限制锁死在 33fps；`wgpu` 呈现器硬编码仅启用 Metal 后端、每帧重建 GPU `BindGroup` 且未接入 D-Bus `ScanoutMap/UpdateMap` 零拷贝脏矩形流；Apple `Virtualization.framework` 原生窗口路径尚未落码。
2. **客机 2D 光栅与窗口合成存在视觉与内存双重代差**：`berry-gfx` 全管线无 8-bit Alpha 混合、无解析抗锯齿、无阴影与渐变、无实时背景模糊、仅支持 1-bit 二值位图字形且核心填充走逐像素双重边界检查标量循环；`guifbd` 无每窗口独立后备表面，采用单全局帧缓冲覆盖写加顶底静态条带重放，无法支撑浮动多窗 Z 序重叠、窗口缩放弹簧动画与多任务实时缩略图；每应用自持全屏像素 VMO 在多应用并发下将迅速耗尽低内存设备物理页。
3. **GPU 加速仅完成「搬运通道卸载」而「像素计算卸载」为零**：`virtio-gpu 2D` 协议不含任何绘制与混合原语，100% 像素生成仍压在客机 CPU；全仓尚无 Virtio-GPU 3D（Rutabaga / Venus）或面向宿主 `wgpu` 的半虚拟化显示列表硬件渲染通道。
4. **SDK UI 停留在底层命令式 Arena 阶段**：缺乏细粒度响应式状态与声明式组件组合，真实设置页需编写逾千行手写同步与 RPC 样板代码；内联文本硬上限 64B、默认静态 BSS 堆仅 256KiB、缺异步 UI 事件执行器与中文输入法架构。
5. **显示实时链与调度器脱节、运行队列仍为线性扫描**：显示与输入关键守护进程全部以 `intent = 0` 启动，未接入 VSync 截止期 EDF 或跨通道帧令牌优先级传递；调度器 `Runqueue` 在选核、限流解冻与带执法处仍依赖侵入式双向环 $O(n)$ 线性扫描。
6. **镜像与存储尚处原型形态**：全量 `rootfs.cpio` 常驻物理内存挤占数十 MB 空间，RAM-fs 硬限 9 文件×16KiB，持久化卷受限于 FAT12 根目录 8.3 大写整文件暂存覆写，构建链串行编译数十个碎片工作区。
