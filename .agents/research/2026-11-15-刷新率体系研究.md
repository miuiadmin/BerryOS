# 刷新率体系研究（60/120 基准、30-480Hz 档谱与 LTPO 可变刷新率）

Type: survey
Status: current
Updated: 2026-11-15

一句话说明：回答「BerryOS 以 60/120Hz 为基准、向下支持 30Hz、向上支持 165/180/240/480、并支持 LTPO 式可变刷新率」离现状有多远、缺哪几层、行业怎么干、怎么分刀落地。

## 问题

owner 2026-11-15 提出显示体系目标：以 60 帧 60Hz 与 120Hz 为基准做；向下支持 30Hz；向上支持 120 以上的 165、180、240、480；并支持 LTPO 可变刷新率。本研究盘点现状管线离该目标的距离，并从行业（Apple ProMotion、Android MRR/ARR、Linux DRM/KMS、VESA/HDMI/DP 标准）提取可移植的档位模型、框架形态与契约面，给出分层缺口与分刀建议。

## 方法与来源

workflow 模式七路并行（wf_f2cc8c24-5c1，7 agent、275 次工具调用）：读仓三路（显示管线 guifbd/gui-wmd/fw_cfg 链；内核时间 timer/sched/idle；GUI 节拍 berry-ui/launcher/输入链）+ 外研四路（LTPO 产业实践；Android 刷新率框架；Linux DRM/KMS 与显示标准；高刷新物理与虚拟显示时序）。仓内结论以 rescue/cbox 分支快照为准（主树 guifbd 已拆 main/guest/lib 三文件、概念一致）；外部结论以官方文档/规范原文/维护者口径优先，URL 见证据与出处节。

## 结论

### 现状判决：刷新率概念「三无」

- **无通路**：刷新率数值在系统里物理上不流动。fw_cfg `opt/berry/display=WxH[@Hz]` 的 @Hz 后缀在内核解析处被剥离丢弃（`kernel/src/main.rs:214` `s.split('@').next()` 只取几何段）；boot info VMO 六域、GOP handoff 五域、present GETINFO 应答三处协议面都无率域；60Hz 退化为三处互不知情的编译期常量——guifbd `SOFT_VSYNC_NS`（`user/bins/guifbd/src/main.rs:77`）、launcher `VSYNC_NS`（`user/bins/berry-launcher/src/frameloop.rs:92`）、berry-ui `DEFAULT_VSYNC_PERIOD_NS`（`user/berry-ui/src/lib.rs:155`）同为 16_666_666，客户端帧钟纯本地推算与服务端软 vsync 无相位关系。改任何刷新率今天等于重编三个件。
- **无锁钟**：呈现不与 vsync 绑定。guifbd blit-at-SUBMIT：SUBMIT 处理内同步 CPU blit 应答即呈现（`main.rs:530-657`），`rate_hint` 与 `target_present_ns` 两域被显式忽略（`:441-442`）；软 vsync 通道（REG_VBLANK/VBLANK_WAIT）真 work 但唯一消费者是 gfxdemo 一次性 smoke 序，稳态零订阅；COMMIT 排队与 PREPARE fence 是留位空壳。帧的实际可见时刻 = 渲染完成时刻，帧率上限 = 流水线尾延迟倒数而非拍点。
- **无仲裁**：投票-仲裁-执行链只有第一环。VOTE 票面 wire 完备（sticky + scene + min/max/preferred_hz u16×3，`berry-guiproto/src/lib.rs:645-654`），berry-ui `VoteBallot` 常量已产票（idle 停帧粘滞 / interacting {60,120,120} 已表达 120Hz 意图 / anim_active {30,120,60}），但服务端收票即记账零仲裁（`guifbd main.rs:503-521`「仲裁策略挂 GUI-6+」），无档位表、无切换执行点、POWER_MODE 同为空转。
- 另：窗口层 gui-wmd 是纯几何策略表 + 同步字节中继，零节拍概念，且单线程中继形态承载不了 vblank 类阻塞调用——多窗 SYSTEM 合成路线的 pacing 层整层空白。

### 底座比预期厚：已兑现的地基

- guifbd 软 vsync 骨架完整：事件驱动 serve 循环 deadline = min(下次软 vsync 点, 10s)，零唤醒不变量（无 armed 无 parked 则零调度），名义点 + 跳过已过点的追赶语义与真实丢 vblank 行为一致（`main.rs:282-322,938-969`）。
- 内核读侧原语完备：CNTVCT 62.5MHz（16ns 粒度）且 `CNTKCTL.EL0VCTEN` 已开、EL0 可 `mrs cntvct_el0` 零陷阱直读；`sys_clock_read`（SVC 0x61）单调纳秒全链约 63 周期（TCG 墙钟约 2µs）；`thread_sleep`（0x37）绝对时刻入睡；EDF 式 deadline 调度带（policy=3：period/budget/vdeadline 周期自续）；tickless idle——SLEEPQ 最近 deadline `arm_at` 精确 park + masked-wfi。
- berry-ui 已是 request-driven 帧循环引擎：RUN/SETTLE/IDLE 三态停帧（IDLE 撤定时器睡事件）、damage K≤8 脏区增量帧、credits≤2 背压、输入重采样 expected−5ms（Android 同式）、expected/actual 双轨 + jank/deadline_miss/spinup_late 遥测全部 day-one 在位（遥测无消费者）。
- 文档层路线图已定案（`docs/GUI渲染调研-2026-10-v1.0.md:73-102` 三档映射：#1 vsync v1 软时基→v2 present mode 三档→v3 硬件 vsync/TE；#10 帧率投票 v1 API 位→v2 仲裁实装→v3 LTPO/ARR）——实码全部停在 v1 行。

### 行业裁决：档位模型、框架形态、契约面

- **档位模型 = 基频整数分频**：Android 15 ARR 是最佳蓝本——单一显示模式内 VSync 率与刷新率解耦，面板跑在 TE（tearing effect）频率的整数分频档上（文档例：TE 240Hz 基频 → 120/80/60/48/40/30 档），帧可在超过最小帧间隔后的任意 VSync 整数倍时刻呈现。Apple ProMotion 实测同构：iPhone 快速滚动常跑约 80Hz 而非 120，档位恰为 240 基频整数分频集。对 BerryOS：产品族档位取整除族 30/60/120/240/480（24/30/60 内容全整数均匀分频、零 judder）；165/180 对 24fps 非整除（165/24=6.875），定位为测试族——专测混合 cadence 下动画与提交面的稳健性。
- **LTPO 本质与省电账**：LTPO = LTPS + IGZO 混合背板（开关用 LTPS、像素保持用低漏电 IGZO），低漏电是 1-10Hz 档的物理前提；纯 LTPS 面板最低档钉在约 60Hz。档位表必须来自面板能力宣告而非软件硬编码。省电大头在降档不在拉高：Samsung 实测 10Hz 档面板功耗仅为 120Hz 的 60%、整机屏幕功耗最多省 22%——「60/120 基线 + 30Hz 降探」的优先级排序正确。AOD 1Hz 是组合拳（1Hz 档 + 精简帧 + OLED 黑底 + 低功耗驱动），归电源态机不归帧循环。PSR/面板自刷新意味着「零帧成本维持画面」：静止时系统可以完全不出帧，guifbd 零唤醒不变量已是软件雏形。
- **框架形态（投票→仲裁→执行三层）**：应用 advisory 投票（Android `Surface.setFrameRate` / iOS `CAFrameRateRange` 三元组——BerryOS VOTE 票面与 Apple 三元组几乎同构，API 形状已被行业验证）；单一裁决点（SF 形态：整数倍偏好打分、primary range 单档驻留迟滞防振荡、min/max 全局钳制、touch boost 独立超时窗、平台兜底拍板防单一内容票钉死全屏）；执行带切换成本（MRR `setActiveConfigWithConstraints`：desiredTimeNanos 预约时刻 + refreshRequired 刷新帧 + onVsyncPeriodTimingChanged 生效 timeline——切档不是瞬时原子操作）。ARR `notifyExpectedPresent` 预告机制让面板提前就位目标档，消「升档迟一帧」，对 30Hz 降探后的首帧延迟尤其关键。
- **契约面四件套（DRM/KMS 综合）**：①能力枚举——完整时序元组（宽高+像素时钟+消隐+极性）而非 WxH@rate 三元组、vrr_capable 三态（缺属性=缺支持，不与「支持但关闭」混淆）、{min,max}_refresh_hz 区间对、链路带宽/压缩位、节拍归属位（panel-driven vs host-driven）；②事件源——每显示设备帧计数器 + 单调 ns 时间戳的 vsync/presented 事件流，无中断硬件的官方出路是定时器合成 fake vblank（`drm_crtc_state.no_vblank` 形态）；③原子模式切换——TEST_ONLY 纯校验 + 非阻塞提交（单飞行中，忙则 EBUSY）+ MODESET 显式声明；④帧呈现回调——presented 时间戳 + seq + 当前 refresh_ns（Wayland presentation-time 形状），VRR 切档后旧周期立即失效。
- **QEMU 车辆判决**：ramfb 协议零时序语义（QEMU 显示维护者原话：极简设备、framebuffer 存 guest 内存、无任何翻转/事件语义）；QEMU 宿主窗口对 guest 画面的采样节拍是编译期常量 30Hz（`GUI_REFRESH_INTERVAL_DEFAULT`）与 guest 想要的频率无关；virtio-gpu 规范同样没有 vblank/扫描时序事件（唯一异步事件是显示器配置变化）。三候选排除后唯一可开发可测的是 guest 侧定时器合成帧时钟——guifbd 现行 SOFT_VSYNC 方向正确，问题只是权威藏在服务私有常量里，应升格为「虚拟面板设备」所有（一事实一归属）。任何时序断言必须锚 guest 时钟（presented_ns 序列），不能以宿主看到为准。
- **120Hz 的相位与节奏工程**：Android 用一个硬件 vsync 经 DispSync 软件 PLL 派生 app/SF 两个相位错开的软信号（Pixel 4 实测 60Hz 下 app 醒在 vsync 后约 2ms、SF 后约 6ms；90Hz 下 SF 相位收到约 1ms 保 10ms 合成窗，app 走 render-ahead 2 帧声明未来呈现时刻）。管线深度公式：延迟 = 级数 × 最长级——现状 blit-at-SUBMIT 是深度 1 延迟最优极端，演进时双缓冲 + 呈现时刻做默认、深度当每应用可调策略。动画/物理面应采固定时步累加器（fix your timestep）：仿真与渲染解耦后 60→120→LTPO 切档动画时长不变、回放可复现（AI 测试友好化同构）。动效时长量化到整帧数（250ms → 15 帧 @60Hz）避免尾帧抖。

### 设计映射：五层缺口与分刀建议

- **层 0 率通路（小刀）**：fw_cfg @Hz 不再丢弃（内核解析保留率域）→ boot info VMO / GETINFO 应答增率域 → 三处 16_666_666 硬编收敛为单源（服务端下发、embedder `set_vsync` 注入——GUI-3 帧循环契约「协商倒数」的既有哲学顺势落地）。
- **层 1 虚拟面板设备（关键新件，QEMU 侧）**：把 guest 自合成帧时钟从 guifbd 私有常量升格为设备语义，最小接口 = caps（档位表：产品族 30/60/120 + 测试族 165/180/240/480 + LTPO 区间与 HOLD/自刷新位）+ 寄存器（current_hz、vote 三元组、切换 ACK 与可配生效延迟——切档经 N 帧生效且可丢一个 vblank）+ vsync 事件（seq + ts_ns + refresh_ns）+ 模式（FREE 自由时钟 / HOST_LOCK 留位 / DETERMINISTIC 可复现测试）+ 故障注入（丢帧、相位抖动、切档丢帧）。30-480Hz 与 LTPO 的调度策略由此在仿真上可开发可测（QEMU 降档零真实节能，验证的是决策正确性与切换平滑度）。
- **层 2 服务端仲裁与呈现语义（对齐 GUI-6+ 既有挂账）**：仲裁器落地（票合并 + 整数倍打分 + 最小驻留迟滞 + 升快降慢非对称 + 全局钳制 + touch boost + LFC——内容帧率跌破 min_hz 时整数倍重发上一帧，max ≥ 约 2×min 否则 LFC 振荡）；present 回执升级 presentation-time 形状（presented_ns + seq + refresh_ns）；SUBMIT 的 target_present_ns/rate_hint 从显式丢弃转为预告消费（next_frame_hint 语义）；latch-at-vsync/双缓冲/异步呈现后端沿既有「异步后端刀」挂账推进。
- **层 3 内核**：最硬缺口是忙核高精度定时——超时摘除今天只在 10Hz slice tick 里跑，授片处取 min（最早超时， 片终点）留后未落（`kernel/src/timer.rs:16-18` 自注），忙核上 thread_sleep 最迟 100ms（TCG 约 200ms）才醒，比 60Hz 帧间隔粗一个数量级；补 timer slack/唤醒合并原语（LTPO 降档时把散布定时聚合成单次醒——设计承诺 v1 day-one 未落）；无定时器对象、无任何 vsync 内核感知。远期：真硬件 TE/vsync IRQ、DVFS/PM governor（现只有 WFI 一档）。
- **层 4 应用面**：动效固定时步化 + 时长整帧数量化；帧回调升 Choreographer 形（附本帧 deadline + 预期呈现时刻）；刷新率查询 + 订阅（不硬编、不缓存跨切换的查询结果）。
- **分刀序建议**：v1 = 层 0 + 层 1（率通路 + 虚拟面板 + 档位表；idle 停帧已有零成本继承）→ v2 = 层 2 主体 + 层 3 忙核 hrtimer（仲裁/LFC/迟滞/boost/切档 timeline）→ v3 = 真硬件（TE/PSR/LTPO 面板、AOD 1Hz、带宽预算含 DSC）。

## 适用边界

仓内结论以 2026-11-15 rescue/cbox 分支快照为准——主树 guifbd 三文件重构与 SYSTEM 带合成方向已在推进，节拍相关结论按概念迁移不按文件形态；外部数据为厂商口径与社区实测，非 BerryOS 实测；QEMU 侧判决限 ramfb 与 virtio-gpu 现行规范（QEMU 侧未来新增带时序语义的显示设备不在本判决内）；本研究的五层缺口与分刀建议已于同日立法——规则见 [`docs/刷新率体系规范-v1.0.md`](../../docs/刷新率体系规范-v1.0.md)（ADR #65），刀谱见 [`../plans/2026-11-15-刷新率体系实施分刀方案.md`](../plans/2026-11-15-刷新率体系实施分刀方案.md)，后续以彼为权威，本档只存事实与依据。
