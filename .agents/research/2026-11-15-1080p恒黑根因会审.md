# 1080p 恒黑根因四路会审（workflow 五代理裁决）

Type: survey
Status: current
Updated: 2026-11-15

一句话说明：2026-11-15 晚 LAN 演示中 1080×1920 桌面恒黑（串口全绿、帧缓冲 md5 不变、480×1000/800×1280 同镜像「正常」）的根因会审——四路并行取证（客机像素通路逐行法证/内核显存审计/架构文献对照/业界机制调研，workflow 五代理）加裁决路，结论：**不是分辨率/内存/分配器问题，是五键导航条合入后桌面 a11y 挂钩数 34 超过 `A11Y_MAX=32` 的容量回归**，修复提交已在并行分支存在未回合；本文同时纠正先前两个错误归因（wave10 笔记的「buddy 4MB 帽」与调研路的 svcmgr 假说）。

## 断点链（五环，全部现场复核）

1. **容量常数**：[user/berry-ui/src/lib.rs:211](../../user/berry-ui/src/lib.rs) `pub const A11Y_MAX: usize = 32`——a11y 侧表满兼任「Ui 容量域满」，返 `NodeFull`。
2. **账目超限**：桌面建树 a11y 账 = 4 状态栏件（[desktop.rs:462/464/483/485](../../user/bins/berry-launcher/src/desktop.rs)）+ 4 dock（:707）+ 5 导航键（:755-759）+ 页容器 1（:797）+ 20 格（:799）= **34 > 32**；大屏档（`big = vp_w>=600 && vp_h>=1800`，desktop.rs:317）才建 dock 与大导航，紧凑档 30 ≤ 32 能建——**这是「480/800 正常、1080 黑」的分辨率假象来源**（布局差异，非内存）。
3. **死亡收口**：[berry-launcher/main.rs:277-279](../../user/bins/berry-launcher/src/main.rs) `desktop build err={e:?}` → `fail()` = eprintln + park（main.rs:78-81）——进程静默停泊，永不进帧循环，零 SUBMIT。
4. **症状**：帧缓冲停在 guifbd 自检终态（黑底 + 左上 "CD" 残字），恒黑、md5 不变——与「串口全绿但画面黑」完全互锁。
5. **漏检原因**：fail 行混在开机自测字符噪声流中间，且关键词（`desktop build err=NodeFull`）不在调查时盯的 fail 集合（vmo create/commit/vmar map/texture desc）里。一行终审：`grep -a "desktop build err" serial.log`（病必中、健康零中）。

## 已排除面（含两例错误归因的纠正）

- **「buddy 4MB 连续块帽」不成立**（[wave10 笔记](../notes/implemented/2026-11-15-vnc-lan-wave10.md)当晚记载，本文纠正）：内核 defer 路径按需取 2^n 连续页（1080p = 2025 页 → order 11 → 8MiB 块 ≥ 8,294,400B，[kernel/src/main.rs:401-408](../../kernel/src/main.rs)），`MAX_ORDER=13`（32MiB，[mm/src/buddy.rs:36](../../mm/src/buddy.rs)）；0x40800000 非硬编码预留而是运行时 order-11 分配；ramfb_set 无尺寸上限断言且 QEMU 已接受（`DISP ok`）；guifbd 自检三步在 0x40800000 逐像素写读一致（`FBW ok` 的前置）——物理层全通。README Profile 表「phone20/tablet 已支持 4MB 连续块、desktop 未标」的真义是**验证登记的边界**，不是分配器帽。
- **「svcmgr 128KiB 平像帽」假说不成立**（[业界机制调研](2026-11-15-survey-模拟器1080p显示机制对照.md)当时的头号嫌疑，本文否决）：该帽是 spawn 期子进程代码平像帽（`USER_CODE_MAX`，[svcmgr/main.rs:7315](../../user/bins/svcmgr/src/main.rs)），帧/壁纸不经它；且其「尺寸敏感静默失败」前提被「病镜像 800×1280 同死」直接否定。
- TextureDesc 校验（[berry-gfx/color.rs](../../user/berry-gfx/src/color.rs)）只拒 w<8/h<16/stride<w*4/溢出；guifbd 行弹舱帽 16384B > stride 4320；guiproto Rect 全 u32 无截断；berry-gfx 光栅宿主离线复测三档（480/800/1080）壁纸像素一致——渲染软件面无罪。

## 终审补记（2026-11-15 深夜）：第三层断点——ramfb 非 32 对齐宽的 QEMU 扫出断裂（已实证已修复）

容量回归之上还有一层：修复分支构建（`6a0260a232` 隔离导出，内核+rootfs 全新构建）在 1080p 下建树/渲染全绿、**客机 ramfb（GPA 0x40800000）100% 非零像素真画面**，但 QEMU 侧永不扫出（VNC 无帧、QMP screendump 挂起、VNC ServerInit 自报 **1088**×1920）。对齐实验定谳：内核 [main.rs](../../kernel/src/main.rs) 的 `ramfb_set` 两条调用路（原地/defer）把 w=1080（非 32 对齐）原样传给 QEMU，QEMU 侧 surface 按对齐几何（1088）建而扫出断裂；把 display_mode 的宽度**向上取 32 对齐**（1080→1088，stride 同步 4352）后一切恢复——1088×1920 桌面经宿主 screenshot/VNC 可见（三行亮度 153/112/112、导航条键块在位），滑动翻页实测响应。480/800 档天生 32 对齐所以从未触雷——「分辨率相关」的最后一块拼图。

- 实验补丁（2 行，只在 `/tmp/k6fix-src` 隔离副本，未入库）：`display_mode_req()` 取值后 `let w = (w0 + 31) & !31;`，两条路共用。
