# 启动产物、配置与日志 AI 可读性调研

Type: survey
Status: current
Updated: 2026-11-15

一句话说明：回答三个问题——系统各方式启动后生成的文件在哪、位置统不统一有没有体系、AI 能不能读到配置与日志来调试；裁决为「半套体系」，并给出按优先级排的补齐建议。

## 问题

1. 模拟器（img 镜像）与其他方式启动系统后，操作系统生成的配置文件和相关文件在哪里？对标 Windows 首次启动在 C 盘铺开一堆文件的现象。
2. 生成位置统不统一？有没有体系？模拟器启动与其他启动方式是否都覆盖？
3. 启动之后，AI 能读到这些配置吗？日志能读到吗？无法调试、无法发现错误的系统不可用。

## 方法与来源

## 结论

### 启动方式分两族

A 族「berry 设备壳」：`just shell` / `just desktop` / `just berry run|shot|device start|vnc` / 双击 .app——宿主程序 `tools/berry` 管理 QEMU 生命周期。B 族「just 直跑」：`just run` / `run-el2` / `run-smp` / `run-rootfs` / `run-release` / `run-x86` / `run-efi` 及 smoke 系——justfile 直接起 QEMU。另有 `just image` 产出的 `out/berryos.img`（MBR+FAT16 自举镜像）可挂 UTM 或真机，属 B 族语义（宿主零留痕）。

### 问题一：启动后生成的文件在哪

宿主侧，A 族有统一 per-run 目录：`~/.berry/run/<epoch秒-纳秒>-<pid>-<label>/`（`BERRY_HOME` 可覆写，Windows 落 `%LOCALAPPDATA%\BerryOS`），内含 `meta.json`（label/pid/started/profile/image/memory_mib）、`state.json`（崩溃恢复态）、`serial.log`（客机内核+服务+应用全部日志，QEMU `-serial file:` 落盘）、`qemu.log`、`events.jsonl`（QMP/VNC 事件流）、`vars.fd`（每次新造的 64MiB 全 0xff UEFI 变量盘）、`ram.bin`（客机 RAM 共享镜像）、`vnc.sock` / `vnc.port` / `vnc.pass`；截图 `frame-*.png` 落 `--out` 指定目录。B 族宿主零留痕：`-serial mon:stdio` 日志只上终端即焚；临时件散落三处——`${TMPDIR}` 下 `berryos-echod.*` / `berryos-evsclient.*` / `berryos-smoke.*`（trap 收删）、`/tmp/berryos-sim1.sock`、仓库根 `disk.img` 与 `boot/out/vars.fd`（均每次重造）。

客机内，所有启动方式同一套：rootfs 是 fw_cfg 递送的只读 cpio，无「首启铺开」动作；唯一启动期生成的配置文件是 fsmgr 在 RAM 树预建的 `/etc/mtab`（定值一行 `b"/dev/root / fat rw 0 0\n"`，`user/bins/fsmgr/src/main.rs`）。启动配置的真实递送机制不在客机内，而是宿主侧 fw_cfg 具名键 `opt/berry/*`（rootfs0..9 / display / rtc / trace / accel / simdev / demo-face / noktest / soakload / asidroll / bootmode 等），两族启动共用这一单机制。

### 问题二：统不统一、有没有体系

裁决：半套体系。做得好的两块——A 族 per-run 目录职责分明、可寻址、可 `--json` 消费，是业界水准的雏形；fw_cfg `opt/berry/*` 是事实上的启动配置递送单一机制。不统一的四处——其一，B 族完全游离在 run 目录体系外，同一台「机器」换 `just run` 启动 AI 就什么都读不到；其二，客机内「首启生成」体系基本不存在：数据盘每次 mkfat 重造（`justfile` A-5/A-6 注释自认结构性不可持久）、EFI vars 每次重造，跨启动用户状态为零；其三，fw_cfg 键目录无单源，键名散在 justfile 注释、`tools/berry/src/qemu.rs`、内核各调用点，没有一份机器可读键表；其四，五套入口（shell/desktop/device start/shot/双击）的 profile 与显示默认值分裂，模拟器体验统一刀 1 已立项未落地，且「生成物位置统一」不在该刀口内。

### 问题三：AI 能不能读到、怎么调试

能读的（均已一手验证）：`berry logs --run <id> [--tail N] [--follow] [--json]` 读串口日志；`berry events [--json]` 读事件流；`berry doctor --json` 环境体检；`berry device list/status --json`；`berry run --marker "BerryOS boot" --timeout 30` 确定性启动判定；smoke 门 `just smoke` 的标记单源在 `tools/markers.sh`（裸相 32 + rootfs 相 56，每标记是 `X ok n=` 格式的确定性状态谓词）；`~/.berry/run/<id>/` 全部明文可直接读。

缺口按痛排序：a) B 族六个入口日志终端即焚，AI 事后零取证；b) `berry run` / `berry shot` 默认 `keep=false`，失败即焚——最需要现场时现场没了；c) smoke 默认删日志（`SMOKE_KEEP_LOG=1` 才留，且靠人记得设）；d) 客机内无自读面——bsh 无 dmesg/log 命令、无 `/var/log`，内核 ring buffer 不经 syscall 暴露；e) 内核日志无时间戳无级别（裸行），排时序只能靠行序；f) 内核 telemetry 环在写但消费口未实现（`telemetry_open` 留待 v3），[../../docs/可观测性设计-v1.0.md](../../docs/可观测性设计-v1.0.md) 承诺的 trace 服务落盘导出尚未兑现——文档承诺与代码现实冲突时以代码为准；g) run 目录无历史索引，死掉的 run 无法枚举回溯。

### 业界共同模式（通识，无一手来源，待补引用）

四层结构：一层镜像只读（系统镜像不可变）；二层实例可变层独立成块（Android 首启格式化 /data 生成 OOBE 标记与 settings 数据库，Windows 首启生成注册表 hive、ProgramData、用户 Profile，二启检测标记跳过首启）；三层固件变量持久（QEMU/EDK2 惯例 vars.fd pflash 跨启动复用而非重造）；四层宿主每 run 留痕（AVD 的 `~/.android/avd/<name>.avd/` 逐 run 保留 userdata、snapshots、logs，日志结构化 JSONL，配 `adb dumpsys` 类机器可读查询面）。对照看，本项目已对齐第四层的 berry CLI 半边与确定性 marker 谓词（后者甚至超前），缺可变层持久化、固件变量持久、B 族留痕。

### 建议（按优先级）

- P0｜B 族 justfile 六入口的 QEMU 行外包 `2>&1 | tee out/logs/boot-$(date +%s).log`（或 `-chardev file` 双路）——stdio 即焚是 AI 取证面最大空白，改动只是包一层 shell。
- P0｜`berry run` / `berry shot` 在 marker 失败、超时、panic 分支自动触发 run 目录保留（`RunDir` 已有 keep 机制，只缺失败触发），成功才默认删。
- P0｜`tools/smoke.sh` 改为失败必留最后一个 boot 的日志，`SMOKE_KEEP_LOG=1` 从「人记得才留」变成「失败自动留」。
- P1｜客机内建最小首启配置体系：沿用 fsmgr 先例约定 `/cfg`（或 `/etc/berry`）+ 持久数据盘挂载点；settings 应用先把开关值经现成 put_file 落成 `/cfg/settings.cfg`——FAT 读写链路已通，缺的只是约定与调用。
- P1｜跨启动持久化三件：数据盘改为复用 `~/.berry/data/<profile>.img` 不重造；`vars.fd` 存在即跳过；`run-efi` 去掉每次 0xff 重造行——UEFI 启动项才能像真机一样留存。
- P1｜bsh 加 dmesg/log 命令 + 内核日志 ring 最小读口（syscall 或 fs 面映射）；`telemetry_open` 的 v3 承诺可一并最小化提前兑现。
- P2｜内核日志行加时间戳与级别前缀（marker 协议 `X ok n=` 可不动）。
- P2｜fw_cfg 键目录单源化（`tools/fwcfg-keys.toml` 或 docs 键表），`berry doctor --json` 增报实际注入键集。
- P2｜`~/.berry/run/index.jsonl` 逐 run append 历史索引，`berry device list --all --json` 可枚举已死 run。
- P3｜与模拟器体验统一刀 1 合并立项：五入口统一时把「生成物统一」一并收口，避免入口统一后再补一轮文件位置统一。

### 开放问题（待人裁决）

- `berry run/shot` 保留策略：默认即焚（省磁盘）、失败自动保留成功删（建议案）、还是全保留？
- 客机内配置体系插哪个刀位：随模拟器体验统一刀 1 落地，还是单开一刀？
- B 族留痕形态：justfile 包 tee 最省但与 berry run 目录仍是两套；并轨 berry run 目录体系统一但改动大。
- 是否引入 `~/.berry/` 下 per-device 状态目录（类似 AVD 的 `.avd`）承载 vars.fd 与数据盘持久化，及其与清理语义的关系。
- x86 面与 EFI 面是否同期补留痕，还是 ARM64 主线优先。
- 业界模式段是否补一轮带引用的调研（AVD 目录结构、EDK2 vars 惯例、Firecracker 布局）支撑后续设计文档。
