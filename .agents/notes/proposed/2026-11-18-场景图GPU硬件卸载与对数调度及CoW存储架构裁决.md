# Agent Note: 场景图 GPU 硬件卸载、对数复杂度帧感知调度与 CoW 存储架构裁决

Status: proposed

## Problem

[渲染管线与桌面 SDK 及镜像存储深度审计](../../research/2026-11-18-渲染管线与桌面SDK及镜像存储深度审计.md) 证明，除微内核与基础会话改造外，BerryOS 要真正实现从「能跑通冒烟的原型」向「旗舰级体验与独创架构的现代操作系统」跃迁，还横亘着四道结构性天花板：

1. **纯位图交换链与 `virtio-gpu 2D` 的物理死结**：`virtio-gpu 2D` 的 14 条命令不含任何绘制语义，即使修通 D-Bus 脏矩形传输，100% 像素生成仍压在客机 CPU（4K 分辨率单帧 33MB 软光栅不可持续），且每个常驻应用若自持双缓冲像素 VMO，在 128MiB 设备上开数个应用即耗尽内存。
2. **调度运行队列线性复杂度与图形实时链断层**：`Runqueue` 在选核与限流恢复路径依赖 $O(n)$ 侵入式双向环全扫，在千级线程桌面/网络并发下尾延迟恶化；同时触控到合成链路缺乏单拍受控的帧截止期令牌传递与窗口失焦自动冻结闭环。
3. **全量内存驻留 `rootfs.cpio` 与无事务 FAT12 存储瓶颈**：开机将 30MiB 级根归档全量装入 RAM 严重侵占低内存设备空间，9 文件上限 RAM-fs 与无崩溃原子性的根目录 8.3 大写 FAT12 无法承载现代应用沙箱与可靠系统升级。
4. **碎片化串行构建拖累研发闭环**：[justfile](../../../justfile) 通过 shell 串行调用近三十次独立 `cargo build`，重复编译基础库并拉长反馈周期。

## Proposal

立定六份正交终态模块规格与配套实施计划，一步到位完成架构升维：

1. **确立「`SceneStream` 免位图场景流 + 三阶真 GPU 硬件卸载」架构（[gfx 总体设计](../../plans/gfx/design.md) + [gpu-accel 总体设计](../../plans/gpu-accel/design.md)）**：在升级 16×16 瓦片分箱 NEON 预乘混合、SDF 超椭圆/阴影与 Dual-Kawase 毛玻璃软核作为确定性基线的同时，引入单点驱动的 `berry-paravirt-gfx`（直驱宿主 `wgpu` Metal/Vulkan/DX12 Uber-Shader）与 `Virtio-GPU 3D`（`BLOB` 零拷贝 + `berry-vkproto` 轻量三管线流），使常规 SDK 应用零像素缓冲驻留（省内存 >90%）且像素计算 100% 卸载至硬件 GPU，并在 GPU 超时挂死时 60ms 内无缝回退软核。
2. **确立「$O(\log n)$ 子树增强侵入式红黑树 + 单拍 `FrameToken` EDF 实时链 + 焦点自动冰封」调度架构（[sched-rt-gfx 总体设计](../../plans/sched-rt-gfx/design.md)）**：以 `berry-rbtree`（维护 `subtree_min_vd`）与双侵入式最小堆将选核与限流唤醒严格压至 $O(\log n)$；通过合成器按拍配发的受控 6ms `FrameToken` 打通触控→应用→合成全链大核亲和与 EDF 保帧，失焦超 3 秒无后台证据自动 `SuspendToken` 冻结归零唤醒。
3. **确立「零 OCR 能力受控 AI 语义场景总线 + 可打断 `Spring2D` 四端桌面」（[desktop 总体设计](../../plans/desktop/design.md)）**：由合成器在硬件安全边界内剥离敏感字段后向经授权的 AI 代理微秒级导出结构化控件树，配合不可伪造的顶层 `TrustRing` 呼吸光圈与一次性 `ActionToken`，兑现无需高耗电截屏 OCR 的真 AI 原生交互。
4. **确立「`BerryROFS` 页对齐 Merkle 按需只读根卷 + `BerryFS` 写时复制崩溃原子文件系统 + `berry-xtask` 统一构建图」（[storage-image 总体设计](../../plans/storage-image/design.md)）**：将冷启动根卷常驻内存从 >30MiB 压至 <2MiB，提供数学级断电一致的 UTF-8 多级目录与不可逃逸 `/app/data/<id>` 配额沙箱，并将增量镜像构建压至 3 秒内。

## Alternatives considered

- **备选一（仅优化软光栅 + 仅用客户端位图 Swapchain，不做服务端场景流与 GPU 着色卸载）**：落选原因——虽然 NEON Span 化能满足 HVF 下 1080P 基础流畅度，但无法解决 128MiB 内存档位多开应用时的双缓冲显存爆炸，亦无法在 4K 高分屏与复杂多层实时毛玻璃下释放 CPU 算力与降低真机功耗。
- **备选二（在每个应用进程内链接 Mesa / Virgl 完整 OpenGL/Vulkan 客户端栈）**：落选原因——严重违背微内核最小 TCB 与全纯 Rust 自研原则（ADR #51），使每个小程序背负数十 MB 驱动内存与庞大着色器编译器攻击面；由合成器单点持有极薄三管线 GPU 后端即可让全生态零成本享受硬件加速。
- **备选三（维持 `Runqueue` 循环链表，仅靠限制系统最大线程数 ≤ 64 规避扫描开销）**：落选原因——多线程浏览器、异步运行时与桌面多应用并发必然突破百级至千级线程，侵入式增强红黑树同样零堆分配，却能从算法根源永久消除线性退化。
- **备选四（在 FAT12/FAT32 上外挂文本预写日志补丁替代新建 `BerryFS`）**：落选原因——FAT 簇链结构天然缺乏高效的原子目录重命名、稀疏 Extent 大文件与 Inode 级沙箱配额账本，直接实装紧凑 CoW B+Tree 文件系统更为干净彻底。

## Consequences

- **核心收益**：BerryOS 在「128MiB 低内存多应用并发能力」、「120Hz/4K 真 GPU 硬件渲染与热自愈」、「千线程 $O(\log n)$ 确定性帧感知调度」、「断电零损坏存储与块级可信启动」以及「微秒级零功耗 AI 语义交互」五个维度形成自洽且领先传统宏内核系统的代际优势。
- **协同边界**：本裁决与微内核底座重构裁决（[莓核 2 代终态架构六大核心裁决](2026-11-18-莓核2代终态架构六大核心裁决.md)）分层互补——`Swapchain` 服务自绘画布与过渡兼容，`SceneStream` 与 `gpu-accel` 提供高阶零缓冲硬件卸载，按 [渲染与桌面 SDK 及存储镜像全栈彻底升级计划](../../plans/2026-11-18-渲染与桌面SDK及存储镜像全栈彻底升级计划.md) 分波推进。
