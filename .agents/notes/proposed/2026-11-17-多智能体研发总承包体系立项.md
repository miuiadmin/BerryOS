# Agent Note: 多智能体研发总承包体系立项

Status: proposed

## Problem

BerryOS 研发靠仓主单会话驱动加零散多 lane 实战（仓根八波以上 RECON/IMPL/VERIFY/REVIEW 交付物），并行能力有存量但无建制：派工凭当次对话，事故修法散在两篇笔记（workflow 产出裸奔窗口、共享树未提交现场三度被清），DSH workflow 的 parallel() 高失败率判例只在 berryos-dev 技能里。仓主 2026-11-17 提出把研发总承包出去：要一个常任总办（PM + 软件总管 + 研发总负责人），操纵 DSH 与 Claude Code 多线派工并派人评审核码，还问能不能做成 DSH 插件。

## Proposal

采纳「总办 + 五科」建制：DSH 主线会话任总办独占主线提交权，RECON / IMPL / REVIEW / VERIFY / AUDIT 五科由 subagent、workflow 与 Claude Code 无头（`claude -p`，经 CLAUDE.md 桥吃本仓规则）分担；每刀七站生命周期（立项→侦察→定刀→实施→评审→核验→集成落账）配四条门禁；每 lane 独立 worktree 加产出即提交，封两类已判例事故。分四期推进：试点波 → DSH 插件 spike（机制已实查为真：`dsh plugin --profile <name> add`，bundles 叠层，@jacklika/dsh-memory 为在装先例）→ 最小 bundle → 常态化。全文见[计划](../../plans/2026-11-17-多智能体研发总承包体系.md)。

## Alternatives considered

- 维持单会话串行：被拒——仓主明确要多线，且存量八波判例证明并行可行，缺的是建制不是能力。
- Claude Code 独扛全部 lane：被拒——单引擎评审盲区自闭环，跨引擎对评才有互补；且 DSH 有 goal / workflow / 记忆库等编排面，Claude Code 无对应物。
- 先做 DSH 插件再开工：被拒——插件机制虽已实查为真，但 entry 类型全集未吃透（skills / MCP 注册面未核实），建制先行、插件化列二期，避免阻塞交付。

## Consequences

- 提交权集中总办：lane 内可在自己 worktree 提交，合入主线必经总办复核——agent 评审降险不免险。
- token 成本随 lane 数线性涨：并发帽由总办按波裁，重构建 lane 初帽 2-3。
- 流水线产物（任务书 / REVIEW / VERIFY）成为仓内常态交付物，与 Curia 文档体系并轨，各归其家。
- 若试点波失败（七站跑不通或事故复发），本提案转 rejected 另立检讨。
