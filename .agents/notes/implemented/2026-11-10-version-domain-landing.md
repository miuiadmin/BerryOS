# Agent Note: 版本管理域全日落阶（五轨道标准与执法闭环）

Status: implemented

## Problem

版本管理域从零问题起步：VER-01 的提问是「别人家的 OS 有很细致的各种版本号，BerryOS 有吗？全套吗」——盘点裁决：项目过程版本工业级（文档双标/ADR/G 关卡/判例库），但**产物版本五轨道缺三整两半**（无内核版本身份、SDK_CURRENT 是布尔门槛非单调 level、无 build id、SPL 缺、manifest version 零消费），恰逢 ADR #82 OEM 配对面与 SDK-2 在途，版本体系是下一个被需要的地基。随后 2026-11-10 一日走完调研→第一档落地（banner 构建标识 + `v0.2.0` 首个产物 tag）→标准 v1.0 成文（Type: standard 首用）→version VMO 查询面→混合构建哨兵→全面审计三洞立修，次日 CI 版本门收尾——从提问到全链执法。仓主号段焦虑之问（「迭代很多版本号不够用」）在标准成文刀定谳，答在 Decision ②。实证流水归沿革 §174–§182，本篇只记决策因果。

## Decision

- **①五轨道模型采纳**：VER-01 A 路五平台取证归纳业界共识——Linux 主版本号无兼容语义（兼容只挂 LTS 分支）、Android 内核兼容锚定 KMI 冻结非版本号、SPL 正交于功能版、SemVer 只管生态包；落法 = 系统版本/平台 API level/构建标识/安全级/生态包五轨各管一个承诺，**兼容承诺只挂单轨、一次发布 = 五元组配对、跨轨合法性由配对矩阵裁决**。这是 AM-02 反比律之后「业界共识作裁决柱」的第二根证据柱——机制问题先取证后立法的路径复用。
- **②走速律「改承诺才动号、迭代烧哈希」——号段焦虑的立法答**：走速决策表把每类改动映射到动哪个号——内部重构/测试/文档不动号只动哈希（迭代烧哈希不烧号，号段永远够）、syscall 加号属内容清单非承诺变更、语义不兼容才 minor+1 且 level+1、里程碑 minor+1+tag、SDK 冻结 1.0.0 三同步门；0.x minor 烧快是正确信号（每跳 = 真里程碑）、到 0.99 直跳 1.0——号段消耗与迭代次数解耦，焦虑无立法基础。
- **③执法七门全机器化**：标准立五门——G-ver-1 level 单调（abi-check 对 git HEAD 只增不减）/G-ver-2 banner 形态（smoke 首行断言）/G-ver-3/4 tag 一致 + 发版净树（`just ver-check`）/G-ver-5 min_level 装载拒；审计追加两门——混合构建哨兵升 FAIL 门（`VER mix` 缺席 + `VER ok` 在席双断言）、nogit 禁发布三脚本执法（标准 §6 从人律升机器）；挂载面扩——ver-check 轻挂 CI fail-fast（浅拉无 tag 空转坑修：fetch --tags 先行，否则门恒走零 tag 豁准假 PASS）+ smoke-smp 补 banner 门三脚本同款。红路径 /tmp 端到端钉死——标准不落人律。
- **④version VMO 而非新 syscall**：运行时查询面（uname 等价物）走 sysver.rs 编译期常量成像（level/semver/git-ident/rustc/flags 逐字段）→ boot 第 9 插 0x0001_0009 只读交付；零号纪律贯穿——查询不动 syscall 号表（37→41 余量属内容清单），与 AM 域 0x84 不前向激活同口径，ABI 面零动是全周期约束非权宜。
- **⑤混合构建哨兵三元组对拍——多会话实害面的正面武器化**：mkcpio `.berryver` 烙印（降级链与 build.rs 同构）× svcmgr 逐字段镜像内核解析 × cpio 直查，全等 `VER ok`/不等 `VER mix` loud。动机 = §A146 三度 sweep 实证的多会话裸奔窗口（workflow 产出与主会话收口之间、共笔混写再次发生）——把「谁混了构建」从字节对拍考古变机器哨兵，实害面转验收面。
- **⑥ADR 号让号**：#83 头注预留归厂商配置簇（产品配置层），版本总纲顺延取 #84；并行 lane 顺号后再让（撞号链终态 #83 配置层/#84 BCTS/#85 版本总纲，沿革 182），表重排在途。裁决 = **引用不追号**——重排期引用不随号漂移追改（防双向追号打架），表定稿后全仓一次清扫（挂 Consequences）。

## Alternatives considered

- **build number 中央计数器**：否决——多会话并行（workflow lane/并行会话）无中央锁面，计数器必漂移，等于再造一个号段焦虑；构建标识取 git 短哈希 + dirty 位（无 git 环境 nogit 降级且禁发布），唯一性由 VCS 单源背书，零新基建。
- **CalVer（YY.MM 时间轨）**：否决——0.x 期无发布节奏可感知、时间信息 git 已有；1.0 后若需时间感知再加（标准 §5 v2 预留），兼容承诺仍只挂 level。
- **0x84 telemetry_open 前向激活**：否决——在册 stage v3 未实现，为查询面提前开号即破零新号纪律；version VMO 只读交付等价达成且 ABI 面零动。
- **派生位挂 am Process**：否决——WAKE_PENDING 式派生位两支柱（事件天然属主 + 按属主钉键单点广播）对版本身份不成立（版本是编译期常量非事件、无属主可钉）；与 AM-2b 候选②同族同因，详 am 域笔记不重复。

## Consequences

- **platform_revision 三方联动候并行收口**：mkimage manifest 列 V9 预埋但恒 0 未取值，与 .berryver/version VMO 的三方联动是下一收敛点；berry_assemble.py 并行在途（让号中），其收口后重派；取值源接 level 还是独立 revision 待裁（validate_platform_revision 消费面已在）。
- **定标随真机**：数值面不预设定标——安全级启用随首个安全公告、配对矩阵随 v2 OEM、发版节奏随真机里程碑校准；走速表「语义不兼容」判定不可机器化，人律 + 评审（审计接受）。
- **生态包运行时消费未启**：.bap version 已从摆设升 mkapp 记录位，但运行时零消费（装载检查只看 min_level）；user/ crate 散置 0.1.0 接受（pre-1.0 SemVer 自律域）——包管理面随 v2 盯。
- **ADR 引用清扫一次**：撞号链重排在途，表定稿后全仓引用一次清扫（含 VER-01 执行记录/沿革旧笔的 #84 旧指）；清扫前引用一律不追号。
