# 自动化开发二期 P0 落地：无人会话外壳五件

Status: implemented

## Problem

深研（[survey](../../research/2026-11-22-survey-impossible-os自动化开发深研.md)）确认 BerryOS 的 Hermes lane 只有「到点开新轮」：进程死了没人接、会话想停零阻力、只磨工具零产出没人管、醒来重导状态烧 token、推送不等绿——缺整层「拉起器+心跳+监督+停机判定+推绿链」外壳。owner 裁决 P0-P2 全量分期，本期 P0。

## Decision

2026-11-22 落地五件（tools/ 七个新件 + .claude/settings.json 钩子）：run-e.sh 单入口拉起（tmux 双会话、claude 独立 session-id、BERRYOS_E_RUN=1 判别、stop 对无人环境拒执）；e-heartbeat.sh（300s 拍、会话私有 transcript mtime 判活、300×2^n 退避 resume、只读观察者不算人、repair 模式换诊断 nudge）；e-supervisor.py（machinery 前缀集 3h 零产品产出整批单 revert + 6h 零 ship 报修，永不许成为停 run 的原因）；e-guard.py（Stop hook 四门 fixpoint 哨兵唯一写点 + FROZEN 集拦截——宪法/闸/编排脚本无人会话不可写）；pack-work.py 开工包（punch-list/facts/git 一次到手）；push-green.py 推绿（落地判据 @{u}..HEAD 空 + CI 三态：green/red/note 无答不归责 + supersession）；e-receipts.py 内容寻址回执；e-doctor.py 发射前自检。底座选型：E lane 用 Claude-Code-native（tmux+claude CLI）而非 Hermes cron——Stop 守卫/FROZEN/心跳/监督是 Claude Code harness 面，Hermes 会话不经过它们；Hermes 四 lane（w1/w2/w3/review）原样保留，RUNBOOK 记两形态分工。

## Alternatives considered

- 把外壳做进 Hermes（cron 承载 E lane）：否——hooks/Stop 判别/transcript mtime 都是 Claude Code 机制，Hermes 无等价面；且用户要「多装其他东西」的灵活性，Claude-native 形态不锁 Hermes。
- 不做监督器（信任会话）：否——深研实证「只磨工具零产出」是 agent 会话的天然失败模式，machinery-undo 是唯一实测过的解。
- fixpoint 哨兵由会话自写：否——哨兵必须不可伪造（唯一写点+四门），否则 Stop 守卫形同虚设。

## Consequences

- E lane 通电方式从「Hermes cron 五步」改为「run-e 三步」（RUNBOOK 已改；Hermes 备选保留）。
- 主仓 .claude/settings.json 新增 Stop/PreToolUse 钩子——交互会话零打扰（钩子严格 BERRYOS_E_RUN 判别）；e-doctor 对主仓报「身份闸未配」是正确形态（bot 身份只配在 lane 克隆）。
- P1/P2 配方入 punch-list 排期；六件自检全接 test-host（selftest_guard 75 件零漏）。
- 已知边界：心跳对「claude 会话活着但卡死」只靠 45 分钟闲判据；launchd 开机自起未装（RUNBOOK 后补项）。
