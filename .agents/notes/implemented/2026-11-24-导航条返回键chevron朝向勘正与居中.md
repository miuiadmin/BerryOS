# 导航条返回键 chevron 朝向勘正：尖头朝左、关于画布中线居中

Status: implemented

## Problem

[桌面沉浸式设计规范](../../../docs/桌面沉浸式设计规范-v1.0.md) §5 规定「返回 = ‹ chevron」——开口朝右、尖头朝左。实现（`user/berry-appshell/src/icons.rs` 的 `nav_glyph_covers`，`NavGlyph::Back` 分支）自提交 `2043c3022`（2026-11-18）起却是另一种几何：注释写「细 chevron ‹」，紧跟的坐标是「顶点 (38,c)，臂端 x=20 上 (20,c-18) 下 (20,c+18)」。chevron 的尖头就是顶点——顶点 x=38 在右、两臂伸向左边的 x=20，画出来是尖头朝右、开口朝左的 `›`。注释的字形与它自己的坐标相反，代码跟的是坐标。同一提交的测试也都是坐标探针：`nav_faces_geometry_probes` 断言 (38,33) 白、中心 (33,33) 被覆盖，`nav_glyph_cover_probes` 断言 (38,c) 在、(45,c) 不在——每一条都与错误几何自洽，没有一条断言「尖头在哪一侧」，所以错误被测试钉住而不是被测试暴露。

用 66×66 源画布（c=33）独立复刻 `hit_seg` 逐像素扫描，旧几何的覆盖集 x 包围盒是 [16,42]，中心 29，比画布中线 c=33 偏左 4 个源像素（键面 96px，折合截图约 6px）；x 最小列（x=16）的像素分居 y=15 与 y=51（两臂端），x 最大列（x=42）只有 y=33（顶点）。这与规范 §5 的「‹」左右相反，且不居中。

## Decision

几何取「关于画布中线镜像」：新覆盖集 = {(62−x, y) : 旧集}，即 `hit_seg(24, c, 42, c - 18) || hit_seg(24, c, 42, c + 18)`（`icons.rs` 第 402 行）。顶点 (24,c) 在左、臂端 x=42 在右，线段长度平方 648 与带宽 d²≤16 不变，两臂关于 y=c 上下对称；x 包围盒变为 [20,46]，中心恰为 c。只动 Back 分支与它的测试，Home、Power、Recents、Rotate 分支字节不变。同步改写注释（开口朝右、尖头朝左、包围盒以 c 为中心），改两组既有探针（中心 (33,33) 落在开口内应为透明，顶点与两臂端为白，顶点左外与臂端右外透明），并新增 `nav_back_chevron_faces_left_and_is_centered`：全画布扫描覆盖集，断言 x 最小列像素的 y 都贴近 c、x 最大列同时有 y≈c−18 与 y≈c+18 的像素且没有 |y−c|<17 的像素、(c,c) 不被覆盖、x 包围盒中心等于 c（±1）。新测试断言的是与「朝向」「居中」直接对应的性质，不再是坐标数值；把几何改回 38/20 时三个测试同时红。

措辞勘正：chevron 关于横轴 y=c 对称（两臂上下对称），不关于竖线 x=c 对称——关于竖线镜像正好把它变成 `›`；「居中」指的是 x 包围盒中心落在 c。

## Alternatives considered

只平移不镜像，把旧的 `›` 右移 4 源像素使其居中（弃——居中的仍是尖头朝右，规范 §5 的「‹」未兑现）；关于旧包围盒自身中心镜像，即 {(58−x, y)}（弃——朝向修正了，但包围盒仍是 [16,42]，照旧偏左 4 源像素）；关于画布中线镜像，即 {(62−x, y)}（采用——朝向与居中一次兑现）。测试面只改既有坐标探针（弃——探针坐标取自几何本身，取自错几何就钉住错；故补一个按形状性质断言的扫描测试）。规范 §5 的文字不动：标准早已写对，错的是实现。

## Consequences

host 测试：`cargo test --release --target aarch64-apple-darwin -p berry-appshell` lib 32（基线 31，新增 1）加 `tests/appshell.rs` 6，全绿；与基线对照，warning 位置集合完全相同（零新增）。launcher 经 path 依赖自动得到新符号，`just build-user` 全链通过。

像素证据（QEMU desktop profile 截图 1088×1920，白像素 = RGB 均不低于 200，返回键区域 x∈[225,320]、y∈[1805,1900]，键中心 (272,1852)）：

| 量 | 修复前（审计机截图，版本 fed545c9） | 修复后（r5 合并机截图） |
|---|---|---|
| 白像素总数 | 937 | 935 |
| x 包围盒 / 中心 | [247,285] / 266.0 | [253,291] / 272.0 |
| x 最小列的像素 y | x=247：{1826, 1878} | x=253：{1852} |
| x 最大列的像素 y | x=285：{1852} | x=291：{1826, 1878} |
| y 包围盒 | [1820,1884] | [1820,1884] |
| 判定 | 朝向反、偏左 6px | 尖头在左、开口朝右、居中 |

修复后的逐列 y 跨度自 x=253 的 [1852,1852] 向两侧线性张开到 x=285 的 [1820,1884]，是一支以 (253,1852) 为顶点的 `‹`。同一张截图上主页实心圆与多任务空心方的白像素数为 1285 与 1008，与修复前截图逐数相同——两键未受牵连。沉浸像素五项（状态栏、桌面格两点、导航底、白条禁令）修复前后均过。

可见的行为变化只有一处：键中心像素 (272,1852) 不再是白色——它落进了 `‹` 的开口。任何假定「导航键中心必白」的像素探针都会因此变红，应改探顶点或臂端。消费者面：`nav_glyph_covers` 与 `NavGlyph::Back` 只在 `icons.rs` 自身；`NAV_BACK` 只被 launcher `desktop.rs` 第 750 行消费，取的是光栅化后的面 id，命中区是整个 96px 的 Icon 节点（第 742—743 行），不依赖 chevron 的 x 范围；全仓无像素 hash 或 checksum 钉板。launcher 自带的 `src/icons.rs` 是不在 mod 表里的死遗留。

未覆盖：真机显示效果未验（只有 QEMU 截图）；紧凑档 44px 键面未单独截图，走同一 `nav_face` 源画布缩放。
