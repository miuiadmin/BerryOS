# 启动器前台态带内帧收口修复方案（frameloop.rs 前台态 + svcmgr 启动器栈页 96）

Type: plan
Status: done
Updated: 2026-11-25

一句话说明：让 berry-launcher 在应用拉起成功后进入「前台态」——每拍只还回状态带与导航带内改文节点的重绘范围、丢弃其余全量重绘、吞掉非导航点击——使 v1 无合成器、共享帧缓冲下应用画面不再被启动器整帧盖掉。两段补丁连同 svcmgr 注释改写、复审 M1 带内帧账留到呈现与回收门改门已落地并实跑（见[启动器前台态带内帧收口修复笔记](../notes/implemented/2026-11-25-启动器前台态带内帧收口修复-带内账至呈现与栈页96.md)）；r11 补上回收门配方的分派修复、点击丢失诊断与启动器导航键长按臂、握手行，回收门与 gui8-smoke 实跑全绿后合入主分支（见笔记「门的闭环」）——「合入前置」三条全部满足，剩下的只有酷刑门无脚本与未试面两件后续事（「未完成事项」）。

## 问题与证据

机制与逐条触发点的事实源是[应用点开不出窗与窗口自消失诊断](../research/2026-11-24-应用点开不出窗与窗口自消失诊断.md)「显示模型调查（R8）」节（Q1 至 Q7），本篇只摘与方案直接相关的结论。该节行号指基线 `dbd7161b`；本篇落笔基线 origin/main `e41ec05c`，`frameloop.rs`、`svcmgr/src/main.rs`、`gui8-smoke.py`、`berry-ui`、`berry-appshell`、`guifbd`、`gui-wmd` 与 `berry-appproto` 相关文件在两者之间零差异，行号同样成立。

- v1 没有合成器，启动器与应用共用帧缓冲：启动器任何一次整帧重绘都会盖掉应用内容区。整帧的来源是 [frameloop.rs](../../user/bins/berry-launcher/src/frameloop.rs) 的 A 面 `set_text` / `set_props` 经 [berry-ui lib.rs](../../user/berry-ui/src/lib.rs) 1464-1481 `mark_ancestors_dirty` 推脏到根，`render_frame` 内 relayout 的 [layout.rs](../../user/berry-ui/src/layout.rs) 691-746 `place` 把根的整视口新旧界加进 damage；`wake` 在 damage 空集时置 FULL（lib.rs 2613-2615）。
- 应用显示期间的大面积重绘触发点共 15 条（诊断篇 Q3 表）。实抓的三条：时钟分钟跳字（frameloop.rs 378-392；实验 a：+11 s 在屏、+20 s 消失，跨分钟界）；任意一下点击的首 MOVE 事件 damage 为空、`wake` 置 FULL（[pump.rs](../../user/berry-appshell/src/pump.rs) 617 → lib.rs 2339-2343 → 2613-2615；实验 b：内容区一击 +3 s 消失）；拉起应用前后的加载灯亮 / 熄翻字（frameloop.rs 657-658、675 与 689）。
- 五个现役应用（BROWSER / CONTACTS / PHOTOS / SETTINGS / TERMINAL）从不向窗口服务建窗，全部以 `surface_id: 0` 兼容档提交（诊断篇 Q1）；启动器的覆盖判据 `covering_app_win`（frameloop.rs 812-824）查 wmd 窗表里「非自窗 ∧ APP 层 ∧ 可见」的表项，对它们恒为 `None`，`covered_by_app`（626-636）恒假——「时钟换字前加 `covered_by_app` 门」这类短修因此不可达。
- 返回与主页键对这五个应用只触发一次全量重绘（点击本身的空集 FULL），不结束也不隐藏应用（诊断篇 Q4；实验 c：HOME / BACK 后 +3 s 窗没了，按键串口零 `TERM` / `killed` / DESTROY 行，进程继续活着）。

## 目标语义

前台态是启动器帧循环里的一个状态 `app_fg: Option<AppFg>`，只用现有信号，不新增树节点，不改 berry-ui / berry-appshell / guifbd。

| 面 | 前台态期间 | 退出前台态 |
|---|---|---|
| 置位 | APP_SPAWN 真拉起成功（ack `(true, _)`）；已活聚焦形（ack `(false, 3)`）不置位——共享帧缓冲下 FOCUS 不重渲，应用像素并不在屏，桌面须保持可交互 | — |
| 清除 | — | 返回 / 主页 / 多任务三个导航键；窗口化应用 1 Hz 表查「见过窗之后表空」（应用退场或被回收）；启动器自身重启回到初值 |
| 每拍帧收口 | `on_tick` 末位（render 前最后一位）：`ui.layout()` 就地消费 layout_dirty，`drain_damage` 丢弃一切 damage（整视口、翻页跟手、按压反馈、空集 FULL），只 `invalidate` 本拍带内改文节点（时钟 / 加载灯 / 呼吸灯 / 关机键），damage 非空才 `wake`；无带内改动不起振，零 SUBMIT | `leave_fg`：清态 + drain + 空集 wake 置 FULL，应用残留像素靠整帧覆盖 |
| 输入 | 只有导航五键可达；非导航点击整击吞掉（不 spawn、不翻 sys 页、tab 位吞掉）；pager 不吃手势；键盘不达 pager | 导航键照旧走原 DESTROY / 翻页 / 归位逻辑 |
| 灯熄灭态 | 加载灯与呼吸灯的熄灭字改为单空格 `LAMP_OFF = b" "`——空文本零宽会让 `invalidate` 零面积、damage 为空、`wake` 置 FULL；一格宽使擦除可行，视觉等同缺席 | — |

## 方案

两段补丁，缺一不可。R9 落地后的实际规模（对 origin/main `12d85625`）：[frameloop.rs](../../user/bins/berry-launcher/src/frameloop.rs) +283/−43（R8 初稿之外另含复审 M1 带内账留到呈现与三条并入建议——三态表查、`invalidate` 失败不计、进前台态收口翻页）、[svcmgr main.rs](../../user/bins/svcmgr/src/main.rs) +13/−7（值与紧邻注释）、[gui8-smoke.py](../../tools/gui8-smoke.py) +65/−27（回收门改门）；r11 另加启动器 +24/−5（导航键长按臂、前台态握手行）与门的分派修复、单批单击、握手交接、两段式重注（见笔记「门的闭环」）；下文条目里的 +231/−41 与 +1/−1 是 R8 初稿数字，保留作来历，逐条落点以笔记为准。

1. **补丁一（[frameloop.rs](../../user/bins/berry-launcher/src/frameloop.rs)，+231 / −41）**：新增常量 `FG_BEAT_NS`（1 Hz 表查拍距）、`BAND_DIRTY_MAX = 4`、类型 `AppFg { win_seen }` 与 `SpawnOut` 三态；`LoopHost` 新增 `app_fg` / `fg_next_ns` / `band_dirty` 三字段；`flush_pending_spawn` 在真拉起成功时置位（先于熄灯改文，熄灯矩形才能以带内帧还回）；`on_head` 新增表查拍，时钟 / 呼吸灯 / 关机键改文处调 `mark_band` 记账并以 `wake_unless_fg` 代替直接 `wake`；`on_msgs` 前台态下非导航点击 `continue`、pager 门加 `app_fg.is_none()`；`on_tick` 末位 `flush_band`；`on_key` 门加前台态；`extra_deadline` 纳入表查拍；`on_nav_click` 的 back / recents / home 分支首行 `leave_fg`、tab 位吞掉；`spawn_by_id_inner` 返回 `SpawnOut`；`set_busy_face` / `set_breath_face` 熄灭字改 `LAMP_OFF`。全文见下节代码块。
2. **补丁二（[svcmgr main.rs](../../user/bins/svcmgr/src/main.rs) 8578，+1 / −1）**：`launcher_assemble` 的 `stack_pages: 64` 改 `96`。原因是补丁一的 `flush_band` 调用 `ui.layout()`，给 `layout::relayout` 增加第二个调用点，LLVM 不再把它内联进 `render_frame`，20 KB 的 relayout 帧叠在 36 KB 的 render_frame 帧上，首帧路径峰值高约 16 KB 越过保护页；启动器主函数约 196 KB 的栈帧常驻，64 页 = 256 KB 下帧循环只剩约 60 KB。不改则启动器启动即栈溢出，有一次真机实证（run2：`launcher died` 两次，PC=0x7ad030 栈探针 `str xzr,[sp]`，FAR=SP=0xbf7180，`LAUNCH ok` 零次）；改 96 后 run3 `launcher died` 零次、`LAUNCH ok` 一次。`launcher_assemble` 直接构造 SpawnSpec，不经 manifest 的「1..=64」域检。

两段补丁对 origin/main `e41ec05c` 的 `git apply --check` 均干净（退出码 0，只检查、工作树零落地）；`git apply --stat` 实测：补丁一 `1 file changed, 231 insertions(+), 41 deletions(-)`，补丁二 `1 file changed, 1 insertion(+), 1 deletion(-)`。调查报告 §6.3 写的「+221/−38，其中代码行 153」与实测不符，以实测为准（诊断篇与证据目录 `final-diffstat.txt` 同为 +231/−41）。补丁 `index` 行的前置 blob（frameloop `d94e51fe`、svcmgr `a3814396`）与 e41ec05c 上两文件的 `git hash-object` 一致。

## 合入前置

三条前置已全部满足（2026-11-25 r11 合入轮，worktree `/tmp/r10-gate`，基线 origin/main `12d85625`）。其一，门——回收门本体已改（二击改多任务键、断言两轮 recycle → killed → it、alive 零），`just gui8-recycle-gate` 配方的既有分派死码（[gui8-smoke.py](../../tools/gui8-smoke.py) `main()` 的 `return run_dual_boot(args)` 在 `--recycle-gate` 分支之前，`03b6b1da` 起）已修，配方可达后暴露的点击丢失（门的三批慢点击被引擎按出队时戳判长按）已定位并由启动器导航键长按臂与门的单批单击、握手行、两段式重注修掉；回收门连续绿、`just gui8-smoke` PASS、长时端到端全步过——数字与证据目录见笔记「门的闭环」。其二，已做（svcmgr 8572-8584 注释随 `stack_pages` 改值同批改写）。其三，建议项采纳三条（下文前三项）与复审 M1，未做三条（每秒两次查表合并、状态机单测、主函数栈帧根修）归后续刀。酷刑门树内无脚本，无法实跑——这一项不是本方案能闭合的，归 owner 决定（「未完成事项」）。以下三条保留作出处。

其一，gui8 回收门必红，须改门并实跑。[gui8-smoke.py](../../tools/gui8-smoke.py) 的 `--recycle-gate` 二击段原是「同一图标再击一次 = already-alive 聚焦路」，`wait_until` 等 `ECO_GATE_ALIVE`（`eco: app BROWSER alive`）；补丁下前台态把这一击整击吞掉、零 RPC，`wait_until` 必超时。改法例如二击改走多任务键，或先按返回键回桌面再击。复审另判断：未打补丁的现行镜像上该门本就拿不到它等的行——五个应用不建窗，svcmgr 已活判据「可见 ∧ APP 层表项 ≥ 2」（[svcmgr main.rs](../../user/bins/svcmgr/src/main.rs) 5965-5970、9940-9941）不成立，二击走 `recycle` + `killed` + `it 03`；这一点已由改门一路在干净 origin/main 上的实跑证实（同一步同形红）。

其二，svcmgr main.rs 8572-8577 的注释（「64 页 = 256KB …… manifest 域检 1..=64 顶格」）须与 `stack_pages` 新值同批改写。

其三，复审的建议项，合入前逐条裁定采纳与否：

- 窗口表应答畸形时不应被当成表空而清前台态：`covered_by_app`（frameloop.rs 626-636）查败 fail-open 返回 false，表查拍里与「表空」不可区分，`win_seen` 为真的窗口化应用会因此被误清前台态。
- `invalidate` 失败时不应仍然唤醒：`flush_band` 里 `let _ = ui.invalidate(*node); any = true` 不看返回值，Err 时 damage 仍空，`wake` 会置 FULL。
- 进入前台态时若翻页手势停在拖拽中要收口：前台态下 pager 不吃消息，拖拽中的手势收不到 End。
- 前台态每秒两次查表可合并：表查拍与呼吸拍各 1 Hz 各做一次 TABLE_GET。
- 前台状态机应抽出纯谓词补单测：frameloop.rs 已有「标记门纯谓词测试」先例（1276-1277 注；1285 至 1473 七个 `#[test]`，aarch64-musl 目标可编译、宿主不可执行）。
- 补丁与并行会话输入链那批提交在消息处理（`on_msgs`）与键盘处理（`on_key`）两处落在同一段，冲突面不小。
- 启动器主函数约 196 KB 的栈帧才是根因，加页只是缓解；根修归启动器 owner。

`tools/gui8-smoke.py` 与 `user/bins/svcmgr` 均为并行会话领地，实施须与领地会话协调。

## 设计取舍

五个无窗应用在前台期间崩溃或被回收时没有任何信号——它们不建窗，wmd 表不变化，应用协议无存活查询（[berry-appproto lib.rs](../../user/berry-appproto/src/lib.rs) 59-75 只有 LIST / SPAWN / EVENT）——前台态会一直保持到用户按导航键；那段时间屏幕残留应用最后像素，桌面点击被吞（导航键除外）。可选方向：

| 方案 | 改动 | 代价 |
|---|---|---|
| A 应用补建窗（每应用一处 CREATE，照 `settings-app` 样板 15 行） | 补丁的表查拍自动生效（退场 → wmd 摘表 → 启动器 FULL 回桌面）；重开走「已活聚焦」 | 与「共享帧缓冲下 FOCUS 不重渲」冲突：重开活实例只聚焦不出画面，需 svcmgr 改走重拉或应用在 FOCUS 事件时重提帧 |
| B 系统服务提供存活查询或通知（appproto 加一个 op + svcmgr 服务端 + 启动器轮询或订阅） | 不动应用 | 多一条 RPC 面；「app 活」≠「app 画面在屏」，前台语义需再定义 |
| C 接受现状：前台态只由导航键解除 | 零改动 | 应用被回收后残留最后像素、点击被吞，直到按返回 / 主页 |

归 owner 裁决；A 是既有架构本意（样板与 svcmgr 判据都假定建窗），但须同时裁定「重开 = 聚焦」在共享帧缓冲下的像素恢复问题。

裁决（2026-11-25，R9 任务书）：取 C——无窗应用在前台期间崩溃或被回收后，前台态保持到用户按导航键，「桌面可见但非导航点击被吞」记为已知边界；A / B 不在本刀。落地写法与未覆盖面见笔记的「设计取舍」段。

## 落地时的验证步骤

前置照调查报告 §6.5：`just build-user` → 隔离 target 的 ktest 构建 → `just build-boot` → `mkimage` → `mkfat` + 印章 → `berry device start … --keep`；轮询 `LAUNCH ok` 后再等 60 s。

1. 参考标记无回归：`VBLK ok cap=2048 slot=31`、`BLKD ok n=512`、`GFX ok`、`err=-13` 零行、`LAUNCH ok` 恰一次、`launcher died` 零次。
2. 应用窗持续不少于 200 s、跨至少三次分钟跳变：每 10 s 截图，线索区 ratio 恒约 1；顶带时钟数字每分钟照变。
3. 应用内容区点击不消失：窗在屏时点内容区两点，各 +3 s ratio 仍约 1。
4. 主页与返回回桌面：HOME 后 ≤2 s ratio 0；再拉起另一应用后 BACK，+3 s ratio 0。
5. 无应用时时钟照走：不拉应用，跨分钟两张，分钟个位数字 bbox (852,47)-(868,71) 变化。
6. 第二个应用同样成立：对 CONTACTS 重复 2 至 4。
7. 改门后 `just gui8-smoke`、`just gui8-recycle-gate` 与酷刑门全绿。
