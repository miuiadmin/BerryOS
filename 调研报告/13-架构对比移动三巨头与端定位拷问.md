# 13 号报告：BerryOS 架构 vs 移动三巨头 + 端定位拷问

> 回答五个问题：① 我们跟其他系统架构区别在哪、到底好不好；② 跟 Android / iOS / 鸿蒙比差在哪强在哪；③ 跑在手表上要砍什么；④ PC 上是不是完全体；⑤ 微内核 / "分布式内核"到底为了个啥。
> 输入：`00-总览与对比` / `03-OpenHarmony内核` / `04-seL4与L4家族` / `05-Zircon-Fuchsia` / `12-三端可行性评估`（内部报告）+ 2025-10 外部查证（来源见 §8）。

## 0. 一句话定位

**BerryOS = Zircon 式微内核的机制骨架 + 三巨头都没有的四样东西（纯能力票制、全 Rust、AI 原生调度注入面、tickless day-one）；它好不好取决于拿"可控"换什么——在手表上，可控直接兑换续航和稳定，所以 v1 主战场选手表是对的；"分布式"是鸿蒙中间件的概念，我们做的是同源分端，不是一回事。**

## 1. 谱系坐标：内核形态光谱

```
宏内核 ──────── 混合 ──────── 微内核
Linux/Android   XNU(iOS)     seL4/QNX/Zircon/BerryOS
                               鸿蒙内核(NEXT)
驱动/FS/网络全内核  Mach底+BSD焊死  只留机制,其余全用户态
```

- **宏内核**：性能好（零 IPC 税）、生态大；代价是 TCB 巨大——任一驱动 bug 可带崩全系统。
- **混合（XNU）**：历史上纯 Mach 微内核性能不达标（IPC 税 + cache 不友好），Apple 把 BSD/IOKit 焊进内核空间——"微内核的底子，宏内核的身子"。这是微内核代价的**最著名历史证据**。
- **微内核**：TCB 小、崩溃隔离、策略可插拔；代价是 IPC 税 + 生态自建。seL4 fastpath ~413 cycles（04 号报告实测引用）证明 IPC 税在现代硬件上"可付"，但没消失。

BerryOS 坐标：**务实派微内核**（内核有对象/分配器，不为纯度牺牲实用）+ 全 Rust——谱系上与 Zircon 最近，与 QNX/seL4 同阵营，与三巨头的距离见下。

## 2. 三巨头解剖

### 2.1 Android：宏内核 + 用户态服务总线

- **内核**：Linux 宏内核（驱动/FS/网络全在内核），近年 GKI（通用内核镜像）模块化是被迫给宏内核"减脂"。
- **服务层**：system_server 等 100+ 系统服务在用户态，经 **Binder**（内核里的 IPC 驱动）通话——**学了微内核的形（服务化），没学内核的质（驱动/FS 仍在内核，TCB 没小）**。
- **权限**：UID 沙箱 + 安装时权限 + SELinux——环境权限制（进程是谁决定能干嘛），IPC handle 像 Zircon，但门禁靠查身份不靠查票。
- **应用模型**：ART + **Zygote 靠 fork 预热分叉**——fork 在安卓是启动性能刚需，恰是我们 v1 砍掉的东西（我们用 process_create + 能力显式传递替代）。
- **手表**：Wear OS = 同一个 Linux 内核缩配跑。

### 2.2 iOS / XNU：微内核底子，宏内核身子

- **内核**：XNU = Mach（task/thread/port/IPC——**Mach port 本身就是能力制 IPC**）+ BSD 宏层（POSIX/VFS/网络）+ IOKit（C++ 驱动在内核态）。
- **权限**：sandbox profile + entitlements——策略配置制，不是内核能力制。
- **分端**：iOS/watchOS/tvOS/macOS/visionOS **同一 XNU**——我们 ADR 引用的"同源分端"原型，四端形态差异巨大但内核一份代码。
- **近况**：Apple 在内存安全上转向 Rust（iBoot 等），但内核 C++ 主体未动——"全 Rust 内核"这个位子是空的。

### 2.3 鸿蒙：多内核分档 → NEXT 自研微内核，"分布式"在中间件

- **两条线**：① **OpenHarmony**（开源）：LiteOS-M（MCU）/ LiteOS-A（轻量带 MMU）/ Linux（rich）**三内核按设备分档**（03 号报告深挖）；② **HarmonyOS NEXT**（商业，2024 起）：**自研鸿蒙内核替换 Linux**、移除 AOSP、宣称微内核 TCB 大减（代码量 < Linux 1/4），鸿蒙 PC 也基于此（华为官方 + 维基，见 §8）。
- **分布式软总线**：把手机-手表-平板组成一个逻辑设备、应用跨设备流转——**这是系统中间件层的分布式，每个设备的内核还是各跑各的，不是"分布式内核"**。
- **权限**：AccessToken（应用令牌 + 权限列表）——环境权限制。
- **手表**：鸿蒙手表走 LiteOS-A 系轻量内核——与 NEXT 手机内核**不是同一个**（多内核分档路线）；对比我们的"同一内核编译到各端"。

### 2.4 五方总表

| 维度 | Android | iOS/XNU | 鸿蒙 | Linux 桌面 | **BerryOS** |
|------|---------|---------|------|-----------|-------------|
| 内核形态 | 宏（GKI 减脂中） | 混合（Mach+BSD） | 多内核分档 → NEXT 微内核 | 纯宏 | **务实微内核** |
| IPC | Binder（内核驱动） | Mach port + XPC | LiteIPC / 软总线 | 信号 + D-Bus(用户态) | **channel + 通知 + 共享内存** |
| 权限模型 | UID+权限+SELinux | sandbox+entitlements | AccessToken | UID+能力 bits | **纯能力票制（handle+rights）** |
| 应用模型 | ART+Zygote(fork) | 原生二进制 | ArkTS/Stage | 原生 | **自有 ABI + POSIX 库，v1 无 fork** |
| 语言 | Java/Kotlin + C/C++ | C/C++/Swift（组件级 Rust） | C/C++/ArkTS | C | **全 Rust** |
| 多端策略 | 同内核缩配 | **同源 XNU 全端** | 多内核分档 | 发行版 | **同源分端 + capacity 抽象** |
| 手表形态 | Wear OS（Linux） | watchOS（XNU） | LiteOS-A（另一内核） | — | **v1 主战场（同一内核）** |
| AI 位面 | 框架层 | CoreML 框架层 | 端侧框架 | — | **内核留调度注入面（独一档）** |

**BerryOS 的四个"人无我有"**：纯能力票制（三家全是环境权限）、全 Rust 内核（三巨头内核全是 C/C++）、AI 原生调度接口（三家的 AI 全在框架层，够不着调度器）、tickless day-one（Linux 的 NO_HZ 是后期补丁，我们出生就是）。**两个"人有我无"要认**：生态（G-eco 关对赌）与驱动广度（明示放弃，12 号 §9）。

## 3. 到底好不好：微内核的"四个可控"与两笔税

**四个可控**（微内核买到的真东西）：

1. **崩溃可控**：驱动/FS/网络在外，崩了只死自己——我们 G1.5 已实测"只死自己"（rogue_ptr 被杀、金丝雀照涨）；Linux/Android 任一驱动 bug 可全系统宕。
2. **权限可控**：票制最小授权——进程能干什么 = 手里几张票，没有环境权限的提权面；票可以随消息精确转手（3-4b 已验 handle 随 channel 迁移）。
3. **策略可控**：机制/策略分离——AI/PM 策略全在用户态可插拔可热换；宏内核要动调度得改内核重编译重启。
4. **升级可控**：服务监督重启（PM 崩→内核降级保活）——手表 OTA 时代，系统服务热更新不用整机重启。

**两笔税**（要付的代价）：

1. **IPC 税**：每次"做事"都过一次消息传递。历史定论（Mach 之死）已被 seL4 fastpath 拆得七七八八，但 cache/带宽影响真实存在——我们不回避，IPC 设计按 <1200/<500 cycle 验收线管控（路线图 P4）。
2. **生态税**：一切自建（libc/驱动/工具链/应用）。**没有内核死于 IPC cycle 数——全部死于没人给它写程序**（00 号引 18 号）。G-eco 关（未修改的 ripgrep 跑通）就是这笔税的对赌协议。

**判决**：微内核不是为快，是为可控。**在手表场景，四个可控直接兑换产品力**（崩溃可控=可靠、策略可控=省电、升级可控=OTA、权限可控=安全），而手表恰恰是性能吞吐最不重要的端——所以"好不好"的答案是：**在 v1 选的战场上，好；在服务器/桌面吞吐战场上，我们明示不打**（12 号 §9 维度化宣称）。

## 4. 手表端拷问：砍什么、留什么

**先纠正一个方向**：v1 不是"从完全体砍成手表版"，是"**从手表长出来，长大成完全体**"（ADR #39）。内核始终是同一份源码（XNU 同源分端模式），变的不是内核，是**配置与服务集**：

| 处置 | 内容 | 说明 |
|------|------|------|
| **砍（v1 不做）** | SMP（单核 `-smp 1`）、demand paging、GUI/framebuffer、POSIX 大面（无 fork/无信号）、驱动广度（仅启动关键 + virtio）、syscall v1 ~27 号、现代 FS（FAT MVP） | 见分阶段基线 #20 |
| **留（机制同源）** | 能力/handle 表、channel IPC、VMO/Vmar、调度机制、tickless idle、监督重启 | **一条代码路径三端通用**——capacity 抽象是命脉 |
| **长大时加** | 每核 runqueue + 负载均衡、AI 策略服务、DVFS/EAS（G5）、demand paging（G4） | 加开机制，不是换内核 |

**内存账**：2025 年智能手表旗舰标配 **2GB RAM**、1GB 是入门线（§8 来源）；BerryOS 内核几百 KB 量级 + 服务集几十 MB，**余量巨大**。真正装不下的不是 rich 档手表，是 MCU 档（KB 级）——那是另一个物种，v1 排除（ADR #40，12 号 §2.1"两档是两个物种"）。

**续航账**：手表是 tickless/EPP/capacity **唯一真兑现**的端——空载零定时器唤醒（00 号列为"我们可赢"维度）在手表上 = 每天实打实的 µA→mA；PC 上省电是锦上添花，手表上是生死线。**这就是 v1 主战场选手表的根本原因：我们的差异化在这个端最值钱，宏内核的短板在这个端最不疼。**

## 5. PC 端完全体：什么形态、什么边界

完全体 = **机制全开 + 边界诚实**：

- 机制全开：SMP 每核 runqueue + 负载均衡、G4 demand paging、G5 DVFS/EAS、全量 syscall + 全服务集、x86_64 全量验证（P7）、AI 调度 M4 满配（×4 带 + 预算包络 + deadline-server 兜底，凭 v1 遥测入场券，ADR #42）。
- 边界诚实（12 号 §9 原则）：**可赢** = IPC 延迟 / 尾延迟 / 故障隔离 / 启动 / 空载零定时器唤醒；**明示放弃** = 服务器极限吞吐、GPU、驱动覆盖广度、桌面 GUI 通用性。
- "完全体"不是"什么都比 Linux 强"，是同一份内核在手表上省电、在 PC 上把可赢的维度真赢下来。

## 6. "分布式内核"辨析：别被名词带偏

- 鸿蒙的"分布式" = **软总线中间件**把多设备组成一个逻辑设备（应用流转、跨屏协同）——**每个设备内核各是各的，不是内核分布式**。学术界的分布式内核（多机单内存镜像 DSO 一系）40 年未主流，不追。
- BerryOS 的跨端答案分两层：
  1. **内核层 = 同源分端**：一份内核源码，手表/手机/PC 各自编译运行（XNU 模式）——这是已定决策；
  2. **策略层远期彩蛋**：AI 策略服务在用户态，天然**可以**跨设备（手机替手表算放置/频率）——AI 原生调度自带的分布式可能性，但 v1/v2 不进承诺。
- 一句话：**我们不需要"分布式内核"，需要"同一份内核各自跑，策略可以联网"**——按排除 8 问的精神，这个词不 PICK。

## 7. 判决与行动映射

| 判决 | 依据 |
|------|------|
| 架构差异化真实成立 | 纯能力 + 全 Rust + AI 注入面 + tickless day-one，四个位子三巨头都空着 |
| v1 战场选对了 | 手表端 = 差异化最值钱 + 宏内核短板最不疼（§4 两本账） |
| 最大的风险不在架构在生态 | 生态税 > IPC 税；G-eco 关是生死线，P4 起当第一优先级 |
| 不追"分布式内核" | 中间件概念，内核各跑各的；策略层联网是远期彩蛋非承诺 |

行动：① 守 ADR #39 单线纪律（每次想加"PC 也想要"时过 kill criteria）；② G-eco 关资源倾斜；③ 改放置路径必守 capacity 抽象（三端同源命脉）；④ AI 注入面是唯一"人无我有"的调度位面，护栏按 `AI调度设计.md`（带内限死、遥测入场券）执行。
