# seL4 与 L4 家族 调研报告

> 调研日期 2026-10-15 · 基于公开资料与源码快照（GitHub seL4/seL4 master，VERSION 16.0.0-dev，抓取于 2026-10-15） · 许可证：内核代码 GPL-2.0-only，libsel4 用户库 BSD-2-Clause（仓库根 `LICENSE.md`：「kernel-level code is licensed under GPLv2 and user-level code under the 2-clause BSD license」，全文用 SPDX 标签管理，`LICENSES/` 目录存全部许可文本）

## 0. 一句话定位

seL4 是 L4 微内核家族的第三代传人、世界上第一个（至今仍是唯一一个）完成端到端机器检查形式化证明的通用 OS 内核，同时保持着「IPC 最快的内核」的公开宣称——它用「机制极少、策略为零」的约一万行 C 内核，换来了可数学证明的安全隔离与约 400 cycle（Cortex-A57）量级的 IPC 往返。

## 2. 总体架构：内核形态、分层与组件，以及 L4 家族谱系

### 2.1 内核形态

**第三代 L4 微内核，纯能力（capability-only），单内核态镜像约 1 万行量级**。内核只提供：线程（TCB）、地址空间（VSpace）、端点（Endpoint）、通知（Notification）、能力空间（CNode）、无类型内存（Untyped）、回复对象（Reply，MCS）与调度上下文（SchedContext，MCS）。没有驱动、没有文件系统、没有网络栈、没有内核内存分配器、甚至没有内核内资源分配策略——**内存怎么分、页表怎么建、能力怎么派生，全部由用户态决定**（通过对 Untyped 能力的 retype）。syscall 总数约 10 个（`src/api/syscall.c` 的 `handleSyscall`：`SysSend/SysNBSend/SysCall/SysRecv/SysReply/SysReplyRecv/SysWait/SysNBWait/SysNBSendRecv/SysYield`，另有一组 `SysBenchmark*` 调试 syscall），是 BerryOS 计划的 ~26 个的一半以下。

### 2.2 分层与组件（seL4 生态全景）

- **内核**：`seL4/seL4` 仓库（GPLv2）。
- **用户态 API 库**：`libsel4`（同仓库内，BSD-2-Clause），只含常量/内联 syscall 桩，自动生成。
- **构建/测试**：seL4 test、sel4bench（公开基准套件）、CAmkES（组件框架，ADL 描述语言生成 IPC 胶水）。
- **能力描述**：capDL（capability distribution language）+ 可证明的用户态系统初始化器（capdl-loader）。
- **新一代组件 OS**：LionsOS（2025，trustworthy.systems 出品，arXiv:2501.06234），用 CAmkES 式组件图构建可推理的系统。
- **验证**：`seL4/l4v` 证明仓库（Isabelle/HOL，约数十万行证明，见 §3.4）。

### 2.3 L4 家族谱系（一节写全）

1. **L3（Liedtke，1980s，i386）**：第一代实证——微内核可以快，但内核内策略（分页器放在内核）拖了后腿。
2. **L4 原版（Liedtke，1993-95，i386）**：确立「**最小化机制 + 极致 IPC fastpath**」哲学，比同时代微内核（含 Mach）快 10-20 倍，定义了第二代微内核。Liedtke 名言「a concept is tolerated inside the kernel only if moving it outside the kernel is provably impossible」至今刻在 seL4 官网。
3. **L4 X.2 过渡期**（UNSW 与 Dresden 各自演进）。
4. **L4Ka::Pistachio（Karlsruhe + UNSW DiSy，V4 API）**：可移植、平台无关 ABI 的正统续作，后随团队重心转移而停更。
5. **Fiasco → Fiasco.OC → L4Re（TU Dresden → Kernkonzept）**：C++ 内核，OC 版引入内核能力模型；L4Re 从「Fiasco.OC 的评估工具」长成完整用户态运行时，主打**硬实时 + 虚拟化 + 车规**，是今天商业上最活跃的 L4 支系之一。
6. **NOVA（Steinberg & Kauer，EuroSys 2010）**：microhypervisor——把 L4 构造原则用于虚拟化，能力模型 + 极小特权域；现被 BedRock Systems 用作其验证底座（BedRock 另起 Rust 重写线）。Genode OS 同时支持 Fiasco.OC/NOVA 作为底核。
7. **seL4（NICTA/Data61/UNSW，2009 证明发布）**：第三代——在 L4 fastpath 基因上加**能力模型 + 形式化证明**。家族中唯一完成端到端证明、也是 IPC 最快的一支（白皮书：其他系统普遍比 seL4 慢 2-10 倍，Mi et al. 2019 实测 Fiasco.OC 约慢 2 倍多、Zircon 约慢 9 倍）。

家族一以贯之的思想是 **IPC fastpath**：把最常见的「同步 send/recv + 线程切换」路径压缩到几百条指令，其余全部走 slowpath。这条路径从 L4 原版汇编级手工优化，到 seL4 演进为「fastpath 本身也被形式化证明」（论文 *Correct, Fast, Maintainable — Choose Any Three!*）。

## 3. 核心机制深挖

### 3.1 IPC fastpath：检查链与实测数字

`src/fastpath/fastpath.c`（926 行，master 实抓）定义了 `fastpath_call` 与 `fastpath_reply_recv`。进入 fastpath 的条件是一长串「最常见情形」检查，任何一项不满足即 `slowpath(SysCall)` 退出——这段检查链本身就是微内核设计教科书（摘自实抓源码 33-71 行，路径 `src/fastpath/fastpath.c`）：

```c
/* Check there's no extra caps, the length is ok and there's no
 * saved fault. */
if (unlikely(fastpath_mi_check(msgInfo) ||
             fault_type != seL4_Fault_NullFault)) {
    slowpath(SysCall);
}
/* Lookup the cap */
ep_cap = lookup_fp(TCB_PTR_CTE_PTR(NODE_STATE(ksCurThread), tcbCTable)->cap, cptr);
/* Check it's an endpoint */
if (unlikely(!cap_capType_equals(ep_cap, cap_endpoint_cap) ||
             !cap_endpoint_cap_get_capCanSend(ep_cap))) {
    slowpath(SysCall);
}
...
/* Check that there's a thread waiting to receive */
if (unlikely(endpoint_ptr_get_state(ep_ptr) != EPState_Recv)) {
    slowpath(SysCall);
}
```

后续还包括：目标线程 VTable cap 有效、ASID 映射有效（ARM64/x86/RISC-V 各自的 `_fp` 内联版本）、优先级域检查（目标优先级不低于当前，或当前是最高优先级）、EP 有 `CanGrant/CanGrantReply` 权限、目标与当前同域、MCS 配置下目标无调度上下文（说明是被捐赠的 passive 服务端）且持有 reply 对象、SMP 下同核亲和。全部通过后，尾部做 `fastpath_copy_mrs`（寄存器级消息搬运）→ `switchToThread_fp`（内联上下文切换，不排队直接切）→ `fastpath_restore`，一次 syscall 完成调用+切换。**注意 fastpath 不做任何队列操作**——这是它快的根源。

**官方基准数字**（sel4.systems/performance.html，数据来自公开 sel4bench，单位 cycle，同核跨地址空间）：

| 平台 | IPC call | IPC reply | Notify | IRQ invoke |
|---|---|---|---|---|
| Armv7a A9/i.MX6 | 366 | 351 | 1024 | 777 |
| Armv8a A57/Jetson Tx1 | **413** | 426 | 1055 | 886 |
| x86_64 i7-6700 | 741 | 597 | 756 | 1669 |
| RV64 U54/HiFive | 714 | 796 | 1178 | 971 |

白皮书补充：Gu et al. 2016 实测 CertiKOS 往返 3,820 cycle vs seL4 1,830（后修正 sel4bench 的 x86 计时 bug，seL4 实际约 **720 cycle**，比 CertiKOS 快 5 倍以上）；Mi et al. 2019 实测 seL4 IPC 开销仅比「内核进入+地址空间切换+内核退出」的**硬件极限高 10-20%**，Fiasco.OC 接近 3 倍硬件极限，Zircon 约 9 倍——即 seL4 已把软件开销压到接近理论下限。

### 3.2 能力模型：cspace、派生树、权限粒度

内核里一切资源访问都过能力。核心数据结构极简（实抓 `include/object/structures.h:149`）：

```c
struct cte {
    cap_t cap;
    mdb_node_t cteMDBNode;
};
typedef struct cte cte_t;
```

cspace 是 CNode（能力节点树）构成的能力空间，每个线程 TCB 的 `tcbCTable` 指向自己的根 CNode。`cteMDBNode` 把所有 cap 串成 **MDB（capability derivation tree）**——copy/mint 派生的能力记亲子关系，revoke 操作沿树回收整个派生分支（`src/object/cnode.c` 的 `invokeCNodeRevoke/Delete/Insert/Move/Rotate`，行号 315-364）。权限粒度到字段级：例如 endpoint cap 有 `capCanSend/capCanReceive/canGrant/canGrantReply` 四个独立位，通知 cap、页帧 cap（读写执行）各自独立；`mint` 可在派生时**加徽章（badge）**不可逆地收窄语义（badged endpoint 用于 IRQ/通知身份标识），`cancelBadgedSends`（cnode.c:325）可取消徽章端点上未决发送。capDL 语言则把整套能力拓扑变成可静态描述、可被初始化器证明执行的规格。

**与 Zircon 务实派的根本差异**：seL4 连「分配内存给新对象」都不在内核做——内核只有 `Untyped` 能力 retype（`src/object/untyped.c`）这一条原语，用户态管理器自己决定把哪块物理内存 retype 成 TCB/EP/CNode。BerryOS 选的 Zircon 路线（内核有对象/分配器、handle 表在内核）是「够用的能力」，换取实现与验证复杂度都低一截——这是有意的取舍而非落后。

### 3.3 MCS（mixed-criticality）配置：reply 对象与调度上下文

MCS 是 seL4 的实时扩展，2020 年合入（5.2.0-mcs 预发布），目标成为默认配置。三个新机制：

1. **Reply 对象**：`seL4_Call` 产生的一次性 reply 能力被收进显式内核对象（此前是隐式能力），成为调用链上 **SC 捐赠的载体**。实抓 `src/object/reply.c:12` 的 `reply_push`：

```c
void reply_push(tcb_t *tcb_caller, tcb_t *tcb_callee, reply_t *reply, bool_t canDonate)
{
    sched_context_t *sc_donated = tcb_caller->tcbSchedContext;
    ...
    /* link caller and reply */
    reply->replyTCB = tcb_caller;
    setThreadStateBlockedOnReply(tcb_caller, reply);

    if (sc_donated != NULL && tcb_callee->tcbSchedContext == NULL && canDonate) {
        reply_t *old_caller = sc_donated->scReply;
        ...
```

2. **调度上下文（SC）**：CPU 时间本身成为能力（`src/object/schedcontext.c` / `schedcontrol.c`，`invokeSchedControl_ConfigureFlags(target, core, budget, period, ...)`），带预算/周期（refill 语义，`switchToThread` 中 `refill_sufficient/refill_ready` 断言可见，`src/kernel/thread.c:462`）。**时间隔离**由此实现：给低关键任务小 SC，它无论怎么疯跑都烧不完高关键任务的预算。
3. **Notification + SC 绑定**：notification 是一组二元信号量（`include/object/notification.h`），绑定 SC 后被动的中断处理线程能借预算运行（`maybeReturnSchedContext`）。

MCS 解决的是混合关键系统的**时间隔离与被动服务器**问题：无 SC 的线程（passive server）只能靠 donation 运行，天然防优先级反转式预算窃取。Lyons et al. 2018 是设计论文。

### 3.4 形式化验证链：证明了什么、没证明什么（边界如实）

**证明栈**（Isabelle/HOL，l4v 仓库）：抽象规格 → 设计规格 → C 代码（含 fastpath 与 slowpath）逐层精化（refinement），辅以三条独立性质。官网 Verification/proofs.html 列明的性质：

1. **功能正确性**：C 代码行为精确等于规格、「nothing more」——顺带豁免整类错误（缓冲区溢出、空指针、内存泄漏、UB）。
2. **安全三性质**：integrity（无授权不得改）、confidentiality（无授权不得读，信息流不干涉）、authority confinement；security theorems 附带对初始能力配置的前提。
3. **初始化正确性**：capDL 描述 + 用户态初始化器证明式建系统。
4. **二进制级正确性**：translation validation 证明二进制实现了被验证的 C（RISC-V 等配置已全链路覆盖，不再需要信任编译器）。

**2025-2026 最新进展（Proofcraft 官方新闻逐条核实）**：2025-09 证明覆盖升至「100% Arm 平台」（此前仅 3 个平台）；2026-08-21 **AArch64 安全证明（integrity+confidentiality+authority confinement）完成**（NCSC 持续资助）；**MCS 配置的功能正确性证明已在 RISC-V 完成、正移植 AArch64**；2026-09-21 「architecture split」重构砍掉 42 万行精化证明中的 25 万行（-57%），显著降低证明维护对专家的依赖（DARPA PROVERS 资助）。

**没证明什么（assumptions 页 + 学术共识，边界必须如实）**：
- **DMA**：证明假设 CPU 与 MMU 是唯一直接访存者——**DMA 视为关闭**；设备不受 IOMMU 约束时 DMA 可绕过一切证明（seL4 官方答复：用 IOMMU/SMMU 把设备也管起来，但这不在证明内）。
- **硬件正确性**：硬件按形式模型工作是假设。
- **单核（经典证明）**：SMP 支持在内核里（`src/smp/`），但 **SMP 配置尚未被证明覆盖**（假设页明言 SMP 同步以 cache 一致等为前提）。
- **启动代码/汇编/机器接口**（cache/TLB 维护等）不在 C 级证明内，靠测试。
- **时序/WCET 完全不在证明范围**：seL4 不是时间可证明内核（MCS 是工程级时间隔离，非 WCET 分析替代）；侧信道（cache/timing）同样不在模型内。
- **规格自身正确**：证明说的是「实现=规格」，你的规格用错了照样错。

一句话边界：**seL4 证明的是「这个万行内核没有实现错误且强制能力隔离」，不是「基于它的系统安全」**——后者还取决于初始能力配置（有 capDL+验证初始化器兜底）和证明假设全部成立。

### 3.5 电源与实时

seL4 内核**没有**任何电源管理机制（无 idle governor、无 DVFS、无 tickless 框架）——idle 就是空闲线程，策略全部上推用户态。这是「策略零」哲学的自然结果，对 BerryOS 的省电支柱而言 seL4 提供的是反面参照：tickless 的实现空间完全留白。实时方向（MCS 的 SC/refill、优先级+MCP 防优先级提升失控、域调度器）见 §3.3。

## 5. 亮点：好在哪

1. **端到端证明栈前无古人**：abstract spec → C → binary 全链路机器检查，且安全定理（integrity/confidentiality）直接建在实现上（proofs.html）；2026 年 AArch64 安全证明收口后，「已证明内核」覆盖最主流的 64 位 Arm。
2. **快与可证明兼得，且是实测的**：官方 sel4bench A57 上 IPC call 413 cycle、reply 426 cycle；独立实测显示软件开销仅超硬件极限 10-20%（白皮书引 Mi 2019），快过 Fiasco.OC 约 2 倍、Zircon 约 9 倍——「微内核=慢」的偏见被这一个家族终结。
3. **fastpath/slowpath 双径且双径皆证明**：不是靠未证明的汇编黑盒换速度（fastpath.c 头部 `FORCE_INLINE` 的 `fastpath_call` 在证明范围内），回应了「Correct, Fast, Maintainable — choose any three」。
4. **「策略零」是可验证性的前提而非洁癖**：内核不含资源分配策略，状态空间才小到可穷尽推理；50k 行现代源码仍维持证明可维护（2026 architecture split 砍 57% 证明行数）。
5. **单一事实源生成代码与证明**：bitfield 生成器从 `.bf` 同时产 C 与 HOL，结构体注释标 word 数——证明工程化到「改代码不破证明」的程度。
6. **治理与工程规范是开源内核范本**：SPDX 全覆盖、CHANGES.md 语义化兼容分级（BINARY/SOURCE/BREAKING）、RFC 流程、公开角色晋升路径；基金会+Proofcraft 让证明维护有持续商业模式（NCSC/DARPA 资助）。
7. **20 年谱系迭代而非一步登天**：L3→L4→X.2→各支系→seL4，每代都有论文级复盘（From L3 to seL4, SOSP13），路径本身可复用。

## 6. 不足与争议：不好在哪

1. **生态薄、上手陡**：内核之外一切自建——驱动、libc、运行时要靠 CAmkES/sel4runtime 手搓，官方也承认组件框架学习曲线陡；以至于 2025 年还要发 LionsOS 来补「可用的组件化系统」层（arXiv:2501.06234）。「能跑 seL4」到「能用 seL4 做产品」之间隔着一个 HENSOLDT 级工程团队。
2. **证明永远追着内核跑**：SMP 支持进了内核多年仍未被证明覆盖；MCS 2020 年合入、2026 年才证完 RISC-V 功能正确性（AArch64 移植中）；每一个新特性都要人年级证明成本——这也是 BerryOS 不可能走全证明路线的现实理由。
3. **证明边界的营销噪音**：「被证明安全」常被读过头；官方 assumptions 页明确 DMA 关闭、硬件正确、单核（经典）、启动/汇编不在证明内、侧信道与 WCET 不在范围。买 seL4 不等于买到安全系统。
4. **极简内核把复杂度转嫁给用户态**：untyped 内存规划、能力拓扑设计（capDL）、初始化器都是集成者的活；做错初始配置，安全定理的前提就不成立。对资源型团队，Zircon 式「内核代管一部分」反而总成本更低。
5. **GPLv2 内核的传染边界**：内核 GPL-2.0-only，闭源产品只能以 syscall 边界隔离（官方 syscall note），内核修改必须开源；对照 BerryOS「GPL 只看思路、不复制实质代码」的纪律，seL4 源码只能读不能搬。
6. **C 语言 + 手写证明，专家依赖重**：证明维护历史上集中在少数人（Proofcraft 的 architecture split 正是为降低这种依赖）；Rust 等现代语言红利（aliasing 等 UB 类错误类型直接消失）seL4 吃不到。
7. **无电源管理、无现代设备模型**：省电、热管理完全留白（对 BerryOS 场景是缺口）；IOMMU 时代的设备隔离依赖集成者自行拼装。

## 7. 对 BerryOS 的借鉴与警示（对照四支柱）

**支柱① 微内核（Zircon 务实派）**
- 借鉴：fastpath/slowpath 分层——把「同步 send→同核接收者→直切」写成一条独立短路径，检查链逐条短路（无 fault、单 cap 查找、EP 处于 Recv、ASID 有效、优先级域、同核），不满足走通用路径；BerryOS 的 `object_*` syscall 合并思路与 seL4 的 ~10 syscall 设计同向，可再压。能力派生树（MDB）与 `revoke` 沿树回收、mint+badge 不可逆收窄——Rust 实现可仿机制不抄代码。notification 的「二元信号量数组 + 绑定」语义比信号量队列简单得多，BerryOS 的异步通知可直接对标。
- 警示：**别学 untyped 全用户态内存分配**——Zircon 务实派（内核分配器/对象）是 BerryOS 已定的 ADR，seL4 的代价（初始化器复杂度）已由它自己证明（需要 capDL+证明式初始化器兜底）。GPL：seL4 内核代码一个字都不能进 BerryOS，本报告全部引用仅为思路对照。

**支柱② 省电（手表/手机）**
- 借鉴（反面教材型）：seL4 内核对电源零贡献也活得好好的，说明 tickless/idle 不需要内核复杂机制——BerryOS 的「idle mask CNTV + WFI」路线与之一致；PM 全推用户态服务（seL4 连 governor 概念都没有）佐证 BerryOS「PM 服务可崩、内核降级保活」分层成立。
- 警示：seL4 没有手表级省电实践可抄，DVFS 决策延迟（要走 IPC 问用户态）对省电场景是真实成本——BerryOS 用共享环形缓冲绕开通销的设计正是针对这个坑。

**支柱③ AI 原生调度**
- 借鉴：**SC 把「CPU 时间」本身做成能力**，是「机制在内核、策略在外部」的最纯样例——内核只做 refill 预算机制，怎么配预算（`SchedControl_Configure`）完全是外部策略输入。这与 BerryOS「内核留 ABI、用户态 AI 干涉放置/频率/优先级」结构同构；reply 对象的 SC 捐赠链（`reply_push`）演示了策略代理如何安全传递执行权。AI 调度的护栏可类比 SC 预算：AI 再怎么建议，内核按预算硬约束兜底。
- 警示：MCS 的 SC 是静态配置模型，动态 AI 干涉要防「配置抖动」，seL4 没有现成答案。

**支柱④ PC 高性能**
- 借鉴：fastpath 的「同核直切不排队」（`switchToThread_fp`）、消息寄存器传递（MR 数量受限时零拷贝）、`nbsendrecv` 合并系统调用等微优化；sel4bench 作为基准方法论（公开数字+公开实验装置+可复跑）值得 BerryOS 的 G 关卡测试照搬姿态。
- 警示：seL4 的 SMP 调度仍是每核 runqueue+优先级，负载均衡同样不复杂——高性能主要来自 IPC 路径而非调度器魔法；BerryOS 双线并行的重心（负载均衡）是差异化而非补课。

**通用工程借鉴**：bitfield 单一事实源生成代码+规格（BerryOS 可做「一份定义生成 `#[repr(C)]` 结构 + 文档 + 测试桩」）；SPDX 全仓许可管理；CHANGES.md 兼容级标注（内核 ABI 演进纪律）；syscall 边界的 GPL 澄清声明（BerryOS 全 Rust+自有 ABI 无此包袱，但值得写清楚）。

**通用警示**：不要把「形式化验证」写进 BerryOS 承诺——seL4 20 人年起的证明成本和「证明追不上特性」的节奏是前车之鉴；可选路线是 Zircon 式安全 Rust 外壳 + 局部不变量测试（G 关卡），最多在能力派生等关键不变量上做轻量模型检查。
