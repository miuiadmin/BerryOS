# 16 · 新生代 OS 设计初衷考（1985–2025）：八系统的赌注、牺牲与死因

> 调研对象：Plan 9、GNU Hurd、BeOS、Redox、Theseus、rCore、Fuchsia、HarmonyOS 八个"从零而写"的系统，辅以 Inferno、serenityOS 两个注脚。技术内幕见既有报告（内核矩阵见 03 号、L4 家族见 04 号、Zircon 见 05 号、Rust 系四家见 11 号），本文只做"演化史 / 踩坑史"视角，重叠处一律交叉引用不重复展开。

## 0. TL;DR

- 每个新生代 OS 的诞生动机都是同一个公式：**「当红系统欠下的历史债」+「一个关于未来计算形态的赌注」**。八家无一例外。
- 它们的**架构判断大多被证明是对的**（9P/每进程命名空间进了 Linux 容器与 WSL；Be 的内核经 NewOS→LK 长成了 Zircon；Rust 安全路线成了新默认；分布式软总线正在跑通）。商业上死掉的系统几乎全部死于**生态冷启动、驱动、金主耐心、时机窗口**四件事，而非架构错误。
- 遗产转移有两条通道：**理念通道**（Plan 9 namespace → Linux 容器；BFS 的"扩展属性+实时查询" → Spotlight 式元数据检索；Be 泛线程化 → 多核时代的默认现实）与**代码/血缘通道**（9P 进 Linux/WSL；OpenHarmony 捐入开放原子；Geiselbrecht 一条师徒线从 Be 内核走到 Zircon）。
- 对 BerryOS 最重要的一条：**架构上"干净"不构成生存优势；"锚定一个可验证的真实负载 + 分阶段关卡 + 可控的开源/兼容时机"才构成。**

| 年代 / 系统 | 在优化什么（针对什么历史债） | 踩的坑 | 关键调整 |
|---|---|---|---|
| 1985–1995 Plan 9（+Inferno 1996） | 分时主机债：集中式计算、Unix 全局命名空间 | 商业收费发布撞上免费 Linux/BSD 浪潮；工作站普及反而吃掉核心需求 | 弃 Alef 语言改线程库；2000 年才开源（太迟）；Inferno 换赛道再败 |
| 1990– GNU Hurd | 专有 Unix 债：内核不可改、无自由内核 | 等 Mach 自由许可约 3 年；Mach IPC 慢 | 微内核基座四迁：Mach→L4(2002)→Coyotos(2006)→Viengoos，仍未成 |
| 1990–2001 BeOS | Win95/Mac 债：协同多任务、弱内存保护、多媒体延迟无保证 | OEM 渠道被锁（2003 年微软 2325 万美元和解反垄断诉讼）；BeIA 转型踏空 | 1998 转 x86 + 2000 免费版；2001 资产售予 Palm；Haiku 接棒至今未到 R1 正式版 |
| 2015– Redox | C 内存安全债 + 单体内核债 + UID 位权限 | 早于 Rust 1.0 起跑；libc/工具链/驱动生态全自建 | scheme 统一资源命名 + relibc + 用户态驱动；0.9.x（2025-09）仍未 1.0 |
| 2016– Theseus | OS 结构僵化 + 内核态内部可变性之恶 | 学术单冠军、无部署出口 | crate_swap/OTA 活演化；2024-09 后停滞 |
| 2016– Fuchsia | POSIX 时代安全模型债（环境权限）+ 单体内核更新难 | 非 POSIX 的生态重建账单；金主耐心（2023-01 裁约 16%） | Starnix 重新进口 Linux ABI；devfs 走过 POSIX 式弯路再折返 |
| 2012/2016– HarmonyOS | 单设备 OS 债：跨设备协同无一等公民抽象 | 双框架兼容税；生态依赖安卓 | 2019 制裁倒逼 → 2024 HarmonyOS NEXT 全面去安卓 |
| 2008– rCore（教学线） | 教学 OS 停留在 C/xv6，学生通篇读 unsafe C | 教学/生产两头拉扯 | 教学线 rCore-Tutorial v3 独活（2k+ star 仍活跃）；生产线裂变为 ArceOS/Starry |

## 1. Plan 9（Bell Labs，1985 起）：赌"资源就是文件服务器"

**① 出生与历史债**。1980 年代中后期由 Bell Labs 计算科学研究中心启动（初期主力 Pike、Thompson、Presotto、Winterbottom、Trickey，Ritchie 作为部门主管支持），1990-07 首篇公开论文。当红 Unix 欠的债：分时集中式模型在"个人工作站 + 局域网"时代已经变形——Pike 在 1995 年论文里原话承认，用户"对超载、官僚的分时机器感到厌倦，宁可净损失也要换到小而自维护的系统"；而 Unix 的全局命名空间无法表达"每人一台用网络资源拼装出来的机器"。讽刺的是：工作站转型**既是 Plan 9 的动机，也顺手解决了用户的痛**——Pike 自己分析，这抽走了 Plan 9 的存在理由；且应用里嵌死了全局命名空间假设，两条根基想法（每进程命名空间、9P）无法廉价回装进 Unix。

**② 核心赌注**。把"一切皆文件"推到极限：每进程可组合命名空间 + 面向连接的 9P 文件协议 + union 目录；/proc、/net 全是文件树；UTF-8 由 Thompson 于 1992 年为它发明。

**③ 主动牺牲**。Unix 二进制/源码兼容（clean slate）；不追 POSIX 认证；**商业授权发布**（第二版 1995 年经 Harcourt 商业发行，源码收费）——等于主动站在了正在起来的自由软件浪潮的对立面。

**④ 结局与死因**。商业死、开源活（"reincarnated"）。直接死因链：1992/1995 收费发布撞上免费 Linux/BSD 崛起 → 设备驱动与应用生态双缺（官方承认） → 1996 年 Lucent 为押注 Inferno 对打 Java 把它搁上"back burner" → 2000 年第三版才开源，2014 年改 GPL，2021-03 移交 Plan 9 Foundation（MIT 许可）。唯一像样的商业用户是存储厂商 Coraid；9front 分支延续至今。ESR 的判词最有资格刻在墓碑上：**"Plan 9 之败，只因它对 Unix 的改进不足以替换其祖先——足够好的既有代码库，是更优方案最危险的敌人。"**

**⑤ 遗产专章：9P 与每进程命名空间的转世**。
- Linux namespaces：Wikipedia 明载"重度受 Plan 9 启发"；mount namespace（Al Viro，2002）是 Linux 第一种 namespace，其工作明确引用论文《Name Spaces in Plan 9》。今天容器编排的底座是 Plan 9 的直接后裔。
- 9P：进 Linux（v9fs）、FUSE 生态；**WSL 自 Windows 10 1903 起以 9P 承载 Windows↔Linux 文件互操作（\wsl$）**——微软成了 9P 最大的当代部署者。
- union 目录思想影响 4.4BSD/Linux 的 union mounts（LWN 2009）；rfork 进程模型被 Linus 在《The Linux Edge》(1999) 中点名影响 Linux clone；/net 树是"网络即文件"的原型。
- 理念通道：Pike 与 Thompson（同 Griesemer）后来造了 Go；UTF-8 统一了世界文本编码。
- 附带一个前瞻性批评：Spring 系统（Roscoe，1995）指出 9P 式无类型接口"禁止类型检查"——25 年后 Fuchsia 的 FIDL 正是对这份批评的正式回应（见 §5）。

## 2. GNU Hurd（1990– ）：赌"最大模块化"，输给了时间

**①** 1990–91 年由 Thomas Bushnell（BSG）依 Stallman 1987–88 年的提议基于 CMU Mach 3 构建。债：专有 Unix 当道、无自由内核（Minix 不自由、BSD 陷 USL 诉讼）。**②** 多服务器微内核：内核只剩 Mach，auth/exec/fs 全是可运行时替换的用户态服务器；**translator 哲学**——`settrans` 让任意路径节点挂上用户态程序动态供给内容，"每个文件都可以是一个小守护进程"。**③** 牺牲发布时间换模块化纯度；牺牲性能——Mach IPC 出了名的慢，这份痛直接催生了 L4 家族（详见 04 号报告）。**④** 活着的僵尸：从未到 1.0（0.2 于 1997-06，0.6 于 2015）；Debian GNU/Hurd 打包二十余年无正式发行版；GNU 官方 FAQ 自认"比 Linux 慢、Mach 已非先进"。死因链：等 CMU 释放自由许可耗掉约 3 年 → Linux 填真空（Linus 明说若有自由内核就不会写 Linux） → 士气人力崩 → 基座迁移（L4→Coyotos→Viengoos）一次次推倒重来；Bushnell 本人 2002 年被移出开发（LWN 报道）。Stallman 2013 年认错："基于 Mach 开发 GNU 内核的技术决定由我负全责……我以为用 Mach 能省下一大块工作，我错了。"**⑤** translator 哲学活成了 FUSE 与 Plan 9 每进程命名空间的近亲——"文件系统行为可编程"这一支今天以用户态文件系统/可编程挂载的形态存活；Hurd 本身则成了"微内核过度模块化"的头号教学案例。

## 3. BeOS（Be Inc.，1990–2001）：赌"多媒体是一等公民"

**①** Be Inc. 1990-10 由前 Apple 高管 Gassée 与 Sakoman 创立；BeBox（双 PowerPC，1995–97）→ 1998-03 R3 首个 x86 商业版 → 2000 R5 拆出免费个人版 → BeIA 转向网络家电 → 2001 Palm 以约 1100 万美元收购资产。债：Win95/Mac OS 7–9 协同多任务、缺内存保护、音视频延迟无保证。**②** "Media OS"：**泛线程化**（每窗口一线程，BLooper/BMessage 强制消息驱动，抢占式内核）；BFS——64 位、日志、扩展属性 + 实时查询（Giampaolo 与 Meurillon 约 10 个月写成，1996）。**③** 彻底放弃向后兼容（无 DOS/Mac 遗产），代价是从零引第三方生态。**④** 公司死、OS 转生（Haiku，2024-09 才发布 R1/beta5，beta6 已跟进）。直接死因：OEM 渠道被排他协议锁死——2003-09 微软以 2325 万美元和解 Be 的反垄断诉讼，等于官方盖印；1996 年 Apple 收购谈判破裂转投 NeXT（Gassée 要价过高的具体数字各方说法不一，存疑）；BeIA 押注不成熟市场，双重踏空。**⑤ 遗产专章（调度线）**：Haiku 直接继承；"媒体线程应获得更高优先级 + 调度器须保证低延迟"的理念，与 Windows Vista 的 MMCSS、Core Audio 实时线程、PipeWire 的 RT 化**同构**（理念谱系，非代码直传）；泛线程化预演了多核时代的默认现实——但"强迫所有 ISV 多线程"等于把难度转嫁给开发者，是超前的正确也照样致命。另两条血缘：BFS 作者 Giampaolo 后入 Apple 参与 APFS（据其公开履历）；**内核师徒线 Geiselbrecht：Be 内核 → NewOS（Haiku 早期基座）→ LK → Magenta → Zircon**（详见 05 号报告）。

## 4. Redox / Theseus / rCore：Rust 一代的三种赌法（技术内幕详见 11 号报告）

**Redox（2015-04-20 首发，早于 Rust 1.0；Jeremy Soller）**。债 = C 内存安全 + 单体内核 + UID 位权限。赌注：全 Rust 微内核 + **scheme 统一资源命名**（`disk:0/...`，一切资源皆 URL）+ 用户态驱动 + relibc。牺牲：POSIX 完整性、硬件覆盖、十年仍未 1.0（0.9.x，2025-09）。现状：靠社区捐赠 + System76（COSMIC 桌面复用其组件）长期供养。继承：relibc 等组件成了 Rust OS 公共财产；"Rust 能写真 OS"的活证明。

**Theseus（Rice 大学，OSDI'20 论文）**。债 = OS 结构僵化 + 内核内部可变性导致的演化困难。赌注：**intralingual design**——用 Rust 类型系统本身（所有权、类型即状态）消灭非法状态，进而实现不停机活演化（crate_swap/OTA 更新）。牺牲：一切实用部署。结局：2024-09 后停滞，作者 Boos 的 FOSDEM 2025 履历已用"Previously"字样；死因 = **学术单冠军毕业即散**（经费情况未见公开来源，存疑）。继承：OSDI'20 论文（被引百余次）把"语言内设计"写进了 OS 课程。

**rCore（清华，2008 起）**。血统：Kaashoek 访华带来 xv6 → uCore（x86 教学）→ RISC-V 移植尝试（向勇/陈渝团队，CRVF 2019）→ rCore（Rust+RISC-V 重写）→ rCore-Tutorial v3 → ArceOS/Starry。债 = 教学 OS 停留在 C。赌注：Rust 的教学清晰度 + RISC-V 开放指令集 + 贴合 OS 发展史的"从简到繁"教程。牺牲：生产野心。结局：家族中最成功的是教学线（2k+ star、os2edu 训练营），生产线裂变。继承：一代中国 OS 学生的第一行内核代码。

**Rust-OS 共同工程坑（与 BerryOS 同路，详见 11 号报告 §3.5）**：unsafe 实际收敛在 HAL/页表/上下文切换小块，"Rust 内核天然安全"是夸大；没有现成的 Rust 通用 OS 基座，libc/工具链人人自建（Redox 的 relibc、Theseus 的全套自造）——**真实税是生态而非语言**；治理上普遍是"微型捐赠 + 单公司雇佣"的脆弱结构。

## 5. Fuchsia（Google，约 2016– ）：非 POSIX 起点是资产还是负债？

（Zircon 内部设计详见 05 号报告）**①** 约 2016 年立项，2021-05 首个商用设备（第一代 Nest Hub）、2021-08 全量推送，2023-05 扩到二代 Hub。债：环境权限（ambient authority）的 POSIX/Linux 安全模型、单体内核更新难、驱动模型碎片。**②** 能力微内核 Zircon + 一切皆组件 + **类型化 IPC（FIDL）** + 用户态驱动——FIDL 恰是对 §1 末 Spring 批评（无类型文件接口）的正式回应。**③** 主动放弃 POSIX：Zircon 不提供 fork/传统 Unix 系统调用，代价是整个 Linux 软件与驱动生态重建。**④** 活着但收缩：2023-01 裁员约 16%（同期全公司约 6%），Ars Technica 标题直问"项目前途"；至今只部署在 Nest Hub 一条产品线，被 HN 戏称"洗衣机操作系统"。**⑤ 论战与判词**。资产派：能力模型 + 无 fork 是安全与可更新的根基，2020 年代有论者认为 AI 时代的干净底座反而成了 Zircon 的机会（观点性文章，非定论）；负债派（Lobsters 2019 "Fuchsia is not unix"、HN "Zircon API 臃肿不如 L4 干净"、Reddit 曝内部争论）：生态引力不可违。**最硬的证据是 Starnix**：Fuchsia 后来内建 Linux 系统调用翻译层以运行存量 Linux/安卓软件，等于把当年主动扔掉的 POSIX 债再买回来；devfs 也走过"POSIX 式目录设备命名空间"的弯路再折返。判词：**非 POSIX 本身不是死因，"没有被动用户市场兜底的非 POSIX"才是**——对照 HarmonyOS NEXT 敢切安卓，恰因其有兜底。

## 6. HarmonyOS（华为，2012 预研 / 2016 立项– ）：赌"设备即外设"

（内核矩阵与开源争议详见 03 号报告）**①** 2012 年起预研，2016-05 正式立项（王成录带队），2017 年向任正非演示手机"碰一碰"音箱并定调"为万物互联而生的操作系统"，2019-08-09 发布 1.0，2021-06 上手机，2024 NEXT 商用。债：安卓的**单设备假设**——跨设备协同靠应用各自为战，没有一等公民抽象。**②** 分布式软总线 + 超级终端：把局域网内一组设备虚拟成一台机器（分布式任务调度/数据管理/硬件虚拟化），低时延确定性调度配套。**③** 双框架时代牺牲纯度换生态冷启动（兼容 AOSP）；NEXT 时代反向牺牲兼容换性能与自主——2019 年制裁把"要不要切"变成"必须切"（2024-06 华为官方确认不兼容安卓，Canalys 解读为三分格局冲击）。**④** 活着，且是本轮唯一长出第三极生态的样本；但鸿蒙内核闭源、2024 下半年起固件内核加密引发安全社区批评（详见 03 号报告 §6）。**⑤** 继承未定：OpenHarmony（2020-09 捐入开放原子）承开源线，软总线/分布式软调度范式已被国内全行业跟进。

## 7. 被推翻的决策

| 决策 | 当初理由 | 推翻触发 | 教训 |
|---|---|---|---|
| Plan 9 自研并发语言 Alef | 语言级并发更优雅 | 维护成本失控，第 3 版起移除改线程库 | 自研语言是奢侈品；Redox/Theseus 的共识是寄生在 Rust 上 |
| Hurd 基于 Mach | 复用 CMU 成果省时间 | Mach IPC 慢 + 维护泥潭 → 四次迁基座 | 借来的地基必须先过核心性能预算审计 |
| Be 桌面 Media OS → BeIA 家电 | OEM 桌面渠道被锁死 | 家电市场本身未成熟 | 向不成熟市场转型 = 双倍赌注，两头死 |
| Fuchsia 纯净非 POSIX | 能力模型不容 fork/环境权限 | 生态引力 → Starnix 重进口 Linux ABI | 兼容层迟早要建，不如一开始就规划分阶段进口 |
| HarmonyOS 双框架兼容 AOSP | 应用冷启动需要安卓兼容 | 2019 制裁 + 双框架性能税 | 兼容是阶段不是终点；但只有市场支配力付得起切割成本 |
| serenityOS 内自研 Ladybird | 自有 OS 需要自有浏览器 | 双创业叠加；2024-06 Kling 分叉 Ladybird 并辞任 BDFL | 一个战壕塞不下两个创业项目 |

## 8. 人物与组织因素

- **Bell Labs / Lucent——企业惰性**：技术全对，但 Lucent 的 KPI 里没有"卖 OS"；2021 年移交 Plan 9 Foundation（MIT 许可）才安顿。
- **FSF——无金主的慢决策**：为等自由许可付出三年窗口期，RMS 一句"我错了"背后是整个项目的命。
- **Be——渠道政治**：Gassée 的苹果旧部光环敌不过排他协议；2325 万美元和解金只够清算，救不了公司。
- **Google vs 华为——金主的痛感**：同为巨头内部创新，Google 把 Fuchsia 当可裁撤的实验田，华为把鸿蒙当生存问题倾注全公司——**金主的痛感决定项目的韧度**。
- **Rust 一代——单冠军风险**：Soller/Boos/陈渝各撑一门；Theseus 停在毕业线上；serenityOS 靠 BDFL 个人意志维系，最终以分叉自保。rCore 证明**体制化资助**（课程/竞赛/os2edu）是学术 OS 存活的现实路径。

## 9. 新生代 OS 死亡率分析（四因子）

- **应用生态**（头号杀手）：Plan 9 应用/驱动双缺；BeOS 无 OEM 即无预装即无用户；Hurd 被 Linux 用"够好 + 免费"截胡；Fuchsia 被迫造 Starnix 补课。唯一反例是 HarmonyOS NEXT——**制裁制造的被动用户市场替代了自然生态**，那是市场支配力，不是工程成就，不可复制。
- **驱动**：OS 的暗物质。Plan 9 官方承认驱动不足；BeOS 死于渠道实质是死于预装；Fuchsia 只能自建驱动栈——只有大金主付得起这张账单；Redox 十年硬件覆盖仍有限。把驱动放用户态（Redox/Fuchsia/BerryOS 路线）只是**移位成本，并未消灭成本**。
- **金主**：Lucent（无 KPI→搁置）、FSF（无钱）、Be（烧完融资）、Google（战略实验，可裁）、华为（生存级投入）、捐赠 + System76（微型但长期）。**金主的耐心结构比金额重要**：按季考核的金主救不了十年周期的物种。
- **时机**：Plan 9 若 1993 年免费而非 2000 年；Hurd 若不等 Mach 三年；Be 若早两年切 x86；Fuchsia 撞上语音助手退潮。时机不可控，但**"何时免费/开源"是可控的时机**——这是 Plan 9 付得最贵的一笔学费。

## 10. 给 BerryOS 的启示（克制版）

1. **先立 IPC 成本预算，再写通道**（Hurd/L4 教训，详见 04 号报告）：微内核的生死不在"是否微内核"，在每消息成本。建议把同步 IPC 的延迟/吞吐纳入 G 卡指标，超预算即视为设计回归。
2. **POSIX 兼容层按"分阶段进口"设计**（Plan 9/Fuchsia 双向教训）：BerryOS 的"自有 ABI + POSIX 库、无 fork"方向正确，但兼容层要预置裁剪/降级开关，避免未来被生态引力逼出第二次 Starnix 式重构。
3. **Rust 税的真实构成是生态而非 unsafe**（详见 11 号报告）：凡社区已有（no_std crate、驱动框架、libc 方案）一律复用，内核面保持最小——Redox 十年未 1.0 的主因是全自建。
4. **去单冠军化**：Theseus/serenityOS 的死法都是"人走茶凉"。BerryOS 已有 G0–G5 关卡、ADR 化的架构决策文档与 QEMU 里程碑提交纪律，应坚持：每阶段产出不经任何个人也能复现的验证路径。
5. **AI 调度赌注锚定可感知指标**（Fuchsia 教训）：干净底座只有兑换成用户可感价值（手表续航、音频/交互延迟）才免于"洗衣机 OS"命运。AI 原生调度接口应绑定一两个可测场景（如省电模式下 EPP 自动切换的收益量化），先在 QEMU/手表形态拿到数字。
