# 调度器与电源管理设计

> BerryOS 用**一个调度器内核**同时服务两类极端场景。本文是单一事实来源，`CLAUDE.md` / `AGENTS.md` 中的调度器约束是本文的摘要。

## 1. 目标与约束

| 场景 | 平台 | 关键诉求 |
|------|------|----------|
| 可穿戴 / 手机 | ARM 大小核、单/少核、电池 | 省电、低唤醒延迟、DVFS、深睡 |
| 桌面 / 服务器 | x86_64 / ARM64 对称多核 | 高吞吐、低尾延迟、多核扩展 |

**已定策略：双线并行** —— 省电路径与多核性能路径同时作为一等公民推进，接受更高复杂度，不分先后。

**核心原则：机制进内核、策略可插拔、把"算力不对称"抽象掉、电源管理做成用户态服务。**

## 2. 总体架构

```
            ┌──────────────────────────────────────────┐
用户态 Rust  │  PM 服务：DVFS governor / 热管理 / 休眠策略 │
            │  AI 调度服务：工作负载分类 → 放置/优先级策略 │
            │   ▲ 遥测(共享环)   ▼ 策略注入(共享环,SET_POLICY)│
────────────┼──────────────────────────────────────────┼───
内核态 Rust  │  调度器核心：每核 runqueue + class 派发框架  │
            │   ├─ class_rt       实时（★ AI 不得干涉）   │
            │   ├─ class_fair     EEVDF, 吞吐/公平        │
            │   ├─ class_deadline 媒体截止期（★AI不得干涉）│
            │   └─ class_idle     进 idle 状态            │
            │  capacity / 负载均衡 / tickless / 安全护栏   │
            └──────────────────────────────────────────┘
```

**职责切分（微内核硬约束）**
- 不可委托、留内核：上下文切换、runqueue、定时器/tick、idle 入口、改频原语、capacity 拓扑。
- 可委托、推用户态：DVFS 算法、热管理策略、休眠决策、调度策略调参。

理由：调度在中断/缺页时也要跑、每秒千次、不容 IPC 延迟 → 机制必须在内核；而策略重、可调、可崩 → 推用户态，崩了内核降级保活。

## 3. 调度机制（内核 Rust）

### 3.1 每核 runqueue + 派发框架
- 每个 CPU 一个 runqueue，热路径几乎不加锁。
- 派发循环：按 class 优先级链查 `pick_next()`，高优先级类（rt/deadline）先空才轮到 fair。
- 上下文切换是固定原语，与策略解耦。

### 3.2 可插拔调度类
每个 class 实现统一接口，启动时按平台注册默认 class 集：

```rust
trait SchedClass {
    fn enqueue(&self, t: &mut Task, rq: &mut Runqueue);
    fn dequeue(&self, t: &mut Task, rq: &mut Runqueue);
    fn pick_next(&self, rq: &Runqueue, topo: &Topo) -> Option<&mut Task>;
    fn tick(&self, t: &mut Task, rq: &mut Runqueue);
    fn priority(&self) -> i32;   // class 间优先级
}
```

### 3.3 capacity 不对称抽象（统一三端的关键）
- 每个 CPU 一个 `capacity`(0..1023) 与 `max_freq`：
  - PC：全 1023（对称）→ 不对称代码退化为 no-op。
  - 手机 big.LITTLE：big=1023 / mid≈700 / little=300。
  - 手表：单核 ≈300。
- energy-aware 放置：小背景任务→小核；突发 perf 任务→大核。对称 PC 看到全相等 → 退化成普通负载均衡。**一条路径三端通用**。
- 拓扑/capacity 由 `架构相关/<arch>/` 启动时填表，核心逻辑架构无关。

### 3.4 负载均衡 / work stealing
- 空闲核定时或被唤醒时从忙核拉任务；考虑 capacity 与能耗（不在小核堆满）。
- PC 多核吞吐主力；手表 1–2 核时近乎零开销。

### 3.5 裁决补注（2026-10-15 战略裁决）
- **fair 类底座写定 EEVDF**（非 CFS）：M4 实现时直接按 EEVDF 语义（虚拟截止期 + lag 排序）落，避免「先 CFS 后 EEVDF」的返工；Linux 6.6+ 仅作思路（GPL）。
- **时间片周期数记账（DVFS 预埋）**：slice 以**周期数**而非绝对时间记账，随当前频点换算（LiteOS-M `OsSchedTimeConvertFreq` 式，调研 03 号）——否则 DVFS 上线后时间片实际时长随频率漂移，省电线与性能线在此汇合。表示法字段随 Phase 2b 落地（见 `路线图.md` P2b）。
- **SMP 锚点**：v1 全程单核贯穿 MVP，不为「将来多核」提前缴复杂度税；per-CPU runqueue 数据结构 day-one 按每核数组写（G1 已如此），但锁与均衡逻辑 G2 才进（关卡顺序即纪律）。

## 4. 省电路径（tickless + idle）

### 4.1 Tickless（NO_HZ）—— 续航第一杠杆
- 每核动态 tick：runqueue 空的核**不收周期定时中断**，把下次定时器编程到"有活到达 / 最早截止期"。
- 双线并行的硬要求：从 day-one 就走真省电路径，不是后期打补丁。

### 4.2 Idle 状态 / C-states
- runqueue 空且无 pending → `class_idle` 接管 → 进最深可用低功耗状态（ARM: WFI 及更深；x86: C-state）。
- 唤醒延迟与省电深度的权衡由 PM 服务定（用户态策略）。

## 5. 电源管理服务（用户态 Rust）

### 5.1 governor 职责
- 订阅利用率（PELT/util_est 风格）→ 算目标频率（schedutil 风格：util→freq）。
- 决定簇（cluster）频率、热限频、休眠/唤醒策略。
- 可加载不同 governor：`watch`（激进省电）/ `perf`（跑分）/ `balanced`。

### 5.2 内核 ↔ PM 通信（低延迟硬约束）
- **共享环形缓冲**传利用率事件与设频请求；**禁止通用 IPC 消息拷贝**（否则吃延迟）。
- 内核侧只暴露最小钩子；频率变更由内核原语执行（写时钟 / 调压器寄存器）。

### 5.3 容错
- PM 服务崩溃 → 内核保住上次频率继续跑，监督重启服务。调度不依赖 PM 在线。

## 6. 每任务能效/性能 hint（EPP 风格）
- 每个任务带 hint：`perf`（大核 + 高频）或 `efficiency`（小核 + 低频）。
- UI/音频/传感器 = perf；同步/备份 = efficiency。
- PC：hint 映射到 boost 选择；手机：映射到大小核 + DVFS；手表：影响频率。

## 7. 诚实的代价 / 取舍
- tickless + 不对称感知 + 可插拔类 + 用户态 PM = **显著复杂度与调参面**。这是跨手表→PC 不 fork 的代价。
- PM 拆用户态是真红利，但通信必须共享环/零拷贝，否则延迟劣化。
- 双线并行意味着两条线都要有 QEMU 验证用例：多核 `virt` 机型（性能线）+ 单核低功耗场景（省电线）。

## 8. 双线搭建路线（并行，非串行）

| 里程碑 | 内容 | 服务线 | 状态 |
|--------|------|--------|------|
| M0 | 每核 runqueue + class 接口 + 上下文切换，先 round-robin | 共基座 | ✅ 已完成（G1） |
| M1a | Tickless idle（空→WFI）+ 单核省电验证 | 省电线 | ✅ 已完成（G1） |
| M1b | 多核负载均衡 + 对称 fair 类 | 性能线 | 待办（G2） |
| M2  | capacity 抽象 + 不对称感知放置（EAS） | 桥接两线 | 待办 |
| M3  | PM governor 服务（共享环 + 改频原语） | 省电线 | 待办 |
| M4  | EEVDF 风格 fair + 每任务 EPP hint | 性能线 | 待办 |
| M5  | RT class / deadline class | 实时 | 待办 |

M1a 与 M1b 可并行推进；M2 是把两条线汇合的关键节点。

> **M-milestone ↔ 阶段化(v) ↔ 关卡(G) 映射**：本节 M0–M5 是调度器内部的工程节奏；下方「阶段化目标」的 v1/v2/v3 是跨子系统统一基线（决策 #20），两者对照——**v1 ≈ M0 + M1a**（单核 + tickless idle，G0–G1）；**v2 ≈ M1b**（SMP + 负载均衡，G2–G3）；**v3 ≈ M2 + M3 + M4 + M5**（capacity/EAS + PM governor + EEVDF + RT/deadline，G3–G5）。**全可抢占**在 v3「逐步推向」，其正确性由关卡 **G3（多核+全抢占）** 把关（见 `测试策略.md`）。

### Phase 2a 实现纪要（M0 + M1a，2026-08 已落地，过关卡 G1）

§3.1/§3.2 的前瞻设计在 Phase 2a 落地为可跑代码。关键实现点（源码 `进程调度/src/{sched,class,runqueue,task}.rs` + `架构相关/aarch64/src/{lib,task,trap,timer}.rs`）：

- **上下文切换 = 纯叶子 asm**（ADR #30）：`switch(prev,next)` 无 prologue，只存 x19–x30+sp、载入、`mov sp`、`ret`。纯叶子保证「存的 SP == `load_frame` 所需 SP」，使 switch 能安全发生在 IRQ 中段——切回时经 `exception_irq` 回退到 `load_frame`→`eret` 回被中断 PC。
- **runqueue 持裸指针**：侵入式环形链表存 `NonNull<Task>`，runqueue **不拥有**可变 `Task`。`pick_next(&Runqueue)` 返回 `Option<&mut Task>` 由指针派生（`unsafe { &mut *p.as_ptr() }`），不经 `&Runqueue` 借用——故能在 `&Runqueue`（冻结签名）下旋转游标（`Cell` interior mutability）并返回可变引用（plan Bug 5）。
- **RoundRobin 先行**（G0/G1 默认 class）：`pick_next` 旋转游标、不摘除任务（runnable 常驻环）；`tick` 饱和递减 `slice_left`；`RR_QUANTUM=1`（每 tick 切一次，最公平、便于压测）。
- **IRQ 驱动抢占（无 yield）**：CNTV timer slice 到 → `exception_irq`（EOIR 之后）→ 经 fn 指针槽调 `on_irq_tick` → `RR.tick(current)` 减时间片 → 归 0 则 `pick_next`，若 `Some(next)!=current` 则 `switch`。两忙循环任务 `A`/`B` 在 slice 下交替，**全程无 `yield` 调用** = 里程碑「两个内核任务在定时器上分时」。
- **fn 指针槽倒置**（ADR #31）：HAL 持 `IRQ_DISPATCH: Option<fn>`，boot 时内核注册 `sched::on_irq_tick`。HAL 不依赖 bos-sched，编译期解环。
- **EOIR-before-dispatch**（ADR #32 / Bug 1）：`ack → timer::handle(rearm) → EOIR → dispatch`。switch 永不跑在「IRQ 已 ack 未 EOIR」窗口，避免 GIC 优先级泄漏致后续 IRQ 饿死。
- **switch 仅在 PSTATE.I=1**（ADR #33 / Bug 2）：协作 `yield_now`/`exit_current` 均 `disable_irq`→switch→`enable_irq`；IRQ 路径硬件入口已屏蔽。switch 无需自重入保护。
- **trait 校对**：§3.2 的 `trait SchedClass` 与实现 `进程调度/src/class.rs` 一字一致（冻结守约，签名未改）。

**实测**（G1 出口）：200s soak 稳定 1000+ 切换、A/B 近平衡、零崩溃；`just run-el2`（EL2→EL1 eret）同样通过。QEMU TCG 下 CNTV tick ≈ SLICE_HZ/2（见 `测试策略.md`）。FPU 陷 EL1（ADR #34）当前隐式依赖 CPACAR reset 值，显式 `FPEN=0b00` 待补。

## 阶段化目标（v1 基线，对照 `架构决策.md` #20）

- **v1**：单核；round-robin + 一个 fair 类桩；**抢占点可抢占**（非全抢占）；tickless idle（WFI）。**不**做 capacity/EAS/DVFS。（测试关卡 G0–G1）
- **v2**：开 SMP，per-CPU runqueue + 负载均衡；细化锁；lockdep。（G2–G3）
- **v3**：capacity 抽象 + EAS + PM governor 服务；逐步推向全可抢占。（G3–G5）

## AI 原生调度（详见 `AI调度设计.md`，决策 #21）

调度器的**策略层**被设计成 **AI 原生**：内核留第一类接口，让用户态 AI 策略服务经共享环**干涉** `class_fair` / 后台类的放置与优先级，并可下发 **per-cluster 频率 hint**（频率由 PM 服务裁决/执行，见下方「安全护栏」与 `AI调度设计.md` §10）。它是 `class_fair` 的策略源之一，与 PM governor 同级同模式。

- **慢/快循环切分（命门）**：快路径 `pick_next` 查「策略表」快照（μs、零分配、**绝不调 AI**）；AI 服务 10–100ms 慢循环重算表。
- **RT / deadline 类屏蔽**：AI 一律不得干涉，软实时确定性不容 ML 方差。
- **安全护栏**：防饥饿 / 热硬限 / 越界拒收，**内核强制**（AI 提议、内核处置）。
- **容错**：AI 服务崩 → 回退启发式（EAS + capacity），调度**不依赖 AI 在线**（同 PM 服务模式）。
- **平台分层**：手表不上 AI（单核已近最优，模型能耗净负）；手机轻量 advisor；PC 完整 advisor 跑专用管家核。
- **阶段**：v1/v2 埋遥测 + 注入留桩；v3 启发式分类 advisor（(B)路线，随 G4–G5 开发）；v4+ 设备端学习策略（(A)路线，G5 之后）。**AI 调度质量是 G5 之后的增强、不作关卡通过条件**；但 **AI 护栏不变量**（RT 屏蔽、越界拒收）须随调度器正确性一起验证（见 `测试策略.md` §8）。
