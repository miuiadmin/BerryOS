## §0 总评

五大战役没有一个是「写错了代码」的单点 bug——**每一个都是若干个各自正确、各自经过验收的设计，在某个新形态入场后交互出的系统性故障**；而且每一个都有多层掩蔽（asm 手排槽、ktest 静态出参、短命任务矩阵、恰好的栈布局、微秒级打印路径）把显形时间推迟了一到三个 Phase。排障产出也远不止修法：每役都沉淀了「判别式」（下次在写码/评审时一句话自检的口诀）与机器活证（遥测计数器、状态谓词断言、对照树零回归）。

## §1 五大战役全链

### 战役一：PI 错捐级联饿死（4-5a console 常驻服务）

- **症状**：`BLOCK ok`（第 14 标记）与 `G1.5 ok` 永不出现（sleeper 路径 2 的 waker 永远轮不到 CPU）；稳态矩阵 A/B/u/s/S/C/p/P 全员静默；**无 panic 无 dump**——不是崩溃，是调度死锁（watchdog 自己也是受害者，一起哑掉）。
- **根因链**（五个各自正确的设计交互）：
  1. [3-4a] 内核任务 `proc_tag=0` → `caller_table` 与 `pi::holder_table` 均派发共享 `BOOTSTRAP_HT`；
  2. [4-3b] PI 受捐判定 = handle 表反查 + 全图重推不动点 + **冻结随行**（唤醒离队不清 `pi_inherited`），ktest J7 把「共享表睡眠者算持有表内一切」固化为 v1 设计断言；
  3. [4-3a] pick 按 `prio_effective` 跨层严格优先；
  4. [4-1] waiter 稳态 = 纯自旋忙循环永不睡（原本无害，因它从未被捐过）；
  5. [4-5a 新增] console = 首个常驻内核服务：睡共享表 + `wait_one(endK:READABLE)` 直睡（自身构成 donor 边），endU(RIGHT_SEND) 以 insert_ref 洒进六用户表。
  交互：pi_client(32) 错捐 console（名义持有 endS，第一跳）→ console donor 边把 32 级联给睡路③的 waiter（表里有 endU，第二跳）→ 唤醒冻结 32 随行 → waiter 永不入睡 boost 永挂 → 严格优先独占 → prio-0 全员永久饥饿。
- **五层掩蔽**：①4-5a 前用户打印走 0xFF 调试槽，用户表无 channel 发端——级联第二跳边不存在；②共享表睡眠者此前全是短命任务，错捐后几个 slice 内 exit/回落；③错捐正主 pi_server 语义恰好正确（4-3b 验收靠它），ktest J7 还把该粒度固化成断言；④严格优先在全员 prio 0 时与轮转逐位等价；⑤waiter 永不睡自 4-1 起在，但从未被传播到。4-5a 一次补齐全部要素，五层同时失效。

- **铁律**：「常驻（不退出）+ proc_tag=0 共享表 + 稳态睡 channel 派生位」三者同场 = 级联错捐死锁配方，任占其二就该挂私有表或改 wait_many；不睡的任务冻结 boost 永挂，严格优先下它就是全系统的暂停键。落档 CLAUDE.md Gotchas「PI 共享表粒度级联饥饿」+「常驻内核服务必须挂私有 handle 表」两条 + main.rs「勿改回 wait_one」注记。

### 战役二：PI 错捐第二形态——断言司机饿死自己（4-6 B 半 ai_probe）

- **症状**：启动后 ~0.8s 串口停摆貌似「全系统冻结」——实为 KERNEL PANIC `assert!(saw, "…时序未达")`（初版 8 次重试预算）→ panic=halt 吃掉全部排队标记（PI ok/BLOCK ok/INTENT ok 全缺）。「冻结」是 halt 的连带面。
- **根因链**：pi_client(32) 灌满通道后睡 WRITABLE（donor 窗几百 ms～800ms+）→ endS 在共享表 → 全体 proc_tag=0 睡眠者被喷 `pi_inherited=32`；ai_probe（初版 plain spawn 挂共享表、1-slice 步进）每睡一次被喷一次、每醒一次冻结 32 随行抢片 → 把断言对象 ai_demo 的里程碑推到 ~830ms，而 probe 自身预算 8×1 slice ≈816ms 先尽——**差 14ms，probe 自己就是延迟源**（受害者=加害者）。
- **三重掩蔽**：①被错捐者此前都无自身时序预算（抬优先级只会更早跑，观测不到）；②4-5 规则按受害画像归纳成「常驻内核服务必须挂私有表」——probe 是短命 prio-0 步进重试的验收司机，不匹配字面、匹配机制（proc_tag=0 + 反复入睡），漏网；③8 次预算在无错捐世界绰绰有余——失败线与预算线只差 14ms 的「恰好被掩蔽」。
- **修法（三刀各治一面）**：①第三张私有表 `ht_pr`（表内仅 E_rel 一个 Event → 零受捐面，结构断根）；②预算 8→64、条件驱动（`AI_BOUND && 在队`，窗口由被等方 deadline 帽保持敞开——与 4-5a「不赌竞速」同一条纪律）；③`for_each_sleeper` 补 IRQ 屏蔽包络（顺手抓到的存量契约违约）。**为何不用战役一的 wait_many 刀**：probe 是纯 thread_sleep（`wait_obj=0`），本来就不是 donor——它的坑在受捐面不在捐赠面，私有表是唯一对症刀。这也是两形态的判别点。
- **铁律**：睡眠的验证者自己也是调度行为的参与者——它睡在哪张表、预算贴没贴正常时序，决定了「观测者即扰动源」；预算按「最坏轮转 + 我自己也在偷片」算，别贴正常时序定。「全系统冻结」先翻 panic 尾巴再疑调度器。

### 战役三：幻影出选结构性饿死（4-6 A 半，4-4 潜伏两步收口）

- **症状**：加入 talker/echo2 高频 ping-pong 后，echo1 出选:切入 = **29:1**（TaskContext 45 秒逐位冻结、出选计数照涨），client svcmgr 10s wait 超时自陷陪葬，稳态 'v' 断流。
- **根因链**：`pick_next` 是**出选原语**（选中即 `advance_past` 无条件消耗 head 槽位）× 4-4 `try_preempt` 写成「先 pick 再判 eff」——稳态矩阵全员同层（判定恒 false）→ 每条 fastpath send 白耗一格 head（幻影出选）→ 真实出选位（tick/yield/block）只认 head，而 head 被重复 IPC 节奏以 ~29 倍于 tick 的速率推进并相位锁定 → 固定节点集吃掉全部真实出选，集外节点结构性饿死。
- **五层掩蔽**：①4-4 自验 bench 用 prio 16/32（eff 判定真切走、真直切）——幻影只在同层矩阵显形；②4-5a 无意拆雷：console 稳态走 wait_many 哨兵 → 流量最大的打印链全走 slowpath，从不触发 try_preempt；③4-5b 圈时长 >> slice，幻影消耗 < tick 消耗，相位仍由 tick 主导；④ktest 在 `sched::init` 前跑（RUNQUEUE 未启用、CURRENT=null），游标副作用在测试面结构性缺席；⑤smoke switches 金丝雀只验总切换递增——锁相饿死不降总切换速率，金丝雀照绿。
- **修法**：`Runqueue::has_eff_above` **只读探峰前置**——探峰 false 根本不 pick。正确性闭环：探峰 true ⟹ 环上有严格更高者 ⟹ pick 必出该层且 ≠ cur ⟹ 必切走（结果必然被消费）；探峰 false ⟹ 必不满足直切条件 ⟹ 直接 return（零副作用）。否决案三则：改 pick_next 纯查询要动 SchedClass trait 冻结面；pick 后回滚游标是「允许错误发生再补救」；手写扫环违反「两路不长第二套」纪律。修法数量跟着漏洞路径数量走（对照战役一两条正交边、本役单点 API 误用单刀闭环）。
- **铁律**：把带副作用的消费型原语当查询用之前先问——**返回值不用时，副作用还在吗？** 在，就必须先加零副作用前置探测证明结果必然被消费；任何「pick 了又不用出选结果」的新调用点同罪（tick 路径 `next==cur` 自耗合法——cur 真被服务过）。

### 战役四：ABI 宽度违约——handle 出参 8 字节写砸穿邻接（G-eco-c）

- **症状**：run-rootfs 联调首跑，hello 以 sp0=0x1000（应 0x3000）入 EL0，第二条指令 `stp` 写 0xff0（映幅正下方未映射）自陷；上游全部「正常」（process_start 返 0、迁移自证 -EBADF 过、`ECO ok` 照打）——内核对 sp 错值零感知（0x1000 恰过 16 字节对齐校验）。
- **根因链**：ABI §8 冻结 handle=u32 × 内核「指针宽度即写宽」惯例（`copy_out_u64` 通吃一切出参，handle 值恒 < 2^32 数值永远正确——数值正确性掩盖宽度违约）× copy_out 界检只查 N 字节落合法用户区、不查接收方声明宽度 × rustc 紧排局部（4 字节 Handle 槽排进两个 8 字节局部的空隙）× 小端高 4 字节恒 0（表现为静默清零非写垃圾）。实测：spawn_elf 里 `thread_create` 出参槽 `[sp+0x25c]` 的 8 字节写砸穿正上方 `[sp+0x260]` 的 saddr 低半 → 0x2000→0 → sp=0x1000。
- **三层掩蔽**：①asm 模板时代出参槽手排 8 字节间距绝对地址（「槽距」这个不存在于 ABI 的隐含契约兜了整个时代）；②ktest 出参指向 `static mut OUT: u64` 再 `as u32` 截读（静态槽无「邻接局部」概念，结构上永远测不出）；③G-eco-b 的 spawn_child 同款违约已在线（ht 槽恰好落帧顶、越界 4 字节落父帧底部无害）——**「编译时代第一天即炸」实为「编译时代第一个致命栈布局」**。
- **修法**：新 `copy_out_u32` + **系统性扫荡**（18 处 handle 出参全改 4 字节，不逐点修——逐点修给下一个紧排布局留暗雷）+ **防矫枉回查**（f174855：扫荡曾把 vmo_get_size 的 size_out 预清误改窄——size 是 u64 出参，改回；一刀切 4 与一刀切 8 是同一反模式的镜像）+ 不在调用方修（要求用户 8 对齐槽 = 把违约合法化）。判定基准单点化：**宽度唯一判据是 ABI 冻结的类型**（handle→4、usize/u64→8），拒绝按调用方形态或「当前能不能跑」适配。
- **铁律**：跨 ABI 边界每个字节的宽度，是查 ABI 类型表定的，还是抄了旁边能跑的调用点？换一个编译器重排过局部的调用方，它还成立吗？**编译 Rust 用户程序 = ABI 宽度类 bug 的检测器**（asm 时代的宽度违约在编译时代第一天显形）。

### 战役五：时序契约双案（G-eco-b send_spin + 4-5a MANY ok）

- **案 A（重试形态是契约的一部分）**：svcmgr Rust 化时按家族印象把 console 发送统一成阻塞——启动期 console 深度 8 队列饱和窗内，被唤醒的阻塞者须等一整圈 RR 轮转（~16 任务 × ~200ms TCG slice ≈3.2s）才拿到片，abuser/spawner 等自旋友商（CPU 在手即 refill）先抢走每个腾出的槽，三场竞速 ≈9.6s 耗尽 10s 帽 → -ETIMEDOUT 自陷（SVC ok 缺失 + echo1 连带饿死）。asm 原文逐点核对：**同一家族三种形态并存**——svcmgr 本体 console 发送 `b 6b` 纯自旋、talker console 发送 clock+wait 阻塞、svcmgr 通道发送阻塞。修法 = 拆 `send_spin`/`send_retry` 逐点保形。掩蔽第四层值得单独记：**前存 bug 清单的反向诱导**——草案把「abuser/spawner 自旋烧 CPU」记为待修项，提炼契约时按家族印象把 svcmgr 正确的自旋也「修正」掉了。
- **案 B（smoke 标记不得建立在竞速上）**：`MANY ok` 原挂在 ponger「首次撞 -EAGAIN」——前提是 ponger 排水 > pinger 补灌（两个独立任务的相对速率）。4-2b 时 0xFF putchar 微秒级无意保证该不等式；4-5a 打印改 console 往返（秒级、进全局调度）后速率反号，实测 120s 队列恒非空、一次 -EAGAIN 都不来的 run 真实出现过——smoke 变抛硬币。修法 = 标记改**入口**先发一次 wait_many（队空睡到首发唤醒 / 非空 poll 即中，两路必然 ret==0/idx==0），稳态路径原样保留继续被锻炼（删稳态验收才是降级）。
- **两案共用哲学**：验收/契约要的是**必然性**，不是大概率——给标记定条件先问「这是状态谓词还是竞速结果？」；迁移/重写并发路径时，重试形态、等待帽、错误容忍集是**逐调用点**的行为契约，绝不按家族归纳。

- **位**：`user.rs` pinger（wait WRITABLE 10s 帽超时自陷）/ ponger（wait_many READABLE 10s 帽自陷）。
- **机制**：互为唯一供应方 + 各挂 10s 绝对帽，**超时无法区分「对端死」与「我被饿满 10s」**（G-eco-b 已实证饱和窗能把阻塞者饿过 10s 帽）——同一超时码两种根因。a27eb9c 修完 waiter 后 pinger 仍死，未结案；上游 d4dcf6a（runqueue 两元环摘除误判——幸存者静默失联）可能顺带相关。
- **修法方向**：超时自陷前先 poll 对端通道 state（READABLE=对端死 / WRITABLE=自己被饿）打区分性 console 行；或退避重试替代一刀自陷。

### 雷 3｜ktest fastpath 无机器护栏【中】
- **位**：`sched.rs` try_preempt（取 CURRENT 后裸解引用）+ fast_wake（无调度器就绪检查）+ ktest 侧纪律仅注释、只有事后清场断言。
- **机制**：「ktest 在 sched::init 前跑，手搭睡眠者在队时绝不可走 SVC send」只是文档铁律——违约者得到的是 boot 期难归因挂死/野指针 abort，而非清晰报错。多会话/AI 写新用例是本项目常态。
- **修法**：短期 try_preempt 开头 `if CURRENT.is_null() { return false; }` 或 fastpath 入口 debug_assert；长期 ktest 框架 `with_sleepers(svc)` 包装统一执法。

### 雷 4｜process_create 无创建权上限【中】
- **位**：`syscall.rs` sys_process_create（job==0 无条件放行）+ `process.rs`（v1 无退出路径）。
- **机制**：每次 create 永久泄漏 root Vmar 帧 + Process/Vmar Box（ASID 可回收、帧/Box 纯泄漏），无数量上限（对照 vmo_create 的 16MiB no-panic 帽）——单 EL0 循环 create → 全系统 -ENOMEM 停摆。当前矩阵无滥用者故未爆。
- **修法**：v2 Job 收口前先加一行每调用方活进程计数帽（超即 -ENOMEM），把无界封为有界。

### 雷 5｜channel v1 双泄漏【中，已挂账 v3】
- **位**：`channel.rs` Drop 仅 release peer 互钉 + Message.handles 令牌数组无 Drop。
- **机制**：未收割令牌随端点销毁永久泄漏；互钉成环两端全关不释放。模块头注明示「v1 接受、v3 DEAD 检测收口」——安全向（泄漏不炸）但量随「发而不收」无界增长。v1 内服务「崩前 drain」纪律兜底。

### 雷 6｜RIGHT_DUPLICATE 不执法【低，v2 收口】
- **位**：`handle.rs` 头注声明不门控 + duplicate() 仅查 new_rights 非零且 ⊆ orig。
- **机制**：任何持有者可无限增殖别名 → 「销毁性 close」永不可达（对象寿命被单方无限延长）。当前无害（dup 只紧不松）；**v2 吊销/回收语义落地前必须先关**，否则吊销可被预增殖别名架空。执法当天注意：svcmgr 的 console dup 点权利集不含 DUPLICATE，会 -EACCES，需 boot 授权利集补位。

### 雷 7｜用户位空间无登记表【低，冲突已在发生】
- **位**：散布四处——user.rs 魔数（U3=1<<35、U2=1<<37）、main.rs（SLEEP_OBJ 1<<33、AI 1<<34/1<<36 注释口头声明）、ktest 局部位；**a27eb9c 已占 1<<38 而 HEAD 无从得知**。
- **机制**：唯一「登记」是散文注释；多会话并行下凭过时注释挑位 → 同位双用途互相清位/误唤醒（雷 1 的同型成因），显形即 missed wakeup 级排障成本。
- **修法**：内核侧集中登记表 `[(bit, 归属, 对象)]`，合并 a27eb9c 时把 1<<38 一并登记（与行动 1 捆绑）。

### 雷 8｜eco: 降级契约不对称【低】
- **位**：svcmgr `eco_skip` 盖解析侧（get_size/read/cpio/elf-parse 失败打一行原因）vs `spawn_elf` 装载侧一律 trap()。
- **机制**：三层帽中空窗——fw_cfg/VMO 16MiB → ROOTFS_MAX 16KiB（越帽可见降级，契约达成）→ ELF 段幅无独立帽（berry-loader 只挡 >2^39），(16MiB, 2^39) 区间放行 → vmo_create -ENOMEM → trap。失败形态恶劣：SVC ok/DEMO ok 已打、svcmgr 中途死、稳态 'v' 停 + watchdog 错杀 panic halt，一行 eco: 都没有。
- **修法**：spawn_elf 内环带原因返回（vmo_create 失败 → `eco_skip("vmo cap")`）+ 段幅 16MiB 前置检查——纯用户态改动。

## §4 横切模式六条（判别式手册）

1. **消费型原语当查询用**——副作用在返回值不用的分支里照样发生。
   判别式：*这个调用的返回值我不用时，它的副作用还在吗？* 在 → 必须先加零副作用前置探测（`has_eff_above` 式只读探峰）证明结果必然被消费，不许「先做了再决定」。〔战役三 try_preempt；战役四 copy_out 写宽度的副作用从未按 ABI 类型表核对；雷 3 同一 try_preempt 在 ktest 语境裸解引用〕
2. **规则按受害画像归纳而非按机制归纳**——画像换了，机制还在。
   判别式：*我写下的条件锁的是机制（proc_tag=0 + 会反复入睡）还是受害画像（「常驻」「console 类」）？换一个受害者画像还拦得住吗？*〔战役一 ktest J7 固化「短命任务无害」前提；战役二 4-5 规则字面「常驻服务」漏掉短命 probe；战役五案 A 家族印象把正确自旋「修正」掉〕
3. **凑巧能跑不是正确性**——隐含契约靠环境参数兜底，环境一变即塌。
   判别式：*这条不变量靠什么成立——ABI 类型表，还是某个恰好没变的环境参数（编译器栈布局/打印路径速率/调度时序）？换掉它还成立吗？*〔战役四 asm 手排槽+ktest 截读双兜底；战役五案 B 0xFF 微秒级速率无意保证排水>补灌；雷 1 注释拿调度时序当契约〕
4. **观测者即扰动源 + 检测器对 bug 类的结构性盲区**。
   判别式：*我的验证任务睡在哪张表、预算贴没贴正常时序？我的金丝雀对这个 bug 类敏感吗——总速率不变时，相位类 bug 看得见吗？*〔战役二 probe 自己就是延迟源；战役三 ktest 在 sched::init 前跑 + switches 金丝雀对锁相饿死不敏感；战役四 ktest 静态槽测不出宽度违约〕
5. **共享空间凭空加边**——往全局表/位空间/全局权限放东西时，图的边数失控。
   判别式：*我往共享空间放新东西时，图的边多了几条——谁会把它视作自己的持有面、会不会撞别人的位？有没有机器可查的登记处？*〔战役一 endU 洒六表 = 捐赠图凭空两条边；雷 7 位冲突已在发生；雷 4 job==0 无限放行〕
6. **状态谓词 vs 竞速结果**——验收条件必须对任意速率组合必然成立。
   判别式：*给标记/断言/帽定条件先问：这是状态谓词，还是两个独立活动体相对速率的竞速结果？换任何速率组合它都必然成立吗？超时分支能区分「对端死」和「我被饿」吗？*〔战役五案 B；战役二修法正面示范（AI_BOUND 状态谓词驱动重试）；雷 2 同一超时码两种根因；雷 1 两种死相〕

## §5 排障方法论七条

1. **「全系统冻结/标记批量缺失」先翻 panic 尾巴再疑调度器**——单点 halt 的连带面最会伪装成调度器 bug（战役二「冻结」实为 panic halt）。
2. **给每个修法配机器活证**——遥测计数器量出 29:1、IRQ 屏蔽窗内 for_each_sleeper 断言字段、AI_BOUND 状态谓词；人工对时间线的结论一律降级为假设，直到有机器断言背书。
3. **换检测器主动暴露「凑巧能跑」**——编译 Rust 用户程序是 ABI 宽度类 bug 的检测器；同理换打印路径、换宿主速率、换栈布局去试探隐含契约。
4. **SVC 寄存器对位法 + 专用 bench**——按寄存器映射（x0=号、x1..x6=参、只回写 x0）从 dump 反推卡在哪个 syscall 的哪个参数，dump 按时间线排序定位连锁死因；量时序用专用点对点 bench（高 prio 独占 CPU），别拿稳态矩阵当基线（console 排队是噪声源）。
5. **失败线与预算线只差十几毫秒 → 先假设观测条件没凑齐**——预算按「最坏轮转 + 自己也在偷片」算，别贴正常时序定（战役二 14ms 之差）。
6. **修法双管正交 + 教训按机制条件回写 Gotchas**——回写本身的计数与行号也要可机核（「18 处」实为 20 的固有瑕疵说明回写自己也会漂移）。
7. **警惕规则与清单的反向诱导**——前存 bug 清单的待修项会在提炼契约时把正确实现一并「修正」掉；换轨/重写前逐调用点核对原实现每个错误分支的去向，**家族归纳只用于提名、不用于定契约**。
