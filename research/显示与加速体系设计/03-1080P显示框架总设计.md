## 0. 一页结论

1. **1080P 定调落案:desktop 档 = 1920×1080 横屏**。owner 已于 2026-11-13 裁定并改入工作树(`tools/berry/src/profile.rs:30-40`,render = panel 零 letterbox;双击/无参入口同批定 desktop + auto accel,`tools/berry/src/main.rs:596-600`)——本件确认定案不再摇摆,并给出体系依据(§1.1)。任务书所引「1080×1920(竖,现 profile)」是 2026-11-06 提交 `4063e879` 至 11-13 翻案之间的旧态,竖屏需求由 phone16 档(1080×1920,`profile.rs:50-58`)承接。
2. **窗口初始 = 1080P 逻辑尺寸 1:1 不缩,重裁波一 A 刀**:`base_window_factor` 的 0.9/0.55 因子与 `default_window_size` 的 0.9 屏幕钳制全部退役(§1.2)。理由:0.9 因子是「窗口太小」痛点最小修的历史遗产,其病根(物理像素口径)已除;「1080P 初始」的用户语义 = 打开即 1:1;小屏超屏 = 可拖 + 等比缩放仍可用(01 号审计 §3c 已证模型)。
3. **横屏定调的第一下游断点在 launcher**:布局 big 分支判据 `vp_w>=600 && vp_h>=1800`(`desktop.rs:311`)是竖屏 1080×1920 专属像素阈,横屏 1920×1080 不满足 → 1080P 桌面上跑紧凑调试档布局(44px 状态栏/S16x32 字号/56px 图标)——违背「初始不妥协」,必须同刀修(§1.3、§3)。
4. **分辨率体系 = profile 档位表增 2K/4K 横屏档 + product.toml 立 `[platform.display]` 键**(§2)。4K 档词表先立、值域锁死待 02 号 virtio-gpu 后端解锁(软光栅 4K 带宽推断不可用)。OEM 定制分辨率 = 设备形态参数,归 platform 合同面——这是产品配置层 §7.3-⑥ 开放项(「host profile 与设备清单的字段合流」)的收口提案。
5. **DPI/vp 框架 = density 单源随显示链下发 + vp 换算单点 + 布局断点 vp 化**(§3)。现状三病灶:density=3 硬编码、断点像素硬阈、vp→px 手乘散布。density 是 Profile 每档字段、作用于 render 几何(布局只见客机 fb):desktop 族 v1=3(单套复用 OH 3x 资产族),phone 族=1(紧凑布局即其 sm 形态,现状延续);断点采 OH 官方 320/600/840vp——横屏 1080P = 640×360vp = md 档。竖屏 OH phone 全分辨率形态(360×640vp)资产在库而档位表暂无载体,列开放项(§3.4)。
6. **动态分辨率两相位分治**(§4):初始态(本文,product/profile 单源 → boot 静态链)与运行态(02 号 virtio-gpu scanout 域)。框架不变量重申:宿主拖窗 = 纯宿主 scale,永不改客机分辨率(01 号 §3c Android 模拟器/QEMU GTK 双先例定谳)。
7. **全链单源图与刀序**(§5):显示几何数值只在家一处(内置档表/product.toml),fw_cfg 串、info VMO、GETINFO、窗口初始值、布局换算全链派生零手抄;五刀序,刀 1(窗口 1:1)与刀 2(launcher 断点)是本波必做。

## 1. 1080P 定调

### 1.1 desktop 档 = 横屏 1920×1080:定案确认

**事实态**(两源:代码 + git):工作树 `profile.rs:30-40` desktop 档 panel_w=1920/panel_h=1080/render 1920×1080/refresh 60/memory 256MiB,注释「横屏 1080P:终端产品主形态(owner 裁定 2026-11-13——初始体验即 1080P 不做低清妥协);render = panel = 1920x1080 零 letterbox」;git 史四折:2026-11-06 `e3dabfd4` 16:9 1280×720 → 同日 `d1f11730` 1920×1080 → 同日 `4063e879` 翻竖屏 1080×1920 → 2026-11-13 工作树翻回横屏(未提交)。双击/无参入口注释「2026-11-13 owner 裁定:双击/无参入口 = 横屏 1080P + 硬件加速,统一启动形态」(`tools/berry/src/main.rs:596-598`,同批工作树件)。

**体系依据**(定案的四条,不再摇摆):

- 形态语义:desktop = 桌面形态,开发者宿主是横屏显示器;16:9 窗口与宿主工作区契合,竖屏 1080×1920 在横屏显示器上浪费纵向空间。竖屏 1080×1920 形态由 phone16 档(`profile.rs:50-58`,panel 1080×1920/render 480×854)承接,档位表内两形态并存、不共用一档。
- 零 letterbox:render = panel = 1920×1080,客机像素与窗口逻辑尺寸 1:1,无缩放损耗(旧 desktop 档 540×960 面板承载 1080×1920 渲染,宿主缩放约 0.28 倍起)。phone 族 panel>render 是「低渲染分辨率 + 宿主放大」的性能取舍,desktop 主形态不做此妥协——正合「初始即最好」铁律。
- 性能位:1920×1080×4B ≈ 7.9MiB/帧,ramfb 路径(HVF)下宿主收帧即显示,软光栅满帧带宽 7.9MiB×60 ≈ 0.45GB/s 可承受;性能主矛盾在 berry-gfx CPU 光栅与帧搬运(系列总背景),1080P 档是 GPU 加速(virtio-gpu,02 号)的第一验证档。
- 初始入口统一:双击/无参 = desktop + auto accel(macOS ARM 上 auto = HVF,`qemu.rs:57-68`)——「1080P 初始」由入口、档位、窗口三层共同兑现,单靠 profile 一层不成体系(§1.2/§1.3 补另两层)。

**遗留同步件**(实施刀附带,非本件改):README 档位表仍是旧态(desktop 540×960/1080×1920,`tools/berry/README.md:119`);`profile.rs` 与双击入口改动同批已在工作树,README 是唯一未同步件。

### 1.2 窗口初始 = 1080P 逻辑尺寸 1:1:重裁波一 A 刀

**波一 A 刀现状**(git `01028a10` 2026-11-13 已提交):`base_window_factor`(Fit 档 panel_h>1200 → 0.55,否则 0.9;`window.rs:202-213`)+ `default_window_size`(与 0.9×屏幕逻辑宽高取 min,factor 下限 0.2,尺寸下限 320×240 逻辑点;`window.rs:224-243`)。desktop 档(panel_h=1080)实际初始 = 1920×1080 × min(0.9, 钳制)——16″ MBP(1728×1117 逻辑点)上 = min(0.9, 0.81) → 约 1555×875 逻辑点。

**重裁定案**:Fit 档初始因子 = 1.0(panel 逻辑尺寸原值),0.9 基准因子、0.55 竖屏因子、0.9 屏幕钳制、factor 下限 0.2 全部退役;尺寸下限 320×240 保留(防零窗);`ScaleMode::Integer(n)` 语义保留(n=1 即 1:1,n=2 放大一档,显式整数缩放对像素字体的清晰度仍有价值,README `--scale` 面不动)。规则单源无特判:phone 档(1080×2250)同样 1:1 初始——竖屏窗口在任何横屏宿主必超屏,超屏即超屏。

**理由四条**:

- 语义正交:「1080P 是初始的」= 打开就是 1080P,任何折扣因子都与定调字面冲突。0.9 因子诞生于 audit 01 §3a「窗口太小」最小修(当时病灶是物理像素口径把窗口压半);口径 bug 已修(逻辑点),因子的历史使命结束,继续保留是对旧病灶的惯性补丁——违「不打补丁」铁律。
- 可用性不损:超屏窗口在 macOS 上合法(winit 允许窗口大于屏幕),可拖回、可 F 全屏;拖动即等比缩放 + 输入坐标反算自动适配(01 号 §3c 已证,`scale.rs::fit` 每帧重算 letterbox)——「可用」由交互模型保,不靠初始尺寸迁就。
- 开发者语义:模拟器给开发者用,1:1 初始 = 所见即客机像素——调字体、量布局、抓截图(qemu 侧帧即客机帧)不撒谎;0.81 倍缩放起手反而制造「字体糊」误判(audit 01 痛点⑥教训)。
- 竖屏规则统一:若 phone 档保留钳制而 desktop 不保留,窗口层出现两套规则;统一 1:1 后窗口层逻辑 = 「初始 = 档位 panel 逻辑尺寸」,一条规则全部档位。

**落点与验收**(实施刀):`window.rs` `base_window_factor`/`default_window_size` 重构(Fit → 1.0;`default_size_tests` 期望值全量翻新——`hidpi_desktop_window_is_logical_not_physical`(:1008-1019)等五测的钳制断言改 1:1 断言);验收 = `just desktop` 开窗 1920×1080 逻辑点(物理 = ×scale_factor),MBP 上超屏属预期;`berry shot` 冒烟不回归(shot 路径不经窗口代码)。

### 1.3 第一下游断点:launcher 布局档(必须同刀)

横屏 1080P 定调后,launcher 的布局分支立即错位:`desktop.rs:311` `let big = vp_w >= 600 && vp_h >= 1800` 是竖屏 1080×1920 专属判据(1920×1080 时 vp_h=1080 < 1800)→ big=false → 紧凑分支:status_h=44px(:315)、字号 S16x32(:316-317)、图标 56px(:319)、grid_h 铺满算式(:548-551)。即 1080P 桌面上跑的是 800×600 调试档布局——「初始体验即 1080P」在客机侧不成立。

这不是改一行阈值的事:big/紧凑二分本身是竖屏专属的档位体系,横屏 1080P(视口宽 640vp)、phone 族(480/540vp)、tablet(800vp)没有共同的像素阈可写。正解是断点体系 vp 化(§3.2,判断面 = vp 视口宽),v0 止血 = big 判据先改按 vp 宽(≥600vp 过 md 线,横屏 1080P = 640vp 过线)——框架修法见 §3,本节只钉死「必须与刀 1 同波,否则 1080P 定调只在窗口层兑现一半」。

## 2. 分辨率体系:档位表 + product.toml

### 2.1 profile 档位表定稿(提案)

现役六档(`profile.rs:20-77`,README :118-123 两源,README desktop 行为旧态):default 800×600(P1 兼容/console)、desktop 1920×1080(横,默认)、phone 1080×2250 render 480×1000、phone16 1080×1920 render 480×854、phone20 1080×2400 render 540×1200、tablet 1600×2560 render 800×1280。

**增补两档**(横屏大屏,提案):

| 档 | panel = render | refresh | memory_mib | density | 解锁条件 |
|---|---|---|---|---|---|
| desktop(默认) | 1920×1080 | 60 | 256 | 3 | 现役(本波) |
| desktop2k | 2560×1440 | 60 | 256 | 3 | 随刀 3 入表(HVF 路可跑,推断) |
| desktop4k | 3840×2160 | 60 | 512 | 3 | 词表立、值域锁——02 号 virtio-gpu 2D 后端解锁(软光栅 33MiB/帧×60 ≈ 2GB/s 带宽,TCG/软链推断不可用;同推断依据:01 号 §0 慢根因假设 = 渲染链非 CPU 虚拟化) |

phone 族维持现值,补 density=1(480×1000 @1 = 480×1000vp,sm 档——紧凑布局即其形态,现状延续;§3.2);tablet 同族 density=1(800×1280vp,md 档)。density 作用于 render 几何而非 panel——布局只见客机 fb,panel 仅是宿主窗口基准(§1.2),两者语义分立是本表结构定调。

几何可行性账(两源:ramfb 界 + buddy 路径):fb 字节 = w×h×4 → 1080P 7.9MiB / 2K 14.1MiB / 4K 31.6MiB;内核 defer 路径从 buddy 取 2^n 连续页(`kernel/src/main.rs:339-380`,01 号审计 §1.2 实测 desktop 档走 `DISP defer`)→ 16/16/32MiB 全可满足(2^24/2^24/2^25);ramfb 设备尺寸界 [16,16000]×[16,12000](01 号审计外部源,QEMU bochs-vbe.h);宿主 RamSource caps 上限 4096×4096(`tools/berry/src/display/ram.rs:124-134`)——4K 档 3840×2160 界内,自定义档超 4096 时走 VNC 通路(caps 是能力声明非变更通道,01 号 §2.1)。内存档:2K 沿用 256(fb 16MiB + 双 slot 合成缓冲 + 系统,推断余量足);4K 抬 512(fb 32MiB + HDI 双 slot + 系统,推断)。

**结构定调**:Profile 增 `density: u32` 字段(§3.2 的单源起点,现 OH_DENSITY=3 硬编码的档位化);档位表 = 显示形态的唯一官方清单——product.toml 引用它而非另立一套值(§2.2)。

### 2.2 product.toml `[platform.display]`(OEM 定制分辨率)

**判据**(采产品配置层 §1.1 双键分界判据「该键翻值会不会改变平台侧承诺行为」,`docs/产品配置层与槽位合同设计-v1.1.md:37-38`):分辨率/density 翻值改变平台侧行为——性能红线(「1080P 能用」的开发者红线)、launcher 布局适用域(§1.3)、fb 内存几何与 buddy 取页——故归 **platform 合同面**,对齐 `platform.feature_level`(形态档)先例(:35),不走 product 自由面。

**键表提案 v1**(两键,枚举 + 覆盖子表;正式收编随 #83 升版,本文按 [product.source]/boot-params 轻追记先例给「提案 + 工具先行」定位):

```toml
[platform.display]
profile = "desktop-1080p"     # 枚举引用官方档(词表 = profile.rs 档位 id 同源,
                              #   add-only;desktop-1080p 为 v1 唯一在册值)
[platform.display.override]   # 可选覆盖(缺省 = 官方档原值,零覆盖零扰动)
# panel_w = 1920             # u32 ∈ [16,16000](ramfb 设备界)
# panel_h = 1080             # u32 ∈ [16,12000]
# render_w = 1920            # ≤ panel_w(横屏档 render=panel;phone 族例外)
# render_h = 1080
# refresh = 60               # u32 ∈ [30,120]
# density  = 3               # 枚举 {1,2,3,4}(§3.2)
```

设计取舍:**枚举保底 + 覆盖自担**——OEM 不写 override = 引用一个全链验证过的官方档(性能/布局/内存都有承诺);写 override = OEM 自担域,组装期 lint 执法(值域校验 + fb×4B ≤ memory 一半 + render ≤ panel)。这与 `platform.boot.params` 的覆盖三档(:186-189)同构:形态键是结构参数不走 free/restricted/locked 逐键分档,枚举引用本身就是「官方承诺档」的机器表达。

**投放链(单源派生,不双写)**:

- 设备侧:berry-assemble 步⑥ 产 `etc/display.toml` 进 rootfs(`etc/locale.toml`/`etc/boot-params.toml` 先例同款「投放面最小」,产品配置层 :205/:228)。**第一读者 = 内核 boot 回退源**——fw_cfg `opt/berry/display` 缺席时(真机路线/自定义 QEMU 启动)内核读镜像内产品定义,与 fw_cfg 同值单源(sidecar 与 fw_cfg 由同一档位解析生成)。这给键组真实消费面,防僵尸键(i18n 键组「有真实读者」纪律,:179)。消费面实施挂内核显示刀,与 bootparams.rs 消费同形(newc 定址查找原语已在册,`kernel/src/bootparams.rs`,产品配置层 :228)。
- 宿主侧:组装产 sidecar `out/<name>.display.toml`(镜像伴生元数据),berry 启动时按 `--image` 找伴生件对齐 profile——**这是产品配置层 §7.3-⑥ 开放项(「portrait/分辨率影子字段是否 v2 设备清单补 display 键后让 host profile 退化为纯『怎么看』」,:625)的收口提案**:设备清单立 display 键(本文),宿主 profile 解析序改为「命令行 `--profile` > 镜像 sidecar > 内置默认」,无 sidecar = 现行为零漂移(兼容式改造纪律,:454)。berry 不解析镜像文件系统——sidecar 是现役「按 --image 文件名约定联动」(:465)的机器化。

**与 host profile 的分轨维持**:产品配置层 §4.4 分轨边界(设备侧清单管镜像产物、宿主 profile 管显示参数,两轨不共享 schema)在 v1 维持——本提案不动 schema 合流,只建「sidecar 对齐」这一条单源派生通道;两轨合流(宿主 profile 退化为纯窗口/怎么看参数)是 02 号动态分辨率落地后的事(运行态归 scanout,初始态归 product,届时宿主侧不再需要持有几何)。

### 2.3 档位值域执法(组装期 lint 清单)

未知键/未知枚举硬拒(七拒家族,产品配置层 :139);override 值域:四几何 ∈ ramfb 设备界、refresh ∈ [30,120]、density ∈ {1,2,3,4};一致性:render ≤ panel、fb = render_w×render_h×4 ≤ memory_mib×1MiB/2、panel 纵横比与 render 纵横比偏差 ≤ 25%(防 OEM 配出变形档,阈值推断待首例校准);desktop4k 档 v1 只词表在册、值域锁(组装器对 4K 档的 override 出现即拒,理由行 = 「待 virtio-gpu 后端解锁」——`min_power_atomicity`「词表先立值域收窄」同款先例,:120)。

## 3. DPI/vp 框架:density 单源 + vp 单点换算 + 断点 vp 化

### 3.1 现状三病灶(全部直核)

- **density 硬编码**:`OH_DENSITY: u32 = 3`(`desktop.rs:98`),注释「密度(1080 物理宽 / 360vp 逻辑宽)」——1080 宽竖屏的隐式假设;换横屏/2K/4K/OEM 自定义档,整套 OH 常量族换算失锚。
- **断点像素硬阈 + 命名误导**:`big = vp_w >= 600 && vp_h >= 1800`(`desktop.rs:311`),两值都是 px(viewport 返回 disp_w/disp_h 像素,`berry-ui/src/lib.rs:537-550`;变量名 `vp_w/vp_h` 实为 px,命名即病灶证据);600/1800 是竖屏 1080×1920 专属阈,横屏/大屏/自定义档无共同阈值可写。
- **vp→px 手乘散布**:OH_STATUS_H×3(:315)、OH_STATUS_PAD×3(:391)、NAV_KEY_PX_BIG = 44×3(:144)、OH_ITEM_H×3(:552)……desktop.rs 全文手乘十数处,无单源换算函数;字号档 S8x16/S16x32/S32x48(`berry-gfx/src/font.rs:140-148`)固定像素档,与 density 无联动表。

**在册基座**(本框架不是新发明,是把两条既有立法接通):应用规范 :138「基准画布:360×640vp @3x = 1080×1920(OH phone 档);一切几何经 GETINFO 协商,禁硬编分辨率(裁决 D)」+ :147「触控目标 ≥44×44 px,视觉可小、命中区不缩」——vp 体系已立法,但只立了竖屏基准,且 desktop.rs :29-31 把「字号档/图标 px 等字体面常量」豁免在裁决 D 之外——豁免面正是病灶聚集处。

### 3.2 框架设计(三层)

**层一:density 单源**。density(px-per-vp)是显示形态定义的一部分,随显示链下发,禁止消费端推导;**作用于 render 几何**(布局只见客机 fb,panel 是宿主窗口基准——两者语义分立,§2.1)。链路(终态):

```
profile/product 定义 density → berry QEMU 行 fw_cfg display 串扩段
  (opt/berry/display: "1920x1080@60@3" 或平行具名键 opt/berry/display-density,
   具名 string 先例族 = display/accel/rtc 三键,qemu.rs:243-267)
→ 内核 display_mode_req 解析(main.rs:211-228 扩)
→ boot info VMO 增 density 域(现 48B 六域:fb_pa/w/h/stride/fmt/gui,
   guifbd/src/main.rs:826-843;追加第 7 域 u64 LE,旧读者按「读 0 = 兼容」
   先例 :838-839 第 6 域 gui 的旧内核兼容法)
→ guifbd → wmd GETINFO → launcher ui.viewport() + density
```

v0/v1 分刀(如实记):v0 过渡 = launcher 档表推(按 GETINFO 几何查档表:{1920 宽 → 3,480 宽 → 1,800×600 → 紧凑兜底}),标注过渡、只服务横屏 1080P 止血(刀 2);v1 正解 = info VMO 域,与 02 号动态分辨率合刀——几何热变时 density 必须随事件流下发,静态推导在 scanout 时代结构性失效,这是 v1 刀不可省的根据。

**层二:vp 换算单点**。berry-ui 暴露 `vp(v: u32, density: u32) -> u32`(乘法;px→vp 用除法取整,仅供断点判断);desktop.rs 全部 OH_* vp 常量族经 `vp()` 换算,手乘清零;44px 触控下限保持 px 口径不随 density 缩(应用规范 :147 立法是 px 下限,「命中区不缩」语义保住)。

**层三:断点 vp 化(采 OH 官方断点)**。断点表 = xs [0,320) / sm [320,600) / md [600,840) / lg [840,+∞),默认断点 320/600/840vp(`research/GUI-11-设计系统硬数值token表-v1.0.md:234-243`,源 = OH 官方 GridRow 文档,Gitee URL 见来源索引)。判断面 = render 几何 ÷ density 的 **vp 视口宽**(横竖两向形态的横向边,与 OH「按宽度定档」同构——横屏 desktop 宽 640vp 落 md,竖屏 phone 宽 480vp 落 sm)。档位落点:

| 档 | render @density | vp 域 | 断点 | 布局形态 |
|---|---|---|---|---|
| desktop | 1920×1080 @3 | 640×360vp | **md** | OH 常量族 @3x(现 big 分支资产) |
| desktop2k | 2560×1440 @3 | 853×480vp | lg | md 形态拉伸容(列数升 12) |
| desktop4k | 3840×2160 @3 | 1280×720vp | lg | 同上 |
| phone | 480×1000 @1 | 480×1000vp | sm | 紧凑布局(现状延续 = sm 形态) |
| phone16/20 | 480×854/540×1200 @1 | 同族 | sm | 同上 |
| tablet | 800×1280 @1 | 800×1280vp | md | 紧凑布局拉伸容 |
| default | 800×600 @— | — | —(console 兜底,不进断点体系) | 紧凑分支保留(P1 兼容) |

phone 族 density=1 的定调依据:render 480×1000 若按 @3 折算是 160×333vp(xs)——低渲染分辨率档的本意是「性能缩放,宿主放大」,不是「缩小的桌面」;@1 下 480×1000vp 落 sm 档,44px 紧凑状态栏恰 = 44vp@1(应用规范 :139 的 44vp 立法数值),现状紧凑分支即 sm 形态的现役形态,零迁移成本。desktop 族 density=3 的依据:OH 3x 资产族单套复用(desktop.rs icons/dock 全 @3x 源)、字号档一致(S32x48 主档)、640/853/1280vp 渐进自然分档;2560/3、3840/3 非整除无碍——vp 常量换算是乘法取整,断点判断是除法取整,两侧都确定。

**与外部对照**(换算公式两源):Android 官方 `px = dp * (dpi / 160)`(dp 即 density-independent pixel,URL 见来源索引);OH vp 同构(px = vp × density,BerryOS 采整数 density 简化,OH 手机 1080/360 = 3 为同值实证,desktop.rs :97-98 + 应用规范 :138 两源)。

### 3.3 字号档对齐(字体面豁免的收回)

裁决 D 把「字号档/图标 px」豁免在屏幕参数外(desktop.rs :29-31)——vp 化后豁免收回:density 档表驱动字号档选择(3x 档主用 S32x48、角标 S16x32;sm/xs 档 S16x32/S8x16,phone 族现状即此),字号档本体(FontSize 枚举)不动,选择逻辑从 big 二分改断点档表。图标资产维持 @3x 单套(ScaledArgb 采样到目标 px,desktop.rs :91-92 现机制不动)。

### 3.4 开放项:竖屏 OH phone 全分辨率形态无档可跑

OH phone 布局族(big 分支资产:39vp 状态栏/80vp item/78vp dock/1002×234 dock 条)的消费判据是 `vp_h >= 1800` 竖屏像素阈,唯一载体曾是旧 desktop 档(render 1080×1920);desktop 翻横屏后,现役档位表中**没有任何档的 render 能承载它**(phone 族 render 480/540 宽,走紧凑)。两个走向:①补竖屏全分辨率档(render=panel=1080×1920,density=3 → 360×640vp sm 档,OH 常量族精确落位;性能账与横屏 1080P 同级,可跑,推断);②接受「模拟器主形态 = 横屏 desktop,竖屏手机形态走低清 phone 族」,OH phone 全分辨率形态等真机。本文不裁(产品形态问题非框架问题),登记为档位表扩展候选,与 02 号性能实测同窗定夺——若 virtio-gpu 使全分辨率竖屏流畅,①的成本只剩一个档位行。

## 4. 动态分辨率:两相位分治(与 02 号联动)

**定调**:分辨率体系分两相位——**初始态**(本文域:product/profile 单源,boot 静态链一次性分发,§2/§5 链图)与**运行态**(02 号域:virtio-gpu scanout,`SET_SCANOUT` 模式权交客机驱动面,01 号 §3b 已列 QEMU `virtio-gpu.c` 证据;01 号钉的五处静态卡点——boot 单点消费/info VMO 定值/guifbd FB_VA 定值/wmd+launcher 视口定值/宿主 RamSource 绑定——的动态化全归 02 号刀)。两相位的关系:初始态参数在 boot 一次走完静态链;运行态切换由 scanout 事件流驱动(几何热变 → guifbd 重配 → GETINFO 失效通知 → launcher 重排),**density 必须进事件流**(§3.2 层一 v1 刀的根据)。

**框架不变量重申**(01 号 §3c 定谳,本框架继承为不变量):宿主拖窗 = 纯宿主 scale(letterbox 等比缩放),永不触发客机分辨率变更——Android 模拟器(客机分辨率 = 设备属性、宿主窗口 = 壳)与 QEMU GTK 前端同款模型;BerryOS 该模型已实现且随刀 1 强化(初始 1:1 后,拖动缩放是从 1:1 出发的连续体)。动态分辨率的价值不在「拖窗跟随」(成熟竞品也不做),在**档位热切换不重启**(RES 菜单换档免整机重启,01 号 §1.1 现状是 QEMU 全重启)与**真机未来形态**(面板由驱动枚举)。

**4K 档解锁条件**(§2.1 表):desktop4k 词表立、值域锁,解锁 = 02 号 virtio-gpu 2D 后端落地 + 性能实测过线(「性能 = 能用不是看图」红线);S1 spike(virtio-gpu 实测)挂 GUI-2 刀前(`docs/GUI里程碑规划-2026-10-v1.0.md:13` 拍板④),其结果同时裁决 4K 档与 GPU 加速档序(soft → virtio-gpu 2D → Vulkan,同文件 :187)。

```

  profile = "desktop-1080p"(枚举引用官方档)

        │

        │      第一读者 = 内核 boot 回退源(fw_cfg 缺席时;bootparams 同形)
        │
        └─(组装期)sidecar out/<name>.display.toml(镜像伴生元数据)
               │      「--image 文件名约定联动」的机器化(§7.3-⑥ 收口提案)
               ▼
   berry(host 壳)profile 解析:--profile > sidecar > 内置默认档
   (Profile 结构:panel/render/refresh/memory/density——官方档表 = 唯一清单)
               │
               ▼
   QEMU 启动行:-device ramfb
     -fw_cfg opt/berry/display(模式串,扩 density 段)

               │

               │

     → wmd(GETINFO 缓存)→ launcher:ui.viewport()(px)+ density
               │
               ▼

     → GETINFO 失效通知 → launcher 重排;宿主拖窗永不触发
```
