## §4 β-0（VNC 增量）距离评估——02 号预判验证

- **QEMU 侧自动获得增量：实证成立**。手动 05 号 §1.2 拓扑（`-device virtio-gpu-device` 先于 `-device ramfb` 声明 + `-vnc :7` + 自写 RFB 3.8 原生客户端含流控重请求）：30s 窗收 **76+ 次 FramebufferUpdate**——初连全帧（1280×800 = gpu console 初始面）→ 固件模式切换全帧（0,0,800,600）→ 此后**全部小矩形**（16×10/16×7/32×10 字符格级，逐格步进）——VNC 传输层「按脏矩形发帧」在 gpu console 面上活体实证；ramfb console 面（berry CLI 现序）同一时刻恒 6121B 黑帧——**增量 vs 静死的对照同机同镜像拿到**。
- **帧源如实分账（推断标注）**：m1 轮 GOP 被 AAVMF 选到 virtio-gpu（VirtioGpuDxe 自驱——FB ok 800×600 fb=0x4c7a0000），故该轮 console 面的字符格级小矩形流主要归因固件文本相/GOP 更新（每字形一更）而非 guifbd 全帧 flush（v1 flush 的 damage = 全帧矩形，QEMU `resource_flush ∩ scanout` 后整面 dirty，08 号 §1.2 源码旁证）；guifbd 提交链的端到端证据 = 标记 + 无停刷 + β-0 传输层活体。实现者 note「VNC 800×600 白字黑底全帧收帧」的帧源即此固件文本相（白字黑底 = EFI 控制台前景色）——如实注不损结论：**QEMU 侧的增量能力与设备在席无关 guifbd 版本，B1 后自动在场**。
- **两接线前提（β-0 剩余距离）**：①**console 绑定序**——VNC 面向先声明图形设备：berry CLI 现序 ramfb 先 → gpu flush 永不达 VNC（boot A 黑帧实证）；gpu 先声明即得（m1 实证；复核期间 owner 在跑会话的 QEMU 命令行已见 `virtio-gpu-device,… xres=1080 yres=1920 -device ramfb` 序——owner 在途布线互证，05 号 §6-4 开放问题就此实证定谳）；②**damage 粒度**——v1 全帧 TRANSFER+FLUSH 使每提交 = 全面 dirty，VNC 每帧发全幅——传输层增量已省（无变化即无帧，ramfb 时代静帧也全帧 pread 的对偶面消失），但 per-rect 真·增量收益挂 v2 per-rect flush（02 号 §3.2 Linux virtgpu_plane.c 同构流位）。壳半（Frame damage 载荷 + wgpu 呈现，B1-b 壳面）本轮未动——β-0 距离 = 宿主一侧接线（qemu.rs 设备序 + 壳消费），guest 半已就位。
