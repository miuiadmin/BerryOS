## §0 一页结论（土话直答）

### 0.1 二期五面各一段

1. **热（PM-07）：热是省电的孪生子，动作空间同一套，分野只在触发原因。** 业界收敛形态 = 原因层各自传感、
   动作层统一仲裁取最严（Android 立法「电池功率约束也必须经 thermal HAL 上报」，
   [官方](https://source.android.com/docs/core/power/thermal-mitigation)，高）。对 app 契约全球一致 =
   **只读档位枚举 + 无议价权**（Apple 连温度都不给）；对调度器 = **帽生效必须同步打折记账面**（thermal
   pressure，Linux 5.7，[LWN 786122](https://lwn.net/Articles/786122/)，高）——这条是 PM-00 未覆盖的机制级新铁律。
2. **Fuchsia（PM-08）：微内核全用户态电源栈走通了，靠一张图 + 三个句柄。** 仲裁算法一行公式
   `required_level = max(enforced claims)`，零策略字节（broker.rs L1623–1636，高）。它最大的坑是 API 皮换了三代、
   而句柄语义（eventpair drop=释放）从未变——**BerryOS 应把句柄语义 day-one 冻结**。它最大的缺是 wake latency
   死在板级配置层没人消费，以及租约票面只有 name≤64 归因弱——P3a「仲裁器真吃 latency」与 P1「reason:u8 票面」
   都因此从「建议」升为「有反面实证的裁决」（PM-08 §0-5/§8，高）。
3. **AI（PM-09）：工业八年真正上量的 ML 只有一件（Adaptive Battery），且出口永远是既有机制（桶位），从不直接控频控帧率。**
   学术 25–42% 的学习型 DVFS 全部死在模拟器里，无一进生产热路径（PM-09 §2，高）。最贵的坑不是不准是误伤不可逆
   （推送延迟投诉群），业界解法 = 豁免面兜底而非精度兜底。BerryOS 兑付面收敛为**五张带内票 + 五条 kill criteria**
   （KC-P1..P5），「人无我有」最强 claim = manifest 内嵌豁免位 + 预测性维护窗（PM-09 §4，高/中）。
4. **无真机验证（PM-10）：业界无真机电源验证 = 三层（软件纪律/契约/物理量），没有一家把功耗绝对值做成仿真 CI 门禁。**
   QEMU TCG 定谳：`psci.c` 未实现 SYSTEM_SUSPEND、CPU_SUSPEND 永远只是 WFI（[源码](https://github.com/qemu/qemu/blob/master/target/arm/tcg/psci.c)，高）——
   「深睡」在仿真里没有物理面，断言只能打在协议调用与记账上（铁律 11 的业界同构）。九条电源断言（A1–A9）+
   sim-battery/sim-thermal/sim-modem 三设备契约草案现在就能落（PM-10 §4，高）。
5. **挂起与时钟（PM-11）：「挂起期间时钟走不走」业界三派，且 POSIX 同名反义（Linux MONO 停 / Darwin MONO 走）。**
   裁决建议 = 照抄 Fuchsia 停钟（程序正确性，RFC-0230 原文）+ 显式连续钟 SLEPT 做挂起记账；SDK 不复用
   `CLOCK_MONOTONIC` 名。维护窗数值第一次有了源码级官方真值（深闲 60min→6h 封顶、浅闲 5→15min、while-idle
   9min，DeviceIdleController.java + AlarmManagerService.java，高），PM-00 开放问题 3/7 双双闭环（PM-11 §2.3/§4，高）。

## §1 五面深挖要点汇总（每面最关键证据）

> 五面交叉互证链（二期最重要的单条合成洞察）：**归因先于治理**在五面各自独立出现——Fuchsia 把归因做在治理前
> （WakeReason→per-source 记账，PM-08 §6）、Android 归因迟到六年的代价（PM-00 §0-2）、热域「severity 必须
> 准 + 一切降档必须上报」（PM-07 §1.4）、验证域「无主唤醒=失败断言」（PM-10 A4）、AI 域「记账不撒谎、只认
> 记账面口径」（PM-09 §4.4-6）——五面全部把「能量化才可治理」当第一性，刀 1 的优先级由此跨面加固而非单报告主张。

| 5 | 记账时间戳用钟 | 运行态 CNTVCT 照旧；挂起相关账（resident/overhead）按 PM-11 两域口径预留 SLEPT 位 | PM-11 §4.1 |

| 7 | 与 intent billing 的账本关系 | per-UID 唤醒账与 intent 消费账（BILLING_* 已有雏形）统一账本口径，防「三本账」复发 | `kernel/src/syscall.rs:2348-2375` + PM-00 §6 intent 单一消费轴 |

### 3.4 开写顺序建议（设计文档内部章节即刀程）

1. **先裁 §3.3-1/2 两件硬前置**（源 id 归属 + 导出通道）——各半页 ADR 级裁决即可解锁开写。
2. 设计文档主体：schema（七字段 + 持有者归因 + 计数器组）→ 写点接线（on_wake 扩展 + IRQ 派发回调挂钩）→
   导出面（环映射/查询）→ 断言面（归因守恒 Σ 记账=内核唤醒总数、无主唤醒=0、二跑规律双轮）。
3. 实现顺序与 PM-10 断言面对齐：记账面先落（A4 判据变可判定）→ A2 冻结压测同刀可挂（sched-1.1 载体已在途）→
   sim 注入通道后挂（A3/A6 等 sim 依赖项留位）。
4. 明确不做的写进设计文档反面节：不记物理量、不给策略服务任何书写面、不进 berry-power 之前任何用户态消费者
   （刀 1 纯内核面纪律，PM-00 §7-1）。

## §4 开放问题更新（一期 7 条处置 + 二期新增）

**一期 7 条处置**（详 §2.4 表 #19–23）：#3、#7 关闭；#4 收紧为实验轨道 + kill criteria；#2 部分收窄；#1/#5/#6 保持开放（#5 路径已清晰：契约冻结 → sim 验证 → 真机计量，PM-10 §4.4）。

**二期新增开放问题**（按风险排序）：

1. **berry-thermal 与 berry-power 的边界**：PM-07 定「同级两服务、帽汇入同一聚合点」，PM-00 裁决 1 又定 berry-power
   合一——热面是第三个「两张面」还是独立进程？涉及失败隔离（热服务崩了帽还在吗）与 critical 短链归属，需 ADR 裁。
2. **源 id 铸造与名字映射归属**（§3.3-1，刀 1 硬前置）。
3. **导出通道与 syscall 预算口径**（§3.3-2，刀 1 硬前置）：35 在册 vs 实查 39 的账要先对平。
4. **unmonitored 逃逸位的治理边界**：Fuchsia 用它做治理逃逸阀（不计时长不报崩溃）——BerryOS 谁有权申请
   （系统服务 only？manifest 能力位？），防止它变成 wakelock 2.0（PM-08 §4.2 第二代）。
5. **SLEPT 连续钟的实现归属**：挂起期由谁累加（always-on 域计数器 vs 唤醒时用 RTC 差补）——QEMU 仿真态如何记，
   影响维护窗判定精度（PM-11 §4.1 留白）。
6. **KVM 相是否进 CI**：真深睡路径只能在 KVM 测（PM-10 §4.3），CI 矩阵要不要加 KVM 相（当前 smoke 全 TCG）。
7. **sim-* 设备族的实现路径**：fork 钉场 QEMU 加设备（goldfish 先例）vs virtio 实验/厂商 ID 段——成本与上游
   漂移维护的裁决（PM-10 §1.6/§4.2 给了两条路未裁）。
8. **预测性维护窗的观察面数据积累起点**：五张票中维护窗票/预唤醒票依赖用户行为数据——遥测里哪些字段从
   day-one 就该记（否则 v4 想训没数据），挂 AI 实验轨道立项（PM-09 §4.3）。
