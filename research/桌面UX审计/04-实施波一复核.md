## 2. 刀 B：状态栏可信化四件对 02 号 M1 与 03 号 B1

### 2.1 真时钟通道形态与红线判定（核心项）

**通道形态（实测五段全链）**：

1. 宿主注入：`tools/berry/src/qemu.rs:253-265` `spawn_image` 把 `SystemTime::now()` epoch 秒写 `-fw_cfg name=opt/berry/rtc,string=<secs>`（UTC；读取失败=不注入）——display 注入同形先例。
2. 内核消费：新文件 `kernel/src/rtc.rs`（84 行）boot 期单次 `boot_init()`（`rtc.rs:50-72`，`kernel/src/main.rs:272` 调用）：读 fw_cfg 具名项（帽 20B、trim NUL、`parse::<u64>`、0 视为未注入），成功即「epoch + 同刻 CNTVCT 纳秒锚」双 AtomicU64 落盘 + 串口证据行 `RTC ok epoch=<n>`。
3. syscall 面：`kernel/src/syscall.rs:433-457` `sys_clock_read` 加 `id==CLOCK_REALTIME(1)` 分支 = `epoch×1e9 + (now−锚)`（`rtc.rs:75-84` 饱和防御）；id 0 路逐行不变；缺席注入 REALTIME 返 -ENOTSUP。
4. ABI 单源：`tools/abi.toml:107-117` 加 `[[clock]] REALTIME=1`（desc 明注 fw_cfg 注入面与 -ENOTSUP 语义）；`tools/abi.toml:724-735` 加 0x88 `power_off`；`tools/gen_abi.py` 四元组钉板 (37,41,40,45)→(38,42,41,45)；五面再生（kernel/berry-sys abi_gen.rs、abi.syz、ABI 文档）。
5. launcher 消费：`user/bins/berry-launcher/src/main.rs:253-270` 单取 `berry_clock_read(CLOCK_REALTIME)` 换算 "HH:MM"（`desktop.rs:247-259` `hhmm_utc` 单源）传入 `desktop::build` 首摆 + 证据行；`frameloop.rs:291-318` 每轮醒读、分钟字变才 `set_text`（等长换文纯 PAINT）+ a11y in-place 覆写 + `wake`；注入缺席回退 `STATUS_CLOCK` 12:00 静态占位零标记零漂移。

**红线判定（任务书「若新 syscall 是否越界」）**：**未越**——零新 syscall 号。壁钟走既有 0x61 `clock_read` 的 id 域扩展（`berry_clock_id_t` 既有框架 add-only，id 0 行为逐位不变，ktest 负样本随刀 1→2，`kernel/src/ktest.rs:181` 实码在案）；真正的新号只有 0x88 `power_off`，那是刀 D 任务书明文授权面（「PSCI 在则 berry-sys 调用面加 power」）。**如实记两处口径突破**（非红线但须呈堂）：其一，ABI 冻结面变更属实（abi.toml/syz/文档/两端生成面五处），走 0x86/0x87（2026-11-07）立的 add-only 破冻先例，属灰色合规；其二，02 号 M1 标题承诺「纯 launcher 层，不动协议/服务」被内核+ABI 改动突破——但任务书 B 项自身写明路径「经 fw_cfg/opt 注入→内核→launcher 换算」，内核侧落点是任务书的必然推论（fw_cfg 唯一消费面在内核，launcher 无既有读 fw_cfg 通道），非私自扩面。另记一处与底稿字面的偏差：02 号 M1 说「launcher 换算+MONOTONIC 差值摆字」，实现把 epoch+monotonic 合并放内核、launcher 只做 HH:MM 格式化——语义等价且更干净，判定无碍。

**通道实跑（本复核独立取证，三组）**：

- `-kernel` 裸启 + 注入 `string=1794512342` → 串出 `RTC ok epoch=1794512342`（逐位一致）；畸形注入 `string=abc` → 零 `RTC ok` 行（负样本过）。

### 3.4 A/B 对照定谳：阻塞与波一 launcher 无关

方法：HEAD 版 launcher（`git show HEAD` 四文件覆写，波一引用零命中验证）+ 现内核 + 其余全现树，重打 cpio（tlsscan 过）+ mkimage 成 A/B 镜像，同拓扑跑 Boot A。结果 **AB_EXIT=1 同卡死**，且复现实施者报告的 `G1.5: kill user task 'user_svcmgr'` 形态（波一 launcher 那次为 svcmgr 存活但 app 批不发——同一病灶两种时序相）。结论：**E2E 首帧阻塞换回旧 launcher 依旧在，归因并行线（sched/dpg 未提交改动随镜像内核入盘 + f44c2ba8 的 svcmgr/P3-1 面），波一 launcher 撤清干系**；实施者「被并行回归堵、svcmgr 修复后重跑即闭环」的自述独立证实。三键可视/关机二击整机退出两项 E2E 顺延该修复（复跑口径：`python3 tools/gui8-smoke.py` 与 `berry shot --wait-marker "LAUNCH ok"`）。
