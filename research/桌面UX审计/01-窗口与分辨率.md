# 01 窗口与分辨率——六痛点之一「分辨率固定不能拖/屏幕显示不到下面」根因与修法

> 采集日期 2026-11-13 · 性质 = 桌面 UX 审计子课题 01(研究波产出,只写本件) · 产出者 = 会话子代理(berry 源码解剖 + 本机 headless 实测 + 外部源码取证)
> 消费面:实施波改 `tools/berry`(窗口/分辨率面)的任务书底稿;02-06 号姐妹件对表(②导航键 ③应用顶栏 ④状态栏 ⑤触摸 ⑥字体)。
> 方法注记:`web_search` 接口认证失败,外部事实改用 `web_fetch`/`curl` 直取 QEMU/AOSP 官方源码仓核实;本机实测含两次 headless boot 抓帧 + 串口日志(`BERRY_HOME=out/.berry-tmp`,TCG,串口行原文收录)。数值与论断凡两源均已核,单源实机取证已注明,推断处标「推断」。

## 0. 一页结论

痛点①实为两条子痛,根因不同:

1. **「分辨率固定不能拖」**——客机分辨率确实固定且改档需整机重启,这是设计现状而非 bug:分辨率档由 profile 在 QEMU 启动行经 fw_cfg 一次性递给内核(`tools/berry/src/device.rs:66-73` → `tools/berry/src/qemu.rs:246-249` → `kernel/src/main.rs:211-228` boot 单点消费),整条显示授能链(fb VMO/info VMO/guifbd 映射/launcher 视口)都是 boot 期静态定值。宿主窗口本身**从 P0 起就可拖**(`window.rs:772` `with_resizable(true)`,git 9cdb9255 2026-11-03 引入,晚于此的所有二进制都含),拖动即等比缩放(`window.rs:441-495` 每帧按窗宽高重算 letterbox)。用户体感「不能拖」的真正放大器是**默认窗口尺寸的 DPI 语义 bug**:窗口尺寸按物理像素算(`window.rs:766-770`),基准系数 0.8/0.55(`window.rs:750-758`)在 Retina 2x 屏上等效减半——16″ MBP(3456×2234,本机实测)desktop 档开窗仅 432×768 物理像素 = **216×384 逻辑点**,1080×1920 内容缩到约 0.2 倍,小到像不可交互,同时直接加重痛点⑥「字体效果差」。
2. **「屏幕显示不到下面」**——双端实测均**不复现**:客机侧 desktop 档(1080×1920)与 phone 档(480×1000)headless 抓帧分析,dock 与底部保留区完整画到最后一行;宿主侧开窗数学带 0.9 屏幕钳制(`window.rs:760-765`),窗口不可能高于屏。残余候选(推断,非本件可闭环):用户实测时的构建/档位不同,或应用窗层几何(应用全屏窗 + 系统窗避让裁剪,`user/bins/gui-wmd/src/table.rs:205-214`)——后者已移交 03 号对表,本件给验证方法(§2.3)。

修法分层与推荐:**a 最小修(推荐先做,0.5-1 天)**=窗口默认尺寸改逻辑像素口径 + 工具栏逻辑化;**c 宿主 scale(架构正解,已基本就位)**=Android 模拟器与 QEMU 自家 GTK 前端同款模型——客机分辨率设备档定死,窗口任意拖、内容纯宿主缩放,补齐 a 与 RES 菜单预期管理即达标;**b 运行时热切换分辨率(数周,不建议当前做)**=QEMU ramfb 热重编程本身支持(已证),卡点全在客机 boot 静态授能链,属显示栈重构,挂远期与 virtio-gpu 择机合并。

## 1. 现状解剖

### 1.1 壳窗口:什么框架,尺寸逻辑在哪

- 框架 = winit + softbuffers,宿主依赖不进客机/ABI(`tools/berry/src/window.rs:1-2`、`tools/berry/README.md:23-25`)。窗口持呈现与输入映射,帧源与来源无关(RamSource 共享 RAM 或 VNC)。
- 可拖性:`.with_resizable(true)` + `.with_min_inner_size(320,240)`(`window.rs:768-772`)。`WindowEvent::Resized → request_redraw`(`window.rs:800-802`),`draw()` 每帧用 `window.inner_size()` 减工具栏高(`TOOLBAR_H = 48` 物理像素,`window.rs:26`)后调 `scale::fit` 等比 letterbox,`scale::render` 双线性缩放上屏(`window.rs:441-465`、`tools/berry/src/display/scale.rs:26-44,61-108`)。即:**拖窗口 = 内容即时重缩放,客机分辨率不动**。
- 初始尺寸与「固定感」来源:`resumed()` 一次性算系数——`ScaleMode::Fit` 下 `panel_h > 1200 ? 0.55 : 0.8`,再与 `0.9 × 主屏物理宽高 / panel 宽高` 取 min,下限 0.2(`window.rs:750-765`);窗口宽高 = `panel × factor` **物理像素**(`window.rs:766-770`,`with_inner_size(PhysicalSize)`)。`ScaleFactorChanged` 只重绘不重排窗口尺寸(`window.rs:868-870`)。
- 换分辨率档 = 换整机:窗口 RES 菜单 `select_profile` 在 Host 路径停旧 `Device` 再起新 `Device`(QEMU 全重启,`window.rs:529-547`);Attach 路径走 `restart_profile`(起新 host 进程 + 旧 run 下线,`tools/berry/src/commands.rs:864-902`)。CLI 面 `berry display set <profile>` 无 `--restart` 只记录 next-profile,`--restart` 才起替换 host(`commands.rs:661-724`,自定义 `WxH` 一律强制 `--restart`,`:669-674`);README 表述「分辨率 `berry display set <profile> --restart`」(`tools/berry/README.md:81`)。

### 1.2 客机分辨率怎么定:fw_cfg → 内核 boot 单点 → ramfb

链路全量(全部已读源码对行,末两步为本机实测):

1. 宿主:`Device::start` 按 profile 生成 `mode = render_w x render_h @ refresh`(非 default 档才生成,`device.rs:66-73`),QEMU 参数面 `-device ramfb` + `-fw_cfg name=opt/berry/display,string=1080x1920@60`(`qemu.rs:245-249`);同时 `-object memory-backend-file,…,share=on` 供宿主直读客机 RAM(`qemu.rs:196-201`)。
2. 客机内核:boot 期 `display_mode_req()` 读一次 `opt/berry/display`(`kernel/src/main.rs:211-228`),与固件 GOP 缓冲容量比对:装得下(如 480×1000×4 = 1.92MiB ≤ 800×600 GOP 缓冲 1.92MiB)就地 `ramfb_set`;装不下打 `DISP defer`,`mm::init` 后从 buddy 取 2^n 连续页再 `ramfb_set`(`main.rs:339-380,393-424`)。`ramfb_set` 经 fw_cfg DMA 口写 28B 大端配置到 `etc/ramfb`(`arch/aarch64/src/fwcfg.rs:249-286`;该文件头注 :182-187 明言「写成功后 QEMU 立刻替换 scanout surface,VNC 与宿主共享 RAM 两侧同时看到新几何」)。
3. 内核打 `FB ok <w>x<h> fmt= stride= fb=0x…` 串口行(`main.rs:285-297,413`)。
4. 宿主 `boot_runtime` 在串口里等这一行,`FbInfo::parse` 后开 `RamSource`(mmap `ram.bin`,几何与偏移**开场一次性绑定**,`device.rs:320-341`、`tools/berry/src/display/ram.rs:63-99`)。
5. 本机实测串口原文(desktop 档,TCG,2026-11-13):`DISP defer 1080x1920` → `MMAP ok segs=35 pages=19151` → `ramfb: select=37 size=28` → `DISP ok 1080x1920` → `FB ok 1080x1920 fmt=1 stride=4320 fb=0000000040800000`。
6. 下游消费者几何同样是 boot 定值:guifbd 从 boot info VMO(gift2)读 w/h/stride,`FB_VA` 映射幅 spawn 期钉死(`user/bins/guifbd/src/main.rs:819-855`);gui-wmd 的 `disp_w/disp_h` 建表定值(`user/bins/gui-wmd/src/table.rs:87-115`);launcher `UiMain::new(disp_w, disp_h)` 一次性 `Box::leak`(`user/bins/berry-launcher/src/main.rs:250-251`),布局按视口分支 `big = vp_w>=600 && vp_h>=1800` 消费 OH phone 常量(1080×1920 专属)或紧凑常量(`desktop.rs:206-219`)。

结论:「改需重启」不是 QEMU/ramfb 的能力限制(见 §3b),而是**模式请求只在 boot 消费一次 + 几何沿授能链静态分发 + 宿主帧源一次性绑定几何**三层叠加的工程现状。

### 1.3 档位表(现行)

`tools/berry/src/profile.rs:20-75`:default 800×600/128MiB(P1 兼容,console 上屏);desktop 面板 540×960、渲染 1080×1920、256MiB(`just desktop` 用,`justfile:1362-1376`);phone 面板 1080×2250、渲染 480×1000(GUI 双击无参默认,`tools/berry/src/main.rs:590-600`);phone16 480×854;phone20 540×1200;tablet 800×1280(后两档 README 注明 buddy 连续块 + ramfb 重编程路径,`tools/berry/README.md:118-123`)。

## 2. 痛点①根因判定

### 2.1 「分辨率固定不能拖」

- **分辨率固定:属实,是设计现状。**档位经 fw_cfg 递给 boot 内核(§1.2),运行期无任何路径改客机几何;RES 菜单/`display set` 换档 = 新 QEMU 新 run(§1.1)。宿主 `RamSource::caps` 上限 4096×4096 只是能力声明(`ram.rs:124-134`),不是变更通道。
- **「不能拖」:与代码不符,疑体感误判,推断。**窗口 resizable 自 P0(git `9cdb9255` 2026-11-03,`git log -S with_resizable` 单命中)就在,用户可跑到的构建(out/*.app 内 berry 为 2026-11-05,仓内二进制 2026-11-10)均晚于该提交。真实体验短板是**默认开窗太小**:本机 16″ MBP 主屏 3456×2234 物理像素(`system_profiler` 实测 2026-11-13,约 1728×1117 逻辑点 @2x),desktop 档 `factor = min(0.8, 0.9×3456/540, 0.9×2234/960) = 0.8` → 窗 432×768 物理 = **216×384 逻辑点**,内容缩放约 0.2 倍;phone 档 `0.55` → 594×1238 物理 = 297×619 逻辑点,尚可。物理像素口径在高 DPI 屏上把窗口视觉尺寸压半,且 `ScaleFactorChanged` 不重算(`window.rs:868-870`),跨屏拖动后依旧。小窗 + 字微小(痛点⑥共因)+ 拖动不改变「分辨率」,三者合成「固定不能拖」的体感。

### 2.2 「屏幕显示不到下面」

双端取证,均**无截断**:

- 客机 desktop 档:headless boot(`berry shot --profile desktop --wait-marker "LAUNCH ok"`,帧 1080×1920)抓帧做 27×48 块平均灰度图——状态栏(y≈0-160)、网格(y≈400-1600)、dock 图标带(y≈1600-1760)、底部保留区(y≈1800-1919)全部在帧内,末行 y=1919 有内容非黑边。
- 客机 phone 档:同法 480×1000 帧——dock 图标带 y≈860-890、底部保留区到 y=999 完整。
- 宿主窗口:0.9×屏幕钳制(`window.rs:760-765`)+ 尺寸下限 320×240,窗口高度物理 768(desktop 档)远小于 0.9×2234,数学上不可能超出屏幕。
- 残余候选(**推断**,本件不闭环):①用户实测走的是别的构建或别的档(如 tablet 1600×2560 面板在更小的副屏上,0.9 钳制虽在但窗口视觉巨大,底部工具栏贴屏底边缘可能被 Dock/刘海底遮住——macOS 不保证客户区完整可见);②应用层窗口几何:应用开全屏窗(如 gfxdemo `0,0,disp_w,disp_h` + `AVOID_SYS`,`user/bins/gfxdemo/src/main.rs:230-240`),wmd 对其按系统窗裁剪(`table.rs:205-214`),若系统层窗(状态栏)高度与应用假设不一致,应用内容底部会被裁——此路归 03/04 号(顶栏/状态栏)对表。
- 验证方法(移交实施波/姐妹件):`just desktop` 后点开蓝顶栏应用,用 `berry screenshot` 抓帧量应用内容底边 y;若 = `disp_h - 系统窗高`,坐实②;若用户能复现「整个桌面下半不见」,请记录当时的 profile/显示器组合,回放 §2.2 两端取证步骤。

## 3. 修法分层

### 3a 最小修(推荐,0.5-1 天)

目标:开窗即合理大小,拖动缩放体验立刻「像样」。全部改动收敛在 `window.rs::resumed()`(及 TOOLBAR 常量口径):

1. 尺寸口径改逻辑像素:`event_loop.primary_monitor()` 取 `size()/scale_factor()` 得屏逻辑尺寸,`factor` 与 0.9 钳制在逻辑口径计算,`with_inner_size(LogicalSize)`(或物理 = 逻辑 × scale_factor 传 PhysicalSize)。效果(本机推算):desktop 档默认窗约 min(0.9×1117 高,960×0.8 基准)——即约 486×864 逻辑点的竖窗,内容缩放约 0.45 倍起步,可读性立即恢复;phone 档约 460×958 逻辑点。
2. `TOOLBAR_H = 48` 改逻辑点语义(× scale_factor 取整),按钮命中区同步;高 DPI 下 24 点高的工具栏按钮过小是现隐患(推断:痛点⑤「能触摸点击了吗」的宿主侧一部分)。
3. 可选(半小时):窗口初始位置居中(winit `with_position`),避免开在屏角被 Dock 遮挡。
4. 验收:`just desktop` 开窗 ≥ 480 逻辑点宽;拖大到全屏内容等比清晰;`berry shot` 冒烟不回归(shot 路径不经窗口代码)。

风险:无协议/客机改动;`ScaleMode::Integer(1|2)` 语义保留(整数倍缩放对像素字体的清晰度仍有价值,README :47 已有 `--scale` 面)。

### 3b 中期:拖动 → 动态分辨率 → 客机热切换(数周,不建议当前做)

先给可行性判据,再给卡点清单:

- **QEMU 侧支持热重编程,已证两源**:仓内 `fwcfg.rs:182-191` 头注(写 `etc/ramfb` 即刻换 scanout);QEMU `hw/display/ramfb.c` 的 `ramfb_fw_cfg_write` 每次写都 `qemu_create_displaysurface_from` + 换 surface,尺寸界 `[16, VBE_DISPI_MAX_XRES=16000] × [16, VBE_DISPI_MAX_YRES=12000]`(`bochs-vbe.h:8-9`),无次数限制。即 ramfb 不是「不支持热切换」,只是被 boot 单点用法钉死。
- **卡点在客机静态授能链与宿主源绑定**,至少五处:①`display_mode_req` 仅 boot 消费(`main.rs:211-228`);②fb 窗/info VMO 在 svcmgr 插表期定值(guifbd 头注 :4-12);③guifbd `FB_VA` 映射幅与 `Srv` 的 w/h/stride 终身定值(`guifbd/src/main.rs:832-858`);④gui-wmd `disp_w/h` 与 launcher `UiMain` 视口一次性建(`table.rs:87-115`、`berry-launcher/src/main.rs:250-251`);⑤宿主 `RamSource` 几何/偏移/缓冲开场绑定(`ram.rs:63-99`),VNC 通路反而已支持 DesktopSize 动态几何(`display/vnc.rs:391-393`)。另缺宿主→客机控制通道(现仅 fw_cfg 启动串与 virtio-tablet 输入)。
- 实施形态(若做):新增「显示热插拔」RPC(重启 guifbd/wmd/launcher 进程族 + 内核重跑 buddy+ramfb_set + 宿主重读 `FB ok`),或引入 virtio-gpu(客机驱动面 `SET_SCANOUT` 协议,QEMU `hw/display/virtio-gpu.c:734,825` 在案)把模式权交给客机 DRM 面。任一路都是显示栈重构级,数周计,且不解决用户当务之痛。
- 对照定案:Android 模拟器改设备分辨率(改 AVD 皮肤/硬件档)同样要重启虚拟机——「拖窗改设备分辨率」在成熟竞品里也不是默认行为(§3c)。

### 3c 成熟对照:宿主 scale 是正解(架构已就位,补短板即可)

- **Android 模拟器模型**:窗口几何与 LCD 显示区由皮肤(skin)配置定义——皮肤规格原文「window containing an image of a fake handset」「layout 'width': The width of the emulator window in pixels」「part 'display': An emulated LCD screen area」(AOSP `docs/ANDROID-SKIN-FILES.TXT`,链接见来源索引):**客机分辨率 = 设备属性,宿主窗口 = 壳,缩放在宿主**。改分辨率 = 换皮肤/AVD 配置 = 重启;窗口缩放(Zoom)即拖即得。
- **QEMU 自家 GTK 前端同构**:窗口 resize 后 `scale_x = (double)ww / fbw`、`scale_y = wh / fbh` 重算,客机表面尺寸不动(`ui/gtk.c:839-850`)——「客机分辨率不变、宿主窗口任意拖、内容 scale 渲染」的现成参照实现。
- **BerryOS 现状对照**:该模型**已经实现**——`window.rs::draw` + `scale.rs::fit/render` 每帧 letterbox 缩放,窗口任意拖动内容即重缩放,输入坐标 `window_to_guest` 反算自动适配(`scale.rs:47-57`、`window.rs:510-517`)。差距只剩:①默认窗口尺寸/DPI 语义(= §3a);②RES 菜单语义是「换设备档(需重启)」而非「改窗口缩放」,需要文案/预期管理(按钮 tooltip 与 README 口径,半小时);③可选增「窗口尺寸记忆」(记上次窗宽高,launch 恢复,半天,非必须)。

## 5. 与其他痛点号的对表

- ⑥ 字体字距:0.2 倍缩放下任何字体都糊——§3a 是其宿主侧共因之一(客机侧字形/字距归 06 号)。
- ② 导航键:桌面 OH 布局只含状态栏/网格/dock/底部保留区,无 nav 条元素(`desktop.rs:23-141` 常量族)——根因在 launcher 建树面,归 02 号;与分辨率档无关(1080×1920 档实测布局完整)。
- ③ 应用顶栏蓝 + 左上角英文:应用全屏窗 + 自绘顶栏(gfxdemo 家族 `GFX` 字形左上角,`gfxdemo/src/main.rs:349-351`)——归 03 号;本件提供 wmd 窗口机制行号(`table.rs:254-283,205-214`)。
- ④ 状态栏:launcher 状态栏 39vp×3 = 117px 图标位已在(`desktop.rs:213,320-341`),实图标/沉浸归 04 号。
- ⑤ 触摸:宿主→客机映射链已就位且随窗口缩放自动反算(§3c);「能不能点」的疑点更多在客机输入服务与命中区大小(工具栏 24 点高按钮过小 = §3a 第 2 条)——客机侧归 05 号。
