## 1. 各家测试形态

### 1.1 moss-kernel——三层分舱最干净，CI 真接线（MIT · Rust · Linux 兼容）

- **三层形态**：① libkernel host 单元层——架构无关库（feature 门控 sync/alloc/paging/fs…，`CpuOps` 抽象 arch 操作，libkernel/README.md），host 上 `cargo test` 验证 AArch64 逻辑（README 原文「validating AArch64 page table parsing logic on an x86 host」），当前快照 grep 实数 384 个 `#[test]`/29 文件（README 自述 230+，快照已增长），dev-deps 用 rand + tokio（libkernel/Cargo.toml）——host 端拿 tokio 执行器测异步内核原语；② 内核内 `#[ktest]` 层——`moss-macros::ktest` + `src/testing/mod.rs` 自带 runner（Rust custom test framework：`#[test_case]` 落 linker section，`.cargo/config.toml` 置 `runner = scripts/qemu_runner.py`，`just test-kunit` = `cargo test --release` 即 QEMU 起内核、跑完 `power_off()`），`catch_unwind` 把 panic 转 Failed **继续跑后续用例**，async ktest 用 `current_work_waker` 同步 poll 到 Ready；③ usertest 运行时层——4,442 行/12 文件（epoll/fpsimd/fs/futex/futex2/inotify/pidfd/sched/signalfd/signals/socket，Linux 兼容面），`inventory` 链接期注册 + `register_test!` 宏，`run_test` = **fork-per-test** + `catch_unwind` + `waitpid`（单测崩溃不杀套件，usertest/src/main.rs）。
- **确定性手法**：fork 进程隔离、panic 捕获续跑；`test_clock_sleep` 只断言 `elapsed >= SLEEP_LEN`（定时类弱断言）；每测先行 `sync()`。
- **门禁接线**：ci.yml = fmt `--check` + clippy `-D warnings`（含 libkernel `--all-features --all-targets`）＋ **cargo-hack `--feature-powerset` check 且 test**（特性幂集测试矩阵）；test.yml = smp 双臂矩阵（""/"smp"）→ 造 alpine 镜像 → QEMU 跑 usertest + `cargo test -r` → **grep 成功行判绿**（"All tests passed in " / "test result: .*ok"）＋ artifact 上传。
- 糙面一例：`TestResult::Failed` 着**绿色**转义（src/testing/mod.rs Display impl）——门面细节失修。

### 1.2 BoredOS——boot 期自测单层，假绿样本（GPL-3.0 · C · 只对照）

- **单层形态**：boot 期内核内自测，`mem/test/` 六套（pmm/slab/mmu/vma/vmm/pagecache，721 行）；`core/main.c` 的 `init_memory` 按「init → 就地测」顺序穿插，**cmdline 旗标门控**（Limine kernel_file cmdline 含 `selftest` 或 `test` 才跑）；断言宏 `TEST_ASSERT` 失败写串口一行即 return，外层 `log_ok`/`log_fail`。
- **假绿破洞（实证）**：`pagecache_run_tests()` **无条件 `return true`**（mem/test/pagecache_test.c）——void 子测试失败只留串口一行，boot 仍打 "Page Cache unit tests passed"——门禁语义不传导的活样本。
- **门禁接线**：Makefile **无 test 目标**（目标族只有 run/run-hd/serial/bochs 三 OS 变体）；CI（pr-build.yml，名 "Build & Test ISO"）**构建 ISO 即止**，nightly.yml 构建加发 nightly 资产——自测不进 CI，全靠人手 QEMU 加旗标。（任务素材预期「Makefile 测试目标」，实读不存在，如实记。）

### 1.3 swift-os——量级最大的验收机器（Apache-2.0 · Swift · 可借语义）

- **三层形态**：① host 单元层（`host-test` 目标）——**host swiftc 直编内核源文件进测试二进制**（`tests/page_allocator_test.swift kernel/mm/page_allocator.swift`、net 栈 12 文件、shmring 加 `-D SHMRING_HOST` 条件编译、errno 表钉板等）；② QEMU 集成层——tests/ 323 个条目（264 个 .sh + 52 个 .swift），模式 = headless QEMU + 串口日志 + EXPECTS 必须子串集（里程碑标记 M6/M8a/C3/C4A 与 **DENY 负向标记**）+ 超时轮询后 kill（tests/boot_test.sh）；③ boot 自测层——FDT `/chosen/bootargs` `selftest=1` opt-in（默认跳过，tests/boot_selftest_optin_test.sh）。
- **确定性手法（三件）**：`tests/lib/run_qemu_harness.sh` 重试边界——**仅当 guest 从未达裁决（boot 超时/无 PASS:/FAIL: 行）才自动重试一次，实质 FAIL 永不重试**，静态门白名单永不重试，retry log 末尾汇总；`tests/lib/timeouts.sh` 角色化超时帽（按角色不按标记文本，480 s = 观测 2× 方差余量，原文「a ceiling, not a sleep」）；**harness 自身有单测**（run_qemu_harness_retry_test.sh 用假 harness 测重试分类）。
- **门禁接线**：Makefile **235 个去重 `*-test` 目标**，按里程碑编号（s0–s5 调度/c5–c7 cell/ns1–ns3 网络/h3–h5 平台/qw* IPC·权限·ABI 族）；ci-fast.yml = host-test job（ubuntu-24.04-arm）+ ci-test job（`make ci-fast` = docs-test + 构建 + boot 冒烟三脚本过 RUNTEST）；ci-nightly.yml = 全量 `make test` + **prod + hetzner 生产门**；另有 ci-ports.yml。
- **测试叙事**：docs/NOTES.md（9,561 行）167 处 Gate/Acceptance、466 处测试目标/脚本引用——每特性条目以「Test: make xxx-test → 脚本 + 标记」收尾，nightly 挂掉（smp_resource_stress 登录段 SIGSEGV）也入记。
- **两个特色门**：errno-test（Makefile 注释原文「pin the shared Errno table's exact raw values (they are syscall ABI)」——25 号（原 13）errno 断层坑的门禁化）；docs-test（docs_reference/roadmap/examples-verification/stability-coverage 五子门——文档可执行性执法）。

### 1.4 urthr 与 TrustOS（转引 13/14 号，不重读源码）

- **urthr**：GitHub Actions 双徽章「Build RPi5 + Runtime Test RPi4b」——**构建与真机运行时测试分离的 CI 先例**（14 号 §1.2，已挂 P0-a 台阶二参照）。
- **TrustOS**：fix 样本含「drop fragile QEMU integration test」——**QEMU 集成测试建了又因脆而砍**（25 号 §1.3），项目已死；其 UDP remote-first 三通道（24 号 §2.4）是可观测性预案而非测试门禁。

## 3. 可借鉴点（已过 BerryOS 既有 G0–G5 面筛除重复）

| 来源 | 机制 | BerryOS 现状对照 | 去处/优先级 |
|---|---|---|---|

| moss ci.yml | cargo-hack `--feature-powerset` test（特性幂集矩阵） | feature 面（lockdep 等）只有定点双相构建（smoke-lockdep），无组合矩阵 | host 侧补 feature 组合测试矩阵，锁特性交叠破编译/破测试类问题；P2 |
| swift-os errno-test | errno 原始值钉板 host 门（「they are syscall ABI」） | 25 号已建议 errno 值域探针（P1 池）——本条为其找到成熟同构实证 | 落地形态直抄 swift-os：host 编译 errno 单源表 + 值断言；P1（随 berry-sys 域下一刀） |

| swift-os docs-test | 文档示例可执行性门（examples-verification 等） | docs_guard 管结构预算、abi-check 管 marker 对拍；文档命令示例可跑性无门 | 文档/命令速览中的示例命令入 CI 验活；P2/P3 |

## 4. 结论——BerryOS 测试工程的相对位置

**纵深第一，广度第二，真机未出发（诚实定位）。** ① 系统级门禁纵深——关卡递进（G0–G5 层稳定前不开下层，docs/测试策略-v1.0.md §1）、确定性源头消灭（-icount 纪律 + fw_cfg 门控零扰动，§7）而非噪声容忍、防假绿语义（churn 严格递增断言、soak 首拍潜伏、对端死亡必须 loud，justfile soak 注）——五项目无一具备等价物；24 号「全场唯一系统级门禁体系」的判断在测试工程专面复核成立。② 量级与广度——swift-os 是唯一可比者（235 目标/323 文件/三层/nightly + 生产门，Makefile + tests/），且**生态验收面更宽**（nginx/sshd/ports/LLM 栈在测，NOTES.md 466 处测试引用）；BerryOS G-eco 现状 hexyl 已过、ripgrep 与样例矩阵未落（测试策略 §2）——此差距与生态阶段相关，如实记。③ 真机门禁——urthr（真机 CI 分离，14 号）与 swift-os（Hetzner 生产门，ci-nightly.yml）已过此关，BerryOS 零出发（G5 待办）。④ 密度短板——moss 的 ktest 失败续跑证明「一次 boot 收全失败清单」可行，BerryOS 首败即停是可修的收割密度损失（§3 第一行）。反面样本的价值同样实证：BoredOS 恒绿 return true + CI 只构建（mem/test/pagecache_test.c + pr-build.yml）与 TrustOS 砍脆弱 QEMU CI（25 号）共同反证——BerryOS 的断言语义传导与主干永绿红线不是自誉，是这批 2025–2026 同行里真实的稀缺品。
