## §0 一页结论（TL;DR）

1. **现役系统的交互功耗架构 = 「事件驱动的两段式」**：平时（无交互）整条链路逐级归零——AP 睡、显示服务停帧、触摸控制器降扫描档、传感器进 FIFO 批量；按下那一刻（事件到）逐级起振——触摸 IRQ 唤醒 AP、提频脉冲（touch boost）+ 提刷新率（LTPO 拉高档）同时开火。全部机制的差别只在**归零的深度**与**起振的速度/时长**这两个旋钮。
2. **touch boost 是「买延迟保险」的暴力手段**：schedutil 按利用率选频看不懂 UI 线程→RenderThread 的串行依赖，低负载下选频必迟、必卡；所以 Android 自 4.x 起就在触摸事件上强制拉高最低频率（Qualcomm `cpu-boost` 驱动 `input_boost_ms=40` 默认值实锤），代价是管线轻时白烧电（[LWN](https://lwn.net/Articles/809545)）。
3. **交互态是一台与「屏幕开关」解耦的状态机**：Android PowerManagerService 用 wakefulness（AWAKE/DREAMING/DOZING/ASLEEP）+ 屏幕策略（BRIGHT/DIM/OFF）两根轴，userActivity 由输入事件驱动、间接事件被显式剔除，DIM 时长从超时尾部按比例扣（[PMS 源码](https://android.googlesource.com/platform/frameworks/base/+/0ac9664a9ee2e6d1d3b68fe00c264ad94fe98966/services/core/java/com/android/server/power/PowerManagerService.java)）。
4. **触控与显示是两条独立采样率**，但软件上强联动：OpenHarmony 在显示服务里放了一台触摸状态机（IDLE/DOWN/UP + 3s 抬手超时），触摸票直接压过光照因子降级、强制重刷 LTPO 档（本地源码一手证据）。
5. **传感器的答案 = FIFO 批量 + 唤醒类隔离 + 低功耗域卸载**三件套：50Hz 传感器不批量 = 每秒吵醒 AP 50 次；计步/抬腕这类 always-on 感知全部住在 sensor hub/CHRE 低功耗 DSP 里，AP 全程不醒（[AOSP batching](https://source.android.com/docs/core/interaction/sensors/batching)、[CHRE](https://source.android.com/docs/core/interaction/contexthub)）。
6. **BerryOS 的落点**：内核只留「交互脉冲」原语 + intent 0x02 单轴（设计位已在册，本报告补参数归属与防风暴限频）；用户态 PM 服务拥有交互态状态机 + 触摸控制器电源档联动表；SDK day-one 定传感器 batching 契约（含 latency=0 逃生门）——详见 §8 清单。

## §1 触摸链路功耗账：从面板扫描到 AP 唤醒

### 1.1 触摸控制器自身的电源状态机【确定度：高（微软官方文档全文取回）】

Windows 硬件规范给 HID 触摸设备定了四档电源态（I²C/USB/SPI 三种总线同构、细节略异），是业界最完整的公开契约（[Microsoft: Touchscreen Power Management](https://learn.microsoft.com/en-us/windows-hardware/design/component-guidelines/touchscreen-power-management)）：

| 状态 | 进入条件 | 行为 | 关键数字 |
|---|---|---|---|
| **Active** | 有触点在屏，或**最近 30 秒内有活动** | 全速扫描，须满足 contact down/move 延迟要求 | 空闲判定窗 = 30s |
| **Idle** | 30 秒无活动 | **自降扫描率**省电，但仍须满足本档 down 延迟要求（首触延迟预算仍成立） | 扫描率档位由 OEM 定 |
| **Sleep / Armed for Wake** | 主机发 SET_POWER SLEEP（I²C）；或系统进 S3/Connected Standby（USB）/主机进低功耗（SPI） | **大幅降扫描率**、只认「合格活动」才拉中断唤醒；**明确要求不得因伪触乱唤醒**；本档**无** down 延迟要求 | USB 态：检出活动后须**缓冲 ≥100ms 报文**再 remote wake，防主机控制器 resume 期间丢输入 |
| **Off** | 断电 | 0 功耗；上电须在显示器初始化前就绪 | 0 |

要点：① 触摸控制器「常开扫描」不是匀速常开——**扫描率分档、按活动度迁移**是标准做法；② 首触延迟要求在 Active/Idle 两档都成立、在唤醒档豁免——「平时归零」牺牲的正是深睡态的首触延迟；③ USB 形态的**唤醒期缓冲契约**（≥100ms 报文）是「唤醒 ≠ 丢输入」的关键设计。

功耗量级：触摸控制器本身是小头——电阻屏方案 10–50mW 级、容性方案待机更低（[TouchPro 博客](https://www.touchpro.us/post/does-touch-screen-drain-battery)，确定度：低，行业博客）；对照显示面板数百 mW 级，**省电主战场从来不在触摸芯片本身，而在它牵动的整条交互链（AP 唤醒/提频/提刷新率）**。手势唤醒档的实测例：Goodix GT911 doze（手势）模式约 0.78mA，对整机待机预算 ~1mA 的设备已算贵（检索转述自 Goodix 社区讨论，无稳定 URL，确定度：低）。

### 1.2 手势唤醒：谁在低功耗域做【确定度：高（微软指南 + 触控 IC 厂商应用笔记）】

「双击亮屏/抬腕亮屏」的现役做法 = **触摸控制器/传感器在 Armed-for-Wake 档自识别手势，命中才拉一根中断线叫醒主机**：

- 微软 Wake-on-Touch 指南（Windows 11 可选特性）：OEM 与触控 IC 厂商约定单击或双击手势；命中后控制器**只发 2 帧「按下+抬起」合成报文**作「用户在场」信号，**系统只用来亮屏、不投递给 shell/应用**；若主机迟迟不来读，控制器应在厂商定超时后**自己回落低功耗态**；形态门控——翻盖合盖自动关手势唤醒，D2（armed）与 D3Cold（断电）按需切换，Win11 22H2 起设置关闭/合盖时直接给触摸设备断电（[Microsoft: Wake-on-Touch Implementation Guide](https://learn.microsoft.com/en-us/windows-hardware/design/component-guidelines/wake-on-touch-implementation-guide)）。
- 触控 IC 侧标准能力：TI 电容触摸方案「唤醒前低功耗 + 检出活动才唤醒 MCU」（[TI SLAA877](https://www.ti.com/lit/pdf/slaa877)）；Microchip PTC 把多通道并成单颗手势检测器作唤醒源（[Microchip DS00003433B](https://ww1.microchip.com/downloads/aemDocuments/documents/MCU08/ApplicationNotes/ApplicationNotes/Touch-BuiltIn-Surf-GestRecogn-Using-PTC-DS00003433B.pdf)）；专利面：低功耗扫描→手势序列判定→唤醒并解锁的完整流程在专利中成文（[US20150346903A1](https://patents.google.com/patent/US20150346903A1/en)）。
- **抬腕亮屏（raise to wake）不走触摸链**，走传感器低功耗域（见 §5.3 sensor hub）。

### 1.3 中断唤醒的代价与「唤醒 ≠ 一条 IRQ」的账

- AP 出 suspend 要**几毫秒级**（AOSP batching 文档原话 "a few milliseconds"，且要求 FIFO 留余量防这窗口溢出，[来源](https://source.android.com/docs/core/interaction/sensors/batching)）——所以**一次唤醒必须捎回一批事件**才划算，这是 batching（§5.1）与触摸事件合并的经济学基础。
- 频率实证（传感器侧同构逻辑）：240Hz 陀螺仪按 10 事件/批上报，中断从 240 次/秒降到 24 次/秒（同上来源的 FIFO 分配优先级表）。
- 触摸事件侧：Qualcomm `cpu-boost` 驱动对输入事件做 **150ms 最小间隔限频**（`MIN_INPUT_INTERVAL`），触摸滑动的事件风暴只在首事件起振一次（[cpu-boost.c](https://android.googlesource.com/kernel/msm/+/android-4.4w_r8/drivers/cpufreq/cpu-boost.c)，一手源码）。

## §2 交互起振（touch boost）：机制谱系与「及时=费电、迟=卡顿」

### 2.1 为什么必须 boost：schedutil 看不懂依赖任务【确定度：高（LWN 深度文全文取回）】

Android 渲染管线是 VSYNC 驱动的流水线：UI 线程（处理输入/动画回调/View 树遍历）→ RenderThread（取 buffer、翻译 GPU 命令、提交）→ SurfaceFlinger 合成上屏，60Hz 每帧预算 16.67ms，典型端到端 2 个显示周期、高负载 3 个周期；任何环节超预算 = 掉帧（[LWN: Scheduling for the Android display pipeline](https://lwn.net/Articles/809545)）。

症结：schedutil 按 runnable 任务的利用率选频。RenderThread 利用率 50% → 选 50% 最大频率；但它要等 UI 线程跑完才能开工（串行依赖，无并行度），结果 50% 频率下干不完 50% 时间窗的活 → **deadline 必失**。PETL/util 信号又爬得慢（内核文档直言 uclamp 的动机之一就是绕过 PELT 约 200ms 的爬坡延迟，[docs.kernel.org](https://docs.kernel.org/scheduler/sched-util-clamp.html)）。

### 2.2 三代机制演化【确定度：高（两份一手源码/官方文档）】

| 代 | 机制 | 一手证据 | 典型参数 |
|---|---|---|---|
| 1（~2014–2018，内核侧） | **cpufreq input boost**：内核输入子系统挂钩，触摸事件直接抬高 CPU 最小频率 | Qualcomm msm 内核 `drivers/cpufreq/cpu-boost.c`：输入 handler 匹配多点触屏/触控板/键盘；`input_boost_ms=40`（默认值）、`input_boost_freq`（0=禁用）、150ms 事件间隔限频；另有迁移同步 boost `req_freq = max(.dest_max × task_load/100, src_cur)`、`migration_load_threshold=15`（[源码](https://android.googlesource.com/kernel/msm/+/android-4.4w_r8/drivers/cpufreq/cpu-boost.c)） | 40ms 窗、150ms 重触发间隔 |
| 2（框架侧并存） | **POWER_HINT_INTERACTION**：框架在 userActivity 时向 PowerHAL 发交互 hint，vendor HAL 据此调频/调调度 | PMS 源码：每次新鲜 userActivity 触发 `powerHintInternal(POWER_HINT_INTERACTION, 0)`，常量值 =2（[PMS.java](https://android.googlesource.com/platform/frameworks/base/+/0ac9664a9ee2e6d1d3b68fe00c264ad94fe98966/services/core/java/com/android/server/power/PowerManagerService.java)） | 窗长归 vendor |
| 3（主线化） | **uclamp（utilization clamping）**：用户态按任务/cgroup 钳制 util 下限（boost）与上限（cap），schedutil 与 EAS 放置都读它 | 内核文档：UCLAMP_MIN=boost、UCLAMP_MAX=cap；只影响决策不改 PELT 本体；rt 默认 min=1024；cgroup `cpu.uclamp.min/max`；EAS/CAS 用它做能效放置（[docs.kernel.org](https://docs.kernel.org/scheduler/sched-util-clamp.html)） | 0–1024 |

Android 官方 jank 文档口径（检索摘要）：Pixel/Nexus 设备实现 touch boost，在触摸事件时改频率 governor 与调度器行为，避免向高时钟的慢爬坡（[source.android.com jank 系列页](https://source.android.com/docs/core/display/jank)，确定度：中——正文未能全文取回）。

### 2.3 提频 vs 迁大核 vs 组合建模的取舍

- **提频**：保延迟的最短路径，但「管线轻时最低频率远超需求，纯浪费能量」——LWN 原话称 touch boost 为 brute-force（[LWN](https://lwn.net/Articles/809545)）。社区实测反向印证：HTC 10 用户关掉 input boost 换续航（[XDA](https://xdaforums.com/t/closed-kfinally-found-the-answer-to-bad-battery-life-on-our-beloved-htc-10s-works-with-oreo.3785638)，确定度：低，社区个案）。
- **迁大核（放置）**：uclamp 在异构系统上同时影响放置——cap 后台任务偏置小核、给短交互任务抬 min 落大核高频（[docs.kernel.org](https://docs.kernel.org/scheduler/sched-util-clamp.html)）；能量效率优于盲目提频，但迁移本身有缓存冷启动代价，且 max-aggregation 聚合下与不 cap 任务同队列时失效（同源，已知限制）。BerryOS v1 单核，此杠杆 v2+ 才存在。
- **依赖任务组合建模**（学术/上游未竟路）：LWN 盘点 utilclamp 组合 util、SCHED_RT、SCHED_DEADLINE、token 传递、层级调度五案，结论是「没有开箱即用的方案，全依赖未合入上游的特性」（[LWN](https://lwn.net/Articles/809545)）——**依赖任务的延迟保证至今是开放问题，touch boost 是它的付费止痛药**。
- **预取**：起振的第三杠杆是「活来了数据已在手」（输入命中前预取资源/热缓存），它不省起振本身、省的是起振后的等待；BerryOS 侧对应 GUI-01 §2.7/2.8 的触摸分发开销教训（仓内已有，不重复）。

### 2.4 「及时=费电、迟=卡顿」的量化证据现状

- 定性机理与代价：LWN 给出完整论证（boost 窗内频率地板 >> 实际需求 = 能耗浪费；不 boost = 低负载下必掉帧）（[LWN](https://lwn.net/Articles/809545)）。
- 公开的「jank% vs mW」对照曲线**未检索到**权威数据（确定度：低）——业界各自在 perf/power 团队内部闭环，公开面只有参数化石锤（40ms/150ms/500ms 级）与社区续航个案。BerryOS 若做此对账即为人无我有（见 §8.4 验收项）。

## §3 交互态状态机：userActivity / interactive / DIM→OFF

### 3.1 两根轴：wakefulness × 屏幕策略【确定度：高（AOSP 源码全文取回）】

PowerManagerService 用 wakefulness 常量：`ASLEEP=0`（只能 wakeUp() 唤醒）/ `AWAKE=1` / `DREAMING=2`（屏保）/ `DOZING=3`（"almost asleep"，跑低功耗 doze dream，**显示屏开着但允许 AP suspend**——这正是 AOD 的框架形态）；源码明确「wakefulness 与屏幕电源态分开管理」（[PMS.java](https://android.googlesource.com/platform/frameworks/base/+/0ac9664a9ee2e6d1d3b68fe00c264ad94fe98966/services/core/java/com/android/server/power/PowerManagerService.java)）。`goToSleep()` 名不副实：先置 DOZING 走 Sandman 流程，`GO_TO_SLEEP_FLAG_NO_DOZE` 才直接真睡。

**超时与 DIM 的算术**：`DEFAULT_SCREEN_OFF_TIMEOUT = 15s`（设置未载入前的兜底）；亮屏期 = `lastUserActivity + screenOffTimeout − dimDuration`，之后 DIM 到 `+screenOffTimeout`；`dimDuration = min(最大 DIM 上限, screenOffTimeout × 比例)`——**DIM 从超时尾部按比例扣**，短超时设备自动短 DIM（同源）。

**谁挡着睡**：`isBeingKeptAwakeLocked` = `mStayOn（插电保持）|| mProximityPositive（通话贴近）|| STAY_AWAKE 型 wakelock || 亮/暗用户活动`（同源）。超时由 `MSG_USER_ACTIVITY_TIMEOUT` 驱动；就寝时按设置转 DREAM 或 goToSleep。

### 3.2 userActivity 语义细节（值得照抄的部分）

同源取回的规则：① 事件时间戳早于最近睡眠/唤醒时刻、或系统未就绪 → 拒收；② **ASLEEP/DOZING 态下 userActivity 无效**（只有 wakeUp 能翻身）；③ `USER_ACTIVITY_FLAG_INDIRECT`（间接事件）被剔出亮屏续命——防止「系统为响应用户而生的合成事件」反过来给自己续命成永动机；④ `NO_CHANGE_LIGHTS` 只记时不重置亮度（动画期间点按不闪亮度）；⑤ 输入侧入口 = `userActivityFromNative`（native InputManager 调入），即**输入分发器是 userActivity 的天然上游**；⑥ 每次新鲜活动触发 `POWER_HINT_INTERACTION`（§2.2）。事件分类 BUTTON/TOUCH/OTHER 定义在 PowerManager 侧（`IsInteractive` 公开语义 = 「清醒且可交互」，见 [Xamarin/Microsoft API 文档](https://learn.microsoft.com/en-us/dotnet/api/android.os.powermanager.isinteractive)，确定度：中）。

### 3.3 各状态允许/禁止什么（综合 §1/§3/§5 事实的对照表）

| 状态 | 输入事件 | 触摸控制器 | 渲染/显示 | 传感器 | AP |
|---|---|---|---|---|---|
| AWAKE·BRIGHT | userActivity 续命 + touch boost 脉冲 | Active | 全速管线（GUI-06 §1.4 三态之 RUN） | 随用即取，非唤醒类即可 | 活跃 |
| AWAKE·DIM | 任何活动 → 回 BRIGHT | Active/Idle | 可降载（AOD 前奏） | 同上 | 活跃 |
| DOZING（AOD） | userActivity 无效，仅 wakeUp() | Sleep/Armed（或 Off） | 面板低刷驻留（§4.2） | 仅唤醒类 + FIFO 批量 | **可 suspend** |
| ASLEEP | 仅 wakeUp()/唤醒源中断 | Armed-for-Wake（手势档）或 Off | 屏灭（PSR 链路断） | 同上 + trigger 类 | suspend |
| DREAMING | wakeUp() 结束 | Active | 屏保渲染 | 随用 | 活跃 |

## §4 显示侧补充（GUI-06 未盖的三个角）

### 4.1 触控×LTPO 刷新率联动【确定度：高（本地 OH 源码一手）】

GUI-06 §2 已盖 LTPO 面板原理与 setFrameRate/ARR/HGM 投票框架；此处补**触摸状态机如何喂帧率决策**（OpenHarmony HGM 一手源码，路径 `graphic_graphic_2d/rosen/modules/hyper_graphic_manager/core/frame_rate_manager/`）：

### 4.2 AOD 的功耗策略与实现路径

- **框架形态**：Android DOZING 态 =「屏开 + AP 可 suspend」（§3.1 源码），AOD 作为 doze dream 运行；低功耗前提 = **出帧责任移出 AP**。
- **硬件路径**：DDIC（显示驱动 IC）内建 AOD 信号发生器/独立 AOD 渲染通路，AP 睡时由面板侧自持（专利成文：[WO2023043518A1（DDIC AOD 信号发生器）](https://patents.google.com/patent/WO2023043518A1/zh)、US20250265964A1（每像素 AOD 支持的 DDIC 架构）、EP3913460（折叠机 TDDI + AOD）；SID Display Week 2022 亦有「AOD 全驻 DDIC」论文题名，无公开 URL，确定度：中）。LTPO 1Hz 档是 AOD 的刷新率地基（GUI-06 §2.1 已引 Apple Watch 1–60Hz，不重复）。
- **策略面**：仅点亮少量像素 + 1Hz 刷新 + 位移/轮换防烧屏；OEM 宣传口径：ColorOS Smart AOD 1Hz「部分场景能效 +30%」（[OPPO 官宣](https://www.facebook.com/colorosglobal/posts/smart-aods-refresh-rate-down-to-1-hz-power-efficiency-up-by-30-in-some-scenarios/1088772315102367)，确定度：中，营销数字）；消费侧实测 AOD 每小时掉电百分之一级（[MakeUseOf](https://www.makeuseof.com/i-stopped-letting-my-galaxys-always-on-display-waste-battery-without-turning-it-off)，确定度：低）。**反面**：第三方 AOD app 靠 wakelock 焬着 AP 渲染，功耗数倍于原生（同源）——**AOD 省电的本质是「渲染责任搬出 AP」，不是「画面变黑」**。
- 与 BerryOS 对接：#53 `power·mode op` 已有 NORMAL/DIM/AOD/OFF 四枚（`docs/架构决策.md:62`）；GUI-06 开放问题 5（AOD 唤醒源）本报告 §8.4 接。

### 4.3 亮度/DVFS 联动

- OLED 功耗 ≈ 点亮像素数 × 亮度，AOD/暗色省电直接吃这根杠杆（同 MakeUseOf/OPPO 语境）；LTPO 低刷档与亮度耦合（低亮度下变频保守，GUI-06 §2.1 已引，不重复）。
- **反向联动的一手证据**：OH HGM 把光照因子（LightFactorStatus）作为帧率降档输入、又被触摸票压过（§4.1）——**亮度/环境光与刷新率不是独立 DVFS 域，是一张联票**，仲裁优先级（触摸 > 光照降级 > 空闲降档）是策略服务的职责。

## §5 传感器省电：batching、trigger、sensor hub

### 5.1 hardware batching（FIFO 批量上报）契约【确定度：高（AOSP 官方文档全文取回）】

[Batching | source.android.com](https://source.android.com/docs/core/interaction/sensors/batching) 全文要点：

- 机理：事件存 sensor hub/硬件 FIFO，「AP 攒够一批才醒」；**功耗申报口径 = 数据躺在 FIFO 期间的功耗**（SoC 未醒）。50Hz 传感器 latency=0 = 每秒吵醒 AP 50 次；正 latency 才进批量。省电量 ∝ 可缓冲事件数。
- API 面：`registerListener(sensor, delay, maxBatchReportLatency)`；`fifoMaxEventCount`/`fifoReservedEventCount` 申报；采样率钳制（下限 1ms/1000Hz，静默钳到 minDelay/maxDelay 内）；精度契约 90–220%。
- **唤醒类/非唤醒类绝不共 FIFO**；唤醒类最好一颗大共享 FIFO（最省电）；on-change 传感器（如计步器）的**最新值存 FIFO 外**——文档亲述惨案：计步 1000 步被加速度计数据环形覆盖，应用以为用户没走路，唤醒后补收「1020 步」。
- suspend 语义：非唤醒类 FIFO 满则环形覆盖、latency 失效；唤醒类 FIFO 满或任一 latency 到期**硬件必须唤醒 AP**；任何一次醒来**所有 FIFO 一次性 flush**（防连环再醒）；AP 出 suspend 要几 ms，FIFO 须留余量。HAL/驱动不得持 wakelock（唯一例外：latency<1s 的唤醒连续类）。
- FIFO 分配优先级表（带目标批量时长）：行人航位推算 1–10min（唤醒类步检+低频罗盘/气压计）、间歇活动识别 3s、连续活动识别 1–3min、**中断减载 <1s（240Hz 陀螺 10 事件/批：240→24 中断/秒）**、低频监测 1–10min。

### 5.2 trigger/one-shot 传感器（significant motion 一族）

HAL 头文件定义 one-shot 模式（sampling_period 无效）与低功耗传感器语义：**SMD（significant motion detector）等唤醒类传感器的设计目标就是允许 AP 进 suspend、且不得显著推高功耗**（[sensors.h（Halium 镜像）](https://github.com/Halium/android-headers/blob/master/hardware/sensors.h)，确定度：高）；Sensors HAL 2.0 文档同口径（[source.android.com](https://source.android.com/docs/core/interaction/sensors/sensors-hal2)）。

### 5.3 sensor hub：低功耗域里的 always-on 感知【确定度：高】

- **CHRE（Context Hub Runtime Environment）**：Android 官方「nanoapp 跑在低功耗 DSP」运行时——传感器处理在 AP 睡着时继续，标准嵌入式 API，AP 只在被需要时叫醒（[AOSP: Context Hub](https://source.android.com/docs/core/interaction/contexthub)；开源实现 [zephyrproject-rtos/chre](https://github.com/zephyrproject-rtos/chre)）。Google 车祸检测即跑在 sensor hub 上（[Esper 深读](https://www.esper.io/blog/android-dessert-bites-12-sensor-hub-chre-7491376)）。
- 谱系：Android 4.4（2013）时代 QuickLogic 超低功耗 hub 已承接计步/检测等强制功能不唤醒 AP（[embedded.com](https://www.embedded.com/ultra-low-power-sensor-hub-for-android-4-4)）；**计步/抬腕/手势识别全部住在 hub/DSP 域**是十年不变的架构事实。
- 实测量级（一手 datasheet）：Bosch BMI270 全开（6.4kHz ODR 加计+陀螺）685µA，而**低功耗加计+片上计步常引约 14–18µA**（[BMI270 datasheet](https://www.bosch-sensortec.com/media/boschsensortec/downloads/datasheets/bst-bmi270-ds000.pdf)；14–18µA 为社区常引低功耗档数字，确定度：中）。

## §6 键鼠/外设唤醒（PC 线）简述

- **USB selective suspend**：按口挂起空闲 USB 设备，键盘/鼠标须厂商启用；代价 = 唤醒 resume 延迟（[Microsoft: USB Selective Suspend](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/usb-selective-suspend)）。实战病：selective suspend 让键盘丢键、与 dock/eGPU 相性差，用户批量关之（[Superuser](https://superuser.com/questions/1699367/usb-selective-suspend-causes-keyboard-to-miss-keys-and-usb-hubs-egpu-and-docs)，确定度：中，社区实证）。
- 触摸屏 USB 形态的 selective suspend + remote wake + **≥100ms 报文缓冲**契约见 §1.1（[MS 文档](https://learn.microsoft.com/en-us/windows-hardware/design/component-guidelines/touchscreen-power-management)）。
- PC 线结论：与移动线同构——**挂起要按口、唤醒要带缓冲、唤醒源要可枚举可关断**（`powercfg` wake_armed 面即「唤醒源治理」的用户面）。BerryOS PC 档照抄三件套即可：设备电源态表（D0–D3 同构）+ 按口挂起 + 唤醒期缓冲契约。

## §7 教训与历史包袱清单

1. **boost 参数散落三层**：内核 input_boost（40ms）、框架 POWER_HINT_INTERACTION、vendor HAL uclamp 策略——同一件事三本账，调优要跨内核/框架/厂商 HAL 三处（[cpu-boost.c](https://android.googlesource.com/kernel/msm/+/android-4.4w_r8/drivers/cpufreq/cpu-boost.c) + [PMS.java](https://android.googlesource.com/platform/frameworks/base/+/0ac9664a9ee2e6d1d3b68fe00c264ad94fe98966/services/core/java/com/android/server/power/PowerManagerService.java) + [kernel docs](https://docs.kernel.org/scheduler/sched-util-clamp.html)）——BerryOS「intent 单一消费轴」（ADR #43/#58）正是对它的正面回答，别再开第二本账。
2. **依赖任务的延迟保证是十年未解的开放问题**：LWN 五方案全部「没有开箱即用」（[LWN](https://lwn.net/Articles/809545)）——touch boost 是止痛药不是治愈；BerryOS 不应幻想 v1 解决，只需把「交互脉冲」语义定干净。
3. **间接事件自续命**是状态机永动机的经典坑——Android 用 INDIRECT flag 显式剔除（§3.2），晚于此设计的系统都会重新踩一遍。
4. **唤醒丢输入**：唤醒链路（USB resume/AP 出 suspend）天然有 ms 级空窗，契约要显式「缓冲 ≥N ms 报文」（Windows ≥100ms）而非事后补；传感器侧同坑 = FIFO 覆盖计步惨案（§5.1）。
5. **伪触唤醒**会毁灭待机功耗（口袋/桌面误触）——微软把「不得因伪触断言唤醒」写成硬要求（§1.1）；手势唤醒档必须配假唤醒抑制与「主机不读则自回落」超时（§1.2）。
6. **第三方 AOD 用 wakelock 焬 AP** = 省电特性的最大反面教材：**省电的是架构（渲染搬出 AP），不是像素变黑**（§4.2）。
7. **触摸票必须压过环境降级票**，否则「一摸就降亮降帧」的设备会被用户骂卡（OH 把优先序写死在仲裁代码里，§4.1）。
8. **扫描率分档**是触摸控制器省电的标准形态，但每档延迟预算不同（首触延迟只在 Active/Idle 承诺）——「平时归零」必然牺牲深睡首触延迟，要明码标价而非含糊其辞（§1.1）。
9. **uclamp max-aggregation**：capped 任务与 uncapped 任务同队列时 cap 失效（[kernel docs](https://docs.kernel.org/scheduler/sched-util-clamp.html)）——「叠加式投票」语义要预研失效模式，BerryOS 公平默认、只叠加（AGENTS 冻结项）与其同向。

## §8 BerryOS 启示：交互功耗机制清单（内核面 / 电源服务面 / SDK 面 / 协议验收面）

### 8.1 内核机制面（预留，机制不策略）

1. **交互脉冲原语**：触摸 IRQ →（inputd/display）→ 焦点窗提频衰减脉冲——设计位已在册（`docs/应用模型设计-v1.0.md:217`，~500ms 衰减、走 4-3c 策略注入面）。本报告补三条参数纪律（全部来自 §2 教训）：① **脉冲时长/衰减曲线/重触发间隔是 PM 策略服务的表项不是内核常量**（对照 Qualcomm 40ms/150ms 两值就是两张调优表）；② **重触发限频必须内置**（150ms 同构，防触摸风暴每事件烧一次提频窗）；③ 脉冲走 intent 0x02（触摸窗内偏性能提频静默回落，`docs/应用模型设计-v1.0.md:185-194` 六档表已画）——与调度/生命周期共用一个声明，禁止再造 powerHint 第二通道。
2. **userActivity 同构入口**：内核/输入服务向 PM 服务上报**分类交互事件**（TOUCH/BUTTON/KEY + 时间戳），PM 服务据此续亮屏 + 发脉冲；**INDIRECT 位 day-one 留**（合成事件不续命），NO_CHANGE_LIGHTS 同理（动画期点按不重置亮度）。GUI-4 gui-inputd 的 INTERACTIVE intent + PM 交互脉冲接线（`docs/GUI里程碑规划-2026-10-v1.0.md:94`）正是此缝，补两枚 flag 位即可。
3. **唤醒归因与记账**：WAKE_RING 已能看醒因（PM-00 §1.1 #7）；补「交互脉冲起止/合并率」遥测位（脉冲次数 vs 触摸事件数 = 限频有效性），这是 §2.4「jank vs 功耗对账」的数据底座。

### 8.2 用户态电源服务策略（PM governor/M3，策略不在内核）

4. **交互态系统状态机**（PM-00 gap 2 直答）：AWAKE(BRIGHT/DIM) / AOD / OFF 四态（对齐 #53 power·mode 四枚枚举，协议已有、系统侧迁移条件缺）——DIM 时长 = min(上限, timeout×比例) 从尾部扣（§3.1 算术照抄）；「谁挡着睡」白名单 = 插电保持/通话贴近（proximity）/持有 STAY_AWAKE 型票/亮暗活动，全部走 PM 服务票箱而非内核特权判断。
5. **触摸控制器电源档联动表**（PM-00 gap 3 外设面第一颗子弹）：状态机每态映射触摸控制器目标档（AWAKE→Active、AWAKE 无活动 30s→Idle 降扫、AOD→Armed-for-Wake 手势档或 Off、OFF→Off）；驱动契约 = 档位申报 + 手势下载 + **假唤醒抑制** + **主机不读自回落超时**（§1.1/§1.2 微软契约直接抄）。加形态门控位（合盖/口袋态关手势唤醒）。
6. **触摸状态机进显示服务**（OH 实证形状）：IDLE/DOWN/UP + 抬手超时（OH 取 3s，可策略化）作为帧率投票输入；**仲裁优先级表**：触摸票 > 光照/亮度降级票 > 空闲降档票 > 应用票面（OH :1241-1259 行为背书）；抬手后 LTPO 首周期拉满窗（OH 1000ms 同构参数位）。
7. **提频×提帧率联合脉冲**：一次交互脉冲同时喂 PM 服务（频率档）与显示服务（刷新档），**同源单脉冲**——防「提了频没提帧」或两处各提各的（安卓三本账教训 §7.1）。
8. **AOD 出帧路径**：AP 睡 + 面板/显示服务低功耗驻留出帧（maintenance 0x05 已是 #42 第一个真实消费者）；AOD 内容更新窗/烧屏位移协议位开给面板服务（§4.2），GUI-06 开放问题 5（AOD 唤醒源）在此闭环：**AOD 态唯一常态唤醒源 = 触摸手势档 + 唤醒类传感器**。

### 8.3 SDK 契约（day-one 定对，v1 无 fork = 无 retrofit 机会）

9. **传感器 batching API 全套**（§5.1 契约逐条翻译）：订阅参数 = `{采样周期, maxReportLatency}`；flush() 显式冲刷；**唤醒类/非唤醒类两通道**（不共 FIFO）；`fifoMax/fifoReserved` 能力申报；**on-change 最新值存批缓冲外**（计步覆盖惨案）；maxReportLatency=0 = 即到即派逃生门（对齐 `docs/GUI里程碑规划-2026-10-v1.0.md:94` 已留位）——「省电换延迟」必须写成显式合同让开发者选边。
10. **交互延迟预算申报**：帧预算表（`docs/应用模型设计-v1.0.md:219-223`）补**功耗列**（PM-00 gap 8 直答）——每个交互环节两列并排（ms + 期望能耗档），SDK 文档把「提频窗=费电换响应」明码标价。
11. **传感器 hub 域 API 预留**：v1 无 hub 硬件也要把「传感器消费者」标在案的接口留出版本域（本地处理 vs AP 上报），CHRE 形状（nanoapp/低功耗域常驻）为 v2+ 参考靶。

### 8.4 协议位与验收（QEMU 可验部分）

12. **能耗代理断言扩展**：既有「IDLE 唤醒计数 0 + icount≈0」smoke（ADR #53）之上，加两条交互功耗断言：① **触摸风暴合并率**（N 事件/150ms 窗 → 恰 1 次脉冲）；② **AOD/IDLE 态合成事件不续命**（INDIRECT 位测试用例）。真机功耗计未选型前（PM-00 gap 6），QEMU 只验这些软件纪律——但它们正是 §7 四条教训的机器可查形态。
13. **guiproto 协议位**：触摸状态机事件（DOWN/UP/超时）与 vote 仲裁优先级字段进 berry-guiproto 版本域（add-only）；power·mode op 四枚已全，勿动。
