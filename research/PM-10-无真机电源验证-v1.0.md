## §0 一页结论（TL;DR）

1. **业界无真机电源验证 = 三层**：软件纪律层（pm_test/suspend_stress_test/emulator 注入——能进 CI）、契约层（PSCI/virtio/OASIS/OH HDI——接口先于实现冻结）、物理量层（µA 计/ODPM/gem5+McPAT——无真机时只能代理或离线，**不进门禁**）。三层没有一家把「功耗绝对值」做成无真机 CI 门禁。
2. **QEMU/TCG 定谳**：`target/arm/tcg/psci.c` **未实现 SYSTEM_SUSPEND（0x8400000C），CPU_SUSPEND 永远只是 WFI**（源码注释原话 "Powerdown is not supported"）；KVM 侧 2022 年起支持。BerryOS 仿真里「深睡」没有物理面，断言只能打在**协议调用与记账**上——这正是铁律 11 的业界同构。
3. **挂起类 bug 二跑才炸是官方背书的规律**（pm_test 文档建议每级测两次）；ChromeOS 把挂起压测做成**状态计数器递增断言**（不是功耗断言）——两条直接可抄进 smoke。
4. **契约先行有四个硬先例**：PSCI fnid 冻结于 ARM 规范（BerryOS `smp.rs:790` 已在消费）、virtio 设备 ID/feature bits 由 OASIS 规范分配且 add-only、ACPI 表先于 SoC、OH HDI battery 接口按 IDL 版本目录冻结。**模拟设备与真机共用同一接口**（goldfish battery → HAL 同构）是「仿真绿 ≈ 真机绿」的唯一保证。
5. **BerryOS 现在就能落**：9 条电源断言（§4.1）挂进 G0–G5 smoke 既有通道（WAKE_RING/bench-icount/RX 注入相/pwrcls 毒环），外加 sim-battery/sim-thermal/sim-modem 三设备契约草案（§4.2）。µA 计量/LTPO/弱信号真跑明确押后真机期（§4.4）。

## §1 主线与机制全景

### 1.1 三层模型：无真机验证到底在验什么

| 层 | 验证对象 | 业界样板 | 能否无真机 CI | BerryOS 对应 |
|---|---|---|---|---|
| 软件纪律 | 状态机/记账/归因/合并行为做对没 | Linux pm_test、ChromeOS suspend_stress_test、Android emulator 注入 | 能（本文主战场） | G0–G5 smoke + soak（§4.1） |
| 契约 | 接口/协议位与实现对齐没 | PSCI、virtio/OASIS、ACPI、OH HDI | 能（冻结动作，非运行时断言） | sim-* 设备契约 + PSCI 探测表（§4.2/4.3） |
| 物理量 | µA/°C/mW 真实数值 | 功耗计、ODPM、gem5+McPAT | 不能进门禁（§1.7） | icount 代理（ADR #53）+ 真机期清单（§4.4） |

**业界没有反例**：没有任何一家在仿真器上断言「功耗低于 X mW」。断言形态永远是「计数器/状态/协议行为」，功耗绝对值要么真机测、要么模型离线估。【高】

### 1.2 Linux：pm_test 五级累进 + 调试基础设施【高】

来源：内核官方文档（[basic-pm-debugging](https://www.infradead.org/~mchehab/kernel_docs/power/basic-pm-debugging.html)，docs.kernel.org 同文镜像）。

| 设施 | 内容 | 关键细节 |
|---|---|---|
| `/sys/power/pm_test` | 五级挂起切片：`freezer → devices → platform → processors → core` | 需 `CONFIG_PM_DEBUG` 编译；`platform` 级仅 ACPI 系统有意义；`core` = 不建 hibernation image 的最深测试 |
| 测试纪律 | 自 freezer 逐级试到 core，**每级至少测两次** | 官方原话 "some problems only show up on a second attempt"；某级失败则更深层必失败 → 对失败级以下做驱动二分 |
| `suspend.pm_test_delay` | 每级停留秒数 | 默认 5s |
| `PM_TRACE` | 挂起失败点回溯 | **仅 x86**（用 RTC 存储 magic） |
| `test_resume` | hibernation 镜像恢复测试 | 独立于 pm_test |
| `/sys/power/suspend_stats` | 挂起失败统计（debugfs） | 记录最后 2 个失败设备 + 失败步骤（`last_failed_step`）——**运行时取证位，非事后调试器** |
| `/sys/power/state` + `mem_sleep` | 触发挂起；`s2idle/deep` 模式选择（[sleep-states 文档](https://docs.kernel.org/admin-guide/pm/sleep-states.html)） | 写文件触发，天然脚本可驱动 |

结构性事实：pm_test 验的是**内核自己切片执行挂起路径**，不依赖固件真的下电——这就是「无真机测软件纪律」的原型。但 Linux 的 PM 功能测试大头（kselftest power_management、挂起真深眠）仍在真机 CI 上跑（§1.3）。

### 1.3 kernel CI 里的 PM 测试跑法【中-高】

KernelCI 官方文档（[docs.kernelci.org/tests](https://docs.kernelci.org/tests)、[device-tests](https://docs.kernelci.org/tests/device-tests)）：CI 侧优先把测试贡献进**树内 kselftest**（`tools/testing/selftests/`，[kselftest 文档](https://docs.kernel.org/dev-tools/kselftest.html)），KernelCI 的 lab 全是**真机**池子跑非破坏性子集；挂起/电源类需要 root 与真实固件配合。结论：Linux 没有「TCG 里测挂起」的通道——QEMU 上游 CI（patchew/qemu-ci）也不跑 guest 挂起测试。**无真机挂起验证在 Linux 生态是空白，BerryOS 在这块是「人无我有」的机会位而非补课。**【中】

### 1.4 ChromeOS：suspend_stress_test = 状态计数器断言【中-高】

源码在 `chromiumos/platform2/power_manager/tools/suspend_stress_test`（[代码](https://chromium.googlesource.com/chromiumos/platform2/+/main/power_manager/tools/suspend_stress_test)）：循环执行挂起（`/sys/power/mem_sleep` 选 s2idle），每轮用 `get_s2idle_count()` **求和内核 s2idle residency 计数器并断言递增**，配 `memory_check` 选项校验挂起往返内存不被破坏；用法见 [ChromiumOS 文档 "Suspend and Memory stress testing"](https://www.chromium.org/chromium-os/testing/power-testing/)。

**这是挂起 CI 化的最佳样板**：断言不是「功耗低」而是「①计数器按预期 +1 ②resume 后系统仍活 ③内存完好」——全部状态谓词，零竞速。BerryOS 挂起/冻结循环断言直接抄这个形态（§4.1 第 2 条）。

### 1.5 Android：模拟器电源注入 + CTS 契约面【高（命令）/中（顺序坑）】

Android Emulator 本身 = **QEMU fork 加 goldfish 自有设备族**（battery/sensors 等）——官方模拟器的电源面就是「厂商 fork QEMU 加电源模拟设备」，这是 BerryOS 加 sim-battery 的直接先例。【高】

- **注入通道**：emulator console（[官方文档](https://developer.android.com/studio/run/emulator-console)）`power ac on|off`（AC 状态）、`power status`/`power display`、电池侧 `power capacity <n>` 等——AC 通断、电量百分比、健康状态全部脚本可注入 = CTS/开发者测试的电池场景输入源。
- **顺序坑**【中】：社区经验中先切 `ac` 再设 `capacity` 可能不触发预期的充电事件——注入接口有状态机顺序敏感。教训：sim-battery 注入应**原子快照**（一次寄存器写带全字段，见 §4.2），不给顺序留缝。
- **CTS 验的是契约不是功耗**：power_profile.xml（[AOSP power 文档](https://source.android.com/docs/core/power)）的组件 mA 值是**归因模型**不是计量——假表问题已在 PM-05 §2.8/:120 取证（AOSP 默认值是明知错误的占位数），此处只引结论：**仿真注入值必须与真机计量 ABI 同源，否则仿真绿毫无意义**。
- goldfish battery 与真机走**同一个 battery HAL 接口**——模拟设备先行不阻碍真机对齐，反而把接口契约提前钉死。【高】

### 1.6 QEMU/TCG 能力面（源码实证）

#### PSCI 实现矩阵（`target/arm/tcg/psci.c`，master 实读【高】）

| PSCI 功能 | fnid | TCG 现状 | 备注 |
|---|---|---|---|
| PSCI_VERSION | 0x84000000 | 返回 1.1 | |
| CPU_ON | 0xC4000003 | 支持 | BerryOS `arch/aarch64/src/smp.rs:790` 已消费（S-0 钉板 HVC conduit） |
| CPU_OFF | 0x84000002 | 支持 | |
| CPU_SUSPEND | 0xC4000001 | **降级为 WFI** | 源码注释："Powerdown is not supported, we always go into WFI"——参数校验后直接 `HELPER(wfi)` |
| SYSTEM_OFF/RESET | 0x84000008/09 | 支持 | 走 `qemu_system_shutdown_request`（异步请求）+ 立即 cpu_off 满足「PSCI 规定不返回」 |
| **SYSTEM_SUSPEND** | **0x8400000C** | **未实现** | 落入 default → `QEMU_PSCI_RET_NOT_SUPPORTED`；`PSCI_FEATURES` 查询同样报不支持 |
| KVM 侧 | — | **2022 年起支持**（guest 调用 → VM 挂起事件上报用户态，[补丁序列 v5/v6 lists.infradead.org](https://lists.infradead.org/pipermail/linux-arm-kernel/2022-April/)） | 【高：patch 在册；精确合入版本号未核】 |

结论：**同一份 guest 代码将面对三档现实——TCG 无 / KVM 有 / 真机固件有**。软件必须走 `PSCI_FEATURES` 探测分支，并把能力表打进 boot 遥测（§4.3）。

#### WFI 语义与唤醒源【中-高】

- TCG 下 WFI = vCPU halt 等中断（事件驱动，不烧宿主 CPU，也不省任何电）；KVM 下 halt 注入由宿主调度。语义上「WFI 期间零指令执行」在两种加速器下都成立——**这正是 icount 能当能耗代理的理论基础**（下条）。
- **virt 板挂起无唤醒源**：QEMU virt 没有 wakeup controller，系统挂起后没有标准机制注入唤醒事件（社区 issue 在册）——想在仿真里测「挂起→唤醒」往返，必须自带可注入唤醒线的自定义设备（= sim 设备正当性之一）。【中-高】

#### icount 虚拟时钟 = 能耗代理的边界【高】

QEMU 官方文档（[TCG Instruction Counting](https://www.qemu.org/docs/master/devel/tcg-icount.html)、[record/replay](https://www.qemu.org/docs/master/system/replay.html)）与 2015 年补丁序列（[icount sleep 参数](https://lists.gnu.org/archive/html/qemu-devel/2015-06/msg01875.html)、[新虚拟时钟](https://lists.gnu.org/archive/html/qemu-devel/2015-06/msg01874.html)）：

- icount 模式下**虚拟时钟 = 已执行指令计数的函数**，与宿主钟完全解耦 → 确定性可复现（record/replay 的基石）。
- `sleep=on`（默认）：guest 睡 N 虚拟纳秒，虚拟时钟精确推进 N，宿主侧快进——**idle 时长也被确定性记账**，WFI 睡眠的虚拟时长可断言。
- 官方明示 **instruction counting ≠ cycle-accurate**：只有相对量可用（同二进制前后对比、回归门禁），绝对值无意义。
- 与 BerryOS 对接：ADR #53 已定「IDLE 唤醒计数 0 + icount ≈0 进 smoke」（`docs/架构决策.md:62`）；B-2 bench-icount 的独立基线 + `--prove` 五跑烘焙 + 跨机不可比纪律（`docs/规则/07-测试与冒烟.md:42`）正是业界边界意识的仓内落地。icount 漂移面判例 A109（`规则/07:58`）已覆盖。

#### 加自定义模拟设备的路径【中】

1. **fork QEMU 加 virtio 设备**（goldfish 先例，§1.5）——BerryOS 可控 QEMU 版本（smoke 已钉场），代价最小。
2. **virtio 规范留了实验/厂商段**：OASIS virtio 1.2 规范 §5 Device ID 表（实读，[规范 HTML](https://docs.oasis-open.org/virtio/virtio/v1.2/csd01/virtio-v1.2-csd01.html)）标准设备 1–42（1=net、2=blk、16=GPU、18=input、26=fs…）；512–1023 实验 / 1024+ 厂商自定义段（附录分配规则，【中】）；新标准 ID 走 virtio-dev 邮件列表分配（[virtio-fs ID 26 保留例，virtio-spec issue #31](https://github.com/oasis-tcs/virtio-spec/issues/31)）。BerryOS 自有 ABI **无需上游分配**，但必须 day-one 冻结 + add-only（与 #53 同构）。
3. guest 侧 virtio-mmio 通路现成：rootfs 相已在跑 virtio-blk/net（`docs/规则/07-测试与冒烟.md:22-23`），驱动框架零新增。

### 1.7 仿真级能耗建模：gem5+McPAT 的量级与边界【中-高】

- 组合本身是学术界标准流：gem5 产生架构统计 → McPAT 解析式估算 power/area/timing（[gem5 官方讨论 #980](https://github.com/orgs/gem5/discussions/980)）。
- **精度短板公开在案**：gem5 官方演示自认 full-system 场景 McPAT 有 "large errors"；文献指 McPAT 偏 CPU 实现（GPU/加速器失真）；gem5 内建 DRAMPower（真实内存事务时序）反而比架构估算准（[gem5 架构探索演示](https://old.gem5.org/Publications.html)、[Extensible Power Modeling in gem5](https://old.gem5.org/Publications.html)）。
- **速度量级**：full-system 时序仿真约 250 KIPS（2026 年 [Rigorous Full-System Timing Simulation](https://arxiv.org/) 论文引述）——比 QEMU TCG（~10^8 inst/s 级）慢约 3 个数量级，**模拟几秒执行需月级**。
- **判决**：gem5/McPAT 进 CI 门禁不可行（速度与精度双杀）。合法用途 = G5/DVFS/EAS 设计期的**离线设计空间探索**（单点实验、论文级对比），v1 完全不引入。BerryOS 的 CI 能耗面就是 icount 相对量代理——ADR #53 已裁对，无需 revisiting。

### 1.8 契约先行先例（四个硬证据）

| 先例 | 契约形态 | 冻结早于实现的表现 | BerryOS 可抄点 |
|---|---|---|---|
| PSCI（ARM DEN 0022） | fnid + 语义冻结于规范 | 一份 OS 代码对固件/KVM/TCG 三家（含「不支持」的合法回答） | `PSCI_FEATURES` 探测表 + 能力进 boot 遥测（§4.3） |
| virtio（OASIS TC） | Device ID + feature bits 分段 + add-only | 规范先行，设备后造；实验段允许先跑后标准化（ID 26 例） | sim-* 设备 ID day-one 冻结 + 版本域（§4.2） |
| ACPI（UEFI 论坛） | 表契约（_S0W/_PSD/S-state）【中】 | OSPM 一份代码对万机，表由固件提供 | 「描述先于实现」——电源域拓扑表化 |
| OpenHarmony HDI（[drivers_interface 仓](https://gitee.com/openharmony/drivers_interface)） | IDL 按版本目录冻结（battery v1_0/v2_0…；[Battery V1_2 文档](https://docs.openharmony.cn/)：IBatteryInterface 获取/订阅/回调 Register，起始版本 3.1【中】） | 南向硬件差异被接口版本吸收，模拟实现与真机实现同接口 | sim-battery 字段面对齐真机 battery 驱动契约（§4.2） |

黄金律（四例同构）：**模拟设备与真机共用同一 guest 侧接口契约，仿真绿才有传递性**。goldfish battery → battery HAL、OH HDI battery IDL → 真机驱动，都走了这条路。

## §3 教训与坑

1. **「二跑才炸」是挂起类 bug 的官方规律**（事实 2）↔ 仓内 A110 flake 双证（`规则/07:59`）。落法：冻结/挂起循环断言至少两轮，且判据是状态谓词非竞速（A32，`规则/07:51`）。
2. **层级依赖做门禁**：pm_test 失败级以下必失败 ↔ G0–G5 分层爬升同构。电源断言也要分层：先记账断言（醒因可归因），再行为断言（合并/下电调用），最后才是（真机期的）物理量。跳层断言必然 flake。
3. **计数器断言 ≠ 功耗断言**：ChromeOS 断 residency counter 递增 + 系统活 + 内存完好，不断 µA（事实 4）。仿真器里永远只有前者——把代理量当物理量是这一域最大的自欺。铁律 11（QEMU 只能验软件纪律，`pm-notes/00:127`）的业界同构。
4. **注入接口的顺序契约**：emulator 电池注入顺序敏感（事实 7）——状态机型被注入对象（充电状态机）对字段写入顺序有依赖。落法：sim-battery 用**原子快照寄存器组**（一次写带全部字段）+ 版本号递增，宿主脚本侧禁止多写拼装。
5. **注入回声与竞速的电源版**：唤醒风暴注入的事件流不能 grep 注入回声自证（A79，`规则/07:57`）；「无主唤醒=失败」断言必须等系统达稳态再取记账（首事件裕量，A129，`规则/07:66`）。
6. **icount 绝对值不可用**：非周期精确 + 源码零改动也会漂（A109，`规则/07:58`）——能耗代理门禁只用「同机同二进制 L2 紧门禁 + 五跑烘焙」形态（`规则/07:42`），不引入新形态。
7. **标称 µA 与实测差 5–15 倍**（事实 16）：深睡电流连同芯片真机板级都测不准标称——仿真里谈论 µA 是双重无意义。day-one 把「物理量只在真机测」写进验收纪律，防止未来有人往 smoke 里塞假功耗数。
8. **模拟设备必须与真机共用契约**（§1.8 黄金律）：若 sim-battery 走仿真专用分支接口，仿真绿对真机零传递性——goldfish→HAL 同构是唯一正确姿势。
9. **平台特定取证设施的教训**：PM_TRACE 仅 x86（事实 3）——挂起失败取证位（suspend_stats 同构）要 day-one 进协议/遥测，不能等 debug 需求出现后按平台打补丁。BerryOS 的 WAKE_RING + suspend_stats 同构位应在第一支电源 smoke 断言里就位。
10. **上游没有免费午餐**：QEMU/TCG 不实现 SYSTEM_SUSPEND、virt 板无唤醒源（事实 9/11）——等上游补齐是死路；自己造 sim 设备（fork QEMU 或实验 ID）是业界常规（goldfish 先例），且 BerryOS 钉场自带 QEMU 版本，风险可控。

## §4 BerryOS 启示与落法清单

### 4.1 现在就能进 G0–G5 smoke 的电源断言（九条）

| # | 断言 | 判据（状态谓词） | 通道 | 业界样板 | 现状 |
|---|---|---|---|---|---|
| A1 | **IDLE 稳态零唤醒** | 稳态窗内 WAKE_RING 醒因计数=0 ∧ icount≈0 | telemetry WAKE_RING + bench-icount | Weston 十年按需重绘（ADR #53 引） | ADR #53 已立法（`docs/架构决策.md:62`），断言待落 |
| A2 | **冻结循环压测** | N≥2 轮 freeze/unfreeze：token 计数严格递增 ∧ pages 稳态窗 ∧ 末轮全量标记在席 | sched-1.1 `kernel/src/suspend.rs` + smoke 新相 | suspend_stress_test 计数器断言（事实 4） | 调度 1.1 收尾期可挂 |
| A3 | **唤醒风暴注入→合并率** | 注入 K 个 ε 邻近超时，实测唤醒 ≤ ⌈K/M⌉（M=合并窗） | fw_cfg/QMP 注入 + 记账 | timer slack 机制位（`docs/调度器设计-v1.0.md:155`） | 需先落唤醒合并机制位 |
| A4 | **无主唤醒=失败** | 稳态窗内每条醒因可归因到持有者 pid；未知/无主醒因 → FAIL | WAKE_RING 归因面 | Linux wakeup source 归因同构 | 需 PM-00 落地刀 1（内核 wakeup 记账面） |
| A5 | **维护窗攒批对齐** | AOD/maintenance 0x05 窗内任务执行计数 ≥ 阈值 ∧ 窗外唤醒计数=0 | intent 六档 + 记账 | Doze 维护窗同构 | 待 berry-power/M3 前的窗内调度策略 |
| A6 | **触摸风暴合并率** | RX 注入风暴事件 → 事件合并率 ≥ 阈值（合并后分发次数/注入次数） | RX 注入相扩展（`规则/07:23`） | 输入节流/touch batching | gui-inputd 落后可挂 |
| A7 | **停帧→交互起振延迟** | IDLE→首帧延迟 ≤ 1–2 帧预算，进遥测非门禁 | GUI 遥测 | `docs/GUI里程碑规划-2026-10-v1.0.md:82` | 协议位在册 |
| A8 | **电源类别毒环** | 非法 lease/power·mode 请求被拒 + 记账不腐蚀 + 连续毒环后系统活 | B4 掉电相扩展 | pwrcls 毒环先例（`规则/07:23`） | 现成通道，加注入样本即得 |

全部九条都是**软件纪律断言**，无一条触碰物理量——与三层模型（§1.1）一致，G0–G4 期间即可分批挂进。

### 4.2 sim-battery / sim-thermal / sim-modem 契约草案（virtio 或 MMIO 私有槽）

共同骨架（三设备同构，day-one 冻结 + add-only）：

| 区 | 内容 | 说明 |
|---|---|---|
| 身份区 | magic + 版本域 + 能力位图 | 版本域学 OH HDI IDL 版本目录（事实 15）；能力位图 add-only 学 virtio feature bits（事实 13） |
| 快照区 | **原子快照寄存器组** + 序号（每次宿主写全量替换，guest 轮询序号） | 防注入顺序坑（§3 坑 4） |
| 事件区 | FIFO + doorbell（变化事件：AC 插拔/温度越 trip/信号档变化） | 唤醒线可接 IRQ——**补 virt 板无唤醒源的结构洞**（事实 11） |
| 计量区 | energy_uj / temp_mC / soc_pct 假设值 | **与 PM-05 meter_query ABI 同源**（`research/PM-05-v1.0.md:167`）——真机期硬件 ODPM 直采换数据源不换 ABI |

设备分则：

| 设备 | 快照字段（对齐业界契约面） | 可断言什么 | 契约对齐来源 |
|---|---|---|---|
| sim-battery | {ac_online, status(charging/discharging/full), capacity_pct, health, voltage_mV} | 电量阈值触发的降档/省电模式迁移；充电事件→策略响应；低电告警链 | goldfish battery + OH IBatteryInterface 字段面（事实 6/15） |
| sim-thermal | 多虚拟传感器 {temp_mC, trip 点表} | 越 trip → 热策略响应（限 lease/降频 hint 投票）；滞回防抖 | thermal trip 契约通例【中】 |
| sim-modem | {尾能时长档, 信号档, RRC 状态} | 维护窗攒批对齐（A5）；无租约时 broker 下电调用发生 | PM-05 §4.5 已裁（`research/PM-05-v1.0.md:198-203`），本文补注入通道 |

实现路径：fork 钉场 QEMU 加 virtio 设备（goldfish 先例，事实 6）或 virtio-mmio 私有槽 + 实验/厂商 ID 段（事实 13）；宿主注入走 QMP（与 gui8 qmp_inject 同通道，`规则/07:23`）。**铁律：guest 侧驱动即未来真机驱动契约层——仿真专用分支禁止进主线。**

### 4.3 PSCI/挂起契约的三档现实处理

| 档 | SYSTEM_SUSPEND | BerryOS 行为 |
|---|---|---|
| TCG（主验场） | NOT_SUPPORTED（事实 9） | boot 期 `PSCI_FEATURES` 探测 → 能力表进遥测；深睡请求走「优雅降级 = 冻结循环（A2）」路径并断言降级事件在册 |
| KVM | 支持（事实 10） | 真深睡路径代码在 KVM 相可测（非 CI 主线） |
| 真机固件 | 取决于 SoC | 同一探测分支，零改软件 |

现有 `smp.rs` 的 HVC conduit + S-1 分型门（事实 18）已证明「一个 conduit 多档现实」的处理模式，SYSTEM_SUSPEND 探测是同型扩展。CPU_SUSPEND 在 TCG 下即 WFI——A1 的零唤醒断言正好覆盖其唯一语义。

### 4.4 真机期才补的验证清单（day-one 写进验收纪律：物理量不仿真）

| 项 | 为什么仿真不可能 | 真机期动作 |
|---|---|---|
| µA 级功耗计（深睡电流） | 标称与板级实测差 5–15 倍（事实 16），仿真无物理面 | SoC 选型时配功耗计里程碑（`docs/路线图-v1.0.md:143` 已有位） |
| ODPM/rail 直采 | 硬件计量器 | 换 meter_query 数据源（ABI 不变，§4.2） |
| LTPO/panel PSR 真实帧率档 | panel 物理特性 | GUI-06 开放问题接续 |
| 弱信号真跑（RSSI 衰落/切换） | 射频环境 | sim-modem 档位值用真机数据回标 |
| 温升-DVFS 耦合 | 热时间常数物理量 | G5 期真机标定 |
| gem5/McPAT 离线建模 | 速度差 3 个数量级 + large errors（事实 14） | 仅 G5 设计期离线实验，永不进门禁 |

### 4.5 明确不做

- 不往 smoke 塞任何「功耗绝对值」断言（§3 坑 3/7）。
- 不为深睡做 TCG 假实现（假装挂起成功）——宁可断言 NOT_SUPPORTED 降级路径（§4.3）。
- 不引入 gem5/McPAT 进 CI（§1.7 判决）。
- 不等 QEMU 上游补 SYSTEM_SUSPEND/唤醒源（§3 坑 10）。
