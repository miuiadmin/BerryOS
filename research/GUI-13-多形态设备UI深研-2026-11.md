# GUI-13 多形态设备 UI 深研（2026-11）

> **定位**：回答用户提出的 BerryUI 多形态问题——手机、平板、全面屏、手表、电脑、电视、汽车是否共用一个 UI 框架，应该在哪些层自适应，哪些层分化。本文是一轮研究与 P5+ 路线草案，不改变现行 [GUI框架地基路线-v1.20.md](../docs/GUI框架地基路线-v1.20.md)，不新增运行时代码。
>
> **二轮追记（2026-11-11）**：用户要求“别急着下结论”后，[GUI-14-多形态UI二轮对抗深研-2026-11.md](GUI-14-多形态UI二轮对抗深研-2026-11.md) 发现 SYSTEM role/layer 权限、`surface_id=0`、damage 越窗、AVOID_SYS buffer 合约与配置事件等高置信阻塞。本文仍是形态矩阵与工业证据基线，但其中 P5a/P5b/P6/P7 执行排序不再是当前施工权威。
>
> **触发**：用户在 P4 Window Policy Matrix 后提出：“我们的 UI 框架要考虑多形态……平板、全面屏、手表、电脑、手机、电视、汽车。”
>
> **基线**：GUI 线已落地 F0..F9、C1、P0..P4。P0 已冻结 Surface role/mode、input class、IME composition、a11y sidecar、safe area 与 scale；P2 已打通 Keyboard；P3/P4 已打通 pointer focus 与基础窗口策略。

## §1 执行结论

1. **“全面屏”不是一个设备形态，而是一组跨形态显示约束**。打孔、刘海、圆角、曲面、手势区、状态栏、电视 overscan、车载异形屏，最终都应该进入 safe area / display shape / gesture region 这类宿主授予的显示约束，而不是派生 “FullScreenDevice” 枚举。

2. **多形态要拆成四个不同问题**：

   ```text
   显示有多少可用空间       → window/form metrics
   用户用什么输入           → interaction/input profile
   系统允许什么窗口策略     → window policy
   使用场景有什么约束       → usage policy
   ```

   只做 `if device == watch` 会把布局、输入、安全、功耗和窗口策略耦合成一团。

3. **正确架构仍是“一个系统契约 + 一个 BerryUI core + 多形态组件集”**。这与 ADR #67 的“一个契约，三条路径”一致：

   ```text
   Berry Session / Berry Room：跨形态系统契约
   BerryUI core：树、布局、状态、主题、命中、a11y
   form packs：touch / desktop / watch / tv / automotive 组件集
   Canvas / Immersive：专业与游戏逃生门
   ```

4. **自适应有三层，不能互相替代**：

   ```text
   responsive：同一组件树随可用约束重排
   adaptive：按 size class / posture 换布局与导航壳
   capability：按输入、显示、功耗、安全能力换交互形态
   ```

   手机竖屏翻转是 responsive；手机→平板 list-detail 是 adaptive；触控→D-pad/遥控/旋转冠是 capability。

5. **逻辑度量必须来自宿主，不允许 app 猜**。物理分辨率、DPI、safe area、scale、display shape、fold posture、driver distraction state 都应由 gui-wmd/guifbd/系统形态服务授予或推送。app 只能收到结构化 `FormMetrics`，不能扫描设备名或硬编码品牌。

6. **P0 的协议地基方向正确，但 BerryUI 尚未消费完整**。`SurfaceGrant` 已有：

   ```text
   scale_permille
   safe_left/top/right/bottom
   input_classes
   ime_mode
   a11y_mode
   ```

   但生产授予值当前仍是 `safe=0,0,0,0` 与 `scale_permille=1000`；普通 BerryUI `WidgetContext` 也仍按物理 viewport 选择 `Compact/Product` 两档，safe area 未成为通用 `SafeArea` 容器。多形态下一刀应先把宿主真值做实并接进 UI core，而不是先做手表/车机样例。

7. **导航与焦点是跨形态核心，不只是桌面/电视需求**。手机需要返回栈；平板需要 list-detail；PC 需要 sidebar/菜单/快捷键；TV 需要 D-pad 焦点；手表需要极短栈；车载需要任务级浅层导航。P2/P3 已有系统键盘与窗口焦点，但 BerryUI 还缺组件级 focus traversal 与 adaptive navigation shell。

8. **IME/文本编辑是所有触摸形态的前置**。手机和平板靠软键盘，PC 靠硬件键盘+候选窗，电视可外接键盘/遥控输入，车载偏语音和受限输入。P0 已有 composition 帧，但 IME Host 仍未生产化；这会阻塞真实文本 UI。

9. **手表、电视、汽车不能靠“缩小/放大手机 UI”解决**。三者分别由功耗/一瞥性、10-foot focus/遥控、驾驶安全/多显示主导。它们需要 form pack，而不是把 phone widget 拉伸。

10. **不要空授能力**。P0 词表中 Gamepad 仍无生产者，IME Host 仍无服务；同理，未来 `Remote`、`Rotary`、`Voice`、`MultiDisplay`、`DriverDistraction` 也不能只加协议词就宣称支持。没有真实生产者/服务时继续 `ST_UNSUPPORTED`。

## §2 用户列举形态的准确归类

| 用户说法 | 归类 | 主导约束 | 不应固化为 |
|---|---|---|---|
| 手机 | 设备形态 + compact touch profile | 单手/双手触控、safe area、软键盘、返回栈、低功耗 | 所有 UI 默认手机唯一形态 |
| 全面屏 | 显示约束 | 打孔/刘海/圆角/手势区/状态栏 | `FullScreen` 设备枚举 |
| 平板 | window size class + touch/stylus/keyboard | medium/expanded、list-detail、多任务、分屏 | 放大版手机 |
| 折叠屏 | posture + window resize | 展开前后状态保持、铰链区、双屏/大屏 | 单一静态分辨率 |
| 手表 | micro form + power/interaction profile | 小屏、圆屏、AOD、一瞥交互、旋转冠/触摸 | 缩小手机 |
| 电脑 | desktop form + pointer/keyboard/windowing | 多窗口、resize、菜单、hover、快捷键、多显示器 | 平板放大 |
| 电视 | TV form + remote/focus profile | 10-foot 视距、D-pad、大字、高对比、overscan | 大号手机 |
| 汽车 | automotive form + safety policy | 驾驶分心限制、多屏、语音、旋钮、日夜模式、乘客屏 | 平板装车上 |

结论：设备名可以用于设计和沟通，但不能成为 API 的第一真值。API 的第一真值应是可用窗口度量、输入能力、窗口策略和使用策略。

## §3 主流系统的收敛模式

### 3.0 本轮子研究核证的关键事实

Android window size class 的当前官方阈值：

```text
width
  Compact     <600dp
  Medium      600..839dp
  Expanded    840..1199dp
  Large       1200..1599dp
  Extra-large >=1600dp

height
  Compact     <480dp
  Medium      480..899dp
  Expanded    >=900dp
```

官方理由是竖向滚动普遍存在，多数应用先看 width class；height class 对视频、阅读、全屏等高约束场景的价值是本文推断。

Apple HIG 当前按平台给出强差异：iPhone Duo 折叠机外屏 compact、内屏 regular， poses 包含 book、tabletop（半折平放）、standing，铰链占用内容空间，内屏可多显示一层列表/详情层级；macOS 以菜单栏、可记忆位置的自由窗口、精确指针和快捷键为中心；watchOS 交互通常小于一分钟，Digital Crown/complication/通知比完整 app 更常用；tvOS 明确要求拥抱焦点系统，焦点就是导航；visionOS 区分 Shared Space 与 Full Space，窗口是可在空间中重定位的 plane。

Flutter 核证到三个 API 细节：`MediaQuery` 后来追加 `sizeOf/paddingOf` 等 aspect-scoped 订阅，避免任一字段变化导致整树重建；`SafeArea` 会消费 padding 并向下重作用域，嵌套不双扣；大屏网格建议按 max cross-axis extent 推导列数，而不是硬编码“平板 N 列”。

Compose 核证到“layered adaptive”规则：在 app 根部一次性计算 window size class，显式向下传；嵌套组件使用局部约束，不读全局设备尺寸。list-detail 的跨档状态保持也有明确语义：收窄时保留 detail、隐藏 list；放宽时恢复双栏并标出当前选择。

Qt 核证到 per-window `devicePixelRatio`：窗口跨显示器移动时 DPR 跟随变化；高层 API 全走 device-independent pixel，物理像素只在低层渲染/资产选择出现。

WinUI 的 effective pixels 把视距折进缩放：1080p 电视在 10 英尺视距下可归类为 small screen。其响应式断点为 small <640、medium 641..1007、large >=1008 epx，缩放档 100%..400%，基础栅格以 4 epx 倍数组织。这是把 TV 并入统一密度模型的第二工业参照。

OpenHarmony ArkUI `GridRow/GridCol` 默认断点：

```text
默认断点：320vp / 600vp / 840vp → xs/sm/md/lg
扩展断点：追加大阈值（如 1080vp）后才出现 xl/xxl
```

子项可按断点声明 span/offset/order。600/840 与 Android/Compose 重合，说明基础三段已是事实工业线。

### 3.1 Apple：同一应用生态，多套形态规范

Apple 的公开设计体系长期按设备分册：iOS、iPadOS、macOS、watchOS、tvOS、visionOS、CarPlay。它不是让同一控件视觉在所有设备上硬拉伸，而是共享开发范式与系统能力，再按形态给不同布局、导航、输入与安全规则。

可借鉴模式：

```text
iOS：safe area、size class、触控目标、返回/标签导航
iPadOS：多任务、分屏、更大 canvas、键盘/指针辅助
macOS：多窗口、菜单、停靠、hover、快捷键
watchOS：小屏、complication、AOD、极短交互
tvOS：焦点导航、10-foot 排版、遥控
CarPlay：驾驶安全模板与受限交互
```
visionOS：Shared Space 多窗口并置、Full Space 独占、窗口作为可重定位 plane，以及 immersion/comfort 边界

参考入口：

```text
https://developer.apple.com/design/human-interface-guidelines/layout/
https://developer.apple.com/design/human-interface-guidelines/
```

对 BerryOS 的启示：可以共享 BerryUI core，但 watch/TV/car 必须各自有 form pack 与设计规范；不能把 phone Scaffold 当万能壳。

### 3.2 Android：window size class 与设备专用 API 并存

Android 大屏方向的核心不是“平板枚举”，而是 window size class / window metrics：按当前窗口可用宽度高度分类，再决定 list-detail、导航栏、双栏等布局。手机分屏也可以进入 compact/medium 类别，折叠展开则触发窗口状态变化。

Wear、TV、Auto 另有专用设计 guideline 与 API 面：

```text
Wear：小圆屏、AOD、功耗预算、腕上交互
TV：D-pad/遥控焦点、10-foot UI、大字与高对比
Auto：驾驶安全、模板化交互、语音、多显示
```

参考入口：

```text
https://developer.android.com/develop/ui/compose/layouts/adaptive/support-different-screen-sizes
https://developer.android.com/guide/topics/large-screens
https://developer.android.com/training/wearables
https://developer.android.com/training/tv
https://developer.android.com/cars
```

本仓 GUI-06/GUI-10 已直证 Wear AOD 的低功耗规则：AOD 内容需更暗更简、少动；Wear OS 官方 always-on 指南给出 on-pixel 与更新频率类约束。这些应作为 watch form pack 的预算参照，而不是写死进全局 UI core。

### 3.3 Flutter：adaptive 与 responsive 分层

Flutter 的跨平台策略把“响应式布局”和“自适应设计”区分开：

```text
responsive：LayoutBuilder/MediaQuery 按约束重排
adaptive：按目标平台/输入/窗口形态选择组件与导航
```

同一 core 可以跨 iOS/Android/desktop/web，但平板双栏、桌面菜单、触控目标、鼠标 hover、键盘快捷键仍需要显式适配。Flutter 还有 CustomPainter/Texture/PlatformView 这类逃生门，对应 Berry 的 Canvas/Immersive。

参考入口：

```text
https://docs.flutter.dev/ui/adaptive-responsive
https://docs.flutter.dev/ui/layout/
```

对 BerryOS 的启示：不要把 adaptive 做成散落在 app 的 `if width > N`；应提供 `AdaptiveSlot` / `ListDetail` / `NavigationShell` 这类可测试结构。

### 3.4 Jetpack Compose：window metrics 进布局体系

Compose Adaptive 的价值在于把 window size class 变成一等布局输入，而不是让 app 手算像素。典型模式：

```text
compact：单栏 + 底部/顶部导航
medium：窄 list-detail 或可折叠导航
expanded：持久导航 + list-detail + 内容详情
```

Material 3 Adaptive 的具体先例是 `NavigationSuiteScaffold`（按 size class/posture 在 bottom bar 与 navigation rail 间切换）和 `ListDetailPaneScaffold`（双栏/list-detail 状态保持）。输入与窗口焦点仍由平台层处理。

参考入口：

```text
https://developer.android.com/develop/ui/compose/layouts/adaptive
```

对 BerryOS 的启示：BerryUI 需要把 `WindowSizeClass` 放进 `WidgetContext`/`AdaptiveContext`，并让布局 dump 输出所选分支，便于 host 测试。

### 3.5 Qt / QML：桌面专业件与高 DPI 的成熟参照

Qt 长期服务桌面、嵌入式与车载。它的经验是：

```text
高 DPI、多屏幕、窗口策略由平台层统一；
QML/Widgets 组件形态分化；
专业桌面控件与移动声明式控件不强求同一套；
嵌入式设备可裁剪。
```

参考入口：

```text
https://doc.qt.io/qt-6/highdpi.html
https://doc.qt.io/qt-6/qml-qtquick-window.html
```

对 BerryOS 的启示：未来 desktop/pro form pack 可以共享 BerryUI core，但停靠面板、树表、命令面板、属性编辑器应是另一个组件集，不应塞进 F4 移动组件。

### 3.6 React Native / Web：约束式响应的对照

React Native 明确区分 `window`（当前可见 app window）与 `screen`（物理设备屏幕），并警告不要缓存 dimensions——依赖尺寸的渲染必须每次读取；`useWindowDimensions` 会在尺寸或 fontScale 变化时更新。Web 侧则以 flex/grid/container query 表达同类约束。这证明“窗口约束”与“设备能力”必须分层，且 metrics 是动态状态而非启动常量。

参考入口：

```text
https://reactnative.dev/docs/dimensions
https://developer.mozilla.org/docs/Web/CSS/CSS_container_queries
```

对 BerryOS 的启示：容器级约束比全局屏幕尺寸更稳；折叠分屏、多窗口、PC resize 都会让“同一屏幕上不同 surface 拥有不同窗口尺寸”。

## §4 七类形态的设计矩阵

### 4.1 手机（phone / compact touch）

目标：

```text
单手优先
触控目标足够大
safe area 正确
软键盘与文本编辑可用
返回栈清晰
低功耗停帧
```

窗口策略：

```text
默认一个主 app surface
系统 overlay/status/navigation 区域
可选分屏/浮窗
```

输入：

```text
Touch 一等
Keyboard 可选（外接/远程）
Mouse 可选
IME Host 必需
```

布局：

```text
compact width
单栏
栈导航
底部/顶部 tab
列表→详情 push
```

Berry 现状：

```text
P0 safe area/scale 已有
P2 Keyboard 已有
P3/P4 focus/window 基础已有
BerryUI phone 组件已可运行
IME Host 未落地
SafeArea 容器未通用化
```

优先级：**v1 主战场，最高**。

### 4.2 全面屏 / 异形屏（display constraints）

这不是独立设备，而是显示约束：

```text
打孔/刘海
圆角
曲面边
手势区
状态栏
导航栏
电视 overscan
车载异形屏
```

应统一为：

```text
safe insets
display shape / mask
gesture exclusion region
optional rounded-corner radius
```

P0 已有四向 safe inset 与 scale。缺口：

```text
BerryUI 未自动消费 safe area
没有 SafeArea widget
没有圆屏/异形 mask 语义
手势区排除仍无协议面
```

建议：P5 先落 `SafeArea` 与逻辑度量；display shape/mask 等真实设备需求到来前只做规格预留，不空实现。

### 4.3 平板 / 大屏 / 折叠屏（medium/expanded）

目标：

```text
同一 app 状态在 compact/medium/expanded 间迁移
避免空白放大
支持键盘、鼠标、stylus
支持多任务/分屏
折叠状态保持
```

布局：

```text
compact：单栏
medium：窄 list-detail / 可展开导航
expanded：持久 sidebar + list-detail
内容网格列数随窗口约束变化
```

窗口策略：

```text
窗口 resize
min/max size
aspect ratio
split screen
fold posture
```

Berry 现状：

```text
WM 有几何设置与 z/hide/show
P4 证明基础窗口策略
但缺 host-driven configure/resize 事件
缺 window state preservation
缺 fold posture
```

优先级：**v1 后半段到 v2 初期高**。

### 4.4 手表（micro / watch）

目标：

```text
1 秒内可读
一瞥即离
AOD 极低功耗
极浅导航
小屏/圆屏布局
```

窗口策略：

```text
单 surface
无普通多窗口
系统 overlay/complication 特权
```

输入：

```text
touch 可用但目标极简
rotary/crown
button
voice/手机代理
```

布局：

```text
micro size class
中心内容
圆屏 inset/shape
极少量文本
complication/grid 信息密度
```

功耗：

```text
active：短交互
ambient：低亮度/低刷新/低 OPR
off：保留极小唤醒面
```

Berry 已有协议优势：

```text
present 协议更早已预留 power mode / frame intent / damage
P0 要求 Retained/Canvas/Immersive 三路径都继续遵守这些契约
GUI-06/GUI-10 已研究 AOD 规则
```

缺口：

```text
round display shape
complication 契约
ambient content tree
rotary/crown input class
watch form pack
```

优先级：**架构能力保持可落，产品化后置**。与 ADR #39 一致：手表是低功耗同族端，不是 v1 主战场锚点。

### 4.5 PC / 桌面（desktop）

目标：

```text
多窗口
精确指针
键盘快捷键
```

## 5.1 已经做对的部分

| 资产 | 多形态价值 |
|---|---|
| P0 Surface role/mode | 普通/专业/游戏三路径不分叉系统契约 |
| input classes | Touch/Stylus/Mouse/Keyboard/Gamepad 语义位 |
| IME composition 帧 | 未来手机/PC/TV 文本输入协议地基 |
| a11y sidecar | 语义旁车可服务屏幕阅读器、AI、自动化 |
| safe area + scale_permille | 全面屏/异形屏/DPI 的宿主真值雏形 |
| frame intent / power mode | 手表 AOD 与低功耗 UI 的关键协议缝 |
| P2 Keyboard | PC/TV/平板输入基础 |

## 5.2 主要缺口

### G1 FormMetrics 缺失

当前普通 BerryUI 主要知道：

```text
viewport physical width/height
Density::Compact/Product
```

不知道：

```text
logical width/height
host scale
safe inset 是否已消费
window size class
orientation/posture
form pack
input profile
display shape
```

建议新增 BerryUI 侧纯数据：

```text
DisplayMetrics
WindowMetrics
FormProfile
InteractionProfile
UsagePolicy
```

先由 Berry Room 从 `WM_GETINFO + SurfaceGrant` 组合构造，不急于扩 wire。

### G2 Size class 未定义

建议逻辑单位：

```text
1 lp = physical_px * 1000 / scale_permille
```

初始 width class：

```text
Micro        width < 220 lp，Berry 自定义 watch/glance 档
Compact      220..599 lp
Medium       600..839 lp
Expanded     840..1199 lp
Large        1200..1599 lp，词表预留，v1 可暂不消费
Extra-large  >=1600 lp，词表预留，v1 可暂不消费
```

600/840/1200/1600 与 Android live table 对齐；`Micro <220` 是 Berry 为 watch/glance 自加的低档，不冒充工业共识。

初始 height class：

```text
Compact    height < 480 lp
Medium     480..899 lp
Expanded   >= 900 lp
```

注意：

```text
以 safe 后可用窗口为准
以当前 window 为准，不以整屏为准
v1 消费 width-only；height class 先冻结词表，视频/阅读/全屏刀再消费
TV 的视距可进入 effective scale，使 1080p/10ft 逻辑宽度接近 small/compact
Auto 不因宽度大而自动 Expanded；由 UsagePolicy/template 覆盖
```

### G3 SafeArea 未成为 UI 结构

P0 有静态 safe inset，但 app/组件仍容易直接把 viewport 当可用区。多形态需要把 inset 分成两类：

```text
padding：持续遮挡——状态栏、打孔、圆角、铰链、TV overscan、手表曲边
viewInsets：瞬时遮挡——软键盘、候选条、临时系统面板
```

应有：

```text
SafeArea 容器：消费 padding，向下重作用域，嵌套不双扣
KeyboardAvoider：消费 viewInsets，只影响文本/滚动区域
SafeScope 查询：组件可读取剩余 inset
布局 dump：显示 safe 前/safe 后两套 bounds
edge-to-edge：允许内容画到系统 chrome 下，但交互/文本必须避让
```

Flutter `SafeArea` 的消费语义与 Android 15 强制 edge-to-edge 方向共同说明：safe area 不是可选美化，而是多形态布局输入。

### G4 Theme density 只有二档

`Density::Compact/Product` 是当前 QEMU 与产品手机的良好起点，但多形态需要：

```text
scale_permille 驱动 token 换算
Micro/TV/Auto 字号档
dark/high-contrast/day-night 主题
动态字级/无障碍缩放
```

当前字体供给仍是少量固定 bitmap 档（A2 分页属于容量策略，不是任意缩放排版）。PC 大屏、TV 10-foot 和无障碍放大最终需要可缩放文本路径或更细字阶资源；这应随 P5/P6 研究，不应在 app 内私自缩放位图。

### G5 Navigation 未成体系

当前 app 多为手写 `page_index` 和 Back 按钮。多形态需要统一：

```text
Route/Stack
Back policy
Tab/Rail/Sidebar 选择
ListDetail 双栏状态保持
焦点恢复
窗口 resize 后状态保持
```

### G6 Focus traversal 缺失

P2/P3 是系统级键盘路由与窗口焦点，不是 BerryUI 组件焦点。PC/TV 需要：

```text
FocusScope
focus order
focus ring
arrow traversal
activation
escape/back
scroll into view
a11y focused state 同步（批量传输未落地前先本地/单帧验证）
```

### G7 输入词表不完整

P0 已有 Touch/Stylus/Mouse/Keyboard/Gamepad。多形态未来还会需要：

```text
Remote/D-pad
Rotary
Voice intent
```

但必须等真实生产者/服务出现再开放，不能空授。既有输入面还有两类未 completeness：

```text
multitouch / ABS_MT / pinch-zoom：当前单 pointer_id
keyboard polish：auto-repeat、布局映射、销毁 release 合成、LED/statusq
```

a11y sidecar 也只有单记录 codec，批量传输/订阅仍未开放；P6a 的 focused state 不能静默假设传输面已存在。

### G8 Host-driven window configure 与配置变更通知缺失

当前 `WM_SET` 主要由 client 请求几何。PC/平板还需要：

```text
host resize
move
min/max/aspect
maximize/restore
raise/lower
multi-display migrate
configure/ack 状态协商
```

另一个结构性问题是 `WM_TABLE_WAIT` 当前单车位主要被 inputd 占用；app 没有独立的 geometry/visibility/density change 通知面。BerryUI 已有 `set_viewport()`，但 Room 尚未在 resize/rotate/posture 变化后重入调用它。P7 必须把“配置变更事件”作为宿主真值链设计，而不是让 app 轮询屏幕。

### G9 文本与 IME 未生产化

没有软键盘和文本编辑，手机/平板/PC 的多形态都无法产品化。P0 composition 帧已是对的，下一步需要 IME Host 服务与 BerryUI text field/focus/cursor/selection。

### G10 Form pack 尚未分层

不能把 watch/TV/car 组件全部塞进 F4 组件集。应有：

```text
berry-ui core
touch pack
desktop/pro pack
watch pack
tv pack
automotive pack
```

具体 crate 分裂与否可后定，但 API 与测试边界先分。

## §6 推荐 Berry 多形态模型

## 6.1 四个档案，不做一个大枚举

```text
DisplayMetrics
  physical size
  logical size
  scale_permille
  safe insets
  refresh policy
  display shape/mask（未来）

WindowMetrics
  window id/surface id
  logical bounds
  size class
  orientation
  posture/fold state（未来）

InteractionProfile
  available input classes
  active input modality
  pointer precision
  hit-target policy
  focus navigation style
  text input strategy
  gesture/rotary/remote capabilities

UsagePolicy
  form pack hint
  viewing distance class
  distraction restriction
  power/AOD policy
  allowed content density
```

落地为 per-surface `SurfaceEnvironment`：

```text
logical_size
physical_size
scale_permille
size_class
padding[4]
view_insets[4]
font_scale
input_modalities
display_features[]   // hinge/fold/posture 预留，可为空
```

订阅必须 aspect-scoped：

```text
size 变化 → 只失效布局依赖
padding/view_insets 变化 → 只失效 SafeArea/KeyboardAvoider 依赖
input modality 变化 → 只失效交互形态依赖
```

Flutter `MediaQuery.of` 初期整对象订阅造成重建风暴、后补 `sizeOf/paddingOf` 的历史，是 BerryUI retained tree 必须避开的坑。

分离理由：

```text
同一汽车中控在不同驾驶态 UsagePolicy 变化
同一平板接键盘后 InteractionProfile 变化
同一 app 分屏后 WindowMetrics 变化
同一设备旋转后 DisplayMetrics/WindowMetrics 变化
```

`active input modality + hit-target policy` 是 macOS HIG 的重要教训：桌面基础密度仍为指针/键盘优化，手触摸同一屏幕时触控目标放大。也就是说，密度不是设备静态属性，而是“当前输入模态 + 视距 + scale”的投影。

## 6.2 权威归属

```text
gui-wmd：窗口、焦点、z、input class 路由、窗口几何真值（显示几何自 guifbd present GETINFO 缓存）
guifbd：显示模式、帧率/功耗、显示物理几何与未来 density/refresh 真值
inputd：设备发现与事件生产
Berry Room：向 app 组合安全 FormMetrics
BerryUI：消费 metrics，不猜设备
app：声明页面语义与业务状态
```

禁止：

```text
app 读设备名
app 自算全局 DPI
app 自报 safe area
app 绕过 input class
form pack 复制第二套布局/主题/焦点引擎
```

## 6.3 组件层形态包

```text

  tree/layout/state/theme/hit/a11y/text/focus seams

  Scaffold/AppBar/List/Card/Tab/Swipe/TextField
```

## §7 P5+ 建议路线

## P5：Display Metrics & Form-Adaptive Host Truth

P5 必须分两段推进；只写 BerryUI 层会把“宿主真值”伪装成 UI 推断。

### P5a 无 wire 变化的宿主真值先行

前置 0：落地第一个真实 SYSTEM-layer 窗口：

```text
系统 top-bar / overlay 以 System role 创建
wmd 由 SYSTEM 窗口有效几何推导 APP 窗口 safe inset
0x67 授予帧继续使用既有 safe 字段，不改 wire
```

没有这一步，“非零 safe inset fixture”不可实现。P1 已允许 surface 重协商；过渡期可用 pull-based renegotiation：SYSTEM 窗口出现后 app 重新 `configure_surface`，新 grant 携带 inset。该 SYSTEM surface 原语同时也是 P6b 软键盘 UI 的宿主。

前置 1：把现有 density heuristic 移到宿主侧：

```text
800×600 debug      → scale 2000
1080×1920 product  → scale 3000
策略单源放 host/wmd 侧，BerryUI 只消费 grant
```

今天 `scale_permille=1000` 会让 1080px 物理宽被误判为 Expanded；必须先有宿主 scale 源，才能谈 size class。

实现：

```text
Berry Room 组合 WM_GETINFO + SurfaceGrant 成 typed metrics
BerryUI WidgetContext::from_grant
SafeArea 容器与 padding/viewInsets 语义
布局 dump 输出 size class 与 safe 后 bounds
Room 在 fixture/poll 变化时重入 ui.set_viewport
```

P5a 验收：

```text
800×600 @2x
1080×1920 @3x
600×900 logical medium fixture
840×600 logical expanded fixture
真实 SYSTEM 窗口产生非零 safe inset
同一 ViewSpec 布局分支 golden
```

说明：medium/expanded 两项在 P5a 是 host 纯函数/合成 grant fixture；若要在 guest GUI8 证明，需为测试几何扩展宿主 scale 表，或等 P5b display metadata，不得让 app 自报 scale。

### P5b Display Metadata Add-Only 协议

P5a 的几何启发式不能区分同尺寸手机/显示器，也不能表达 PC @1x、refresh、多显示。P5b 需要版本化 add-only display metadata：

```text
scale/density source
display id
refresh interval
rotation
future viewing-distance/form profile
```

自然归属是 guifbd present display 域，由 wmd 中继/缓存，避免第二显示真值。`@1x` 也要求 BerryUI 增加 `Density::OneX` 或最小密度档；该档归 P5b，不得让 P5a fixture 悄悄依赖。

P5b 验收：

```text
1920×1080 @1x PC fixture
density/refresh round-trip 与拒面
窗口跨显示迁移时的 scale 变更事件（可与 P7 push 合并验收）
```

### P5/P7 配置变更边界

```text
P5：Room→ui.set_viewport 重入 seam，可用 fixture/poll 验证
P7：host→app configure/push 事件
```

`WM_TABLE_GET` 当前可 per-session 拉快照；`WM_TABLE_WAIT` 单车位被 inputd 占用是 push 面限制，不是轮询面缺失。

## §9 明确不做 / 后置

1. **不做每设备一套 UI 全栈**。那会复制输入、IME、主题、a11y、焦点税。
2. **不做单一万能控件集**。phone Scaffold 不应硬撑 TV/手表/专业桌面。
3. **不让 app 自报设备形态**。设备名不可靠，分屏/多窗/外接显示器会立刻失效。
4. **不把全面屏做成设备枚举**。它是 safe area/shape/gesture 约束。
5. **不空授 Remote/Rotary/Voice/Gamepad/IME 能力**。无生产者继续 fail closed。
6. **不先做手表/车机样例再补地基**。先 FormMetrics、SafeArea、Navigation、Focus、IME。
7. **不把 P0 Canvas/Immersive 逃生门变成跨形态逃逸口**。所有形态仍必须经 Berry Room 契约。
8. **不在本报告直接改 Surface wire**。P5 应先穷尽 `WM_GETINFO + SurfaceGrant` 组合；确需新增宿主字段时走 add-only/versioned 协议刀。
9. **v1 不建模跨设备连续性**。Handoff/Sidecar/分布式流转/投屏属于多设备会话迁移，不是单设备 FormMetrics 问题；在 form pack 与生命周期契约稳定前只保留“不烧死单屏、单进程、单显示”的约束。

## §10 对“现在该做什么”的直接回答

当前最合理的下一刀不是手表、电视或车机，而是：

```text
P5 Display Metrics & Form-Adaptive Host Truth
```

原因：
