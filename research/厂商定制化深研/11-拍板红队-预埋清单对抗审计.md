## §0 摘要（一屏版）

- **总判断：A 档 16 项中 15 项成员资格维持、0 项否决，但 8 项须修改表述或拆分、1 项降档（V11）、2 项应并档（V8→V12、V15→V13）**；10 号的分档骨架（三类代价机制）成立，败在**计价时点**与**两处事实前提**（§1）。
- **结构性修正一（分档判据混同「代价机制」与「计价时点」）**：BerryOS 现无任何在野件——SDK-2 §八立法原文「v1 确定不外发……**无在野包，改格式零成本**」（:16/:111-112 直核）。机制 I 的「全量重打包/账本迁移」代价只在过闸后发生。真死线不是「v1 现在」，而是五道闸：**闸 A** SDK 外发反转/首个第三方 .bap 在野（SDK-2 §八关门触发器）｜**闸 B** SDK-2 开刀（账本/索引首实现合入）｜**闸 C** OTA/签名格式开刀｜**闸 D** P8 真机/首 OEM 接触窗（10 号硬闸，维持）｜**闸 E** handoff/boot 结构冻结点。§3 给 16 项逐项闸位——A 档全部项的死线都落在 v1 窗口内或其边缘，故档位不降，但排期语义从「现在一律做」改为「各自闸前必做」。
- **结构性修正二（两处事实前提错误，行号级证伪）**：①**V1「收格式不消费=零行为漂移」不成立**——svcmgr（appd 雏形）对 `app/*.bap` 收集槽**全量拉起**（`user/bins/svcmgr/src/main.rs` :1884/:1954-1955；应用规范 :203「appd 扫描全量拉起」两源），parser 的 `ty != b"app"` 拒收是 type 的**唯一闸门**；parser 放行 `"driver"` 而不同刀给 svcmgr 加过滤 = driver 包开机被当应用拉起。②**V10「reserved 区切两个具名槽」前提错误**——`BerryHandoff` v1 = 128B 头全字段分配，仅 `_r0@52`/`_r1@124` 两个 4B 对齐保留位（`kernel/src/handoff.rs` 偏移表直核），**不存在 32+16B 的 reserved 区可切**；正确机制 = 头部追加字段 + `HANDOFF_VERSION` bump v1→v2 + 双侧镜像同步（结构自身纪律明文「扩字段 = bump version」）。
- **结构性修正三（僵尸件独立判定，比 10 号 §5.1 自认更窄）**：真死重不是签名链字段位（V2–V5 是 1 行级保险且跟版执法有真实消费面），而是三件**工程件**：V11 的「词表校验器保留段断言」（现役闭集硬拒之下增量≈零）、V14 的单源生成器（两实例不配 abi.toml 式五面单源，08 号 §7-5 自认「四面里有一面半是人写的」）、V16 的 docs_guard 审计扩展（06 号 §7-12 工具置信题）。三者均拆出/降档，登记与文档行保留。
- **对主会话的一句话**：10 号清单**可采**，但须按 §6 裁决表执行 8 处修改 + 1 处降档 + 2 处并档 + D 组补登 2 件（mkimage 件 4 密钥分区预留槽、OTA §7.5-① 槽身份绑定句——后者使 V7 后半从「新动作」转「已兑现」）；#82 附录落库前本表为内容校核单。

## §1 审计总纲：三条结构性发现

### 1.1 计价时点：机制 I 的代价是「过闸后才计价」的

10 号 §1.1 的三类代价机制（在野格式 break / 双侧同步扩散 / 文档纪律漂移）作为**分类学**成立；红队攻击点在它隐含的**计价时点**：「错过 = 全量重打包」把代价描述成随时间匀速累积的债，而实际是**阶跃函数**——在野件为零时，改格式的成本 ≈ 重跑一次 `just build-user`（SDK-2 §八 :16 原文「无在野包，改格式零成本」是仓库自有立法，两源：同文件 :111-112 关门触发器「外发决定反转 / 首个第三方 .bap 在野——先到即关门」）。因此：

- 「A 档 = 必须 v1」**作为集合**成立（§3 将证明 16 项死线全在 v1 窗口内或边缘——SDK-2 开刀、OTA v2+、P8 都在视野内）；
- 但「A 档 = 现在一律做」**作为排期**不成立：V4/V5 挂在未开工的 SDK-2 上（10 号 §5.2-1 自认「纸面定稿→推倒重对」风险），现在写与闸 B 前写成本相同；V9 的 manifest.txt 至今零消费者（grep 直核：仅 `tools/mkimage.py` :23/:73 自产自弃，「侧产物，不进盘」）。
- **辩护（真辩）**：10 号把全清单压进 v1 有一个真实收益——**排期免疫**。「各自闸前必做」要求每刀开工前核对清单，漏一刀就是静默破面（35/39/38 口径打架的生成机制正是「下次再对」）。因此红队不建议把 A 档拆散降级，只建议**给每项钉闸位**（§3），把「A 档」从时间承诺改写为「闸前承诺」集合。V16 登记表正是这个语义的执法面——这 rescued 了 V16 的登记表半件。

### 1.2 「零行为漂移」类论断须过消费面核验

10 号的仓库抽查停在**词表/常量层**（berry-manifest 行号、mkimage 行号），没下到**消费面语义**。两处翻车：

- **V1**：svcmgr 收集槽全量拉起（`main.rs` :1884 `name.starts_with("app/") && name.ends_with(".bap")` → :1954-1955「收集槽全量拉起」→ :5491 `berry_manifest::parse` 后按 manifest 启动）。parser 是 type 唯一闸门 → 放行即漂移。**修法见 §2-V1**。
- **V10**：`kernel/src/handoff.rs` 偏移表 assert（`size_of::<BerryHandoff>() == 128`）+ 字段注释 @0–@124 逐位分配，无成片保留区。SEC-1 §5 day-one 1 的原始表述是「预留缝」，09 号 §1.6 把它演绎成「reserved 区分格」，10 号照抄——三级转写把「追加字段」写成了「切保留区」。**机制描述必须改**，否则落库者会去找一个不存在的区。

附带发现（同源方法）：mkimage 还有 **件 4【SEC-7】MBR 密钥材料分区预留槽**（16MiB、type 0xDA，`tools/mkimage.py` :26-28 直核）——与 V6/V10 同属信任面 day-one 留缝，**10 号 D 组漏登记**（§4-D）。

### 1.3 僵尸 schema 风险：比 10 号自认的更窄，且位置不同

10 号 §5.1 自认三条过度设计嫌疑（签名链五字段位 / product 骨架+生成器 / V16 审计）。红队独立判定：

- **签名链字段位（V2–V5）不是死重**——即使 BerryOS 永远单一 OEM：`platform_compat` 是跟版执法（D2 判据）的数据面、`last_revision/cert_status` 是 D1–D4 的原始数据、`oem-system` 是白名单对账的准入凭据（09 号 §2.3-2 三个机器判据全读它们）。单一 OEM 场景这些字段**照常消费**，僵尸化的只是 `kind ∈ {odm}` 一个枚举值（1 行注释的事）。09 号 :399 原文自身也倾向预埋（「此时应为『未来多 OEM』预埋而非为当下设计」——10 号 §5.1-1 引用时略去了这半句倾向，红队补正）。
- **真死重在工程件**：V11 校验器断言（闭集硬拒已达成其全部目标，§2-V11）、V14 生成器（两实例 × 手写可守；abi.toml 单源的价值在 37 号 × 5 面的规模，08 号 §7-5 自认「有一面半是人写的」）、V16 审计脚本（16+7 行的表动用 docs_guard 重炮；06 号 §7-12 工具置信题：审计器自己错了谁负责）。三者共同特征：**为「防漂移」再造一个会自己漂移的机制**。拆分/降档后，A 档总工作量从 10 号自报的约 15–21 人日修正为约 14–19 人日（V13 按 5–8 日计，§2-V13），量级不变、重心右移到构建面。

## §2 逐项攻击 V1–V16（三问 → 终判）

> 每项格式：①过度设计？②设计有错？③代价失真？→ **终判 + 一句理由**。最晚时点统一在 §3 表给，此处不重复。

### V1 manifest `type` 词表加 `"driver"` 位 —— **修改后通过**

- ①不过度：`"driver"` 是 v2 既定议程（驱动模型 §6 词表注 + 驱动包示例 manifest `type = "driver"` 直核两源），词表位 add-only 是真预埋；僵尸风险低。
- ②**设计有错（实质）**：「收格式不消费零行为漂移」被证伪——svcmgr 收集槽全量拉起（§1.2），parser 放行 `"driver"` 而 svcmgr 不过滤 = driver 包开机被当应用拉起（行为漂移 + APP_SLOTS 计数被占——现役 9/9 恰满，`justfile` :315-317 注释直核）。**修法**：同刀给 svcmgr 启动批加「`type != "app"` 不收集」过滤（约 3 行 + smoke 断言）；「mkapp 镜像常量同步」改为「mkapp **收面**收 driver（结构合法）但**产面**不同步」——`tools/mkapp.py` :333 `type 仅 "app"` 门禁维持拒产，待 [hw] 节 schema 立法（刀 B）再开产面。否则出现无 [hw] 节的合法 driver 包，刀 B 时这批包语义悬空（W4 抽查证实此点载荷性，§4-B）。
- ③代价失真（小）：「词表 1 行 + 头注 + 常量 + 测试 ≈ 半日」漏了 svcmgr 过滤与 mkapp 收/产面拆分决策 → **约 1 日**。
- **理由**：预埋真实且便宜，但「不消费」的零漂移承诺必须由消费端过滤兑现，且产面开口须押后到 [hw] 立法。

### V2 distribution 域 `platform_compat = [min,max]` 键位 —— **通过**

- ①不过度：单一 OEM 也消费（D2 编队判据读它）；缺省语义「不写即 [1,∞)」使 v1 全部存量包零迁移。
- ②设计基本对，两处补强：a) **双 revision 字段纪律**——`abi_revision`（事实，双轨 §二已立法自动打戳）与 `platform_compat`（承诺）同住 distribution 域相邻位，**必须在 #59/#77 同一节写明分工与单一定义源**，否则就是下一个「35/39/38」三口径（章程「35」vs abi.toml「37」是现役实证，三源直核）；b) `[1,∞)` 的 ∞ 须落为可编码语义（上界缺席 = 无界，或 u16 哨兵值），TOML 数值写不出 ∞——留给 ADR 一行。
- ③代价「1 小时」成立。
- **理由**：1 行键位买「外发后免全量重打包」保险，唯一义务是把与 abi_revision 的关系立法进同一节。

### V3 `[security]` 域 integrator lineage 字段位 —— **修改后通过**

- ①中度嫌疑：系统件 manifest 的 integrator 键消费面待证——签名者身份已在 `.sig` 信封 `lineage_id` 回声（SDK-2 §三直核），boot 对账读的是**产品包**（09 号 §2.3-2「白名单签发者 lineage == 本镜像系统树的产品包 lineage」）。若消费面只有白名单对账，键只需进产品包（V8），系统件 manifest 的第三键近冗余。**修法**：键位照留（1 行便宜），但 #77/#83 拍板时必须给**消费面清单**（谁在何时读 manifest 的 integrator），列不出即降为产品包专属键——防僵尸键落册。
- ②**设计有错（漏项）**：现役不变量是「`profile`/`key_lineage` **两键齐备或齐缺**」（berry-manifest :31 头注 + 收尾裁断直核）；加第三键必须重立法不变量（三键齐备？integrator 独立可选？）+ mkapp 侧 `SEC_RE` 镜像同步（berry-manifest :478 头注「SDK-1a 词表/值域……镜像」）。10 号「parser 键槽 1 个 ≈ 半日」没算这两笔。
- ③代价：半日 → **约 1 日**（不变量重立法 + 双侧镜像 + 七拒测试）。
- **理由**：字段位该留，但不变量重立法与消费面清点是预埋本身的组成，不是后续。

### V4 信任账本 `anchor_type` 加 `oem-system` + 条目四字段 —— **通过**

- ①不过度（§1.3 已辩：字段位在单一 OEM 场景照常消费）；09 号 :399 自认的「≤3 家无意义」只打击 `kind` 的 {odm} 值，不打击整包字段。
- ②设计基本对，一处须单一化：`cert_status` 在 09 号 §2.4 落**账本条目**、§3.1/§3.2 的写者却是「平台（**索引端**状态迁移）」——账本与索引两处 cert_status 有双写漂移风险。**修法**：#77 落册时定「`cert_status` 事实源 = 签名索引，账本条目不存或只读回显」；`last_revision` 同理（写者 = 平台签发索引时，09 号 §3.1 表已这么写，账本侧不重复）。保守拒绝立法（未知枚举值不降级跳过）维持——与 berry-manifest 未知节/键硬拒同构，两源。
- ③代价「SDK-2 文档 5 行 ≈ 1 小时」成立（走 SDK-2 §八升版流程，定稿面纪律直核）。
- **理由**：枚举事后插值 = 旧账本语义二义（09 号 §2.6 代价机制成立），5 行注释买掉一个全量账本迁移档位，值。

### V5 签名索引条目加 `last_revision`/`cert_status` + 版本当时钟成文 —— **通过**

- ①不过度：D1–D4 全部判据的原始数据在此；N 值未定不影响字段（字段记事实，N 是政策——10 号 §2.12 拆维正确）。
- ②设计对：「六字段」直核为 `{id, 三值版本, size, 哈希, key_lineage, 公钥见证}`（SDK-2 §五 :83-85），加两行 = 八字段；TLV 单解释器复用（ADR #59，禁双解析器——Janus 课）成立；「无墙钟过期」补注「时间义务换算为上游版本序」正是把 SDK-2 §五 :85 原文义务化的唯一便宜窗口。与 V4 的 cert_status 归属单一化（见上）是唯一交叉义务。
- ③代价「3 行 ≈ 1 小时」成立。
- **理由**：跟版执法的机器面，字段与原则各 1 行，无懈可击；仅须与 V4 拼成单一事实源。

### V6 mkapp blob 披露五字段门禁 —— **修改后通过**

- ①不过度：预编译件是「两处收敛」唯一真破口（07 号 §4.5-3），空转也立与 SDK-2 §八关门触发器同哲学。
- ②**设计有错（执法点错位）**：mkapp 对 app-dir 打包，**无从判定 `bin/` ELF 是预编译还是现编**（provenance 盲区）——mkapp 眼里只有一个过门禁 5（ELF 魔数）的文件。「包内含预编译件而无 blob.* 声明 = 拒」在 mkapp 层**不可实现**；能实现的是倒转形「有 blob.* 声明 → 五字段齐备才收」（声明校验）。正面检测（无声明 = 拒）只能落在**组装管线**——berry-assemble 知道哪些条目出自平台构建，非构建产物 = blob = 须声明。**修法**：拆两半——mkapp 声明校验（含 `[blob]` 载体节进 berry-manifest 词表，**未知节硬拒的 parser 前置变更，10 号未列**）现在做（约半日）；组装期正面门禁随 V13 落地（08 号 §3.1 步②顺路）。
- ③代价：1 日 → 拆「mkapp 半日现在 + 组装门禁随 V13」；若坚持原案 1 日，买到的是一个**空转且不可实现**的门禁。
- **理由**：目标对、执法点错；provenance 信息只在组装层存在，门禁必须跟着信息走。
