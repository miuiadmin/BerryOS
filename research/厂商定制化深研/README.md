## 核心结论（供快速引用）

1. **能定制**：架构 day-one 支持四组接缝（01 §1），且禁改面执法已在仓（abi-check/L0 永冻/trait 冻结/词表冻结）——「冻住下三路、开放上三路」结构成立。
2. **怎么定制**：三包 + 四层（04 §2）——调参走配置面（轻）、换实现走替换面（须过契约测试）、加件走扩展面；平台永不 fork，上游升级=OEM 包 rebase。
3. **为什么不会重蹈安卓**：安卓病根=交付形态是「一棵邀请你改的源码树」且无稳定边界（02 §1）；BerryOS 把交付形态改成「工件+合同」，fork 成为不必要且不划算的路径（03 §9.3：禁改不靠禁令，靠交付形态）。**第二轮补证（05 号）**：完全放开死（WM）、完全锁死也死（WP7/W10M）——中间路线的必要条件集 N1–N7，架构（三包四层）只保 N1/N2/N3/N5，N4（升级管线先于 OEM 接入）/N6/N7（治理与时机）是架构外命题，不能靠架构自满。
4. **最大风险（诚实结论）**：成败不在四层模型（接缝已在），在**产品工程三件套（产品配置层/签名链/BCTS）是否先于首个 OEM 接入落地**——三件套缺席期间任何 OEM 接入都必然以 fork 形态发生（04 §8.2 失败判据经 05 号 N5 升格为生死判据）。
5. **架构怎么「弄对」（第二轮收口，10 号）**：v1 预埋 16 项 A 档（全部文档行/词表位/schema 字段级，零内核/syscall/wire 改动）——错过 v1 在野格式即 break（全量重打包/账本迁移），预埋成本半日~5 日级/项；立法走新 ADR #82（总纲+预埋登记表）→#83（配置层+槽位合同）→#84（BCTS），OEM 身份并入已预留 #77。
