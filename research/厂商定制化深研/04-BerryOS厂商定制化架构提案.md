## §0 摘要（一屏版）

- **核心命题**：厂商定制 = **组装，不是 fork**。OEM 拿到的不是一棵邀请你改的源码树（安卓病根，02 号 §1.1），而是「平台工件 ⊕ OEM 三包」的组装合同：产品包（配置）+ 服务包（替换）+ 扩展包（新增），全部走 `.bap`/签名链/信任账本既有轨道。
- **四层定制面**：**配置面**（声明式产品清单——今天硬编在 justfile/svcmgr/launcher 常量里，要补 `product` 清单 schema）、**替换面**（用户态服务按稳定契约换实现——架构 day-one 支持，要补契约文档+一致性测试+编排数据化）、**扩展面**（新增驱动/服务/系统应用——受 APP_SLOTS=9 与 type 词表现实约束，要补 devmgr/[hw] 节 v2 落地）、**禁改面**（内核/IPC 核心/syscall/wire 语义/能力模型/intent 词表——执法已在仓，要补「对本仓 CI 之外也执法」的外化）。
- **兼容性保障**：BCTS（暂名）按 L0–L4 分级——**只测承诺面**（L0/L1/L2），不测不承诺面；能力基线（不得砍 syscall 全集/L1 已发布接口/最小系统应用集/能力词表/`user/` 语义）；OEM 身份对接 SDK-2 信任账本（lineage=身份别名、源钥=通道、系统集成者签名白名单）；「BerryOS 兼容」认证门槛草案四条（§4.5）。
- **关键判断（推断）**：本提案的成败不在四层模型本身（架构接缝已在，01 号 §1），而在 01 号 §4.2 点名的**产品工程三件套——产品配置层、签名链、兼容测试**是否先于首个 OEM 接入落地；三件套缺席期间任何 OEM 接入都必然以 fork 形态发生，架构优势无法兑换为治理优势。

## §1 命题与设计公理

### 1.1 命题陈述

> **OEM 的全部合法定制 = 在平台预留的组装点上，投放「数据（配置）、实现（服务包）、增量（扩展包）」三类交付物；平台源码与冻结面（内核二进制、syscall ABI、wire 协议语义、能力模型）不在定制词汇表内。**

依据链：02 号 §4 结论「凡承诺缺位处必碎」+ 03 号 §9 五条共性（合同化/正交/组装/平台保升级权/槽位化）+ 01 号 §4.3「冻住下三路、开放上三路」。安卓 OEM 的深改不是恶意，是交付形态的默认输出（02 号 §1.6 推断）——BerryOS 的对策是把交付形态本身改成「工件 + 合同」，让 fork 成为**不必要且不划算**的路径（03 号 §9.3：禁改不靠禁令，靠交付形态）。

### 1.2 五条设计公理（每条可回溯到 01–03 号证据）

| # | 公理 | 证据锚 |
|---|---|---|
| P1 | **定制面必须是合同**：可改什么编码为 schema 化、版本化、机器可校验的载体 | 03 号 §9.1（六正面样本全无例外）；安卓反面 = 「能编过就行」（02 号 §1） |
| P2 | **平台与产品正交**：构建参数二元组（平台工件 × 产品清单），产品定义永不进平台仓库 | Fuchsia (product × board)（03 号 §1.2）；OH vendor/ 目录（03 号 §5.2） |
| P3 | **个性出口收敛于大槽位**：差异化发生在预留替换点（launcher/策略服务/品牌资产），不发生在框架内部 | 03 号 §9.5；Fuchsia session、Windows OOBE 同构 |
| P4 | **平台保升级主权**：上游按自己节奏发工件，OEM 增量 rebase（包级），兼容由契约测试把关 | 03 号 §9.4；GMS 教训（治理杠杆双刃，02 号 §3.2） |
| P5 | **执法先于开放**：每个开放面必须同时存在可执行门禁，否则不开 | API治理章程 §六「仅成文不执法 = 没有」；应用规范 §0 总原则 3 |

### 1.3 BerryOS 的四个天然锚点（现状事实）

1. **用户态服务 + wire 协议**：FS/网络/驱动/显示/电源策略全是持证用户态服务，消费者只认 wire 协议不认实现（`docs/驱动模型设计-v1.0.md` §1「fsmgr 只认 `/svc/disk/blk0` 的 channel」）——替换面的结构性存在。
2. **`.bap` 一格式一扇门 + 签名信封**：分离式 `app.bap.sig`（ed25519 + SHA-512/256）、两层信任分离、信任账本（`docs/SDK-2-分发与签名链设计-v1.1.md` §二/§三）——OEM 交付物的现成轨道。
3. **L0 syscall 永冻 + L1 wire add-only**（`docs/API治理章程-v1.0.md` §一；`tools/abi.toml` 五面生成 + `just abi-check` 逐字节守卫，nr_total=37/implemented=36/nr_ceiling=45 两源：abi.toml 头注 + AGENTS.md）——禁改面的现役执法。
4. **机制/策略分离 + 硬护栏**：SchedClass trait 冻结、策略注入动作空间四类封顶、权重 ±64 夹紧（`sched/src/policy.rs:48` `WEIGHT_MAX`）、intent 六档词表冻结（`user/berry-manifest/src/lib.rs:140-156`，0x00–0x05）——OEM 调策略的自由度**天然是包络内的**（01 号 §1.1）。

## §2 四层定制面模型

### 2.0 总览

```
┌─ 配置面(a)  声明式产品清单：选什么、默认什么、长什么样（数据）
├─ 扩展面(c)  新增件：驱动/服务/系统应用/资产（增量 .bap）
├─ 替换面(b)  按稳定契约换实现：调度策略/FS/网络/GUI 壳/电源热策略（服务包）
└─ 禁改面(d)  Meihe 内核 / IPC 核心 / syscall ABI / wire 语义 / 能力模型 / intent 词表
```

定制动作自上而下：先配置（零成本）、再扩展（加件）、再替换（换件，须过契约测试）、永不进禁改面。四面对应安卓的「改配置=改源码、加驱动=改内核、换皮肤=改 framework」三级坍缩（02 号 §1）——本模型把每一级还原为独立交付物。

### 2.1 配置面（a）：声明式产品清单

**定义**：OEM 以**数据文件**声明一款产品，不含任何代码。内容五类（提案）：①板级引用（DTB/设备描述、内存与外设集——现役 `kernel/src/dtb.rs` 仅解析 `/chosen`，`docs/驱动模型设计-v1.0.md` §2.1）；②预装集（rootfs 条目 + 特权白名单 `{app_id → [G2/G3 能力键]}`，对接应用规范 §11.2）；③默认策略参数（IntentProfile 档位初值、PM/thermal 表、短时任务配额——ADR #42「数字不写死」纪律的机制落点）；④品牌资源（壁纸/图标蒙版/语义色 token 数值/开机横幅/OOBE 文案）；⑤选择项（launcher 选择、默认应用、特性开关）。

**今天的仓库对应物（事实）**：
- rootfs 条目硬编在 `justfile` mkcpio 调用（:317 起，`app/*.bap` × 10 + `bin/*` 逐条映射）；镜像四件套与 96MiB 盘容硬编在 image 配方（:1010–1069）——与 01 号 §1.6 取证一致（其行号 :309-368/:975-989 为其采集时点，文件演进后行号略移，事实不变）。
- 服务启动编排硬编在 svcmgr 源码（`user/bins/svcmgr/src/main.rs` vblk 预拉 :939、fsmgr :946 等，手写「预拉 arm」+ 端点直递）。
- launcher 视觉常量编译期烘焙（`user/bins/berry-launcher/src/desktop.rs` 的 `OH_*` 常量族；壁纸宿主预采样静态源，ADR #63）。
- 概念先例：`tools/berry`（宿主设备壳）已有 phone/desktop/phone16 等 profile 与 `--profile` 参数（`tools/berry/README.md`）——「产品 profile」思维已在，但它在**宿主侧**，非设备侧产品配置层（01 号 §1.6）。

**要补的交付格式（提案，暂名 `product` 清单）**：
- 双键结构：`platform` 键（平台合同面：能力档位枚举、特性开关——schema 化、进 L2 承诺分级）+ `product` 键（自由面：预装集/品牌资源/默认应用/策略表初值）——直接采 Fuchsia `fuchsia_product_configuration` 的 platform/product 双键形态（03 号 §1.2）与 OpenHarmony `vendor/{厂商}/{产品}/config.json` 目录合同（03 号 §5.2）。
- 「启动配置参数表」（ADR #42 承诺、机制面未见实现【待核实】，01 号 §1.1）与本清单**是否同一件**——开放问题（01 号 §5-Q3，本文 §7-Q2）。
- 组装工具（暂名 `berry-assemble`，随 ADR 定名）读清单产 rootfs/镜像；产品包 = 清单 + 资产 + 白名单的签名信封（签名形态见 §7-Q3）。
- 纪律（提案）：产品清单 schema 进 ABI 治理 L2；manifest/清单**未知键硬拒**（与 berry-manifest add-only 纪律同构）。

### 2.2 替换面（b）：按稳定契约换用户态服务实现

**定义**：OEM 以自己的实现替换某个系统服务槽位。**契约 = 三件套**：①**能力**（该服务槽需要被授予哪些 handle——设备能力/MMIO 窗/资源池，对接驱动模型 §2「申请寄存器 = 申请摄像头」）；②**IPC wire 接口**（L1：add-only + per-interface version，`docs/API治理章程-v1.0.md` §一）；③**消费侧链接 ABI**（协议 crate 静态链接，L2 semver + N=3 废弃窗口）。

**候选槽位清单（提案，开放集待 ADR）**：FS 服务（fsmgr 位）、块设备驱动（vblk 位）、网络栈（vnet 位）、显示驱动后端（HDI 三口：reg_vblank/prepare/commit，ADR #50「换实现不换契约」）、呈现服务（guifbd 位）、窗口策略（gui-wmd 位）、launcher 与系统应用（同格式 .bap，应用规范 §11.1）、输入法（v2 词表位）、调度策略服务（经 `sched/src/policy.rs` 三槽注入表；运行时换表协议 `policy_bind`(0x83) 为 v3 预留）、电源/热策略服务（berry-power/berry-thermal 位，ADR #66/#67/#68）。

**今天的仓库对应物（事实）**：
- 架构接缝在：消费者只认 wire 协议（驱动模型 §1）；#28 代号链使服务可崩可热换；协议 crate 族分层（berry-netproto/berry-netdproto/berry-tcp 等）host 可测（01 号 §1.2）。
- 工程无门：替换 = 改 svcmgr 源码重编（01 号 §3 缺口 2）；数据驱动装卸（appd/devmgr）= v2（驱动模型 §5 阶段表）。
- 调度策略注入机制在（三槽 RCU 换表 + 动作空间四类封顶 + ±64 夹紧，`sched/src/policy.rs`），但 v1 仅内核侧 ktest/boot 期调用（`sched/src/policy.rs:354` 头注）——OEM 经用户态策略服务换表的正门 = v3 协议。

**要补的交付格式（提案）**：
- **服务包** = `.bap`（type 词表扩 `service`/`driver`——现役 manifest v0 `type` 恒 `"app"`，`type=driver` 为 v2 词表，`docs/驱动模型设计-v1.0.md` §6 落地注）+ 声明所实现的 per-interface version + 能力申请节。
- **契约文档面**：每个可替换槽位一份「槽位合同」——能力需求清单 + wire op 全表 + 语义合同（时延/错误码/失败隔离义务）。合同本身是 L1/L2 承诺面，进 API 治理。
- **契约一致性测试（conformance）**：BCTS L1 核心（§4.2）——没有契约测试的槽位不得对 OEM 开放（公理 P5）。
- **编排数据化**：svcmgr 预拉链从手写 arm 改为读产品清单/服务包声明的依赖与端点（配置面与替换面的接缝；v2，随 devmgr 同刀）。
- **粒度纪律（提案）**：「调参」归配置面（策略表/档位），「换实现」归替换面（须过全量契约测试）——把 OEM 最常见的诉求（调参）从最贵的通道（换实现）里分流。

**替换的硬护栏（不可协商，事实性立法已在）**：SchedClass trait 签名冻结（`sched/src/class.rs:8`）；策略动作空间四类封顶、「没有第五类」；intent 词表 0x06..0x0F 保留拒绝；公平默认、只叠加永不替代（ADR #42/#58）——OEM 策略自由度 = 包络内，「护栏先于策略」（01 号 §1.1）。

### 2.3 扩展面（c）：新增驱动/服务/系统应用

**定义**：OEM 加自己的件，不替换既有槽位。含：新 SoC/外设驱动、增值系统服务（账号/推送/云服务代理）、预装系统应用、字体/资产包。

**今天的仓库对应物（事实）**：
- 驱动 = 持证应用已立法（ADR #46 + 驱动模型 §1），但 `type=driver` 词表、devmgr（DTB 枚举→池→匹配→授 MMIO 窗→注册 `/svc`）、IRQ→channel 转发原语均 v2（驱动模型 §5；v1 vblk 轮询 INT_STATUS + 1ms 睡步进）。
- 应用扩展的现实帽：`APP_SLOTS = 9` 静态槽（`user/berry-manifest/src/lib.rs:112`）+ rootfs 静态 cpio 无运行期增删——厂商预装规模受硬帽（01 号 §3 缺口 8）。
- 系统应用轨道已在：七系统应用（appstub 壳）+ 转正刀序（应用规范 §11.5/§15.3）。

**要补的交付格式（提案）**：
- **扩展包** = 普通 `.bap`（预装走系统集成者签名 + 白名单，应用规范 §11.1/§11.2——OEM 预装没有第二安装通道）；驱动扩展包加 `[hw]` 节（能力申请：MMIO/IRQ/DMA）随 devmgr v2 落地。
- **blob 显式声明政策**（采 Zephyr module 政策同构，03 号 §6.1）：闭源 OEM 驱动若允许，二进制 blob 必须构建期声明（来源/许可/哈希），构建可见可审。
- **上游化政策**（采 Zephyr「专为 Zephyr 写的代码不得藏进模块」同构，03 号 §6.1）：专为 BerryOS 写的**通用**代码（新 FS 通用优化、协议栈通用改进）应上游化回主线；模块位只留给真正产品特有件。具体边界与激励 = 开放问题（§7-Q9）。
- `/apps` 动态装载（v2）解锁 APP_SLOTS 帽——扩展面的规模前提（01 号 §5-Q8）。

### 2.4 禁改面（d）：内核 / IPC 核心 / syscall ABI / berry-sys

**定义（与 01 号 §2 冻结表同源）**：Meihe 内核（二进制统一交付）、IPC 核心（同步 channel + 异步通知 + 共享内存三路及其语义）、syscall C-ABI（L0 永冻）、berry-sys/libc 公开面、服务 wire 协议**语义**（L1 add-only——可加新 op，不可改旧义）、能力模型（handle 唯一权限机制，永不第二种）、intent 词汇表、应用模型（一格式一扇门/永不第二容器）、调度机制/策略分界、存储语义（零分区 + 四棵树 + `user/` 永不动）、度量/信任结构（槽位表 add-only）。

**今天的仓库对应物（事实）**：`tools/abi.toml` 单源五面生成 + `just abi-check` 逐字节守卫（挂 build/smoke 前置）；mkapp 五道门禁 + 规范形重序列化 + 三值版本链执法（`tools/mkapp.py`）；ADR #55 两冻结面；API治理章程三硬纪律；AGENTS.md 冻结常量表。**共同点：全部只对本仓 CI 生效**（01 号 §3 缺口 4）。

**要补的执法外化（提案）**：
1. **上游只以工件交付**：内核 = 上游签名的 `KERNEL.ELF` 二进制（+ 源码公开供审计，Apache-2.0）；OEM 产品镜像里的内核必须逐字节等于上游工件（进度量链对账）。类比：GKI 单内核二进制 per 架构（02 号 §3.4）、QNX/Windows 闭源内核天然不可改（03 号 §2/§3）。
2. **诚实面（推断）**：Apache-2.0（ADR #37 协议洁净线）允许任何人 fork 源码——「永不 fork」**不可能由许可证执法**，只能由「认证 + 签名链 + 商标」组合执法（fork 出去的设备拿不到「BerryOS 兼容」身份、进不了官方信任账本与源生态）。这正是 02 号 §2.5 的教训：GMS 这类治理杠杆有效但双刃——BerryOS 的对应物是什么，超出技术立法（§7-Q5）。
3. **boot 豁免件纪律（提案，回应 02 号 §6-Q5）**：启动关键暂留内核件（GIC/timer/早期 UART/console，ADR #12 + 驱动模型 §4/§5）清单 = **公开常量 + 逐版外提时间表**；OEM 不得以「我也要 boot 关键件」为由新增豁免——否则这里会长成 BerryOS 自己的 out-of-tree 角落（02 号 §6-Q5 原文警示）。
4. **度量链对账**：OEM 镜像的度量清单（TLV 槽位表 0–4，add-only）必须可由「上游工件 + OEM 三包」确定性重组——同输入同 hash（组装工具单编码器原则，mkcpio/mkimage 已是现役实践，推断可推广到全镜像）。

### 2.5 四面总表

| 面 | OEM 动作 | 交付物 | 今天有无门 | 前置缺口（01 号编号） |
|---|---|---|---|---|

## §3 「永不 fork」原则的执行机制

### 3.1 交付物模型：三包一信封，全走既有轨道

```
平台工件（上游发版，暂名 AIB 同构）
  = KERNEL.ELF（签名二进制）+ 基座 rootfs 条目 + 协议 crate / berry-sys（版本化）
  + 工具链版本 + 契约测试集（BCTS）
        ⊕
OEM 三包（全部 .bap 信封 + .sig 签名 + 信任账本登记，SDK-2 §二/§三轨道）
  ① 产品包：产品清单 + 品牌资产 + 预装集 + 特权白名单
  ② 服务包：替换槽位实现（声明 per-interface version + 能力申请）
  ③ 扩展包：新驱动/服务/系统应用（v2 起含 [hw] 节）
        ↓ berry-assemble（组装工具）
产品镜像（确定性组装，hash 可复现）
        ↓ BCTS（契约 + 基线 + 签名链校验）
「BerryOS 兼容」设备（认证徽标 + 官方信任账本登记，治理面待立法）
```

要点：
- **复用不新建**：信封/签名/账本/装载全走 SDK-2 已定案轨道（分离式 `.sig`、ed25519 + SHA-512/256、lineage 身份别名、换钥重叠双签窗、防剥离、单调水位）；产品包只是信封家族新成员，不造第二格式（API治理章程硬纪律 1 同构）。
- **产品包的签名形态**（开放问题 §7-Q3）：走 `.sig` 信封还是镜像级签名（对标 Fuchsia 产品以 product bundle 分发、03 号 §1.2；及 SDK-2 §五「镜像内置官方源静态实例」的镜像签名先例）——两者不冲突，提案倾向：清单与资产走 `.sig`，最终镜像走度量链（推断）。

### 3.2 上游升级 = 厂商包 rebase，不改上游码

上游发新版（新 KERNEL.ELF + 新基座 + 新契约测试）→ OEM 侧动作 = 用同一产品清单对新工件重跑组装 + 重过 BCTS → 通过即发新版。OEM 的全部自有内容始终在**自己的包**里，从不触碰平台源码，因此：
- 上游升级成本 = 组装 + 测试（自动化可收敛），不是 AOSP 式全树合并（02 号 §1.1/§2.1：LTS 合并难、安全补丁回传贵、上游延迟 18 个月）。
- 对接四层 OTA（`docs/更新与OTA设计-v1.0.md` §1）：L1 目录级 A/B + 指针原子翻 + 启动计数回退（L0 slot 三字段）+ **`user/` 永不动**——OEM 升级 =「换家具不换房子」，整机重刷文化（该文档 §0 病灶）被结构性排除。
- 与 Yocto layer「叠加增量优先于复制」同构（03 号 §4.1）：定制增量的可 rebase 形态是工程收益的来源。

### 3.3 对照 02 号机制链：逐条封口

02 号 §0 因果链逐环节对照（左列 = 02 号原文机制链编号引用；「残余风险」列为推断）：

| 02 号机制根因 | BerryOS 机制（本提案） | 残余风险（推断） |
|---|---|---|
| §1.1 交付形态 = fork 整个 AOSP | 平台以**工件 + 合同**交付；OEM 仓库只有清单与自有件（§3.1） | 无工件发布纪律则退化为「拉源码 tag 自己编」——发布工程本身是新负债 |
| §1.2 framework 内部无稳定 ABI | 反向解：**中间不设稳定 ABI**（ADR #55）+ 应用静态链接自兜底——OEM 没有可依赖的框架接口面，fork 框架无从获利；服务面只有 L1 wire（add-only） | OEM 若依赖平台 crate 内部 API（L3 零承诺），升级即碎——契约文档须明示「只许依赖 L1/L2」 |
| §1.3 换肤 = 改 SystemUI/framework 源码 | 换肤正门 = 配置面品牌资产 + launcher = 系统应用槽（同格式可换，应用规范 §11）；深度交互 = wmd/launcher 替换槽（契约测试把关） | RRO 式老问题：token/资产覆盖不了深度交互差异，冲动会涌向替换面——槽位契约必须覆盖交互语义（窗口表/焦点/避让），否则形同虚设 |
| §1.4 HAL 接口弱承诺、三代迁移 | wire 协议 L1 = add-only + per-interface version（永不「换代重写接口」）；驱动 = 持证应用，接口即应用间协议 | 协议语义漂移（同一 op 两种实现行为不同）——靠 BCTS L1 契约测试钉住 |
| §1.5 驱动进内核树（50% out-of-tree） | 驱动全用户态（ADR #12/#46）；内核二进制统一交付 + 度量链对账 | boot 豁免件是唯一的内核侧残留——§2.4-3 纪律：清单公开 + 只减不增 |
| §2.1 升级合并成本爆炸 | 包级 rebase（§3.2）+ 四层 OTA + `user/` 永不动 | OEM 包自身的契约测试维护成本（见 §8.2-2） |
| §2.2 版本碎片（六版本并存） | 「BerryOS 兼容」认证挂跟版窗口（§4.5-d，数值开放）；上游版本节奏治理 | 无 GMS 式商业杠杆时，**无强制退场机制**——02 号 §2.5 教训：这是治理题不是架构题，开放 |
| §2.3 应用兼容差 / 开发者适配 | 三值版本域 + abi_revision 把兼容拦在工具期；L0/L1 全网一致 + BCTS 基线（不得出子集设备） | 认证覆盖率不足时，未认证 fork 设备在野外仍可跑 `.bap`——签名链关门触发器（SDK-2 §八）的执行时机关键 |
| §3.7 架构修复晚于碎片化十年 | day-one 立法：冻结面/能力模型/一扇门均 v1 在册 | 「day-one」只在立法意义上成立——OEM 接入窗口若早于三件套落地，01 号 §4.2 判断生效 |

### 3.4 治理面的诚实陈述（推断，不拍板）

1. **许可证不禁止 fork**（Apache-2.0，ADR #37）——「永不 fork」是平台治理目标，执法组合 = 认证（BCTS）+ 信任账本（源钥/lineage）+ 商标（未立法）。三者缺一则 fork 无代价。
2. 02 号 §2.5/§3.2 的双刃教训直接适用：若未来引入类 GMS 商业杠杆（官方源独占、商店准入），会重演欧盟反垄断风险；若完全不引入，则对 fork 漂移无速度限制。**中间态**（认证 + 官方信任账本的自然网络效应）是否足够——开放问题（§7-Q5）。
3. SoC 厂商是第一压力源（推断）：安卓 50% out-of-tree 的主体是 SoC 代码（02 号 §1.5）。BerryOS 的对应防线 = devmgr 能力表 + MMIO 窗 VMO（机制已在，P6 A-2/A-3）+ 驱动扩展包正门（v2）+ 上游化政策；**IRQ 转发/高性能 DMA 面 v2 前不完整**（驱动模型 §5 诚实披露），此窗口内 SoC 厂商「不碰内核出驱动」做不到——须诚实告知 OEM，不得虚报能力（01 号 §3 缺口 5）。

## §4 兼容性保障：BCTS（暂名）与认证门槛

### 4.1 定位与设计原则

**BCTS（BerryOS Compatibility Test Suite，暂名）**：对标 Android CTS（免费、开源、可自测，02 号 §3.1），但机制化程度更高——三条原则（提案）：
1. **按承诺分级测试**：只测 L0–L2 承诺面；L3/L4 不承诺面**不进 BCTS**（防 CTS 式无限膨胀；与 API治理章程 §五 Hyrum 纪律同构：不承诺面自由变更，测它反而制造伪契约）。
2. **测试即门禁**：BCTS 挂组装管线（§3.1），不过 = 不能产「BerryOS 兼容」镜像；不是事后认证仪式。
3. **host 可测优先**：协议 crate 族/berry-sys 的 host 单测是现役先例（01 号 §2 L1 行）——契约测试大部分在宿主 CI 可跑，真机/QEMU 面只留必须项。

**与现役测试的关系（事实基础）**：smoke 86 基础标记（boot 32 + rootfs 54，`tools/smoke.sh`）是开发冒烟非认证面；abi-check/mkapp 门禁是单源守卫；BCTS = 把这些「种子」外化 + 扩充为面向任意组装者的套件（01 号 §3 缺口 4）。执法位与 G0–G5 关卡的关系 = 开放问题（03 号 §11-Q5，本文 §7-Q4）。

### 4.2 按 L0–L4 分级测什么（提案表）

| 级 | 测什么 | 形态 | 现役种子 |
|---|---|---|---|
| L0（syscall 永冻） | ①abi-check 五面逐字节对账（含 OEM 镜像内的内核与 berry-sys）；②syscall 全集语义套件：37 在册号逐号行为（含 -ENOTSUP 存活语义、能力门控、错误码） | host（abi 对账）+ QEMU/真机（语义） | `just abi-check`；smoke boot 相 |
| L1（wire 协议 add-only） | ①每接口契约套件：合法 op 序列、非法 op 拒绝、per-interface version 协商、错误域、超时/失败隔离语义（DEAD 重试）；②**替换实现一致性**：OEM 服务包对同一契约测试的通过性（替换面开放的充分条件） | host 优先（协议 crate 轨道） | 协议 crate 族 host 单测 |
| L2（公开库 API） | ①berry-sys/libc/gfx/ui 行为测试；②三值版本域与废弃窗口执法（mkapp 编译期，现役）；③产品清单 schema 校验 + 组装确定性（同输入同 hash） | host | `tools/mkapp.py` 门禁；mkcpio/mkimage 单编码器 |
| 行为双轨（章程 §二） | compat 轨：按 `target` 分档断言新旧语义；security 轨：修复对所有包即时生效（无豁免断言） | host + QEMU | 双轨设计登记表（`docs/SDK-2-双轨与演化纪律设计-v1.0.md`） |
| L3/L4 | **不测**（零承诺面；防伪契约） | —— | —— |

### 4.3 能力基线：厂商不得砍掉什么（提案，逐条给依据）

| # | 基线（不得砍/不得改） | 依据 |
|---|---|---|
| 1 | **L0 syscall 全集实现**——在册 37 号（nr_ceiling=45 内只加不删），不得出「支持 30 个号」的子集设备 | abi.toml + AGENTS.md「v1 37 在册」；API治理章程 L0 永冻 |
| 2 | **L1 已发布接口全集**——替换实现也必须说全量契约，不得「实现 fsproto 的一半」 | L1 add-only + §4.2 契约测试设计 |
| 3 | **最小系统应用集与卸载语义**——SETTINGS/FILES 不可卸载（可停用）、CAMERA 不可卸载、appd 分发渠道不可卸载 | 应用规范 §11.3（269 号文四类映射，现役七件落位） |
| 4 | **能力词表不裁剪不私扩**——G0 词表全网一致；OEM 专属能力键 = 违反「handle 唯一权限机制」；特权只走「系统签名 + 白名单」一条路 | ADR #2/#3；应用规范 §2.1/§11.2（「一条申请通道，ACL 双轨漂移禁入」） |
| 5 | **系统应用义务不可豁免**——`console=false`、遥测近零、能力最小集、不豁免用户可见管控 | 应用规范 §11.4（「谁预置谁负责」，269/407 号文监管面） |
| 6 | **GUI 语义 token 闭集与官方 token 名保留**——应用只消费语义 token，系统切肤全树生效；OEM 可改 token **数值**、不得删 token 或冒用官方动效 token 名 | 应用规范 §3.4/§3.5；ADR #63（token 词表闭集） |
| 7 | **存储语义**——零分区 + 四棵树 + `user/` 永不动 + 树即登记簿；OEM 盘布局自由但归属语义不变 | ADR #45；01 号 §2 存储行 |
| 8 | **intent 词汇表冻结**——OEM 调档不造词（0x06..0x0F 保留拒绝） | ADR #42/#58；berry-manifest 词表镜像 |
| 9 | **签名链与度量结构**——.sig 信封语义、账本水位、TLV 槽位表 add-only、verifiedbootstate 四态语义不可变造 | SDK-2 §三；安全与硬件隔离 §4（经 01 号 §1.5 转引） |
| 10 | **不承诺面保持自由（反向基线）**——调度延迟形态、错误码→errno 映射次序、遥测字段次序等 OEM 可调可换，**BCTS 不锁**（防伪契约反向滥用） | API治理章程 §五 |

### 4.4 OEM 签名与身份：对接 SDK-2 信任账本

现役设计（SDK-2 §二/§三/§五，事实）→ OEM 扩展（提案，标注）：

| SDK-2 既有件 | OEM 对接（提案） |
|---|---|
| `key_lineage` = 身份别名（1..=16B，Apple Team ID 同构；ADR #59 预留壳转实用） | **OEM lineage 由平台分配**（发放机构/规则/多级授权 OEM→ODM→开发者 = 开放问题，01 号 §5-Q2）；一台设备镜像内所有系统件同 lineage = 「系统集成者」身份的机器表达 |
| 两层信任：源钥=通道、包钥+lineage=身份 | OEM 商店/镜像源 = 一种「源」，持自己的源钥；**官方源钥出厂预装机制**（SDK-2 §二）原样适用于 OEM 镜像内置 OEM 源静态实例（v1 镜像内置官方源同构，SDK-2 §五） |
| 信任账本 `{lineage_id → anchors[(公钥, anchor_type ∈ tofu\|system\|ca)], gen_max, ver_max}` | `ca` 占位已为「商店时代 A+CA 双验」留口（SDK-2 §二）——OEM 认证锚是否新增 anchor_type（如 `oem-system`）= **开放问题**（账本 schema 是 SDK-2 定稿面，勿轻改；§7-Q6） |
| 特权白名单随镜像签名 + 构建期校验 + boot 对账（应用规范 §11.2） | 白名单的签发者 = OEM（系统集成者）；「未列而申请 = 拒授 + loud 降级」现役语义对 OEM 同样生效——**OEM 不能给自己开后门**（特权永不进 G0/G1 词表） |
| 度量链槽位表（0–4 已分配，add-only）+ `.bap` manifest 进槽 4 | OEM 镜像 = 上游工件 + OEM 包的确定性重组（§2.4-4）；换服务/加预装后度量链必须可复现，否则认证失败 |
| sideload 系统开关：产品镜像默认关、dev 镜像预开 | OEM 产品镜像默认姿态继承（关闭）；OEM 若要开（开发者版设备）= 产品清单 `platform` 键声明项 |

### 4.5 「BerryOS 兼容」认证最低门槛（草案，供 ADR）

1. **技术门槛**：BCTS L0 + L1 + L2（§4.2 全表）全绿；能力基线（§4.3 十条）断言全过。
2. **身份门槛**：OEM lineage 在册；预装/特权白名单构建期校验 + boot 对账通过；签名链负样例（篡改/断链/跨 lineage）全拒（复用 SDK-2 §九验收线）。
3. **可复现门槛**：同工件同清单重组，镜像 hash 一致；度量链可由公开工件重建。
4. **跟版门槛（数值开放）**：认证设备须在 N 个上游 minor 版本窗口内完成跟版（超窗 = 认证标记失效/降级）——对标「Google 不给旧版本授权 Play」的时间杠杆（02 号 §3.2），但以认证标记而非商业许可执法（推断：合法性更稳，强制力更弱，见 §3.4）。
5. **法律/商业面**：商标与「BerryOS 兼容」徽标的授权关系、认证运营主体（平台方/基金会/第三方测评——开放原子模式 vs YP Compatible 模式，03 号 §11-Q8）= 超出技术立法，原样列开放问题。

## §5 定制点矩阵：OEM 想做的事 → 层 → 交付物 → 风险

> 「风险」列为推断；「现役可行」= 按 2026-11-10 仓库现状（01 号 §3 缺口编号在括号内）。

| # | OEM 想做的事 | 四层归属 | 交付物 | 依赖契约 | 现役可行 | 兼容性风险与执法点 |
|---|---|---|---|---|---|---|
| 1 | 换壁纸/图标蒙版/色板数值/字体档 | 配置面 | 产品包（品牌资产节） | 语义 token 闭集（基线 6） | 部分：构建期烘资产可行，运行时换肤 v2（缺口 7） | 低——token 数值覆盖不破应用；禁专有字体（ADR #63） |

| 3 | 预装自家应用全家桶 | 扩展面 | 扩展包 + 白名单条目 | 应用规范 §1–§11 全量（只加严不豁免） | 部分：APP_SLOTS=9 硬帽（缺口 8）；/apps 动态装载 v2 | 中——义务清单/预装元数据强制（407 号文）；「以防万一」全量申请拒 |

## §6 与 v1/v2 路线的关系

### 6.1 v1 就该预埋的（纪律面，零/低成本；逐条给依据）

1. **接口契约纪律保持不动**：L0 五面生成 + abi-check、L1 add-only、mkapp 门禁、三值版本域——全部现役，勿因任何「OEM 专项」开口（API治理章程 §四三硬纪律）。
2. **产品变量的「清单意识」**：v1 内每次改 justfile/svcmgr/launcher 常量时，同步记录「哪些是产品变量」——为 v2 产品清单 schema 攒词汇表（近乎零成本的设计纪律，提案）。
3. **特权白名单构建期校验先行**（应用规范 §11.2 已 v1 立法）：白名单机制是 OEM 预装的执法地基，v1 落构建期校验、boot 对账随镜像工程。
4. **SDK-2 P0/P1 勿再推迟**（建议，推断）：mkapp 产 `.sig` + berry-crypto（RFC 8032 + Wycheproof 门）是 OEM 身份的全部地基——签名链晚于首个 OEM 接触 = 01 号 §4.2-2 的欠账窗口拉长。
5. **测试标记名升承诺面的路线成文**：smoke 标记/abi-check 输出从 L4（无承诺）升为 BCTS 消费面，须走章程 §六 api-diff 流程——v1 动作 = 把这条升级路径写进治理文档（立法位，不是工程位）。
6. **上游化政策成文**（Zephyr 同构，§2.3）：v1 生态为零时立法成本趋零，错过不可补（与 SDK-2 §八关门触发器同哲学）。
7. **诚实披露义务**：对任何潜在 OEM 明示 v1 现实（QEMU virt 主验/单核/APP_SLOTS=9/无 OTA 代码面/驱动正门 v2）——虚报定制能力 = 自毁信任 + 诱导 fork（推断）。

### 6.2 v2 落地件（本提案的主体依赖）

产品配置层 + `berry-assemble` 组装工具实装；devmgr + `type=driver` + `[hw]` 节（驱动扩展正门）；/apps 动态装载（APP_SLOTS 解放）；token 运行时换肤/主题覆盖；G1/G2 授权运行面与能力词表扩展；系统应用独立换发（sys+apps 双树）；OTA L1 双目录 + 指针翻转；在线源与 OEM 商店轨道。——全部与既有 v2 规划同轨（01 号 §3 缺口表、`docs/驱动模型设计-v1.0.md` §5、`docs/更新与OTA设计-v1.0.md` §7），本提案**不新增 v2 议程**，只把它们编排为「OEM 接入的前置集」。

### 6.3 v3+ 件

namespace 挂载策略（OEM 重组服务树的合法面，01 号 §1.3/§5-Q6）；`policy_bind`(0x83) 运行时换表协议（调度策略服务的正门）；intent ×4 带实例化（M4）。

### 6.4 时机判断（推断）

v1 期（P8 真机窗口前）OEM 只能做评估/预研/虚拟机跑镜像——真正定制窗口 = v2+。本提案 §6.1 的预埋项，目的就是把「三件套落地前 OEM 硬要进来」的 fork 风险压到最小：即便发生，冻面执法（abi-check/wire add-only/一扇门）也保证 fork 出去的设备**在应用兼容面上与主线同构**，碎片只剩「服务实现差异」一维，而非安卓的三维乘积（02 号 §2.3 注解）。

## §7 开放问题（原样列出，不替拍板）

1. **OEM 身份发放机构与规则**：lineage 分配权在谁；能否多级（OEM→ODM→独立开发者）；与「系统集成者」签名的关系（01 号 §5-Q2）。
2. **产品配置层形态**：产品清单与「启动配置参数表」（ADR #42）是否同一件；cargo feature 是否参与；schema 归属 L2 还是新分级（01 号 §5-Q3）。
3. **产品包签名形态**：`.sig` 信封 vs 镜像级签名 vs 度量链覆盖；与 SDK-2 §五「镜像内置源」的关系。
4. **BCTS 执法位**：并入 G0–G5 关卡还是独立套件；谁跑（OEM 自测 + 平台裁决 vs 第三方测评）；测试集的发布节奏与版本绑定（03 号 §11-Q5）。
5. **治理杠杆形态**：认证标记失效（§4.5-4）之外，要不要任何类 GMS 机制（官方源独占/商店准入）；商标运营主体（02 号 §6-Q6、03 号 §11-Q8/Q9）。
6. **信任账本 anchor 扩展**：是否新增 OEM 系统锚类型（`oem-system` 类）；账本 schema 变更走 SDK-2 哪个流程。
7. **能力档位枚举**：feature 档位怎么切（移动 rich/PC/穿戴同族/MCU 排除的映射）；「只准加不准减」的最小产品边界（03 号 §11-Q4）。
8. **替换面开放集**：v2 首批对 OEM 开放哪些槽位（本文 §5 建议：显示后端/launcher/电源热策略先行，FS/网络栈重认证）；调度策略服务的深度边界（01 号 §5-Q4）。
9. **上游化政策的强制力**：纯倡导（Zephyr 式 TSC 门只管默认清单）还是认证条件；产品特有件与通用件的判定权。
10. **blob/闭源驱动政策**：允许与否、最低披露线（许可/来源/哈希）、度量链如何覆盖闭源件（03 号 §11-Q6）。
11. **boot 豁免件外提时间表**：豁免清单常量化 + 逐版收敛的节奏；OEM 新增豁免的否决机制（02 号 §6-Q5）。
12. **跟版义务 SLA**：N 值多少、超窗后果（标记失效 vs 摘牌）、OEM 停更后的设备责任边界（03 号 §11-Q9：无先例可抄）。
13. **launcher 转正 .bap 的刀序**（01 号 §1.4 待核实项）——它是替换面「换壳」槽位成立的前提之一。

## §8 反面自检（如实写）

### 8.1 最可能被厂商反抗的三点

1. **「禁改面太大，内核碰不得」**——SoC bring-up 与性能调优在中短期离不开内核侧改动（中断控制器细节、定时器精度、缓存维护）；GKI 至少给了 KMI + vendor module 面（02 号 §3.4），BerryOS v2 前连 IRQ 转发原语都没有（驱动模型 §5 诚实披露），厂商会说「你们的用户态驱动是画饼」。**缓解**：devmgr/[hw] 节 v2 兑现节奏 + boot 豁免件公开清单；**诚实结论（推断）**：P8 前无法完全回应此抗议，只能以路线图 credibility 对冲。
2. **「替换面契约负担 = 平台方转嫁成本」**——说全量 wire 契约 + 过 BCTS = 重写一个 FS/网络栈的成本，而厂商真实诉求 80% 是调参/换壳/预装（§5 读法）；若三包模型强迫一切走重通道（或认证费/测试时长失控），会复现「跑 CTS 贵」的老抱怨（02 号 §3.1 的 CTS 虽免费但 Tradefed 体系重）。**缓解**：配置面/扩展面轻通道必须真的轻（§2.2 粒度纪律）；**残余风险（推断）**：BCTS 若由平台方单方扩表，会变成准入税。
3. **「槽位化锁死深度差异化」**——品牌厂商的核心卖点恰是「面目全非」的那部分（多任务手势/AI 助手入口/跨端互联）；RRO 覆盖不了深度交互是安卓实证（02 号 §1.3），若 BerryOS 槽位契约只开放「换 launcher + 调 token」，厂商的差异化冲动会挤压替换面契约或直接施压开禁改面。**缓解**：wmd/输入管线槽位契约预留深度交互面（§3.3 第三行）；**诚实结论（推断）**：槽位模型与深度差异化之间存在结构性张力，无法全消，只能靠「槽位集合随版本扩张」的承诺管理预期。

### 8.2 最可能失败的两点

1. **治理三件套晚于首个 OEM 接入**（01 号 §4.2-1 的直接推演）：商业压力先来（大 OEM 带 SoC 带订单），配置层/签名链/BCTS 缺位，则接入必然以 fork 形态发生——此时冻结面执法仍在，碎片被限制在服务实现层，但「永不 fork」原则即告失败，且 02 号 §3.7-2 教训适用：**已形成的 fork 存量不可逆，只能等设备退役**。失败判据（推断）：首个 OEM 交付物是源码分支而非三包。
2. **平台演进速度吞掉承诺或跟不上 OEM 周期**：v1→v2 是 BerryOS wire 协议/词表/词表槽的快速增长期，契约测试集自身维护成本高（每加一个 op = 契约文档 + conformance 用例 + BCTS 版本绑定）；同时 OEM 机型周期（6–12 个月）天然短于 OS 版本周期，若上游发版节奏慢于 OEM 需求（新硬件特性等不到上游槽位），OEM 就有动机私开槽位 = 事实 fork。**失败判据（推断）**：出现「OEM 在服务包里内嵌平台行为变更」（绕过 L1 语义）或认证设备长期停更（§7-Q12 的 N 值形同虚设）。这两点共同指向：**本提案一半是架构题，一半是版本节奏与治理运营题——后者无先例可抄**（03 号 §11-Q9）。
