## 0. 结论摘要(先给链,再给证据)

安卓的反面教材(02 号稿)证明:**当官方交付形态是「一个可改的源码树/系统镜像」,且不为改动设稳定边界时,OEM 必然滑向 fork 深渊**。本稿横向解剖七个做到了「改得出个性、不破坏兼容」的系统,发现它们的共同结构是同一句话:

> **平台以二进制工件 + 显式配置合同交付;产品 = 平台工件 ⊕ OEM 自有件,按清单组装;个性表达收敛到少数几个被平台预留的「大槽位」;兼容性靠契约化测试/签名/认证执法,不靠 OEM 自觉。**

五条共性机制(§9 归纳,逐条可回溯到证据):

1. **定制合同化**:可定制面全部固化为显式合同——Fuchsia 的 platform 配置 schema、Windows 的 unattend/OOBE.xml 模式、Yocto 的 layer.conf/.bbappend、OpenHarmony 的 config.json 部件表、QNX 的公开 ABI/BSP 文档、Zephyr 的 module.yml/board.yml。
2. **平台与产品正交**:构建参数都是二元组——Fuchsia (product × board)、QNX(内核二进制 × BSP)、Windows(系统镜像 × 驱动/应答文件)、Yocto(metadata × layer)、OpenHarmony(部件 × 产品配置)、Zephyr(核心 × module/board)。
3. **组装而非 fork**:六家中没有一家让 OEM 改平台源码来出产品;产品仓库里只有清单和自有件。
4. **平台方保升级主权**:平台按自己节奏发版(Fuchsia SDK 节奏 / Windows Update / QNX SDP 版本),OEM 增量叠加;兼容由契约测试(CTS/HLK/兼容性测评)把关,不由 fork-sync 保证。
5. **个性出口 = 预留槽位**:session/shell(Fuchsia)、OOBE+预装+品牌(Windows)、发行版品牌与拼装(OpenHarmony)——差异化发生在「应用层的系统组件」,而不是改框架本身。

对 BerryOS 最直接的启示(§10 只列机制):BerryOS 的用户态服务 + 路径命名空间 + .bap 签名信封 + L0 永冻,恰好是这套范式的四个天然锚点,缺的是「产品配置合同 + 组装工具 + 兼容性执法」三件套(01 号稿 §4 已盘点该缺口)。

## 1. Fuchsia:product assembly + component framework(重点,微内核同源)

### 1.1 治理演化线:从「树内产品」到「树外组装」

Fuchsia 走过一条完整的自我纠正曲线,这条曲线本身就是 BerryOS 最值钱的证据:

1. **起点(Global Integration)**:花瓣仓库(petal,如 flutter-runner、workstation 组件)的产物被 roll 回 fuchsia.git 主树,产品在主树内组装。RFC-0124 白纸黑字列出三大弊端:产品配置锁在 fuchsia.git 而非产品所有者手里;平台版本永远领先于花瓣所用的 SDK 版本;跨花瓣的版本兼容只能靠手工 roll 对齐(RFC-0124 Motivation,gitiles 原文已核)。
2. **路线图转向(2021)**:「Scaling Product Assembly and Configuration」提出 assembly 与 configuration 是同一过程的两半,引入 sub-assembly(子组件集 + 配置点 + 显式文档说明哪些配置可在组装期改);目标是「客户产品完全树外组装,不直接使用 fuchsia.git」(roadmap 原文)。同年「Decentralized Product Integration」提出 PDK:全局可寻址工件仓 + 工件命名/元数据约定 + 产品集成描述格式 + 组装工具,全部进 SDK。
3. **RFC-0095(废弃)**:Workstation 树外组装提案——核心句子:「There is no clear distinction between Fuchsia as a platform and the workstation product」,即平台与产品不分 = 病根。后被 RFC-0220 取代(该 RFC 头部自注 superseded)。
4. **RFC-0220(现役决策)**:树内产品从十个收缩到 minimal / bringup / workbench(+core、terminal 标记弃用);「产品作为 SDK companion image 分发,树内树外同等工作」列为 Requirements;生产产品一律树外组装。//products/README.md(2026-11 快照)印证现状,并给出关键合同句:「Minimal is intended to be the basis for all production Fuchsia products, which should not subtract from its contents, only add to them」(生产产品对 minimal 只准加不准减)。

**对 BerryOS 的映射意义(推断)**:这条曲线演示了「树内产品爆炸 → 收缩为参考产品 + 树外组装」的完整路径;BerryOS 尚无树内产品,可从 day-one 直接落在终点形态。

### 1.2 组装模型:(product, board) 元组 + 三依赖分集

- **构建参数 = (product, board) 二元组**,两者都是 GN include;「This set of parameters completely describes the work the build system must complete」(RFC-0220 Glossary,两源:build_configuration.md 同口径)。
- **board 定义架构/硬件特征/驱动集合/内核参数,并初始化三个依赖列表;product 只做增补**(build_configuration.md 原文:board is always included first, boards define and products augment):
  - **Base**:进磁盘镜像与系统更新,原子更新、运行时永不逐出——系统与安全关键面;
  - **Cache**:预进镜像但不进系统更新,可临时(ephemeral)更新、可被逐出;
  - **Universe**:只进包仓库,按需拉取。
- **当前(Bazel)形态**:OEM 在自己仓库写 `fuchsia_product_configuration`(JSON)——`platform` 键(平台合同:build_type / feature_set_level / storage…)+ `product` 键(自由面:session、base_packages…);再以 `fuchsia_product` 规则把 product_config × board_config × 平台工件(Assembly Input Bundle, AIB)组装成镜像,`fuchsia_product_bundle` 打成可 `ffx emu start / target flash` 的产品包(product_bundle_codelab,已在 fuchsia 主树核)。
- **platform 键的两个核心枚举**(两源:codelab + `src/lib/assembly/config_schema/src/platform_settings.rs` 源码):
  - `feature_set_level`:**embeddable**(不自更新、只有 /bootstrap 子集)/ **bootstrap**(可启动、仅串口、无 netstack/存储驱动,板级 bring-up 用)/ **utility**(最小含 /core realm,恢复类系统)/ **standard**(完整 Fuchsia,默认);
  - `build_type`:**eng / userdebug / user**(RFC-0115 体系;userdebug/user 下平台配置的合法项被收窄,源码注释自证)。
- **session = 产品体验顶级组件**:产品的 UI/交互外壳是一个普通组件,由 product 键指定 URL——换 shell = 换一个包,不动平台(codelab 原文:"A session is the top-level component that defines the product's user experience")。
- **平台协议留槽**:平台定义 FIDL 协议(如 fuchsia.web),实现由产品侧插入(workbench 在拓扑里给 fuchsia.web 留位但不给实现;产品可用自己的实现替换,RFC-0220 原文)——「平台定协议、产品供实现」。

### 1.3 特性启用四模式与「驱动 = 交集」语义

官方 codelab(implementing_platform_feature)给出平台特性上线的四种合法路径,这是一个可直接抄的合同设计:

| 模式 | 语义 | 机制 |
|---|---|---|
| 产品显式 opt-in | 产品配置里开 flag | `platform.<subsystem>.enabled` |
| 档位自动含 | 所有 eng 产品自动带 | AIB `auto_include_in = ["utility::eng"]` |
| 板驱动 | 板声明硬件能力,产品即得 | `fuchsia_board_configuration(provided_features=[...])` + 子系统 `context.board_config.provides_feature(...)` |
| 能力 + 显式 | 两者同时满足才上 | 条件与 |

配套的关键裁决(RFC-0220 原文):**最终镜像里的驱动集合 = 产品请求的特性 ∩ 板的硬件支持(intersection)**——产品要蓝牙但板没有,不会把蓝牙栈编进去;板有蓝牙但产品不要,也不编。这把 product/board 的正交性落实到了驱动粒度。

同时 codelab 给出**特征放置准则**:平台特征必须实现在 fuchsia.git 且「generic enough that it can be enabled on multiple products or boards」;单产品特有的功能不属于平台——「It is critical to keep the platform generic」。这是防止平台被产品需求腐蚀的守门条款。

### 1.4 core realm 拼装(RFC-0089)与配置面收敛

- **core realm 变体(RFC-0089)**:CFv2 的 core.cml 拆为公共 base + CML shard(子组件 + 能力路由片段),产品按需拼装;GN `core_shard()` 目标化。动机原文:单一 core realm 导致「components existing that have no purpose」+「overly broad capabilities…union of all product configurations」。——组件拓扑按产品裁剪,而不是全量并集。
- **配置面收敛**:旧 config-data(按包名投配置文件)被 RFC-0182 判死,理由是「以包名为未强制契约的远距离作用(spooky action at a distance)……包名不是能进 SDK、能版本化的稳定标识」;替代链 = 结构化配置(RFC-0127/0146:配置 schema 写进组件 manifest,类型化、校验)→ 父组件 overrides(RFC-0215)→ Configuration Capabilities(RFC-0242:配置作为能力路由,受同一套能力语义管)。**教训直译(推断)**:给 OEM 的配置面必须是 schema 化、版本化、可路由的,散文件投递必死。

### 1.5 兼容性保障机制

- **CTS(Compatibility Test Suite)**:RFC-0015 立项、RFC-0141 定流程——针对公开 ABI/API 面的兼容测试套件,由平台方维护、对 SDK 消费者跑;这是 Fuchsia 生态的兼容执法器。
- **SDK 分级暴露**:RFC-0165 定 SDK categories,RFC-0268 更新——接口按 public/partner/internal 分级,产品/OEM 只能依赖承诺级别内的面。
- **ABI revision 编码进包(RFC-0135)**:包元数据携带系统 ABI revision,版本错配在分发/安装期即拦。
- **树内树外等价(RFC-0220 Requirements)**:所有树内产品以 SDK companion image 分发、用同一套工具在树外工作;所有产品在基础设施中自动测试。

### 1.6 四元组

| 维度 | 内容 |
|---|---|
| **定制单元** | 组件包(fuchsia-pkg);产品配置 JSON(platform/product 双键);board 配置(GNI/Bazel);core shard(CML 片段);AIB(平台工件包) |
| **允许改什么** | 选 feature_set_level × build_type;开/配平台子系统;指定 session(整体换体验外壳);加产品自有组件包与平台协议实现(fuchsia.web 槽);板级驱动/内核参数;结构化配置值(合同内) |
| **禁止改什么** | 不改平台源码(平台只以二进制 AIB 进产品);树内不得加产品特有件(平台通用性守门);生产产品不得削 minimal(README 原文);不得依赖 SDK 承诺级别外的接口;userdebug/user 下部分平台配置项被禁(源码自证) |
| **兼容性保障** | CTS 兼容套件 + SDK 分类承诺 + ABI revision 进包 + 树内树外同工具链 + 产品全部自动测试(RFC-0220 Requirements) |

## 2. QNX/车载:接口契约 + 分层产品 + 认证变体

闭源微内核,但「定制面」从第一天就是产品形态的一部分。仓库底稿 `research/06-QNX-Neutrino.md` 已给内核侧证据,本节只补 OEM 定制面。

### 2.1 BSP = 契约化交付的板级件

- 官方《Customizing a BSP》(SDP 7.1 文档):「While QNX provides Board Support Packages (BSPs) for many common platforms and their individual variants, in some cases, you need a BSP for a board that QNX does not provide. If this is the case, you can modify a QNX BSP or develop your own」;开发流程明确「BSP development begins with a reference BSP from QNX」。BSP 定制面 = OS 镜像 buildfile、startup 代码、graphics/I2C/USB/网络/串口/SPI 驱动(该书目录即合同清单)。
- **驱动零特权耦合**:resmgr 三层框架(dispatch/resmgr/iofunc)让驱动 = 填 POSIX 函数表的用户态服务器,「no magic or private interface between the kernel and a resource manager」(`research/06` §3.2 引 qnx.com 原文)——OEM 写驱动不碰内核,接口契约就是公开 ABI 文档(SDP 6.4/7.1/8.0 三版文档树全公开)。
- **procnto 例外**(`research/06` §2):进程/内存/路径名管理住在与内核同地址空间的 procnto 里,OEM 不可改——闭源边界天然清晰。

### 2.2 分层产品栈与认证变体

分层(每层独立产品、独立合同):

1. **SDP**(内核+procnto+工具链):BlackBerry 按 SDP 版本发布(6.x/7.x/8.0),runtime 版税模式(`research/06` §1);
2. **QNX Hypervisor**:混合关键性隔离,独立产品——车载把 QNX/Android/Linux guest 各自隔离的载体;
3. **平台层中间件包**:如 QNX Platform for ADAS(SDP 7.1 文档树有整书系列:com.qnx.doc.adas.arch / getting_started / system_services),2026 年又有面向 SDV 的 Alloy Kore 基础软件包(`research/06` §1)——OEM 买的是「平台件组合」而非「改平台的权利」;历史上还有 QNX CAR 车载信息娱乐平台(现役状态以 ADAS/Alloy 线为主,**待核实**);
4. **OS for Safety 认证变体**:TÜV Rheinland 认证 ISO 26262 ASIL D / IEC 61508 SIL 3 / IEC 62304 Class C,与商业版「同源不同默认值」(procnto safety 版,`research/06` §3.6)——**认证作为产品变体而非代码分叉**,这是闭源世界「合规不改码」的范本。

### 2.3 四元组

| 维度 | 内容 |
|---|---|
| **定制单元** | BSP(参考 BSP 起步:startup + 驱动 + buildfile);resmgr 驱动(用户态服务器);商业中间件包(Hypervisor/ADAS 平台件);认证变体(选配) |
| **允许改什么** | 新板 bring-up(startup/设备驱动/镜像拼装);应用与中间件;Hypervisor guest OS;以上全部经公开 ABI,不碰内核 |
| **禁止改什么** | 内核与 procnto 二进制不可改(闭源,源码仅商业 source license 客户可看,`research/06` §4);安全认证场景须用认证变体;接口面 = 公开文档 ABI(越过 ABI 依赖私有行为不在支持合同内——**推断**,由商业合同而非公开条文执法) |
| **兼容性保障** | 三版全公开的 ABI/文档树;TÜV 认证(ASIL D/SIL 3/Class C);BlackBerry 版本节奏与 runtime 版税把「内核升级权」留在平台方;45 年二进制连续性口碑(**推断**,无官方兼容承诺条文,待核实) |

## 3. Windows OEM:内核永不动,定制全是外围包

桌面 PC 是「OEM 规模化定制 + 平台统一升级」共存最久的样本。证据全部来自 learn.microsoft.com 官方页。

### 3.1 定制面全景:三个 XML + 一块注册表 + SMBIOS

官方 Customizations for desktop devices 门户页给出的定制清单本身就是合同:

| 定制项 | 载体 |
|---|---|
| 任务栏 | TaskbarLayoutModification.xml |
| 开始菜单布局 | LayoutModification.xml |
| OOBE(首次开机体验) | OOBE.xml + OEM 注册页 + OEM 许可条款附加 |
| 深色模式 / Get Help / 颜色 | Unattend.xml |
| 品牌支持信息 | 注册表 OEMInformation(unattend 配置) |

- **OEMInformation 字段演化是个精妙样本**(unattend 参考页):现役字段 SupportAppURL / SupportProvider / SupportURL / TradeinURL / RecycleURL;Logo / Manufacturer / Model / SupportHours / SupportPhone 已弃用——厂商名与型号改为从 **SMBIOS(msinfo32 的 System Manufacturer/Product Name)**读取,即品牌数据收敛到标准固件数据合同,镜像里的品牌定制面反而收缩。
- **OOBE 合同**:OEM 可加注册页、许可条款、HID 配对引导;但 OOBE 流程骨架(语言→区域→网络→EULA→账号→隐私设置)由微软定义,部分屏幕官方明言「not customizable」(OOBE screen details 页)。
- **云页面机制**:OOBE 部分页面由云服务下发,「can be rolled out…at any time」——平台方对体验的持续控制权保留(OOBE 总览页原文)。

### 3.2 驱动:签名门 = 兼容执法

- 64 位 Vista 起**内核态驱动必须签名才能加载**;Win10 起内核驱动必须经 **Hardware Dev Center 用 EV 证书提交签名**(driver-signing 页原文:「the Windows Hardware Developer Center Dashboard must sign kernel-mode drivers. The process requires an extended validation (EV) certificate」)。微软成为内核态代码的唯一签发者——OEM 驱动想进系统,先过微软的测试与签名。
- **WHCP(Windows Hardware Compatibility Program)**:用 **HLK(Hardware Lab Kit)测试框架 + 官方 playlist** 判定兼容性,提交走 Dashboard(WHCP 官方页)。测试在 OEM 侧跑、认证由平台方裁——「实验室可复制的标准清单」模式。
- **升级主权**:OS 更新经 Windows Update 统一分发;OEM 驱动亦经 Dashboard/WU 分发(分发细节**待核实**,签名与 Dashboard 门槛为双源确认)。

### 3.3 四元组

| 维度 | 内容 |
|---|---|
| **定制单元** | 应答文件(unattend.xml)、布局/OOBE XML、注册表 OEMInformation、SMBIOS 固件数据、预装应用、签名驱动包(INF) |
| **允许改什么** | 品牌(支持信息/壁纸/主题/任务栏/开始布局)、OOBE 附加页与预装、驱动(过 WHQL)、固件数据 |
| **禁止改什么** | 内核与系统二进制不可改(OEM 渠道无源码交付);无微软签名内核驱动不得加载;OOBE 骨架与指定屏幕不可定制(官方明言) |
| **兼容性保障** | 内核驱动强制 Dev Center 签名(EV 证书);WHCP+HLK+playlist+Dashboard;品牌数据标准化(SMBIOS);OS 升级权归微软(WU) |

## 4. Yocto/嵌入式 Linux:layer 叠加,而非 distro fork

### 4.1 layer 模型

- 官方定义(yoctoproject.org Compatible 页):「The Layer Model simultaneously supports collaboration and customization. Layers are repositories that contain related sets of instructions that tell the OpenEmbedded Build System what to do」——**layer 本身就是仓库,协作与定制同一机制**。
- 机制(dev-manual「Understanding and Creating Layers」):
  - `bitbake-layers create-layer` 生成标准骨架(conf/layer.conf + 示例 recipe);
  - **BBFILE_PRIORITY**:同名 recipe 出现在多个 layer 时按优先级取一个——冲突解决规则内建;
  - **LAYERDEPENDS / LAYERSERIES_COMPAT**:层依赖与版本代兼容声明;
  - **.bbappend:只覆盖原 recipe 需要改的部分**(「use append files (.bbappend) to override only those parts of the original recipe you need to modify」);官方最佳实践把「复制整个 recipe」列为反模式,把机器专用文件放进 BSP layer 的 machine-specific 路径。
- **定制增量保持可 rebase 的形态**:上游层升级时,append 增量仍适用;这是「叠加优先于复制」的工程收益(前半句为文档事实,后半句为**推断**:收益分析非官方原文)。

### 4.2 治理:Yocto Project Compatible

- YP Compatible 标志授予「appropriate products and software components (BSPs, other OE-compatible layers, and related…)」(官方页原文)——生态兼容以认证/标志方式背书,而非强制。

### 4.3 与「distro fork」模式对照

- layer 模式的对立面是直接 fork 发行版仓库(嵌入式 Linux 圈长期存在的 vendor tree 模式;具体案例对照属 02 号稿反面证据范畴,此处不展开)。结构性差异(**推断**,基于机制对照):fork 把升级责任转移给 OEM(每次上游发版要手动合并),layer 把定制压缩为可声明的增量(优先级+append+依赖),升级责任留在上游节奏内。

### 4.4 四元组

| 维度 | 内容 |
|---|---|
| **定制单元** | layer(仓库):recipe(.bb)+ append(.bbappend)+ conf(machine/distro 配置) |
| **允许改什么** | 加新 recipe;append 增量修改上游 recipe(变量/文件路径);BSP 层(机器专用);发行版策略层(distro conf);镜像类型 |
| **禁止改什么** | 无强制法律边界(开源构建系统);约束 = 官方最佳实践(append 优先于复制、machine 文件归位)+ 层优先级纪律 + LAYERSERIES_COMPAT 版本兼容声明;违规代价是升级时自定义崩溃(**推断**) |
| **兼容性保障** | YP Compatible 认证;LAYERSERIES_COMPAT/层依赖声明;官方文档化的冲突解决规则(BBFILE_PRIORITY);上游-first 的生态文化(**推断**) |

## 5. OpenHarmony:三段式(芯片适配 → 设备/产品开发 → 兼容性测评)

仓库底稿 `research/03-OpenHarmony内核.md` 已覆盖内核侧;本节补 OEM 定制面。官方文档结构本身就是三段式:

### 5.1 芯片适配层:device/ 目录 + config.gni

- **芯片解决方案 = 一个特殊的部件**,源码路径规则 `device/{开发板}/{芯片解决方案厂商}`,含 hals(OS 南向接口适配)、linux/liteos 内核版本配置;**config.gni 全局可见**(kernel_type/kernel_version/board_cpu/board_arch/工具链/编译选项)——编译系统级合同(官方《芯片解决方案》文档)。
- 移植指南按系统分档成体系(porting-minichip-* 轻量、porting-smallchip-* 小型、standard-system-porting-guide 标准),以芯片厂商为主角。

### 5.2 产品定制层:vendor/ 目录 + config.json

官方《产品解决方案》文档:**产品解决方案源码路径规则 `vendor/{产品解决方案厂商}/{产品名称}`**,目录合同:

```
vendor/company/product/
├── config.json        # 编译主入口:开发板、OS 部件、内核配置
├── init_configs/      # rcS/Sxxx/fstab 脚本 + init.cfg(服务启动)+ hals(OS 适配接口)
├── fs.yml             # 文件系统镜像打包规则(rootfs/userfs)
└── BUILD.gn           # 产品编译入口
```

- **产品配置 = 部件列表拼装**:「通过产品配置文件配置一个产品包含的部件列表,部件不同的产品配置可以复用」(subsys-build-all);编译前对 device_company/board/kernel_type/kernel_version/subsystem/component 做有效性检查——**清单错误在编译期拦截**。
- **部件模型**:subsystem → component → feature 三级;系统类型(mini/small/standard,最小内存 128KiB/1MiB/128MiB,device-dev-guide 自述;与 `research/03` §2 表一致口径)决定必选部件集,OEM 在其上加可选组件。
- **驱动**:HDF 框架 + HCS 配置化设备描述,内核态/用户态部署位置与内核形态正交(`research/03` §3.8)。
- **工具链**:hdc = 官方设备调试连接器(gitee openharmony/developtools_hdc,Apache-2.0,「提供设备连接能力与命令行工具」)。

### 5.3 兼容性测评与发行版模式

- **兼容性测评**:开放原子基金会体系,1700 余款产品通过测评(openatom.org,`research/03` §1 引)——第三方权威背书,生态准入事实门槛。
- **发行版模式**:开源版(OpenHarmony)与商业发行版(华为 HarmonyOS、深开鸿/软通等厂商系统)分层并行;商业版可持闭源增值件(如鸿蒙微内核不开源,`research/03` §6 争议项)——**「开源底座 + 认证测评 + 厂商发行版外壳」三件套**。
- 节奏治理:每年两 Release + 两年一 LTS(gitee release-management 路线图,`research/03` §1)。

### 5.4 四元组

| 维度 | 内容 |
|---|---|
| **定制单元** | 部件(component);芯片解决方案(device/board 特殊部件);产品解决方案目录(vendor/...);HCS 驱动配置;hdc 工具链 |
| **允许改什么** | 按系统类型选必选集 + 增选部件;板级适配(hals/驱动/init 脚本/内核版本选择);文件系统与启动配置;商业发行版可加闭源外壳 |
| **禁止改什么** | 实际边界主要是结构性的:标准系统绑 Linux 内核(内核形态不可换档,`research/03` §6);LiteOS 档驱动/FS 在内核态;官方无「禁改清单」条文(开源仓库可 fork),约束靠兼容性测评与版本节奏(**推断**) |
| **兼容性保障** | 编译期部件有效性检查;兼容性测评(开放原子,1700+ 款);系统类型三档合同;SIG-Release 版本节奏 + LTS;HDF/HCS 把驱动差异压进配置 |

## 6. Zephyr:devicetree + Kconfig + module——配置面定制的极致

仓库底稿 `research/09-Zephyr.md` 已覆盖内核与构建;本节补 module/树外板治理。

### 6.1 module:仓库外代码的编译期并入

官方 Modules 文档(doc/develop/modules.rst,主树快照):

- **准入条件**:模块必须有「own life-cycle outside the Zephyr Project——reside in its own repository, and have its own contribution and maintenance workflow and release process」;**「Zephyr modules should not contain code that is written exclusively for Zephyr. Instead, such code should be contributed to the main zephyr tree」**——专为 Zephyr 写的代码必须上游化,模块位只留给真正独立的项目(芯片厂 HAL、加密库、FS、IPC 库等)。
- **机制**:`zephyr/module.yml` 声明模块名与构建入口(cmake/kconfig 根);CMake/Kconfig 变量 `ZEPHYR_<NAME>_MODULE_DIR` 自动生成;`ZEPHYR_EXTRA_MODULES` 手动追加;west manifest 管理版本锁定(west projects ≠ modules,但 west 负责发现)。
- **默认清单治理**:进默认 manifest 的模块须 TSC 批准 + 许可合规 + 「a Zephyr developer that is committed to maintain the module」。
- **binary blobs 显式声明**:模块可声明二进制 blob(如厂商 HAL 固件位),构建期可见可审(blob 政策段)。

### 6.2 board:板卡 = 数据

- board.yml(HWMv2)元数据 + devicetree + Kconfig 构成一块板;树外板经 BOARD_ROOT 并入(board_porting 文档:「Convert the out-of-tree board to the current hardware model (recommended)」);shields(overlay 复用)使 4.4 单版新增 121 块板(`research/09` §3.6)。
- 板级定制几乎全是**数据**(DTS/绑定/Kconfig)而非代码——配置面定制的极致形态。

### 6.3 四元组

| 维度 | 内容 |
|---|---|
| **定制单元** | module(独立仓库 + module.yml);board 目录(board.yml + DTS + Kconfig);devicetree overlay / shield;Kconfig 片段 |
| **允许改什么** | 加模块(厂商 HAL/中间件,编译期并入);加板(DTS/Kconfig 数据);配置裁剪(Kconfig 编译期) |
| **禁止改什么** | 专为 Zephyr 的代码不得藏进模块(官方政策原文);默认清单模块须 TSC 认可 + 许可合规 + 维护承诺;运行时不可换(静态单映像,`research/09` §2) |
| **兼容性保障** | west manifest 版本锁定;module.yml 契约 + 自动生成变量;blob 显式声明;半年一版 + LTS 线的版本纪律(`research/09` §1);板/模块不触碰内核源码树 |

## 7. 快扫:Genode Sculpt 与 Tizen(一段带过)

- **Genode Sculpt**:组件框架 Genode 上的桌面系统,「fairly minimalistic and generic base system」起步,用户在线组合组件(网络/存储/GUI/运行时管理),「Making customizations permanent」持久化定制、**「Reproducing the system from source」整系统可从源码复现**(Sculpt 25.10 官方文档)。模式:**平台方只造积木,集成者(用户/OEM)组装**,定制=组合选择而非改码;Genode 商业模式即「按客户组装场景收费」。对微内核同源的 BerryOS 有参照价值:能力路由 + 组件清单本身就能表达一个「产品」。

## 9. 跨范式共性提炼(基于上表的归纳;泛化表述为推断)

1. **定制面必须是合同,不是惯例**。六家全部把「可以改什么」编码为机器可读/可校验的载体(schema 化 JSON、unattend 模式、layer.conf、config.json、module.yml、ABI 文档)。惯例式定制面(安卓早期那种「能编过就行」)没有出现在任何正面样本里。
2. **平台与产品正交是结构性前提**。构建参数都是二元组;平台的升级权与产品的定义权分属两方,靠组装点衔接。凡是产品定义混进平台仓库的(Fuchsia Global Integration、Workstation 时代),都被官方文档记录为教训。
3. **「禁止改什么」不靠禁令文本,靠交付形态**。闭源(QNX/Windows)天然不可改;开源(Fuchsia/Yocto/Zephyr)靠「平台只以二进制工件+配置合同交付」「append 优先于复制」「专码上游化」的机制让改平台成为没必要的高成本路径。安卓的反面是:交付形态本身就是一棵邀请你改的源码树(02 号稿)。
4. **兼容执法三件套:契约测试 + 签名/认证 + 版本权**。CTS/HLK/兼容性测评管「行为兼容」,签名门(WHQL/Dev Center)与认证(TÜV/YP Compatible)管「准入」,平台方掌版本节奏管「升级不碎片」。三者缺一,前两者都会退化成纸面承诺。
5. **个性出口收敛于「大槽位」**:session/shell、OOBE+预装、发行版外壳、board 数据。差异化发生在平台预留的替换点,而不是框架内部。槽位之外的定制欲望,被引导为「贡献组件回平台」(Fuchsia/Zephyr 上游化政策)。

## 10. 对 BerryOS 的可移植机制清单(只列机制,不做方案——方案归 04 号稿)

以下每条都能在上文找到出处;是否采纳、如何裁剪是 04 号稿与 ADR 的事。

1. **(product, board) 构建二元组** + Base/Cache/Universe 三依赖分集(§1.2)。
2. **产品配置双键**:platform 键 = schema 化平台合同(枚举+开关+参数),product 键 = 自由面(session/自有服务/预装);配置面进 ABI 治理分级(§1.2、L0–L4 可挂靠)。
3. **feature_set_level 式能力档位枚举**(embeddable/bootstrap/utility/standard 同构物)+ build_type 三档(eng/userdebug/user 同构物)(§1.2)。
4. **特性启用四模式合同**:产品显式 opt-in / 档位自动含 / 板能力声明驱动(provides_feature)/ 能力+显式双门(§1.3)。
5. **驱动集合 = 产品特性 ∩ 板硬件支持**的交集语义(§1.3)。
6. **平台通用性守门条款**:「单产品特有件不得进平台」的放置准则 + 树内只留参考产品、生产产品树外组装 + 「对最小产品只准加不准减」(§1.1/§1.3)。
7. **服务拓扑拼装**:命名空间/服务清单 base + shard 片段化(core realm 模式),按产品裁剪能力路由(§1.4;与 BerryOS 路径命名空间直接同构)。
8. **结构化配置**:组件配置 schema 化(类型化+校验)+ 父级 override + 配置即能力(受能力语义管),废弃散文件投递(§1.4)。
9. **兼容性测试套件(CTS 等价物)+ 接口分级暴露(public/partner/internal)+ ABI revision 编码进包**(§1.5;与 .bap/.sig 信封及 berry-sys 版本域可直接拼)。
10. **OEM 交付物 = 组件包清单 + 签名**(ed25519 链可承载 OEM 身份与设备型号绑定),驱动/OEM HAL 走「独立仓库 + module.yml 式契约 + blob 显式声明」(§6.1、§1.6)。
11. **签名门 + 实验室测试清单准入**(WHQL/HLK 同构物:OEM 件过标准清单才准入)与**第三方兼容性测评背书**(开放原子同构物)(§3.2、§5.3)。
12. **叠加增量优先于复制**:若开放源码级定制,采 layer/append 式叠加与内建优先级冲突规则(§4.1)。
13. **认证变体而非代码分叉**:合规场景(未来工业 RT)用「同源不同默认值」的 safety 变体(§2.2)。
