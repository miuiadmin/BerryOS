## §0 摘要（一屏版）

- **槽位合同 = 四件套**（§1）：能力清单 + wire op 表 + 语义合同（时延/错误码/失败隔离义务）+ conformance 用例集。合同文档做成 **`tools/slots.toml` 单源（暂名）**，对照 `tools/abi.toml` 五面生成先例（:1-27）产「合同 md / 协议 crate 断言 / conformance 骨架 / BCTS 清单条目」四面——「五面生成」的既有纪律直接复制到合同面。两个字段级实例：**fsmgr 位**（fsproto 10 op 全表 + 挂载语义 + 掉电原子性三档枚举）与**显示驱动后端位**（HDI 四 op——「三口」为系列惯称，wire 实为 REG_VBLANK/VBLANK_WAIT/PREPARE/COMMIT 四 op（guiproto :79-86）——时序合同/像素格式协商/vsync 义务，现役第一实现 = ramfb 软 vsync 退化形（guifbd :659「wire 零改动」））。
- **product 清单 schema v0**（§2）：`platform` 键（合同面：arch/feature_level/build_type/storage/boot.params）+ `product` 键（自由面：预装集/品牌资源/默认策略/launcher/替换声明）双键结构，未知键硬拒；每键给类型/校验规则/消费方。**ADR #42「启动配置参数表」落点 = `[platform.boot] params 子表`**（合一提案，§2.5）。
- **berry-assemble 组装管线**（§3）：输入（平台工件 + product 清单 + OEM 三包）→ 步骤（清单校验 → 板级选择 → 白名单构建期校验 → rootfs 条目解析 → cpio → 镜像 → 签名/度量）→ 输出（确定性镜像 + manifest.txt 侧产物）。改造清单落到 justfile 行号：mkcpio 47 条显式映射（:317-376）参数化、image 的 `--size-mib 96` 硬编（:1086）改读清单、`IMAGE` 常量（:1032）按产品命名。**mkimage 的 `--size-mib` 与 manifest.txt（SHA-256+rollback_index，格式 v0 已冻 2026-10-30）已经是组装管线的现役地基**——本设计是参数化与外化，不是重造。

- **现实约束扩容路径**（§5）：APP_SLOTS=9 / 96MiB 盘容 / type 词表恒 "app" / FILE_COUNT_MAX=9 等现实在 v1→v2 各刀松绑；每项给「现在预埋 1 行 vs 将来改 1 周」的代价对照。**最便宜的刀是盘容**（`--size-mib` 已参数化，清单化零成本）；**最贵的刀是 type 词表**（双侧同步义务横跨 mkapp/berry-manifest/appd/devmgr 四点）。

## §1 槽位合同文档规范（v0 草案）

### 1.1 合同 = 四件套（结构定义）

04 号 §2.2 已把替换面契约定义为三件套（能力/wire 接口/消费侧链接 ABI）。本节把它下沉为**可开工的文档形态**：每个可替换槽位一份合同，合同 = 四件套：

| 件 | 内容 | 机器形态（提案） |
|---|---|---|
| ① 能力清单 | 该槽位被授予的 handle 全集（设备能力/MMIO 窗/端点/资源池）+ 授能路径（谁铸、何时授、如何回收） | 合同文件 `[capabilities]` 节；对照驱动模型 `[hw]` 节（`docs/驱动模型设计-v1.0.md:33-41`）与 svcmgr gift 链现役实践 |
| ② wire op 表 | 该槽位必须实现的 op 全集：op 号、请求/应答字节布局、随行 handle 数、错误码域、版本号 | 从协议 crate 单源生成（§1.2）；与 L1 add-only 纪律绑定 |
| ③ 语义合同 | 时延义务（如有）/错误码语义/失败隔离义务/并发模型（串行 or 并发）/帽常量（不得收窄） | 合同文件 `[semantics]` 节；conformance 用例的断言来源 |
| ④ conformance 用例集 | 每合同一组用例：合法 op 序列、非法 op 拒绝、帽执法、语义断言 | 用例 id 进合同文件；实现进 BCTS L1（07 号 §6-1/6-2：冻结测试件 + PlaSA 式机器可读清单） |

**为什么是这四件**（推断，锚证据）：AUTOSAR 把「配置合同」拆成交换格式 Schema + 语义约束 + 工具中立三件套（06 号 §1.2 autosar.org 原文转引），证明「机器可校验语法 + 机器可校验语义 + 任意工具可消费」是合同区别于惯例的最低结构；BerryOS 的槽位合同多出第四件（conformance），因为 BerryOS 替换发生在运行期服务进程（06 号 §1.5 对照表：隔离与热换更强 ⇒ 语义漂移风险也更高——同一 op 两种实现行为不同，04 号 §3.3 已点名为 BCTS L1 的核心标的）。

### 1.2 合同文档的机器形态：单源四面生成（对照 abi.toml 先例）

**提案**：合同单源 = `tools/slots.toml`（暂名；或每槽位一文件 `tools/slots/<slot-id>.toml`，取舍见 §6-Q1），由生成器产四面：

```
tools/slots.toml（单源，手改这里）
  ├── ① docs/槽位合同-v0.md          —— L2 承诺面文档（人读+评审）
  ├── ② 协议 crate 断言              —— 每槽位一份 const assert/锚点（钉住 op 号与帽
  │                                      常量，协议 crate 现有 const 集合的「合同视图」）
  ├── ③ conformance 用例骨架         —— BCTS L1 用例的枚举骨架（用例 id/分组/断言点）
  └── ④ BCTS 覆盖率清单条目          —— 07 号 §6-2 PlaSA 同构物：每槽位的 op 全表
                                         （「未测面」报表的数据源）
```

先例依据（事实）：`tools/abi.toml:1-27` 已实现同构机制——单源产五面（kernel/src/abi_gen.rs、user/berry-sys/src/abi_gen.rs、ABI 文档 §4 编号表、tools/abi.syz、arch/aarch64/src/wake_gen.rs），`just abi-check` 逐字节守卫挂 build/smoke 前置；改 ABI 的流程 =「改本文件 → `just abi-gen` → 提交（产物 diff 一并入册）」（abi.toml 头注 :19-22）。**合同面复制这套纪律，零新发明**。区别仅在：abi.toml 覆盖**常量层**（号/位/码/宽度，abi.toml :24-26 范围注记自认），合同还要覆盖**语义层**（③件的时延/隔离义务）——语义无法从 crate 单源生成，须在 slots.toml 里手写、由 conformance 用例执法（推断：语义合同的机器执法只能靠测试，不靠生成）。

### 1.3 合同怎么进 API 治理 L1/L2

对照 `docs/API治理章程-v1.0.md` §一分级（经 01 号 §2 转引）与 07 号 §6-9 分类执法链：

- **合同②件（op 表）**：归 **L1**（wire 协议 add-only + per-interface version）——本就在册，合同只是把「协议 crate 里的散装 const」升格为「有承诺文档的合同面」。op 号永不改义、只加新号；per-interface version 即 guiproto 现役 `VER_*` 常量族（guiproto :316-325，四域全=1）。
- **合同①③④件（能力/语义/conformance）**：归 **L2**（公开库 API 同级承诺 + N=3 废弃窗口）——语义合同变更（如掉电原子性档位定义改动）须走章程 §三废弃纪律。
- **未进合同的槽位内部细节**：L3/L4 零承诺——BCTS 不测（04 号 §4.2 原则 1：防伪契约）。
- **执法位**（提案）：`just slots-check`（暂名）挂 build 前置，四面逐字节对账（抄 abi-check）；conformance 用例集按 07 号 §6-1 冻结测试件模式随版本冻结。

### 1.4 实例一：fsmgr 位合同（字段级）

现役事实基座：fsmgr = RAM-fs + FAT12 经 vblk 的用户态服务（`user/bins/fsmgr`），协议 = berry-fsproto 10 op 严格串行 RPC；消费者 = bsh/fsclient/libc（端点经 svcmgr gift[3] 直递，`user/bins/svcmgr/src/main.rs:1292-1370` 预拉段）。

#### slots.toml 之 svc.fs 节（提案草案）

```toml
[slot.svc-fs]                       # 槽位 id（暂名；命名规范见 §6-Q2）
title        = "文件系统服务（fsmgr 位）"
interface    = "berry-fsproto"       # 协议 crate = 单源指向
ver_min      = 1                     # 实现必须 ≥ 此 per-interface version
consumers    = ["bsh", "berry-fsclient", "appd(v2)", "launcher"]  # 现役/规划消费者

[slot.svc-fs.capabilities]          # ① 能力清单（现役 svcmgr 预拉段的成文化）
blk_endpoint  = "optional"          # vblk 客户端端点（gift[3]；缺席 = RAM-only 降级，
                                   #   fsmgr fat.rs init 对 blk_h()==0 静默 None——svcmgr
                                   #   :1355-1358 注释原文）
console       = "required"          # stdout（诊断行）
mmio          = "forbidden"         # FS 服务不得持 MMIO 窗——块设备归属 drv.disk 位
appdata_tree  = "required(v2)"      # $appdata handle 授予链（ADR #45，v2 消费）

[slot.svc-fs.semantics]             # ③ 语义合同
rpc_model     = "strict-serial"     # 一请求一应答、队列深 1 用量、无乱序死锁面
                                   #   （fsproto 头注拓扑原文）
error_domain  = ["ST_OK=0","ST_NOENT=1","ST_FULL=2","ST_BAD=3","ST_NOEMPTY=4","ST_EXISTS=5"]
caps_frozen   = ["CHUNK=192","NAME_MAX=48","PATH_MAX=128","PATH_DEPTH_MAX=8",
                 "FILE_SIZE_MAX=16384","FILE_COUNT_MAX=9"]   # 帽=合同，替换实现不得收窄
power_atomicity = "declared-level"  # 掉电原子性档位（见下）：实现自声明、
                                    #   不得低于镜像清单要求的最低档
mount_semantics = "single-volume"   # 挂载语义（见下）
failure_isolation = "degrade-not-halt"
                # 服务崩 → 消费者端点 DEAD → 上层降级（现役：fs_h()==0 时 bsh 退三元
                #   gift「fs not available」不死 shell，svcmgr :1299-1302 注释；
                #   fsmgr RpcRes::Poison 降级先例 = 确定性失败优于无告警错数据，
                #   docs/驱动模型设计-v1.0.md:72）

[slot.svc-fs.conformance]           # ④ 用例集 id（骨架进生成物③，实现在 BCTS L1）
suite = "bcts-l1-fsproto-v1"
cases = ["roundtrip-all-10-ops",    # 合法 op 序列（PUT→GET 对拍、TRUNC size=0 建
         #                              空文件等——fsproto host 单测已有底子）
         "illegal-op-reject",       # 未知 op/截断/尾随字节 → None（fsproto 严格解析）
         "cap-enforcement",         # FILE_COUNT_MAX=9 / FILE_SIZE_MAX=16KiB 越帽=ST_FULL
         "blk-absent-degrade",      # blk 缺席 → RAM-only 降级且 ST_OK 路全通
         "power-atomicity-level"]   # 声明档位校验（组装期，非运行期）
```

#### 合同要钉死的三个语义面（任务书问题逐条回答）

1. **钉死哪些 op**：**全部 10 op 一个不可少**（OP_PUT=1/TRUNC=2/GET=3/LIST=4/LOOKUP=5/MKDIR=6/UNLINK=7/READDIR=8/STAT=9/STATFS=10，fsproto :70-88 常量段）——04 号 §4.3 基线 2「不得实现 fsproto 的一半」。替换实现的增量自由度只有：加新 op（走 L1 add-only，从 11 起编号）与**实现质量**（更快的树、更大的帽**上限**——下限被 caps_frozen 钉死）。
2. **挂载语义**：现役 = 单卷（FAT12 经 vblk）+ 卷级 STATFS（无路径参，fsproto :57-60）+ 空路径串=根寻址（读面三 op LOOKUP/READDIR/STAT 白名单，fsproto :66-69 头注）。合同钉死三条：**①单卷挂载模型**（v1；多卷=挂载点扩展走 v2 提案，接 namespace v3——`docs/IPC设计-v1.0.md:56-63`）；**②根不可写**（写面与 GET 拒空路径，同头注）；**③卷级几何真值义务**（STATFS 应答 21B 定长，total/spc/cluster_count/free_clusters/sector_sz 五字段必须为真值非估计——「df 面」的合同表述）。
3. **掉电原子性档位**（提案，现役空白）：现役 FAT MVP **无任何掉电原子性保证**（推断：FAT12 写路径无 journal/两阶段提交，仓库文档无掉电语义条目——这是诚实披露不是缺陷，FS MVP 定位如此）。合同引入**三档枚举**，实现自声明、组装期校验：

| 档 | 名称 | 义务 | 现役 |
|---|---|---|---|
| P0 | `none` | 无保证：掉电后卷可能不可挂载 | **FAT12 MVP 现役档** |
| P1 | `metadata` | 掉电后卷必可挂载、结构一致；最近数据写可能丢 | — |
| P2 | `data` | fsync 语义：已应答 ST_OK 的写在掉电后存活 | — |

   产品清单（§2）可声明 `min_power_atomicity`（如工业产品 = P1），组装器拒绝声明档位低于要求的 FS 服务包（构建期执法，零运行时成本）。**为什么现在就立法**（推断）：Android fs_mgr/EXT4 的教训是掉电语义事后补=格式锁死；BerryOS 在 FS 可换的第一天就把档位做成合同字段，替换实现（现代 FS）自带 P1/P2 时无需改合同——档位枚举是 add-only 的（可加 P3，不改 P0-P2 义）。

### 1.5 实例二：显示驱动后端位合同（字段级）

现役事实基座：HDI 域 = guiproto 四 op（**任务书与 01 号 §1.4 惯称「三口 reg_vblank/prepare/commit」，wire 实为四 op**：REG_VBLANK=0x40/VBLANK_WAIT=0x41/PREPARE=0x42/COMMIT=0x43，guiproto :79-86——本合同以源码四 op 为准）；第一实现 = guifbd 内 ramfb 软 vsync 退化形（guifbd :45「REG_VBLANK 存 event、VBLANK_WAIT park 到软 vsync 点」、:659「hdi 域分发：四 op 退化形（软 vsync；wire 零改动）」、:78 `SOFT_VSYNC_NS = 16_666_666` ≈60Hz）；第二后端 virtio-gpu 在排（ADR #51 后端序列，经 01 号 §1.4 转引）。ADR #50 立法「换实现不换契约」「像素格式烧进常量 = 移植性死刑禁」。

#### slots.toml 之 drv.display.backend 节（提案草案）

```toml
[slot.drv-display-backend]
title     = "显示驱动后端（HDI 位）"
interface = "berry-guiproto/hdi"     # hdi 域（op 0x40..0x43）
ver_min   = 1                        # VER_HDI = 1（guiproto :322-323）
consumers = ["guifbd(合成器)", "gui-wmd(中继,ADR #61)"]

[slot.drv-display-backend.capabilities]
mmio_window  = "board-dependent"    # 板级 MMIO 窗 VMO（virtio-gpu 需要；ramfb 不需要
                                    #   ——QEMU fw_cfg 面）。devmgr v2 授能
buffer_vmos  = "required"           # PREPARE 随行 1 buffer VMO handle（guiproto :298-299）
event        = "required"           # REG_VBLANK 随行 1 Event handle（guiproto :296-297）
console      = "forbidden"          # 后端不持 console——诊断走合成器

[slot.drv-display-backend.ops]      # ② wire op 表（从 guiproto 单源对账）
0x40 = "REG_VBLANK  req 4B [op][enable∈{0,1}][r16] + 1 Event handle → rep 1B"
0x41 = "VBLANK_WAIT req 4B 无参（阻塞）→ rep 16B [st=0][r24][seq u32][ts_ns u64]"
0x42 = "PREPARE     req 20B + 1 buffer VMO handle → rep 4B [st][slot u8]（slot<2）"
0x43 = "COMMIT      req 12B [op][slot u8][r16][target_ns u64] → rep 1B"

[slot.drv-display-backend.semantics]
# —— 时序合同 ——
vsync_cadence   = "declared"        # 实现自声明周期（现役软 vsync 16_666_666ns；真面板
                                    #   = 面板时序）。合同义务不是「必须 60Hz」，是：
seq_monotonic   = true              #   ① seq 严格单调增，每 vsync 恰 +1
ts_honest       = true              #   ② ts_ns = 名义 vsync 点（滞后追赶跳过已过点、
                                    #      不补偿积压 vsync——guifbd tick_vsync :292-296
                                    #      现役语义成文化；**不得伪造未来时刻**）
signal_on_vsync = "edge"            #   ③ REG_VBLANK 注册的 Event 每 vsync 沿 signal 一次；
                                    #      无 vsync 不虚假 signal（零唤醒不变量，guifbd
                                    #      :289-291「armed∧parked 双空后撤点」）
# —— 像素格式协商 ——
format_negotiation = "getinfo-bits + prepare-value"
                 # 协商在 present 域 GETINFO format_bits 位域（XRGB8888=1<<0 /
                 #   ARGB8888=1<<1 / RGB565=1<<2，guiproto :231-236）；hdi 域 PREPARE
                 #   携带 format **值**非位域，不在协商集 → ST_UNSUPPORTED 服务端拒面
                 #   （guiproto PrepareReq doc 原文）。合同钉死：**后端必须至少支持
                 #   XRGB8888**（ramfb fmt=1 基线，guifbd :839）；其余格式可选声明
prepare_lifecycle = "server-exclusive"
                 # PREPARE 应答 slot 后到 COMMIT 呈现完成前，buffer 采样权归服务端
                 #   （PREPARE_F_SERVER_SAMPLABLE 位语义冻结=0 不可采样，guiproto
                 #   :238-244——bit0 已认领、置位帧 encode assert 炸响/parse None）
# —— 失败隔离 ——
failure_isolation = "degrade-not-halt"
                 # 后端崩 → 合成器端点 DEAD → wmd/launcher 降级（#28 代号链）；
                 #   后端崩溃不得打穿内核（用户态驱动结构性保证，ADR #12/#46）
tear_free       = "required"        # COMMIT 原子换帧（真后端）或整帧拷贝（软后端
                                    #   ramfb 先例）——呈现不可撕裂是义务，实现路径自由
[slot.drv-display-backend.conformance]
suite = "bcts-l1-hdi-v1"
cases = ["reg-vblank-edge-signal",   # 每 vsync 恰一次 signal；静止期零 signal
         "vblank-wait-seq-monotonic", # 连续 wait 的 seq 严格 +1、ts_ns 单调
         "prepare-slot-cap",          # HDI_SLOTS_MAX=2 越帽拒（guiproto :272）
         "prepare-format-unsupported",# format 不在声明集 → ST_UNSUPPORTED 非 ST_BAD
         "commit-atomic-present"]    # COMMIT 后帧内容完整（tear-free 断言）
```

#### 时序合同/像素格式/vsync 义务——为什么这么钉（推断+锚）

- **vsync 义务钉「诚实」而非「频率」**：把「必须 60Hz」写进合同会把软实现（软 vsync 16.67ms 定时器）与真面板（59.94/90/120Hz）排除在外，合同即失弹性；钉「seq 单调 + ts 诚实 + 沿信号」三条不变量，任何频率的实现都合法，而消费侧（合成器按 ts 排帧）的假设被保护——这与 ADR #53「砍实现不砍协议位」同构（协议钉不变量、实现自由）。
- **像素格式协商钉「XRGB8888 必须支持」**：ramfb 第一实现即 XRGB8888（guifbd :839 QEMU ramfb fmt=1），合成器/wmd 代码路径已按 32bpp RGBX 族假设（guifbd :421「单格式：32bpp RGBX 族」）——把它钉为合同最小集 = 现役事实成文；扩充（RGB565 用于低档面板）走 GETINFO 位域协商，零合同变更。
- **第一实现即退化形是合同的资产**：guifbd 的软 vsync 把「wire 四 op 与 vsync 物理源解耦」已跑通（wire 零改动注释自证）——合同文档只需把这个解耦**成文**，virtio-gpu 后端接入时合同零改动（这正是「换实现不换契约」ADR #50 的机制兑现路径）。

### 1.6 两实例的共性钉子（生成器与执法要点汇总）

| 钉子 | fsmgr 位 | 显示后端位 | 执法点 |
|---|---|---|---|
| op 全集不可裁剪 | 10 op 全实现 | 4 op 全实现 | conformance `roundtrip` + 组装期 version 对账 |
| 帽常量不得收窄 | CHUNK/NAME_MAX/… 6 顶 | HDI_SLOTS_MAX=2 | 协议 crate 断言（生成物②） |
| 失败隔离 = 降级非停机 | fs 降级不死 shell | 后端崩 DEAD 降级 | conformance 失败注入用例 |
| 实现自声明档位 | 掉电原子性 P0-P2 | vsync 周期 | 组装期清单校验（§3.2 步②） |
| 能力面最小+禁持清单 | MMIO 禁持 | console 禁持 | 能力授能链（svcmgr gift / devmgr v2） |

### 2.3 platform 键与 product 键的分界依据

分界 = **承诺面与自由面**（04 号 §2.1 双键定义的直接字段化）：platform 键的每个枚举/开关都对应平台侧的**行为合同**（feature_level 决定预装最小集与能力基线；build_type 决定 sideload/调试面收窄；boot.params 键集是内核消费的冻结词表）——所以 platform 键 schema 归 L2 承诺、变更走章程；product 键是集成者自由（装什么、长什么样、默认什么），schema 只做结构校验不做承诺。这直接采 Fuchsia 的分法（platform 键 schema 化进 `platform_settings.rs` 源码执法，03 号 §1.2 两源核验）与 AUTOSAR 的「语义约束随格式同发」（06 号 §1.2）。

### 2.4 与 ADR #42「启动配置参数表」的合一提案

**现状**：ADR #42 立法「数字进启动配置参数表不写死」（docs/架构决策.md :51 原文），但该参数表的**机制面形态（谁写、内核哪里读）未见实现**——01 号 §1.1 已核（sched/src/ 现无外部参数表加载路径）。

**合一提案**：启动配置参数表 = `[platform.boot.params]` 子表，理由三条：
1. **消费半径相同**：参数表要到达「内核/早期服务」，唯一现役通道 = boot 链（fw_cfg/INITRD）——而 INITRD 正是组装器产物（mkimage --initrd，justfile :1085）。参数表进清单 → 组装器序列化成 INITRD 内定址段（如 `boot/params.bin`，定长 TLV），内核启动期按槽读取——不新增装载机制。
2. **治理半径相同**：参数表的键集必须 add-only 冻结（否则每次内核改常量都破兼容）——与 platform 键 schema 同一执法面（slots/清单 schema 生成器 + L2 废弃窗口），分两套必漂移。
3. **写入者相同**：能合法改这些数字的 = 产品集成者（OEM 调参正是 04 号 §5 矩阵第 4 行）——与 product 清单的作者同一人，两份文件 = 两个漂移点。

**反合一论点（如实记）**：内核参数有「上游也改」的双主风险（上游调缺省值 vs OEM 覆盖）——处理：params 键**缺省值归上游**（编译期常量仍是缺省）、清单**只存覆盖值**；上游改缺省 = OEM 清单不写该键即自然跟随（推断：这是 Fuchsia structured config 的 override 语义同构，03 号 §1.4 转引 RFC-0215）。是否合一 = §6-Q3（原样开放）。

### 3.1 输入 → 步骤 → 输出


### 3.3 host 侧 tools/berry --profile 与设备侧清单的分轨

现役事实：`tools/berry` 是 host 独立 workspace 的设备壳（单二进制三角色 CLI/GUI/session host + control.sock），持 `--profile phone/desktop/phone16` 等 profile 与 runtime pack（ADR #62 追记；tools/berry/README.md）——`berry shot --profile phone`、`just desktop`（用 out/berryos-portrait.img + tablet + 1080×1920@60）是**宿主侧显示几何/窗口形态参数**，不进客机。

分轨边界（提案）：
- **设备侧**（product.toml 消费）：镜像内容——预装/品牌/策略/板级/盘容。判据 = 这件事**改镜像字节**吗？
- **宿主侧**（berry profile 消费）：窗口几何/缩放/快捷栏/截图超时——**不改镜像字节**，只是宿主怎么看客机。
- **两轨的字段交集预警（推断）**：`just desktop` 消费 `berryos-portrait.img`（竖屏镜像）——「portrait 产品出竖屏镜像」同时影响两侧（镜像内容 vs 窗口几何）。分轨纪律：设备侧清单管**镜像产物**，宿主 profile 管**显示参数**，`berry run` 按 `--image` 文件名约定联动（现役约定俗成），**不共享 schema**——合流 = §6-Q8（开放）。

## §4 svcmgr 编排数据化

### 4.1 现役手写预拉链解剖（行号级，改造的起点）

svcmgr main.rs 的启动编排 = **硬编码的顺序预拉段**，每段四拍：`cpio_find(H_ROOTFS, b"bin/<name>")` → `channel_pair()` → `spawn_rootfs_elf(SpawnSpec{…})` → 失败显式回收 handle（防表槽泄漏）：

| 序 | 服务 | 行号 | 依赖（gift 链） | 失败降级（现役） |
|---|---|---|---|---|
| 1 | vblk | :939-1013 | H_MMIO 门（:953）；blk_b → gift[2] | `eco_skip(b"mmio absent")`；blk_cli=0 传递 |
| 2 | guifbd | :1015-1107 | H_MMIO 门；fb 自验 | 静默跳过零新行 |
| 3 | gui-wmd | :1109-1211 | **guifbd 交接件门**（:1112「rootfs 相 guifbd 门已跳」） | 静默跳过 |
| 4 | gfxdemo | :1213-1290 | wmd 的 wm_cli（:1160 换手） | 回收 wm_cli |
| 5 | fsmgr | :1292-1370 | **blk_cli → gift[3]**（:1338-1345，vblk 先起的理由 :941-943 注释原文） | fs_client=0 → bsh 退三元 gift |
| 6 | vnet | :1372-1426 | H_MMIO 门；net_b → gift[2] | eco_skip；NET_A=0 传递 |
| 7 | gui-inputd | :1428-1573 | H_MMIO 门；WMD_PUSH_B（wmd 先起） | 静默跳过（EFI 相） |
| 8 | stdhello | :1575-1600 | fsmgr（fs 让位判别器） | — |
| 9 | bsh | :2030 起（延后重排） | **fs_a_h 队列唯一读者**（:932-938 注释：app 批须排前面） | fs 缺席 =「fs not available」不死 shell |
| 10 | berry-launcher | :6421-6471（装配段） | WMD_PUSH_B/WM_CLI_DUP/FS_A_H/NET_A 四 static 源（:701-757） | 任一 0 = 装配静默跳过 |

三个结构性事实：
- **依赖图隐含在代码序与 gift 链**：fsmgr→vblk（gift[3]）、bsh→fsmgr（fs 端 dup）、wmd→guifbd、gfxdemo→wmd、launcher→wmd+inputd+fsmgr+vnet 四源——**没有任何一处显式声明**，全靠注释（:940-943「fsmgr 的 FAT 层要 blk 服务端端…⇒ vblk 必须更早」）与阅读顺序。换一个 FS/加一个驱动 = 改这段源码重编（01 号 §3 缺口 2 原判）。
- **降级已是系统性的**：每段失败都走「可见降级不 halt」——`eco_skip` 诊断行 / 0 端点传递（`fs_h()==0` 三元 gift）/ 静默跳过。这是失败隔离矩阵的现役雏形（推断：数据化时把这套语义保留为默认，不引入 halt 类）。
- **static 源 = 「留表即留命」的常驻端点池**：NET_A/WMD_PUSH_B/WM_CLI_DUP/FS_A_H 四个 AtomicU32（:701-757）就是手工维护的「provides 注册表」——launcher 装配从它现 dup 新别名。数据化后这张表应由声明生成（推断）。

### 4.2 编排声明面：服务包 manifest 的 `[slot]` 节（提案）

驱动模型已给驱动包 `[hw]` 节先例（`docs/驱动模型设计-v1.0.md:25-41`——match/mmio/irq/dma/provides 五键）。服务包对称加 `[slot]` 节：

```toml
# 服务包 manifest.toml 增量节（add-only，未知键硬拒同 manifest 纪律）
[slot]
id        = "svc-fs"                  # §1 槽位 id（合同对账键）
provides  = ["fs"]                    # 端点名（编排表内引用键；v3 起 = /svc/fs 路径）
requires  = ["blk"]                   # 依赖端点（缺 = 降级路径声明见下）
startup   = "base"                    # 阶段枚举 {critical, base, ui, app}
                                    #   critical = 失败 halt 候选（v0 无——全降级）；
                                    #   base = vblk/fsmgr/vnet 层；ui = guifbd/wmd/inputd；
                                    #   app = stdhello/bsh/launcher
on_missing_req = "degrade"            # 枚举 {degrade, skip, fail}（fsmgr 对 blk = degrade）
intent    = "utility"                 # 启动档（SpawnSpec.intent 现役字段成文化）
```

编排数据流：**声明随包走（包内 [slot] 节）→ 组装器合成总表（rootfs `etc/orchestr.toml`，暂名）→ svcmgr 读表按 startup 阶段 + requires 拓扑排序拉起**。 gift 链（谁把哪个端点 dup 给谁）由组装器从 provides/requires 推导生成接线表（推断：推导规则 = requires 名匹配 provides 名即接线；现役 gift 手工配线的成文化）。

### 4.3 启动依赖图形态与失败隔离矩阵

依赖图（提案，由 [slot] 声明生成；现役隐含图的成文）：

```
critical(预留)  base                     ui                    app
                vblk ──┐                 guifbd ──┐            stdhello
                       ├→ fsmgr ──┐      gui-wmd ─┼→ gfxdemo   bsh(依赖 fsmgr)
                vnet ──┘          │      gui-inputd┘           launcher(依赖 wmd+inputd
                                   │                             +fsmgr+vnet 四源)
                                   └→(fs 端)→ bsh/launcher
```

失败隔离矩阵（= 4.1 现役降级语义的成文化，非新设计）：

| 失败 | 后果边界 | 降级路径 | 依据（现役先例） |
|---|---|---|---|
| base 槽失败（如 vblk） | 只死自己 + 下游声明 degrade 的槽降级 | fsmgr RAM-only（fat.rs init 静默 None） | svcmgr :1355-1358 |
| ui 槽失败（guifbd） | wmd/gfxdemo 链静默跳过 | 0 端点传递 | :1112 注释 |
| fsmgr 失败 | bsh/launcher fs 面降级 | 三元 gift「fs not available」 | :1299-1302 |
| 服务运行期崩溃 | 代号 +1，handle DEAD（#28） | 消费者重试/重连（v2 appd 监督线） | 驱动模型 §3 表 |
| launcher 崩溃 | wm/fs 端点池不销毁（留表即留命） | 监督重启从源现 dup | :719-731 注释 |

**设计判断（推断）**：v0 编排数据化**不引入 restart/halt 语义**——现役「全降级 + appd 监督归 v2」的切面保持；数据化只把「谁先谁后、谁缺谁降级」从源码搬进数据。运行期监督（重启策略/退避）归 v2 appd（04 号 §6.2 已列），与本刀解耦——一刀只做一件事（justfile 小步纪律同构）。

### 4.4 v2 devmgr 接缝

devmgr（v2 最小面：DTB 枚举→池→匹配→授 MMIO 窗→注册 `/svc`，驱动模型 §5 阶段表）与本编排的接缝：
- **[hw] 与 [slot] 分节不合并**：[hw] = devmgr 消费（设备认领/授能）；[slot] = svcmgr/appd 消费（编排/接线）。驱动包**两节都有**（如显示后端包：[hw] 声明 mmio 窗申请，[slot] 声明 provides=["display"]）——各消费方各读各节，单一职责（推断：合并节 = devmgr 要懂编排、svcmgr 要懂设备，跨界耦合）。
- **接线交接**：v1 svcmgr 手工 gift → v2 起 devmgr 注册的 `/svc` 路径成为 provides 的解析物（namespace v3 后编排表 provides 名 → mount 路径直译）；编排表的端点名字段**前向兼容**（v1 = 内部接线表键，v3 = 路径前缀同构——`docs/IPC设计-v1.0.md:58` `/svc/fs` 即 `provides=["fs"]` 的未来形态）。
- **顺序权威**：devmgr 起来后，「拉起别人之前就要用的」豁免件判断标准（驱动模型 §4）与 startup 阶段对齐——critical 阶段的存在理由 = devmgr/appd 自己（推断）。

### 5.2 代价对照的规律（推断）

三条规律从上表归纳：
1. **参数化的债最便宜**（#2）：`--size-mib` 当年参数化的 1 行，今天清单化零成本——**「先参数化后清单化」是低债路径**；反之 #3 type 词表的消费端实装无法参数化预埋，只能「词表先行 + 消费后至」两刀走。
2. **双侧同步义务是债的放大器**（#1/#3/#5）：凡「双侧同步」头注的常量（berry-manifest 头注自认、mkcpio CPIO_PAD 四点同步 :29-32），扩容成本 = 同步点数 × 验证面——预埋的价值不是省改的时间，是**防止漏掉一个同步点**（历史判例：35/39/38 三口径打架，abi.toml :33-35 史注）。
3. **帽的松绑方向分两种**：数值帽（#1/#4/#5）可 add-only 抬升（词表纪律）；**结构性帽**（#6 静态 cpio、#7 单 launcher）只能换机制——预埋对后者无效，刀序规划才是解（诚实面）。

## §6 开放问题（原样列出，不替拍板）

1. **合同单源的文件形态**：`tools/slots.toml` 单文件 vs `tools/slots/<id>.toml` 每槽位一文件？槽位数量增长后单文件的合并冲突/审阅粒度如何取舍（abi.toml 单文件先例 vs 其规模尚小）。
2. **槽位 id 命名规范**：`svc-fs` / `drv-display-backend` 连字符串是否够用；与 v3 路径命名空间（`/svc/fs`）的映射规则是否 day-one 钉死。
3. **启动配置参数表合一**（§2.5）：`[platform.boot.params]` 与 ADR #42 承诺的参数表是否确认为同一件——上游缺省/OEM 覆盖的 override 语义（RFC-0215 同构）是否采纳；内核读取面（INITRD 定址段 vs fw_cfg 新键）选哪个。
4. **berry-assemble 的实现语言**：host 侧 Python（tools/ 族先例，mkcpio/mkimage/mkapp 全 Python）vs Rust crate（与 berry 工具同 workspace）——前者零新依赖上手快，后者类型系统扛 schema 演进。
5. **product.vendor/lineage 的发放机构**：04 号 §7-Q1 原样保留（谁分配、能否多级）；v0 组装器是否先接受任意字符串（无账本对账）——接受 = 无执法；不接受 = 无产品可组。鸡生蛋时序。
6. **build_type 收窄面的成文**：user 型下哪些清单键被禁（sideload 必禁，还有呢）——Fuchsia platform_settings.rs 的收窄清单（03 号 §1.2 两源）可参照，但 BerryOS 的键集不同，须本土化立法。
7. **launcher 转正刀序**（04 号 §7-Q13 原样保留）：bin/ ELF → .bap 的时点与 `product.defaults.launcher` 键的启用绑定。
8. **host profile 与设备清单的字段合流**：显示几何类字段（portrait/分辨率）两侧都有影子，是否在 v2 设备清单补 display 键后让 host profile 退化为纯「怎么看」。
9. **orchestr.toml 的信任面**：编排表进 rootfs = 进度量链；OEM 改编排表（加自有服务）是配置面自由还是须过 conformance（替换面义务）——「加一件」与「换一件」的边界在编排数据上的表达。
10. **conformance 结果的登记与时效**：替换包的 BCTS 结果挂在包版本还是 lineage（04 号 §4.4 相邻）；上游新版契约测试发布后旧结果的失效规则（07 号 §7-1 冻结件节奏题的具体化）。
11. **掉电原子性档位的最小档**：v1 产品清单是否允许声明 P1/P2（现役无实现可满足——声明即无包可组）还是 v0 只收 P0、P1/P2 词表先立（add-only 收宽先例：PREPARE_F_SERVER_SAMPLABLE 位认领零行为变更，guiproto :238-244）。
12. **预埋的执法**：§5 的「现在预埋 1 行」如何防止漂移——预埋项进 docs_guard 式审计（工具执法）还是只进设计文档（约定执法）；P5「执法先于开放」对预埋本身是否适用。

## §7 反面自检（如实写）

1. **本稿全是「提案」，零件已实施**：slots.toml/product.toml/berry-assemble/[slot] 节在仓库中均不存在——本稿是设计纸面，未经任何实现验证；§1 两实例的字段表从现役源码反推成文，**成文过程可能与实现漂移**（源码一行未改，但合同化叙事可能误解原注释——已逐条给行号供复核，仍不能替代实现期对拍）。
2. **语义合同的执法依赖 BCTS 立项**：§1 四件套的④件（conformance）在 BCTS 立项前是空位——没有测试的语义合同 = 纸面承诺（05 号 N5：执法先于开放）——**在 conformance 用例存在之前，任何槽位不得实际对 OEM 开放**（本稿设计前提，非结论）。
3. **svcmgr 数据化的重构风险**：§4 把 10 段手写预拉改读表，是五块中唯一动设备侧运行时的——svcmgr 是启动关键路径（04 号 §2.4-3 boot 豁免纪律相邻），数据化引入「读表-解析-排序」新失败面；现役手写版的每一拍（gift 链/回收/降级）都是实测踩坑的产物（注释里的判例密度可证），**数据化版本必须逐拍复刻这些语义而非简化**——简化即回归（判例：4-5 前置补丁的共享表错捐级联，IPC设计 :121 注释）。
4. **清单 schema 的膨胀风险**：§2 的键表已 17 键——v0 就要防 Fuchsia platform 键式增长（platform_settings.rs 已是巨 schema，06 号 §1.4「schema 巨大→工具即门槛」自认）；「platform 键最小集 + product 键自由」的纪律执行不严 = 三年后 BerryOS 版 ARXML（重配置面）。
5. **单源生成的边界**：§1.2 生成器覆盖常量层（abi.toml 同构），语义层靠手写 + conformance——「合同四面里有一面半是人写的」这个事实使 slots.toml ≠ 完全机器执法；宣称「合同机器可校验」时须限定为①②件 + ③件的枚举字段（诚实面）。
6. **外部参照的时点风险**：本稿直接外部依赖仅 Fuchsia 双键/收窄先例与 RFC-0215 override 语义（经 03 号核验，2026-11-10 快照）；Fuchsia assembly 体系自身仍在演进（RFC-0220 后树外组装是现行决策，但 Bazel 化仍在途）——参照的是机制不是稳定 API（推断标注已尽，漂移风险如实记）。
