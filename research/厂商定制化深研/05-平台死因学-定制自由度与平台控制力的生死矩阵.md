## §0 摘要（一屏版）

- **谱系与结局**：本篇覆盖 9 个失败/残局平台族（Windows Mobile、Windows Phone 7→Windows 10 Mobile、Symbian、MeeGo、Tizen 手机线、webOS、Firefox OS、Ubuntu Phone，外加 KaiOS「活着的残局」）与 3 个存活对照组（Android / iOS / HarmonyOS NEXT）。**纯放开（WM/Symbian UI 层）死于碎片与体验劣化，纯锁死（WP7/W10M、webOS）死于 OEM 离场与生态饥饿，巨头同盟（MeeGo/Symbian Foundation/Tizen）死于治理单点断裂，Firefox OS/Ubuntu Phone 死于与定制策略无关的生态因素**——四种死法在样本里各有至少两个实例。
- **最锋利的对照**：微软一家公司 2007–2017 年先后跑完两档。WM 6.x 放开定制（授权费每台最高 $25 + OEM 自换 UI 壳 + 微软不设界面边界）→ OEM 壳碎片化、体验劣化、iPhone/安卓冲击下 4 年美国市占 42%→3%（§2.1）。WP7 反向铁幕（chassis 规范钉死分辨率/芯片/六键、统一 Metro、OEM 差异化只剩硬件与预装）→ OEM 无差异可做且要付费，安卓免费且放开，OEM 用脚投票，最终 2017-10 官宣停更（§2.2）。**同一个平台方，放开碎死、锁死饿死，两次都不是「定制政策选错档位」这么简单——两次都缺了第三档：合同化定制面。**
- **失败模式四分类**（§4）：A 死于放开碎片（Symbian 三 UI 应用互不兼容、WM 壳碎片）；B 死于锁死无 OEM（WP 系列、webOS 单一 OEM 资金断裂）；C 死于巨头同盟治理（MeeGo 诺基亚一夜退出、Symbian Foundation 无独立工程能力、Tizen 手机跳票两年）；D 死于生态非定制因素（W10M 应用缺口与财务、Ubuntu Phone 无 OEM 无变现、Firefox OS 性能与定位）——**D 类诚实标注「定制策略无辜」**：本谱系中定制政策既不是死亡的充分条件也不是必要条件，它是「死亡方式的选择器」，不是「死活的决定器」。
- **收口推论**（§5）：中间路线（合同化定制）的必要条件集 N1–N7——合同化定制面、平台保升级主权、OEM 真实差异化出口、商业动机对齐、执法先于开放、无单点依赖、生态启动窗口。**每一条都有对应的死亡案例作反证**（缺 N1→滑向 A，缺 N3/N4→滑向 B，缺 N6→滑向 C，缺 N7→D 类谁也救不了）。逐条映射回 04 号三包四层与五公理：三包四层覆盖 N1/N2/N3/N5 的结构面，但 **N4（OEM 商业动机）、N6（单点依赖与平台方角色）、N7（生态窗口）是三包四层管不到的治理与时机命题**——与 04 号 §8.2 自检「一半是架构题，一半是版本节奏与治理运营题」独立互证。
- **单一 OEM 是活路但不是退路**：iOS / HarmonyOS NEXT / webOS-LG / Tizen-TV / KaiOS-Jio 五个样本共同显示——把平台变成单一 OEM 的私有资产可以活，但代价是平台方必须自己扛硬件、芯片或绑定一家运营商级金主（Apple 全栈 / 华为被制裁后收权 / LG 买断 / Jio 持股 16%）。**对 BerryOS：若走多 OEM 路线，N1–N7 缺一即死；若走单一 OEM 路线，BerryOS 平台方必须回答「谁出硬件、谁扛库存」——这不是架构题。**

## §1 方法与口径

### 1.1 「定制政策」三档定义（沿用 02/03 号的分类语言）

| 档 | 定义 | 判据（条款级） | 样本 |
|---|---|---|---|
| **放开** | 平台方对 OEM 改什么**无契约边界**，定制深度由 OEM 能力决定 | 授权合同只管「能不能装」，不管「装成什么样」；无界面/行为一致性认证 | WM 6.x、Symbian UI 层（S60/UIQ/MOAP）、Firefox OS（运营商侧） |
| **合同化** | 定制面 = 接口 + 测试 + 认证，机器可校验 | CDD/CTS 式兼容合同、签名/认证门、平台方掌版本节奏 | Android（02 号 §3）、QNX/Windows 桌面（03 号 §2/§3） |
| **铁幕** | OEM 无定制权或趋零，UI/交互统一由平台方定 | 硬件 chassis 规范钉死按键/分辨率/芯片；OEM 差异化只剩硬件外观与预装 | WP7（§2.2）、iOS（无 OEM，极端形态）、HarmonyOS NEXT（单一 OEM） |

注：三档是**对 OEM 定制自由度**的度量，与「开源/闭源」正交——Symbian 2010 年全开源（EPL）但 UI 层定制是放开的碎片源（§2.3）；Tizen 开源但手机线上 OEM 实际只有三星一家（§2.5）。开源≠放开，闭源≠铁幕。

### 1.2 生死判据与存活期口径

- **死亡** = 平台方官宣停止特性开发，或停止设备出货，或商店/云服务关停（三者其一即记死，取最早）。**支持终止日**（security patch 停发）单列，不与死亡日混用。
- **残局形态** = 死亡后代码资产/生态的去向：转生（webOS→LG）、收缩（Tizen→TV）、社区养护（Ubuntu Touch→UBports）、企业续命（WM→Windows Embedded Handheld）。
- **OEM 数** = 发售过该平台消费级手机的品牌数（口径为「品牌」非「机型」；单一 OEM = 1）。
- 存活期从**首个消费级设备发售**起算（不是官宣日），到死亡日止。

### 1.3 事实纪律

数值/枚举类至少两源；单源标「待核实」；媒体转引的口径差异（出货份额 vs 网络流量份额）显式标注。案例内推断（如「OEM 离开的动机」）标「推断」。

## §2 案例解剖（四件套）

### 2.1 Windows Mobile 6.x：放开定制的黄昏（2000–2010）

**① 定制政策：放开 + 收费授权。** WM 以「proprietary software licensed to OEMs」形态授权（维基 Windows Mobile 信息框）；微软对第三方软件开发「no restrictions imposed by Microsoft」，Radio Interface Layer 的设计明文「allows OEMs to integrate a variety of modems into their equipment」（允许 OEM 自由集成各型基带）——即**系统边界内 OEM 想改什么就改什么，微软只收钱不设边界**（维基 Windows Mobile）。NYT 2009-10-26 报道此授权费「up to $25 for each copy」，同时「rival Google gives away Android for free」（NYT, Big Cellphone Makers Shifting to Android System）。没有兼容性测试，没有 UI 一致性要求，没有升级义务。

**② OEM 实际怎么定制：换壳。** OEM 的差异化落在「在 WM 之上再造一层 UI 壳」：HTC 的 TouchFLO 3D（2008，Touch Diamond，WM 6.1）与三星 TouchWiz（2008 年首发，跨 WM/Bada/Android/Tizen 的家族资产，维基 TouchWiz：2008 release、首见 SGH-F480 Tocco）——任务原文写「HTC Sense」，需修正：**Sense 是 TouchFLO 血统在 Android 时代的延续品牌，WM 时代 HTC 的壳叫 TouchFLO 3D**。运营商再加一层自己的定制（运营商品牌 ROM 是 WM 时代的常态）。同一颗 WM 核心，用户在 HTC/三星/摩托/运营商手里拿到的是完全不同的系统观感。

**③ 死因主因链。** 事实链：美国市占 2007 峰值 42%（含 PDA 口径）→ 2008 27% → 2009 15% → 2010 7% → 2011 3%（维基 Windows Mobile Market share 表，源 ZDNet/BGR）；2008 年全球智能手机出货口径 14%（Gartner，经 LinuxDevices 转引）。同期体验劣化的直接证据：WM 6.5（2009-10，微软仓促补的第一个「免触笔」版本）被 Gizmodo 评为「There's No Excuse For This」、TechCrunch 评为「It Still Sucks」（两篇均见维基 Windows Mobile 引用）。OEM 出走时间线密集：Palm 2009-09 弃 WM 转 webOS（The Inquirer）；Acer 2009-10 转安卓（DigiTimes）；三星 2009-11 宣布逐步退出转自研 Bada/安卓/等待 WP（Korea Herald/Telecoms Korea，经维基转引）；LG 2009-02 与微软签 50 机型大单后无果而终（NYT）。死因链（推断，逐环有证据）：**放开无边界 → 每家 OEM 独立维护 UI 壳 → 壳与 OS 深度耦合拖慢系统级体验演进（触屏/浏览器/应用商店全面落后 iPhone）→ 授权费 $25/台 vs 安卓免费且同样放开 → OEM 用脚投票 → 平台空转**。定制策略在因果链上的位置：**共因之一**——碎片化不是主死因（主死因是 iPhone 世代性冲击 + 商业模式被免费模式击穿），但「微软从不投资一致性体验」与「OEM 各自为战无法分担平台级体验演进」互为放大器。
最后清算：Windows Marketplace for Mobile 2011 年停止收新应用、2012-05-09 关闭（维基 Windows Mobile）；WM 的企业残局 = Windows Embedded Handheld 6.5（2011-01-10 发布，兼容 WM 6.5 应用，面向仓储/物流手持）。

**④ 对 BerryOS 的一条启示（负）**：**「OEM 自由换壳」不是差异化的礼物，是平台体验债务的转嫁**——壳层碎片化后，平台级体验跃迁（WM 案例：触屏交互、现代浏览器、商店）没有任何一方能独立完成，因为每个体验变更都要 N 家 OEM 的壳重写。映射到三包四层：BerryOS 替换面若开放「GUI 壳」槽位，**壳与平台的接缝必须是 wire 契约（gui-wmd/gui-inputd 契约面）而不是「拿源码改」**——04 号 §2.2 槽位合同三件套（能力/wire 接口/消费侧 ABI）正是为此；且「换壳不换契约」的 conformance 用例应优先于壳槽位开放（P5：执法先于开放）。

### 2.2 Windows Phone 7 → Windows 10 Mobile：铁幕的两次死亡（2010–2020）

**① 定制政策：铁幕 + 收费授权（与 WM 同价、反向管制）。** WP7 的「chassis 规范」条款级钉死：WVGA 800×480 唯一分辨率、指定 Qualcomm Snapdragon 芯片族（QSD8X50/MSM7X30/MSM8X55）、**六枚专用硬件键**（back/Start/search/两段式相机/电源/音量）、512MB RAM（Tango 起降 256MB）（MSDN「Hardware Specifications for Windows Phone」存档 + 维基 WP7 Hardware 段，两源）。微软移动业务 SVP Andy Lees 对这套要求的名言是「tough, but fair」（Engadget MWC 2010 现场报道）。Metro UI 统一，OEM 不能替换 Start 屏/不能换壳（OEM 差异化被压缩到硬件外观与少量预装应用——此句为二手共识性表述，标「推断」：其一手依据是 chassis 规范的穷举式枚举本身，规范里没有任何「OEM 可定制 UI」条款）。应用面同样收权：只能经 Windows Phone Store 分发 XAP。

**② OEM 实际怎么定制：几乎不定制。** 首发 10 机型、HTC/Dell/Samsung/LG 四家、60 运营商 30 国（2010-10-11 Ballmer 官宣，Engadget）；Mango（7.5）后补 Acer/Fujitsu/ZTE（维基 WP7）。诺基亚 2011-02-11 宣布 WP 为主要平台（Elop/Ballmer 联名公开信，Nokia Conversations 存档）——铁幕平台靠「收编最大一家前放开时代 OEM」续命。WP7 设备之间的真实差异 = 机身尺寸/摄像头/键位手感；系统观感完全一致。这是铁幕的**目的**（统一体验对抗 iPhone）也是**代价**（OEM 无品牌粘性，谁都能走）。

**③ 死因主因链。** 三个死亡点：
- **WP7 之死（2012）**：WP8 换 NT 内核，**既有 WP7 硬件全部不能升级**，微软以「7.8 美容包」（2013-01-31）安抚（维基 WP7：existing WP7.x hardware could not upgrade to the incompatible WP8）。这是铁幕的镜像伤害——平台方拥有全部控制权，也拥有全部伤害用户的权力：一次内核转向就烧掉全部存量（对照：安卓同代设备大多能升一个大版本，02 号 §2.4）。
- **WP 整体之死（2017）**：2017-10-08 Joe Belfiore 官宣不再开发新特性/新硬件，「citing its low market share, and the resultant lack of third-party software」（The Verge「Microsoft finally admits Windows Phone is dead」）。份额事实：W10M 网络流量口径 2016 年 0.34% → 2017 0.1% → 2019 0.02%（netmarketshare，维基 W10M 表）；出货口径 2013 年峰值约 3%（Gartner/IDC 系报道，**待核实**，与流量口径不可混用）。财务：微软手机部门营收 FY2016 $33.58 亿 vs FY2015 $77.02 亿（-44%），FY2015 另计 $25 亿重组成本（SEC 10-K，两份文件两源）。
- **死因链拆解（推断，各环有证据）**：铁幕 → OEM 差异化只剩硬件 → 与免费且放开的安卓相比毫无商业理由 → OEM 逐代流失（W10M 时代只剩 HP Elite x3/Alcatel/VAIO 等零星机型，维基 W10M 设备表）→ 出货萎缩 → 开发者先于用户离开（Belfiore 自己把死因归为「缺第三方软件」）→ 微软 2016-02 砍掉安卓兼容层 Astoria（Ars Technica）= 承认应用缺口无法靠兼容层解决 → 死亡螺旋。**定制策略在因果链上的位置：重要共因**——铁幕不是唯一死因（应用生态缺口是直接死因），但铁幕是 OEM 离场的推手，而 OEM 离场是出货萎缩的起点。对照 WM：**微软两代平台死于同一件事的两面——它从未建立过「合同化定制面」这个中间档。**
- 尾声：W10M 支持 2020-01-14 终止（微软生命周期文档）；微软转身给安卓/iOS 做应用（Surface Duo 是安卓机）。

**④ 对 BerryOS 的一条启示（正）**：**平台方单方面拥有「烧掉存量」的权力是隐性负债**——WP7→WP8 断裂烧的是用户，BerryOS 若上游随意改 wire 语义/L0 破坏，烧的是 OEM 与开发者。映射：04 号 §2.4 禁改面 + L0 永冻 + L1 add-only + N=3 废弃窗口（API 治理章程）正是「平台方自缚」的制度化——**铁幕对平台方的要求不是「控制 OEM」而是「控制自己」**；04 号 §3.2「上游升级 = 厂商包 rebase、上游不改 OEM 码」把升级主权和存量保护写成双向合同，这是 WP 断裂案的反面教材立法。

### 2.3 Symbian：三层 UI 分裂与基金会的空转（1998–2014）

**① 定制政策：放开（UI 层结构性放开）+ 股东制。** Symbian 的架构本身就是「内核/OS 一层 + UI 中间件一层」：S60（诺基亚系，三星/LG 也授权）、UIQ（索尼爱立信/摩托，笔控路线）、MOAP(S)（NTT DoCoMo 主导的日本路线）——**三个 UI 层的应用互不兼容**（「Applications for these different interfaces were not compatible with each other, despite each being built atop Symbian OS」，维基 Symbian）。「UI wars 'tore Symbian apart'」（The Register, 2004-02-24）。治理形态：Symbian Ltd（1998，Psion+爱立信+摩托+诺基亚 JV）→ 诺基亚 2004 最大股东 → 2008 全资收购（约 $410M，DailyTech 口径，**待核实**单源）→ 2008-06 宣布成立非营利 Symbian Foundation，2009-04 运作，2010-02-04 全平台 EPL 开源（Symbian Foundation 新闻稿自称「biggest open source migration project ever」）——但第三方许可组件只能以更严的 SFL 许可给成员可见（维基 Symbian），**开源不彻底是条款级事实**。

**② OEM 实际怎么定制：造平行 UI 生态。** UIQ 造了自己的机型线（P800/P900/P910）；诺基亚 S60 自成体系并授权三星/LG；DoCoMo MOAP 带着日本四家厂自转。开发者面对的是**三套 SDK/IDE、三种交互范式**（维基 Symbian Criticism 段：编程复杂、IDE/SDK 昂贵、各家自家 IDE/SDK 加剧碎片，「All of this discouraged third-party developers」）。2008-11 UIQ Technology 破产清算（The Register, UIQ staff put on notice）。

**③ 死因主因链。** 份额事实：2006 全球智能手机 67%（Canalys）→ 2009 47.2% → 2010 37.6%（安卓 22.7% 首超在 Q4，Canalys）→ 2011Q2 22.1%（Gartner）→ 2012Q2 4.4%（IDC）。基金会死亡快于平台：2010-09 三星宣布无 Symbian 新机计划（All About Symbian）；2010-11 基金会宣布转为 licensing-only 组织、诺基亚收回平台 stewardship（BBC, 2010-11-08「Nokia reabsorbs Symbian software」）——**基金会从运作到空壳仅约 1.5 年**。2011-02-11 Elop 宣布转 WP、Symbian 转「franchise platform」逐步退役；2011-04 源码转闭源（Ars Technica）；2011-06 开发外包 Accenture（约 2300 人转移，Accenture 新闻稿）；末代机 808 PureView（2012，诺基亚 Q4 2012 财报自证「last Symbian device」）；2014-01 商店冻结（ZDNet）。死因链（推断，各环有证据）：**UI 层放开 → 三生态互不兼容 → 开发者成本三倍 → 应用生态长不起来（维基 Symbian 直陈 native app ecosystem 未能到 Apple/Google 量级）→ 份额下滑 → 股东 OEM 逐个退场（动机：转安卓成本更低、生态更大）→ 基金会失去存在基础 → 诺基亚收编后自身转向**。**定制策略在因果链上的位置：主因之一**——Symbian 的碎片不是「OEM 乱改」而是「平台架构把 UI 定制点设计成了三个互不兼容的官方分支」；这是「放开且把放开写进架构」的最纯样本。
日本残局：DoCoMo 的 OPP(S)（MOAP 后继）机型出到 2014（Fujitsu F-07F/Sharp SH-07F）。

**④ 对 BerryOS 的一条启示（正）**：**「同一内核多个官方 UI 分支」是结构性碎片——比 OEM 私改更难治，因为它披着合法外衣**。映射到三包四层：BerryOS 的 berry-ui「框架是库不是层、不出现第二官方框架」（应用规范 §3.5，01 号 §1.4 引证）与「壳=普通 .bap、同格式同门」正是在 UI 层封死 Symbian 式分裂——**BerryOS 的对应纪律应该是：可替换的壳槽位（launcher/wmd）全部走 .bap 服务包 + 契约测试，永不出现「平台侧维护的第二套官方 UI 框架」**；同时 SDK/工具链单一化（mkapp 一扇门）避免 Symbian 式「各家自家 IDE」的开发面碎片。

### 2.4 MeeGo：巨头同盟的治理死亡（2010–2011）

**① 定制政策：放开（且条款上特意为厂商定制留白）+ 巨头同盟治理。** 2010-02 MWC 官宣：Intel Moblin + Nokia Maemo 合并，Linux Foundation 托管（TechRadar/Intel 新闻稿）。Intel 的入局动机是供应链级的：「MeeGo exists because Microsoft let us down」（Atom 得不到 Windows 7 全面支持，Intel 高管语，TechRadar 2010-04）。许可政策条款级证据：MeeGo 官方许可政策要求**参考 UX 层用宽松许可（明确「to allow hardware vendors to personalize their device's user experiences」），而扩展 MeeGo API 的库用 LGPL「to help discourage fragmentation」**（MeeGo License Policy 存档）——这是本谱系里唯一把「定制自由度」写进许可证设计的平台，且方向与 BerryOS 相同（个性面宽松、API 面防碎）。

**② OEM 实际怎么定制：没有 OEM 来得及定制。** 支持名单很长（Intel/Nokia/AMD/华硕/宏碁/GENIVI 车联/Tencent/Telefónica……维基 MeeGo 支持表），但维基自己标注多家只是「rhetorically supports」（口头支持）。真实整机只有诺基亚 N950（开发者机）与 N9（2011-06-21 发布，唯一消费级）——且 N9 跑的 Harmattan 实为 Maemo 6 改名（官方口径「a MeeGo instance, though not a MeeGo product」，维基 MeeGo）。

**③ 死因主因链。** 2011-02-11 诺基亚官宣转 WP、退出 MeeGo 合作（BBC；Nokia MeeGo 团队负责人同期离职，Engadget）；**唯一整机厂一夜退出，同盟立刻只剩 Intel**；2011-09-27 Intel 的 Imad Sousou 官宣 MeeGo 并入 Tizen（MeeGo 官方博客「What's Next for MeeGo」+ Ars Technica）。从官宣到死亡 19 个月，商用机 1 款。死因链（推断，环环有证据）：**治理 = 两家各有私心的巨头（Intel 卖芯片、诺基亚在 iOS/安卓夹击下战略摇摆）+ 治理载体（Linux Foundation）无自有工程资源 + 唯一整机依赖单点诺基亚 → 诺基亚换帅（Elop 2010-09 上任）后战略急转 → 同盟瞬间瓦解**。**定制策略在因果链上的位置：无辜**——MeeGo 的定制设计（UX 宽松+API LGPL）是全谱系里最接近「合同化」思想的许可级实现，它死于治理结构，不是死于定制政策。社区残局：Mer 项目接续 → Jolla（诺基亚前员工）2013-11 出 Sailfish 手机（BBC）。

**④ 对 BerryOS 的一条启示（负）**：**「平台质量」救不了「治理单点」**——MeeGo 的许可政策是好的，N9 的工程口碑也是好的，但一家 OEM 的董事会决议就能杀掉平台。映射：BerryOS 若出现「唯一大 OEM 承载全部出货」的早期格局（04 号 §8.1-3 的商业压力场景），平台方对该 OEM 的任何战略变更都毫无对冲——**必要条件 N6（无单点依赖）是治理命题，三包四层无法提供**；04 号 §7-Q1（OEM 身份发放机构）应把「单 OEM 出货占比」列为治理面观察指标（开放问题，不替拍板）。

### 2.5 Tizen：接棒者的残局形态（2011–，手机线 2015–2017）

**① 定制政策：开源 + 认证专利闸门（半合同化）+ 事实单一 OEM。** 2011-09-28 官宣：Intel+Samsung+Linux Foundation，商业伙伴含 NEC Casio、NTT DoCoMo、Panasonic Mobile、SK Telecom、Telefónica、Vodafone（The Verge/Ars Technica）；Sprint 2012-05 加入（The Verge）。条款级治理杠杆：**Flora License**——Apache 2.0 变体，**专利许可只授予「Tizen-certified platforms」**（维基 Tizen，引 tizen.org 许可页）：开源代码人人可取，但专利护城河圈在认证圈内——这是「开源 + 认证」混合治理的罕见样本（对照 GMS：闭源服务 + 许可合同）。

**② OEM 实际怎么定制：没得定制，因为没别人来。** 三星 2013-01 官宣「当年发多款 Tizen 手机」（The Verge），实际跳票两年，首款 Z1 2015-01 才在印度发布；Z2/Z3/Z4（2017 末代）全部低端/新兴市场（维基 Tizen 设备表）。日本伙伴 DoCoMo 2014 年放弃 Tizen 手机上市计划（媒体报道，**待核实**单源）。同盟名单上的其他手机厂从未发机——**Tizen 手机线事实单一 OEM 化**。三星自己双轨：旗舰安卓、低端试 Tizen。

**③ 死因主因链（手机线）。** 跳票两年 → 只发低端机 → 无应用生态（2021-12-31 Tizen 应用商店永久关闭，GSMArena/Times of India）→ 2017 Z4 后无新机。死因链（推断）：**同盟决策慢（多家运营商+两巨头共识成本）+ 三星主力在安卓、Tizen 仅作谈判筹码与备份 → 投入不足 → 应用生态永远起不来 → 手机线自然终结**。**定制策略在因果链上的位置：次要**——Flora 认证闸门没能吸引第二个 OEM，但手机线死亡的直接原因是「无生态 + 无投入」，与定制自由度无关。**残局存活**：Gear 2（2014-02）起手表线、2015 起三星电视全系、2018 年 Tizen 占全球智能电视 21% 第一（Strategy Analytics，经 FierceVideo）；2021-05-18 Google I/O 官宣手表线并入 Wear OS（Galaxy Watch 4 起，The Verge/Ars）；2025 起平台仅剩 TV/显示器/家电，且 2022 起授权 Bauhn/Akai/Linsar、2024 授权 Loewe 等电视品牌外溢（维基 Tizen）。另：2017-04 Motherboard 报道安全研究者 Neiderman 在 Tizen 代码中找到 40+ 零日漏洞——单一 OEM 维护的开源平台工程化薄弱的实证。

**④ 对 BerryOS 的一条启示（正）**：**「平台转生为单一 OEM 的细分资产」是失败的标准去向之一，且转生后平台会外溢**——webOS（§2.6）、Tizen、KaiOS（§2.8）殊途同归：手机主战场死，单一 OEM 带着代码资产退守 TV/手表/功能机等它能独占的细分市场，站稳后再把平台授权给第二圈层 OEM（LG 2021 授权 20 家电视厂；Tizen 2022+ 授权电视品牌）。映射：**BerryOS 的「移动 rich 主战场」与「v2 工业 RT」应被视为同一平台的两条战线而非主从**（AGENTS.md 冻结常量已定 v1 移动 rich、v2 工业 RT）——工业 RT 正是 QNX 式「接口契约+认证变体」的细分存活区（03 号 §2）；若移动战线承压，三包四层模型在工业战线的复用度决定平台有没有 Tizen 式退路。

### 2.6 webOS：平台转生为单一 OEM 资产（2009–2011 手机命；2014– TV 转生）

**① 定制政策：单一 OEM 自产，不授权。** Palm 2009-01-08 发布 webOS（CES 新闻稿存档）；2010-04 HP $12 亿收购（2010-06 完成；HP 新闻稿/维基 webOS）。期间 HP 曾放话 webOS 进 PC/打印机全线（2011-02 Digital Trends），也讨论过授权他厂但从未执行（维基 webOS：It remained unclear whether HP would consider licensing）。**平台从未有过第二个 OEM——这是「不开放的铁幕」而非「锁死 OEM 的铁幕」：Palmed 自己就是 OEM。**

**② OEM 实际怎么定制：运营商小改。** Pre/Pixi（Sprint 2009-06 首发）、Veer/Pre 3/TouchPad（HP 时代）——型号间差异有限，运营商定制是主要外部变量。第三方侧：homebrew 社区（Preware/webOS Quick Install）极其活跃，是平台忠实度的最高体现，但不是官方定制面。

**③ 死因主因链。** 2011-07-01 TouchPad 上市；**2011-08-18 HP 官宣终止 webOS 设备线并考虑分拆 PC 业务**（HP 新闻稿/BusinessWire，2011-08-18）——平板上架 7 周即砍，$99 清仓被抢空（PCWorld）。直接死因是 HP 层面的：CEO 更替（Hurd→Apotheker）导致战略 U 转、「卖 PC 业务转软件」的冒进被市场否决（Apotheker 数周后被董事会解职）。**定制策略在因果链上的位置：无辜但放大了脆弱性**——单一 OEM 模式下，平台的生死 = 母公司一个财季的决策；没有任何外部 OEM 份额可以对冲。转生链（事实）：2011-12-09 HP 官宣开源（HP 新闻稿）→ 2012-08 Open webOS/Gram → **2013-02-25 HP 卖 webOS 给 LG**（源码/文档/开发者/网站全归 LG；专利留 HP，2014-01 转卖 Qualcomm——HP 新闻稿 + BBC，两源）→ 2014-01 CES LG 首批 webOS TV → 2018-03-19 webOS OSE 开源版（LG 新闻稿）→ **2021-02 LG 把 webOS 授权给约 20 家电视厂**（RCA/Konka/Ayonz，Yonhap/LG 开发者官网）→ webOS Re:New 五年升级承诺（2024，FlatpanelsHD）→ 2025 webOS Auto 上 Hyundai/Genesis。原手机生态的余烬：HP App Catalog 2015-03-15 关服（维基 webOS）。
**残局形态是本谱系最完整的「转生标本」：手机死 → 单一 OEM 买断 → 细分市场（TV）站稳 → 平台外溢授权 → 再扩张（车）**。

**④ 对 BerryOS 的一条启示（正）**：**「平台资产的可迁移性」是死亡保险**——webOS 能转生，是因为 LG 买到的 「documentation, source code, developers and all related websites」是一份**可整体移交的资产包**（HP 新闻稿原文）。映射到三包四层：上游工件（KERNEL.ELF + 基座 rootfs + 协议 crate + BCTS）+ OEM 三包的分离，使「平台」在任何时点都是可移交、可审计的整体——04 号 §3.1 交付物模型应补一条治理面问题：**平台方若退出/停运，工件与信任账本的接管义务是什么**（webOS/Tizen 商店两次关停都给存量设备留了断崖，见 §6 开放问题 5）。

### 2.7 Firefox OS：运营商定制驱动的死亡（2013–2016）

**① 定制政策：面向运营商/低端 OEM 的放开，认证条款窄。** Mozilla 2011-07-25 在 mozilla.dev.platform 邮件列表公布 B2G（Andreas Gal 原帖）；2012-07 更名 Firefox OS。生态战略是**运营商中心**：2013-02-24 MWC 官宣 LG/ZTE/Huawei/TCL 承诺制造、首发九国（巴西/哥伦比亚/匈牙利/墨西哥/黑山/波兰/塞尔维亚/西班牙/委内瑞拉）（BBC + Mozilla 新闻稿，两源）；Telefónica 2013-07 在西班牙首发 ZTE Open（$90，TechCrunch）。认证条款级证据：「Certified 'Powered by Firefox OS' devices require Firefox Marketplace, minimum hardware specs」（The Verge, 2013-02-28）——认证只管「装我的商店 + 最低硬件」，**不管运营商在系统层加什么**。2014-12-16 达到 14 运营商/28 国（Mozilla 官方博客）。

**② OEM 实际怎么定制：运营商深度介入分发。** The Verge 当时的诊断（Chris Ziegler, 2013-02-27）：Firefox OS「would take app distribution back to the pre-iPhone era, requiring application developers to deal with multiple carriers and their app stores」——**运营商各自运营应用商店、各自定植入**，开发者面对的不是一张 Android 式大一统商店，而是运营商分发的再碎片化（推断成分：该批评针对战略设计而非实测统计，但与 2014 年 Mozilla 转向自家 Marketplace 统一的动作相容）。机型全是低端：Alcatel One Touch Fire（256MB RAM）、Tarako 计划下探 128MB（Mozilla wiki）。

**③ 死因主因链。** 2015-12-08 Mozilla 官宣停止通过运营商销售 Firefox OS 手机（TechCrunch + Ars Technica「Firefox OS smartphones are dead」，两源）；2016-02-04 Mozilla 内部公告智能手机团队 5 月撤出（Mozilla discourse 官帖）；2016-09-27 Ari Jaaksi/David Bryant 邮件列表官宣 B2G 代码移出 mozilla-central、停止全部商业化开发（Google Groups 存档）。内部复盘（Ben Francis，B2G 工程师，《The Story of Firefox OS》2017-03）：项目方向三变（开放 Web 技术 → 廉价智能机 → connected devices），评估标准滑向「第三平台市占」——**目标是市占，产品却是 $25–90 的最低端硬件 + Web 技术的性能天花板**。死因链（推断，环环有证据）：**低端 Web 技术体验不敌同价位安卓 → 用户不买 → 运营商补贴意愿消退 → OEM 无利可图 → Mozilla 裁决止损**。**定制策略在因果链上的位置：次要共因**——运营商碎片化分发抬高了开发者成本、削弱了生态，但主死因是「产品定义错位 + 性能不可兑现」；Firefox OS 恰恰说明**放开定制可以是一种自杀方式（把分发权让给运营商），但它的死亡即使没有定制问题也会发生**。
fork 残局谱系：KaiOS（活，§2.8）/ Acadine H5OS（前 Mozilla 总裁 Li Gong 创业接盘运营商合作，未发布，CNET）/ B2G OS（社区，2017 停）/ Capyloon（2022 至今的小众延续）。

**④ 对 BerryOS 的一条启示（负）**：**「谁是你最初的 OEM/渠道，谁就会塑造你的定制面」**——Mozilla 把运营商当 OEM 的代理，于是「定制开放」实际开放给了运营商的商店与植入偏好，生态分发权外流。映射：BerryOS 官方源/信任账本（SDK-2 §二）是分发主权的地基——**若首个 OEM 接入是以「OEM 自营商店 + 平台方不管分发」为条件，BCTS 与信任账本的执法面就在第一天被架空**（04 号 §7-Q5 治理杠杆形态的又一证据输入）。

### 2.8 KaiOS：B2G fork 的存活——事实单一 OEM 化（2017–，动态观察）

**① 定制政策：闭源化 fork + 深度绑定单一客户。** KaiOS 2017 年从 Firefox OS（B2G）fork，MPL/GPLv2 部分开源、主体闭源（KaiOS 支持页「Can I access the source code?」），开发商 KaiOS Technologies（香港），最大股东为 TCL（维基 KaiOS，两源）。**与 Mozilla 的运营商开放路线相反：KaiOS 把平台收敛为一家公司的私有资产**。

**② OEM 实际怎么定制：Jio 不是客户，是股东。** 关系演进（事实，两源）：Reliance Jio 2017-07 发布 JioPhone（印度，本质是 KaiOS + Jio 深度定制）；**2018-03 Reliance Retail 以 $700 万购入 KaiOS Technologies 16% 股权**（Economic Times）；2018-06 Google 投资 $2200 万（The Verge）；2019-05 再融 $5000 万（Cathay/Google/TCL）、装机破 1 亿台（TechCrunch）。结果：**KaiOS 的出货、分发、补贴、应用预装全部围绕 Jio 一家**——JioPhone 是「功能机价格 + 4G + WhatsApp/YouTube」的定义性产品；Nokia/HMD、Alcatel/TCL、Energizer 等长尾机型共享平台但不构成第二重心。市占事实：2018 年 KaiOS 在印度超越 iOS 成第二大移动 OS（Counterpoint 口径，BGR/AndroidAuthority 两源转引）；2018Q1 全球产 2300 万台。

**③ 存活主因链与隐忧（动态观察）。** 活的原因链（推断，环环有证据）：**单一运营商金主（Jio 补贴 + 独家渠道）+ 收敛定制面（Jio 定制即事实标准，无碎片）+ 市场卡位精准（4G 功能机升级潮）+ Google 战略投资（防安卓低端失守）**。隐忧同样结构性：2021 年 JioPhone Next 转 Android（Pragati OS）——**金主自己开始离场**；WhatsApp 2025 退出 KaiOS（SpudnikLab）；KaiOS 3.0（2021）引擎断代、老应用须开发者适配重发、WhatsApp 不再可用（维基 KaiOS）——平台内部也发生了版本碎片；KaiOS 4.0（2025-05）底座改用 Android 14（Gonk 弃用）——**连存活者最终都向安卓驱动生态投降**（TCL Flip 4，Reddit/kaios.dev，**待核实**二源弱）。
**④ 对 BerryOS 的一条启示（正负各半）**：**「事实单一 OEM 化」能救平台命，但救不了平台的主权**——KaiOS 活了，但它的路线图由 Jio 的市场盘与 Google 的支票簿决定，平台自身已无独立演进（4.0 换底座即证据）。映射：若 BerryOS 早期出现「一 OEM 占绝对出货」格局，三包四层仍是正确架构（JioPhone 恰恰证明收敛定制面=存活条件），但**平台方必须在合同层保留路线图主权**（04 号 §7-Q12 跟版义务 SLA 的反向条款：OEM 不得绑架平台路线图——立法面空白，列为开放问题）。

### 2.9 Ubuntu Phone：convergence 野心的非定制死亡（2013–2017，残局社区）

**① 定制政策：开放 OEM 计划，硬件要求公开。** Canonical 2011-10-31（Shuttleworth 博客）宣布 Ubuntu 进手机/平板/TV；2013-01-02 官宣 phone OS（The Verge）；面向 OEM/运营商的硬件要求页公开（ubuntu.com 存档：中高端机 Cortex-A7/1GB/8GB 起）。对 OEM 无铁幕：BQ/Meizu 直接拿公版安卓机装 Ubuntu Touch。

**② OEM 实际怎么定制：只有二线厂来。** 商用机型全集：BQ Aquaris E4.5（2015-02，欧洲）、Meizu MX4 Ubuntu Edition（2015-05，中国）、BQ E5、BQ M10 平板（2016-04）、Meizu PRO 5（2016-04）——**5–6 款，两家二线厂，无一线上品牌**（维基 Ubuntu Touch 设备清单）。一线 OEM 的替代尝试是 **Ubuntu Edge 众筹：2013-07-22 发起、$3200 万目标未达标**（The Verge）——Canonical 试图自己出旗舰硬件，市场用钱包否决。

**③ 死因主因链。** 2017-04-05 Shuttleworth 官宣《Growing Ubuntu for Cloud and IoT, rather than Phone and convergence》——放弃 Unity8/手机/convergence，Ubuntu 18.04 回归 GNOME，公司转云与 IoT（Canonical 官方博客存档 + OMG Ubuntu，两源）。死因链（推断，环环有证据）：**无一线 OEM 愿做旗舰（Edge 众筹失败是直接证据）→ 只有二线厂小众机型 → 应用生态与销量双缺 → convergence 愿景（手机接显示器变 PC）无法在存量机型上兑现 → Canonical 商业主线（云/IoT）与手机线争夺资源 → 止损**。**定制策略在因果链上的位置：无辜**——Ubuntu 对 OEM 的开放姿态、公开硬件要求、无认证门槛，都没有构成死因；它死于「没有 OEM 来」与「愿景无法变现」，这两件事任何定制政策都救不了。残局：UBports 社区 2017 年接手，维护至今（2025-10 仍在发 24.04-1.1 RC，UBports 论坛）——**社区养护是开源平台死亡后的默认形态，但它养护的是爱好者存量，不产生商业 OEM**。

**④ 对 BerryOS 的一条启示（负）**：**「对 OEM 友好」不构成 OEM 加入的动机**——OEM 加入的动机只有「比我自研更赚钱/更省钱/更快」，Ubuntu Touch 技术上不乏可取（MWC 2013 被 CNET 评为超越 Firefox OS），但**没有商业引擎**。映射：BerryOS 三包四层是「OEM 来了之后」的制度；「OEM 为什么来」需要 04 号 §7-Q5（治理杠杆）与 §8.2-2（版本节奏 vs OEM 周期）给出商业答案——**架构完备性不是采用理由，这是 04 号 §8.1-1（厂商问「你们的用户态驱动是画饼」）的商业版**。

### 2.10 存活组对照

**Android：中间路线 + 治理杠杆（02 号已解剖，此处仅收口）。** 定制政策从放开（2008 交付形态=整树 fork）逐步「合同化」（CTS→GMS→Treble→GKI→Mainline），配合商业杠杆（GMS 许可）——「架构边界决定碎片化的形态，治理杠杆只决定碎片化的速度」（02 号 §4 提炼，第 218 行）。安卓证明中间路线能活，但 02 号同时记录了代价：碎片化存量不可逆（§3.7-2）、治理杠杆被欧盟反垄断认定越界（§3.2）。

**iOS：无 OEM 的极端铁幕（对照点，非可复制样本）。** Apple 是「平台方=唯一 OEM=芯片设计者=商店运营者」的全栈垂直整合，不存在平台-OEM 关系，因此不在本矩阵的定制自由度轴上。它的存活证明「完全控制」在商业上可行，前提是平台方自己扛硬件、芯片与渠道——即 **iOS 的铁幕成本由 Apple 独自支付**。对 BerryOS 的意义仅在边界条件：除非 BerryOS 平台方自产设备，否则 iOS 模式不可引用。

**HarmonyOS NEXT：从「开放兼容」收权到「铁幕」的活样本（2024–，动态观察）。** 事实链（两源）：美国实体清单（2019-05，Federal Register）迫使华为 2019-08-09 发布 HarmonyOS（自述 2012 年起研发，Yu Chengdong 称之为 plan B，SCMP/CNBC）；1.0–4.3 为**双框架（AOSP+OpenHarmony，可跑安卓 APK）**——Ars Technica 2021 年的著名评价「Huawei officially replaces Android with HarmonyOS, which is also Android」；2020-09 华为把 OpenHarmony 捐给开放原子开源基金会（开源版不含 AOSP）；**2023-08-04 HDC 官宣 HarmonyOS NEXT：去安卓、单框架、HongMeng 微内核；2024-06-21 公测、2024-10-22 正式商用**（Huawei Central/heise，两源）。生态重建数据（华为口径，经 Huawei Central/SHINE 转引）：2024-05 生态设备 8 亿+（含 IoT）、原生应用 4000+、目标 5000；2025-12 注册开发者超 1000 万；2026-03 应用超 35 万、HarmonyOS 5/6 激活迈向 5000 万（另一口径 2025-11 为 2700 万，**口径差异待核实**）。OEM 面：**单一 OEM**——华为之外的头部手机厂商均未发布 HarmonyOS/OpenHarmony 手机（推断：基于公开产品线盘点，无反例见诸报道）；海外因 GMS 缺失基本失去竞争力。铁幕收权的代价与收益：**收益 = 体验/生态/安全完全自主、在中国市场靠自芯（Kirin）+本土应用集体适配完成生态冷启动；代价 = 放弃全球市场 + 单一 OEM 承担全部硬件风险 + 生态指标高度依赖本土动员**。它是「铁幕能否活」的活体实验：目前活，但样本仍在演化中——**本稿仅记录为动态观察点，不作终局判断**。

## §4 失败模式分类

### A 类：死于放开碎片（定制无边界 → 生态/体验崩坏）

- **Symbian（主因级）**：三个官方 UI 分支应用互不兼容 + 各家 IDE/SDK 碎片 → 开发者三倍成本 → 应用生态未达量级（§2.3）。这是「碎片写进平台架构」的极端形态——不是 OEM 乱改，是平台自己裂成三瓣。
- **Windows Mobile 6.x（共因级）**：OEM 各自维护 UI 壳（TouchFLO 3D/TouchWiz）+ 无一致性边界 → 平台级体验跃迁无人牵头 → 触屏世代全面落后（§2.1）。碎片是放大器，主死因是商业模式与代差。
- **Firefox OS（次生伤害）**：把分发与定制让渡运营商 → 开发者面对多家运营商商店（§2.7）。「放开」的另一种自杀姿势：不是 OEM 改平台，是渠道改生态。

**A 类共性**：定制自由度存在，但**没有合同承载**（无兼容测试/无版本纪律/无统一分发）——与 02 号 §4「凡承诺缺位处必碎」同构。放开本身不杀人，**无合同的放开才杀人**。

### B 类：死于锁死无 OEM（铁幕 → 差异化归零 → 无人造/无对冲）

- **Windows Phone 7/W10M**：chassis 铁幕 + 付费授权 → OEM 差异化只剩硬件 → 与免费放开的安卓相比零商业理由 → OEM 逐代流失 → 生态饥饿死亡（§2.2）。铁幕在 WP 上还叠加了「平台方单边毁约权」伤害：WP7→WP8 烧掉全部存量用户。
- **webOS**：不授权、单一 OEM → 母公司一次战略 U 转即死（§2.6）。铁幕的另一种形态：不是锁 OEM，是根本没有 OEM。

**B 类共性**：平台方把「控制」当作价值本身，但 OEM 的参与动机被清零或从未建立。**铁幕要求平台方自己支付 OEM 缺席的全部成本**（硬件/渠道/生态冷启动）——Apple/华为付得起，微软/HP 选择了不付。

### C 类：死于巨头同盟治理失败（多巨头共治 → 单点断裂/决策空转）

- **MeeGo**：Intel+Nokia 双巨头 + Linux Foundation 空壳托管 → 诺基亚换帅一夜退出 → 同盟即死（§2.4）。治理载体无自有工程资源，全靠赞助商输血。
- **Symbian Foundation**：股东即客户 → 客户（三星/索爱）跑光 → 基金会 1.5 年转 licensing-only 空壳（§2.3）。基金会模式在「成员都是直接竞对」时天然失灵。
- **Tizen 手机线**：多巨头+多运营商共识成本 → 跳票两年 → 主力 OEM（三星）双轨投入 → 手机线无声终结（§2.5）。

**C 类共性**：同盟的治理结构没有**独立于赞助商商业利益的决策与工程实体**——任何一个赞助商的战略变化都会传导为平台死刑。对照正面：Linux Foundation 托管的普通项目活得好，是因为没有「单一整机厂承载全部出货」的依赖结构。

### D 类：死于生态非定制因素（诚实标注：定制策略无辜）

- **Windows 10 Mobile**：直接死因是应用缺口与财务失血（FY2016 营收 -44%，SEC；Belfiore 归因「缺第三方软件」）。铁幕是起点推手但非致死机制（§2.2 第三个死亡点；矩阵 #3 行）。
- **Ubuntu Phone**：无一线 OEM 愿做 + convergence 愿景无变现 + Canonical 资源转投云/IoT。对 OEM 的开放姿态无可指摘（§2.9）。
- **Firefox OS**：低端 Web 技术性能不可兑现 + 产品定义三变——即使没有运营商碎片化也难逃（§2.7 内部复盘引证）。
- **（部分）Windows Mobile**：主死因是代差与商业模式，碎片是共因不是主因（§2.1）。

**D 类的诚实结论**：在本谱系 9 个失败样本中，**至少 3 个的死亡与定制策略基本无关**。定制政策是「死亡方式的选择器」（决定了你以什么姿势死：碎着死/饿着死/被盟友背刺死），**不是「死活的决定器」**（决定死活的是生态临界质量、商业引擎、时机窗口）。任何「选对定制政策就活」的叙事都不成立——02 号安卓篇的结论（架构定形态、治理定速度）在失败侧同样成立：**架构定死法，治理定死期**。

### 存活组的模式归位（对照）

- **Android**：中间档（合同化）+ 治理杠杆 = 唯一「多 OEM 大规模存活」样本。
- **iOS / HarmonyOS NEXT**：铁幕 + 平台方独担硬件成本 = 存活，但样本条件苛刻（全栈能力/被制裁后的本土动员）。
- **KaiOS / webOS-TV / Tizen-TV**：收敛为单一 OEM 私有资产 + 退守可独占细分市场 = 「残局存活」三连样本。
- **结构性观察（推断）**：谱系上不存在「纯放开且多 OEM 且活着」的样本——A 类全灭；也不存在「铁幕且多 OEM 且活着」的样本——B 类全灭。活着的全在两极（多 OEM 合同化 / 单一 OEM 自持）之间或之外：**「中间偏合同」或「单一 OEM 收敛」是仅有的两个存活区，且后者要求平台方付得起硬件账**。

## §5 收口推论：「中间路线」的必要条件集 N1–N7

以下每条为一个必要条件（缺一即滑向对应死法，锚到 §2/§4 证据），并逐条映射回 BerryOS 三包四层（04 号 §2）与五公理（04 号 §1.2，P1–P5）。

### N1 定制面必须是合同，不是自由（缺 → 滑向 A 类）

- **证据锚**：Symbian 三 UI 分裂（§2.3）、WM 壳碎片（§2.1）、Firefox OS 运营商分发碎片（§2.7）；正面 = 03 号 §9.1 六样本全合同化。
- **映射**：配置面声明式产品清单（04 号 §2.1，schema 化 + 未知键硬拒）+ 替换面槽位合同三件套（04 号 §2.2）＝ P1（定制面必须是合同）的直接落地。**BerryOS 已对齐**；缺口在「槽位合同的 conformance 用例」尚不存在（01 号 §3 缺口 4，BCTS 未立项）。

### N2 平台保升级主权 + 双向自缚（缺 → 碎片不可逆 / 存量被烧）

- **证据锚**：正面 = Treble/GKI/Mainline（02 号 §3.3–3.5）；反面 = WP7→WP8 断代烧存量（§2.2）——升级主权单边握在平台方手里且无合同约束时，平台方自己就是最大风险源。
- **映射**：禁改面 + L0 永冻 + L1 add-only + N=3 废弃窗口（04 号 §2.4；API 治理章程）+「上游只以工件交付、OEM 包 rebase」（04 号 §3.2）＝ P4（平台保升级主权）。**BerryOS 结构面对齐；但「平台方对 OEM 的稳定性承诺」是单方面宣誓，尚无对 OEM 可执行的违约救济**（开放问题，§6-4）。

### N3 OEM 必须有真实差异化出口（缺 → 滑向 B 类）

- **证据锚**：WP7 铁幕下 OEM 差异化只剩硬件 → 出走（§2.2）；正面 = Android 的壳/预装/多形态（02 号 §1.3）、Fuchsia session 大槽位（03 号 §1）。
- **映射**：替换面槽位清单（launcher/wmd/显示后端/电源热策略/调度策略服务，04 号 §2.2）+ 扩展面（驱动/增值服务/系统应用，04 号 §2.3）＝ P3（个性出口收敛于大槽位）。**BerryOS 槽位集尚小（v2 首批建议见 04 号 §5），且深度交互面（手势/多任务）槽位是已知张力点（04 号 §8.1-3）——B 类风险的残余在槽位的「深度」而不在「有无」**。

### N4 OEM 的商业动机必须成立（缺 → 滑向 B 类；架构管不到）

- **证据锚**：WM/WP 每台 $25 授权费 vs 安卓免费 → OEM 用脚投票（NYT，§2.1/§2.2）；Ubuntu Touch 无商业引擎 → 无 OEM（§2.9）；KaiOS 靠 Jio 补贴与分成成立（§2.8）。
- **映射**：三包四层**不提供**此条件。对应 04 号 §7-Q5（治理杠杆形态）、Q12（跟版义务 SLA）——OEM 在 BerryOS 上的盈利模型（省自研成本？独占槽位价值？官方生态分成？）是治理面必答题，本稿证据侧结论：**「免授权费 + 槽位价值 + 官方生态准入」是安卓验证过的组合；「收费 + 铁幕」是微软验证过的死法组合**。

### N5 执法先于开放（缺 → 一切合同退化为纸面）

- **证据锚**：CTS 的作用与盲区（02 号 §3.1/§3.6）；WP 铁幕无需 CTS 但以 OEM 离场为代价；03 号 §9.4 兼容执法三件套（契约测试+签名认证+版本权）为六正面样本共性。
- **映射**：BCTS（04 号 §4）+ 签名链/信任账本（04 号 §4.4）+ 执法外化（04 号 §2.4）＝ P5。**BerryOS 最大缺口**：01 号 §3 缺口 4 明示「全部执法只对本仓 CI 生效」；04 号 §8.2-1 已把「治理三件套晚于首个 OEM」列为首要失败风险——本谱系把该风险从「失败风险」升格为「生死判据」（WM/Symbian 的碎片存量不可逆，02 号 §3.7-2）。

### N6 无单点依赖 + 平台方角色自律（缺 → 滑向 C 类；架构管不到）

- **证据锚**：MeeGo 死于诺基亚单点退出（§2.4）；webOS 死于母公司单点战略 U 转（§2.6）；Symbian Foundation 死于「股东即客户」结构（§2.3）；KaiOS 的存活与隐忧同源于 Jio 单点（§2.8）。
- **映射**：三包四层**不提供**此条件。对应 04 号 §7-Q1（OEM 身份发放）应扩展：**单 OEM 出货集中度上限/观察线、平台方是否自产设备（Apple/华为模式与「组装不 fork」的利益冲突）、治理载体的独立性**——全部立法空白，本稿只列证据不拍板。

### N7 生态启动窗口（缺 → D 类，任何定制政策都救不了）

- **证据锚**：W10M 的应用缺口死亡螺旋（§2.2）；Firefox OS 低端性能不可兑现（§2.7）；Ubuntu Touch 应用生态与销量双缺（§2.9）；正面 = HarmonyOS NEXT 用「双框架过渡 + 本土动员 + 35 万应用口径（2026-03）」硬扛冷启动（§2.10）。
- **映射**：对应 04 号 §8.2-2「平台演进速度吞掉承诺或跟不上 OEM 周期」与本系列未答之问：**BerryOS 的生态冷启动窗口是什么？**（v1「SDK 不外发、无 OEM 通道」= 窗口未开；鸿蒙的「双框架过渡再收敛」提供了另一种时序样本——先兼容后铁幕——是否适用于 BerryOS 的 POSIX 兼容库定位，是开放问题，§6-3。）

### 映射总表

| 必要条件 | 滑向死法（缺此条件） | 三包四层对应 | 五公理对应 | 架构能否独立保障 |
|---|---|---|---|---|
| N1 合同化定制面 | A（碎死） | 配置面+替换面 | P1 | **能**（schema+契约测试） |
| N2 升级主权+双向自缚 | A'（存量被烧/碎片不可逆） | 禁改面+三包 rebase | P4 | **能**（工件交付+ABI 执法） |
| N3 真实差异化出口 | B（饿死） | 替换面槽位+扩展面 | P3 | **部分**（槽位深度是张力） |
| N4 OEM 商业动机 | B（无人造） | —— | ——（P4 治理面相邻） | **不能**（治理/商业题） |
| N5 执法先于开放 | A（合同退化纸面） | BCTS+签名链外化 | P5 | **能**（需立项 BCTS） |
| N6 无单点依赖 | C（盟友背刺/母公司 U 转） | —— | —— | **不能**（治理题） |
| N7 生态启动窗口 | D（谁也救不了） | —— | —— | **不能**（时机题） |

**收口一句话（推断）**：三包四层 + 五公理覆盖 N1/N2/N3/N5 的结构面——这是它作为**架构**提案的合格线；N4/N6/N7 是架构外命题，04 号 §8.2 已自认「一半是版本节奏与治理运营题」，本谱系为这一半提供了死法对照表。**BerryOS 若走多 OEM 路线，N1–N7 缺一即死；若走单一 OEM 路线，用 B 类样本（webOS）与存活样本（iOS/鸿蒙/KaiOS）的差集自查：平台方是否付得起硬件账、有没有 KaiOS 式金主、有没有鸿蒙式本土动员——三问皆否，则单一 OEM 路线同样是死路。**

## §6 开放问题（原样列出，不替拍板）

1. **单 OEM 集中度治理**：是否为「单 OEM 出货占比」设观察线/上限？超过即触发何种治理动作（对应 N6；KaiOS 的 Jio 单点是存活条件也是路线图绑架，§2.8）？（接 04 号 §7-Q1）
2. **平台方是否自产设备**：BerryOS 平台方自己做硬件（Apple/华为/早期 Nokia 模式）与「组装不 fork」的多 OEM 提案是否互斥？平台方当 OEM 时，三包模型中「上游工件」与「OEM 三包」的利益冲突如何处理？（N6）
3. **铁幕时序可逆性**：鸿蒙 NEXT 提供了「先双框架兼容（开放）→ 再去安卓收敛（铁幕）」的时序样本；BerryOS 的对应问题是——v1/v2 的「POSIX 兼容库 + 自有 ABI」双轨（AGENTS.md 冻结常量）是否可视作同类过渡结构？收敛时机由什么信号触发？（N7）
4. **平台方违约救济**：L0 永冻/L1 add-only 目前是平台方单方宣誓；是否需要面向 OEM 的可执行承诺（如 WP7→WP8 式断代的赔偿/退出条款）？以何种载体（认证合同/许可协议）承载？（N2，接 04 号 §7-Q12）
5. **平台终止时的存量义务**：webOS App Catalog 关服（2015-03-15）、Tizen 商店关闭（2021-12-31）、Windows Marketplace 关闭（2012-05-09）均给存量设备留下断崖；BerryOS 信任账本与官方源若停运，OEM 三包与已售设备的最低退出义务是什么？（接 04 号 §7-Q3/Q5）
6. **「收费+铁幕」与「免费+合同」之外的第三象限**：BerryOS 若开源（Apache-2.0 已是 ADR #37 洁净线），「免费+合同化」组合中治理杠杆只剩认证/商标/信任账本——对照安卓 GMS 的反垄断教训（02 号 §3.2），认证杠杆的合法边界怎么画？（N4/N5，接 04 号 §7-Q5）
7. **生态冷启动的度量**：N7 的「窗口」以什么指标判开合（应用数/开发者数/首 OEM 机型周期）？鸿蒙口径（设备 8 亿含 IoT vs 手机激活 2700 万）显示口径本身即政治——BCTS/认证体系是否需要预定义生态健康度的公共度量（对照 02 号 §3.7-3 公共度量退场的教训）？

## §7 反面自检（如实写）

1. **归因是分析性的，不是实证的**：「定制策略是否主因」的判定基于公开叙事的事后重构，无反事实实验。WP 案例中铁幕/应用缺口/付费模式三者纠缠，本稿的拆分（§2.2/§4-D）是分析工具，不宣称因果识别。
2. **幸存者偏差与样本量**：谱系只含「做到上市」的平台；死在娘胎的项目（如 Nokia 内部多个 Maemo 分支、Intel Moblin 前身）不入样本，可能系统性高估了「选对政策」的作用。9 个失败样本对四类死法的归纳（每类 ≥2 例）是弱归纳，不是统计。
3. **口径粗糙**：OEM 数按品牌计不按机型/出货量；存活期起算点（首个消费设备）对「项目命 vs 商用命」不加区分（MeeGo 行两种口径差 19 倍）；市占数据跨口径（出货 vs 网络流量）已尽量标注，仍有混用风险。
4. **动态样本未封口**：KaiOS（Jio 转安卓、4.0 换底座）与 HarmonyOS NEXT（生态指标快速演化、口径存疑处已标）都可能在未来推翻本稿的中期判断；两处均标「动态观察」。
5. **本稿对 BerryOS 的全部映射均为证据层建议**：N1–N7 是必要条件的假说集（每条有死亡反例支撑），不是充分条件集，更不是「满足即活」的承诺——D 类样本（Firefox OS/Ubuntu Phone）恰恰死于 N1–N6 之外。
