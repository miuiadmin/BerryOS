### 1.3 两不可逆点与五道闸（行号现场重锚）

- **五道闸**（`docs/架构决策.md` :236–238）：闸 A = SDK 外发决定反转或首个第三方 .bap 在野；**闸 B = SDK-2 开刀（账本/索引首实现合入——在野之始）**；闸 C = OTA/签名格式开刀；闸 D = P8 真机/首 OEM 接触窗；闸 E = handoff/boot 结构冻结点。
- **两处不可逆点的最晚重议**（`docs/架构决策.md` :301）：**Q6 账本 schema = SDK-2 P0 合入前**（在野后改 = 全量账本迁移 + 旧设备不认新账本）；Q3 信封格式 = 首个编队 OTA 实现合入前（之后改 = 更新协议 break + 全量重刷）。Q6 原文（:280）：「anchor_type add-only 扩 `oem-system` + 条目四字段；旧验证器对未知枚举**保守拒绝** + **两步发布纪律**」。
- **与 P0 的关系（任务书要求明示）**：P0 含信任账本 schema 的**首次代码化**（berry-crypto::ledger）——P0 合入即「账本首实现合入」即**过闸 B**。因此：
  1. **P0 合入前**，主会话须对 Q6 schema 做最后一次确认（v1.2 §二 :38–45 + 09 §2.4 字段表是否即终态——本稿 §3.5 的 TOML 形态逐字段照抄该两处，未加新字段）。此后 anchor_type 枚举与条目字段进入 add-only 冻结轨道，改 = 全量账本迁移。
  2. Q6 的「两步发布纪律」（新枚举进账本前，全网最低验证器版本先升）在 v1 单实现期是**空操作**（无在野验证器），P0 只在 ledger 模块头注预留该纪律的注释位（§3.5）。
  3. P0 的信封 v1 是 Q3 未冻结面的**第一版实现**：信封 `ver=1` 字段的存在价值正是给 P3 前的重议窗留兼容轨——P0–P2 期间内野无消费者，改信封零成本；P3（首个编队 OTA 实现合入）前必须冻结。

sha2 补充两源事实：docs.rs Structs 列表**预置 `Sha512_256` 类型**（FIPS 180-4 SHA-512/t 家族完整六型）——即外购 sha2 可直接得 SHA-512/256，无需自写 IV 截断。自研路对应的自写成本 = SHA-512 核心 + SHA-512/256 的 IV 换装与 32B 截断（≈+50 行级，推断——SHA-512 核心本身 ≈200 行级）。

自研案（v1.2 拍板③现状）无外部事实可核，工作量依据：v1.2 §三 :67–68 自评「数周级工程，不阻塞 host 面」；参照系 = ed25519-dalek 本体 crates.io linecounts 1731 行 Rust（不含 curve25519-dalek 数千行）——自研最小面（verify+sign，无 Ristretto/SIMD/batch/预计算表）可显著低于此（推断，≈1500–2500 行 + 测试），但 sc_reduce（标量约减）与小阶点检查是公认易错区，RFC 8032 + Wycheproof 门是唯一硬校验。

### 2.3 建议 + 反论（终裁归主会话）

**建议一（ed25519 面）：维持拍板③自建，P0 按自建走；dalek 的 TESTVECTORS/VALIDATIONVECTORS 文件收编为第三测试向量源（数据非代码，BSD-3 容许，零依赖成本）。**

理由：①user/ workspace 零外部依赖现行纪律（§1.4）——31 crate 先例全在，破例该由主会话显式拍而非随刀夹带；②设备侧（P3）必经 aarch64-unknown-none，dalek 树的 cpufeatures 运行时探测面在 none target 有编译/行为风险（推断，§2.1）——host 先用 dalek、guest 再自建的「双实现」方案违反单实现精神（host 验签器与设备验签器语义漂移 = 对拍成本常驻，Janus 课的远亲）；③签名链是安全关键面，仓有黄金字节/CI 全向量门传统（berry-lifecycle CRC32 向量钉板、berry-manifest 拒因面），自建 + RFC 8032 + Wycheproof 门的组合与仓测试文化同构；④v1 不外发（拍板① v1.2 §〇 :16）——单向门敞开期自建格式零成本窗口仍在。

反论（诚实）：①自建 = 数周级且密码学易错（sc_reduce/点解码/小阶点），dalek 十年维护 + 2.69 亿下载生态背书，错的概率不对称；②「审计态」不是自建的加分项——dalek 未见公开审计、自建根本无审计，**两案的安全论证都压在测试向量门上**（§2.1），自建并不比 dalek 更可审计，只是更可控；③若 P0 工期溢出成常态，「host 用 dalek 先行 + 设备侧自建后补」的中间案会被反复重提——本稿预登记其代价（双实现语义漂移面）防临时起意；④BSD-3-Clause 许可证无障碍（§2.1 两源核），若终裁翻案外购，无许可证回退成本。

**建议二（SHA-512/256 面）：与 ed25519 同裁（绑定）——自建路自写 SHA-512 + IV 截断（+50 行级）；若翻案外购，sha2 0.11.1 预置 Sha512_256 直接可用（docs.rs 实证）。**

理由：v1.2 §三 :53 拍板摘要 = SHA-512/256 的核心理由是「复用 ed25519 内部 SHA-512 一份实现，guest 免带双哈希」——SHA-512 无论如何都要有（ed25519 内部），SHA-512/256 是它的免费衍生；外购 sha2 反而引入第二份 SHA-512（dalek 内部一份 + sha2 一份）与 cpufeatures 面，与拍板理由对冲。

反论：自写 SHA-512 本身也是易错面（尽管远易于椭圆曲线）；sha2 是 12 亿下载的最广泛审计替代品；若终裁 ed25519 翻案外购，SHA 面自然随 dalek 树（其内部即用 RustCrypto sha2）——单独外购 sha2 而自建 ed25519 的组合**不建议**（两不沾）。

**建议三（BLAKE3 面）：不引入。维持 SHA-512/256。**

理由：①v1.2 §三 :53 已定稿（换摘要算法 = 改定稿面，须走 #77 重议而非随刀）；②BLAKE3 crate 含大量 C/asm（§2.1 linecounts 实证），`pure` 路径也有依赖面——对 no_std 设备侧是三案中最重的；③引入 BLAKE3 不消除 SHA-512 依赖（ed25519 内部仍需），guest 反而带双哈希——与拍板③的「免带双哈希」初衷正相反；④BAP_MAX = 4MiB（v1.2 §四 :80）量级下哈希吞吐非瓶颈（推断——4MiB 单包 SHA-512 host 侧毫秒级，性能论据不成立）。

反论：BLAKE3 树内并行/SIMD 吞吐显著更高（host 侧索引批量生成的未来场景）；CC0 许可证几乎无义务。但该反论在 v1 量级下无购买力——登记为 §5-Q4 开放问题（若 v2 单包 ≥50MB 增量闸门立项〔v1.2 §四 :79–82〕时重议）。

### 2.4 仓内先例交叉（建议一的旁证）

- **berry-tcp 先例**（`user/Cargo.toml` :39–41）：最小 TCP 客户端状态机纯函数 crate 自写而非引外部网络栈——「协议面自持纯函数 + host 测试」的家族形态在复杂协议面已走通，berry-crypto 是同型（更大）复刻。
- **Ginux 反面教材**（规则 13 :71）：内核内 crypto 全量是 Ginux 调研的明确否定项—— BerryOS 不搬大 crypto 框架，自建最小面与「内核极简」原则同向。
- **berry-lifecycle CRC32 先例**（`user/Cargo.toml` :109–111）：CRC32 bitwise 自写 + png.rs 镜像 + 向量钉板——「哈希类原语自写 + 向量钉板」在仓内有直接先例，SHA-512 是其放大。

## §3 P0 最小件设计（首刀，≤1 周）

### 3.1 目标与非目标

**目标**（全部 host 可测、零内核面、零外部依赖——按建议一自建路写；若终裁翻案外购，§3.4–3.7 骨架不变、原语模块换装）：

1. `user/berry-crypto`（暂名，定名随 #77）crate：ed25519 verify（strict 语义）+ sign + SHA-512/256；
2. .sig 信封 v1 解析 + 轮换链验证 + 顶签名验证（纯函数）；
3. 信任账本 TOML 源形态解析 + 单调水位比较器（纯函数）；
4. selftest：RFC 8032 §7.1 官方向量（两源核）+ Wycheproof ed25519 全向量 + 信封三负样例。

**非目标**（明示边界）：不动 `kernel/`/`svcmgr`/`appd`（设备侧 = P3）；不动 `tools/mkapp.py`（集成 = P1）；不做索引生成工具（P2）；不做 per-app 记录账本与 freshness 水位落盘（P3，v1.2 §五 :98）；不做密钥管理/秘钥存储（host 测试用测试钥，生产钥管理随 #77 另议——§5-Q3）；信封格式**不冻结**（Q3 重议窗开到 P3 前，§1.3）。

### 3.2 crate 落位与形态

- 落位：`user/berry-crypto/`，入 `user/Cargo.toml` members（实施刀动作，本稿只设计）。「解析器即产品」家族新例（manifest 第 8 例、layout 第 9 例之后——**推断**编号顺延），家族形态逐条对齐：`cfg_attr(not(test), no_std)`、零分配（验签栈上定长数组 ≈1KB 级，推断）、零 unsafe（域运算用安全原语 u128 乘法——常时性靠写法不靠 unsafe，规则 13 unsafe 纪律不涉白名单桶）、零依赖、输入只借用、永不 panic。
- 命名注：v1.2 §三 :66 用名「berry-crypto」，SDK-2 v1.2 §〇 :18 拍板③同——暂名定名随 #77（与 ADR #59「TLV 校验器定名随 SDK-2 开刀」同窗）。
- 模块清单（七件）：

```text
user/berry-crypto/
  src/sha512.rs     SHA-512 核心 + SHA-512/256（IV 换装 + 32B 截断，FIPS 180-4）
  src/field.rs      Fe25519 域算术（u64 limb ×4：加/减/乘/平方/逆）
  src/scalar.rs     标量算术 mod L（sc_reduce/sc_muladd——RFC 8032 参考实现逐字对照移植）
  src/edwards.rs    Edwards 点运算 + decompress（验签路径）
  src/ed25519.rs    verify（strict：S < L、点在主子群、非规范 R 拒）+ sign
  src/envelope.rs   .sig 信封 v1 解析 + 轮换链验证 + 顶签名验证（§3.4）
  src/ledger.rs     信任账本 TOML 源形态解析 + gen_max/ver_max 水位比较器（§3.5）
  tests/fixtures/   RFC 8032 向量 + Wycheproof ed25519_test.json + dalek TESTVECTORS
```

### 3.3 模块间纪律三条

1. **单解释器纪律的 P0 落实**（v1.2 §三 :65 禁双解析器）：信封的 manifest 关键域摘要输入**必须**由 berry-manifest 解析产物单源派生（berry-crypto 经 path 依赖消费 berry-manifest，或定义摘要输入 = manifest 规范字节段并让 berry-manifest 提供该段——实施时二选一，§5-Q2）；禁止 berry-crypto 内部出现第二个 manifest 语义判断。
2. **拒因 BerryErr 化**（SDK-2 错误域 v1.0 先例，§一 :13–26「稳定枚举 + 附因 + 两舱」）：envelope/ledger 的拒绝面从第一天就走结构化枚举（`SigErr::{BadMagic, BadVer, BadAlg, ChainBroken, TopSigBad, …}` + ledger 的 `LedgerErr`），人读文案渲染在后——不重蹈「一行中文拒因」旧态（错误域 §二 :39–44 的反面教材正是 mkapp/berry-manifest）。
3. **帽常量单源 + mkapp 镜像同步义务注**（家族惯例，berry-manifest Cargo.toml :5–8 同款）：lineage 帽 1..=16B [a-z0-9-]（与 berry-manifest `SEC_VAL_MAX`/mkapp `SEC_RE` :137 同值同语义）在 berry-crypto 头注声明同步义务——三处单源改动必须同刀。

### 3.4 .sig 信封 v1 字节布局（设计面草案——Q3 未冻结，标注推断）

v1.2 §三 :57–60 字段序的字节级细化（**推断**：本节是首刀实现规格草案，冻结走 #77/Q3，P3 前最后重议点）：

```text
偏移   字段              型/长            说明
0      magic             "BSIG" 4B        容器识别（对照 .bap 容器头先例）
4      ver               u8 = 1           信封版本（Q3 重议轨）
5      alg_id            u8 = 1           1 = ed25519 + SHA-512/256（add-only 枚举）
6      lineage_len       u8 (1..=16)      + lineage 字节（值域 [a-z0-9-]，帽同 SEC_RE）
7+L    gen               u32 BE           单调代际（v1.2 §三 :58）
…      pk                32B              当前公钥
…      pending           0B 或 32B        后继钥 day-one 位（§三 :62 换钥纪律；空 = 无 pending）
…      chain_len         u8               轮换链节点数（线性单路径，禁分叉）
…      chain[i] ×N       每节点 64B 签名   over ("BSIG-ROT" 域标签 ‖ old_pk 32B
                                          ‖ new_pk 32B ‖ gen u32 BE ‖ lineage 字节)
                                          —— old_pk 入覆盖域防链节点嫁接（推断）
…      top_sig           64B              over ("BSIG-TOP" 域标签 ‖ 信封头〔magic 至
                                          chain 末字节〕‖ bap_digest 32B〔SHA-512/256
                                          全字节〕‖ manifest 关键域摘要 32B)
尾     ——                （无 trailer）    总长 = 12 + L + 4 + 32 + P + 1 + 64N + 64
```

设计注三条：①域分隔标签（BSIG-ROT/BSIG-TOP）防跨上下文签名重放（密码学惯例，RFC 8032 context 的精神——推断）；②manifest 关键域摘要的覆盖域建议 = [app] id/version + [compat] 三值 + [security] 三键（身份与版本面——独立于容器布局的身份锚：即使容器重排再打包，身份域不变则信封仍可对账；推断，实施时随 §3.3-1 的单源路径定）；③信封是**分离件** `app.bap.sig`（v1.2 §三 :51「不内嵌——.bap 载荷是冻结面 L1」）——P0 只做字节解析与验证，不涉分发命名。

### 3.5 信任账本 TOML 形态（host 源形态先行）

§二 :38–45 + 09 §2.4 :153–171 的 TOML 落形（**Q6 面——P0 合入前主会话终核，此后 add-only**）：

```toml
# trust-ledger v1（host 源形态；分发/设备形态 = TLV，随 P2/P3 转译）
schema = 1                             # u32，add-only（对照 V12 product 清单 schema=1 先例）

[[lineage]]
id = "upstream"                        # 1..=16B [a-z0-9-]（帽同 berry-manifest SEC_VAL_MAX）
anchors = [
  { pk = "<64 hex>", type = "system" },# anchor_type ∈ tofu|system|ca|oem-system（add-only）
]
gen_max = 3                            # 单调水位（v1.2 §三 :63 护栏②）
ver_max = 0                            # per-app 水位归 per-app 记录账本（P3，§五 :98）
kind = ""                              # V4 占位：integrator|odm|developer，v1 恒空
issued_by = ""                         # V4 占位：v1 恒空（09 §2.4 :161）
cert_status = ""                       # V4 占位：事实源 = 签名索引，账本不存或只读回显（v1.2 §二 :43–44）
last_revision = 0                      # V4 占位：v1 恒空（09 §3.1 :213）
```

解析纪律五条：①未知 `anchor_type` **保守拒绝**（09 §2.4 :169「不可评估」拒绝该锚——不降级跳过）；②未知键硬拒（V12 product 清单同款）；③`schema` 非 1 硬拒（前向：升版走 add-only 轨）；④水位比较器独立纯函数（`check_gen(gen, gen_max)` / 索引版本回降拒——供 P1 门禁与 P2/P3 复用，单源不两套）；⑤头注预留「两步发布纪律」注释位（§1.3——v1 单实现期空操作）。

TOML 解析器落位：berry-crypto::ledger **自持账本专用行解析器**（berry-manifest :870 同款逐行形态）——非「第二套」：解析的是不同 schema（「不长第二套」指同一格式/同一事实源不长两套解析器；berry-layout 的 JSON v1 解析器与 manifest 的 TOML 解析器并存即此格局）。

|---|---|---|
| D1 | crate 骨架 + sha512.rs（+SHA-512/256）+ FIPS 向量 | 低（纯搬运级算法，berry-lifecycle CRC32 先例） |
| D2 | field.rs Fe25519 + 一致性测试 | 中（limb 进位/借位边界） |
| D3 | scalar.rs（sc_reduce/sc_muladd 逐字对照 RFC 8032 参考实现）+ edwards.rs | **高——本刀最大风险点**（sc_reduce 公认易错；RFC 8032 附录参考实现逐字对照移植是主缓解） |
| D4 | ed25519.rs verify+sign；RFC 8032 §7.1 全绿 | 中 |
| D5 | Wycheproof fixture 接入 + strict 拒收面全绿 | 中（mixed-order 例首跑可能红——修复回灌 D3） |
| D6 | envelope.rs + ledger.rs + 三负样例 + test-host 挂行 | 低（与原语正交） |
| D7 | 缓冲 + 拒因 BerryErr 化 + 头注/帽常量同步注 | —— |

溢出预案（诚实）：D3–D5 若超 1.5 日，envelope/ledger（D6）**并行先行**（与原语零耦合，可独立合入半刀）；原语面溢出不阻塞信封/账本 schema 的 Q6 终核与 #77 落册节奏。

### 3.9 风险清单（反面自检前置于设计）

1. **密码学实现错**（自建固有）：缓解 = RFC 8032 参考实现逐字对照 + 双向量源全量门 + 仓外第三源（dalek TESTVECTORS）；残余风险 = 向量未覆盖的实现角（时序侧信道在 host 验签非敏感，设备侧 P3 再评估常时性——推断）。
2. **Q6 schema 终核被跳过**：P0 合入即过闸 B——若主会话未在合入前确认 §3.5 字段表，add-only 冻结轨道提前锁死。缓解 = §4.2 开工前检查单第一条 + 本稿 §3.5 逐字段标注来源（零新增字段）。
3. **信封设计草案被当终态**：§3.4 全节标推断——P0 实现即第一版，Q3 重议窗开到 P3 前；若 P2 静态实例内置索引时发现信封字段不足，改版成本在内野为零（无在野消费者）。
4. **暂名漂移**：berry-crypto/索引工具/账本文件名均暂名（README :50 纪律），定名随 #77——实施刀不得在 #77 落册前把暂名写进冻结面（docs/索引/AGENTS）。

### 4.2 P0 与「SDK-2 P0 合入前」两不可逆点的关系（任务书要求明示，收口）

1. **Q6 账本 schema（主关系）**：架构决策.md :301 定 Q6 最晚重议 = 「SDK-2 P0 合入前」。本拆刀的 P0 含账本首实现（berry-crypto::ledger），故 **P0 合入 = Q6 重议窗关闭、闸 B 通过**。开工前检查单：①主会话终核 §3.5 字段表（对照 v1.2 §二 :38–45 + 09 §2.4 :153–164，本稿零新增字段）；②确认 `oem-system` 枚举与四字段占位即终态（V4 文档面已随 v1.2 落——修订记录 :145–148；P0 是其首代码化）；③保守拒绝语义过一眼（09 §2.4 :169）。三项确认后 P0 才可合入。
2. **Q3 信封格式（次关系）**：:301 同行定 Q3 最晚重议 = 「首个编队 OTA 实现合入前」（≈P3 合入前）。P0–P2 全程信封**不冻结**：P0 实现 v1（§3.4 推断草案）、P1 随 mkapp 消费再校、P2 随索引实例再校——三次实装即三次免费评审；P3 合入前冻结。这意味着 P0 无信封格式上的不可逆压力，**唯一不可逆压力在账本 schema**——工期与注意力分配据此倾斜（原语与账本优先，信封保持轻实现）。

### 4.3 P1 详述（mkapp 集成）

- 半刀①（前置修复）：`tools/mkapp.py` :433–446 [security] 两键硬等式 → 三键（berry-manifest lib.rs :897 已三键的镜像同步——帽常量同步义务注 §3.3-3 的首次兑现）。不修则三键 manifest 打包即拒（§1.4 活隐患）。
- 半刀②（签名产出）：mkapp 产包管线尾部产 `app.bap.sig`（信封 v1：测试钥/开发钥签名；manifest 关键域摘要按 §3.4-②）；`abi_revision` 打戳（双轨 v1.1 §二 :28–33——u16、构建工具自动打、v1 起 = 1）。

### 4.4 P2 详述（镜像内置静态源 + boot 对账）

- 索引生成工具：条目八字段（id/三值版本/size/哈希/key_lineage/公钥见证/last_revision/cert_status——v1.2 §五 :88–91）+ 源钥签索引 + 索引级单调版本号（回降拒）；TLV 形态（ADR #59 基座归属 = §5-Q1 开放问题）。

## §5 开放问题（不替拍板，终裁归主会话）

- **Q1 TLV 基座归属**：信封/索引的 TLV 解析 = berry-crypto 自持（本稿 P0 方案——信封专用最小结构层）vs 并入 ADR #59「TLV 校验器独立 crate」（:68 立法在册、crate 未落、三消费者 = 设备解释器/live preview/LSP 的 GUI DSL 面）。v1.2 §三 :65/:94 的「复用 ADR #59 TLV 单解释器」若指同 crate，P0 信封解析器将来要迁居——迁移成本 vs 先行收益，归主会话。本稿立场（推断）：#59 的 TLV 是 DSL 语法族面，信封/索引是二进制 wire 面，两者同纪律（单解释器）不同载体，P0 自持不违约；但若终裁同一 crate，P0 的 envelope.rs 应写成可整体迁出的独立模块。
- **Q2 manifest 关键域摘要的单源路径**：berry-manifest path 依赖消费 vs 规范字节段约定（§3.3-1 二选一）——涉及 berry-manifest 是否 v2 化出「关键域导出面」，归实施刀设计 + #77。
- **Q3 生产钥管理与官方源钥生成**：P0/P1 用测试钥；P2 需要真官方源钥（生成/保管/轮换的运营面——09 §2.5 仪式的钥管理半边）。SDK-2 v1.2 未覆盖（边界 = 不预设商店政策），归主会话另立（或随 #77 附则）。
- **Q4 BLAKE3 重议触发器**：若 v2 增量更新闸门三条件立项（v1.2 §四 :79–82，单包 ≥50MB 时代），哈希吞吐论据复活——届时重议摘要算法（§2.3 建议三反论的登记位）。
- **Q5 sign 面 是否进 P0**：本稿建议进（RFC 8032 向量双向免费覆盖 + P1 必需，§3.2）；工期溢出时后滑 P1（§3.8 预案）。归实施刀自裁即可，非主会话级。
- **Q6 选型终裁本体**：§2.3 三建议 + 反论的拍板（维持自建 or 翻案外购）——**本稿唯一要求主会话显式出拍板语句的项**（建议格式：裁定/依据/边界/重议触发器——12 号 §1 拍板语句形态）。

## §6 反面自检（如实写）

**最可能被挑战的三点**：①「≤1 周做自研 ed25519 是乐观的」——成立风险实在（§3.8 D3 高风险注），缓解 = 溢出预案（envelope/ledger 并行先行）+ 本稿工期是「首刀合入」口径不是「完美实现」口径；②「P0 合入即过闸 B 太重，账本 schema 应该再拆」——反方有理但拆掉更糟：账本解析器与水位比较器离开信封验证没有独立验收面，且 Q6 终核点本来就该钉在首代码化上（早钉早便宜）；③「裁决包对 dalek 不公平（拿纪律压生态背书）」——部分成立：零外部依赖是事实纪律非成文铁律，若主会话裁决「user/ 工作区可开 crypto 例外」，本稿 §2.1 事实表已备齐外购路径的全部前置（许可证/MSRV/依赖树/none target 风险点），P0 骨架（信封/账本/selftest）对选型零敏感。

**最可能失败的两点**：①Wycheproof mixed-order 例首跑红且修复回灌超预算——首刀红线（全向量门不过不合入）会推迟 P0 合入，连带 Q6 终核与 #77 落册顺延——失败判据 = D5 末仍未全绿；②Q6 终核流程被「先把刀合了再说」的惯性跳过——这是流程失败非技术失败，本稿已在 §4.2 检查单 + §3.9-2 双位布防，但布防只在文档里，执行靠主会话开工令引用本稿 §4.2。

**本稿未做而该被追问的**：①未实测 none target 编译（若外购案的 cpufeatures 风险要坐实/排除，需一次 aarch64-unknown-none 试编——P0 开工半天可做，本稿只标推断）；②未给 Wycheproof 向量精确计数（fixture 实测为准，§3.6 已注）；③P2 的官方源钥生成未设计（§5-Q3 开放）；④V4/V5 总表行「待落」滞后只报不修（并行 lane 共享文件纪律）。
