## §0 摘要（一屏版）

- **预埋分档的判据是代价机制，不是重要性**（§1.1）：①进包/镜像/账本/在野验证器的**持久格式与枚举**——错过 = 全量重打包/账本迁移/旧验证器拒新件（Linux/Windows 两课，07 号 §5）；②**双侧同步面**的词表/常量——每迟一天同步点更多（08 号 §5.2-2）；③纯文档/纪律——漂移债但不破在野件。**A 档（必须 v1）16 项全是①②类或③类的关键行**；product 清单全键集、svcmgr 编排数据化等降 B 档（可 v2）；namespace/policy_bind/治理三题降 C 档（v2+ 再说，且 C5 治理题**无技术载体可预埋——预埋是错误的解法**，05 号 N4/N6/N7 架构管不到）。
- **13 条开放问题全部有证据基座可拍**（§2）：两轮下沉后，Q1/Q3/Q6 有 09 号星状身份与账本 schema 草案、Q2 有 08 号双键+合一提案、Q4 有 07 号 BCTS 工程形态 12 条、Q10 有 09 号 blob 三案、Q12 有 09 号 D1–D4 判据——**没有一条仍是「无证据裸问」**；但 Q5/Q12 数值/Q9 强制力是治理与商业题，建议明确不进技术 ADR。
- **立法路线三去向**（§3）：不可逆原则走 ADR（新号 #82 总纲 / #83 配置层+槽位合同 / #84 BCTS；OEM 身份与账本**并入已预留的 #77**，09 号 §2.4-3 已明示「不另开通道」）；字段级机制走 docs/ 设计文档（08 号升格、09 号并入 SDK-2 升版）；案例证据留 research 存证不执法。插入点与 `docs/路线图-v1.0.md` 的对接：**预埋全部是文档行/宿主工具行，零内核/syscall/wire 改动，M-VM 主线零影响**；硬闸只有一个——**三件套（配置层/签名链/BCTS）必须全绿先于 P8 真机/OEM 接触窗**（04 号 §8.2-1 失败判据，05 号 N5 已升格生死判据）。

## §1 v1 预埋清单（核心交付）

### 1.1 分档判据：三类「错过的代价机制」

预埋项的取舍不按「重不重要」，按**错过 v1 再改的代价机制**（每项必须能回答「晚做会发生什么」）：

| 机制 | 含义 | 晚做的代价（可复述的坏事） | 出处 |
|---|---|---|---|
| **I 在野格式 break** | 进 `.bap`/镜像/账本/签名索引/在野设备验证器的持久格式与枚举值 | 全量重打包 / 账本迁移 / 旧验证器拒新件 / 更新协议 break + 全量重刷——且 add-only 词表**退出机制只有两种**（语义退出不退号 / 整代表换域），不存在「删号重排」（07 号 §5.1） | 07 号 §5.1/§5.2（Linux 全量重打包课、Windows「错过嵌入 ABI revision 时机，现在用启发式猜」课）；09 号 §2.6/§3.4/§5.4 |
| **II 双侧同步面扩散** | 词表/常量在多个消费点有镜像（parser↔mkapp↔appd↔devmgr；内核↔BerryBoot） | 扩容成本 = 同步点数 × 验证面；预埋的价值不是省时间，是**防止漏掉一个同步点**（史例：35/39/38 三口径打架，abi.toml :33-35 史注） | 08 号 §5.2（三条代价规律）；berry-manifest「双侧同步」头注 |
| **III 文档/纪律漂移** | schema 文档、治理原则、登记表 | 不破坏在野件，但产生口径漂移与心智债（章程「35」vs abi.toml「37」文档债为现役实证）；可后补，代价是债 | 01 号 §2 L0 行；08 号 §6-12（预埋的执法） |

**分档**：A 档（必须 v1）= 机制 I 全部 + 机制 II 全部 + 机制 III 中「随 ADR 落册才有效力」的关键行；B 档（可 v2）= 格式已由 A 档预埋、实装重且动设备侧或依赖 BCTS 立项；C 档（v2+ 再说）= 运行面里程碑未到（namespace/policy_bind/M4）或**根本没有技术载体**（治理三题）。

### 2.1 Q1 OEM 身份发放机构与规则

- **重述**：lineage 分配权在谁；能否多级（OEM→ODM→独立开发者）；与「系统集成者」签名的关系（01 号 §5-Q2 原题）。
- **证据**：09 号 §2.2 星状 vs 树状全维表（16B 姓氏帽装不下深树=算术事实；信任不传递与「永不引 X.509 链」同哲学；父倒子连坐；Apple Team ID 集中分配同构；树状无成功先例）；09 号 §2.3 integrator lineage = 品牌商、ODM 是受托组装者不出现在信任面；05 号 §5-N6/§6-1 平台单点与官僚化风险；09 号 §7.1-1 自认「≤3 家 OEM 时此选择无意义」。
- **选项**：
  - **A 纯星状**：平台唯一注册处，每 lineage 独立锚定。后果：信任最干净、吊销粒度细；平台成身份瓶颈单点。最强反论：Android 无任何身份分配层照样跑起生态——层本身可能是负资产。
  - **B 树状**：OEM 前缀自分配（`acme-*`）。后果：OEM 渠道权力得到满足。最强反论：16B 帽内两级已紧张（算术）；委托链 = 链式信任回潮，与 X.509 禁令精神冲突；OEM 倒闭连坐无辜 ODM（WM 时代 OEM 大批退场是常态，05 号 §2.1）。
  - **C 星状 + 账本元数据**：分配权全在平台，层级关系降级为 `kind`/`issued_by` 元数据不进信任路径（09 号 §2.2 实际提案）。后果：两害相权取其轻。最强反论：元数据可能被 OEM 游说逐步升格为真实委托——滑坡起点。
- **倾向（推断）**：C。
- **载体**：并入 **#77**（SDK-2 分发签名链 ADR，账本 schema 变更随其落册——09 号 §2.4-3 明示「不另开通道」）；发放**运营规则**（注册流程/审核字段）另走治理文档，不进 ADR。

### 2.2 Q2 产品配置层形态

- **重述**：产品清单与「启动配置参数表」（ADR #42 承诺）是否同一件；cargo feature 是否参与；schema 归属 L2 还是新分级（01 号 §5-Q3 原题）。
- **证据**：08 号 §2.4 合一提案三理由（消费半径=boot 链/治理半径=add-only 同执法面/写入者同一人）+ 反合一论点如实记（上游缺省 vs OEM 覆盖双主风险 → override 语义，RFC-0215 同构）；08 号 §2.1-2.3 双键 schema v0 + platform/product 分界依据（承诺面 vs 自由面）；06 号 §7-1/§7-2（作用域与「ECU 提取」中间层开放）；01 号 §1.1 参数表机制面未见实现【待核实】。
- **选项**：
  - **A 合一**：参数表 = `[platform.boot.params]` 子表，缺省归上游（编译期常量仍是缺省）、清单只存覆盖值。后果：单一漂移点/同作者/同治理；内核读取面走 INITRD 定址段（08 号 §2.4-1）。最强反论：双主风险真实存在——上游改缺省值与 OEM 覆盖的交互面是新型兼容问题。
  - **B 分离**：启动参数表独立文件进 INITRD，产品清单只管组装。后果：职责清晰。最强反论：消费/治理/写入三半径全同（08 号 §2.4），两份文件 = 两个漂移点，分两套 schema 执法必漂移。
  - **C cargo feature 参与**：产品差异走编译期 feature。后果：零新文件。最强反论：与 P2 公理（产品定义永不进平台仓库）正面冲突——feature 是平台仓编译面，OEM 无法树外参与；且 feature 组合爆炸是 Rust 生态已知泥潭。
- **倾向（推断）**：A（含 override 语义）。
- **载体**：独立 **ADR #83**（产品配置层与槽位合同——与 Q3/Q7/Q8 同刀，输入 = 08 号升格文档）。

### 2.3 Q3 产品包签名形态

- **重述**：`.sig` 信封 vs 镜像级签名 vs 度量链覆盖；与 SDK-2 §五「镜像内置源」的关系。
- **证据**：04 号 §3.1-要点（提案倾向：清单与资产走 `.sig`，最终镜像走度量链）；09 号 §1.5/§2.3（清单+委托段 + 产品包 `.sig` 组合；AVB chain partition 委托段同构）；09 号 §1.4（度量链是完整性账不是身份账——blob 三住址的覆盖证明）；SDK-2 §五镜像签名先例。
- **选项**：
  - **A 产品包走 `.sig` 信封 + 镜像走度量链**（04/09 双稿同倾向）。后果：复用信封家族零新格式（章程 §四-1 同构）；身份（信封）与完整性（度量）分账清晰。最强反论：两种机制的边界要讲清楚——「度量不保证 blob 无恶意」的诚实边界在对 OEM 叙事里极易滑坡（09 号 §7.2-2）。
  - **B 镜像级整体签名**：产物一次签完。后果：模型简单。最强反论：与编队/增量更新冲突——每改一张壁纸重签全镜像；且产品包无法独立于镜像验签（组装期白名单校验失去载体）。
  - **C 仅度量链覆盖**（无独立产品包签名）。后果：最轻。最强反论：度量链答「变了没有」不答「谁负责」——integrator lineage 身份无处表达，V3/V8 字位悬空。
- **倾向（推断）**：A。
- **载体**：**#83**（与 Q2 同刀——产品包格式是配置面的信封面）；账本/信封细节归 #77。

### 2.4 Q4 BCTS 执法位

- **重述**：并入 G0–G5 关卡还是独立套件；谁跑（OEM 自测+平台裁决 vs 第三方）；测试集发布节奏与版本绑定（03 号 §11-Q5 原题）。
- **证据**：07 号 §6 十二条工程形态（冻结测试件/PlaSA 清单/依赖闭包白名单/三 tier/版本绑定尾缀/abi_revision 四级执法/防特调结构性/四层分工/SDK 分类执法链/测试专用 API 面/基础件-扩展件分离/商业模式选位）；07 号 §7-1/§7-9（节奏与 G 关卡关系原样开放）；06 号 §7-3（AUTOSAR 验收测试独立版本化先例）；01 号缺口 4（smoke 是开发冒烟非认证面）；05 号 N5（执法先于开放，升格生死判据）。
- **选项**：
  - **A 独立套件 + 冻结工件随版本发**（CTF freeze/thaw 同构，07 号 §6-1）：认证 = 用设备声称版本的冻结件回放。后果：防 OEM 特调是结构性的；与 G 关卡（开发冒烟）天然分离。最强反论：07 号 §8.1——只抄结构无 tier 政策，「冻结的可能是空集」；测试集维护是持续成本。
  - **B 并入 G0–G5 关卡**（随开发节奏滚动）。后果：零新体系。最强反论：G 关卡是「本仓开发验收」，BCTS 是「对外承诺执法」——受众/节奏/失败语义全不同；活树测试对 out-of-tree 组装者不构成承诺（01 号缺口 4 病根本身）。
  - **C 双轨 + 组装门禁**：承诺面冻结件（A）+ 执法挂 berry-assemble 组装管线（「测试即门禁」，04 号 §4.1-2）+ Tier 1 先行（在野回归=用例欠账记账，07 号 §6-4）。后果：成本最低起步。最强反论：「组装门禁」依赖 V13 工具落地——门禁晚于清单工具则 BCTS 空转期无执法。
- **倾向（推断）**：C（= A 的形态 + 渐进覆盖策略）。
- **载体**：独立 **ADR #84**（BCTS 立项）；依赖 #82（能力基线）/#83（槽位合同面）；工程种子挂 smoke/abi-check 现役轨道（01 号 §1.6「CTS 的种子在这里」）。

### 2.5 Q5 治理杠杆形态

- **重述**：认证标记失效之外，要不要任何类 GMS 机制（官方源独占/商店准入）；商标运营主体（02 号 §6-Q6、03 号 §11-Q8/Q9 原题）。
- **证据**：05 号 §5-N4（OEM 商业动机——「免费+合同化」组合中治理杠杆只剩认证/商标/信任账本）+ §6-6（GMS 反垄断教训，认证杠杆合法边界）；02 号 §3.2（GMS=治理补丁双刃）；04 号 §3.4（治理面诚实陈述：三者缺一则 fork 无代价）。
- **选项**：
  - **A 纯技术杠杆**：认证标记 + 信任账本网络效应，无商业准入。后果：合法性最稳、强制力最弱。最强反论：对 fork 漂移无速度限制——fork 设备在野外仍可跑 `.bap`（04 号 §3.3 末行）。
  - **B 类 GMS 商业杠杆**：官方源独占/商店准入挂钩。后果：强制力强。最强反论：直接复刻欧盟反垄断风险（02 号 §3.2），且 v1 连在线源都没有——杠杆无支点。
  - **C 商标 + 认证合同**（法律面）。后果：对「BerryOS 兼容」徽标有法律抓手。最强反论：商标未立法、运营主体未定（04 号 §4.5-5 自认超出技术立法）。
- **倾向（推断）**：A 起步（与技术杠杆成熟度匹配）；B/C 在首个 OEM 接触前再裁。
- **载体**：**不走 ADR**——治理/商业文档 + 合同模板，延后至首 OEM 接触窗口（X5 同判）。

### 2.9 Q9 上游化政策的强制力

- **重述**：纯倡导（Zephyr 式 TSC 门只管默认清单）还是认证条件；产品特有件与通用件的判定权（04 号 §2.3 原题）。

### 2.10 Q10 blob/闭源驱动政策

- **重述**：允许与否、最低披露线（许可/来源/哈希）、度量链如何覆盖闭源件（03 号 §11-Q6 原题）。

- **载体**：原则进 **#82**（分层适用表）；五字段门禁随 mkapp（V6，工具面）；cage 档随 devmgr v2 刀 ADR（驱动模型既有轨道）。

### 2.12 Q12 跟版义务 SLA

- **重述**：N 值多少、超窗后果（标记失效 vs 摘牌）、OEM 停更后的设备责任边界（03 号 §11-Q9「无先例可抄」原题）。

  - **B v1 末转正**（早于产品清单实装）。最强反论：v1 无 OEM 无换壳需求；svcmgr 装配段改造在 M-VM 主线上是纯风险（08 号 §7.3 同款重构风险）。
  - **C 不转正**（launcher 永为 bin/ ELF）。最强反论：与「系统应用 = 普通 .bap 同格式同门」（应用规范 §11.1）正面冲突——launcher 是事实上的系统应用。
- **倾向（推断）**：A（v2，与 W5 同刀）。
- **载体**：应用规范 §15.3 升版补行 + GUI 刀序规划文档；v1 动作 = V12/W5 的过渡值设计（已含）。

## §5 反面自检（如实写）

### 5.1 本清单最可能过度设计的三条（为遥远未来付出当下复杂度）

1. **签名链 OEM 字段位按「多 OEM 未来」全额预埋**：A 档 16 项中 V2/V3/V4/V5/V7 五项是签名链/账本字段位——而 BerryOS 是否走多 OEM 路线本身未决（05 号 §6-2「平台方是否自产设备」开放），09 号 §7.1-1 自认「若永远只有 ≤3 家 OEM，这个选择无意义」。辩护是「1 行文档位很便宜」，但**便宜是按单项算的**：五个字段位 + schema 文档行 + 校验器占位 + V16 登记条目，合计是一套要永久维护的负空间；若后续走单一 OEM 路线，它们成为无人消费的僵尸 schema。
2. **product 清单骨架 + slots 单源生成器在零 OEM 期定形**：V12/V14 是「先造模具后知道要铸什么」——08 号 §7.2 自认 ARXML 化风险（Fuchsia platform_settings.rs 巨 schema 是前车），06 号 §6.3-抛弃 1 恰恰批判「为想象中的跨组织交换预付复杂度」，而本清单把它部分合法化了（本稿已把全键集降 B 档对冲，但骨架与生成器仍是 A 档）。诚实代价：两实例（fsmgr/显示后端）的合同是从现役源码**反推**成文（08 号 §7.1 自认「成文过程可能与实现漂移」）——第一版模具可能就要返工。
3. **预埋登记表 + docs_guard 审计扩展（V16）**：为防漂移再造一个执法工具——而执法工具自身也是债（06 号 §7-12 工具置信 TCL 题：mkapp/abi-check/berry-assemble 这些执法者自己错了谁负责——登记表审计器加入该清单）。且 16 项 A 档 + 7 项 D 组的登记维护本身就是新的同步义务，恰是 08 号 §5.2-2「双侧同步是债的放大器」的自我复制。

### 5.2 最可能漏掉的三类风险

1. **预埋载体的时序风险（挂在未开工的地基上）**：V4/V5 挂 SDK-2（定稿**未开工**，01 号缺口 3）、V7 挂 OTA 设计（无代码面，缺口 11）、V2/V3 挂 ADR #59 骨架——09 号 §7.2-1 明示「若 SDK-2 开刀晚于首个 OEM 接触，本文的账本 schema/编队格式会经历一次『纸面定稿→推倒重对』的浪费循环」。本清单**未对每项标注「最晚预埋时点」**（如 V4 最晚 = 账本首个在野实现合入前），预埋过早与预埋缺失同样是错——这是本稿结构性缺口，登记为待补。
2. **平台自演进推翻预埋（无外部对拍的首版设计）**：v1→v2 是 BerryOS 自身 schema 快速增长期（04 号 §8.2-2），预埋的首版枚举（feature_level 三值/anchor_type 四值/cert_status 四态/oem: 前缀）没有任何真实 OEM 消费者校验——错误的设计第二版就暴露的概率不低；而 add-only 纪律只保证「能加」不保证「首版对」，**首版错的 add-only 词表 = 永久携带错误语义位**（07 号 §5.1：退出机制只有语义退出不退号）。缓解 = 枚举最小集（已采）+ 首个真实消费者入场时强制作废复核（本稿新增建议）。
3. **「架构已备好」的组织错觉延迟治理决策**：本清单 16 项全是技术面，而生死矩阵判一半死因在 N4（OEM 商业动机）/N6（单点依赖）/N7（生态窗口）——05 号 §5 映射总表三行明示「架构能否独立保障 = **不能**」。预埋清单越完备，组织记忆越容易滑向「OEM 问题已解」，推迟真正的治理/商业/时机决策（收费模式/自产设备冲突/生态冷启动度量——05 号 §6 三题至今零立法）。这是文档债的组织学形态，无工具可执法，只能靠本节这样的自检条目周期性重读。
