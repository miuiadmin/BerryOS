## §2 案一攻击：查询面双件制（G2）

### 2.1 攻点 A1：双轨对第三方开发者可达性双断——G2 空白未被闭合 【致命】

- **件一（静态件文件读）**：「查询 = 文件读」（19 号 :52）预设第三方 app 能打开 `sys/…/info`。现役事实：路径命名空间无运行面（01 号维 6 行，:126 一带：「现役发现 = svcmgr 端点直递」；ADR #61 延后 v3）；S3 per-process 命名空间挂 v2（存储布局 :166 阶段表）。app 读系统树只有两条现设想的门：①fs scope 能力（`fs∈{"rootfs"}` 词表位在、appd 现役 loud 拒，01 号维 8 行）——为读一个 128B 级静态件授整棵 rootfs 读域，违反最小权限，且是 Android「重权限换薄需求」的老病；②默认把 `sys/info` 挂进每个 app 命名空间——环境可读面扩散，恰是沙箱纪律要防的方向。**19 号只自认了件二的悬空（§1.8-4 依赖边、§3.2 自检），件一的消费面依赖未自认**。
- **件二（试连探测）**：探针原语 = 「受控 connect 尝试 + 入口存在性检查」（19 号 :58）——现役机制里**两个动词都不存在**：无按名连接 syscall/IPC op（handle 是 spawn 时 svcmgr 直递的，不是连来的）；「入口存在性检查」预设可查的路径表（= v3 命名空间 + V14 X1「槽位 id ↔ `/svc` 路径映射规则一行」，而 V14 归档位现状态 =「归档位待落」，`docs/架构决策.md` :254）。依赖栈两层全未立，且 v3 命名空间**没有排刀位**（挂在「多 app 并发刀后再独立 ADR」）——19 号说「查询面落 #83 时须与命名空间可见性一刀对齐」（:111），但 #83 是产品配置层 ADR，**不辖命名空间可见性**——「同刀」是空指。
- **合击**：18 号 G2 空白原文 =「**第三方开发者运行时感知**设备差异全系列零研究」（18 号 :97，着重号为引者加）。双件制两轨在 v1 对第三方 app 皆不可达——即便照单收编，G2 也只是「立法收口、运行时空心」。19 号自己的验收线改写（「`sys/info` 解析 host 测」，:109）泄露了这一点：**host 测 = 开发者面交付为零**。
- **终判：致命**（对「作为 G2 收口件照单收编」的形态）。修法一句：v1 交付重定义——键位立法 + host/BCTS 消费 + VMO 面承接「版本身份」现已落的部分，应用可达查询面明标随 v3 命名空间刀激活，18 号 G2 状态改「部分收口·运行时面挂 v3」。

### 2.2 攻点 A2：与 version VMO 职责重叠 + 现役查询面已在漂移——撞车属实，合并可行 【可修·收编前必裁】

- **重叠面**：VMO 现役携带 level/semver/flags(debug)/git-ident/rustc（`kernel/src/sysver.rs` :9–:18 合同），boot 经 svcmgr 表第 9 插 `0x0001_0009` 只读交付（`kernel/src/main.rs` :1500–:1517）。`sys/info` 键位表（19 号 :63–:75）中 `platform.platform_revision`（:72）与 VMO `level` 是**同一 datum**（7775ccf 后 PR≡level 单源，`tools/abi.toml` :28–:29 唯一源）——两运行面、两种类型（清单 u16 / VMO u32）、**零对拍设计**（VMO↔.berryver 有字节级对拍哨兵，`user/bins/svcmgr/src/main.rs` :685–:687、:2193；sys/info 谁与谁对拍？无）。`platform.build_type` {eng,userdebug,user}（:71）与 VMO `flags` bit0 debug_assertions 双编码同语义近邻，可各自漂移。术语地雷：`platform.feature_level`（形态档 {rich,minimal,wearable}，08 号 :271 逐键表）与 PR≡level 后「level = 能力代次」的负载词**撞名**——SDK 文档层面必然混淆。
- **实锤（查询面碎片化已发病，非假设）**：`user/berry-libc/src/sys.rs` :291–:315 **现役已有第三路查询面**——libc `uname`，且返回硬编码常量：`UNAME_RELEASE = "0.1"`（:293）、`UNAME_VERSION = "berry-libc-shim-1"`（:294），而 workspace 版本已是 0.2.0（`Cargo.toml` :7，tag `v0.2.0` 在册）——**现役 app 面版本查询已在说谎（漂移一个版本）**。这是「查询面无单源消费纪律」病的现行犯：平台对词表立了「无手写副本」纪律（SDK-2 §四 :61–:63），对**版本查询面**还没有——19 号不加消化地再添 `sys/info` L2 读取 API（:110），等于往五路载体（VMO/.berryver/libc-uname/探针/sys-info）里再加第六路。
- **撞车判定**：非全含重叠——VMO 无 product/board/locale/形态档，`sys/info` 无 semver/git-ident/rustc；但重叠带（平台身份）上 VMO 完胜（完整性最强：内核 .rodata 编译期成像 vs 待验签文件；已落地；有对拍哨兵）。**合并窗正当其时**：两边的 app 面 API 都还没定（VMO 现役消费者 = svcmgr 对拍 + ktest；sys/info 未建）——现在合并是零成本，#83 schema=1 冻结后再合并 = add-only 长期带伤。
- **终判：可修**（合并案）。修法一句：版本身份键（platform_revision/build_type/将来 security_level 呈现位）以 VMO 为单源（BVER `hdr_ver` 合同本就允许向后兼容加字段，`sysver.rs` :35–:36），`sys/info` 收缩为「产品身份件」（product.\*/board/形态档/locale 族），L2 查询 API 单入口合流两源，libc uname 常量接单源先修漂移。

### 2.3 攻点 A3：「试连 = 探测」的语义漂移——替换实现 × 合同版本不透明 【可修】

- 19 号 :58「探测即事实——OEM 结构性无法谎报『有』」只对**存在性**成立。替换面现实：OEM 换实现（槽位合同保 wire 兼容，04 号 §2.2/:77–:93），同一探针名下行为面（时延/错误码细节/时序）允许合同内漂移——开发者跨设备观测不稳定的正是这一层，探针布尔对此**结构性哑然**。更硬的一刀：服务包带 per-interface version 声明、`platform_compat = [min,max]` 区间合法（09 号 §3.1 字段表）——同一服务名可呈现**不同 op 集**（旧版合同实现）；探针「不返回版本号」（19 号 :58）意味着开发者探到「有入口」却无从知道「有没有你要的那个 op」——需要 v2 op 的应用探针 true + 运行时调 op 失败。探测把「存在」与「够用」混为一谈，**「探测即事实」是过度宣称**。另外试连的错误分类学（无入口/无权限/服务死）未定义——服务崩溃重启期探针 false，应用误判「无此能力」，瞬态与结构性缺席不可分。
- **终判：可修**。修法一句：探针返回 `(present, interface_version)` 二元组（或词表钉死每名一版），错误面三分（not-found/denied/dead）随 v3 命名空间错误码族一并立；行为漂移残差由槽位合同 conformance 兜底并如实登记为不可消除项。

### 2.4 攻点 A4：sys/info 住系统树随槽验签——验签机制现役不存在的先有鸡先有蛋 【可修】

- 「度量即防篡改——静态件在树内，树签名覆盖它」（19 号 :54）：整树验签 = 度量链 #24 延伸，**设计位**（`更新与OTA设计-v1.0.md` :63 验签步）；签名链**未开工**（01 号现状表维 3：「签名 = 无」；SDK-2 签名链实现几周级、待拆刀）；闸 C 才开。而 `sys/info` schema 计划**先于**执法就位冻结（#83 拍板时 schema=1 add-only，19 号 :108）。窗口期推演：OEM 是文件的**作者**（组装器跑在 integrator 侧）——树验签防的是运行时篡改，防不了作者说谎（见 A5）；在验签就位前，连「运行时不可篡改」也只是修辞——对比之下 VMO 的完整性靠内核镜像本身（编译期 .rodata，`sysver.rs` :121），不依赖任何未建机制。次生问题：若闸 C 时验签/度量面设计反过来要求 sys/info 变更形态（进度量分区/加 hash 字段），schema=1 已冻结，只能 add-only 绕行。
- **终判：可修**。修法一句：`sys/info` 内容 hash 进 V9 `manifest.txt` 侧产物（构建期对账，D2 三件套同刀）+ 全部「防谎报/防篡改」宣称的生效点明绑闸 C，此前文案只许称「构建期对账」。

### 2.5 攻点 A5：防谎报三执法位的实际可执行性——同源自证循环 【可修】

三执法位（19 号 :92–:94）逐位拆：①**组装期对账** = 组装者（= OEM integrator 自己）跑自己的工具检自己的清单——lint，非见证；②**认证期 BCTS 断言 A/B** = 对**送检镜像**回放——认证时诚实、出货时换镜像，无在野对账机制拦截（度量链重组对账是设计位；BCTS v0 门禁宿主 = 现役 just 配方树 host 侧，`docs/架构决策.md` :276 Q4）；③**运行期词表拒载** = 读**设备能力集**——而设备能力集本身又是镜像内声明（作者期数据）。**三位读的是同一份自声明族**——不是三个独立见证，是一个事实查三遍。唯一独立见证是试连，而试连只覆盖可连特性（v0 唯一在册 = gfx 三档）。19 号 :92 的结论句「谎报『有』结构性不可谎报」只对探测轨成立，对描述轨（feature_level/board/vendor——恰是谎报高价值区）实为「组装自检 + 送检对账」，强度口径与措辞不符。
- **终判：可修**。修法一句：文案降格为「防运行时篡改（绑闸 C）+ 认证送检对账」，删「防谎报三执法位」的独立见证暗示；在野证明能力挂度量链（闸 C 后）如实列为缺口。

### 2.6 攻点 A6：内部矛盾——布尔返回装不下 gfx 三档能力位 【可修】

§1.3 件二定义「返回布尔」（19 号 :58）；同段自证「v0 唯一在册探针族 = gfx 三档后端能力位」（:61），SDK-2 §三原文「三档 gfx 后端差异用**能力位**表达（ADR #51 既定方向）」（v1.1 :51）。布尔装不下三档；§1.6 断言 B「gfx 能力位与镜像内容一致」（:93）同样预设档位值。**提案自身返回形态与唯一在册用例不兼容**——schema 起草时未对拍消费面（又一次 11 号 §1.2 病）。
- **终判：可修**。修法一句：探针返回形态定为位集/枚举（对齐 SDK-2「能力位」原语），SDK-2 §三升版时同步。

## §3 案二攻击：安全快道（G3）

### 3.1 攻点 B1：「功能轴回退不受安全地板反噬」在常态下为伪——回滚语义与自家行业证据对撞 【致命】

- **机制推演（全部锚点在册）**：快道后安全地板绑 `lane_revision`（19 号 :170 配套②：「反回滚计数绑 lane_revision……**功能轴回退不受安全地板反噬**（09 号 §5.3-2『解耦』推理的落地形态）」）。但 L1 是整树翻转：任何回退目标树携带的是**它自己被编队时的 lane 值**。常态序列：快道 F（lane 6）→ SUCCESSFUL → 地板 6 → 整编队 M（含更新的安全内容，lane 7）→ SUCCESSFUL → 地板 7 → M 功能回归需回退到 F 树（lane 6 < 7）→ **被安全地板挡死**。「功能轴回退不受反噬」仅在 M 不含新安全内容时偶然成立——而整编队吸收快道内容是必然（M 必须含 F 的修复，否则 M 的 lane < 地板装不进去），**所以常态恰是反噬成立的情形**。09 号 §5.3-2 的解耦原意是「OEM 件版本变化不抬地板」（:360）——被 19 号误植到「快道抬地板不碍功能回退」，对象错了。
- **自家证据反自家结论**：19 号 §2.2 行业表原文——Mainline「模块间原子安装/**回滚**」（:127，两源：02 号 :186–:188 本轮复核同文）、ChromeOS DLC「每 DLC **自带 A/B 预留块**」（:128）、Windows 质量更新有卸载窗（:129 页面族）。三家快单元**全部自带快回滚**；§2.2 提炼②「拆轨件各有自己的原子边界」被 19 号读成「各有各的翻转」，实际共性是**快单元 = 原子安装 + 原子回滚对**。案二只借了速度（快道先行），没借回滚（整树回退被自家 lane 地板堵死），却保留了案甲的地板纪律——案甲从不面对此矛盾，因为案甲编队稀少且联测。**SUCCESSFUL 后的坏快道不可回退、只能前滚修复，而前滚修复过的是同一套未实证的质量闸**——失败遏制不对称。
- **终判：致命**（裁定理由③与配套②的不变量表述错误，非参数级）。修法一句：lane 地板延迟生效（SUCCESSFUL + 浸泡窗；无墙钟则以 boot 计数或「下一 lane 到达」为界——版本当时钟同族推理）或允许回退到「同 lane 重制树」；不变量重立前不得收编。

### 3.2 攻点 B2：`lane_revision` 的偏序/累积未定义——`≥` 比较的数学地基缺角 【致命·照文冻结形态】

- 八键 schema 把执法压在「更新服务校验 lane_revision ≥ 活跃槽值」（19 号 :161）上——`≥` 成立的前提是 lane 全序。未定义处三连：①**快道必须累积吗**（F2 ⊇ F1？）——非累积快道（F1 修 A、F2 修 B 不含 A）使 lane 7 与 lane 6 不可比，`≥` 地板判定无意义；累积强制则每次快道全量重发安全内容，与「先行子集」的轻量叙事矛盾。②**快道→整编队吸收是否重复计数**——M 含 F 已发修复，M 的 lane 是重记（同内容双计数，security_level 与安全内容脱钩）还是继承 max（内容寻址）？未裁。③**`scope` 预留 `"critical"` 分级**（:168）——分级即双轨道双地板，偏序问题平方级复发；该预留自嵌矛盾。另：u16 全序号跨设备可比（sys/info 公开·诊断，:73）预设一张**平台安全公告序列注册表**（Android SPL 日期的对应物）——全新治理面，零设计（#82 :215 只留字段位）。
- **终判：致命**（照文冻结形态；执法键的比较语义空洞）。修法一句：累积强制 + lane 内容寻址（lane = 所含最高公告序）+ 整编队不重复计数 + `scope` 降纯元数据（不参与地板）——四句入 schema 注记方可冻结。

### 3.3 攻点 B3：carried 段「原验签续用」与 D9 槽身份绑定纪律直接冲突 【致命】

- 冲突双方：快道 `oem_segment = "carried" + 段 hash`，「OEM 段 = 当前活跃槽原段整段引用；原验签续用（不重签）」（19 号 :166）；D9 已落纪律——「L0 slot 条目与 L1 树清单的**签名消息设计时即绑槽与树身份**」（`docs/架构决策.md` :247 表 D 行；源头 `更新与OTA设计-v1.0.md` :102–:107，动机原文「跨槽重放（A 槽签名条目挪进 B 槽）签名拦不住」）。推演：若 OEM 段签名按 D9 绑槽/树身份——从活跃槽携带进**备槽新树**验签即死（这正是 D9 要杀的重放形态）；若为快道开洞让段签名不绑槽——D9 对 OEM 段留洞，且「绑树身份」的完整叙事需重写。两头都动纪律。附带一击：carried 语义使快道包**设备状态相关**（每台设备活跃槽 OEM 段 hash 各异，在野 OEM 段版本多元）——平台签名的通用包要么按段 hash 变体发包（平台须知道全部在野段 hash——账本/遥测负担未设计），要么包不签段引用、设备端自行拼装——那平台签名覆盖什么、拼装后树完整性谁证，未定义。
- **终判：致命**（与已落 D 行纪律冲突，且 carried 的签名覆盖面未闭合）。修法一句：段级签名域条款（OEM 段绑段身份不绑槽、树身份由平台段装配清单承担）或改「OEM 段 hash 白名单进平台段」替代案——随 #77 签名格式一刀裁并同步改写 D9 句；未裁前 `[security_fastlane]` 不得随 V7 冻结。

### 3.4 攻点 B4：Tier 1 回放空心 + 联测悖论——案乙死因原样复活 【致命】

- **回放三无着落**：承诺 =「编队期对在册替换件执行 Tier 1 ∩ 受影响面子集回放」（19 号 :151 反论④、:167 `replay_tier`）。执行者/场地/时机拆解：平台侧编队（快道的全部意义 = 平台单方出件）**手里没有 OEM 替换件**（逐 OEM、可闭源）；设备侧装前执行替换件回放 = 在备槽上下文里跑第三方服务的 staging 机制——全仓无此设计；BCTS v0 门禁宿主 = 现役 just 配方树 host 侧冻结件回放（`docs/架构决策.md` :276 Q4）——host 跑不了硬件绑定的替换件。三处皆不承接，承诺无可执行形态。
- **联测悖论（更根本）**：案甲的卖点从来不只是「单次翻转」的机械原子性，而是**组合经过联测**——09 号 :329 案乙死因原文「平台新版 + OEM 旧件的组合**未经联测即上设备**」。快道 carried 设计 = 平台新安全件 + OEM 旧件的组合，OEM 零动作 = **无人联测过这个组合**——与案乙中间态同构，只是换了动轴（安全轴动 vs 功能轴动）。19 号 §2.3 对照表把案三（槽级独立）判死时用的正是这条理由（:140「中间态有——案乙死因的放大」），却未检查案二自己是否同病：单次翻转保住了**机械原子性**，没保住**联测过的组合**这一案甲实质不变量。
- **终判：致命**（对策无执行形态 + 核心不变量未保）。修法一句：承诺降格为「白名单工件回归 + 替换件 conformance 案例静态适用性比对 + pre-SUCCESSFUL 观察窗」，在野联测残差如实进 #84 断言清单——降格后快道质量闸的真实强度须在裁定理由里重新陈述，不得再以「Tier 1 回放」一语带过。

### 3.5 攻点 B5：`security_level` 单调性 × OEM 停更（D1 expired）语义未定义 【可修】

- 未定义态推演：D1 expired 后（09 号 §3.2 判据表；Q12 停更处置采案 b 替换面回退，`docs/架构决策.md` :284），快道是否继续 carried 一个 **expired lineage 的段**？继续运 = 平台签名无限背书已停更 lineage 的内容，且与案 b 终态（OEM 件拒载、官方实现顶上，09 号 §5.2-2/:351）打架——两套终局并列无裁决；若 expired 触发回退后快道只运官方件，则 carried 条款须写明（19 号 :166 无一字）。更深一层：expired 设备上 `security_level` 持续上升（平台件在补），而树里 OEM 替换件（如闭源网络栈替换件）的 CVE 永远无人补——**单调号以平台轴冒充整机安全态**，对用户/attestor 是系统性误导（sys/info 公开·诊断，19 号 :73）。快道客观上还削弱了「安全补丁断供」这一推动案 b 回退落地的用户受害压力源，延长 expired 态的带病存续（推断——机制推演成立，生态幅度无数据）。
- **终判：可修**。修法一句：快道节增条款「`cert_status ≠ active` 的 lineage 段不获 carried（expired 触发案 b 回退后快道只运官方件）」+ `security_level` 语义明文限定「平台轴安全水位，不含 OEM 件漏洞面」。

### 3.6 攻点 B6：与 PR≡level 三方联动的对拍——无硬冲突，但三冻结合同再动、计价失真 【可修·如实记】

- **正面裁定（对拍结论）**：快道「`platform_revision_unchanged`」（19 号 :162）与 VER lane「PR≡level 单源 + 装配反回滚门 + smoke 断言」（`7775ccf`；`tools/berry_assemble.py` :368–:386 PR ≤ level；`tools/smoke-image.sh` :141–:149 PR == level）**语义相容**：快道树 PR = 当前 level 照过两门；版本域刚挂账清零（沿革一百八十四，`68a2b2f`）不构成技术冲突。攻点在计价：「复用在册冻结件」理由③（:149）低估三处合同再动——①BVER 冻结布局无 security 字段（`sysver.rs` :9–:18 双路合同逐字段冻结；加字段须 `hdr_ver` +1 向后兼容，:35–:36）；②`.berryver` 三段单行格式字节精确对拍（`tools/mkcpio.py` :278–:287，「对拍全等才可达」——加 lane 段 = 两侧解析器锁步改，混合构建哨兵语义随动）；③V9 `manifest.txt` 已落 golden（`d2c7354`/`7775ccf` golden PR 列 0→1 连动），加 `security_level` 列 = 格式再升版 + golden 再生——19 号「与 V9 同刀」（:170）写作时 V9 未落，现已过时。三处都是**有纪律的升版路径**（做得成），但都是成本，「零新机制」的卖点话术失真。
- **终判：可修**。修法一句：三处升版路径与成本如实入计价（BVER hdr_ver+1 / .berryver 加段锁步 / V9 再升版+golden 再生），「复用在册冻结件」改为「三处合同升版 + 复用回退次序纪律」。
