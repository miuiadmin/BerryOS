## §0 摘要（一屏版）

- **题一（G2 查询面）结论：双件制**——①**描述轨**：组装器（V13 管线）从产品清单 + 板表 + 上游工件锚生成静态件 **`sys/info`**，住系统树、随槽整树验签，查询 = 文件读（零新 IPC、零新常驻服务、零启动序依赖）；②**探测轨**：`berry_feature_query`（SDK-2 §三既立）收敛为**能力式试连**——「特性存在 = 服务/协议入口在命名空间可连」，探测即事实、结构性不可谎报「有」。行业四样本同构印证：Fuchsia hwinfo 三 `@discoverable` 协议只管**描述性**信息（本轮两源核验），Android 特性事实源 = 只读系统属性 + `Build.FINGERPRINT` 官方原文「Do not attempt to parse」（SDK-2「不给读系统版本号推荐路径」同款纪律），OpenHarmony deviceInfo「cannot be configured by developers」+ hardwareProfile 废弃改走 SysCap。防谎报三执法位：组装期对账（既立）/认证期 BCTS 断言「声明与实际档位一致」（本文补全断言形态）/运行期探针即事实。**可见性矩阵**：feature_level 可见但仅诊断；**槽位替换的实现者对应用不可见**（透明替换防碎片）；闭源披露位不进第三方查询面。
- **题二（G3 编队粒度）结论：建议采案二「安全快道」**——单次 L1 槽翻转的原子边界原封不动（09 号案甲不变量），编队**内容**粒度细化为「平台安全工件子集 + OEM 三包原样续用（OEM 段零动作）」。四条纪律：ABI 中立（Mainline「不引入新 API」同款）/功能轴 `platform_revision` 不动（`platform_compat` 检查域不受扰）/安全轴独立单调（**`security_level`**——#82 :214 预留位恰是 BCTS 侧承接件，启用触发点同为「首个安全公告」）/BCTS Tier 1 子集回放。案三（槽级独立）判否：多通道多时刻 = 09 号案乙中间态死因的放大。反论四条如实列出（§2.4）。
- **编队清单粒度字段**：更新包平台段新增 **`[security_fastlane]` 节**（§2.5，八键：lane_revision/platform_revision_unchanged/artifacts/abi_neutral/cve_refs/oem_segment/replay_tier/scope）；防降级计数改绑安全轴。

## §1 题一：开发者运行时能力查询面（18 号空白② / G2）

### 1.1 空白重述与现状盘点（仓库事实）

18 号 §2.6 判定：Q7 的 `feature_level` 是**组装期**产品清单键（08 号 :271，消费方 = 组装器，用于预装最小集对账），不是运行时查询接口；第三方开发者运行时感知设备差异全系列零研究。本轮盘点现状四件：

1. **版本面只有编译期常量**：`BERRY_PLATFORM_LEVEL: u32 = 1` 由 abi.toml 单源生成（`user/berry-sys/src/abi_gen.rs` :18，内核侧同源），唯一消费点 = svcmgr 装载期与 `.bap [compat] min_level` 比较（`user/bins/svcmgr/src/main.rs` :5524–:5528；词表定义 `user/berry-manifest/src/lib.rs` :343）——**装载期门槛检查，不是查询 API**。
2. **特性探针是设计位**：`berry_feature_query`（「入口存在性检查」「不给读系统版本号推荐路径」）只见于 SDK-2 §三 :42–:44 与验收线 :79（「gfx 后端能力位 host 测」），零实现零细化（全仓 grep 仅文档命中）。
3. **无 hwinfo/sysinfo 型服务**：`user/bins/` 常驻件 = svcmgr/fsmgr/berry-launcher 一族（实测目录），描述性设备信息查询无宿主。
4. **开发者现状 = 试错**：只能靠装载期词表拒载碰壁（appd loud 拒，01 号 :128；18 号 :97 转引）。

即：**「这台设备是什么、有没有某能力」对第三方是黑盒**——恰是 07 号研究 SDK categories 时该追问而未追问的接口面（18 号 §2.6 推断）。

**提炼四条共性（后面设计的对照尺）**：

1. **静态描述与能力探测是两件事**：Fuchsia hwinfo vs 能力路由；Android `Build` vs `hasSystemFeature`；OH deviceInfo vs SysCap——没有一家把「我是谁」与「我有没有」混在一个接口里。
2. **特性事实源必须是不易变媒体**：系统属性（Android）/产品配置（Fuchsia）/参数区（OH startup）——不是活服务的自述；活服务自述可被运行态污染。
3. **声明与事实分离、对账在分发/认证面**：Android 的 `<uses-feature>`（声明、informational only）× 设备特性（事实）对账发生在 Play；装置自身不执法。
4. **版本号永远在场但被官方劝阻解析**（FINGERPRINT「Do not attempt to parse」）——与 SDK-2 §三 :43「不给读系统版本号推荐路径」完全同构（Web 课）。

### 1.3 提案：查询面双件制

**件一（描述轨）：`sys/info` 静态件。** 组装器（V13 管线新一步，建议步⑧）从产品清单 + 板表 + 上游工件锚生成一个定长/有界 TLV 静态文件，住系统树（`sys/…/`），随槽整树验签（09 号 §5.1 度量链语义）；消费 = 文件读——berry-libc/berry-sys 提供只读解析 API。**零新 IPC、零新常驻服务、零启动序依赖、零 syscall 增量**（nr_ceiling=45 预算纪律，07 号 §5.1）。

- 为什么不是 Fuchsia 式常驻协议服务（推断，三条）：①**事实不变性**——清单事实（feature_level/board/vendor/arch/build_type/语言区域）在运行期零变化，「连一个服务问一份永不变的数据」是纯浪费；②**失败隔离**——无服务即无挂点（规则/05-服务监督的常驻面只增不减的纪律反向适用）；③**度量即防篡改**——静态件在树内，树签名覆盖它，OEM 无法运行时单改（对照 Android 只读系统属性）。
- 为什么不挂 svcmgr：svcmgr 是启动关键监督件（规则/05），且编排面正由并行 lane 数据化（`[slot]` 节，08 号 §4）——把只读数据面耦合进监督控制面违反一事实一归属。
- 动态信息（serial、运行态）v1 不进；若 v2 真机需要，届时立 sysinfo 服务**外挂扩展件**，`sys/info` 静态 schema 不动（add-only 纪律同清单 schema=1）。

**件二（探测轨）：`berry_feature_query` = 能力式试连。** 特性存在性 = 服务/协议入口在应用命名空间**可连**（`/svc` 路径族——V14 X1 已预留「槽位 id ↔ `/svc` 路径映射规则一行」，#82 :253）；探针 = 受控 connect 尝试 + 入口存在性检查（SDK-2 §三原文语义），返回布尔，**不返回版本号**。这在「能力即权限」哲学下是把 Fuchsia「能力路由即特性判定」翻译到 BerryOS 通道语义：**探测即事实**——OEM 结构性无法谎报「有」（连不上就是没有），谎报面收敛到描述轨（见 §1.6）。

- 探针词表 = **平台特性闭集、add-only**，单源于 abi.toml/清单 schema 生成器（SDK-2 §四「无手写副本」纪律）；探针名 ⊆ 服务词表 ∪ 协议词表，**永不独立发明第三套名**。OEM 不得私造特性名（V11 已裁：OEM 专属能力键 v2 前不开，`oem:` 前缀不进词表执法——#82 :250；对照 04 号 :217 基线 4「词表不裁剪不私扩」）。
- v0 唯一在册探针族 = gfx 三档后端能力位（SDK-2 §三 :44、验收线 :79、ADR #51）。

### 1.5 与 G0–G3 能力词表的关系：三层模型

G0–G3（应用规范 §2.1 :71–:76）是**授权档位**（通用/敏感/受限/特权——「你能不能用」），不是设备描述。查询面与之构成三层，各答一问：

| 层 | 问题 | 载体 | 词表 | 执法时机 |
|---|---|---|---|---|
| 0 描述 | 我是什么设备/什么版本 | `sys/info`（静态件） | 清单 schema 键 | 组装期生成 + 树验签 |
| 1 能力集 | 这设备有没有这类 API | `requires_caps`（SDK-2 §三 :38–:41） | core/full 两集（add-only） | 安装期 mkapp/appd 子集校验 → `ERR_CAP_SET` |
| 2 特性探针 | 此刻有没有 X | `berry_feature_query`（试连） | 特性闭集（add-only，源同 1） | 运行期即时 |
| 3 权限 | 我能不能用 X | G0 自动授/G1 弹窗/G2 签名/G3 白名单 | 服务名+档位词表（应用规范 §2.1） | 安装期+运行期（v2 弹窗） |

纪律：**三层词表单源生成**（abi.toml/清单 schema 生成器，SDK-2 §四），层间只有粒度差不发明新名；探针过不了 ≠ 权限被拒——探测答「有没有」、授权答「准不准」，二者正交（G1 弹窗永不因探针结果短路）。

### 1.6 防 OEM 谎报的三执法位

- **谎报「有」（声称有实无）**：能力式探测下结构性不可谎报——试连失败即无；描述轨的版本/档位是事实进度量树，运行时单改不可能（树验签）。对照 Android：改系统属性即改事实，但应用实测即穿帮——BerryOS 把「实测」做进机制本体。
- **谎报「无」（偷偷砍件/降档）**：①**组装期**——组装器对账 `feature_level` ↔ 预装最小集（08 号 :271 既立）；②**认证期（BCTS，本文补全 18 号 §4.3-2 要求的断言行）**——回放 Tier 1 时读 `sys/info`：断言 A「声明档位 ∈ 在册词表且与能力基线（04 号 §4.3 十条）一致」、断言 B「探针最小集全绿（gfx 能力位与镜像内容一致）」；③**运行期兜底**——装载期词表拒载（`requires_caps` 不含即 `ERR_CAP_SET`），「装不上」即暴露。
- **版本谎报**：`sys/info` 在树内被整树验签 + 镜像 index `platform_revision` 列（V9）为第二源——两源对账，OEM 无单点可改。

### 1.7 运行时可见性矩阵（18 号 §4.3-①④ 承接）

| 信息 | `sys/info` | 探针 | 裁决与理由 |

## §2 题二：安全补丁粒度 × 编队原子性（18 号空白③ / G3）

### 2.1 问题重述：案甲的响应时钟没人算过

在册基线：编队案甲 = 平台工件 + OEM 三包**一次 L1 槽翻转**（09 号 :328 表/:334 结论；#82 :283 Q12 落册「编队案甲一句」+ D2 执行点在编队检查）；案乙（分刀：平台先、OEM 后）因「中间态 = Android 版本碎片的结构性来源」被否。**从未被问的题**：高危 CVE 要求周级响应时，唯一原子通道是整版编队——机制上成立吗？

算术（推断，锚点在册）：案甲下每次平台安全补丁 = 平台出新件 → OEM 三包随队（09 号 :332「OEM 必须随平台版本一起发」）→ 编队 → BCTS 回放 → 翻转。OEM 机型/跟版周期 6–12 个月（04 号 :329；07 号 :293 窗口数学 N × 发版周期 ≥ 迁移周期）——**响应地板 = OEM 组织成本，周级结构性不可达**。反面证据：安卓「安全补丁回传贵、上游延迟最长 18 个月」（02 号 :25/:110）、Tizen 40+ 零日 = 单一 OEM 维护工程化薄弱实证（05 号 :101）。若把「关键安全件绕过 OEM 版本链」视为生态生死（Mainline 的立项动机，02 号 §3.5），案甲原样不动就是一个没算过账的缺口。

### 2.2 行业对照（三体系，一手/两源）

| 体系 | 主通道（原子边界） | 安全时效怎么拆 | 拆轨纪律 | 一手源 |
|---|---|---|---|---|
| Android Mainline | 系统镜像 OTA（A/B 整版，Android 同源 update_engine） | 选定组件转 APEX/APK 模块，Google 签名经 Play 分发（Play System Updates），**模块间原子安装/回滚**，绕过 OEM 版本链 | 「**不引入新 API**、只用 CTS 保证的 SDK/System API + 稳定 AIDL 接口」；覆盖有年限（≤11 的 Mainline 支持 2025Q4 结束） | 02 号 :186–:188（两源：本稿再验 [modular-system](https://source.android.com/docs/core/ota/modular-system?hl=en) 页在册） |
| ChromeOS | **整镜像 A/B**：kernel/root 各双份，payload = manifest 操作序列 + 数据段，写备槽 → 重 hash 对拍 → postinstall 重建 dm-verity + 顺带装固件 → 高优先级重启；「applies correctly but fails to boot → rollback to the old partition」 | 组件面 = **DLC**：stateful 分区按需下载安装，rootfs 只装可验证元数据；每 DLC **自带 A/B 预留块**（4KiB 块计，建议 130% 余量）；「updated atomically with ChromeOS **only if installed**」；scaled DLC「will not update with the OS at the moment」=独立节奏雏形 | DLC 安装缺策略检查被官方列为安全风险，劝「勿依赖 DLC 存在性写代码路径」；固件随 OS 更新走 postinstall（= BerryOS L3 固件随包同构，更新与OTA §5） | [update_engine README](https://chromium.googlesource.com/chromiumos/platform2/+/main/update_engine/README.md)、[DLC 开发指南](https://chromium.googlesource.com/chromiumos/platform2/+/main/dlcservice/docs/developer.md)（均全文直抓） |
| Windows | 功能更新年度（Feature update） | **质量更新月度累积**：「one cumulative monthly update that **supersedes the previous month's** update, containing both security and nonsecurity payloads」——不可挑选，防「装了安全件漏了非安全件」的组合态；LTSC 只收质量更新 | 双轨正交：安全轴快、功能轴慢，各自节奏各自回滚 | [Windows as a service](https://learn.microsoft.com/en-us/windows/deployment/update/waas-overview)（全文直抓） |

**提炼三条**（对照尺）：①成熟体系全部把「安全时效」从功能列车上拆下来（模块化/双轨/组件化）；②但**没有一家用中间态换速度**——拆轨件各有自己的原子边界（模块原子安装/月度累积全量替换/DLC 自带 A/B）；③拆轨件变更面自律（Mainline 不加 API、Windows 质量更新不带功能、DLC 劝退存在性依赖）。

### 2.3 粒度三案对照

命名说明：**案一 = 09 号案甲原样**；**案三 = 09 号案乙（分刀）的槽级化放大**；**案二 = 本文新案（安全快道）**——保持案甲「一次 L1 翻转」的原子边界不变，只细化编队**内容**粒度。任务书所称「案乙（security_fastlane）」即本文案二。

| 维度 | 案一：整编队保守 | 案二：平台安全件先行（快道） | 案三：槽级独立 |
|---|---|---|---|
| 原子性 | 单次 L1 翻转 | **单次 L1 翻转（不变）**——备槽仍是完整系统树 | 多通道多时刻（安全件走 L2/L3 式独立换树） |
| 中间态 | 无 | 无（OEM 件原样在树） | **有**——案乙死因（09 号 :329「组合未经联测即上设备」）的放大 |
| CVE 周级可达 | 否（地板 = OEM 组织成本 + 全量回放） | **是**（平台单方出件 + Tier 1 子集回放） | 是 |
| OEM 义务 | 每次安全补丁都要求随队 | 安全件零动作（功能跟版义务不变，D2 只挂功能轴） | 各件各自响应 |
| 回滚 | 整树回退（09 号 §5.3-1） | 整树回退（快道槽也是完整树，OEM 件随树保全） | 组合态回滚语义复杂（09 号 §5.3-3 张力放大） |
| 账本影响 | 单轴 | fastlane 不刷 OEM `last_revision`（其工件未变）；安全轴一列（`security_level`） | 每件版本列爆炸；D2 判据被噪声淹没 |
| 验签面 | 双段清单统一验（V7，#82 :246） | 同——平台段更新，OEM 段 = 当前活跃槽原段引用 + 原 `platform_compat` 声明续验（chain partition 式双签天然支持，09 号 :330） | 交叉兼容无统一执法点（案乙同病，09 号 :330） |

### 2.4 裁定建议：采案二（倾向 + 反论）

**理由四条**：①周级可达——唯一为 CVE 时钟设计的案，且不牺牲原子性（拆的是内容粒度不是翻转次数——正是 §2.2 共性②的翻译）；②跟版义务不稀释——D2 判据与 N 窗口照旧挂**功能轴**（`platform_revision`），OEM 功能跟版不被安全轴绑架也不被安全轴豁免；③防降级与回滚次序全部复用在册冻结件（SUCCESSFUL 先于 rollback index，更新与OTA §2.1-2；回退自由→防降级次序契约）；④**#82 :214 已预留的 `security_level` 字段位（「正交于功能版本的安全补丁轨道雏形，启用随首个安全公告裁」）恰是案二的 BCTS 侧承接件**——OTA 侧快道与 BCTS 侧字段位应在同一触发点（首个安全公告）同笔启用，一次裁决两轴。

**反论四条（如实）**：①「快道也可能引入行为变化」——无 Google 式全网灰度数据兜底；对策 = 变更面白名单 + BCTS Tier 1 回放作替代质量闸，违中立纪律即强制走整编队（纪律见 §2.5 `abi_neutral` 键）。②「双轴版本语义复杂」——代价真实，但 Windows 双轨与 Android「targetSdk × 安全补丁级」双轴证明生态可学习；BerryOS 生态为零，day-one 立轴成本最低（SDK-2 §二立法窗口同款论证）。③「OEM 件自身 CVE 不受益」——如实成立：快道只覆盖平台件；OEM 件漏洞责任边界 = OEM（09 号 信任链分工），响应走整编队或 OEM 件独立通道（L2 系统应用/L3 固件，09 号 :334 已保留且收窄）。④「安全补丁 × OEM 替换件交互回归」——替换面有槽位合同四件套含 conformance（Q8），快道编队期对在册替换件跑 Tier 1 ∩ 受影响面子集回放；若合同不含安全相关 op，快道不涉。

**启用门槛与时机**：v1 不实现（OTA 无代码面，更新与OTA §7）；**字段落位 = 闸 C（OTA/签名格式开刀）前**随 V7 双段清单一并（V7 前半本就「提案态·终形随 Q3/#83」）；**真正启用 = 首个安全公告**（#82 :214 既定触发器，不多设门）。

### 2.5 编队清单粒度字段设计（案二采纳时的 `[security_fastlane]` 节）

更新包**平台段**新增节（OEM 段不动），八键：

| 键 | 类型 | 语义与执法 |
|---|---|---|
| `lane_revision` | u16 单调 | 安全轴号 = #82 `security_level` 的 OTA 侧同值；更新服务校验 ≥ 活跃槽值（防降级，替换「整编队下 rollback index 只认镜像代数」的粗粒度） |
| `platform_revision_unchanged` | bool 断言 | 快道不得动功能轴；更新服务对目标槽 `platform_revision` 与活跃槽比对，不等即整包拒装（loud） |
| `artifacts[]` | `name@sha256` 锚 | 平台安全工件白名单清单；**v0 白名单 = 内核镜像 + berry-sys/libc 级库**（构建单源可比对）；L1 服务件暂不入道（反论③·保守起步） |
| `abi_neutral` | bool 断言 | 构建侧工具执法（对照签名清单生成面），违规拒出件——Mainline「不引入新 API」纪律的机器化 |
| `cve_refs[]` | string | 公告锚（审计与账本回溯用，不参与装载判定） |
| `oem_segment` | `"carried"` + 段 hash | OEM 段 = 当前活跃槽原段整段引用；原验签续用（不重签、不需 OEM 在线）——09 号 :330 双段验签语义的直通 |
| `replay_tier` | u8 = 1 | 声明 BCTS 回放子集（Tier 1 先行，Q4 #82 :275）；编队期对在册替换件执行 |
| `scope` | enum | v0 = `"security"` 单值（预留 `"critical"` 分级，是否分级随首个安全公告一并裁） |

配套三线：①**兼容检查**（09 号 §5.2 两档不动 + 一改）：安装期 `platform_compat` 检查**只对功能轴**执行（快道目标槽功能轴不变 → OEM 原声明恒真，检查保留防手误）；启动期 boot 对账加 `lane_revision` 单调列。②**回滚**：整树回退天然保全（09 号 §5.3-1 树即版本）；反回滚计数绑 `lane_revision`（CounterBackend 单调）——功能轴回退不受安全地板反噬（09 号 §5.3-2「解耦」推理的落地形态）。③**账本**：OEM `last_revision`/D2 判据零扰动（其工件未变）；平台镜像 index 增 `security_level` 列（与 V9 `platform_revision` 列同刀）。

## §3 反面自检（本稿自己的弱点，如实写）

1. **静态件方案的演化僵硬**：`sys/info` 键位变更 = 清单 schema 同步升版（周级返工，18 号 §4.2 边界条件同款）——add-only 纪律是对冲不是豁免；v2 动态信息（serial/传感器在场性）到来时若把动态键塞进静态件，会把「组装期定值」的防篡改卖点稀释成杂货铺（推断：裁决纪律 = 只放进组装期定值，动态位一律走新扩展件）。
2. **探针 = 试连的 v1 现实缺口**：服务命名空间对应用可见性规则未立（§1.8-4 依赖边）——查询面若先于命名空间面落 #83，「试连」语义悬空；本文按「同刀」建议，但主会话排刀时可能被并lane 冲突挤压（svcmgr/命名空间正在并行 lane 手里）。
3. **快道 `abi_neutral` 断言的可判定性**：Rust 无稳定 ABI（07 号 §4 命题）——「中立」对内核镜像/库级工件可由构建单源比对机判，对未来入道件不可通用判定；白名单收窄是当前唯一诚实解，代价 = L1 服务件 CVE 仍走整编队（慢轴），两轴覆盖不齐是已知残余。
4. **单轮无对抗**：本稿是补研建议稿，两题均未经红蓝队（11/12 号式流程）；尤其案二四条反论的对策强度（Tier 1 回放能否替代灰度数据）无实证——首个安全公告前应有一次桌面推演。
5. **外部源单源项如实登记**：Android 两页为官方站点 2012/2014 存档快照（字段描述自 API level 1–8 起未变——推断），现版页面正文未抓到（动态导航截断）；Mainline 事实经 02 号转引 + 本轮页面在册性复核（正文同因截断未重取）；OH deviceInfo 取自 master（版本跟随开发主线，v5.x 发行版或有差异）。
