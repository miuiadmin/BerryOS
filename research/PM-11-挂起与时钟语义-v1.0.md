## §0 一页结论（土话直答）

1. **「挂起期间时钟走不走」业界分三派，且 POSIX 同名反义**：Linux `CLOCK_MONOTONIC` 挂起**停**、
   Darwin 的 `CLOCK_MONOTONIC` 挂起**走**——同一个名字、相反语义，是跨平台应用第一大坑。
   四家全给「双钟」：停的管程序时间观、走的管真实经过时长（Linux MONO/BOOTTIME、macOS
   UPTIME_RAW/MONOTONIC、Windows unbiased/biased、Android uptime/elapsedRealtime）。
2. **Fuchsia 把「停钟」写进内核四原语**，理由是程序正确性（RFC-0230 原文：「the time the system is
   suspended does not affect the correctness of the programs」）——BerryOS 应照抄此裁决，同时必须
   配一条**连续钟**做挂起记账，否则维护窗判定在挂起期根本不推进。
3. **维护窗口径有官方源码数字**：深闲 idle 间隔 60min→2h→4h→封顶 6h（×2 倍增），浅闲 5min→10min→
   封顶 15min；窗预算浅 1–5min、深 ≥30s。Android 三处文档配额口径打架（9 分钟/7 次每小时/约 1 分钟），
   源码真值 = 非 idle 5s、idle 9min——**配额数值必须单一权威源**，BerryOS 用协议位+遥测一份。
4. **醒来补发语义必须 day-one 定义**：Windows 相对定时器在 Win8 翻转过一次语义（睡眠中倒数→睡眠中
   暂停），文档至今两段并存；Linux 给五组 clockid 才补齐。BerryOS 三档定时器（batched/window/precise）
   × 挂起的语义矩阵本报告 §4.2 给全，随 berry-sys ABI 一次定形（PM-00 §5.2 P5）。

## §1 主线：挂起期时间观的三种世界观

**核心问题**：CPU 停了、钟停不停？三派答案，派生三种系统形状：

| 派别 | 代表 | 主单调钟挂起期 | 配套第二钟 | 定时器跨挂起语义 |
|---|---|---|---|---|
| 暂停派 | Fuchsia、Linux(MONO)、Android(uptime) | 停 | BOOTTIME/elapsedRealtime（含睡眠） | 相对定时器醒来「没怎么走」，错过的到窗补发 |
| 续走派 | Darwin(MONOTONIC)、Windows(QPC) | 走 | UPTIME_RAW/unbiased（不含睡眠） | 相对定时器醒来常「已过期」，须定义补发/整形 |
| 双轨明示派 | Linux 全家桶 + ALARM 后缀 | 停(MONO) | BOOTTIME + `*_ALARM`(可唤醒, 需 CAP_WAKE_ALARM) | 唤醒与否成为 clockid 的一部分 |

**机制全景一句话**：每家都是「程序时间观（停）× 真实经过时长（走）」双轴 + 「唤醒位」第三轴；
差别只在哪根轴是默认、第三轴藏不藏在 API 名字里。

## §2 关键事实与证据

### 2.1 挂起期时钟语义四家对照【确定度：高（全部一手原文）】

| 系统 | 时钟 | 挂起期 | 原文/出处 |
|---|---|---|---|
| Linux | `CLOCK_MONOTONIC` | **停** | man page："This clock does not count time that the system is suspended."（https://man7.org/linux/man-pages/man2/clock_gettime.2.html） |
| Linux | `CLOCK_BOOTTIME`（2.6.39+） | **走** | "identical to CLOCK_MONOTONIC, except that it also includes any time that the system is suspended."（同上） |
| Linux | `CLOCK_MONOTONIC_RAW` | 停 | 同 man 页；RAW 免 NTP 频率调整，仍不含挂起 |
| Fuchsia | monotonic | **停（内核原语）** | RFC-0230：内核四原语之一 "Ensure the monotonic time is paused when the system enters Suspend-to-Idle. The time should not advance when the system is in suspended mode."（https://fuchsia.dev/fuchsia-src/contribute/governance/rfcs/0230_suspend_to_idle，2023-10-24 accepted） |
| Windows | QPC | **走** | "returns the total number of ticks … including the time when the machine was in a sleep state such as standby, hibernate, or connected standby."（https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps） |
| Windows | interrupt time 双 API | 走/停双轨 | `QueryInterruptTime` 含睡眠；`QueryUnbiasedInterruptTime`："The unbiased interrupt-time count does not include time the system spends in sleep or hibernation."（https://learn.microsoft.com/en-us/windows/win32/api/realtimeapiset/nf-realtimeapiset-queryunbiasedinterrupttime） |
| macOS | `CLOCK_MONOTONIC` | **走** | Darwin man page："will continue to increment while the system is asleep."（https://keith.github.io/xcode-man-pages/clock_gettime.3.html，Darwin man 镜像） |
| macOS | `CLOCK_UPTIME_RAW` / `mach_absolute_time` | **停** | 同 man 页："does not increment while the system is asleep … identical to the result of mach_absolute_time()" |
| macOS | `mach_continuous_time`（10.12/iOS10+） | 走 | XNU 源码醒来时刻 `total_sleep_time = mach_continuous_time() - mach_absolute_time()`（https://github.com/apple-oss-distributions/xnu/blob/xnu-11215.1.10/osfmk/kern/clock.c 约 :1195；引入版本见 [macports-legacy-support time.c](https://github.com/macports/macports-legacy-support/blob/master/src/time.c)，确定度：中） |

- **同名反义石锤**：POSIX `CLOCK_MONOTONIC` 在 Linux 停、Darwin 走。Rust `std::time::Instant` 走
  `CLOCK_MONOTONIC`，同一段代码两平台挂起行为不同——跨平台应用最大的时间坑（推断自上表两 man 页，确定度：高）。
- **Fuchsia 停钟的动机原文**："This will ensure that the time the system is suspended does not affect the
  correctness of the programs. It is critical to have a consistent behavior…"（RFC-0230，同上）。
  与 PM-03 §5.4 引述一致（`research/PM-03-Linux电源机制与微内核归属-v1.0.md:179`）。

### 2.2 定时器/闹钟跨挂起：唤醒位与补发语义

| 机制 | 行为 | 出处【确定度：高】 |
|---|---|---|
| Linux timerfd `CLOCK_BOOTTIME`（3.15+） | 挂起期继续计数，到期在唤醒后即刻可见 | man："does include the time during which the system is suspended"（https://man7.org/linux/man-pages/man2/timerfd_create.2.html） |
| Linux `CLOCK_REALTIME_ALARM`/`CLOCK_BOOTTIME_ALARM`（3.11+） | "will wake the system if it is suspended"，需 **CAP_WAKE_ALARM**——唤醒是能力不是权利 | 同 man 页；能力即权限的现成先例 |
| Linux alarmtimer 框架 | "similar to hrtimers, but triggers a RTC alarm if the box is suspend"，自认受 Android RTC alarm 影响（John Stultz, 2010） | https://github.com/torvalds/linux/blob/master/kernel/time/alarmtimer.c 文件头注释 |
| timerfd `TFD_TIMER_CANCEL_ON_SET` | 墙钟跳变时绝对定时器转 ECANCELED 取消——「墙钟不可靠」的显式出口 | 同 timerfd man 页 |
| Windows `SetWaitableTimer(fResume=TRUE)` | "restores a system in suspended power conservation mode when the timer state is set to signaled"——唤醒位是参数 | https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-setwaitabletimer |
| Windows 相对 waitable timer | **Win8 语义翻转**：XP–Win7「timer includes time spent in low-power states… continues counting down while the computer is asleep」→ Win8+「does not include / does not continue counting down」 | 同上页与 [SetWaitableTimerEx](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-setwaitabletimerex)，文档两段并存 |
| Windows 补发 | "The system uses biased interrupt time … ensuring that relative timers that would have expired during sleep expire immediately upon waking." | QueryUnbiasedInterruptTime Remarks（2.1 节 URL） |
| Android 四类闹钟 | `ELAPSED_REALTIME(_WAKEUP)` 挂起期照走（boottime 口径）、`RTC(_WAKEUP)` 墙钟口径；"Registered alarms are retained while the device is asleep … cleared if it is turned off and rebooted" | https://developer.android.com/reference/android/app/AlarmManager |
| Android handler/sleep | `Thread.sleep`/`Handler`/`System.nanoTime` 全部基于 uptimeMillis，「if the device enters sleep, the remainder of the time will be postponed until the device wakes up」——醒来**顺延补完**而非立即到期 | https://developer.android.com/reference/android/os/SystemClock |

**app 的「时间流逝 vs 真实墙钟」偏差契约（Android 版，成文最全）**：
- uptimeMillis（停）= 程序时间观；elapsedRealtime（走）= 记账口径（"including time spent in sleep"）。
  Android 官方点名：间隔测量跨睡眠必须用 elapsedRealtime，uptime 只适合「不跨睡眠的间隔」（SystemClock 页，同上）。
- 偏差上不封顶：Doze 把 `setExact`/`setWindow` 一律**推迟到下一维护窗**（官方 Doze 文档：
  "Defers standard AlarmManager alarms, including setExact and setWindow, to the next maintenance window"，
  https://developer.android.com/training/monitoring-device-state/doze-standby）——app 申请的时刻与实际放行
  时刻之差随闲置时长增长，无补偿承诺；例外三口：`setAndAllowWhileIdle`（限频）、`setExactAndAllowWhileIdle`、
  `setAlarmClock`（准点放行，且系统「may also do some prep-work … to avoid … swamping the network」——
  提前做预备工作防早高峰惊群；【勘误 2026-11-07：本条原引旧版页文 "The system exits Doze shortly before those alarms
  fire"，现行 AlarmManager 页已无此句，改引现行措辞，实质（prep-work/防惊群）不变】，AlarmManager reference，同上）。
- `setExactAndAllowWhileIdle` 触发时给 app 约 **10 秒**临时电源豁免窗（同 reference 页；AOSP
  `ALLOW_WHILE_IDLE_WHITELIST_DURATION = 10*1000`，§2.3 源码同源）。

## §3 教训与坑

1. **POSIX 同名反义**：`CLOCK_MONOTONIC` Linux 停/Darwin 走（§2.1）。POSIX 只保证单调不保证挂起口径——
   自有 ABI 的 BerryOS 千万别复用这个名字承担二义语义。
2. **语义中途翻转的代价**：Windows 相对定时器 Win8 翻转（睡眠中倒数→暂停），官方文档至今两段并存
   （§2.2）——API 语义发布即冻结，改语义等于新 API。Linux 用五组 clockid（MONO/BOOTTIME/REALTIME/两个
   _ALARM）才拼全语义空间，复杂度自食。
3. **配额数值三处打架**（§2.3）：官方文档、培训文档、限制表各说各话，源码才是真值。治理面数值必须
   单一权威源 + 可遥测核验，写文档不写数字（Android 官方 Doze 页通篇无数字）是数字漂移的温床。
4. **只停钟不配连续钟 = 治理失明**：维护窗节奏、idle 世代时长、能耗归因全要「真实经过时间」；
   Fuchsia 停钟的同时内核仍导出 CPU 指标（四原语之四，RFC-0230）——连续钟/指标是停钟的对价。
5. **唤醒惊群要提前做功课**：Android `setAlarmClock` 到点前系统提前出 Doze 预热、还防「早高峰全体设备
   同时醒来涌网络」（§2.2 reference 原文）；维护窗放行同样要抖动（jitter），否则闹钟对齐=定时风暴。
6. **补发语义三态必须显式**：Linux timerfd 到期即读得出（走钟）、Windows「睡眠中该到期的醒来立刻到期」
   （biased 补发）、Android handler「醒来后把剩余时间睡完」（顺延不提前）——三种都合法，没定义就是坑。
7. **唤醒位是权限不是参数细节**：Linux `CAP_WAKE_ALARM` 把「吵醒整机」收成能力（§2.2）——与 BerryOS
   「能力即权限」直接同构；Android 的逃逸口（9min 配额+10s 豁免窗）证明收权必须配出路（PM-01 规律 R6，
   `research/PM-01-安卓省电演化史与历史包袱-v1.0.md:163`）。

## §4 BerryOS 启示（可执行落点）

### 4.1 裁决建议 A：主单调钟暂停 + 显式连续钟（与挂起四原语同刀）

| 方案 | 优点 | 代价 | 裁决 |
|---|---|---|---|
| 主钟暂停（Fuchsia 派） | 程序时间观连续：超时/动画/重试在挂起前后无跳变；RFC 原文背书「correctness of the programs」 | 需第二钟做记账；app 测 elapsed 缺睡眠段 | **采纳为主** |
| 主钟续走（Darwin/QPC 派） | app 心智简单（墙外时间也流逝） | 醒来瞬时「全体过期」→定时风暴须整形；sleep 型等待全错位 | 不采 |
| 双钟全暴露（Linux 派） | 语义完备 | 五组 clockid+文档打架；app 选错钟没人救 | 命名收敛，不学其发散 |

- **内核面**：暂停单调钟=挂起四原语之一（PM-03 §8.2 已预留，`research/PM-03-Linux电源机制与微内核归属-v1.0.md:231`）；
  同刀加「连续钟」内核计数器（mono_ns + slept_ns，唤醒路径累加）。策略一个不进内核。
- **SDK 面**：`clock_now(MONO | SLEPT)` 两域，**不复用 `CLOCK_MONOTONIC` 名**（POSIX 二义雷，§3-1）；
  POSIX 兼容层映射表里显式声明 BerryOS 语义（`CLOCK_MONOTONIC→MONO` 停钟、`CLOCK_BOOTTIME→SLEPT`）。
- **定时器面**：timer 创建带 `{clock 域, wake 位}`；wake 位=能力（等价 `CAP_WAKE_ALARM`），manifest 声明
  （B8 能力类别，PM-01:182）、默认零配额。

### 4.2 裁决建议 B：三档定时器 × 挂起语义矩阵（进 berry-sys ABI 冻结评审，PM-00 §5.2 P5）

三档定义承接 PM-01 B3（`research/PM-01-安卓省电演化史与历史包袱-v1.0.md:177`）与 PM-00 P5（:241）：

| 档 | 挂起期怎么算 | 醒来怎么补 | slack（per-thread，PM-06:199） | 唤醒系统 |
|---|---|---|---|---|
| **batched**（默认） | 挂起不唤醒；到期时刻以 SLEPT 域记账 | 错过的并入**下一维护窗**批量放行（对齐放行+抖动） | 宽松，可到 100ms–分钟级 | 否（无 wake 能力） |
| **window** `{earliest, deadline}` | 窗随 SLEPT 域流逝；deadline 未到不唤醒 | 醒来时已过 deadline→立即放行一次；仍在窗内→窗内自选点放行 | 窗宽即 slack 显式化 | 否（可选 wake 能位升级） |
| **precise**（能力+配额） | 分两型：**wake 型**挂起前编程到 always-on 域（RTC/alarmtimer 同位），准点唤醒；**run 型**挂起即静默 | wake 型准点；run 型错过→醒来补发一次并遥测计费 | 0（但配额：per app 每 idle 世代 N 次，初值照 9min 语义） | wake 型是；run 型否 |

- 补发三态显式化（§3-6）：batched=并窗、window=看 deadline、precise=补一次+计费；周期型定时器（若有）
  遵守 pm-notes 绝对截止纪律不外推（`research/pm-notes/00-BerryOS省电现状与缺口盘点.md:29`）。
- 邻闹钟护栏照抄：维护窗/深闲准入前查未来 60 min precise 闹钟（§2.4 表末行）。

### 4.3 裁决建议 C：per-thread slack 与挂起的交互（三句话）

1. slack 只在**运行态**生效；挂起期定时器域整体停摆，slack 无意义也不耗电——两者天然正交。
2. 醒来放行用 slack 做**风暴整形**：同一唤醒世代内到期的 batched 定时器合并成一个放行批
   （等价 Android 维护窗"runs all pending … alarms"一次放行，§2.2 Doze 原文），批内共享一次尾能（PM-05:72）。
3. slack 档位表照 PM-00 P5：`latency_critical=0 / interactive≈50µs / maintenance 100ms 级`
   （`research/PM-00-全系统省电架构综合裁决-v1.1.md:241`）；berry-libc 永无全局精度入口（PM-06:151）。

### 4.4 验证断言（ktest/smoke 可落）

1. 停钟断言：模拟挂起（停钟原语）前后 `clock_now(MONO)` 差=0、`clock_now(SLEPT)` 差=suspend_ns。
2. 补发断言：挂起跨 batched 到期→醒来不立即 fire，等到首维护窗；跨 window deadline→醒来即放行一次；
   precise(wake)→准点唤醒且记账一次配额。
3. 配额断言：per app 每 idle 世代 precise 次数超配额→自动降级 batched（不是拒绝，照 Android「降级不报错」惯例）。
4. 维护窗断言：sim-modem 上按 §2.4 基线表跑 24h 仿真，断言放行次数曲线=间隔×2 封顶曲线；策略表项全部
   遥测导出（参数可调、对比进 PM-00 开放问题 3 的自定标闭环）。
5. 风暴断言：同一秒内 N 个到期定时器合并为 ≤1 个放行批（唤醒世代记账面=PM-00 刀 1 wakeup 记账的对偶）。
