## 0. 总判断

墓碑模式不是单一机制，是一个按时间尺度与代价分层的**处置梯度**。全部被调研系统收敛到同一形状：能不杀就不杀（冻结驻留），杀了要留轻量状态（KB 级墓碑 + 视觉快照），长期不用连存储一起收（归档），全量检查点是低频重器不进日常路径。**性能最好的主路径 = 冻结 + 压缩换出**（恢复≈解冻或缺页，CPU 零消耗，内存约半价）；**最先进的形态不在 Android，在 Fuchsia**——墓碑不是特例机制，而是「VMO + 用户态 pager + 组件持久存储」的自然推论：杀进程零序列化成本，恢复成本按页惰性支付，这与 BerryOS 架构完全同构。[D1][D2]

## ① 执行摘要

1. **谱系四层**（时间尺度 × 状态归宿）：秒级 freeze-in-place（进程驻 RAM 不跑 CPU）→ 压力级 save-state-then-kill（杀进程留 KB 级状态 + 快照）→ 月级包归档（连 APK/权限/编译产物一起收）→ 显式全量 checkpoint（秒~分钟级，不进日常）。[A1][A4][C1][D3]
2. **Android 现行答案 = 四件套横跨四层**：freezer（A11 引入、A14 定形：进 cached 态 10s 冻结、cgroup v2、冻前排 GC、冻时脏页写回 + 匿名页进 ZRAM、全冻断 TCP keepalive）+ lmkd（PSI 驱动杀进程，内核 LMK 已于 4.12 删除）+ SavedState/SavedStateHandle（进程死后 KB 级恢复态）+ TaskSnapshot（双分辨率零拷贝快照横跨冻结与被杀两态）；A12 hibernation / A15 archiving 管月级。**官方硬数字：多驻留 cached 进程使冷启动最高降 30%**。[A1][A2][A3][A4][A5][A7][A8]
3. **Chromium 两级**：bfcache = freeze-in-place（整页含 JS 堆原地冻结、恢复零网络零重解析，Chrome 96+ 全平台）管热路径；Memory Saver = discard-then-restore 管冷路径【缺：细节 404】；freeze/resume/persisted 是两级共用的开发者事件契约，notRestoredReasons 让「为何没冻成」可审计。[B1][B2]
4. **Fuchsia 无墓碑机制**：组件生命周期到 stop 即进程终止，状态归宿 = 组件自身持久存储（storage capability）；内存压力走内核 5 态水位（示例 50/60/150/300MB）→ 用户态三级信号 → 回收梯子（blobfs 用户态 pager LRU 回收 → 零页去重 → 页表回收 → discardable VMO）→ 兜底 OOM 干净重启。**杀进程 = 零序列化成本的「墓碑」，恢复 = pager 按页惰性重取**。[D1][D2]
5. **OpenHarmony = Linux 内核 + 用户态优先级引擎**：memmgr 事件驱动维护回收优先级列表（-1000 系统/-800 常驻/0 前台/100 后台短时/200 可感知/260 分布式/400 普通后台），查杀由 PSI 触发按水线选列（500MB→P400 … 100MB→P0）；回收侧 availBuffer 800/750/850 三水线 + zram 压缩比 60–70% + 分级换出到 ESwap + **闪存寿命预算（日换出 50MB / 总量 199MB）**——把「换出多少」当成闪存资产管理是独有先进点。[E1]
6. **CRIU = 全量 checkpoint 的数量级真相**：dump 耗时与镜像体积 ∝ 进程内存（22.35GiB 原始 → dump ≈54s，LZ4 后 12.17GiB 省 45.5%）；restore 4B 模型 2.6s / 27B 23.3s / 容器整恢复 22.7–152.6s；且需特权注入 parasite code、每页落盘、外设逐设备插件——**不适合移动日常路径，适合预热/迁移/取证**。[C1][C2][C3]
7. **Windows Phone 考古（墓碑一词出处）**：WP8 执行模型已两级化——Deactivated 先进 dormant（线程全停、完整驻内存），内存不足才升级 tombstone（进程终止，OS 留导航栈 + State 字典，**同时最多 5 个墓碑**，生命周期事件限时 10s）；UWP 现代形态 = 数秒即 suspend + SuspendingOperation.Deadline + PreviousExecutionState 恢复。**WP 的「真墓碑」是低内存年代的强制手段，后被两级模型与冻结取代**。[D3][D4]
8. **冻结的工程暗面**（Android 亲自踩过，全量记录在官方故障模式节）：同步 IPC 打冻结进程 = 服务进程直接被杀（REASON_FREEZER）；异步事务溢出缓冲 = 杀；scheduleAtFixedRate 解冻后补跑风暴；冻结进程不能 GC、收不到 trim 事件——**冻结不是免费的，IPC 语义要配套改造**。[A1]

## ② 机制谱系全景

| 线 | 代表 | 后台时发生什么 | 状态归宿 | 恢复成本 | 内核依赖 |
|---|---|---|---|---|---|
| freeze-in-place | Android freezer（A11+）、Chromium bfcache、WP dormant、UWP suspend | 进程/页面原地冻结：线程全停、驻 RAM（Chromium 连 JS 堆一起） | 进程自身内存 | 解冻（近零）/ bfcache 内存内复现 | cgroup v2 freezer；Chromium 为渲染器进程级 |
| save-state-then-kill | lmkd + SavedState、WP tombstone、Fuchsia stop、Memory Saver | 杀进程；留 KB 级状态（Bundle/State 字典/URL+滚动）+ 逐出前快照 | 系统（task-bound 状态 + 快照文件） | 冷启动 + 状态重放 | PSI/memcg（Android）；Fuchsia 无需（状态本来就在持久存储） |
| snapshot-restore | TaskSnapshot（A8+） | 感知层横跨两线：退后台截图进 GraphicBuffer | 显存（进程在）/磁盘双分辨率（进程亡） | 首帧前即显示 + crossfade | GraphicBuffer 零拷贝共享 |
| checkpoint-restore | CRIU / Podman / K8s(KEP-2008) | 冻结 → 全量序列化落盘（内存+fd+TCP+信号） | 磁盘镜像（GB 级） | 秒~分钟级 | ptrace/parasite 注入、逐设备插件 |
| 换出不杀（横切） | zram / OH eswap / Fuchsia blobfs pager | 冻结后匿名页压缩驻内存（~2:1）、冷页回写 | 压缩池/盘 | 缺页级 | zram、用户态 pager |

**冻结语义细节**（cgroup v2 freezer 权威口径）：写 1 到 `cgroup.freeze` 冻结整组含子孙；异步完成（「可能耗时」），完成后 `cgroup.events` 的 frozen 置 1 发通知；层级继承；冻结态进程仍可被致命信号杀死；迁入即停/迁出即恢复，fork 竞态已处理；`frozen_usec` 记累计冻结时长。[C4]

**zram 细节**：官方预期压缩比约 2:1（disksize>2×内存无意义）；闲置元数据 ~0.1% disksize；`mem_limit` 防压缩池自膨胀；idle 按访问时长（如 86400s）标冷页 → writeback 落 backing 设备，`writeback_limit` 做写入预算护闪存；最多 4 算法分级重压缩（冷页换更强算法）。[C5]

**开发者契约面**（各系统的通知与限时）：Android 广播排队/解冻投递 + A16 `IBinder.FrozenStateChangeCallback` 公共 API；Chromium `persisted`/`freeze`/`resume` 事件；UWP `SuspendingOperation.Deadline`（GetDeferral 只延迟不减量）+ 终止无通知；WP 生命周期事件硬限 10s；OH 明文「onBackground 时间短，勿做数据库事务等耗时保存」。[A1][B1][D3][D4][E2]

## ③ 性能对照（什么性能好）

- **恢复延迟谱**（好→差）：解冻（Android/Chromium 均无官方 ms 数字，官方口径「essentially instant」[B1]）→ 缺页级惰性重取（Fuchsia pager / CRIU lazy-pages）→ 冷启动 + KB 级状态重放（SavedState，TaskSnapshot 快照先行遮盖）→ 解档重下 APK（A15 archiving）→ CRIU restore（2.6s～152.6s[C2]）。
- **内存代价谱**（省→费）：WP 墓碑（≤5 个 State 字典[D3]）→ 快照双分辨率（low-res 0.5 scale 先行[A3]）→ 冻结 + zram（≈全量 RSS 半价[C5]）→ 冻结裸驻（全量 RSS）→ checkpoint 镜像（GB 级磁盘[C2]）。
- **官方硬数字表**：冷启动 −30%（A14 多驻留 cached[A1]）；PSI 阈 partial 70ms 高性能/200ms 低 RAM、complete 700ms、thrashing 100%/30%、swap_free 20%/10%[A2]；冻结 debounce 10s（源码 `DEFAULT_FREEZER_DEBOUNCE_TIMEOUT=10_000L`[A5]）；TaskSnapshot scale 1.0/0.5、Recents 旧降采样 64%[A3]；bfcache 覆盖桌面 1/10、移动 1/5 的导航[B1]；OH 查杀水线 500/400/300/200/100MB 对应 P400/300/200/100/0，日换出预算 50MB[E1]；zram 2:1、元数据 0.1%[C5]；CRIU 22.35GiB→54s dump、LZ4 省 45.5%[C2]；WP 墓碑配额 5、事件限时 10s[D3]。
- **「什么性能好」的直接回答**：日常路径 freeze + zram——CPU 零消耗（冻结即不调度）、内存约半价（压缩）、恢复近零（解冻或缺页）；杀 + 轻量墓碑是压力后备（省全量 RSS，代价冷启动）；Android 用 30% 冷启动数字证明「多冻结驻留少杀」方向正确；CRIU 级全量快照对移动日常是负资产。【证】+【推】

## ④ 最先进判据（八条，全部有出处）

1. **分层梯度而非单一机制**：Android 四层 / Chromium 两级 / WP 两级——没有系统用单一「墓碑」覆盖全部时间尺度。[A1][A4][B1][D3]
2. **「不动最好」哲学**：能冻结不杀（30% 数字）、能换页不冻结（OH/Fuchsia 回收梯子在查杀之前）、能 discardable 不换页（Fuchsia lock/unlock 交内核择机丢）。[A1][D2][E1]
3. **压力信号 = 体验级指标**：PSI 度量「任务因内存不足被延迟的时间」直接对应卡顿；内核 LMK 死于硬编码 free 阈值；OH 查杀同样 PSI 触发。[A2][E1]
4. **开发者事件契约 + 硬限时**：freeze/resume/persisted、Deadline、10s 上限、onBackground 短时警告——给应用留下「落盘窗口」但不许赖着。[B1][D3][D4][E2]
5. **资格与逐出可审计**：bfcache 的 notRestoredReasons、freezer 的豁免清单（文件锁/BIND_WAIVE_PRIORITY）与故障模式全公开——「为何没冻成/为何被杀」必须可解释。[A1][B1]
6. **感知连续**：TaskSnapshot 双分辨率零拷贝横跨冻结/被杀——无论哪层处置，用户看到的最近任务与启动窗口永远连续。[A3]
7. **生态联动回收**：hibernation 把权限回收、缓存、ODEX/VDEX 编译产物与「数月未用」绑定成一个可逆动作——存储优先而非性能优先的分层。[A4]
8. **微内核终极形态（Fuchsia）**：墓碑 = VMO + 用户态 pager + 组件持久存储的推论——不建墓碑文件、不序列化进程，stop 即杀、恢复靠 pager 按页重取；全链路可测（`k mem avail_state` / `ffx profile memory signal`）。[D1][D2]

## ⑤ BerryOS 映射（【推】，v1 可落地梯度）

1. **冻结 = 调度停投 + 能力域配套**：微内核无 cgroup，冻结即调度器停止投放该进程线程（与 `SCHED-01` 的 token 化 freeze 增量合流）；同批必须解决 Android 踩过的 IPC 暗面——同步 IPC 打冻结进程的致死语义要有显式答案（拒并唤醒 / 自动解冻二选一，倾向自动解冻 + 排队投递，对齐 A14 广播排队）。
2. **换出 = 用户态 pager 压缩页仓**：`内存管理设计` 的可换出 VMO + pager 正是 zram 等价物——冻结后由 pager 收页压缩（借 zram idle 分级 + writeback_limit 闪存预算思想，OH 的日换出配额直接可抄）；discardable VMO（Fuchsia lock/unlock 同款）作第一梯队回收。
3. **墓碑 = pager 的自然推论**（采纳 Fuchsia 形态）：杀进程不序列化——常驻可换出 VMO 的页已在压缩仓/盘上，task-bound KB 级状态（SavedStateHandle 式，onStop 窗口写入）+ 合成器侧快照（TaskSnapshot 式双分辨率零拷贝）补齐恢复体验；**不建 WP 式墓碑文件特例**。
4. **压力信号 = 缺页/换页停顿统计**（PSI 等价）：内核记「等页时间」→ 带内接口发用户态策略（与 AI 原生调度机制预留同构）——intent + 返回概率可决定冻结深度与换出优先级，这是 BerryOS 有机会超越 Android 的点：处置梯度可被策略插拔。
5. **监督服务 = lmkd/memmgr 等价**：用户态常驻服务（`规则/05` 服务监督域）持优先级表（OH 式事件驱动更新）+ PSI 式信号触发，按水线选列杀；杀前快照、杀后留退出原因（ApplicationExitInfo 等价，REASON_FREEZER 式可解释）。
6. **契约面 day-one 定死**（呼应 PM-00「形状决定命运」）：onBackground 短时限 + 显式落盘窗口（Deadline 语义）、冻结/解冻通知回调（A16 FrozenStateChangeCallback 式）、豁免面显式（锁持有者不冻）。
7. **梯度总表**：discardable 收割 → pager 压缩换出（日预算）→ 冻结（10s debounce 量级）→ 杀 + KB 墓碑 + 快照 → 月级归档（权限/缓存联动）。全量 checkpoint（CRIU 式）v1 明确不做——kill criteria：任何「为恢复体验而全量序列化进程内存」的提案直接引用本报告 §③ 数字否决。

## ⑥ 反面清单（别人替我们踩过的坑）

- 内核态 LMK：硬编码 free 阈值、无压力伸缩、伙伴魔改 slowing vmscan——4.12 删净，勿复刻。[A2]
- 单一墓碑配额制（WP ≤5 个 + 10s）：低内存年代产物，恢复体验差到成为 WP 应用质量抱怨主力——分层后无人再走。[D3]
- 同步 IPC × 冻结 = 必死组合（Android 官方故障模式）——设计冻结时 IPC 语义先行。[A1]
- scheduleAtFixedRate 补跑风暴：解冻后积压任务连发——BerryOS 定时器 API 的 fixed-delay 默认值可 day-one 定对（PM-06 同结论）。[A1]
- unload/no-store/IndexedDB 事务取消 bfcache 资格：资格门槛越多，冻结覆盖率越低——资格面要小而可审计。[B1]
- CRIU 进日常路径：秒级延迟 + GB 级盘 + 特权注入 + 密钥入镜像（KEP-2008 自己列的安全顾虑）。[C2][C3]
