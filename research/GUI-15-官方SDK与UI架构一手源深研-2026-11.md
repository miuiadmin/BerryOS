## §1 总判断

1. **SDK 不是“一堆控件 API”，而是七层契约的共同产物**：

   ```text
   app/runtime lifecycle
   window/session authority
   UI tree / state
   layout
   input/focus/text/IME
   semantics/accessibility
   docs/spec/versioning/tooling
   ```

   只做控件不做后四层，会重复“皮毛往上建”的错误。

2. **官方系统都把窗口/组件所有权放在系统服务或宿主中**。Android WindowManager、Fuchsia Scenic/component manager、OpenHarmony WindowStage/UIAbility 的方向一致；Berry 当前把窗口激活、seat focus、键盘路由留在 `gui-wmd` 是正确方向，不应搬进 BerryUI。

3. **声明式语法不是地基，状态/生命周期/重建边界才是**。ArkUI V1/V2 与 Compose 的差异显示：自动观察、深度监听、冻结、同步时机都会成为兼容性负担。Berry 在文本、焦点、无障碍和 API 治理未闭环前，不应引入全局 reactive 环境。

4. **Berry 的保留树路线仍可成立**，但需要把“描述、布局、语义、状态副作用”拆清楚。Flutter/Compose 都没有把 immutable description 与 mutable render state 混在一个对象里；Berry 当前 `Node + Props + side table` 是小型可行形态，layout v2 前必须再拆。

5. **布局的通用规则是 constraints down / sizes up / parent positions**。Flutter 官方文档一句话给出核心；Compose/WinUI/Android 也是 measure/arrange 两阶段。L1/L2/L3 已有局部约束与主轴 flex，但还没有完整 `min/max constraints × intrinsic × arrange` 代数。

6. **文本输入是下一块不可绕开的地基**。OpenHarmony TextInput 明确区分 `onChange/onSubmit/onTextSelectionChange/onFocus`、caret、selection menu、keyboard avoidance、caret avoidance；Compose 也有独立 text input service。GUI-T1 TextField Foundation 应先于 IME 和表单产品化。

7. **焦点至少有三层**：

   ```text
   window/view activation authority
   component focus traversal
   text/IME focus
   ```

   Fuchsia focus chain 文档把这层拆得最清楚。Berry 当前 `gui-wmd` 窗口焦点 + BerryUI C1 组件焦点的二分正确，但 GUI-T1 前必须补 text focus 语义。

8. **无障碍不是 label 字段，而是独立 semantic tree**。Compose semantics 有 merge/clear/hit test/minimum touch target；OpenHarmony accessibility API 有事件、动作、窗口更新类型。Berry 现有 a11y 条目太薄，不能支撑 screen reader。

9. **设计 token 需要 bg/fg 成对、色彩方案矩阵、对比度验证和字号缩放**。libadwaita 的 paired background/foreground 变量、Microsoft 的 4.5:1 与 text scaling 100–225%、Material HCT 是三条互相印证的证据。

10. **控件规格和文档是 SDK 质量门**。WinUI 的 spec→docs→Gallery 管线、Swift Book 的 Tour/Guide/Reference + 可执行示例、OpenHarmony `.d.ts` 单源 API 面，都比“边写代码边补 README”可靠。

11. **版本治理必须进入 API 定义本身**。OpenHarmony `@since` 与 SystemCapability、WinUI release channel + API availability matrix、Fuchsia FIDL version rubric 都说明：版本不是事后文档，而是 API 面属性。

12. **下一刀不应做设备形态 pack，也不应做 Route/Back/FormMetrics**。官方一手源显示这些产品形态都建立在 text/focus/a11y/lifecycle/tooling 稳定之后。Berry 下一刀优先 **GUI-T1 TextField Foundation**，并行做 **控件规格模板与 SDK API 版本治理**。

## §2 平台架构对照

| 维度 | OpenHarmony ArkUI | Android/AOSP/Compose | Flutter | Fuchsia | Microsoft/Apple 参考面 |
|---|---|---|---|---|---|
| 应用/运行时 | UIAbility、WindowStage、UIContext | Activity/Context、WindowManager、Compose runtime | runApp/Binding/embedder | component manager、capabilities、runner | WinUI app lifecycle / Apple link-only |
| 树模型 | 前端组件 + UINode/FrameNode | View 树或 Compose slot table + Applier | Widget + Element + RenderObject + Layer | Flatland/Scenic retained scene graph | XAML visual tree / API 无本地源 |
| 状态 | V1 decorators；V2 `@Local/@Param/@Event/@Trace/@Monitor` | Compose state/slot/recomposition | StatefulWidget/setState + immutable widget | 组件外状态 | 官方内容有限 |
| 布局 | 组件声明式布局、自适应 Navigation | measure/layout；Compose Constraints | constraints down/sizes up | Scenic view bounds/composition | XAML Measure/Arrange |
| 窗口/焦点 | WindowStage、FocusController | window focus + view focus | embedder/windowing | view focus + focus chain | keyboard/accessibility 文档 |
| 文本 | TextInput/TextArea/Search、selection/caret/键盘避让 | InputMethodManager、Compose TextInputService | text input/IME、semantics | IME 权限依赖 view focus | Windows IME/text scaling 文档 |
| API 治理 | `.d.ts` `@since`、SystemCapability | targetSdk/annotation/compat | stable SDK surface | FIDL rubric/version | Experimental/Preview/Stable + availability matrix |
| 文档/规格 | docs + `.d.ts` 单源 | API docs/samples | website + API docs | docs in monorepo | spec→docs→gallery；Swift Book/DocC |

关键差异：

- OpenHarmony 提供最完整的**同语言应用 SDK 面**，适合 Berry 借 `.d.ts`/`@since`/UIContext 组织。
- Compose/Flutter 提供最完整的**声明式运行时机制**，适合 Berry 借重建边界和 constraints，不适合直接复制语法。
- Fuchsia 提供最接近 Berry 的**微内核组件/能力/合成器/焦点链架构**。
- Microsoft 提供最完整的**控件规格与发布通道流程**。
- Apple 官方 HIG 只能链接，不能作为本地正文事实；Swift Book/DocC 提供可借的文档工程证据。

## §3 OpenHarmony：ArkUI 与 SDK 面的组织方式

### 3.1 状态是显式契约，不是隐式魔法

本地源：

```text
reference/sdk-ui/cache/openharmony-docs/en/application-dev/ui/state-management/arkts-state-management-overview.md
reference/sdk-ui/cache/openharmony-docs/en/application-dev/ui/state-management/arkts-state-management-introduce.md
reference/sdk-ui/cache/openharmony-docs/en/application-dev/ui/state-management/arkts-v1-v2-update-difference.md
reference/sdk-ui/cache/openharmony-docs/en/application-dev/ui/state-management/arkts-new-local.md
reference/sdk-ui/cache/openharmony-docs/en/application-dev/ui/state-management/arkts-new-param.md
reference/sdk-ui/cache/openharmony-docs/en/application-dev/ui/state-management/arkts-new-event.md
reference/sdk-ui/cache/openharmony-docs/en/application-dev/ui/state-management/arkts-new-observedV2-and-trace.md
reference/sdk-ui/cache/openharmony-docs/en/application-dev/ui/state-management/arkts-new-monitor.md
```

官方定义：

```text
UI 是应用状态的执行结果；状态变化驱动重新渲染。
```

V2 明确拆分：

```text
@Local：组件内部状态，只能本地初始化，不允许父组件覆盖
@Param：外部输入，子组件不能直接改
@Event：组件输出回调，由父组件决定如何更新数据源
@ObservedV2 + @Trace：深度/属性级观察
@Monitor：监听状态变化，能取 before/now
```

V1 的问题官方写得很清楚：

```text
状态变量不能独立于 UI
只观察顶层属性
嵌套对象导致冗余重渲染
装饰器输入/输出约束不清晰
```

V1→V2 的官方映射也说明了迁移成本：

```text
@State       -> @Local / @Param + @Once
@Prop        -> @Param（深拷贝改引用）
@Link        -> @Param + @Event
@Observed    -> @ObservedV2
@Track       -> @Trace
@Watch       -> @Monitor
@Provide     -> @Provider
@Consume     -> @Consumer
LocalStorage -> 全局 @ObservedV2 状态
AppStorage   -> AppStorageV2
```

ArkUI 的更新时机不是立即全树刷新。官方文档描述为：

```text
状态变量收集依赖它的系统组件 elementId 集合
变更先标记对应自定义组件脏
下一次 VSync 只重渲染脏组件
单个 VSync 周期内重新推导迭代不超过 3 次
```

`@Watch` 与 `@Monitor` 也有时序差异：

```text
@Watch：同步执行，同事件内可能多次触发
@Monitor：异步合批，同事件内多次变更只回调一次
```

这给 Berry 的直接结论是：即使未来引入声明式重建，也必须有：

```text
dirty scope
帧内迭代上限
同帧合批
事件同步/异步语义
full rebuild oracle 对照
```

这直接警示 Berry：若现在做自动 reactive，必须先定义：

```text
谁是 state owner
哪些变更可观察
父/子同步方向
重建 scope
inactive/frozen 语义
事件是否同步
```

Berry 现阶段更安全的结论：

```text
app 保留状态所有权
BerryUI 提供显式 rebuild API
不做全局 AppStorage
不做深度对象自动观察
不做双向绑定语法糖
```

### 3.2 UIContext 是运行时能力的显式入口

OpenHarmony 多处从 Window/MainWindow 取 `UIContext`，再访问：

```text
FocusController
animateTo
Router
KeyboardAvoidMode
TextMenuController
HostContext
```

本地证据：

```text
openharmony-docs/en/application-dev/ui/arkts-manage-keyboard.md
openharmony-docs/en/application-dev/ui/arkts-uicontext-custom-dialog.md
openharmony-docs/en/application-dev/ui/state-management/arkts-v1-v2-migration-application-and-others.md
```

这对 Berry 的启示：

```text
UI 能力不能散落成全局函数
窗口、焦点、键盘避让、菜单等应由显式 Session/AppContext 授予
BerryUI 只消费传入的能力，不自行联系 wmd
```

当前 `Ui` 已显式持有上下文，这是正确方向；后续 GUI-T1 应保持“UI 不找全局服务”。

### 3.3 组件生命周期与冻结

本地源：

```text
openharmony-docs/en/application-dev/ui/state-management/arkts-page-custom-components-lifecycle.md
openharmony-docs/en/application-dev/ui/state-management/arkts-custom-components-new-lifecycle.md
openharmony-docs/en/application-dev/ui/state-management/arkts-custom-components-freezeV2.md
openharmony-docs/en/application-dev/reference/apis-arkui/arkui-ts/ts-custom-component-new-lifecycle.md
openharmony-docs/en/application-dev/ui/rendering-control/arkts-rendering-control-foreach.md
```

官方生命周期要点：

```text
aboutToAppear：实例创建后、build 前执行
aboutToDisappear：销毁前执行，不建议改状态或挂异步
父子创建顺序是父 aboutToAppear -> 父 build -> 子 aboutToAppear
删除时父/子 aboutToDisappear 均触发
最小化或切换应用不等于组件销毁
```

V2 freezing：

```text
inactive 组件可冻结
@Monitor 不触发
关联节点不重渲染
Tab/Navigation/Repeat/隐藏页面是主要场景
```

API 23 后 ArkUI 引入装饰器生命周期状态机：

```text
@ComponentInit
@ComponentAppear
@ComponentBuilt
@ComponentDisappear
@ComponentAttach
@ComponentDetach
@ComponentReuse
@ComponentRecycle
```

状态枚举：

```text
INIT = 0
APPEARED = 1
BUILT = 2
MOUNTED = 3
RECYCLED = 4
DISAPPEARED = 5
```

官方动机是修正旧回调错序：旧 `aboutToDisappear` 在特定场景可能被强制补 `aboutToAppear`，`aboutToReuse` 也可能在组件未实际展开复用时误触发。状态机让非法转换显式化。

Berry 不需要照搬回调名，但 `apply_desc / reset / remove / focus` 应升级为状态机不变量：

```text
每个 Node/子树有显式生命周期阶段
非法转换 loud reject
删除子树时焦点清理是状态迁移的一部分
不得为满足旧回调形状合成事件
```

渲染控制还有一个重要键规则。ArkUI `ForEach` 默认 key 是：

```text
index + "__" + JSON.stringify(item)
```

官方文档明确展示 index key 会产生重复渲染，并给出自定义 key 后约 70MB 的优化案例。因此 Berry 未来 keyed re-apply 必须：

```text
禁 index-only key
禁 JSON.stringify 默认 key
key 冲突有诊断
优先使用 app 提供的稳定业务 key
```

Berry 目前只有节点/damage/focus 生命周期，还没有组件逻辑生命周期。结论：

```text
GUI-T1 TextField 前只补输入/焦点生命周期
不引入通用组件 aboutToAppear/aboutToDisappear
ListDetail 保持无状态
```

### 3.4 Navigation 是树/栈/自适应布局组合，不是简单 Route API

本地源：

```text
openharmony-docs/en/application-dev/ui/arkts-navigation-introduction.md
openharmony-docs/en/application-dev/ui/arkts-navigation-architecture.md
openharmony-docs/en/application-dev/ui/arkts-navigation-split-mode.md
openharmony-docs/en/application-dev/ui/arkts-router-to-navigation.md
```

官方建议 `Navigation` 替代旧 Router，核心结构：

```text
Navigation：根容器
NavDestination：子页容器
NavPathStack：页面栈控制器
```

自适应规则：

```text
宽度 < 600 vp：单栏，整页替换
宽度 >= 600 vp：split view，左侧 NavBar + 右侧 NavDestination
```

这验证 Berry L3 的 ListDetail 方向：布局原语先提供 pane 几何与焦点顺序，选择状态、返回栈、Compact/Expanded 分支归 app。Route/Back 仍应后置。

### 3.5 焦点是一个带圈禁和优先级的词汇表

本地源：

```text
openharmony-docs/en/application-dev/ui/arkts-common-events-focus-event.md
openharmony-docs/en/application-dev/reference/apis-arkui/arkui-ts/ts-universal-attributes-focus.md
```

ArkUI 明确：

```text
Page / Dialog / SheetPage / ModalPage / Menu / Popup / NavBar / NavDestination
属于 hierarchical page
```

规则：

```text
hierarchical page 自动捕获并圈禁键盘焦点
用户不能用键盘把焦点移出当前 hierarchical page
应用至少有一个 hierarchical page 处于焦点中
焦点激活态默认隐藏，Tab 进入，点击退出
```

遍历策略：

```text
Tab：Z 形叶子遍历，可循环
方向键：十字形搜索，结合中心点距离
```

官方还有恢复优先级：

```text
FocusPriority::AUTO = 0
FocusPriority::PRIOR = 2000
FocusPriority::PREVIOUS = 3000
```

并规定：

```text
tabIndex 与 focusScopeId 不能同时使用
Button/TextInput 默认可焦
Text/Image 默认不可焦
tabIndex < 0 时只允许程序化聚焦
```

Berry C1 目前是树前序 + 主轴导航，后续应补的不是复杂调度器，而是把这些词汇先入账：

```text
focus scope
activation state
restore previous/prior
default focusable matrix
programmatic-only focus
```

无障碍方面 ArkUI 的最小词汇也值得直接采纳：

```text
accessibilityText
accessibilityDescription
accessibilityGroup
accessibilityLevel = auto | yes | no | no-hide-descendants
```

### 3.6 文本输入与键盘避让是完整合约

TextInput 官方事件面：

```text

onSubmit：Enter 提交
onTextSelectionChange：选择柄或 caret 位置变化

```




## §4 Android/AOSP/Compose：窗口、View、声明式运行时

### 4.1 窗口与输入权威在系统侧

本地源：

```text

android-frameworks-base/core/java/android/widget
android-frameworks-base/libs/input

```

AOSP 的分层证据：

```text

InputDispatcher 在系统侧路由
SurfaceFlinger/BufferQueue 管理图形缓冲
Binder 承载跨进程调用
```

几个具体合约值得进入 Berry 设计账本：

1. Android window flag 是声明式输入能力位：

   ```text
   FLAG_NOT_FOCUSABLE
   FLAG_NOT_TOUCH_MODAL
   FLAG_ALT_FOCUSABLE_IM
   ```

   其中 `FLAG_NOT_FOCUSABLE` 会隐含 `FLAG_NOT_TOUCH_MODAL`。Berry P4 window policy matrix 可演进为纯数据 record，而不是分散 if。

2. `InputDispatcher` 有默认 5 秒 dispatch timeout。本地证据：

   ```text
   android-frameworks-native/libs/input/android/os/IInputConstants.aidl
   android-frameworks-native/services/inputflinger/dispatcher/InputDispatcher.cpp
   ```

   其中 AIDL 常量：

   ```text
   UNMULTIPLIED_DEFAULT_DISPATCHING_TIMEOUT_MILLIS = 5000
   ```

   行为面：

   ```text
   focused app 无响应 -> ANR
   focused app 存在但无 focused window -> watchdog ANR
   ```

   Berry P2/P3 目前只有路由正确性，还没有“目标不可达/不响应”的看门狗语义。

3. `ViewRootImpl` 将输入队列与 Choreographer traversal 汇流：

   ```text
   scheduleTraversals
   doTraversal
   measure -> layout -> draw
   ```

这支持 Berry 现行权威：

```text
gui-wmd：window activation / seat focus / keyboard routing
Berry Room：surface/buffer authority
BerryUI：in-tree component focus/layout
```

不应让普通 app 直接拿 seat 或全局窗口焦点。

### 4.2 Compose 的关键不是语法，而是 Applier + slot table

本地源：

```text
androidx/compose/runtime/runtime/samples/src/main/java/androidx/compose/runtime/samples/CustomTreeCompositionSamples.kt
androidx/compose/runtime/runtime/src/commonMain/kotlin/androidx/compose/runtime/Composer.kt
androidx/compose/runtime/runtime/src/commonMain/kotlin/androidx/compose/runtime/Composition.kt
androidx/compose/runtime/runtime/src/commonMain/kotlin/androidx/compose/runtime/Recomposer.kt
```

Compose 将：

```text
Composition：描述与更新上下文
Applier：把变更应用到具体节点树
SlotTable/SlotReader/SlotWriter：线性化存储与 diff
Recomposer：调度失效与重组
```

CustomTreeCompositionSamples 展示了自定义 `NodeApplier` 和 `Composition`，说明声明式核心可以驱动不同目标树。

实现细节也值得注意：

```text
SlotTable：IntArray groups + Object slots，gap buffer 存储
Composer：startRestartGroup/endRestartGroup 绑定 RecomposeScope
Recomposer：按 frame clock 调度 invalidation
mutableStateOf：默认 structural equality policy
```

AndroidX 仓中还存在新的 link buffer slot table 实验，说明 Google 仍在重造 slot 存储；Berry 不应过早复制该内部数据结构。

Compose 在 Android 宿主上只有单一 `AndroidComposeView` 适配层：

```text
onMeasure / onLayout 转发 constraints
dispatchKeyEvent 转发 focusOwner
dispatchDraw 转发 compose draw
AccessibilityDelegate 桥接 semantics
```

这证明声明式树可以完整骑在系统窗口/View 宿主上，而不需要 OS 知道 composition 内部。

Berry 可借的架构经验：

```text
描述更新和树应用分离
失效以 scope 为单位
remember/side effect 是运行时合约，不是普通缓存
不要让每个字段变更都全局重建
```

暂不借：

```text
Kotlin compiler plugin
@Composable 语法
跨线程重组调度
```

## §5 Flutter 与 Fuchsia：引擎、嵌入、能力与焦点链

### 5.1 Flutter 布局规则是最清晰的官方表述



```text

performLayout()
```

```text
!parentUsesSize
```

```text
!needsLayout && new_constraints == old_constraints

```


libadwaita 把“断点即数据”做得很清楚：

```text
条件：min/max width/height、min/max aspect ratio
组合：AND / OR
setter：object + property + value 三元组
命中：BreakpointBin 统一 apply/unapply
```

另有三个不同层次的机制：

```text
Clamp：maximum-width + tightening-threshold 渐进收紧
Leaflet：folded 是运行时折叠状态，不只是断点重排
Breakpoint：显式条件切换属性集
```

Berry 未来 breakpoint AST 可采用同形数据模型，但不需要 GObject 属性系统。

Berry F3 主题应引入：

```text
paired bg/fg token
standalone foreground token
scheme matrix
contrast fixture
token 不允许单边改背景不改前景
```

## §7 Berry 当前架构复核

### 7.1 已被官方一手源支持的做法

| Berry 现行做法 | 官方对应证据 | 结论 |
|---|---|---|
| `gui-wmd` 持窗口激活/seat focus/键盘路由 | Fuchsia Scenic focus chain；AOSP system-side dispatcher | 保持 |
| BerryUI 只做树内组件焦点/布局 | Compose/Flutter in-tree focus；Fuchsia focus chain 分层 | 保持 |
| Room 管 surface/buffer authority | Fuchsia component capability；Flutter embedder | 保持 |
| L1 局部 Tight/Loose 约束 | Flutter constraints；Compose Constraints | 保持并扩展 |
| L2 runtime-only flex side table | Compose slot/side state；WinUI API versioning | 短期保持 |
| L3 ListDetail 无状态，选择归 app | OpenHarmony Navigation/NavPathStack 分层 | 保持 |
| 不做 FormMetrics/Route/Back | OpenHarmony Navigation 是后续高层能力 | 保持后置 |
| 不按设备名分支 | Windows/GNOME 均以窗口/受限形态为基础 | 保持 |
| 普通 app 禁止手写 WM/VMO | Fuchsia capability + AOSP system authority | 保持 |

### 7.2 官方源暴露的 Berry 缺口

| 缺口 | 影响 | 建议位置 |

| 文本模型/caret/selection/edit commands | 无法做表单、搜索、设置输入 | GUI-T1 |

| 控件规格模板 | 组件 API 容易凭感觉演化 | SDK-S0 |
| API since/capability/channel | SDK 无兼容治理 | SDK-S0 |
| paired bg/fg token 与对比度门 | 主题容易不可读 | DESIGN-D2 |
| 完整 constraints/intrinsic 代数 | 复杂组件和文本布局会撞墙 | layout v2 |
| keyed re-apply 与 dirty scope | `apply_desc` 粒度过粗，性能难以证明 | 后续 |
| 生命周期状态机 | remove/reset/focus 边界靠约定而非状态机 | 后续 |

## §8 BerryOS 决策矩阵

### 8.1 直接采纳

| 决策 | 依据 | Berry 落法 |
|---|---|---|
| API 版本是 API 面属性 | OpenHarmony `@since`；WinUI channel | 建 SDK API ledger，每个公开项带 since/channel/capability |
| 控件先写规格 | WinUI spec 流程 | 统一 BerryUI control spec 模板 |
| 键盘行为进规格 | WinUI appendix | 每个可交互控件必须有 keyboard contract |
| 文本状态显式建模 | OpenHarmony TextInput；Compose TextInputService | GUI-T1 冻结 value/selection/caret/edit events |
| 窗口基准自适应 | Windows/GNOME | 不按设备名，按 window constraints |
| constraints down/sizes up/parent positions | Flutter | layout v2 硬定理 |
| relayout boundary 与约束相等短路 | Flutter `RenderObject` | 布局停止条件进规格与断言 |
| 单遍测量 | Compose runtime guard | L2/LAYOUT-L4 禁多遍 measure/weight 重分配 |
| stable key diff | Flutter `Widget.canUpdate`；ArkUI ForEach | 禁 index/JSON key，key 冲突显式诊断 |
| 生命周期状态机 | ArkUI API23 lifecycle | apply/reset/remove/focus 变成非法转换可测状态机 |
| 焦点 scope + restore + activation | ArkUI/Compose/Fuchsia | C1 后续词表，不改变 wmd 权威 |
| semantic tree 独立 | Compose semantics；Flutter `flushSemantics` | SEM-A1 sidecar，不塞 Props |
| a11y 四级可见性 | ArkUI accessibilityLevel | auto/yes/no/no-hide-descendants |
| paired bg/fg token | libadwaita | DESIGN-D2 token 代数 |
| 对比度与文本缩放检查 | Microsoft a11y | 设计 token 测试夹具 |
| Present credits + 实际呈现反馈 | Fuchsia Flatland | FrameTimeline 归因补 OnNextFrameBegin/OnFramePresented 语义 |
| 文档示例可执行 | Swift Book | BerryUI docs snippets 接 host test |
| design guidance 与 API reference 分离 | Apple/WinUI/Swift | Berry HIG 与 berry-ui API 文档分家 |

### 8.2 改造后采纳

| 官方模式 | 不照搬原因 | Berry 改造 |
|---|---|---|
| ArkUI `@Local/@Param/@Event` | Rust 无 ArkTS decorator； reactive 语义过重 | 用 ownership + event handler + rebuild scope 显式表达 |
| Compose slot table | 需编译器与复杂 invalidation | 先用 plain data desc + diff + retained side table |
| Flutter Element tree | 当前规模不需要三树全量 | 保持 Node，layout v2 再拆 |
| Fuchsia focus chain | Berry 只有单窗口主验 | 先记录 focus path snapshot，再扩展多窗口 |
| Fuchsia View token pair | 当前无多进程嵌入 | 未来跨进程父子授权用 token-pair，不给全局树句柄 |
| WinUI release cadence | 项目节奏不同 | 保留 channel 语义，不承诺 6 个月 major |
| OpenHarmony Navigation | Route/Back 后置 | L3 ListDetail 只做几何，app 管选择 |
| Material HCT | 不直接复制 Google 色彩体系 | 用于算法与对比度思想，Berry 自有 token |
| DocC renderer | 先解决内容与验证 | 用 Markdown + rustdoc + 可执行测试起步 |
| Android window flags | 分散 boolean 会扩散 | P4 演进为纯数据 window capability record |

### 8.3 明确拒绝

```text
镜像 Apple/Huawei/Microsoft/Material 3 受版权页面
把 CC-BY-SA/GPL 文本复制进公开文档
普通 app 直接操纵窗口焦点/seat/VMO
按 isPhone/isTablet/isDesktop 分支
在没有 SDK 版本治理时冻结大量易变 API
为了像 Flutter 而引入全局 reactive 环境
ArkUI V1 代理式隐式双向绑定
index-only / JSON.stringify 默认 key
Android 多遍 measure 与权重循环
无 successor 的弃用
为了组件好看先做 form/navigation 产品化
运行时双渲染后端开关
3D 场景图 API
逐控件 GObject 式属性样板
```

### 8.4 后置

```text

form metrics

multi-window app API
```

## §9 下一步路线裁决

本文建议下一刀保持“底层夯实”原则：

**程序前置**：本报告成稿时，GUI-T1 / SDK-S0 尚未进入当时的 GUI 框架地基路线 v1.15 里程碑表。按路线 §6，实施前必须先升版路线并同步 `docs/规则/14-GUI与UI框架.md`，再写代码；该前置已在后续 v1.16 完成。DESIGN-D2 若修改现行 F3 主题规格，不能直接改旧规格语义，必须新建设计规格或将 F3 版本升档并同步引用。

### 第一优先：GUI-T1 TextField Foundation Before IME

范围：

```text
TextState plain data
selection/caret 模型
hardware key edit commands
input filter/type 词表
on_change/on_submit/on_selection_change 事件
focus enter/leave 与 wmd 键盘路由对齐
selection/caret damage
a11y text event 最小面
keyboard occlusion 数据消费接口（不实现软键盘）
```

两个必须先裁决的交互合约：

1. **与 C1 keymap 的优先级**。非文本组件维持 C1 的 `Enter/Space -> Activate -> Msg::Click`；焦点在 TextField 时，编辑键先被文本状态机消费：
   ```text
   Enter -> submit（或换行，按 multiline）
   Space -> 字面空格
   Tab/Shift+Tab -> 焦点导航
   ```
   不允许同一键同时触发编辑与组件激活。

2. **与 P0/R2 已冻结词表的 add-only 映射**。P0 已冻结 IME composition frame 的 `purpose = Text/Multiline/Number/Password` 与 phase；R2 已冻结 typed insets 且 `Ime` producer 属后续系统层。GUI-T1 的 email/phone/URL 等 input type 只能作为 purpose 的 app 侧超集/过滤词表，不得另造一套 wire purpose；键盘避让消费必须落到 `insets::Ime` 数据面，即使当前 producer 恒 0。

明确不做：

```text
软键盘
IME Host
FormMetrics
复杂富文本
clipboard
autofill
Route/Back
```

### 并行小刀：SDK-S0 SDK/API Governance Baseline

范围：

```text
control spec 模板
API ledger 字段
since/channel/capability 语义
breaking change 记录格式
 BerryUI 现有公开面回填账本
```

这不是产品化，而是防止未来 SDK 漂移。

### 同步记录的架构接缝：UIContext 形态

OpenHarmony 与 Compose 在不同实现下收敛到同一接缝：

```text
window/session 之下、widget tree 之上
存在一个 per-window UI instance
持有 focus controller、keyboard mode、theme、text menu 等 UI 能力
```

OpenHarmony 叫 `UIContext`，Compose 在单树内由 `FocusOwner` 等对象承担。Berry 不需要立刻新增大对象，但后续应把当前 `Ui` 中的隐式上下文拆清：

```text
window/session 授予的能力
组件树自身状态
text/focus 临时状态
theme/token 快照
```

裁决：这只是接缝记录，不在 GUI-T1 中实现新全局 service。

### 第二优先：SEM-A1 Semantic Tree Sidecar

范围：

```text
role/label/value/state/action
merge/clear 规则
focusable/focused
text range
hit/a11y bounds
最小 screen reader 事件面
```

### 第三优先：DESIGN-D2 Design Token Pair Contract

范围：

```text
paired bg/fg
scheme matrix
contrast fixtures
text scale ladder
effective-pixel/grid policy
```

### 第四优先：layout v2 constraints/intrinsic

在 GUI-T1 文本内在尺寸之后做，避免文本组件倒逼布局返工。

## §11 主要风险与未解问题

1. **Apple HIG 不能当正文源**
   只能实时访问官方 URL；不要在公开文档引用“Apple 说……”而无本地许可证据。

2. **OpenHarmony 商用 HarmonyOS 与 OpenHarmony 不完全等价**
   本地可复现源是 OpenHarmony。HarmonyOS NEXT 页面仅链接，不作为实现依据。

3. **Compose/Flutter 的内部机制体量巨大**
   本轮只读核心路径，不能声称完整复刻其优化策略。

4. **layout v2 会破坏现有 AST/measure 假设**
   必须以独立规格和迁移测试推进，不能和 GUI-T1 混成一大刀。

5. **SDK API ledger 有维护成本**
   先从 berry-ui 公开面试点，不能一次性要求全仓所有 syscall/service 面。

6. **a11y 可能引出跨进程服务边界**
   SEM-A1 先做树/事件模型，不提前实现完整 screen reader 服务。

7. **rootfs0 已精确到单卷帽**
   L3 记录 `rootfs0 = 33,554,432B`，即 32MiB 单卷帽为 0 余量。GUI-T1 一旦增加 guest payload，规格必须携带 per-`.bap`/rootfs 两帽账；若需要增长，先给拆卷、压缩或迁出方案。SDK-S0 属文档/规格面，不触镜像预算。

## §13 结论

本轮官方一手源研究没有推翻 Berry 当前“从底层夯实”的方向，反而强化了它：

```text
窗口/输入/表面权威留在系统服务

SDK 版本和规格先行

```

下一刀的最优路径是：

```text

+ SDK-S0 Control Spec / API Governance Baseline
```

随后：

```text
SEM-A1 Semantic Tree Sidecar
DESIGN-D2 Design Token Pair Contract
LAYOUT-L4 Constraint-aware Measure/Arrange
```

在 GUI-T1/SEM-A1/SDK-S0 完成前，不应进入 form/navigation/设备形态 pack 或软键盘产品化。
