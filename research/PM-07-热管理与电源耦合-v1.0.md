## §0 一页结论

1. 热管理与电源管理共享**同一动作空间**（频率帽/核数帽/充电限流/关机），分野只在**触发原因**（温度 vs 电量）。
   业界收敛形态：原因层各自传感，**动作层统一仲裁取最严**；Android 甚至立法「电池功率约束也必须经 thermal HAL 上报」。
2. 应用契约全球收敛为**只读枚举 + 变更通知 + 自愿配合，无议价权**（Apple 四档 / Android 七档 / OH 档位制）；
   且 Android 明说**severity 准确性优先于温度真实性**——契约面是档位不是摄氏度。
3. IPA 的本质是「**PID over 能量模型（EM）**」：按相对能效把总功率预算分配给各冷却设备（PM-03:100 一段话的完整展开，含
   全参数与量纲约束）。
4. Linux 5.7 起热帽必须反馈进调度器容量（thermal pressure），否则降频帽对调度器「不可见」，选核选频继续按满容量预测——
   **这是 PM-03 归属裁决未覆盖的坑，BerryOS 帽生效时记账面要同步打折**。
5. BerryOS 裁决：berry-thermal 用户态服务（第 2 层）+ 驱动自报 trips（对齐一期「驱动自报 power levels」先例）+
   降档走既有票据与帽执行面（不新开通道）+ sim-thermal = 同一自报接口的普通注入驱动 + smoke 断言四件套（见 §5）。

## §1 机制全景

### 1.1 Linux thermal framework：zone → trip → cooling → governor 四件套【确定度：高】

来源：[thermal sysfs API](https://docs.kernel.org/driver-api/thermal/sysfs-api.html)

| 构件 | 内容 | BerryOS 视角 |
|---|---|---|
| thermal zone | `thermal_zone_device_register_with_trips()` 注册；sysfs `/sys/class/thermal/thermal_zone[0-*]` | 一个传感器源（可虚拟）= 一个 zone |
| trip point | 四型：active（风扇）/passive（降频）/hot/critical；带 hysteresis | 迟滞一等公民，全平台同 |
| cooling device | `get_max_state/get_cur_state/set_cur_state` 三回调 + `should_bind` 绑定 | 降档动作的统一抽象 |
| governor | **逐 zone** 挂策略（`policy`/`available_policies` 属性），可混布 | 策略可插拔，同 BerryOS 调度哲学 |
| 采样双模 | 中断 trip + `set_trips` 动态窗口；无中断传感器走 `polling_delay` 轮询 | 事件驱动优先 + 轮询兜底 |
| critical 链 | critical trip → `orderly_poweroff` → 失败则 `emergency_restart/poweroff` | 兜底链必须短且独立于用户态服务 |

cooling 谱系（动作空间实证）：cpufreq 降频帽、idle 注入（[intel_powerclamp](https://docs.kernel.org/admin-guide/thermal/intel_powerclamp.html)：
全核同步注入空闲周期达到目标空闲百分比）、风扇（active trip）、CPU 离线。**降频与注闲是同一问题的两个档位**。

### 1.2 governor 谱系：step_wise vs power_allocator(IPA)【确定度：高】

来源：[power_allocator 文档](https://docs.kernel.org/driver-api/thermal/power_allocator.html)

| 项 | step_wise | power_allocator（IPA） |
|---|---|---|
| 决策 | 温度穿档 → 逐档加减冷却状态，保守防抖 | PID 控制器直接产出**总功率预算**再按能效分摊 |
| 输入 | 当前 trip 档 | 温度误差 + sustainable_power + 各冷却设备 Power Actor |
| 适用 | 单点简单场景 | 多核多设备手机 SoC 主战场 |

IPA 钻深（PM-03:100 一段话的展开）：

- 两个锚定 trip：**switch_on**（首个 passive，越过才启动 PID）+ **desired**（末个 passive，目标温度）。
- 核心公式：`P_max = k_p*e + k_i*err_integral + k_d*diff_err + sustainable_power`。
  默认 `k_i` 积分限幅 1–2 倍 sp 且 `integral_cutoff` 之下不积分、`k_d` 默认 0（即多数产品跑 PI）。
- 比例增益默认斜坡：switch_on 处 `k_pu = 2*sp/ΔT`（温度越低增益越高，**越冷越敢给电**）；`k_po = sp/ΔT`。
- `sustainable_power` 参考量级：4 寸手机 ~2000mW、10 寸平板 ~4500mW——**整机热预算是一等参数，不是派生值**。
- Power Actor 三 ops：`get_requested_power`（各设备当前要多少）/`state2power`/`power2state`（预算→冷却状态反解）。
- weights = 各 CPU 相对能效；**要求功率量纲一致**（EM 的 active_power 表），否则分配系统性偏差。

### 1.3 thermal × cpufreq/EAS 耦合：thermal pressure【确定度：高】

来源：[LWN 786122](https://lwn.net/Articles/786122/) · [LWN 810782](https://lwn.net/Articles/810782/)（Linux 5.7 落地，2020）

- 起因：EAS/schedutil 按利用率预测频率请求，热降频帽生效后若调度器不知情，会继续按满容量选核选频——
  **帽被调度「看不见」**，表现为选核次优 + 频率请求虚高。
- 修法：把每 CPU 的热帽折算成容量折扣（thermal pressure）注入调度器容量计算；
  schedutil 预测随之收敛。**降档动作必须同时修正记账面**，这条对所有 OS 成立。

### 1.4 Android 全链：HAL → 系统服务 → app API【确定度：高】

来源：[thermal-mitigation 官方文档](https://source.android.com/docs/core/power/thermal-mitigation)（本段引号均为该页原文）

| 层 | 事实 |
|---|---|
| HAL 演化 | 1.0（Android 9-，轮询）→ 2.0（Android 10+，HIDL 回调推送）→ AIDL IThermal（Android 14+） |
| 状态枚举 | THERMAL_STATUS 七档 0x0–0x6：NONE/LIGHT/MODERATE/SEVERE/CRITICAL/EMERGENCY/SHUTDOWN |
| 系统服务 | 常驻监测 HAL 回调，向双客户端发档位：IThermalEventListener（内部/OEM）、IThermalStatusListener（app） |
| app API | `PowerManager.getCurrentThermalStatus()` + `addThermalStatusListener()`（查询 + 订阅） |
| 厂商铁律 1 | 「The device skin temperature is the most important system to track」——**皮肤温优先于结温**（用户体验面） |
| 厂商铁律 2 | 「Anything that throttles device performance, **including battery power constraints**, must be reported through the thermal HAL」——电源约束是热框架的输入 |
| 厂商铁律 3 | 「the severity level must be accurate」——温度值可以不是真实温度（允许 guardband/假值换迟滞），**档位必须准** |
| 厂商铁律 4 | 一切降档动作必须上报（含 jobscheduler 节流、modem 关闭）；EMERGENCY 档可关蜂窝 |
| 测试面 | 必须过 VTS；可用内核 sysfs `emul_temp` 模拟温度——**测试走同一接口注入，不旁路** |

ADPF×thermal 协作（[ADPF Thermal](https://developer.android.com/games/optimize/adpf/thermal)）：
`getThermalHeadroom(forecastSeconds)` 返回 0.0–1.0（NONE→SEVERE）**预测值**——把「现在几档」升级成「N 秒后到几档」，
供游戏/重载应用提前降载；速率上限 10s 一次，无 HAL 2.0 支持的旧设备退化为启发式（0.85/0.95/1.0 映射三档）。

### 1.5 高通 thermal-engine：厂商热引擎黑箱【确定度：高（官方文档）/中（生态观察）】

来源：[User space thermal engine](https://docs.qualcomm.com/doc/80-88500-4/topic/56_User_space_thermal_engine.html) ·
[Software thermal management](https://docs.qualcomm.com/doc/80-88500-4/topic/52_Software_thermal_management.html)

- 分工：kernel 侧 thermal core（upstream Linux）做监测识别；**用户态 thermal-engine 实施缓解**——印证「机制在内核、策略在用户态」可落地。
- 双算法并行：monitor（阈值型，如 `quiet_therm` 43/45°C 触发、41/43°C 清除，动作为 battery 限流 2 3）+
  DTM/"ss" 闭环设定点控制（10ms 高频采样，把温度压在 `set_point` 85°C 直到降到 `set_point_clr` 65°C，带 `time_constant`）。
- **虚拟传感器**：两个以上真实传感器读数加权混合估计皮肤温——单点传感器测不出 skin 温，虚拟化是必需品。
- **override mode：阈值整体平移预设常量**（官方文档自述可用于 benchmark 场景）——厂商给跑分放水的制度性后门，
  热治理动作必须**可审计**的反面教材。
- 生态面：root 社区删 `/system/vendor/bin/thermal-engine` 换性能即失去关机保护（中，XDA 讨论）——热服务不可选配。

### 1.6 Apple：thermalState 四档只读契约【确定度：高；表见 PM-02 不重写】

iOS thermalState 四档（nominal/fair/serious/critical）与系统单方降档哲学详见 `research/PM-02-iOS与鸿蒙省电哲学对照-v1.0.md:118-131`。
本文补三点：枚举定义 [ThermalState](https://developer.apple.com/documentation/foundation/processinfo/thermalstate-swift.enum)；
serious 档官方描述「fans run at maximum speed, system performance may be reduced」（macOS，
[Respond to Thermal State Changes](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/RespondToThermalStateChanges.html)）；
变更通知 `thermalStateDidChangeNotification`（WWDC19 Session 422 示范注册）。
**平台无公开的「每传感器温度」API，连温度都不给，只给档**——比 Android 更彻底的 severity-only 契约。

### 1.7 OpenHarmony：档位仲裁 + 动作查表【确定度：高（官方仓 raw README）】

来源：[powermgr_thermal_manager raw README](https://gitee.com/openharmony/powermgr_thermal_manager/raw/master/README_zh.md)

四模块：Thermal Manager（对应用及子系统的**温控查询及回调**）/ Thermal Service（温度检测、**档位仲裁**、动作下发）/
Thermal HDI（内核连接：驱动上报 + 指令下发）/ **Thermal Protector（非运行态简化温控——关机充电态也要有热保护）**。

配置模型（`thermal_service_config.xml`）完整展示了「传感器簇 → 档位（threshold + threshold_clr 迟滞）→ 状态（screen/charge）
→ 动作 → 策略」链路，动作空间实证：

```xml
<sensor_cluster name="warm_base" sensor="shell">
  <item level="1" threshold="35000" threshold_clr="33000"/> ... </sensor_cluster>
<policy><config name="warm_base" level="1">
  <cpu screen="1">2800000</cpu>  <cpu screen="0">2400000</cpu>   <!-- 频率帽，分亮灭屏 -->
  <current charge="1">1500</current>                             <!-- 充电限流 mA -->
  <thermal_level>3</thermal_level>                               <!-- 对 app 的档位 -->
</config></policy>
```

要点：**充电限流是热服务的一等动作**（逐档 1500/1200/1000mA 递减）；档位还与 screen/charge 状态联动（同档亮屏帽更高）；
`thermal_level strict="1"` 档位仲裁收敛策略。

### 1.8 Windows/桌面热简线【确定度：高（MS 设计指南）/中（ACPI 细节）】

来源：[Windows 硬件设计指南](https://learn.microsoft.com/en-us/windows-hardware/design/device-experiences/design-guide) ·
ACPI 6.6 第 11 章 Thermal Management（[uefi.org/specifications](https://uefi.org/specifications)）

- Windows 热管理 = ACPI `_TZ` 命名空间热区：**active cooling**（风扇，`_ACx` trip + `_PSL` 设备列表）与
  **passive cooling**（降性能，`_PSV`/`_PPC`，ACPI 自述「不产生噪音不消耗额外功率」）两类；
  Win8 起电源计划里用户可选主动/被动散热策略（中，社区指南）。
- 桌面与手机的分野：**有风扇 = 有主动制冷余量**，passive 降档更保守；无风扇移动设备被动降档是主手段。
  PM-06 已覆 EcoQoS/Power Throttling 的「谁被降档」问题（`PM-06:23,152`），本文只补热侧触发面。
- 翻车面（中）：`_TZ.TZ00` 固件热表错误/误读引发假热降频甚至休眠——**传感器数据可信性要进设计**。

### 1.9 桌面对照外一个 RT 面：idle 注入即降温【确定度：高】

[intel_powerclamp](https://docs.kernel.org/admin-guide/thermal/intel_powerclamp.html) + 通用 cpu idle cooling（LKML 2018 系列）：
把「注入空闲周期」注册成标准 cooling device，与降频帽并列——**降频降的是功率斜率，注闲直接砍占空比**，
对无风扇设备是更狠的一档。社区坑：注入不随温度回落及时停止致卡顿（thermal_daemon issue 263，中）——解除路径与迟滞同样要验收。

## §2 热↔电源耦合面（谁压谁 / 充电热预算 / 热感知 DVFS）

| 耦合问题 | 事实与裁决 | 证据 | 确定度 |
|---|---|---|---|
| throttle 与 battery saver 谁压谁 | **报告层合一**：Android 立法电池功率约束必须经 thermal HAL 上报（电源约束=热框架输入）；**动作层交叠取严**：两者最终都落 cpufreq 帽，有效值=各帽最小值（机制同 Linux freq QoS max 夹取） | [thermal-mitigation](https://source.android.com/docs/core/power/thermal-mitigation) / 机制推断 | 高（报告层）/中（动作层） |
| 热与低电量同时触发 | 两轴独立传感、独立进档；对计算侧的降档叠加生效，无「豁免热」一说——**电省不能牺牲热安全，热降不保证省电目标** | 平台行为归纳 | 中 |
| 充电时的热预算 | JEITA 充电温区五档（COLD/COOL/NORMAL/WARM/HOT）：10–45°C 全速快充；0–10°C 降流（防析锂）；45–60°C 降压降流；>60°C 或 <0°C 停充——**充电本身是主要热源，温区表是硬安全约束** | [TI slyt365](https://www.ti.com/lit/pdf/slyt365) · [JEITA 官方指南 PDF](https://home.jeita.or.jp/upload_file/20210407112651_JbDgUSWGiB.pdf) | 高 |
| 快充降档 | OH 配置实证：热档逐级把充电电流 1500→1200→1000mA；高通 monitor 规则用 `quiet_therm` 触发 battery 动作限流——**快充降档是热服务对充电服务的限流指令** | §1.5/§1.7 | 高 |
| 充电态持续热保护 | OH 专门设 Thermal Protector：系统非运行态（关机充电）也要温控——**热服务不能假设系统全活着** | §1.7 | 高 |
| 热感知 DVFS | thermal pressure 进调度容量（Linux 5.7）；IPA 直接以功率预算驱动 DVFS 状态反解——两条路都要求 EM/记账面知情 | §1.2/§1.3 | 高 |

## §4 BerryOS 启示（接口/契约/协议位/验证断言）

| # | 可执行动作 | 落点 |
|---|---|---|
| 1 | **berry-thermal 用户态常驻服务**（第 2 层，与 berry-power 同级）：订阅传感器事件 → 档位仲裁（查表 + 迟滞，OH 模型）→ 三类输出：(a) 频率帽写请求 (b) 充电限流票 (c) 对外 thermal_level 档位。PID over EM 是 v2 升级件，v1 先 step_wise 查表（保守防抖、无 EM 依赖） | 用户态服务（规则 05 服务监督域）；PM-03:221 兑现 |
| 2 | **传感器自报 trips 对齐一期「驱动自报 power levels + 唤醒延迟」先例**：热驱动经驱动自报接口上送 `(sensor_id, kind: real|virtual, temp_mc, trips[{level, threshold_mc, clr_mc}])`；事件驱动优先（对齐 Linux 中断 trip + set_trips 动态窗口），无中断传感器轮询兜底；虚拟传感器=多真实传感器加权混合，在驱动层做不在服务层做 | 驱动自报协议位扩展；规则 06/08 |
| 3 | **降档不新开通道**：berry-thermal 的频率帽与 berry-power 的帽**汇入同一内核聚合点取 min**（学 cpufreq freq QoS），聚合器是「唯一合法帽书写面」的扩展；对调度器 = 系统态叠加票（#42 语义、只叠加），对 app 侧降载引导走 intent 既有词汇表（#58），不发明第二条应用通道 | 调度策略插件输入 + 内核频率帽聚合点；`PM-02:294`/`PM-03` §8 兑现 |
| 4 | **帽生效必须同步打折记账面**（thermal pressure 等价物）：频率帽/注闲生效时，utilization·容量记账按折扣修正，防调度器「看不见帽」继续虚高预测——作为 sched-1.2 议题登记（教训 1 的直接兑现） | sched 记账面 + 遥测环；§1.3 证据 |
| 5 | **对外契约 = thermal_level u8 四档**（0=nominal/1=fair/2=serious/3=critical，4–255 保留）：只读 getattr 查询 + 订阅变更通知（复用 berry-sys 通知通道）；**severity 是承诺面，温度只进遥测不进契约**（教训 2）；无议价权写进 SDK 文档；豁免走 PM-06 教训 4 assertion 通道且 critical 档无豁免 | berry-sys ABI 只读位 + SDK 契约（自有 ABI day-one 窗口，`PM-06:141`） |
| 6 | **sim-thermal 契约位 = 传感器自报接口本身**：QEMU virt 无真温传感器，sim-thermal 做成一个普通热驱动（用户态），经同一自报接口按脚本注入温度序列（学 Android emul_temp + VTS「测试走同一接口不旁路」）；固件级 critical trip 兜底留在内核（对齐 PM governor 崩溃内核保底先例，`pm-notes/00:43`） | 驱动自报接口 + tools/ 脚本 |
| 7 | **smoke 断言四件套**（挂 just smoke）：(a) 注入温度穿 trip → N ms 内帽变化在遥测环可观测（遥测环加 THERM 臂，接 `kernel/src/telemetry.rs` 既有 64 槽切换环）；(b) 回落穿 threshold_clr → 帽解除；(c) 迟滞窗内往返温度不产生档位抖动；(d) critical 注入走短链关机路径且不依赖 berry-thermal 存活。验收叙事对齐 PM-00「QEMU 代理断言→A/B 模型账→真机」三段（`PM-00:316`） | tools/smoke + ktest 断言 |
| 8 | **充电限流进动作空间 + JEITA 温区表为第一张系统热表**：v1 即把 `charge_current_limit(level)` 定义为热服务对充电服务的票面动作（OH 同构）；JEITA 五温区硬约束表随电池驱动自报，优先级高于性能热档 | berry-thermal ↔ 充电服务 IPC 契约；§2 证据 |
| 9 | **关机充电态热保护不缺位**：Thermal Protector 同构——最小系统态的热兜底由内核 critical trip + 充电固件共同保证，不假设用户态服务活着 | 内核 trip 兜底 + 充电驱动；教训 7 |
| 10 | **热治理可审计**：档位迁移、帽变化、豁免生效全部进遥测环；预留「档位→动作」表在服务侧可 dump（对抗 override 式放水，教训 3） | 遥测环 + 服务 dump 接口 |

一句话总纲：**热与电共享动作空间、分立传感原因；对外只承诺档位不承诺温度；
帽要打得下也要被调度器看得见——berry-thermal 落第 2 层，降档汇入既有票据与帽聚合点，v1 用查表迟滞起步、PID over EM 留 v2。**
