# AM-02 应用生命周期裁数调研——回调是不是越多越好（2026-11）

> 版本：**1.0**（v1.0）｜2026-11-08｜文件名 `AM-02-应用生命周期裁数调研-v1.0.md`
> **定位**：对 BerryOS 现役「4 态 + 3 口」的设计拷问——业界证据是否支持生命周期状态/回调数继续增长？证据基座 = 本地对标报告（`research/应用规范-*对标*` 族 + AM-01）+ 三路 workflow 采集（本地挖掘/网源 Android+iOS/网源全谱）+ 主会话补抓（Android 官方文档正文 curl 剥取）。

> **与 docs/ 的关系**：只读不改——结论供规范 §4.1 / am design / SDK-2 消费。

## 问题

应用生命周期的状态数与回调数是不是越多越好？BerryOS 现役 4 态（active → freeze → tombstone → not running）+ 3 回调口（pause 注册 / state 写 / relaunch 读，规范 §4.1-5「框架代收、应用只写业务」）——这个裁数在业界谱系里站得住吗，v2 该加还是守？

## 结论（先给）

**不是越多越好。业界十五年大势是砍不是加，且回调数与 OS 机制强度成稳定反比：回调是平台机制缺位的补偿——机制越强（冻结/代收/快恢复），开发者需要感知的 lifecycle 越少。** BerryOS 4 态 + 3 口落在「新平台极小集」区间（OH 核心 4 回调 / UWP 4 / 主机 0-2），且比它们更有资格极简——因为 BerryOS 的机制面（token 冻结 / 唤醒 / 墓碑 / 压力事件）已全真码实证，正坐在反比律的强机制端。v2 扩枚举的唯一合法通道 = 「资源证据定义封闭枚举」门（本地既有律，`research/应用规范-HarmonyOS对标-2026-11.md:47`）。

## 证据与出处

### 二、反比律的三条机理证据

1. **Android freezer 冻结不派发任何生命周期回调**（A11+，freeze 级对 app 零预告——`docs/app-1实施设计草案-v1.2.md:57`）：机制吃掉了本该由回调通知的转换——直接证据。
2. **回调膨胀与机制缺位同源**：Android 因早期无冻结 → 七回调 + 五进程层 + SavedState 补救四件套（`research/PM-01:44,50`）；机制补齐后（freezer/hybernation）反而开始做减法——新回调零增、旧复杂度靠封装层收窄。
3. **最先进形态在最少了**：Fuchsia 墓碑 = VMO+pager 自然推论，仅 task-bound KB 级状态需一个写窗口（`research/AM-01:14,65`）；主机平台零回调全代收——机制谱系顶端的两端都不靠多回调。

### 三、回调数的正确度量（不是数量）

①每个回调对应 app **必须知道**的真转换（可见性 / 持久化 deadline / 资源得失）——可省则省；②**正交性**：iOS 后台 14 值弃 3 的教训；③**零义务默认**：未注册 = 默认可杀可墓碑（BerryOS 规范原话——比 OH/UWP 更激进的最低义务）；④**框架代收比例**：Flutter 引擎停帧 / 主机快照 / BerryOS「框架代收」——代收越多，回调越少。

## 对 BerryOS 的裁决建议

- **4 态 + 3 口在甜点上**：谱系对齐「新平台极小集」（OH 4 / UWP 4 / 主机 0-2），且零义务默认严于全部对标。
- **资本 = 机制面全真码**：冻结（token）/ 唤醒（wake-pending）/ 墓碑（64KiB 容器头）/ 压力事件（等页阈值）皆已实证——反比律强机制端的资格是挣来的，不是省出来的。
- **v2 扩枚举的唯一门**：新触发器（失焦 / GUI 事件 / 传感器得失）逐个过「资源证据定义封闭枚举」律——按业务命名无限生长（OH 长时任务 9→11）是明令禁止的反面形态。
- **WP 教训的映射**：极简不自动等于好——若冻结/墓碑机制的**质量**（配额/延迟/恢复连续性）不达标，回调再少也是差评；反之 Android 证明回调再多也补不动弱机制。**投入应继续压在机制侧，不是 API 面侧。**
