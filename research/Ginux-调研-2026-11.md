> **未构建、未跑 QEMU**：本机 rustc 1.97.0，Ginux 钉 1.99.0；不擅自安装新 toolchain。以下“当前能力”以仓库自述 + 测试门记录为准，不当作独立实测。

## 0. 一句话结论

Ginux 是 **x86-64、Rust `no_std`、模块化单体、以 Linux 用户态容器为工作负载** 的 UEFI 操作系统；它不是微内核，也不是 BerryOS 的同路线竞品。
对 BerryOS 的价值不在“搬内核代码”，而在四件事：**domain/capability 的授权与失效语义、boot authority 封套、HDAE 式证据门禁、以及 Linux ABI 规模的负面标尺**。

## 1. 它是什么

- 单一 `GINUX.EFI`：内核 + boot catalog + 静态链接的 ring-3 controller + recovery/组件目录，直接 UEFI 启动，无 GRUB/initramfs/宿主发行版。
- controller 是 **第一个 ring-3 进程**（Linux ABI 静态程序），通过版本化 device/ioctl UAPI 管理 domain/设备/网络/存储；不能改内核或扩大 boot 授权。
- **domain** 是原生隔离/记账/生命周期单位：进程与地址空间、capability 表、CPU/内存预算、IPC、设备/网络/文件系统授权、失败策略。
- 内核核心：调度、VM、capability、domain、IPC、IOMMU/DMA/MMIO、boot-critical 存储/文件系统/网络/主设备；Linux personality（x86-64 syscall/ELF/VFS/socket/signal）是内核内的一层。
- OCI 只作**传输与文件系统组装**，不是运行时/安全边界；镜像层 digest 校验 + content-addressed cache + writable overlay。
- 目标工作负载：Alpine musl/BusyBox、Rocky Linux 10 glibc/systemd `multi-user.target`、后续 SSH/包管理/CUDA/HPC。

### 2.1 与 BerryOS 的对照矩阵

| 维度 | Ginux | BerryOS（当前 main） | 结论 |
|---|---|---|---|
| 内核形态 | 模块化单体；VFS/网络/主驱动/OCI/crypto 在内核 | 微内核；FS/网络/驱动在用户态 | **不借 placement**；只借边界论证方法 |
| 能力 | 64 槽、4 位 rights、slot+generation、boot authority seal | handle = slot16+gen14、u64 rights、duplicate 只收紧；无 boot seal | **借 boot 授权封套/域级表**；generation 已有 |
| 隔离单位 | kernel domain（进程/AS/cap/预算/失败策略） | process/thread + handle 表 + appd；无 kernel domain | **借语义，做成用户态 AppDomain** |

## 3. 架构中最值得看的四处

### 3.1 domain + generation-tagged capability

- `kernel/src/domain.rs`：domain 有 id/generation、capability table、boot roots、CPU/内存上限、resource service class、failure policy、address-space root、parent/child。
- `kernel/src/capability.rs`：`Rights` 仅 READ/WRITE/MANAGE/EXECUTE 四位；`Handle` = `slot + generation`；`Table` 64 槽，`authorize_boot()` 是唯一无父授权入口，`seal_boot_authority()` 后只能 `derive()` 严格更小权限。
- 失效语义：generation 不匹配即拒绝；domain teardown 按 generation 回收；capability 不能通过 id 重用复活。
- 对 BerryOS：BerryOS 已有 handle generation 与纯能力；可对照的是 **“boot authority 封套 + 只能派生更小权限 + 授权来源可审计”** 这条不变量，而不是 64 槽/4 权限的小表。

### 3.2 boot authority 与 ring-3 controller

- 一个 authenticated EFI envelope 定义本次 boot 的 authority ceiling；controller 是唯一初始 ring-3 authority，只能委派/撤销，不能合成新权限。
- controller 不是 ring-0，也不是内核模块；管理面走版本化 ioctl，普通 I/O 走 Linux syscall。
- 对 BerryOS：svcmgr 已经是 ring-3 服务管理器，但“**所有运行时能力都能追溯到 boot 授权上限**”尚未成为显式不变量；可作为 v2 安全/启动 ADR 的候选。

### 3.3 IOMMU/DMA 失效序

- Q35 + VT-d：精确 root/context/四层页表，仅映射一个 DMA page；先指向 sentinel page 要求“不被写”，再验证 fault record，清 fault，最后做真实 I/O。
- 每次 service generation 重新分配 DMA/翻译表 lease；clean exit、fault、timeout、restart、corrupt-media 都要求先 quiesce 设备，再撤翻译，最后还 DMA page。
- 对 BerryOS：这正是 ADR #22（SMMU/DMA 隔离）需要的**测试形态**：sentinel + 负向 fault + revoke-before-reuse + generation lease；aarch64 可平移到 SMMU。

### 3.4 HDAE：把外部批评变成可复现门禁

- 方法固定六步：**Verify → Reproduce → Specify → Implement → Regress → Review**；一次只开一个 gate，证据落文件，完成后停下来等人审。
- 关键门禁示例：privileged entry 只用受信栈；user-copy 必须可恢复 fault；每个 writable global 必须有 owner/lifecycle/锁序，`writable-globals.tsv` 与源码精确一一对应（新增未分类 global 直接红）；SMP 前先做 ownership/synchronization；测试默认 2 vCPU，另跑 1/2/4 拓扑。
- 对 BerryOS：这套方法比“再看一遍代码”更适合 AI agent；可与现有 `docs_规则/13`、G0–G5、`unsafe_audit.py` 对接。

## 4. 可借鉴（按优先级）

### P0：只做研究，不搬代码

- 将 Ginux 固定为 `reference/ginux/` 本地快照（已 ignore），在 `reference/README.md` 记录出处/协议/边界。
- 读序与结论落 `reference/ginux/NOTE.md`；本报告作为对照材料。**不把 Ginux 加入构建/依赖/CI。**

### P1：验证方法论（低风险、直接可用）

1. **Gate 模板**：每个改动写 `Verify / Reproduce / Specify / Implement / Regress / Review` 六段，验收证据落文件；一次只开一个 gate；完成后停等人审。
2. **writable globals 清单**：给 kernel 的 `static mut`/可写全局建 manifest，CI 精确比对；新增未分类 global 直接红。BerryOS 已有 `unsafe_audit.py`，但“可写全局”是另一张网，尤其对 SMP/抢占。
3. **负向测试优先**：每个门至少一个“应该失败”的用例；Ginux 的 sentinel/fault/replay 测试是模板。
4. **基准不作弊**：同一二进制、同一 QEMU 机型/CPU/内存、固定 digest、N 次采样、公开分布；不得为 benchmark 特判。BerryOS 的 B-0/B-1/B-2 可吸收此纪律。

### P2：架构语义（需 ADR，不直接改 v1）

1. **AppDomain（用户态 domain）**：不引入内核 domain 对象；在 appd/svcmgr 侧把“一个 app + 其子进程/服务 + capability 集 + 资源预算 + 失败策略”建模成用户态 domain。可服务移动端应用沙箱/后台生命周期，且不破坏微内核。
2. **boot authority 封套**：v2 安全启动时定义“boot 授权上限”，所有运行时能力必须可追溯到该上限；与纯能力/ADR #22 同链。
3. **generation 失效贯穿 teardown**：domain/app 重启后旧 capability、旧 mmap、旧 IPC peer 一律 generation 拒绝；对照 Ginux 的“generation-bound handles + ordered teardown”。
4. **SMMU/DMA 测试形态**：sentinel page + fault record + revoke-before-reuse + fresh generation lease；先做 QEMU 可编程故障注入，不承诺真机。

### 明确不借

- **内核内 VFS/网络/OCI/crypto**：与 BerryOS 微内核五原则 1/2 冲突；Ginux 自己也承认 privileged core 比 strict microkernel 大，靠 review/W^X/fuzzing 兜底。
- **Linux ABI 全量**：53 Complete + 257 Partial 才跑到 Rocky systemd；BerryOS v1 34 syscall + 无 Linux 二进制是刻意收窄。v2 兼容若做，必须钉一个**命名 profile**（如“某发行版某 init”），不要泛化“Linux 兼容”。
- **112k 行内核 / 1,033 unsafe blocks 的规模**：不是“先进”本身；BerryOS 的 659 条 unsafe 台账已需持续治理，不能以 Ginux 规模为合理性背书。
- **x86-64 only / 单 vCPU 基线 / 未完成安全审计**：不能作为移动/aarch64/生产安全论据。
- **kernel 直接依赖 smoltcp/miniz/ed25519**：BerryOS 应继续把网络/压缩/验签放用户态或受审计的窄接口。

## 6. 对 BerryOS 的具体下一步（建议）

1. **本轮**：只保留 reference 快照 + 本报告；不改内核/构建/依赖。
2. **下一刀（文档/流程）**：把 HDAE 六步门禁模板落 `docs/规则/13-工作流程与协议.md` 的“验证门”节；给 kernel 增加 `writable-globals` 清单门禁（先只读盘点，不阻断构建）。
3. **再下一刀（架构讨论）**：在 `docs/架构决策.md` 开一条“v2 boot authority 封套 / AppDomain 用户态建模”预研 ADR，明确不引入内核 domain 对象。
4. **兼容线**：把 Ginux 的 Linux 账本作为“兼容成本证据”，支持 BerryOS v2 只做命名 profile，而不是“Linux 兼容”口号。
5. **安全线**：把 sentinel/fault/revoke-before-reuse 测试形态写进 SMMU 设计草案的验收节。
