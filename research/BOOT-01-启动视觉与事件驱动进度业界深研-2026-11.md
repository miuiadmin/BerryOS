# BOOT-01 启动视觉与事件驱动进度业界深研（2026-11）

Type: survey
Status: current
Updated: 2026-11-14

一句话说明：为「统一模拟器入口 + 引导视觉双模式（verbose 滚动日志 / 图标遮罩 + 事件驱动进度条）」立项做的六系统一手深研（Android AOSP / Plymouth / Apple XNU / Windows / OpenHarmony / 游戏机车机 + 进度条人因）与仓内现状盘点，产出 BerryOS 设计裁决弹药；六路全文见 `.agents/research/` 四份 survey（见 §7）。

## 问题

用户四条拍板（2026-11-14）：①模拟器收敛为一个入口——「一打开就是那个，没有太多东西，不要开开这一个那一个」；②打开即设备即引导，「慢慢引导、慢慢启动」——引导过程是体验的一部分；③系统两种启动模式：命令行模式 = Linux 式详细滚动启动日志、滚完进桌面；图标模式 = logo 遮罩 + 进度条；④进度条是「虚拟进度条对应真实启动事件，越细越好」，且必须多参考其他系统实现、不闭门造车。本调研回答：业界六家怎么做（进度模型、事件粒度、双模式切换、视觉交接），BerryOS 仓内现状离这一步有多远、事件源从哪来。

## 结论

### 一句话总裁决

六家证据同构收敛出三条设计铁律：**①双模式不是两套系统，是同一事件流的两种投影**（Android 属性+日志双消费 / Plymouth ESC 换主题重放日志缓冲 / Apple 同一 framebuffer 双前端）；**②进度条 = 事件锚点 + 显示端整形**，没有一家裸奔纯事件，也没有一家敢用纯假进度（Android 显示端限速 10%/s + 退出补满 100；Plymouth 时间渐近插值 + 跨启动校准；Apple 内核期伪进度 + 用户态真值接管）；**③粒度的价值不在事件数量堆料，在「真实、单调不回退、结束必达 100%」三原则**（AOSP 自己也只有约 25-30 个可见锚点）。

### 三、进度条人因设计铁律（跨系统共性 + 学术）

- **never-decrement 双权威**：Win32 UX Guide 明文「Don't back up progress… Always increase progress monotonically」+「Don't restart progress」（多阶段共用一条条只换文案）；Fluent 2「move backward → lose confidence」。工程侧同构：XNU 伪进度计数器天然单调、跨所有者只 forward；Android 显示值只增；若必须回退只重绘局部（圆角帽）不重画整条。
- **Harrison 实证（UIST 2007《Rethinking the Progress Bar》，22 人/9 函数/恒 5.5s 成对比较；勘误：任务书所记「CHI 2004/2007 / It's not nihilism」查无此文）**：结尾暂停伤害最大、加速型（Power/Fast Power）唯一显著快于线性、开头慢/停最被容忍——设计推论 = 开头缓存进度（position jump 向前补偿）+ 前慢后快 + 慢阶段排最前。XNU 的 8 档减速表（前快后慢）与该结论相反，属「永不填满」策略的另一极——两者共同点是不许结尾停死。
- **99% 停滞被 Win32 点名**（「shoot to 99% then stay」），对策族：初值至多 33%、不满格直到真完成、标签动态换任务、超 10s 给剩余时间、indeterminate→determinate 转换；Apple 内核条渐近 50% 永不填满 + 完成瞬间直接切桌面、Plymouth ShowAnimationPercent=0.9（条只映射前 90%）同为此病而生。
- **混合模型一手范本 = WebKit ProgressTracker**：初值 0.1（起跳反馈）、增量 =（0.9-当前）× 字节占比（渐近插值永不触顶）、首 layout 前上限 0.5、100ms 心跳判 stall、完成才置 1——与 Harrison 三建议同构，与 Plymouth 的 systemd 事件+插值互相印证。
- **事件跳变必须被显示端整形**：Android 的做法最简——显示值每 100ms 最多 +1%（追赶上限 10%/s），事件值跳变被天然抹平，不需要 easing 曲线与时长估算；退出时不足 100 先补满再退。
- **假进度 vs 真事件的划界（Harrison）**：已知静态总量（拷贝）不上把戏，动态粗估（安装/碎片整理）才用增强；启动事件可枚举属 bounded——**宜真事件锚点 + 区间插值**，正合 BerryOS。
- **密码/交互暂停进度**：Plymouth ask-for-password 默认先 A 暂停、答完 a 恢复——等待输入期间进度条不许空转。
- **失败即诊断**：Apple 把「卡住的位置」变成故障域语义（前半程 ≈ 内核/IO、后半程 ≈ 用户服务；noroot 专用图标 + 停条挂起）；用户报障说进度条位置、开发者直接定位对应子系统。
- **仪式感两档制**：PS5 冷启全仪式（logo→健康警告→CGI）vs rest 唤醒轻仪式（跳过 logo 与警告）是现成样板；「启动动画太短显得廉价」无任何一手证据（未证实）——时长下限是产品决策非规律，建议 BerryOS 模拟器按「冷启全引导 / 快启轻引导」两档走。
- **微软反面教训**：启动并行化后「线性百分比无法定义」，Win8+ 退到无进度 spinner——BerryOS 的事件粒度天然更细（微内核 = 每个服务一个事件），可以做微软没做到的真进度条。

### 四、仓内现状盘点（差距与可挂点）

- **内核 boot 事件链现成**：EFI 路串口标记序列 = KVA ok → FB ok → HANDOFF ok ver= → VBS ok slot= → DISP ok → ROOTFS ok src=（`kernel/src/main.rs:262-619`）+ ktest/bench 族标记（RX/RT/LATIPC/LATSGI/PAR/LB/ASIDR/TLBS/ALLOC/HT/PP/TAGTAB）；smoke 门 = 8 boot 共 83+ 标记的确定性断言。**这就是 verbose 模式与进度事件的现成词汇表**——但载体只有串口，无结构化事件总线。
- **遥测环在、boot 环不在**：调度遥测环 = per-CPU seqlock 双环（切换/唤醒）+ WAKE_SRC_TABLE（`kernel/src/telemetry.rs`），消费路径 v3 才开；**boot 事件流需要新面**（最小形：boot 环或 fw_cfg/VMO 通道把 marker 变结构化事件递给 host 与 guest GUI）。
- **svcmgr = 现成事件源**：`user/bins/svcmgr/src/main.rs`（7645 行）boot 槽位硬编码 9+ 插（console→rootfs VMO→bsh stdin→MMIO 窗→fb 窗→fb 几何→fan-out→pressure Event→VER VMO）+ spawn echo/talker/bsh/launcher + 监督重启；每个 spawn/ready 点都可发进度事件，BerryOS 可做到 30-50 个事件点（粒度超 AOSP 的 25-30）。
- **引导期视觉现状 = 黑屏**：guest 屏（ramfb）在 kernel→GUI 服务第一帧之间无输出，串口日志在 host 终端；「打开即引导」要把这段黑屏变成 verbose 滚动或 logo+进度条。
- **berry 平台 22 verb、shell 已是双击入口**：`tools/berry/src/main.rs` Cmd 枚举（Doctor/Run/Shot/Device/Power/Logs/Display/Record/Play/Shell/Vnc/…），Shell 注释即「the double-click entry」、手机比例窗口；统一入口骨架已立，缺的是「打开 = 开机引导」默认形态与两模式视觉。
- **boot 时长现实**：`berry run` marker 默认超时 30s、shot BERRYBOOT ok 120s（工具侧等待上限非实测值）；真值以仪器刀实测为准——verbose 滚动内容量与「慢慢引导」节奏需要实测后定（QEMU TCG 路径偏慢、KVM/hvf 路径更快，进度条的时间插值参数应按 profile 分档）。

### 五、BerryOS 设计裁决建议（立项弹药，待设计草案吸收）

1. **统一入口裁决**：`berry shell` = 唯一双击/打开入口（现有 CLI verb 保留为开发者面不删）；打开即开机——host 窗口先画 logo 帧（BGRT 语义：宿主直接给一张 BMP+坐标，QEMU 等价固件 splash），guest 接管 ramfb 后同帧同坐标续画，桌面 launcher 全窗口 drawn 后揭幕（Android 三件套照抄）。
2. **双模式 = 同一 boot 事件流两种渲染前端**（三家同构证据）：事件流单源（内核 marker + svcmgr 服务事件 + GUI 首帧事件），双消费者——一行结构化日志喂 verbose 滚动屏、一个进度值写喂图形模式；模式切换只是换渲染端（Cmd+V 等价键 + berry 配置等价 boot-args -v），运行中 ESC 热切换按 Plymouth 形态（重放日志缓冲）。
3. **进度模型四层合成**：分段所有权（BerryBoot 0-10% / 内核 10-40% / 服务拉起 40-80% / GUI→launcher 80-100%，Apple 式声明区间）→ 事件跳变 + 显示端限速（Android 式 10%/s 追赶上限）→ 事件间时间渐近插值兜底（Plymouth 式 scalar + berry 会话持久化跨启动校准——模拟器独有优势）→ 90% 封顶 + launcher drawn 直接揭幕（防卡 99%）。
4. **事件总线最小形**：内核 boot 环（marker 结构化：id + CNTVCT + 字符串）+ fw_cfg/VMO 通道并行递 host（berry shell 消费画进度）与 guest GUI（bootanim 等价服务消费）；词汇表沿用 smoke marker 命名（`KVA ok` 等既有断言零漂移）。
5. **verbose 滚的就是真日志**：现成串口 marker 流即 verbose 内容（Linux 式「滚完进桌面」无需造字）；GUI 服务起来后日志缓冲重放到桌面切换处，等价 vcattach/msgbuf 先例。
6. **诊断语义**：进度条位置 = 故障域（Apple 式）；berry doctor 增加「boot 事件时间线」输出（每事件毫秒差，等价 ro.boottime.* / systemd-analyze），CI 回归基线直接复用。

## 适用边界

- 未证实项照录：Pixel/OEM 的 progress 里程碑写入方不在 AOSP 树内（百分比锚点私有）；iBoot 逐百分比映射表闭源；macOS 大版本升级首启时长官方无数值；Apple silicon Cmd+V 是否生效官方无记载；OpenHarmony 调试模式 verbose 未见公开资料。
- Windows 进度权重取自 Vista/Win7 白皮书样本（2011 年），绝对值仅作形状参考。
- 本报告只出「业界怎么做 + 仓内差多远 + 设计裁决建议」；接口细节（事件 id 编码、通道选型、模式键位）属实施设计草案（`plans/` 家）的活，不在本文展开。
