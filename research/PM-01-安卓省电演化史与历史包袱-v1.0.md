## §1 演化主线：Android 电源权力「下放 → 逐步收回」的五个时代

### 1.0 一句话总纲

Android 2008 年上线时的电源模型是「**默认全速，靠 wakelock 阻止睡眠**」——把「保持清醒」的权力直接以 API 形式发给每一个 app；此后 15 年的省电史，就是平台一步步把这份权力收回、换成「受监管的通道」的历史。每一代收紧都在收上一代给多了的东西（§3 有逐条对照表）。

### 1.1 时代一（2007–2013）：无监管下放——wakelock、alarm、后台服务、常驻连接

**wakelock 的起源与设计意图**【确定度：高（API 事实）/ 中（意图转述）】

- Android 1.0（2008，HTC Dream/T-Mobile G1 上市）起，`PowerManager.WakeLock` 就是公开 SDK API（API level 1 即存在，[官方 API 参考](https://developer.android.com/reference/android/os/PowerManager.WakeLock)）。其中 `PARTIAL_WAKE_LOCK` 允许**屏幕关闭后单独保住 CPU**——app 后台轮询/通知/音乐全靠它。
- 设计意图（转述自早期 Android 内核文档与 LWN 报道）：移动 app 不可信、不可依赖它们「自己空闲」，所以内核侧发明 **opportunistic suspend（机会式挂起）**——只要没人持锁，系统**无视还有可运行进程**就整机挂起，一把大锤兜底防劣质 app 耗干电池；wakelock 是给「守规矩者」在关键段保清醒的例外口。早期 Android 移植文档（wakelock/early_suspend 机制）见[当年 source.android.com 移植文档镜像](https://wladimir-tm4pda.github.io/porting/power_management.html)。
- 问题在于：**例外口是向所有 app 无差别开放的**，且 `PARTIAL_WAKE_LOCK` 拿了不还（泄漏）或故意长持（保活）都合法——「防止劣质 app」的机制本身成了劣质 app 最大的武器（§2.1）。

**2010–2012 上游化大战**【确定度：高（LWN 一手报道）】

- Android 内核补丁（binder、logger、lowmemory killer、wakelock 等）长期 out-of-tree：2009 年底–2010 年初被 Greg Kroah-Hartman 从 staging 树整体移除，Google 一度停止上游贡献，Android 成为事实 fork，期间积怨深重（["ill will and difficult discussion" — LWN 2011-12](https://lwn.net/Articles/472984)）。
- 2011 年内核峰会意外达成「Android 代码应回 mainline」共识，同年 11 月底驱动重回 staging——但 **wakelock（suspend blocker）作为争议核心被刻意排除**："nobody seemed to want to revisit it"（[LWN: Bringing Android closer to the mainline](https://lwn.net/Articles/472984)）。
- 内核社区的反对本质：mainline 的挂起模型是「用户/电源管理器发起 + 冻结全部任务」，而 Android 模型是「内核随时自动挂起 + 特权用户态可持锁否决」，等于把内核电源策略做成了用户态 ABI；且唤醒事件在进入挂起途中可能丢失（竞态）。mainline 先以 wakeup events（2.6.36）/wakeup sources（2.6.37）补底层（[LWN: Autosleep and wake locks](https://lwn.net/Articles/479841)）。
- 2012-02，Rafael Wysocki 发布 autosleep + wake_lock/wake_unlock sysfs 补丁：复用 wakeup source 基础设施、API 刻意模仿 Android 原接口，他自嘲「**推销一个曾被拒绝的功能，最容易的办法是给它换个名字**」——opportunistic suspend 改叫 autosleep 重新出道（[LWN 2012-02](https://lwn.net/Articles/479841)、[LKML 2012-04-22](https://lkml.org/lkml/2012/4/22/105)）。
- **结论**：公案以「语义全盘获胜、名字全部换掉」告终——`kernel/power/wakelock.c`（版权 2012 Wysocki）至今在 mainline（[torvalds/linux](https://github.com/torvalds/linux/blob/master/kernel/power/wakelock.c)），Android 用户态接口跑在 mainline wakeup source 之上。教训：**争的不是机制而是 ABI 主权与策略归属**。

### 1.2 时代二（2013–2014）：第一代收紧——alarm 批处理与 Project Volta

- **Android 4.4 KitKat（2013）**：`set()`/`setRepeating()` 对 targetSdk≥19 的 app **默认变为不精确+成批**（把多个 app 的闹钟对齐合并唤醒），精确闹钟需显式改用新 API `setExact()`（[Android 4.4 APIs](https://developer.android.com/about/versions/android-4.4.html)、[官方闹钟指南](https://developer.android.com/develop/background-work/services/alarms)）。这是平台第一次单方面降级已发布 API 的语义——「**精确唤醒从默认变成例外**」的开端。
- **Android 5.0 + Project Volta（2014-06 Google I/O 宣布）**：三大件——① `JobScheduler`：把可延迟后台工作交给系统**按充电/WiFi/空闲等条件合批调度**；② **Battery Historian** 归因工具首秀（见 §2.4）；③ 系统级省电模式（Battery Saver）。Ars Technica 实测 Android L 续航提升约 36%（Nexus 5，[Ars Technica 2014-07](https://arstechnica.com/gadgets/2014/07/examining-project-volta-we-put-android-l-through-our-battery-test)、[9to5Google: Project Volta](https://9to5google.com/guides/project-volta)）。

### 1.3 时代三（2015–2017）：强制代——Doze 三连击

- **Android 6.0（2015）Doze + App Standby**：设备息屏+静止+未充电即进 Doze，期间**无视（ignore）app 的 wakelock**、暂停网络、**连 `setExact()` 也被推迟到维护窗口**；只有 `setAndAllowWhileIdle()`/`setExactAndAllowWhileIdle()` 可逃逸且**每 app 每 9 分钟限一次**；JobScheduler/同步适配器/WiFi 扫描全部冻结；维护窗口随时间拉长变稀（[官方 Doze 文档](https://developer.android.com/training/monitoring-device-state/doze-standby)）。App Standby 则按「用户不碰+无前台进程+无通知」判 app 空闲，空闲 app 长期闲置时每天只给一次网络。**这是平台第一次公开宣布『以前发给你的 wakelock 作废』**。
- **Android 7.0（2016）**：① Doze on the go——去掉「静止」条件，口袋里晃着也进轻量 Doze；② 砍隐式广播：`CONNECTIVITY_ACTION`、`ACTION_NEW_PICTURE/VIDEO` 不再发给 manifest 注册的接收器——**事件驱动唤醒这个类别被连根削**（[Android 7.0 行为变更](https://developer.android.com/about/versions/nougat/android-7.0-changes)）。
- **Android 8.0（2017）**：① 后台 app 不能再自由 `startService`（几分钟后被停，导向 JobScheduler）；② **manifest 注册隐式广播接收器整体被禁**（少数豁免清单除外）——「一次广播唤醒全机 app」的模式终结（[官方后台执行限制](https://developer.android.com/about/versions/oreo/background)）。

### 1.4 时代四（2018–2021）：ML 代与收权提速

- **Android 9.0（2018）App Standby Buckets + Adaptive Battery**：按使用模式把 app 分入 Active/Working set/Frequent/Rare 四档桶，**桶决定网络/任务/闹钟/FCM 的限额**；Adaptive Battery 与 DeepMind 合作，端上 ML 预测「你接下来会用哪个 app」，Google 称对「不太会用」的 app CPU 唤醒减少约 30%（[官方电源管理文档](https://developer.android.com/about/versions/pie/power)、[Android Developers Blog 2018-09](https://android-developers.googleblog.com/2018/09/moar-power-in-android-9-pie-and-future.html)、[Google 官宣](https://blog.google/products-and-platforms/platforms/android/introducing-android-9-pie)）。
- **Android 12（2021）**：① 引入 `SCHEDULE_EXACT_ALARM` 特殊权限——精确闹钟从「默认可用」变「需声明」；② **app 从后台启动前台服务（FGS）被限制**；③ 引入 **app freezing**：cached 进程可被整体冻结（cgroup freezer，类 iOS 墓碑化）（[Android 12 行为变更](https://developer.android.com/about/versions/12/behavior-changes-12)）。
- **Android 13/14（2022–2023）**：13 增 `USE_EXACT_ALARM`（闹钟/日历类专属、随装随授、Play 政策审核）；14 对 targetSdk≥13 的新装 app **默认拒发** `SCHEDULE_EXACT_ALARM`，且 FGS 必须**声明类型**（camera/location/media… 每类型单独权限）、后台禁止启动敏感类型 FGS、Play 上架需申报 FGS 类型清单（[Android 14 精确闹钟变更](https://developer.android.com/about/versions/14/changes/schedule-exact-alarms)、[Android 14 FGS 类型](https://developer.android.com/about/versions/14/changes/fgs-types-required)、[Play FGS 政策](https://support.google.com/googleplay/android-developer/answer/13392821)）【FGS 类型细节确定度：高】。Android 15 进一步给 dataSync 类 FGS 加 6 小时运行上限【确定度：中】（[Android 15 行为变更](https://developer.android.com/about/versions/15/behavior-changes-15)）。至此，**精确唤醒、常驻服务、后台启动三大逃生口全部装上门禁**。

### 1.5 时代五（2023–）：平台收权终局与量化罚则

- 2025-11，Google 把「**过量 partial wakelock**」指标移出 beta：**24 小时内累计非豁免 wakelock >2 小时即记为不良行为**，进入 Play 可见性与分发的考核面（[Android Developers Blog 2025-11](https://android-developers.googleblog.com/2025/11/raising-bar-on-battery-performance.html)、[Android vitals](https://developer.android.com/google/play/vitals)）。
- 平台侧的最终形态收敛为：**默认冻结（无执行）+ 例外经权限化通道（FGS 类型/精确闹钟权限/FCM 高优先级）+ 度量罚则（vitals）**——即 iOS 2009 年就有的模型，Android 用了约 15 年、经 7 代系统逐步迁回（对照 [Apple 应用生命周期：后台转 suspended](https://developer.apple.com/documentation/uikit/managing-your-app-s-life-cycle)【确定度：中】、[Android 12 app freezing](https://developer.android.com/about/versions/12/behavior-changes-12)）。

## §2 关键事实与证据（URL + 确定度）

### 2.1 电池杀手之一：partial wakelock 滥用与「卡死锁」

- 学术研究对大规模 Android 应用的分析表明 wakelock 误用（泄漏、过长持有）普遍存在，是系统性问题而非个案（[ACM FSE'16：Understanding and Detecting Wake Lock Misuses for Android Applications](https://dl.acm.org/doi/pdf/10.1145/2950290.2950297)）【确定度：高（论文实证）】。
- 官方为此专设「**stuck partial wake locks**（卡死部分唤醒锁）」质量概念与文档，把「app 后台长持锁→设备进不了深睡」列为头号可诊断耗电形态（判档阈值：后台 24h 内累计 ≥1h 即报 stuck）（[官方：Stuck partial wake locks](https://developer.android.com/topic/performance/issues/stuck-wakelock)、[Android vitals: Excessive partial wake locks](https://developer.android.com/google/play/vitals/excessive-wakelock)）【勘误 2026-11-07：本条原写「过夜掉电 20%+」，该定量值在上述两官方页均不存在，已删——两页只给机制与判档阈值，无掉电百分比】。
- 2025-11 起量化罚则：24h 内非豁免 wakelock 累计 >2h = 不良行为会话；系统自身有明确用途的 wakelock 豁免（[Android Developers Blog 2025-11](https://android-developers.googleblog.com/2025/11/raising-bar-on-battery-performance.html)）。
- **机制根源**：`PARTIAL_WAKE_LOCK` 是无限期租约、无预算、无归因压力——一个 API 形状决定了十五年的对抗面。

### 2.2 电池杀手之二：alarm 风暴与精确闹钟的十年权限化拉锯

| 时间 | 平台动作 | 动机/后果 | 源 |
|---|---|---|---|
| ≤2013 | `set()` 精确即发，app 各自为政 | N 个 app 各按各的周期唤醒整机 = alarm 风暴 | [闹钟指南](https://developer.android.com/develop/background-work/services/alarms) |
| 2013（4.4） | 默认批处理化，`setExact()` 成例外入口 | 唤醒对齐合并；targetSdk<19 的老 app 保持旧行为（碎片化开始） | [4.4 APIs](https://developer.android.com/about/versions/android-4.4.html) |
| 2015（6.0） | Doze 连 `setExact` 也推迟到维护窗口 | 逃逸口 `setExactAndAllowWhileIdle` 限 9 分钟/次/app——**配额制雏形** | [Doze 文档](https://developer.android.com/training/monitoring-device-state/doze-standby) |
| 2021（12） | `SCHEDULE_EXACT_ALARM` 特殊权限引入（默认仍授予） | 精确唤醒开始「按身份发证」 | [SO 汇总](https://stackoverflow.com/questions/71031091/android-12-using-schedule-exact-alarm-permission-to-get-show-data-at-specific-t) |
| 2022–23（13/14） | 13 增 `USE_EXACT_ALARM`（闹钟/日历类专属）；14 新装 app 默认拒发 `SCHEDULE_EXACT_ALARM` | 精确闹钟 = 特权：要么是身份（应用类别）要么是用户明示批准 | [Android 14 变更](https://developer.android.com/about/versions/14/changes/schedule-exact-alarms) |

【确定度：高（均为官方文档）】轨迹清晰：**默认免费 → 批处理降级 → 空闲时作废 → 配额限流 → 权限化 → 默认拒绝**——六步走了十年，每一步都伴随开发者迁移之痛与「闹钟不响」的用户回归。

### 2.3 电池杀手之三/四：后台常驻与心跳长连接（含微信案例）

**心跳长连接的物理账**【确定度：高（官方机理）+ 中（具体数值）】

- TCP 长连接会因中间设备 NAT 表项超时被静默掐断，故需周期心跳维持；每发一次心跳，蜂窝网就要重建无线资源、走一遍信令——**心跳是流量极小但信令成本极高的操作**（[52im：微信智能心跳机制](http://www.52im.net/thread-120-1-1.html)）。
- 各网络 NAT 超时实测差异巨大：移动 2G/3G ≈5 分钟、联通 2G ≈5 分钟、电信 3G >28 分钟、WiFi ≈15 分钟——固定心跳只能按最短网络取值，白白多跳（同上，52im 整理的运营商实测表）。
- **微信智能心跳**：客户端自动探测当前网络 NAT 超时上限、在安全边界内取最长间隔逐步逼近；心跳间隔 5→10 分钟信令量减半，拉到 20+ 分钟减约 80%（[52im thread-120](http://www.52im.net/thread-120-1-1.html)）——这是 app 在「无统一推送可用」约束下的自救最优解。
- **代价外溢到运营商**：2013 年中移动统计微信占其约 **60% 信令资源却只贡献约 10% 流量**，「信令风暴」引发收费之争，腾讯随后推 2G/2.5G 心跳优化与「新一代动态心跳」（[搜狐财经 2013-04](https://business.sohu.com/20130411/n372292524.shtml)、[第一财经](https://m.yicai.com/news/2617979.html)、[人民网](http://www.people.com.cn/24hour/n/2013/0326/c25408-20922692.html)）【确定度：中（媒体报道口径，量级可信）】。
- GCM 自身也非零成本：官方通道同样分钟级心跳，社区长期受「心跳太稀→推送延迟」「太密→耗电」两头夹（[SO：GCM heartbeat](https://stackoverflow.com/questions/19560448/how-to-avoid-delay-in-android-gcm-messages-change-heartbeat)、[eladnava.com](https://eladnava.com/google-cloud-messaging-extremely-unreliable)、[HeartbeatFixerForFCM](https://github.com/grimseraph/HeartbeatFixerForFCM)）【确定度：中】。

**FCM 为什么省电——官方机理**【确定度：高（官方文档原文）】

> 「FCM 提供一条到云端的**单一持久连接**，所有需要实时消息的 app **共享**这条连接……多个 app 各自维持长连接会迅速耗干电池」（[官方 Doze 文档](https://developer.android.com/training/monitoring-device-state/doze-standby)）。

即省电机理 = **心跳合并**（N 条连接 N 份心跳 → 1 份）+ 射频唤醒合并（一次无线电唤醒服务所有 app 的下行）+ 与 Doze 联动（高优先级消息临时放行网络与 wakelock，送达即收回）。

**统一推送通道横向对照**【确定度：中（生态侧）/ 高（官方机理）】：

| 系统 | 常备唤醒通道 | 谁持连接 | 通道可用时 app 自建连接的动机 | 源 |
|---|---|---|---|---|
| Android（海外） | FCM 单一持久连接 | Google Play 服务（系统级） | 基本为零——官方文档明确劝退自建长连接 | [Doze 文档](https://developer.android.com/training/monitoring-device-state/doze-standby) |
| iOS | APNs | 系统 | 为零（后台无执行能力，自建无意义） | [Apple 生命周期](https://developer.apple.com/documentation/uikit/managing-your-app-s-life-cycle) |
| Android（中国大陆） | 厂商通道 ×N（联盟 UPS 标准化中） | 各 ROM 系统服务 | 高——通道碎片化+到达率不确定，头部 app 仍保留长连接兜底 | [维基：统一推送工作委员会](https://zh.wikipedia.org/zh-hans/%E7%BB%9F%E4%B8%80%E6%8E%A8%E9%80%81%E5%B7%A5%E4%BD%9C%E5%A7%94%E5%91%98%E4%BC%9A)、[MixPush](https://github.com/taoweiji/MixPush) |
| BerryOS 目标态 | 系统推送服务唯一长连接 | 用户态网络服务（B4） | 结构性为零（app 无自建通道的权限面） | 本报告 §4 |

**中国对照：GCM 缺位 → 各 app 自建长连接的灾难与补课**【确定度：中（生态事实，二手源）】

- Google 服务在国内不可用 → FCM 合并红利为零，头部 app 人手一条长连接（微信/QQ/淘宝/微博……），耗电与信令双重灾难（背景见[统一推送联盟成立报道](https://www.jiguang.cn/tips/859)）。
- 2017-10-16 信通院联合华为/小米等 75 家企业成立**统一推送联盟**，制定 UPS 标准；2021-06 覆盖 OPPO/vivo/小米/三星等 15 品牌，华为/荣耀完成适配，并纳入信通院 CMS 体系（[维基百科：统一推送工作委员会](https://zh.wikipedia.org/zh-hans/%E7%BB%9F%E4%B8%80%E6%8E%A8%E9%80%81%E5%B7%A5%E4%BD%9C%E5%A7%94%E5%91%98%E4%BC%9A)、[百度百科：统一推送联盟](https://baike.baidu.com/item/%E7%BB%9F%E4%B8%80%E6%8E%A8%E9%80%81%E8%81%94%E7%9B%9F/22165880)）。
- 但**碎片化未根治**：厂商通道各自为政，app 要么集成 N 个厂商 SDK（如 [MixPush](https://github.com/taoweiji/MixPush) 聚合 6 家），要么继续保活长连接兜底——「统一推送」在 2017 年才开始补 iOS/FCM 2009–2013 年就已完成的课。

### 2.4 工具面：batterystats / Battery Historian 与功耗归因

- 标准链路：`adb bugreport` → **Battery Historian**（Google 开源，2014 年随 Project Volta 面世）时间线可视化系统/app 级事件、单 app 电力统计、逐个 wakelock（需 `dumpsys batterystats --enable full-wake-history`）、内核 `wakeup_source_activate` 唤醒追踪、外接 Monsoon 功率计数据叠图；要求 Android 5.0+；2022-12 仓库归档只读（[google/battery-historian](https://github.com/google/battery-historian)、[Project Volta 发布报道](https://9to5google.com/guides/project-volta)）。
- 快速侧：`dumpsys batterystats`（设备端直接读累计 wakelock 时长/唤醒计数），Play 侧 vitals 聚合田野数据（excessive wakeups / stuck wakelocks 等不良行为口径）（[Android vitals](https://developer.android.com/google/play/vitals)、[excessive wakeups 文档](https://developer.android.com/topic/performance/issues/wakeup)）。
- 归因模型：Android 用 `power_profile.xml` 组件电流估值（屏幕/WiFi/蜂窝各态 mA 值）折算各组件与各 app 的 mAh 责任【确定度：中】（[AOSP Power values 文档](https://source.android.com/docs/core/power/values)）。
- **教训**：Battery Historian 面世（2014）晚于 wakelock 面世（2008）六年——**归因工具缺席的年份正是滥用野蛮生长的年份**；「why is my battery dead」直到内核导出 `prevent_sleep_time` 类统计才可回答（[LWN 479841](https://lwn.net/Articles/479841)）。

### 2.5 军备竞赛：国产 ROM 杀后台 vs 开发者保活黑科技【确定度：中（社区一手汇编 + 仓库 README）】

- **保活黑科技谱系**（开发者侧，因「通知收不到=用户流失」而刚需化）：1 像素透明 Activity（锁屏拉起提优先级）、无声音乐（占音频通道扮前台）、双进程互拉（AIDL 互相 restart）、`START_STICKY`、前台服务+取消通知（灰色保活）、以及现代组合拳；开源汇编 [KeepLiveService](https://github.com/Pangu-Immortal/KeepLiveService) 收录 35+ 种策略、覆盖 Android 7.0–16 与 10+ 家厂商 ROM，本身就是一部对抗史（另见[掘金综述](https://juejin.cn/post/7444215159264772115)）。
- **厂商侧反制**：MIUI/EMUI/ColorOS 等自启动管理、关联启动拦截、激进杀后台与类墓碑冻结——杀得更狠则 app 保活更烈，形成「**契约失守→双方加码**」的死循环；根因是平台通道缺失（推送不可靠）+ 权力早已下发（wakelock/服务）收不回来。
- **平台的终局答案**是收回执行权本身：Android 12 起对 cached app 直接 cgroup 冻结（不再靠杀），配合 FCM 高优先级作唯一常备唤醒通道（[Android 12 行为变更](https://developer.android.com/about/versions/12/behavior-changes-12)、[Doze 文档 FCM 节](https://developer.android.com/training/monitoring-device-state/doze-standby)）。

## §3 教训与历史包袱清单

### 3.1 每一代在收上一代给多了的什么（因果链）

| 上代给多的权力 | 滥用形态 | 收回动作 | 代价 |
|---|---|---|---|
| wakelock 无限租约（2008） | stuck wakelock、过夜掉电 | Doze 无视锁（6.0）→ vitals 罚则（2025） | 正规场景（音乐/导航/IM）十五年间反复被误伤，豁免清单越列越长 |
| 闹钟默认精确（2008） | alarm 风暴 | 批处理（4.4）→ Doze 推迟（6.0）→ 权限化（12/14） | 「闹钟不响」用户回归；exact alarm 权限博弈延续至今 |
| 后台自由起服务（2008） | 常驻进程遍地 | 8.0 服务限制 → 12/14 FGS 类型化+启动限制 | 迁移成本巨大；保活黑科技产业兴起 |
| manifest 隐式广播（2008） | 一次广播全机苏醒 | 7.0 砍三个 → 8.0 整体禁 | 生态大量功能依赖旧模式，碎片化 targetSdk 迁移拖了五年+ |
| 各 app 自建长连接（GCM 缺位区） | 心跳×N、信令风暴 | 无平台解（中国）→ 联盟 UPS（2017） | 国内耗电与到达率问题延续十年，厂商各自为政至今 |
| app 一律平权（2008–2018） | 长尾 app 搭便车常驻 | 9.0 桶 + Adaptive Battery | ML 误判（偶尔用的 app 被限）；预测依赖历史行为 |

### 3.2 历史包袱（至今仍背着的）

1. **API 兼容性税**：`setExact`/`setAndAllowWhileIdle`/FGS 类型/exact alarm 权限……每个补丁 API 都永久进入 SDK，开发者要按 targetSdk×版本×厂商三维矩阵编程（[闹钟指南](https://developer.android.com/develop/background-work/services/alarms)、[FGS 政策](https://support.google.com/googleplay/android-developer/answer/13392821)）。
2. **信任崩塌的旁观者税**：厂商不再信任 app（激进杀后台），app 不再信任系统（保活），用户不再信任两者（手动管后台）；三方都在为对方的越界付费。
3. **不可逆下放**：wakelock 类 API 一旦发布就无法真正回收语义，只能叠加「无视层」（Doze ignore wake locks）——**平台最终不得不在执行层之上再造一个否决层**，复杂度永久化（[Doze 文档](https://developer.android.com/training/monitoring-device-state/doze-standby)）。
4. **度量迟到的十年**：田野级耗电度量（vitals）2025 年才成罚则；此前「谁耗电」在用户/开发者/厂商之间是罗生门（[Android Developers Blog 2025-11](https://android-developers.googleblog.com/2025/11/raising-bar-on-battery-performance.html)）。
5. **上游化公案的协同成本**：Android 内核 fork 期（2010–2012）整条生态（芯片厂/手机厂）维护 out-of-tree 电源代码多年；ABI 主权之争的代价由全行业分摊（[LWN 472984](https://lwn.net/Articles/472984)）。

### 3.3 规律提炼

- **R1 权力下放容易、回收极贵**：每一个「给 app 的自由」最终都要用「否决层+权限+配额+度量」四件套赎回，历时 5–15 年。
- **R2 形状决定命运**：无限期租约（wakelock）、免声明精确性（alarm）、免类型常驻（service）——API 形状本身就是滥用面，事后补丁改不了形状只能打补丁。
- **R3 缺席的统一通道会被民间自建**：没有官方推送 → N 条心跳长连接；没有官方归因 → 野路子耗电诊断；通道要 day-one 存在，晚十年就是十年灾难。
- **R4 默认值即生态**：默认批处理/默认冻结/默认拒绝精确——生态跟随默认值，例外走权限；反过来（默认精确、默认常驻）则万劫不复。
- **R5 度量先于治理**：能量化才可治理；归因工具与罚则是契约的执法部分，不是锦上添花。
- **R6 收权必先给出路（例外通道要成对出现）**：Doze 限网的同时给 FCM 高优先级；限精确闹钟的同时给 `setAndAllowWhileIdle` 配额——只收不给的收紧会造成「闹钟不响」级用户回归，逼平台反复回退。
- **R7 否决层是技术债**：在已下放的权力之上叠「无视层」（Doze ignore wake locks、冻结层、豁免清单）而非改 ABI 形状，导致每代机制都完整保留、叠加运行——最终复杂度由平台、开发者和用户三方永久分摊。day-one 无此债。
- **R8 生态缺位没有局部解**：中国厂商各自修推送、各自杀后台，本质是在「无统一通道」的地基上做局部补丁，结果是 N 个补丁互不兼容（app 集成 N 个 SDK）；架构级缺失只能架构级补。

## §4 BerryOS 启示（具体到接口/契约/协议位）

> 前提对齐：BerryOS 能力即权限（内核态 handle）、机制在内核/策略在用户态、tickless、intent（u8）第一类输入、ADR #53 已有 GUI 停帧三态与 PM 共享环协议位。以下每条都映射一个安卓教训，避免空话。

| # | 契约建议（day-one 定死） | 对应安卓教训 | 具体落点 |
|---|---|---|---|
| B1 | **app ABI 里没有裸 wakelock**。「保持清醒」只能申请**带截止时间的完成窗口**（deadline wake-window，类比 ADR #53 的 vote 区间票面：有理由、有区间、自动过期），到期自动收回；持有者必须是用户态服务，app 经 IPC 请求 | wakelock 无限租约 → stuck wakelock 产业（§2.1） | syscall 面：不设 `wake_lock/unlock` 对；改为 `wake_window{reason, deadline_ms}` 单向申请；内核 PM 服务统一记账 |
| B2 | **唤醒归因 day-one 内建**：每次 PM 唤醒记录「谁唤醒了谁、耗了多少」进 PM 共享环（ADR #53 六件套已留位），暴露 `power attribution` 只读接口 | Battery Historian 迟到六年；`prevent_sleep_time` 才回答「谁耗的电」（§2.4） | 与能耗代理断言（ADR #53）合并；进 G4/G5 验收断言：**无主唤醒 = 测试失败** |
| B3 | **定时唤醒三档 + 配额**：默认批量对齐（batched，idle 世代合并放行，对应 maintenance window）；对齐窗（window）；精确（precise）= 能力位 + 每 app 每 idle 世代配额（借鉴 9 分钟/次/app 的教训但 day-one 化）+ 遥测计费 | alarm 六步十年拉锯（§2.2） | berry-sys 定时器 API 只暴露三档；precise 档走能力即权限，默认零配额 |
| B4 | **系统推送/唤醒通道是唯一常备网络长连接**：网络服务（用户态）代持长连接+智能心跳（吸收微信智能心跳：按网络 NAT 特性自适应），app 收推不建连；基带/射频唤醒是计费资源（PM 共享环可见） | FCM 合并机理 + 中国 60% 信令/10% 流量灾难（§2.3） | net 服务契约：`push_subscribe(cap, filter)`；心跳策略在服务侧可 OTA 调优而非每 app 自带 |
| B5 | **事件订阅无 manifest 等价物**：订阅=运行时能力+租期+自动退订；系统事件（网络变化/时间变化）只投递给持有效租约者，无「一次广播全机苏醒」面 | 7.0/8.0 砍广播之战（§1.3） | IPC 通知（异步通知面）按订阅句柄投递；订阅带 TTL；进程死=订阅灭 |
| B6 | **后台进程默认冻结而非杀死**：cache 态进程 cgroup-freezer 语义（挂起全部执行，状态保留），因 B4 保证通知可达，app 无保活动机 | Android 12 才到 app freezing；此前十年杀后台大战（§2.5） | 服务监督域（规则 05）加 freeze op；冻结进程的 IPC 投递排队到解冻——保活黑科技的 1px/无声音乐/双进程全部无意义 |
| B7 | **耗电预算与 intent 联动**：调度器 admission/budget（sched-1.1 已有）扩展「wake admission」——每 app 每世代唤醒次数与 wakelock 等价时长有软预算，超预算降档（对应 bucket 但用确定性规则而非 ML，保留 ML 为用户态策略可插拔层） | 9.0 桶 + Adaptive Battery（§1.4）；vitals 2h/24h 罚则（§2.1） | u8 intent 六档词汇表（ADR #58）与 wake 预算同一命名空间；只叠加不覆盖（公平默认铁律） |
| B8 | **精确性/常驻性都要「身份」**：闹钟类（用户可见定时任务）与前台常驻（导航/音乐）在应用清单里 day-one 声明为能力类别，安装时用户可见——事后无需 12/14 式翻旧账 | exact alarm 权限化与 FGS 类型化是十年补课（§1.4） | berry-sys 应用 manifest 增 `precise_timers`/`persistent_role` 能力位；缺失者三档定时自动落到 batched |
| B9 | **契约面进 AI 测试友好化（G0–G5）**：把「无主唤醒零容忍」「后台零周期活动」「心跳单连接」写成可机检断言，smoke 即测 | 安卓的度量全部后置（§3.2-4） | 新增 PM smoke 档：idle 世代唤醒数上限断言 + 归因环非空断言 |

**与既有材料的关系**：B1/B3 的「票面+区间」与 GUI-06 §1.4 停帧三态、ADR #53 damage/vote/power·mode 同构——**全系统统一为「声明需求区间、系统合批决策」的一票制**，而非 app 直控硬件（与「上层只投票，不直接设频设帧率」的带内纪律同源）；B4 心跳自适应下沉为系统服务后，GUI-06 的 PSR/停帧只管显示侧，本篇管射频/唤醒侧，二者在 PM 共享环汇合。

### 4.1 落地顺序建议（挂到现有里程碑节奏，不另起炉灶）

| 阶段 | 先做 | 理由（对应教训） |
|---|---|---|
| 现在（G1–G2 间） | B2 归因环 + B9 smoke 断言雏形 | 度量先于治理（R5）；等生态长出来再补 = Battery Historian 六年空窗重演 |
| 网络服务立项时 | B4 唯一长连接 + 心跳自适应 | 通道 day-one 存在（R3）；一旦头部 app 自建长连接成事实标准就再也收不回（R1） |
| berry-sys ABI 冻结前 | B1 唤醒窗口 + B3 三档定时 + B5 订阅租约 + B8 能力类别 | ABI 形状即命运（R2）——这四项一旦定错形状，后续只能走 Android 的否决层路线（R7） |
| 多应用生态成形前 | B6 默认冻结 + B7 wake 预算 | 保活军备竞赛的窗口期在「生态成形之前」（R8） |
