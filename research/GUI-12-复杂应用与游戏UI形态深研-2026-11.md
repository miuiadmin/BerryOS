# GUI-12 复杂应用与游戏 UI 形态深研（2026-11）

> **定位**：回答一个架构级问题——BerryOS 同时面向移动端与 PC 端，界面从简单设置页到 Photoshop 级专业软件、AAA 游戏和大型创作工具，是否应由同一个 UI 框架包揽？立项时本文是研究报告与路线建议，不修改当时 F0..F9 出口门；裁决后现行执行序按 [GUI框架地基路线-v1.10.md](../docs/GUI框架地基路线-v1.10.md) 插入 P0 Surface Mode。
>
> **触发**：用户提出移动端与 PC 端共存、简单程序与复杂程序共存、未来可能出现 3A 大作和 Photoshop 级软件；要求深研开源工业级先例，并判断 BerryUI/Berry Session/Berry Room 的支撑边界。
>
> **生成方式**：主线直接抓取专业 DCC 源码，并汇总三路子研究（跨平台 UI 框架、游戏/实时 UI、OS 图形分层），覆盖四个角度。搜索工具在本会话不可用；关键一手来源改由官方源码仓库、Gitiles、Gitee 与官方文档原文抓取。证据标注：**直证** = 本轮抓到官方源码/协议原文；**核证** = 子研究用 curl 抓取官方页面原文；**推断** = 由多案例归纳，不是来源原文。
>
> **裁决结果（2026-11-08）**：用户确认采纳本文 §15 建议；ADR #67 与 [GUI框架地基路线-v1.10.md](../docs/GUI框架地基路线-v1.10.md) 已落地“一个系统契约，多个 UI 形态”，并在 F5 后、F6 前新增 P0 Surface Mode 协议门。

## §1 执行结论

1. **开源工业级先例存在，而且很强**：Photoshop 级软件可对标 Blender、GIMP、Krita、Inkscape；实时编辑器/游戏可对标 Godot、Bevy、Dear ImGui、egui；跨平台工业工具包可对标 Qt、GTK、Flutter。它们足以回答架构问题。
2. **没有一个成功系统用单一控件库包揽“简单移动应用 + 专业桌面工作台 + AAA 游戏 UI”**。Qt 甚至长期维护 Qt Widgets 与 Qt Quick 两套控件栈，共享平台与渲染地基。
3. **“支持复杂软件”不等于“所有界面都由 BerryUI 控件绘制”**。产业共识是：OS 固化窗口/surface/输入/IME/无障碍/帧率/安全契约；控件工具包只是可选层。
4. **专业应用的主流形态是“工具包外壳 + 自绘 canvas”**：GIMP/Krita/Inkscape 用 GTK/Qt 组织面板、对话框、停靠区，但文档画布自持事件、文档模型与渲染管线。
5. **游戏运行时 UI 几乎全部自绘在游戏帧内**，不使用 OS 控件。OS 提供全屏/immersive surface、输入、IME、系统覆盖层、帧率意图、安全区和无障碍旁车。
6. **Blender 是“大型专业软件自绘 UI”的成功极端**：它没有采用通用桌面控件栈，而是自持编辑器 UI、窗口/面板系统和 GPU 抽象。这说明专业创作工具可以作为 OS 上的独立工具包/引擎存在，但不说明系统普通 app 也应如此。
7. **OS 级必须统一的是契约，不是视觉控件**：窗口角色、surface/buffer 生命周期、输入焦点、IME、无障碍语义树、DPI/安全区、帧率/功耗、系统覆盖层、进程死亡清理。
8. **BerryUI 应保持“单 core + 多形态组件集 + 逃生门”**：当前移动触摸件继续做；未来 PC 专业件可在同一 core 上另建组件集；游戏/高帧率不走 BerryUI 控件，直接走 Berry Room 的 surface/present 契约。
9. **Berry Session/Berry Room 是关键支撑层**：BerryUI 可以被替换或绕过，但 Berry Session 的合成/输入/焦点/层序契约与 Berry Room 的 per-app surface 契约不能被绕过。
10. **当前 F4/F5 不需要扩范围**：先把移动组件和 UI 系统验收 app 做稳。报告建议在 F5 后单独立 ADR 定形“UI 形态与 Surface Mode”，不在组件刀里夹带游戏或桌面工作台。

## §2 复杂度模型：五类界面不是同一种问题

| 级别 | 形态 | 典型 | UI 树规模 | 帧模型 | 输入重点 | 关键资源 |
|---|---|---|---|---|---|---|
| C0 | 系统壳/覆盖层 | Berry Home、状态栏、音量、锁屏 | 中 | 按需/damage | 全局焦点、系统手势 | 壁纸、图标、状态资源 |
| C1 | 简单 utility | Settings、开关、列表 | 小-中 | RUN/SETTLE/IDLE | 触摸/键盘焦点 | 少量文本图标 |
| C2 | 内容/记录应用 | Files、Contacts、Photos | 中 | 列表滚动/图片解码 | 触摸、滚动、选择 | 文件、图像、分页 |
| C3 | 专业工作台 | Photoshop、GIMP、Krita、Inkscape | 大：停靠、树表、命令面板、插件面板 | 静态外壳低频 + canvas 高频 | 键盘快捷键、精确指针、手柄/笔、IME | 文档模型、撤销栈、插件、大资源缓存 |
| C4 | 沉浸式游戏/实时应用 | AAA、模拟器、视频、3D viewer | UI 可能少，但每帧变 | 持续 RUN，帧率意图 | 手柄、键盘、鼠标、触摸、低延迟 | GPU 资源、世界状态、音频、网络 |
| C5 | 创作工具/引擎编辑器 | Blender、Godot editor、IDE | 极大：节点图、时间线、属性面板、嵌入 viewport | 外壳 + 实时 viewport 双频 | 命令面、快捷键、拖拽、脚本插件 | 文档、脚本、渲染目标、资源浏览器 |

结论：C1/C2 与 C3/C4/C5 的差异不是“控件更多”，而是：

```text
输入范式不同：触摸 vs 键盘/指针/手柄/笔
帧模型不同：空闲停帧 vs 文档 canvas/游戏帧持续更新
数据模型不同：页面状态 vs 文档/世界/节点图
扩展模型不同：静态应用 vs 插件/脚本/资产管线
渲染逃生门不同：控件树 vs 专用 canvas/游戏 renderer
```

因此一个控件库可以在 C1/C2 上最优，但不应强行成为 C3/C4/C5 的唯一渲染路径。

## §3 开源工业案例总表

| 案例 | 开源/许可 | UI/窗口形态 | 文档/实时画面 | 对 BerryOS 的启示 |
|---|---|---|---|---|
| Blender | GPL，大型工业 DCC | 自绘编辑器 UI、自持布局/面板/按钮/主题 | GPU module 支持 GL/Metal/Vulkan 等后端 | 超大型专业工具可以自成一整套 UI；OS 只需给它窗口、输入、surface 与 GPU 契约 |
| GIMP | GPL | GTK 外壳、dock/dockable 面板 | GimpDisplayShell + GimpCanvasItem | 专业软件可用通用工具包做外壳，画布仍是专用模型 |
| Krita | GPL | Qt Widgets/QDockWidget 外壳 | KisCanvas2 适配 QPainter/OpenGL canvas | “Qt 面板 + QOpenGLWidget canvas”是专业绘画软件典型形态 |
| Inkscape | GPL | GTKmm 外壳与事件控制器 | 自持 CanvasItem/CanvasPrivate，Cairo 表面与区域 | 矢量文档不能塞进普通控件树；画布事件与重绘策略独立 |
| Qt | LGPL/商业 | Widgets 与 Qt Quick 两套控件栈 | Quick scene graph + QRhi；Widgets 有 Graphics View | 工业级工具包也承认桌面专业件与声明式移动件分层 |
| Flutter | BSD | 单声明式框架 + engine | CustomPainter/Texture/PlatformView 逃生门 | 单框架可跨端，但专业桌面件与游戏仍需要低层逃生门 |
| Godot | MIT | Control 节点保留树 + Theme | RenderingServer canvas item，UI 在 3D 之上 | 编辑器与游戏 UI 可同核，但这是引擎内 UI，不是 OS 控件 |
| Dear ImGui | MIT | 即时模式调试/工具 UI | 输出 renderer-agnostic draw list | 极佳调试 overlay；官方不把它定位为成品游戏 UI |
| egui | MIT/Apache | Rust 即时模式 + ID 缓存 + AccessKit | 可集成 wgpu/glow，`requires_repaint` 支持按需重绘 | 即时模式的合法生态位是工具/调试，不是系统主 UI |
| Bevy | MIT/Apache | ECS 保留实体 + Taffy 布局 | bevy_ui_render 专列 UI pass，可渲到纹理 | 引擎 UI 与渲染图深度绑定；OS 只接收最终 surface |
| Android | AOSP | View/HWUI 可选；NativeActivity/Vulkan 可直绘 | SurfaceFlinger 合成所有 surface | 游戏绕控件，但不绕 surface/input/IME/a11y/帧率契约 |
| Fuchsia | BSD 等 | Flutter 只是 runner，不是特权系统 UI | Flatland 2D 组合协议 | 系统提供多进程组合契约，工具包可替换 |
| Wayland | MIT | 工具包多样 | wl_surface + role + xdg_shell | 窗口角色、configure/ack、frame feedback 是通用地基 |
| OpenHarmony | Apache-2.0 | ArkUI + Rosen | XComponent/NativeWindow 供游戏与自绘 | XComponent 是“绕控件不绕契约”的直接开源样例 |

## §4 专业软件案例深读

### 4.1 Blender：自绘工业 UI 的极端成功样本

直证来源：

- [blender/editors/interface/interface.cc](https://github.com/blender/blender/blob/main/source/blender/editors/interface/interface.cc)
- [blender/gpu/intern/gpu_context.cc](https://github.com/blender/blender/blob/main/source/blender/gpu/intern/gpu_context.cc)

源码事实：

```text
interface.cc 直接包含 GPU_matrix/GPU_state/UI_interface，
widget 绘制使用 GPU blend/scissor/matrix；
gpu_context.cc 按 GL/Metal/Vulkan/Dummy 后端创建 GPUContext。
```

这说明 Blender 的 UI 不是宿主桌面控件，而是编辑器自己保留并绘制的一套专业界面。它的价值在于：

```text
复杂工作台可以自己拥有 UI 系统；
插件/脚本可以按 operator/panel/context 组织；
专业 UI 可以和文档/渲染器同进程深度协作；
```

但它不能推导成：

```text
BerryOS 普通 app 也应手写 UI；
BerryUI 应内置 Blender 级节点图/动画时间线；
系统控件应承担 3D DCC 的编辑器界面；
```

Blender 的正确对应位置是：未来作为一个 Berry Room 客户端，使用专业/immersive surface 与完整键盘、笔、手柄、IME、无障碍契约。

### 4.2 GIMP：GTK 工作台 + 自定义显示 shell

直证来源：

- [app/widgets/gimpdock.h](https://github.com/GNOME/gimp/blob/master/app/widgets/gimpdock.h)
- [app/widgets/gimpdockable.h](https://github.com/GNOME/gimp/blob/master/app/widgets/gimpdockable.h)
- [app/display/gimpdisplayshell.h](https://github.com/GNOME/gimp/blob/master/app/display/gimpdisplayshell.h)

源码事实：

```text
GimpDock 继承 GtkBox，包含 GimpDockbooks；
GimpDockable 继承 GtkBin，把其他 widget 变成可停靠面板；
GimpDisplayShell 继承 GtkEventBox，内部持有 GimpCanvas 与 GimpCanvasItem。
```

模式：

```text
GTK：主窗、菜单、dock、对话框、状态条
GIMP 自定义：显示 shell、canvas item、工具事件、文档投影
```

这是“通用控件外壳 + 专业画布核心”的经典形态。

### 4.3 Krita：Qt 停靠面板 + QPainter/OpenGL 双 canvas

直证来源：

- [libs/ui/canvas/kis_canvas2.h](https://github.com/KDE/krita/blob/master/libs/ui/canvas/kis_canvas2.h)
- [libs/ui/opengl/kis_opengl_canvas2.cpp](https://github.com/KDE/krita/blob/master/libs/ui/opengl/kis_opengl_canvas2.cpp)
- [plugins/dockers/historydocker/HistoryDock.h](https://github.com/KDE/krita/blob/master/plugins/dockers/historydocker/HistoryDock.h)

源码事实：

```text
KisCanvas2 不是最终 widget，而是适配器；
它可创建 QPainter canvas 或 OpenGL canvas；
KisOpenGLCanvas2 继承 QOpenGLWidget；
HistoryDock 继承 QDockWidget 并观察 canvas。
```

模式：

```text
Qt shell：主窗、dock、面板、设置
Krita canvas：坐标变换、投影、笔刷轮廓、OpenGL 纹理、显示色彩管理
```

这证明专业绘画软件不需要“整个应用都是自定义控件”。它需要的是：可靠桌面控件外壳 + 高性能、可替换的专业 canvas。

### 4.4 Inkscape：GTKmm 外壳 + 自持矢量 CanvasItem

直证来源：

- [src/ui/widget/canvas.cpp](https://gitlab.com/inkscape/inkscape/-/blob/master/src/ui/widget/canvas.cpp)
- [src/ui/interface.cpp](https://gitlab.com/inkscape/inkscape/-/blob/master/src/ui/interface.cpp)

源码事实：

```text
Canvas 使用 gtkmm event controller/key/motion/scroll/gesture；
内部维护 CanvasItem 树与 Cairo ImageSurface/Region；
注释明确列出 redraw_all/redraw_area/request_update/on_idle/on_draw 与事件 pick 流程。
```

模式：

```text
GTKmm：窗口、对话框、控件
Inkscape Canvas：矢量文档、控制项、重绘区域、命中 pick
```

Inkscape 进一步证明：专业文档不能简单映射为按钮/列表控件树。文档对象模型、canvas item 树和 UI 控件树应分层。

## §5 工业工具包案例深读

### 5.1 Qt：双控件栈，共享平台与渲染地基

直证来源：

- [qtwidgets-index.qdoc](https://github.com/qt/qtbase/blob/dev/src/widgets/doc/src/qtwidgets-index.qdoc)
- [qtquick scene graph](https://github.com/qt/qtdeclarative/blob/dev/src/quick/doc/src/concepts/visualcanvas/scenegraph.qdoc)
- [qrhi.h](https://github.com/qt/qtbase/blob/dev/src/gui/rhi/qrhi.h)

事实：

```text
Qt Widgets 明确定位 classic desktop-style UI；
Qt Quick 使用 QML/scene graph，可跑 OpenGL/Vulkan/Metal/D3D；
QRhi 抽象 Vulkan/OpenGLES/Metal/D3D 等图形 API。
```

启示：

- 桌面专业件与移动声明式件可以共享平台抽象、文本、输入、无障碍、渲染后端。
- 但控件范式不必强行统一。
- Qt 的“双栈税”也真实：主题、IME、无障碍、控件 API 需要分别适配。

### 5.2 Flutter：单声明式框架 + 明确引擎/嵌入层

直证来源：

- [Flutter Engine architecture](https://github.com/flutter/flutter/blob/main/docs/about/The-Engine-architecture.md)

事实：

```text
Framework 提供 widgets/hit-test/gesture/a11y/text input；
Framework 组合 scene；
Engine 负责 rasterizing composited scenes；
Embedder 对接渲染 surface、输入、无障碍与平台事件。
```

Flutter 的启示：

```text
声明式框架可以有强一致性；
引擎/嵌入层必须与 OS surface/input 契约对接；
复杂内容仍需要 CustomPainter/Texture/PlatformView 类逃生门。
```

### 5.3 GTK/GSK、Slint、Avalonia 的共同点

核证/档证归纳：

```text
GTK4：控件 snapshot 成 GskRenderNode，渲染器可换；
Slint：声明式 item 树 + femtovg/Skia/software renderer；
Avalonia：XAML 控件树 + Skia/合成线程。
```

共同结论：

```text
控件层与渲染层分离；
专业/嵌入/桌面/移动的控件集取舍不同；
低层 surface 或自绘节点是一等逃生门；
无障碍与 IME 不能事后硬补。
```

## §6 游戏/实时 UI 案例深读

### 6.1 Godot：引擎内保留树 UI

直证来源：

- [Godot UI tutorial](https://docs.godotengine.org/en/stable/tutorials/ui/index.html)
- [Control class](https://docs.godotengine.org/en/stable/classes/class_control.html)

事实：

```text
Godot UI 由场景树中的 Control 节点组成；
文档区分 content controls 与 layout controls；
Godot 也可用来做非游戏 application；
主题、anchor、container 是引擎内 UI 体系。
```

启示：

```text
游戏引擎可以自带完整 UI 工具包；
编辑器和运行时 UI 可以共享控件系统；
这不等于 OS 控件应进入游戏帧；
Godot 对 BerryOS 来说是一个未来客户端，不是 BerryUI 的模板。
```

### 6.2 Dear ImGui：调试与工具生态位

直证来源：

- [Dear ImGui FAQ](https://github.com/ocornut/imgui/blob/master/docs/FAQ.md)

官方 FAQ 明确：

```text
可以写严肃工具：game editors、debuggers、profilers；
它主要面向 dynamic tool/debug UI；
它不是为成品游戏用户界面设计的；
输出是 renderer-agnostic meshes/draw commands，由宿主后端渲染。
```

启示：

```text
即时模式适合调试 overlay、性能面板、内部工具；
不适合 BerryOS 主应用 UI 与低功耗桌面；
可留作未来 Berry DFX 工具或引擎调试层。
```

### 6.3 egui：即时模式 + ID 缓存 + AccessKit

直证来源：

- [egui README](https://github.com/emilk/egui/blob/master/README.md)

事实：

```text
egui 可集成到游戏引擎；
每帧布局，但 requires_repaint 支持交互/动画时才重绘；
通过稳定 ID 保留滚动/窗口状态；
eframe 可接 AccessKit。
```

启示：

```text
即时模式不是完全不能做无障碍；
关键是稳定语义身份；
静态系统 UI 仍应选保留树/damage 路线。
```

### 6.4 Bevy：ECS 保留实体 + 渲染图 UI pass

直证来源：

- [bevy_ui Cargo.toml](https://github.com/bevyengine/bevy/blob/main/crates/bevy_ui/Cargo.toml)
- [bevy_ui_render/render_pass.rs](https://github.com/bevyengine/bevy/blob/main/crates/bevy_ui_render/src/render_pass.rs)
- [render_ui_to_texture.rs](https://github.com/bevyengine/bevy/blob/main/examples/ui/render_ui_to_texture.rs)

事实：

```text
bevy_ui 依赖 Taffy 与 AccessKit；
UI 有独立 render pass；
UI 可渲染到纹理并贴在 3D 场景上。
```

启示：

```text
引擎 UI 与渲染图同帧序；
UI 可以作为世界纹理，而不仅是屏幕覆盖层；
这类需求不能通过 OS 控件树满足。
```

### 6.5 AAA 游戏的通用模式

推断 + 商业引擎对照：

```text
游戏 HUD/菜单通常由引擎或中间件自绘；
游戏世界与 UI 常在同一帧图/交换链中提交；
OS 只接收最终 surface，不识别每个 HUD 按钮；
系统覆盖层、IME、无障碍、权限对话框仍由 OS 合成在上层。
```

因此 BerryOS 的正确游戏支撑不是“BerryUI 游戏控件库”，而是：

```text
immersive/fullscreen Room surface；
低延迟输入；
帧率意图与 present credits；
安全区/DPI；
IME composition；
可选 a11y semantic sidecar；
系统 overlay 层；
```

## §7 OS 分层先例

### 7.1 Android：NativeActivity 证明“绕控件不绕契约”

直证来源：

- [SurfaceFlinger.h](https://android.googlesource.com/platform/frameworks/native/+/refs/heads/main/services/surfaceflinger/SurfaceFlinger.h)
- [native_activity.h](https://android.googlesource.com/platform/frameworks/native/+/refs/heads/main/include/android/native_activity.h)
- [Choreographer.java](https://github.com/aosp-mirror/platform_frameworks_base/blob/master/core/java/android/view/Choreographer.java)
- [Surface.java](https://github.com/aosp-mirror/platform_frameworks_base/blob/master/core/java/android/view/Surface.java)

关键事实：

```text
NativeActivity 给游戏/native activity 提供 ANativeWindow 与 AInputQueue；
仍有窗口创建/resize/redraw/content insets/input queue/soft input 回调；
Choreographer 协调 input、animation、drawing 与 vsync；
Surface 是 compositor 管理的 buffer handle，并支持 frame rate intent；
SurfaceFlinger 管理层、frame timeline、合成与硬件组合。
```

启示：

```text
游戏可以不用 View/HWUI；
但不能绕开窗口、surface、输入、IME、无障碍、帧率与安全契约。
```

### 7.2 Fuchsia：Flatland 的 2D 组合契约

直证来源：

- [flatland.fidl](https://fuchsia.googlesource.com/fuchsia/+/refs/heads/main/sdk/fidl/fuchsia.ui.composition/flatland.fidl)

关键事实：

```text
Flatland 提供布局、transform、image/buffer collection、Present；
OnNextFrameBegin 提供 present credits 与下一帧信息；
OnFramePresented 提供到屏反馈；
Viewport/layout 信息携带 logical size 与 device pixel ratio。
```

历史教训（仓内 GUI-05 与 Fuchsia RFC-0162 共同指向）：

```text
过度通用 3D 场景图让 2D 产品与硬件 overlay 都受挫；
Flatland 收敛为 2D/组合器友好协议。
```

对 BerryOS：

```text
Berry Session 不应变成通用游戏 3D 场景图；
它应是安全、可组合、可反馈的 2D surface/window 协议。
```

### 7.3 Wayland：role、configure 与 frame feedback

核证来源：

- [Wayland core](https://wayland.app/protocols/wayland)
- [xdg-shell](https://wayland.app/protocols/xdg-shell)
- [presentation-time](https://wayland.app/protocols/presentation-time)
- [commit-timing](https://wayland.app/protocols/commit-timing-v1)

模式：

```text
wl_surface 只有获得 role 后才成为有用窗口/弹出/层；
xdg_toplevel 通过 configure/ack_configure 协商状态；
presentation-time 回报真实到屏时间；
commit-timing 允许提交不早于目标时间。
```

启示：

```text
窗口状态是双段协商，不是客户端单方面声明；
frame feedback 是 OS 契约；
系统 UI 层与应用层需要不同 role。
```

### 7.4 OpenHarmony：XComponent 是最接近 BerryOS 的样例

核证来源：

- [NativeWindow](https://gitee.com/openharmony/docs/blob/master/zh-cn/application-dev/graphics/native-window-guidelines.md)
- [XComponent](https://gitee.com/openharmony/docs/blob/master/zh-cn/application-dev/ui/napi-xcomponent-guidelines.md)
- [DisplaySync](https://gitee.com/openharmony/docs/blob/master/zh-cn/application-dev/graphics/displaysync-overview.md)
- [自绘无障碍](https://gitee.com/openharmony/docs/blob/master/zh-cn/application-dev/ui/ndk-accessibility-xcomponent.md)
- [自绘 IME](https://gitee.com/openharmony/docs/blob/master/zh-cn/application-dev/inputmethod/use-inputmethod-in-custom-edit-box-ndk.md)

关键事实：

```text
XComponent 面向游戏/自绘画面；
SURFACE 与 TEXTURE 分别对应独立合成分层与并入 UI 纹理；
NativeWindow 是 buffer queue producer；
DisplaySync 把 UI/XComponent/自绘期望帧率纳入整机 LTPO 决策；
自绘编辑框接 IME Kit；
自绘内容通过 AccessibilityProvider 上报语义树。
```

这对 BerryOS 极重要：

```text
“游戏/专业画布不走 ArkUI 控件”与“必须守 OS 契约”是同时成立的。
```

## §8 产业收敛出的架构不变量

### 8.1 OS 必须统一

```text
窗口角色与生命周期
surface/buffer 所有权
damage/present/release
输入焦点与事件路由
键盘/手柄/触摸/指针抽象
IME composition 与编辑矩形
无障碍语义树旁车
DPI/scale factor/safe area/rotation
帧率意图、credits、present feedback
系统 overlay 与权限 UI
进程死亡清理与安全隔离
```

### 8.2 控件工具包可以分化

```text
移动触摸件：大目标、手势、低功耗、主题一致
桌面专业件：菜单、快捷键、停靠、树表、虚拟化、命令面板
嵌入/工业件：高密度仪表、可靠状态、长生命周期
游戏 UI：引擎内自绘，与渲染帧同序
调试 overlay：即时模式可接受
```

### 8.3 专业应用必须有 canvas/surface 逃生门

产业同构原语：

```text
Android SurfaceView / TextureView
OpenHarmony XComponent SURFACE / TEXTURE
Windows SwapChainPanel
Qt QQuickFramebufferObject / RHI item
Flutter Texture / PlatformView
```

BerryOS 对应未来应有两个模式：

```text
独立合成分层 surface：canvas/游戏最终帧由 Berry Session 合成
并入 UI 纹理 surface：canvas 作为 BerryUI 树里的一个纹理节点
```

### 8.4 无障碍不是控件库私有问题

即使应用完全自绘，也必须能上报：

```text
角色 role
文本 label
位置 bounds
状态 state
动作 actions
焦点/选区/文本范围
```

Android AccessibilityNodeInfo 与 OpenHarmony XComponent a11y Provider 都证明：自绘应用不能因为“不用控件”就退出无障碍系统。

### 8.5 IME 是 OS/应用边界问题

专业软件与游戏都可能自绘文本框，但：

```text
组合字符串
候选窗定位
光标矩形
选区
提交/取消
软键盘显隐
```

必须由 Berry Room/Berry Session 协议承载，而不是每个游戏各造一个输入法通道。

## §10 BerryUI 的职责边界

## 10.1 BerryUI 应该做

```text
一个可靠 core：
保留树、布局、状态失效、命中、主题、文本测量、诊断

多个组件集：
当前移动/触摸组件集
未来可选桌面专业组件集

关键模型缝：
焦点/键盘导航
文本编辑与 IME 消费
虚拟化列表/树/表
命令与快捷键语义
surface/canvas 节点
a11y 语义树
```

## 10.2 BerryUI 不应该做

```text
不直接持有 WM endpoint
不收发 WM RPC
不映射 VMO
不计算 frame stride
不做游戏引擎
不强制游戏 HUD 使用系统控件
不承诺所有第三方 UI 框架都改写成 BerryUI
不把 Photoshop 文档塞进 UI 树
不把插件脚本塞进 BUI
```

## 10.3 未来桌面专业件不是推翻现有 core

现有 BerryUI core 的方向是正确的：

```text
保留树适合低功耗普通 UI；
布局/命中/damage 可测试；
主题 token 已单源；
AST/ViewSpec 是数据；
诊断 dump 可支撑 AI 测试。
```

未来桌面专业件需要的是：

```text
另一个组件集 + 输入模型 + 虚拟化 + 停靠布局
```

而不是另一套渲染/状态引擎。Qt 的教训是“共享地基，分化控件”，不是“所有东西两套全栈”。

## §12 资源与规模问题

### 12.1 UI 树 ≠ 文档对象树

大型软件的正确分界：

```text
BerryUI：面板、按钮、菜单、属性表、状态
App document model：图层、节点、矢量对象、音频 clip、undo/redo
Canvas renderer：可见文档区域、tile、纹理、缓存
Asset system：图片、字体、shader、音频、网络资源
```

不要把十万个矢量对象或百万游戏实体放进 BerryUI 保留树。

### 12.2 虚拟化是专业件刚需

未来桌面件必须有：

```text
virtual list
virtual tree
virtual table
property grid
command palette
lazy panel construction
```

否则 UI 树规模会压垮布局与失效。

### 12.3 系统资源单源，应用资源归属应用

系统侧继续单源：

```text
字体
基础图标
主题 token
图像解码基础件
```

应用侧自持：

```text
大文档
插件资源
游戏纹理/网格/shader
项目资产缓存
```

两者通过 Berry Room 能力与资源 id 协作，不能回到每个 app 复制系统资产。

## §13 对当前 BerryOS 路线的裁决建议

## 13.1 不改变当前路线

F4/F5 仍按原目标执行：

```text
F4：移动组件第一版
F5：UI 系统验收 app
```

不在 F4 中夹带：

```text
桌面 Dock
专业树表
游戏 API
immersive mode
BUI 语法
```

理由：

```text
组件未稳时先扩形态，会造成三套半成品；
当前 rootfs 与内存余量极小；
协议应先设计再实现；
F0..F9 的地基纪律仍然正确。
```

## 13.2 F4/F5 期间只需守三个缝

1. **不要把移动几何写死在 core**
   - 组件消费 ThemeMetrics。
   - 布局 core 不知道 phone/desktop。

2. **不要把 a11y 做成控件私有**
   - role/label/bounds/action 词表应能服务自绘 sidecar。

3. **不要把文本输入做成单行控件私有**
   - 未来必须能映射到 IME composition 与选区模型。

## 13.3 F5 后建议新增 P0 专项

建议名称：

```text
P0：UI 形态与 Surface Mode 协议
```

出口：

```text
ADR：一个 OS 契约，多 UI 形态
Surface role/mode 词表
immersive/fullscreen 语义
safe area + scale factor
input class + focus chain
IME composition sidecar
a11y sidecar
game/pro canvas escape hatch
host 测试与协议拒面
```

实现可以后置，协议面先定。

## §14 风险与反面清单

| 风险 | 后果 | 对策 |
|---|---|---|
| BerryUI 包揽一切 | 游戏延迟高、控件 API 膨胀、低功耗模型被破坏 | Surface mode + 游戏直连 Berry Room |
| OS 过度场景图化 | Fuchsia Scenic 旧路：2D 产品和硬件 overlay 都受挫 | Berry Session 保持 2D 组合与窗口契约 |
| 专业件延迟补焦点/IME/a11y | 桌面件返工，Wayland/GTK 式欠债 | core 词表和 sidecar 先留缝 |
| 每个控件集复制输入/主题/文本 | Qt 双栈税放大 | core 共享，组件集分化 |
| 把文档对象塞进 UI 树 | 布局爆炸、虚拟化失效 | 文档模型独立 + canvas surface |
| 游戏绕过 Berry Room 获得屏写权 | 安全、焦点、死亡清理全部失守 | 屏写只归 Berry Session；app 只拿 surface 能力 |
| BUI 变成脚本语言 | 副作用/权限/热更新失控 | BUI 仅描述结构，逻辑留 Rust |
| 过早做桌面 Dock/树表 | F4/F5 质量被稀释 | P0 后单独立项 |

---

## §15 最终建议

BerryOS 的 UI 架构应该写成一句：

> **一个 Berry Session/Berry Room 系统契约，多个可选 UI 工具包和渲染路径；BerryUI 是默认声明式工具包，不是所有应用的强制渲染器。**

具体分层：

```text
简单应用：
BerryUI 触摸组件集

PC 专业应用：
BerryUI desktop/pro 组件集 + CanvasSurface

游戏/实时应用：
immersive Berry Room surface + app/engine renderer

调试/工程工具：
BerryUI 或即时模式 overlay

系统壳：
Berry Session 专属 layer surface + BerryUI/专用 renderer
```

这就是“支持简单界面，也支持 Photoshop 级软件和 3A 游戏”的正确解释：

```text
不是用一个控件库画所有东西；
而是让所有形态共享同一个安全、输入、合成、帧率、无障碍与资源契约。
```
