## 1. boot 全链：从加电到用户态 init（问题 ①）

**固件形态 = 真 UEFI 链 + 自制 loader，不是 ELF 直启（但 ELF 直启保留为兜底）。** swift-os 的 loader 是约 750 行 C 的自制 UEFI 应用（boot/efi/loader.c:1-19 头注：「Built as an AArch64 PE32+ EFI application (\EFI\BOOT\BOOTAA64.EFI) and launched by UEFI firmware (QEMU + AAVMF/edk2). It replaces QEMU's `-kernel` shortcut」）。它不依赖 gnu-efi 或 EDK2 头——boot/efi/efi.h:1-8 自述「We do not depend on gnu-efi or the EDK2 headers. UEFI on AArch64 uses the ordinary AAPCS64 calling convention」：自制最小 EFI 接口切片，只声明用到的结构，偏移按 UEFI 规范手写。构建用 clang `--target=aarch64-unknown-windows`（COFF）+ `lld-link -subsystem:efi_application -entry:efi_main -nodefaultlib` 产 PE32+（Makefile:3733-3737；NOTES.md M10a 节）。验签能力编译进 loader 本体：SHA-256 与 Ed25519 verify 是两个 header-only 自包含实现（boot/efi/loader_sha256.h:1-7、loader_ed25519.h:1-9——TweetNaCl 形态、从内核已测 kernel/crypto 移植、RFC 8032 向量宿主可测），信任根公钥经 boot/efi/efi_pubkey.S `.incbin build/image_trust_root.bin` 嵌入——与内核 trust_root.S 焊的是同一个公钥文件（efi_pubkey.S:1-9）。

**完整链条（加电 → init）：** ① 加电，固件（QEMU AAVMF/edk2 或 Hetzner 真机固件）按可移动介质默认引导序扫到 ESP 的 \EFI\BOOT\BOOTAA64.EFI 并加载（Makefile:332-335 注释：无独立 NVRAM vars store，AAVMF 默认 boot order 扫 removable media）。② loader efi_main 先勘测环境：从 Configuration Table 按 GUID 找 FDT 指针与 ACPI 2.0 RSDP（loader.c:117-125、542-551）、GetMemoryMap 报告最大可用 RAM 区（loader.c:553-572）、GOP 查线性帧缓冲（loader.c:574-593）。③ 读 ESP 上的 SWOSKERN v4 双槽 manifest 并逐槽验 Ed25519 签名（loader.c:286-328），读 SHA-256 保护（不签名）的 kernel-state 可变选择器（loader.c:377-406），执行 attempt 回退决策：未确认且 attempt ≥ 3 的活动槽让位 fallback（loader.c:647-659，KS_MAX_ATTEMPTS=3）。④ load_slot 把选中槽的 kernelA/B.bin 读入固定物理地址 KERNEL_LOAD_ADDR（QEMU virt = 0x40080000，loader.c:33-35）并整镜像 SHA-256 复核（loader.c:428-468）；签名无效的槽直接跳过、坏槽回落另一槽（loader.c:663-675）；全失败则回落 loader 内嵌 kernel blob（kernel_blob.S `.incbin`，loader.c:705-719）——U1g-1 的设计纪律是「ESP 文件路径永不比嵌入式 blob 更不可靠」（NOTES.md U1g-1 节）。⑤ H3 路径：再从 ESP 读 base.img 进 2GiB 以下 RAM 作 ramdisk（AllocateMaxAddress 限顶，loader.c:476-511）——这是给「内核不驱动引导盘控制器」的板子（Hetzner VM 引导盘是 virtio-scsi）准备的：固件 SimpleFileSystem 代读，内核零块驱动即可挂只读 base FS（loader.c:163-169 注释；NOTES.md H3 节）。⑥ GetMemoryMap + ExitBootServices（失败重试一次），daifset 关中断，跳内核入口，寄存器约定 x0=DTB、x1-x3=帧缓冲三元组、x4/x5=ramdisk base/size、x6=ACPI RSDP（loader.c:728-748）。⑦ 内核 boot.S `_start`：x0-x6 存 x19-x25、park 非零亲和核、装栈、归一化 CPU 状态——「We may be entered with the MMU and caches ON (a UEFI loader hands off that way) or OFF (QEMU -kernel)」，强制 sctlr_el1 清 M/A/C/I 位把两条路收敛到同一 MMU-off 起点（kernel/arch/aarch64/boot.S:1-52）。⑧ kernel_main（main.swift:1270-1286）：uartInit → ramdiskInit → platformInit（ACPI 优先于 DT——真机 Hetzner 固件无 FDT）→ heap/MMU/PMM → vfsInit（其内部先跑 updateStoreInit 选 base A/B 槽，updatestore.swift:75）→ espProbe（U1g-4a，main.swift:1521）→ 网络/USB/tty → runInit spawn 用户态 /bin/swos-init（main.swift:1057-1077），无头服务器路径（virtio-gpu 无串口输入）直通 init 起 sshd（main.swift:1553-1573 interactiveConsole 决策注释）。

**为什么选这条链：** 演化证据明确——早期就是 QEMU `-kernel` ELF 直启（boot.S 头注第一行仍写「aarch64 boot stub for QEMU `virt`…QEMU loads us via `-kernel`」），M10 里程碑把它迁到真固件 + GPT 盘（NOTES.md:3809-3811 M10 目标原文；M10b 节注明「Highest risk is the UEFI handoff (M10)…the `-kernel` path stays as a fallback until UEFI is stable」）。迁移动因有三：真机兑现（Hetzner ARM VM 只有固件引导，无 `-kernel` 捷径——12 号已记其真机 nginx 部署）；loader 承载验签选槽（U1g-3b 把镜像签名信任根做进引导层，kernel-state 让运行时激活免重签 manifest，loader.c:170-172、622-633）；以及 Hetzner 引导盘 virtio-scsi 内核不驱动，固件路径让 base.img 以 ramdisk 形态过墙（H3）。内核本身仍是位置依赖 flat bin 链接在固定物理地址（kernel.ld:1-10：「The image is position-dependent…must be linked at the physical address the loader places it」，QEMU virt 0x40080000 / VirtualBox ARM 0x08080000 由 Makefile `--defsym` 切换）——这是与 BerryOS ELF 解段装载的关键形态差异（见 §5）。

## 2. 整盘镜像布局：GPT 分区与可刷镜像组装（问题 ②）

**两条镜像产线，对应两个时代。** 早期双盘形态（M10c/U1g，2026-06）：scripts/make-disk.sh 造 96MiB 单分区 GPT 盘——sgdisk 建 ESP（sector 2048 起，type EF00），mtools 以 `image@@offset` 字节偏移访问填 FAT32，全程免 mount 免 root（make-disk.sh:1-8 头注 + M10c 节）；ESP 内容五件套由 Makefile `uefi` 目标 staging：\EFI\BOOT\BOOTAA64.EFI、\EFI\swift-os\{kernelA.bin, kernelB.bin, kernel-boot, base.img}（Makefile:3805-3810）。kernelA/B.bin 不是裸内核而是零垫片到 KERNEL_SLOT_BYTES = 4 MiB 的定长槽文件——目的有二：FAT 写入器只做同尺寸原地写（无 FAT/目录增长），且每槽签名条目覆盖定长区域，宿主与机上安装器垫片方式一致才保证 SHA-256 对拍（Makefile:3745-3757 注释）。base 盘是独立 SWOSBASE 签名镜像，作为第二 virtio-blk 盘挂给内核（Makefile:304-308）。

**现行单盘形态（system-disk，2026-10-31，Hetzner 真机装机）：** tools/systemdisk.swift 一件工具组装三分区 GPT 整盘（systemdisk.swift:44-65）：P1 = ESP，LBA 2048 起 256MiB（EF00，FAT32 via mformat/mcopy）；P2 = base A/B store，紧跟 ESP，容量 = store.img 向上取整 MiB，私有类型 GUID `53574F53-424F-4F54-8000-000000000001`；P3 = data 数据分区，默认 1GiB，GUID `...0002`，首扇区写 `SWDATAFS` 魔数（systemdisk.swift:54-62；docs/SYSTEM_DISK.md Layout 表）。store.img 先由 tools/updatestore.swift 造好再整体 dd 进 P2：SWOSBOOT manifest 双缓冲写在 LBA 0/1、LBA 2-7 保留、slot 0 自 LBA 8 起、slot 1 紧随，manifest 记录每槽 base_lba/length_sectors（tools/updatestore.swift:4-21 布局注释；124-127 槽位计算）。Makefile 端到端配方（Makefile:4799-4803）：`updatestore build/system-store.img A $(BASE_IMG) $(BASE_IMG) --slot-bytes 134217728 --slot-a-version 1 --slot-b-version 1 --min-version 1` 然后 `systemdisk` 合成 build/swift-os-system.img——双槽同灌 prod base.img、槽容量 128MiB 预留增长、初始反回滚地板 1。工具自带防呆：拒绝设备路径与已存在输出文件（systemdisk.swift:34-36），完成后 sgdisk --verify。另有第三产物 build/hetzner-update-store.img（外挂 Volume 形态的 store 盘，Makefile:3823-3827 hetzner-update-store 目标）。

**内核侧读盘面：** kernel/fs/gpt.swift 是手写 bounded GPT 解析器——头 CRC（字段 16-19 清零后复算）、entries CRC、几何边界、分区重叠全部校验，只认两个私有类型 GUID 的分区（gpt.swift:26-43、45-68），与宿主 gpt_test 共编互测（Makefile:4810-4812）。kernel/fs/esp.swift:42-102 从 LBA 1 的 EFI PART 头走分区表定位 ESP 类型 GUID 分区；此后是最小 FAT32 读（BPB/cluster→LBA/FAT 链/LFN 与 8.3 双名大小写不敏感目录游走，esp.swift:104-120）与 FAT32 原地写。注意挂载拓扑：整盘走 virtio-scsi PCI（真机）或 virtio-blk（QEMU），内核用 virtioBlkSelectEsp/ReselectServed detour 在「服务中的 base 盘」与「ESP 分区」之间切换读写（esp.swift:6-12 注释）——单盘三分区下 ESP 与 store/data 同盘不同区。

## 3. 签名双槽更新完整生命周期（问题 ③）——16 号信任边界之上的全貌

**密钥管理（构建时）：** 三钥分立、同一工具生成——image 签名钥（OS vendor 身份）、model 签名钥（模型发布者）、site 签名钥（站点 bundle），生命周期各异（Makefile:85-100、2104-2117 注释原文：「image key = OS vendor, model key = model publisher」）。`modelsign keygen` 一条配方同时落 seed（32 字节私钥半）与 pub 到 models/ 目录，order-only 依赖保证重建工具不误铸新钥；CI/生产可用 SWOS_IMG_SIGNING_SEED / SWOS_SITE_SIGNING_SEED 环境变量替换开发钥（Makefile:87-89、99-101）。image 公钥经 build/image_trust_root.bin 单一文件同时编译进内核（kernel/security/trust_root.S）与 UEFI loader（efi_pubkey.S）——loader、内核、用户态（base 内 /etc/swupdate/os-root.pub）三方共享同一信任根。docs/SYSTEM_DISK.md「Build and retain signing material」节明确运维合同：镜像签名 seed 必须保留在一次性构建目录之外——「future bundles must be signed by the key trusted by the installed loader, kernel, and userland」。

**构建时签名的三个产物：** ① base.img = SWOSBASE v3 签名镜像（basepack 工具，Makefile:3878）——镜像自带 Ed25519 签名头，挂载时由内核验（I8 路径）。② kernel-boot = SWOSKERN v4 manifest（tools/kernelboot.swift）——232 字节，每槽独立条目 {size u64, sha256[32], sig[64]}，签名消息是 52 字节 `"SWOSKSLT" || u32 slot_index || u64 size || u8[32] sha256`（kernelboot.swift:9-28）；OS-1c 演化的要点是 v3（单签名盖两槽）→ v4（每槽独立签名）：新内核可只装进备槽、只写该槽的宿主签名条目，无需重签另一槽（kernelboot.swift:20-28；NOTES.md OS-1c-1 节）。③ release.swsys = SWSYS v2 系统更新 bundle（tools/syspack.swift）——`[64 字节 Ed25519 签名][header + 垫片 kernel || base || v4 manifest]`，带单调 systemVersion；格式核心在共享的 I/O-free userland/lib/sysbundle.swift，宿主打包器与机上验证器永不漂移（syspack.swift:1-19）。宿主一条命令出包：`syspack create kernel.bin base.img release.swsys --version N --seed … --slot-bytes 4194304`（SYSTEM_DISK.md 实操示例）。

**分发与安装（在线更新核心流）：** /bin/swupdate os <https-url>（或 os-apply-local 本地文件）七步（userland/swupdate.swift:655-780 逐行实读）：(1) 用户态整包验证——从 base 读 OS 公钥，verifySysBundle 验签 + payload SHA + 格式 + 版本；(2) swiftos_update_stage_begin(version, bytes)——内核侧（syscall 83）查反回滚地板 `version <= minSystemVersion 即 EPERM`、槽容量、capConsole 能力位、单 owner（updatestore.swift:456-479）；(3) 分块流式写 base 半入 inactive SWOSBOOT 槽（64KiB/次，syscall 84）；(4) stage_commit——内核验证写入头 64 字节是「签名 v3 SWOSBASE 且自述长度 == 声明长度」、virtio FLUSH 落盘、然后才写 manifest 标记槽 present+UNTRIED+generation+1+systemVersion（updatestore.swift:513-570）；(4b) kernel 半：kernel_install_begin/write/commit(entry)（syscall 107/102/103）把垫片新内核流入 inactive ESP 槽并递交 bundle 内切的 104 字节该槽签名条目——commit 内核侧重验四件事：整槽写满、entry.size == 槽定长、盘上全槽重哈希 == entry.sha256、entry.sig 对 image_trust_root 且槽索引绑定（「a slot-A entry replayed into slot B fails the index binding」——被攻破的用户态装不进宿主没为该槽签过的内核，esp.swift:648-673 头注 KEY SECURITY PROPERTY + 805-884 实现）；(5) 协调激活——swiftos_kernel_activate 翻 ESP kernel-state 单一选择器（kernel+base 同步换），无 ESP 的 store-only 机器回落翻 SWOSBOOT activate（swupdate.swift:747-770）。两个半体都到位才翻选择器，此前失败机器留在原槽（staged 内容惰性无害）。

**启动时选槽与失败回滚（三路）：** 路径 A「镜像坏」——loader 对每槽验签名 + 整镜像 SHA-256，无效槽跳过、活动槽加载失败落另一槽、全败落内嵌 blob（loader.c:663-719）；base 侧挂载验签失败由 vfsInit 调 virtioBlkUseFallbackBase 重挂 fallback 槽（U1a 节）。路径 B「能启动但不健康」——attempt 计数回退：loader 与内核各自持有 3 次上限（KS_MAX_ATTEMPTS=3，loader.c:346；maxBootAttempts=3，updatestore.swift:24），未确认槽每次 boot attempt+1 并持久化，耗尽即标 FAILED 换 fallback（loader.c:647-659、681-690；updatestore.swift:117-143）；swupdate confirm（OS-5 统一确认命令：base 半 syscall 65 + kernel 半 syscall 70，best-effort）标 CONFIRMED 停止计数，`--auto` 模式只在进程健康探测见 sshd+nginx 都在时才确认（NOTES.md OS-5 节）。路径 C「确认后防降级」——confirm 成功把 SWOSBOOT manifest 的 minSystemVersion 提到该槽 system_version，此后 stage-begin 拒绝等版本或更低版本（updatestore.swift:221-239「closing the anti-rollback loop…so the box can no longer be staged back onto that-or-older (validly signed but superseded, possibly vulnerable) OS」）——注意次序：地板只在 confirm 后抬升，回退自由存在于确认之前。贯穿全程的掉电安全纪律：槽数据全量写 + FLUSH 先于任何 manifest 指认；manifest 双缓冲写「另一份」（LBA 0/1 轮换）+ FLUSH，读者取有效副本中最高 sequence（swosboot.swift:28-47；U1h 节）。16 号已记的核心信任边界在此生命周期中的落位：SWOSBOOT manifest 与 ESP kernel-state 都只做完整性保护（CRC32 / SHA-256）不做签名——内核只持公钥不能自签运行时要写的状态；它们的角色被严格限定为「在自认证的签名镜像之间选择」，篡改者最坏造成换选另一个仍有效签名的旧槽或 boot loop——DoS 面，永不升级为代码完整性绕过（swosboot.swift:13-20 原文；loader.c:170-172）。

**诚实记录一处文档未直论的减弱面：** 反回滚地板 minSystemVersion 本身存在可写 manifest 里，而 manifest 不签名——持有整块 store 盘的攻击者理论上可把它清零后配旧签名镜像降级。swift-os 的信任边界论证（swosboot.swift:13-20）覆盖的是 active 指针面，未直接讨论 floor 被磁盘篡改降低的面；其事实威胁模型似乎是「stage 写入只能来自持 capConsole 的在位 OS」。这与 BerryOS OTA 设计 §2.1 把反回滚计数放 RPMB/eFuse（CounterBackend）的结构性选择形成对照——BerryOS 方案对离线磁盘攻击者更强。

## 4. Hetzner 在线更新实操：协调 OS 更新的实际流程（问题 ④）

**门禁先行（QEMU 复刻真机拓扑）：** `make hetzner-os-update-test`（Makefile:2975-2981）先以 prod profile 构 GPT 盘（INCLUDE_OS_STAGE_TEST=1 烤入 SWSYS fixture）+ hetzner-update-store.img（SWOSBOOT 双槽 = prod base.img，active A），再在「Hetzner-faithful QEMU」——virtio-gpu 与 NIC/RNG 走 PCIe root port、GPT 在 virtio-blk-pci、SWOSBOOT store 挂第二 virtio-blk-pci 盘、只跑 sshd-supervised——里通过 SSH 无头执行 `swupdate os-apply-local`，断言协调 ESP 激活生效（base 落 B 槽 + kernel-state 翻转）（NOTES.md:9379-9392 OS-1b-Hetzner 节）。该节同时诚实标注边界：「GPT boots on blk-pci in QEMU so loader/kernel can drive ESP kernel-state I/O (production boots scsi; real HW Console check still pending)」——QEMU 门用 blk-pci 是因为内核当时还驱动不了 scsi 引导盘，真机 Console 验证仍挂账（OS_UPDATE_AUDIT.md 亦列「real-hardware Console validation on Hetzner」为 open gap）。

**真机装机与更新手册（docs/SYSTEM_DISK.md）：** 一次性 Rescue 迁移先保旧盘与哈希、在真实 virtio-scsi 拓扑上试盘再换盘；装机镜像已含 kernel+base 双槽，此后 Provider Rebuild 不在常规更新工作流内。机上日常更新四步（SYSTEM_DISK.md「Installation and updates」节命令原文）：宿主 `syspack create … --version N` 出版本化签名 bundle → 机上 `swupdate os https://updates.example/release.swsys`（HTTPS 端点须在其 CA store 信任集内）→ `reboot` 试验启动 → 验 SSH/HTTPS 与应用健康后 `swupdate confirm`。约束面同节明示：SWSYS 只更新内核与签名 base，**EFI loader 本身不在更新范围**；/data（站点内容与证书）刻意不随 OS 回滚；3 次未确认启动 loader 选 fallback、base 跟随；确认抬反回滚地板，确认过的版本重放会被拒。大 bundle 可超 datafs 单文件 4MiB 帽——用 HTTPS 或只读 payload 盘承载而非 os-apply-local。

**真机验收叙事（NOTES.md 2026-10-31 两节）：** 单盘系统落地过程中 e2e 测试抓出两个真 bug：kernel.bin 曾是链接 kernel.elf 的副作用产物，并行 UEFI 构建会打包到旧二进制（后改显式依赖）；8KiB 进程 EL1 栈不够签名内核安装调用链——GDB 定位用户态 bundle 验证后保存的 FP/LR 被 Ed25519 域 limbs 覆写，命令打出 success 后跳 0x24b4 段错误，栈提到 32KiB，验收改为要求 SSH 命令零退出码后重启并确认安装镜像（NOTES.md「Single-disk hosting image」节）。随后的「Hetzner PCI discovery investigation」节记录真机排障与闭环：活体结构化诊断发现 root-port function 0 是多功能桥而递归存储搜索只走了 bus 0/1/9，修正字节/半字配置读后 live validation 在 bus 6/LUN 1 找到 SCSI、挂上 /data、恢复 /try 的可信 HTTPS，最后一句是本问题的关键验收——「The kernel/base slots were confirmed using SwiftOS, which also exercised persistent ESP metadata writes」：真机上用 SwiftOS 自身完成了 kernel/base 双槽的 confirm，顺带验证了 ESP 元数据持久写。另一处诚实记录（NOTES.md:8837-8838）：测试环境的 swupdate os/site 走 --insecure（TLS 对端验证默认关闭，V-TS3 deferred）——签名检查才是这些测试行使的目标，真机 TLS 面仍是待补项。

## 5. 对照 BerryOS：BerryBoot EFI 链 vs swift-os 链（问题 ⑤，只读对照）

**形态差异四点。** 其一，装载物形态：swift-os loader 装的是位置依赖 flat bin（kernel.bin 整镜像搬到固定物理地址 0x40080000，kernel.ld:1-10），BerryBoot 装的是 ELF——justfile run-efi 注释记录 BerryBoot 的 berry-loader boot_parse 走「p_paddr 口径 + DRAM 窗拒面」逐段解析装载（坏档打 `elf: parse e=<码>`），并先 GetInfo 探长、AllocateAddress 认领、整窗清零、逐段拷贝回读对拍、写 BerryHandoff v0。ELF 装载对段布局/调试信息更宽容，flat bin 简单但把链接地址焊死在板上。其二，loader 职责纵深：swift-os loader 已是「验签 + A/B 选槽 + attempt 回退 + ramdisk 暂存」的安全引导机构（Ed25519/SHA-256 编译入 loader）；BerryBoot 当前是纯装载器（九行横幅：fw/gop/fs/kfile/init/elf/load/BERRYBOOT ok），验签面在 BerryOS 是 L0 设计位（OTA 设计 §2：真机 P8 窗口、SEC-01 verifiedbootstate 四态）而非现网代码。其三，内核文件系统访问方向相反：swift-os 内核自带 FAT32 读写器直接写 ESP 槽文件与 GPT store 盘（esp.swift/updatestore.swift 皆内核态）；BerryOS 铁律是 FS/驱动用户态（AGENTS.md「FS/网络/驱动用户态」）——BerryBoot 只读装载，rootfs 走 fw_cfg/cpio（justfile image 注释：INITRD.BIN = rootfs.cpio 整档读入页钉）。其四，镜像组装：BerryOS justfile image = mkimage.py 造 MBR + 单 FAT16 96MiB 四件套盘（BOOTAA64.EFI/HELLO.TXT/KERNEL.ELF/INITRD.BIN，EDK2 PartitionDxe+FatDxe 消化分区偏移，BerryBoot SFS 面零改动）；swift-os 双产线（双盘开发形态 / GPT 三分区单盘生产形态 + 外挂 store 盘），且镜像内组件全部签名定长。

**可借鉴五点（签名槽生命周期/镜像组装面）：** ① 每槽独立签名的 manifest 设计——52 字节签名消息把 slot_index 绑进签名（SWOSKSLT||index||size||sha256），跨槽重放条目在验签时即死； BerryOS L0/L1 槽条目签名可采同型，esp.swift:648-673 的「错误索引正确签名条目必须被拒」测试夹具（Makefile OS-1c-2b fixture 段）是现成的对抗测试范式。② 「选择器非信任锚」信任边界的生命周期兑现——可变状态（active/attempt/state）全部走不签名的 CRC/SHA 保护通道，因为内核只持公钥不能自签；签名的只有镜像本体与 manifest 元数据。BerryBoot 将来做 L1 指针翻写时会遇到完全同构的「谁有权写指针」问题，swift-os 的答案是「指针不需要签名授权，因为指向物自认证」。③ 流式 stage begin/write/commit 三段式 + commit 时内核（或 BerryOS 对应面：持证服务）全量重验 + flush 先于元数据指认的掉电次序——比「写完即信」多一整层防线，且 begin 即查容量与版本地板、fail 早。④ confirm 才抬反回滚地板的次序——与 BerryOS OTA 设计 §2.1「SUCCESSFUL 先于 rollback index 更新」次序纪律完全同构（两个项目独立收敛到 AOSP 同一条规则），swift-os 提供了该次序的一个可测实现。⑤ 双形态镜像产线 + I/O-free 格式核心单源共享——swosboot.swift 同一文件编进内核、宿主工具、宿主测试三处（「so the bytes this writes are exactly what the kernel parses」，tools/updatestore.swift:20-21），格式永不漂移；BerryOS 未来槽/镜像格式同样应单源编译进 berry-boot 工具链与内核两侧。

**不适用面四点：** ① 内核态 FAT32 写与块设备直写——BerryOS FS/驱动用户态原则下，槽写入应走用户态更新服务 + 能力门控 IPC，而非 swift-os 式内核 syscall 直通块设备；代价是多一层协议，收益是内核面不扩大。② 单 capConsole 位即放行槽写——swift-os 的能力粒度是一个掩码位；BerryOS 能力模型是内核态 handle + 细粒度委托，更新引擎应是独立的持证服务而非任意 console 会话进程。③ 位置依赖 flat bin 固定地址链接——BerryOS EFI 链已选 ELF 解段装载路线，更通用，无需回头。④ 块层双槽本身——BerryOS L1 主刀已裁定为 sys 目录级 A/B（OTA 设计 §3：「同样掉电安全；我们不翻倍整盘空间…不需要改分区表的专用 bootloader」），swift-os 的整槽块镜像双备份（base 双槽各 128MiB 全量副本）恰是 BerryOS 设计文档点名规避的空间形态；可借的是它的签名/次序/验签纪律，不是它的存储布局。另一点真机教训值得预告：swift-os 单盘 e2e 抓出的「并行构建打包旧 kernel.bin」与「EL1 栈深调用链溢出」两 bug（§4）都是 QEMU 简化拓扑藏住、真验收暴露的——BerryOS 真机窗口（P8）应预设同类「输出件新鲜度」与「深调用链栈预算」检查。

## 6. 与预期不符处（诚实清单）

预期一（承 12/16 号报告印象）：swift-os 更新面 = 签名 base 双槽 + /data，内核镜像不在更新范围。实读推翻：OS-1c 已完成新内核装入 ESP 垫片槽的全链（每槽签名 v4 manifest + 内核侧 commit 四重验 + SWSYS bundle 双半同装），kernel 与 base 由单一 ESP 选择器协调同步换（NOTES.md OS-1c 节「Closes the last OS-1 gap」；OS_UPDATE_AUDIT.md TL;DR「both the kernel (ESP) and the base image…already have signed slots」）。预期二：ESP 上的 base.img 是主根文件系统来源。实读：它是 H3 兜底路径——只在内核不驱动引导盘控制器（Hetzner virtio-scsi 早期）或无块盘时作 ramdisk；有 virtio-blk base/store 盘时内核优先块盘（loader.c:163-169、470-475 注释；Makefile H3 段注释「the kernel still prefers it」）。预期三：EFI loader 应该也在自更新范围内（否则引导层是永久缺口）。实读 SYSTEM_DISK.md 明文：「The EFI loader itself is not updated by this command」——最底层信任锚（loader + 内嵌公钥）当前无更新机构，这是 swift-os 自己承认的开放面。预期四：反回滚地板应有硬件或独立存储背书。实读：地板就是可写 SWOSBOOT manifest 里的一个 u64（swosboot.swift:128-131），不签名——见 §3 末的减弱面记录。
