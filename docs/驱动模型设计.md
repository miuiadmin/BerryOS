# 驱动模型设计（驱动 = 持证应用 · devmgr · 硬件资源能力化）

> 回答三件事：**驱动以什么形态存在（持证应用）、怎么装卸与热换（appd 同链 + 代号）、硬件资源怎么授权（devmgr + 能力表）**。
> 核心论点：**驱动不是二等公民，是一类应用——「持设备能力证的应用」。硬件资源（MMIO/IRQ/DMA）全部进能力表：「申请摄像头权限」和「申请 0x0A00_0000 那块寄存器」在机制上是同一个动作**。别人家的水电工住在承重墙里，换个灯泡要拆房子；我们家的水电工是持证租户，换人只换工牌。
> 挂钩：`架构决策.md` #46（本文索引）+ #12（用户态驱动为主、boot 关键暂留内核——本文是它的制度化展开）+ #22（IOMMU = DMA 的硬件后盾）+ #28（代号 DEAD = 热换面）+ #43/#44（驱动包与应用包同源）；`存储布局与沙箱设计.md`（驱动住哪 = 轴二来源）；`安全与硬件隔离设计.md`（SMMU/度量链）；`优化议程.md`（「驱动热换不重启」挂账的结构性答案）。**现役证据**：vblk 就是用户态驱动（`VBLK ok`）；MMIO 窗口 VMO（P6 A-2）+ `vmo_get_phys` 查 DMA 页后备（P6 A-3）+ dtb.rs walker 枚举留位（G-eco 第一刀）都已落地——boot 手铸 svcmgr 表第 4 插 0x0001_0004 的 MMIO 窗，就是 devmgr 的手工前身。

## 0. 病灶对照：驱动的历史包袱全来自「住在内核里」

| 系统 | 形态 | 病 |
|---|---|---|
| Linux | .ko 可加载模块 | **与内核版本锁死**（符号 CRC/ABI 每版变，DKMS 现场编译）；驱动崩溃 = 整机 oops/panic；闭源 blob 只能随内核版换 |
| Windows | WDM/WDF + WHQL 签名 | 蓝屏主力（驱动 bug 直接打穿内核）；签名流程重（WHQL 认证以月计） |
| Android | vendor HAL + Treble/GKI | **补课反例**：初期驱动全塞内核，Treble 花十年把 HAL 拆向用户态 + GKI 统一内核接口——十几块分区就是这次补课的遗产 |
| macOS | kext → DriverKit（2019 掉头） | 方向同我们：内核扩展迁到用户态 IOKit IPC——**业界正在向我们这个方向走** |
| QNX / MINIX / seL4 / Fuchsia | day-one 用户态驱动 | 先例保证：微内核 + 用户态驱动在车载（QNX）与量产消费电子（Fuchsia）都验证过 |

结论：驱动的问题从来不是「驱动难写」，是**驱动被安排住在了一个不该住人的地方**。BerryOS day-one 就不在坑里（ADR #12）——本文把这个决策走到底：形态、装卸、授权全部制度化，不留「先塞内核以后再拆」的 Treble 式补课债。

## 1. 形态：驱动 = 持证应用（.bap 同链）

驱动包就是应用包，差一个字段组：

```toml
[app]
id = "org.berry.drv.virtioblk"
version = "1.0.0"
entry = "bin/vblkd"
type = "driver"                # 轴三·身份：驱动（待遇差异仅此一条）。v2 形态——v0 manifest type 唯一值 "app"，"driver" 随 devmgr v2 入表（应用模型设计.md §3 注）
intent = "utility"

[hw]                           # 匹配键：devmgr 拿它到资源池认领设备
match = ["dt:virtio,mmio", "pci:1af4:1042"]   # DT compatible 串 / PCI vendor:device，同一张表两种总线

[capabilities]                 # 硬件资源申请表——与「申请摄像头」同一张表
mmio = ["window"]              # → devmgr 铸 MMIO 窗口 VMO
irq  = [1]                     # → IRQ→channel 转发端点
dma  = true                    # → IOMMU 限定窗口（#22）
provides = ["/svc/disk/blk0"]  # 注册进命名空间（决策 #6）——它对外就是服务
```

- **「驱动框架」不是二进制格式，是薄层**：devmgr（授权）+ 协议 crate 家族（SDK，fsproto/blkproto/netproto 模式）+ `/svc` 注册约定。没有 .ko 式独立模块格式——**格式独立 = 版本地狱的起点**（Linux 教训）。
- **住哪按轴二来源**（`存储布局与沙箱设计.md` §6）：系统自带驱动住 `sys/`（svc 同级或 `sys/drv/`）；后装驱动（打印机/外置加密狗）= 普通 `.bap` 进 `apps/`。卸载驱动 = 卸载应用 = 删树。
- **消费者视角无「驱动」概念**：fsmgr 只认 `/svc/disk/blk0` 的 channel——对面是 virtio-blk、NVMe 还是 RAM 盘，它不知道也不需要知道（现役 fsmgr↔vblk 已是这个形状）。
- **固件随包**：驱动包内 `fw/` 目录住设备固件（版本绑定/签名随包/回滚同步）——展开见 `更新与OTA设计.md` L3。

## 2. devmgr：硬件资源池的管理员

一个普通系统服务（v2，svcmgr 家族演化），持「设备资源池」这枚大能力，职责五件：

1. **枚举**：boot 期从 DTB（ARM）/ACPI（x86 线）读设备树 → 建「未认领资源池」。`kernel/src/dtb.rs` walker 已留位（G-eco 第一刀，现役 `/chosen` 解析）；ACPI 随 ADR #41 x86 最小集后再议。
2. **匹配**：驱动包装载时按 `hw.match` 键在池中认领设备（多候选同键 → 版本/优先级裁定，v2 细化）。**认领即独占**（单设备单主人——P6 A-4 已文档化的 v1 缺口在这里收口：池中设备一次只授一个驱动，第二个实例拿不到窗口）。
3. **授权（铸能力）**——三铸件：
   - **MMIO 窗 VMO**：`Vmo::create_mmio` 已是现役 boot-only 原语（P6 A-2：页对齐执法、commit/read/write 一律拒、只许 volatile 经映射访问、Drop 不进还帧路径）——devmgr 就是它的合法持铸人；EL0 永不可自造物理窗口，**物理窗口是授的能力**。
   - **IRQ→channel**：中断以消息/Event 递给驱动。PL011 RX 的 IRQ→Event→wake 是内核内先例（P5 A-1）；外提 = 把同一模式变成 devmgr 服务。**欠的原语**：转发对象——v1 vblk 轮询 INT_STATUS + 1ms 睡步进（GIC 从不使能 virtio SPI），能跑但费电，tickless 纪律下真机不可接受，v2 补。**转发对象的语义设计已在册**：`IPC设计.md` §3「IRQ 投递」——设备 Interrupt 对象 signal 一个 Event、驱动 wait 该 Event（Interrupt 对象入 `能力模型设计.md` §3 对象表）；欠的是内核实现（v1 无 Interrupt 对象），非设计。
   - **DMA 圈**：IOMMU 把设备 DMA 限定在授权 VMO 的物理区间（#22——能力安全的硬件后盾）。用户态驱动查自己 VMO 页后备走 `vmo_get_phys`（P6 A-3 现役）。无 IOMMU 板上的披露面诚实记录（已授窗口的设备本可 DMA 全内存，v1 接受）；cache 维护 DMA API（dc cvac/ivac）v2 挂账（P6 A-3 对抗审查注记：单屏障不足以真机可工作）。
4. **注册**：驱动就绪后把 `provides` 挂进命名空间——设备从「硬件」变成「服务」的仪式（`/svc/disk/blk0` 即现役 blk_a 通道的命名空间形态）。
5. **导出**：未认领池以机器可读**设备任务书**面暴露（`AI工程面设计.md` §2.1 活儿清单的格式出处）——devmgr 自身的对外产品面，对人 / CI / AI 同样可用，非 AI 专用。

**「申请摄像头」=「申请寄存器」**：两者都是 manifest 能力表的一行、都由授权服务（设置服务/devmgr）铸 handle、都被能力模型同一条链门控。手机上的割裂（app 权限一套、系统服务无权限概念）在机制上不存在——见 `能力模型设计.md` §8「应用层是皮，唯一机制纪律」。

## 3. 装卸 / 崩溃 / 热换：全走应用链

| 事件 | 机制 | 现役先例 |
|---|---|---|
| 安装/升级 | appd 翻译 manifest → devmgr 授权 → 拉起（与普通应用同链，#44） | svcmgr 拉起 vblk（手搭版） |
| 崩溃 | 只死自己（G1.5）；appd 监督重启，代号 +1 | 用户进程矩阵 |
| 热换（拔旧上新） | #28 代号：旧驱动全部 handle DEAD → 消费者（fsmgr 等）重试/降级 → 重连新代 | 决策 #28 协议在册 |
| 卸载 | 删树 + devmgr 回收设备入池 | ADR #45 |

- **「驱动热换不重启」**（`优化议程.md` 挂账项）的机制面就是上表——零新内核机制，欠的是消费者侧 DEAD 重试纪律（fsmgr 的 RpcRes::Poison 降级是同族先例：确定性失败优于无告警错数据）。
- 消费者重连新代 = 重新查 `/svc/disk/blk0` 拿新 channel——与「服务监督重启」是同一个协议（appd 监督线），不分驱动版。

## 4. 诚实面：性能、安全、boot 豁免

- **性能**：用户态驱动吞吐先例充分（virtio 用户态块/网卡达线速率是业界常态；SPDK/DPDK 干脆绕内核）。高吞吐面（网卡/GPU）用共享环而非逐消息 IPC——与 PM 服务共享环同一纪律（禁通用 IPC 拷贝的面走专用环，`调度器设计.md`）；channel fastpath/slowpath 分层（4-4）打底日常面。
- **安全**：能力结构性缺席（没授的窗口表里就没有）+ IOMMU 后盾（#22）+ 驱动包签名随度量链（#24，v2 分发面）。恶意驱动的最大攻击面 = 它持有的那扇窗，圈定在设备自己的地址范围。
- **boot 关键豁免清单（#12 的现役边界，逐版外提）**：GIC、CNTV timer、早期 UART、console 服务循环（P4-5a 内核任务形态）。判断标准写死：**「拉起别人之前就要用的」才许留内核**——devmgr/appd 自己起来的那一刻，剩余豁免面全是外提候选。
- **按端诚实**：车机/工业端的 ASIL/DAL 认证不承诺（12 号报告 §3 老实账）；工业 RT 驱动（v2 端）走同一模型 + RT 调度类，**不做第二套驱动框架**。

## 5. 阶段化目标

| 时点 | 内容 | 验收 |
|---|---|---|
| v1（现状） | 用户态驱动**已在跑**：vblk（块设备常驻服务）+ vnet（网络常驻服务，P6 A-7/A-8 起——DNS/TCP 面皆经它）+ vprobe（窗口探测）；窗口由 boot 手铸（svcmgr 表第 4 插）；GIC/timer/UART/console 在内核 | `VBLK ok` / `VIRTIO ok` / `NET ok` / `DNS ok`（已过） |
| v2 | **devmgr 最小面**：DTB 枚举 → 池 → 匹配 → 授 MMIO 窗 + 注册 `/svc`；IRQ→channel 转发原语（首个消费者 = virtio-blk 中断驱动版）；驱动包进 .bap/appd 链 | smoke `DEVMGR ok`（枚举→匹配→授权→注册→导出 N 台设备任务书全链，确定性状态谓词） |
| v2+ | 热换演练（消费者 DEAD 重试）；IOMMU 实板收口；cache 维护 DMA API；高吞吐共享环面 | 热换标记 + 真机 G 卡复测 |
