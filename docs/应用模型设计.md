# 应用模型设计（包格式 · 三层形态 · 生命周期）

> 回答三件事：**应用是什么（APK/IPA/.exe 怎么理解）、系统怎么分层（三层够不够、层怎么定义）、GUI 怎么做到可拔插（去掉一身轻）**。
> 核心论点：**「应用」不是内核概念，是纯用户态的协议约定——包（文件）+ 清单（数据）+ 能力授予（handle）+ 生命周期（消息）**。GUI 只是能力集的扩项，不是另一种程序。
> 挂钩：`能力模型设计.md`（授能与监督）、`IPC设计.md`（协议载体与命名空间）、`系统调用ABI设计.md` §4（process_create/process_start/bootstrap 迁移）——env 块协议见 `G-eco编译侧设计草案.md` d-3a、`shell设计.md`（headless 应用的现役形态）；决策 #43/#44（ADR）。GUI 本体不在 v1 路线图内——本文是设计先行（`路线图.md` 明文允许设计文档与任意 Phase 并行产出）。

## 0. 四大应用包拆开看：同一副骨架

| | APK（安卓） | IPA（iOS） | .exe / .app（桌面） |
|---|---|---|---|
| 容器 | zip | zip | 单文件 PE / 目录 bundle |
| 清单 | AndroidManifest（组件注册+权限声明） | Info.plist + entitlements | PE 资源里**后补**的 manifest |
| 代码 | dex 字节码 + 可选 .so | 原生 Mach-O | 原生 PE / Mach-O |
| 生命周期 | **系统持有**（AMS 造/杀进程，回调 onCreate…） | **系统持有**（后台真冻结） | **应用自持**（自己的消息循环） |
| IPC | Binder | Mach port / XPC | 窗口消息 / COM |
| 信任 | 签名+安装期授权+UID 沙箱 | 强制签名+entitlement | 起初裸奔，后补 UAC/AppContainer |

真正的自由度只有四个：**代码形态**（字节码 vs 原生）、**生命周期归属**（系统 vs 自持）、**信任是否 day-one**、容器封装。其余全是同构。

20 年下来各家在收敛：Windows 后补了 manifest 与沙箱（AppContainer/MSIX），安卓把 Dalvik 换成 AOT 的 ART——都在向「**原生代码 + 声明式清单 + 系统持有生命周期 + 能力沙箱**」靠。这是被量产验证的收敛点，BerryOS 直接以它为起点（能力沙箱我们比谁都彻底：纯能力模型，决策 #2）。

## 1. 三层怎么切：层 = IPC 边界，不是代码模块

**判据**：跨进程边界（要 IPC、要排队、有延迟、可独立崩溃重启）才算一层；静态链接进程序的库是零层（无边界、零 IPC 开销）。macOS 的「厚」一半是把本该是库的东西做成了层。

```
L3  应用 + 库      [应用进程] ←静态链接→ [UI 工具包·库] [协议 crate] [berry-libc]
                  应用 = 进程 + 一组 handle + 一份 manifest
L2  系统服务       appd(安装/生命周期/监督)   display(合成 + 输入路由 + 焦点)
                  fs  net  pmu  ...          平级进程，互相也走 channel
L1  内核（现役）    调度(intent/PI)   IPC(channel)   内存(VMO)   能力(handle)
                  永远不知道「应用」「窗口」是什么
```

- **L1 内核**：只提供机制。对一个 GUI 应用与一个 shell 管道段，内核视角无差别——都是「持若干 handle 的进程」。
- **L2 系统服务（中间层的答案）**：七八个**平级**服务进程，不是一摞框架栈。appd 就是 svcmgr 的成人形态（拉起/监督/reap 的现役逻辑直接演化）；display 单进程管合成 + 输入路由 + 焦点（Wayland / macOS WindowServer 同款——焦点在哪儿输入就该从哪儿路由，拆开就是 Windows win32k/DWM 的历史包袱）。
- **L3 应用 + 库**：UI 工具包是**库不是层**——链进应用进程，画界面不跨任何 IPC。

**两个「不能塌缩」**（三层的物理下限，不是审美）：

1. **合成器不能进内核**：应用不能直接扫描输出，否则任何应用可截屏/覆盖他人——合成是能力安全的必经隔离（微内核纪律 + 决策 #2）。
2. **工具包不能进系统服务**：否则每次工具包升级 = 升系统，且锁死第三方工具包（Android View 与系统框架绑定的教训）。

**L2 与 L3 同构**：fsmgr（服务）与未来的记账 App（应用）在系统眼里没有本质区别——都是「持有某些能力、被监督的进程」。系统服务不是特权身份，是**持证身份**；差别只在谁授的证、监督链挂在哪。

**再往下拧一圈：硬边界其实只有一条**。EL1/EL0（kernel/用户）是唯一的硬件信任线；线之上是**能力分级的服务平原**——display/fs/net/appd/drivers/应用全是平级进程，等级是动态授予的能力集，不是结构性叠起来的层。「三层」是给人看的表述；工程上执法的是三条规则：

1. **跳数预算**：触摸→应用 ≤2 跳、应用→像素恒 1 跳；每个边界上的队列必须挂 deadline——没有 deadline 的暗队列不让存在（§5）。
2. **依赖方向铁律**：GUI 组件清单外不得依赖清单内（§2）。
3. **中间不设稳定 ABI**：冻结的只有最底层 `berry_*` syscall + 每服务的 wire 协议（add-only，ABI §8.5）；工具包是库，应用自带版本静态链接——系统永不为「老应用的旧工具包」保兼容。macOS 真正的厚不是服务多，是中间摞了 Carbon/Cocoa/UIKit/Catalyst 好几层**框架 ABI**，每层各自背二进制兼容包袱。

**加层检验**：每加一层，问它买到了什么——独立崩溃域 / 信任边界 / 独立演进（驱动、display、fs、appd 各买到一个，值）；「框架层」什么都没买到，只是把库 ABI 化（不值）。

## 2. 一体两面：能力决定形态

「可大可小、去掉 GUI 一身轻」的可验证表述——**应用的形态完全由它持有的能力集决定，不由运行时/框架决定**。现役件已经是这个模型的 headless 原型：

| 现役件（已落地） | 应用模型中的角色 |
|---|---|
| env 块 gift handles（d-3a） | 应用拿能力的唯一方式（= APK 安装期权限授予的内核侧机制） |
| EOF 约定（d-3b）+ svcmgr reap（Plan B） | 生命周期与监督（headless 版） |
| cpio + ELF + berry-loader（G-eco-c） | 包格式与装载器；mkcpio = 打包工具的胚 |
| rootfs | 「已安装应用」存储的雏形（未来 /apps 与它同构） |
| hexyl 0.17.0 上游逐字未动跑通（d-3c） | **SDK 的第一个活证据**：第三方 Rust 程序编译即跑 |

三条推论：

- **GUI 应用 = 同一协议，gift 里多两枚 handle**（一枚 surface VMO、一枚 input channel）。应用代码形态不变，「GUI」只是能力集变了。
- **headless 构建 = 撤掉 GUI 组件，其余一字不改**。
- **GUI 可拔插铁律（依赖方向，可审计）**：GUI 组件清单 = {display 服务、appd 的 UI 半边、工具包库、输入/显示驱动}；清单**外**的组件（fs/net/pmu/svcmgr/调度…）**不得依赖清单内**的任何一项。违反即 GUI 变成空中楼阁。审查面 = 服务的 import 面 + handle 持有面，进对抗审查 checklist。

## 3. 包格式：cpio + manifest（ADR #44）

暂名 `.bap`（berry application package）——**与 rootfs 装载链同构，不发明新容器**：

```
notes.bap (cpio newc)
├── manifest.toml          # 声明式能力申请表（唯一必选项）
├── bin/notes              # ELF（musl target + berry-libc，与 stdhello/hexyl 同链）
└── res/…                  # 资源（图标/字体/布局）
```

manifest v0 **已落地冻结**（2026-10 app-0：`user/berry-manifest` 纯函数解析 + `tools/mkapp` 门禁打包；字段集 add-only 演进，对齐 ABI §8.5 稳定性纪律）：

```toml
[app]                        # 五键必填，缺一即拒
id = "APPDEMO"               # [A-Za-z0-9._-]、首字符字母数字、≤24B（v0 短 id；反域名是 v2 形态）
version = "0.1.0"
entry = "bin/appdemo"        # 必 bin/ 前缀整串比对 = 无路径遍历面；== 包内唯一 bin 文件路径（mkapp 门禁）
type = "app"                 # v0 唯一值；gui|headless|daemon 词表 v2 add-only 回归（§4.2 角色定档随之解锁）
intent = "utility"           # 必填六词之一（unspecified…maintenance，串形 ↔ berry_intent 0x00–0x05）

[capabilities]               # 能力申请表 = 安装期授权面（唯一入口）；v0 恰 console 一键
console = true               # → spawn stdout 授 console handle；false → appd 私有采集对（EOF-only 收集）

[runtime]                    # 整节可省（省 = stack_pages 缺省 8）
stack_pages = 8              # 1..=64
```

语法子集**冻结到字节级**（LF-only 拒 CR/tab、整数纯十进制 [0-9]+、串内无反斜杠/引号、仅可打印 ASCII；未知节/未知键一律拒——loud 失败优于半工作）；`mkapp` 门禁五道含**规范形重序列化逐字节相等**——把「tomllib 收下」收紧到「子集收下」的唯一执法点。

下例为 **v2 目标态**（display/input/fs/net/background 键、`[ui]` 节与 id 反域名 = 能力词汇随各服务就位 add-only 回归，schema 演进位已留）：

```toml
[app]
id = "com.example.notes"     # 反域名；安装即命名空间（数据目录/日志归属）
version = "0.1.0"
entry = "bin/notes"
type = "gui"                 # gui | headless | daemon —— 能力面形状
intent = "interactive"       # 0x02（4-3c 编码冻结表）；daemon 可 background；未声明时 appd 按 type 角色表定档（§4.2）

[capabilities]               # 能力申请表 = 安装期授权面（唯一入口）
display = true               # → surface VMO + frame channel
input = true                 # → input channel（display 路由）
fs = ["$appdata"]            # → 私有数据目录（fsmgr 授）
net = ["client"]             # → net 服务端点
background = false           # → 后台执行类（v1 = intent 降档 + 墓碑候选（§4.1）；真冻结 v2）

[ui]
render = "vmo-surface"       # v1 渲染模型：应用画进 VMO，display 合成
```

**安装 = 翻译**：appd 读 manifest → 按 `capabilities` 逐项向对应服务申请/复刻 handle → 存为「该应用的授权集」。**启动 = 授能**：spawn 时把授权集经 env 块 gift 数组交给应用（d-3a 机制；gift 槽容量随字段数扩）。没申请的能力，应用表里就没有对应 handle——不是「有权限位但被运行时检查」，是**根本拿不到**（能力模型与 ACL 的本质区别在此兑现）。

**SDK 三件套**（全部已有胚胎）：`berry-sys`（ABI crate）+ `berry-libc`（musl shim，hexyl 已验）+ 协议 crate 家族（fsproto/blkproto/netproto 模式——每服务一个纯函数 crate，host 可测）。第三方开发者视角 = Rust 工具链 + 一个 target 约定 + `mkapp` 打包。

## 4. 生命周期：一组约定消息，不是一组内核机制

系统持有生命周期（§0 收敛点），载体就是 channel 消息——**协议在用户态，内核零新增**：

| 事件 | 消息（appd ↔ 应用，经 spawn 交付的 lifecycle channel） | 现役先例 |
|---|---|---|
| 启动 | env 块 gifts + argv 块 | d-3a |
| 退出 | 应用 `process_exit`；appd wait TERMINATED + `process_get_exit_code` + reap | Plan B / P5 v0 |
| 流终止 | 零长 EOF 消息 = 终点（写侧对称面） | d-3b |
| 失焦/获焦 | `pause(save)` / `resume` 消息（触发源：GUI 失焦 v2；headless 压力/策略 app-1 起） | 与 EOF 同构：消息层约定 |
| 收尾超时 | appd 监督杀（fault 槽）+ 代号 +1 重启，旧代号调用返 DEAD | 决策 #28 |

### 4.1 墓碑模式（v1 可造，零内核新增）

生命周期分级，压力逐级上收：**active → freeze（v2，内核 suspend 原语）→ tombstone → not running**。墓碑 = Windows Phone 同名机制与安卓 saved-state process death 的合体：**进程杀掉、状态留下、回来复活**——省电最狠的一颗子弹是不跑。

```
失焦/压力 → appd 发 pause(save) → 应用把状态序列化进 state blob（VMO 或 $appdata 文件，≤64KiB 帽防失控——appd 执法，超帽拒收）
         → 应用 process_exit → 墓碑表记 {app_id, blob, 时间戳}
回来     → relaunch + env 块多塞一枚 state handle → 应用读档复活
压力     → 墓碑表 LRU 淘汰；表有界
```

- **v1 纯用户态可实现**（协议消息 + VMO/文件 + appd，内核零新增），比 freeze 先行；手表 v1 现实也正好是这个形态——单应用前台，切走即墓碑（watchOS 同款激进）。
- **恢复动画由 display 直驱**：系统壳先播过渡动画、不等应用启动完——「墓碑了还感觉快」的视觉魔术（iOS 冷启动先播动画同款，§5）。
- freeze 与墓碑不是二选一：失焦先 freeze（RAM 富余恢复快），内存压力上收才落墓碑——压力策略 = appd 消费 intent + 遥测（§4.2）。
- **reboot 语义**：state blob 落 $appdata（FAT 现役）就天然跨 boot 存活——文件在盘上；墓碑表本体驻 RAM，reboot = 全墓碑（语义安全：等价「没跑过」，不是「丢状态」）。要「跨 boot 复活」只需 v2 把表落盘，协议零改。

### 4.2 intent 单一消费轴（墓碑 + 实时是一根轴的两头）

安卓的教训：**三本互相不知道的账**——oom_adj 管杀谁、sched policy 管 CPU、cgroup 管 cpuset/io——各自演化各打补丁，最后 top-app boost 全是特判代码。BerryOS 的答案：**intent 声明一次，三处消费**（调度 / 生命周期 / 电源投票共用一个字段，编码冻结见 ADR #42）：

| intent | 调度待遇 | 生命周期待遇 | 电源待遇（EPP / PM 投票） |
|---|---|---|---|
| 0x01 latency_critical（音频回调/传感器融合/display 自身） | class_rt/deadline + RT 屏蔽 | **永不墓碑、永不降档** | EPP=performance；活跃窗内 PM 投票禁深睡 |
| 0x02 interactive（前台 GUI） | 高带 + touch-boost 窗（§5） | 失焦先 freeze（v2），压力下才墓碑 | 触摸窗内偏性能提频，静默后回落 |
| 0x03 utility | 中带 | 失焦→墓碑候选 | EPP=balanced；不挡深睡 |
| 0x04 background（下载/同步） | 低带 + 空闲 loan | 立即墓碑候选 | 空闲 loan 与深睡同向——省电盟友而非敌人 |

0x00 UNSPECIFIED 不上这张表，是刻意设防：XNU 式「未声明=最强档」若被生命周期轴照抄，就是「不写 intent 的应用永不墓碑」的后门。appd 在**装载期**就把缺省定死——manifest 未写 intent 时按 type 角色表定档（gui→0x02、headless→0x03、daemon→0x04），生命周期轴永远只见 0x01–0x04（ADR #42「可被角色表定档」的同款授权；运行期 msg_intent 借入的 0x00 上限语义不受影响，4-3c 照旧）。**v0 前提注（app-0 落地形态）**：schema v0 的 intent 为 `[app]` 五键**必填**之一——「未写 intent」形态 v0 不可达、appd 零缺省推断；角色定档路径随 v2 type 词表分化（gui/headless/daemon）解锁。

「实时模式」= 第一行：机制全在册（调度器设计的 class_rt/deadline 与 RT 屏蔽；PI 恰好覆盖 RT 阻塞在慢服务上的场景）；诚实边界照旧——软实时（决策 #16），v2 对齐 PREEMPT_RT 量级（ADR #39）。

## 5. GUI 路径：跳数封顶与队列纪律

安卓复盘：早期原型是键盘机，2007 后改道触摸——事件传递/渲染管线没有为「手指贴着玻璃、16ms 一帧」的物理现实设计，Butter（帧节拍）/ART（GC 停顿）/Oreo 后台限制全是补丁。**GUI 无法事后贴上的根本原因：输入→像素的预算是毫秒级，路径横跨调度器，调度器必须看得见 deadline**。

BerryOS 的 GUI 路径设计线：

```
触摸 IRQ → 内核（A-1 RX 模式：handler 置 Event）→ 输入驱动（用户态，持 MMIO 窗口 VMO）
        → display（焦点路由）→ 应用                  ← 至多 2 跳（驱动并入 display 时 1 跳）
应用渲染 → surface VMO（display 授）→ frame-ready 消息（channel，带 intent=0x02）
        → display 合成 → 显示设备                     ← 恒 1 跳
```

- **队列纪律**：路径上每个边界只在有 deadline 的地方排队。没有 deadline 的暗队列（安卓的 Handler→Choreographer→BufferQueue 链）是延迟与后续补丁的温床——「没有 deadline 的地方就不该有队列」。
- **帧的调度优先级不特判**：frame-ready 消息天然携带 intent（4-3c msg_intent）；display 收帧队列满、高优交互应用阻塞在 WRITABLE 时，PI 捐赠（4-3b）自动把应用的优先级给 display——**帧路径的优先级反转恰好是 4-3b 的教科书场景**，机制已在库里，无需任何「前台应用特判」。
- **VMO + channel = BufferQueue + Binder + dmabuf 三件套的合体**：surface 是 VMO（零拷贝共享，mapcnt 机制现役），帧同步是 channel 消息（fastpath/slowpath 分层现役）。
- **即时反馈 display 直驱**：按压/惯性滚动的前 ~50ms 反应由 display 自己画、不等应用醒——「摸上去就动」的观感一半来自这里（应用供应内容，系统驱动物理感）；墓碑恢复动画同款（§4.1）。
- **触摸即提速（touch-boost）**：触摸 IRQ → display → 给焦点应用一个临时提升窗（~500ms 衰减，定值随策略服务调），走 4-3c 策略注入面（policy::apply 包络内），不写死内核——安卓 uclamp touch-boost 的对应物，但它是注入协议而非硬编码。

**帧预算（架构先行，真机验收）**——120Hz 一帧 8.3ms，触摸→像素全链路分解：

| 段 | 预算 | 靠什么 |
|---|---|---|
| 触摸 IRQ → 驱动唤醒 | ≤0.5ms | A-1 的 IRQ→Event 路径（已验证） |
| 路由到应用唤醒 | ≤1.5ms | 两跳 channel + PI 保优先级 |
| 应用逻辑 + 渲染 | ≤4ms | 帧 deadline 对应用可见（M4 deadline-server） |
| 合成 + 扫描输出 | 1–1.5 帧 | display 独占扫描输出 |

合计 ~1.5 帧 ≈ 12ms@120Hz、~2 帧@60Hz——「手指贴上去就动」的物理线。诚实注记：TCG 量不了这些（墙钟是模拟的），沿用 `FAST ok` 惯例——架构预算先定，真机线留 G 卡复测。

| 安卓的病 | BerryOS 的钉子（已在库） |
|---|---|
| UI 线程 GC 停顿 | 全 Rust 无 GC |
| 帧节拍后补（Choreographer，2012） | intent=交互档是一类调度输入（4-3c）；帧 deadline 挂 M4 deadline-server（入场券制） |
| 前台提优先级靠 AMS 特判 | 声明式 intent + PI 捐赠（4-3b）——无特判代码路径 |
| 后台应用捣乱（2017 才限制） | 能力模型：没持有就不能碰；`background=false` 连 handle 都没有——**2026-10-23 v0 落地注**：`background` 属 §3 v2 词表、schema v0 未收（app-0，2026-10：`[capabilities]` 白名单恰 `console` 一键，执法 = `user/berry-manifest` + `tools/mkapp`，未知能力键一律拒）；v0 现役同款例证 = `console=false`（不授 console handle → appd 私有采集对，§3） |
| HAL/框架割裂（Treble 才收拾） | day-one 用户态驱动（A-2 MMIO 窗口 + A-1 IRQ→Event 模式已验证） |

AI 红利一条：manifest 机器可读 + intent 声明 + 遥测环 = AI 调度器 day-one「看得懂」应用（设计总原则 2），不用像安卓那样事后发明 perceived-performance 指标。

## 8. Agent 面：给 AI 一台电脑（v2+ 设计先行）

「给 AI 一台电脑」的正确翻译不是把 AI 塞进操作系统，是**操作系统对 AI 友好**（设计总原则 2）——AI 友好 ≠ 操作系统智能（ADR #38 三不赌照旧：AI 不进内核、不作支柱、不挤占正确性预算）。BerryOS 想成为「AI 操作系统」，靠的是**人和 AI 走同一扇门、用同一把能力锁**：Agent 不是系统的亲人，是持工作证的访客。

### 8.1 Agent = 普通应用（零新概念）

Agent 就是一个进程 + 一组 handle：manifest 权限上限 = handle 集的物理封顶（§3「没申请的能力表里就没有」原样生效）、沙箱免费、崩溃只死自己（G1.5）、监督走 appd。给 Agent 授权 = 用户经 picker 把 handle 递给它——与给一个普通 App 授权是同一个动作，零特判。

### 8.2 底层方法清单（机制全在册或已设计）

| 面 | 方法 | 现状 |
|---|---|---|
| 沙箱 | manifest 权限上限 = handle 集 | 机制现役（能力模型） |
| **委托链** | `duplicate` 收紧 rights 传递、`close` 吊销、handle 随消息迁移全程可审计——设置服务能列出「谁把什么给了谁」 | 原语现役（3-0/3-4），审计面 v2 |
| 机器可读面 | berryctl `--json` / 遥测 dump / wire 协议 add-only（ABI §8.5 纪律） | 设计在册，逐项落地中 |
| **manifest 即接口** | `provides = ["search", "play"]` 语义声明 + intent（#42）——Agent 查 manifest 就知道能调什么，调用走 channel 能力门控，无注册表无反射 | manifest 已定（#44），语义槽 v2 |
| GUI 面 | display 服务（§1 L2）出**无障碍语义树** + 输入注入 channel——Agent 读语义树而非爬像素；一等公民接口，非事后补的 accessibility API；**单一输入路径、无合成标记位（§8.4）** | v2 随 display |
| 调度面 | Agent 以 intent 声明排队（与人类应用同队）；影响调度走 policy 注入槽（4-3c 词汇表封顶，带内）——**Agent 永不凌驾调度器**；观察侧 = 按-app 资源账（`AI调度设计.md` §4 stats 查询面） | 注入槽现役留桩 |

### 8.3 两条纪律

- **不设「Agent 特权 API」**：Agent 能做的一切都经由人类应用同样可用的机制。「只有 Agent 能调」的接口 = 违规——今天没有，将来也不立。
- **调度护栏照旧**：Agent 的调度影响只能经 intent 声明与带内 policy 注入（ADR #21 修订，动作词汇表封顶）——防「AI 优先于人类」的结构性后门。

（互推：`兼容子系统设计.md` 的 T2 人格是同一套机制的消费者——Agent 操作 Wine 应用 = 语义树 + channel，同一扇门。开发期的对偶面——AI 造软件（写驱动 / 移植）——见 `AI工程面设计.md`：运行时面管「AI 用电脑」，工程面管「AI 造软件」，零特权纪律两处共用。）

### 8.4 输入不可区分性：单一输入路径（2026-10 增补）

「应用无论如何无法知道是 AI 在操作」不是加一层伪装，是**架构性质**——现状的检测面全是「自动化走旁路」的架构后果：

| 系统 | 检测面 | 成因 |
|---|---|---|
| Web | 合成 DOM 事件 `isTrusted=false` / `navigator.webdriver` | 自动化协议与人类输入是两条路，标记位必然存在 |
| Android | app 可枚举「启用了哪些无障碍服务」 | 辅助功能是可枚举的特殊身份 |
| iOS | AX / 自动化接口带痕迹 | 同上，旁路即痕迹 |

BerryOS 的形状（§5 输入路径）：触摸/按键驱动 → 输入服务 → 焦点应用，**单一路径**。Agent 注入 = 把事件发进输入服务的同一 channel、同一消息类型——应用收到的触摸与人类产生的**逐位相同**。四条推论：

- **不设合成输入标记位**——设计选择而非疏忽：一旦设了就是给检测面递刀。display/输入服务正式设计文档 v2 立时，此条为预埋约束。
- **无第二身份可枚举**：Agent 不是「无障碍服务」那样的特殊身份，就是普通输入的另一个生产者；Agent 进程在别的沙箱里，应用无权查询其他进程（能力隔离反向保护了操作者）。
- **辅助科技同路受益**：人类无障碍用户与 Agent 走同一条路——接口层不存在「只封 AI 不封无障碍」的检测面，反误伤是结构性红利（与「同一扇门」同源）。
- **「愿意被操作」靠激励不靠对抗**：`provides` 语义动作面（§8.2）是首选通道——声明了的应用被操作得又快又稳，不配合的退到语义树 + 输入注入（照样能用，但脆、慢）。应用想要 AI 生态流量就得声明接口，与 deep link 生态同一逻辑。

**两条诚实边界（写死，不随实现漂移）**：

1. **接口不可检测 ≠ 行为不可检测**。对端服务器/应用内逻辑仍可看统计：操作节奏的规律性、24h 不眠、响应延迟分布。拟人化节奏是 Agent 策略层的事——OS 只承诺「输入路径上无标记」，不承诺「你的 Agent 表现得像人」，也不该承诺。
2. **用户主权立场，刀两边都切**。设备是用户的、能力是用户授的，应用在用户设备上不当警察——这是设计立场；但同一机制下滥用（外挂/批量假活跃）同样不可检测，OS 层**不做善恶预设**（一旦预设就回到了标记位）。滥用治理在对端风控与法律，不在本层。

与 §8.3 的对偶：**不设「Agent 特权 API」⟺ 不设「Agent 痕迹」**——前者保证 Agent 不比人强，后者保证 Agent 不比人特殊，合起来才是「同一扇门、同一把锁」的完整表述。
