# 架构综合纲领（Synthesis Charter）

> 本文是 **「博采众长不杂糅」的执行纪律**。六个参考（Redox / Theseus / rCore(zCore) / hubris / seL4 / Zircon）各有所长，但它们在**同一根轴上常常互斥**——全拿就是 Frankenstein。
> 本文锁定三件事：① BerryOS 的**单一中心**（所有决策绕它转）；② **矛盾矩阵**（每个冲突轴只给一个 PICK + 理由）；③ **排除规则**（往后每来一个「cool 借鉴点」怎么判生死）。
> 决策依据回溯 `架构决策.md`（#7/#8/#18/#20/#21/#22–#29）。本文不改 ADR，是 ADR 之上的**综合视角**（#28/#29 即由本文导出）。

## 0. 系统四层速览（BerryOS 长这样）

> 从下往上：第一层内核（地基）→ 第二层系统服务（承包商）→ 第三层运行库（翻译官）→ 应用层（住户）。

```
┌────────────────────────────────────────────────┐
│ 应用层    bsh / berryctl / ripgrep / 用户程序     │ EL0
├────────────────────────────────────────────────┤
│ 第三层    运行库：libc（POSIX 兼容）/ berry-sys   │ EL0（库，链接进每个程序）
├────────────────────────────────────────────────┤
│ 第二层    系统服务：init / 文件系统(/svc/fs) /     │ EL0
│           网络 / 驱动 / PM / trace / AI 策略      │
├────────────────────────────────────────────────┤
│ 第一层    微内核：调度 / 地址空间 / 能力 / IPC     │ EL1 ← 全系统唯一特权层
│           （+ 启动关键 GIC/timer/UART 暂留）      │
├────────────────────────────────────────────────┤
│ 硬件     ARM64                                   │
└────────────────────────────────────────────────┘
```

| 层 | 住什么 | 仓库目录 | 落地时点 |
|----|--------|----------|----------|
| 第一层 内核 | 调度器、页表/VMO、handle 表、channel——**只有机制没有政策** | `kernel/ mm/ sched/ ipc/ arch/` | P0–P3 |
| 第二层 服务 | FS / 网络 / 驱动 / PM / AI 策略——**全是普通进程** | `drivers/ fs/ net/ user/` | P4 起 |
| 第三层 库 | 把 `open/read` 翻译成发 `/svc/fs` 的 channel 消息 | `user/`（libc、berry-sys） | P4–P5 |
| 应用层 | bsh、berryctl、第三方程序（G-eco 关验收对象） | `user/` | P4–P5 |

**一条命令走完全程**（`cat file.txt`）：bsh 解析 → `process_create("cat")` 传能力 → cat 调 `open()` → libc 翻成 channel 消息发 `/svc/fs` → FS 服务经块设备 handle 找 virtio-blk 驱动服务（也是用户进程）→ 驱动经 MMIO 能力摸硬件，数据原路返回。**内核全程只做三件事：调度、查能力、传消息——它不知道"文件"是什么。**

**两条微内核特有铁律**（对照宏内核的心智差异）：

1. **真特权只有两级**：EL1 内核 vs 其余所有人 EL0。二三四层之间无权限高低——FS 服务与 hello world 在 CPU 眼里一模一样，**区别全在手里几张票（handle）**。权限不看你住几层，看你有什么票（见 `能力模型设计.md`）。
2. **层是信任梯子，不是权力梯子**：越往下越少越稳（内核几乎不崩），越往上越多越常崩——但崩了影响越小（app 崩死 app；FS 崩内核监督重启，G1.5 已验"只死自己"）。Linux 反着来：FS/net/驱动全塞第一层，任一驱动 bug 都可能带崩全系统。

> 土话：一楼是内核机房（全楼唯一有钥匙的），二楼一排承包商，三楼起每个程序自带翻译官，顶层随便住人——谁是住户谁是承包商不看出身，看物业发的门禁卡（handle）。

## 1. 单一中心（不可妥协的 pole）

> 删掉这一条，BerryOS 就不再是 BerryOS——是某个别的项目。

**中心 = 可注入的「机制/策略分离」+ 硬件信任边界。**

一句话展开：

> BerryOS = **Zircon 的对象 / 能力 / IPC 机制骨架**，用 **Rust 重写**获得编译期内存安全；再把**策略层**（调度放置、改频、AI 干涉）做成**内核可注入的可插拔面**（共享环 + 能力门控），并用 **capacity 抽象**让同一条放置路径同时服务手表 / 手机 / PC 三端。

这个中心由两个不可拆的半边组成，**两边都不能让**：

| 半边 | 内容 | 谁威胁它 | 守住的动作 |
|------|------|---------|-----------|
| **机制/策略分离 + 可注入** | 内核只有机制（上下文切换 / runqueue / 派发 / 能力）；策略（含 AI、PM）全在用户态，经共享环注入；RT 类屏蔽 | seL4 的单一调度语义、hubris 的协作式、Redox 的 round-robin 都没有这维度 | 调度做成可插拔 trait；AI/PM 走共享环；护栏内核强制 |
| **硬件信任边界** | ASID（每进程 AS）+ EL1/EL0 + 纯能力 + IOMMU/SMMU + PAC/BTI/MTE + 度量启动 | Theseus「编译器=隔离」、hubris「MPU 物理寻址」 | 信任边界永远是硬件，**不是编译器**；Theseus 思想只进进程内 |

**为什么是这条中心，不是别的**：四身份支柱（微内核 + 省电 + AI 原生调度 + PC 高性能）看似四件无关的事，但它们能共存，**全靠这一条中心**——capacity 抽象让三端一条路径（统一省电与高性能），可注入的策略面让 AI 成为一等公民，硬件边界让用户态服务能崩能热换不拖垮内核。砍掉任一半边，四支柱立刻塌掉一半。

## 2. 矛盾矩阵（十轴，每轴一个 PICK）

> 每根轴上，参考们是**互斥**的。这里给 BerryOS 的**唯一选择** + 一句理由。「PICK」是定死的，不是建议。

| # | 轴 | 选项（谁站哪边） | **BerryOS PICK** | 理由（一句话） |
|---|----|------------------|------------------|---------------|
| 1 | **信任边界** | 编译器（Theseus）vs 硬件（Zircon/seL4/hubris） | **硬件** | 要跑 POSIX 子集 / 第三方程序；编译器不是 privilege boundary；Theseus 思想收缩到进程内 |
| 2 | **内核对象粒度** | 极简 ~10 原语（seL4）vs 富对象 ~30–45（Zircon/Redox） | **富对象（v1~26）** | 不做 seL4 全栈证明，富对象换开发效率 + 可观测 + **AI 调度钩子的安身之处**（极简内核放不下 AI ABI） |
| 3 | **地址空间** | 单 AS（Theseus）vs 每进程 AS（Zircon/seL4） | **每进程 AS（ASID）** | 隔离靠硬件，不是靠编译器；与 #1 同根 |
| 4 | **IPC 主形态** | 同步 RPC（Redox scheme / hubris rendezvous）vs 共享内存优先 | **分层，不统管** | channel/event/VMO 给通用；**共享环独占热路径**（PM/AI 快路径）——**任何 IPC 借鉴不得让一种形态统管所有流量** |
| 5 | **调度模型** | 协作 / 固定优先级（hubris）/ RR（Redox）vs 全可抢占可插拔 | **可插拔 trait + 全可抢占 + capacity + EEVDF 底座 + intent 两段式（ADR #42）+ EAS + tickless** | 这正是 BerryOS 的差异点；Redox/hubris 调度是**反例教材**；intent 叠加在公平底座上、永不替代（#42：公平是机制默认，intent 是策略输入） |
| 6 | **动态性** | 编译期固定（hubris）vs 运行时动态（Zircon） | **运行时动态** | 要 `process_create` + 用户态 pager + demand paging(v2+)；hubris 的「静态」只借给 **boot 静态服务集 + 度量启动层** |
| 7 | **隔离恢复** | 服务监督重启（hubris generation/DEAD）vs 能力撤销（seL4 CDT/Revoke） | **两者融合** | `handle=(obj, gen)` + DEAD 做**服务监督**；CDT 式 mint 降权 / revoke 子树回收做**权限派生** |
| 8 | **syscall 边界** | Rust 原生（Redox）vs C-ABI 约定 | **C-ABI（`extern "C"`+`#[repr(C)]`）** | Rust ABI 不稳定；两端皆 Rust；ABI 一旦发布不被编译器版本牵着走 |
| 9 | **安全保证手段** | 全栈逐行证明（seL4 Isabelle）vs 类型 + 轻量模型检验 | **TLA+/loom 锁机制不变量 + Rust 类型锁内存安全** | 形式化的 ROI 在锁「不可委托核心机制」，不在逐行证明整个内核；各司其职，留空间给富对象与 AI |
| 10 | **内存后备枚举** | 单一 VMO（Zircon）vs 5 类 Provider（Redox grant） | **采纳 Redox 5 类细化 VMO 后备** | CoW / 共享 / MMIO / 跨 AS / fmap 显式区分，比单一 VMO 精细，直接落 `mm/` |

## 3. 取 / 留总表（六个参考一览）

> 「取」是可落地的具体机制；「留」是**坚决不取**（写明与哪条 ADR 冲突）。

### Redox（MIT，Rust，0.9.0，活跃）
- **取**：grant 5 类 Provider → VMO 后备枚举（CoW/shared/MMIO/external/fmap）；scheme/URL 命名空间 + 命名空间沙箱（已锁路径式命名空间，借其「按协议而非按树区分资源」）；PageInfo 引用计数 + CoW→shared 迁移；`event:` 统一事件源注册范式。
- **留**：**整个调度器**（RR/单队列/无 tickless/无 capacity/无可插拔 trait——全面冲突，当反例）；FD 即能力（无 rights 位，退步，留 Zircon handle+rights）；scheme 同步 RPC 当通用 IPC（与共享环硬约束冲突）；纯 Rust syscall 边界（留 C-ABI）。

### Theseus（MIT，Rust，OSDI'20）
- **取**（**仅进程内**）：state-spill 作设计审计尺（问「这 IPC 端点在缓存客户端进度吗？」）；drop-only 清理（panic/kill 路径也覆盖）；分布式 bookkeeping（rendezvous 状态以 owned 数据传回客户端）；cell=可重定位服务 crate + 依赖 manifest。
- **留**：单 AS / 单特权级（与每进程 AS + EL1/EL0 + 纯能力 + SMMU 根本冲突）；跨 syscall 的 lossless interface（BerryOS 故意 C-ABI，**不留 Rust lifetime 跨边界**）；「信任编译器=隔离」（编译器不是特权边界）。
- **分层解**：Theseus 的 intralingual / spill-free 思想**收缩到单进程内部**——进程内吃状态管理红利，进程间吃 Zircon 式 HW+能力隔离，两者分层不冲突。

### rCore / zCore（zCore=MIT 可读可抄；rCore-Tutorial=GPL 只读思路）
- **取**：**zCore 三层 crate 拆法**（`hal/` + `zircon-object` + `zircon-syscall`）1:1 作 v1 crate 边界模板（与 BerryOS 天然同构，协议干净）；zCore HAL 之上 ~20 个 `unsafe` 块的收敛模式（作 `unsafe` 纪律 code review 基线）；rCore-Tutorial 的 boot asm + `TaskContext`/`TrapContext` 数据结构（平移 aarch64，首行换 EL2→EL1 降级 + `dmb/dsb/isb`）；zCore LibOS 模式（内核当用户进程跑，做 host 端单测）。
- **留**：`UPSafeCell` 单核假设（多核数据竞争地雷，与每核 runqueue + 细锁冲突）；裸 RR；**GPL-3.0 代码一行不进**（rCore-Tutorial、原 rCore Linux 兼容路径）；zCore 协程当主调度（违全可抢占 + RT）；「Linux 兼容」执念（v1 无 fork、不跑 Linux 二进制）。

### hubris（MPL-2.0/Apache-2.0，Rust，~2000 LOC 内核）
- **取**：**generation-number + `DEAD` 错误码 + 栈 scribble** → BerryOS 能力撤销 / 服务监督底座（`handle=(obj, gen)`，旧代调用返 DEAD→重试/降级，无缝对接 AI/PM 崩→降级保活）；**驱动全用户态 task + supervisor 重启**（最干净参考实现，搬 `jefe` 模式）；**Idol IDL → 生成桩**（`berry_*` 从 IDL 自动镜像 `berry-sys`，消灭手写不同步）；boot 关键服务集可静态度量。
- **留**：**编译期固定任务图 / 零分配 / 物理寻址**（与运行时 `process_create` + pager + demand paging + 每进程 AS 正面冲突，不可调和）；同步阻塞 IPC / 同优先级协作式（与 channel+event+共享 VMO 异步、全可抢占相反）。
- **分层解**：generation 协议是**协议**，不绑定静态 task——保留协议语义，但「安全重启是否保证资源可用」分层：boot 静态服务集（PID 有界、度量启动覆盖）用 hubris 式保证；动态进程由 supervisor 按能力树定重启策略；demand paging / 动态堆与重启协议**正交**。

### seL4（GPL v2，C + Isabelle，已证明）
- **取**：**能力派生纪律**（永不增权 + Mint 降权/badge + Revoke 递归回收子树）→ 进 BerryOS `handle=u32/rights=u64`（但用 Zircon 式进程槽位表，**不要** CSpace guarded page table）；形式化方法论（**边界明确**：TLA+/loom 做「机制不变量」模型检验，不做全栈 Isabelle refinement）；配置依赖意识（G0–G5 显式建模恶意 cap 流转）。
- **留**：**~10 极简原语**（BerryOS 富对象——理由：极简是为可证明，BerryOS 不走全栈证明，富对象换效率/可观测/AI 钩子，**极简内核无处安放 AI ABI**）；单一调度语义（MCS SC 时间隔离好但策略贫乏，容不下 capacity/EAS/EEVDF/快慢循环）；GPL v2 C 代码（只看思路）。

### Zircon（MIT/BSD，C++，BerryOS 直接对标）
- **直接继承**（设计同源）：VMO/Vmar、handle(u32)+rights(u64)、channel+eventpair+signal、Job/Process/Thread、`object_*` 合并、路径式 namespace、**用户态 pager**、**用户态驱动**、**无 fork**、能力只收窄。
- **砍 / 改**：语言 C++→**全 Rust**（内存安全从「靠人」变「靠编译器」）；syscall 表面 ~100→**v1~26**（更激进 `object_*` 合并）；调度增量（Zircon 只有 fair+deadline）→**capacity + EEVDF/EAS + 不对称放置 + tickless day-one + 每核 rq + 细锁 + 全可抢占**；**AI 原生调度**（Zircon 完全空白，BerryOS 增量）；PM 通路 Zircon FIDL→**BerryOS 共享环**（直击 Zircon PM 走 FIDL 的延迟痛点）。

## 4. 排除规则（防杂糅，往后每个借鉴点过这 8 条）

> 这是把「博览众长」从冲动变成纪律的**闸门**。任何「参考里有个 cool 的点想搬进来」先过这 8 问：

1. **轴 + PICK**：它落在矛盾矩阵哪一轴？那一轴的 PICK 是不是它？不是 → 不拿（或先改 ADR，写明取舍，再拿）。
2. **中心**：它与「机制/策略分离 + 硬件信任边界」冲突吗？冲突 → **一律 reject**。
3. **Theseus 边界**：intralingual / spill-free 思想只进**进程内**，不跨进程间 / 硬件边界。
4. **IPC 不统管**：任何 IPC 借鉴不得让「单一形态统管所有流量」——热路径（PM/AI）永远独占共享环。
5. **seL4 用途**：seL4 纪律用于「锁机制不变量」，**不用于「极简化整个内核」**。
6. **hubris 静态边界**：静态 / 零分配只进「boot 静态服务集 + 度量启动层」，**不渗透到动态进程 / pager / demand paging**。
7. **协议洁净**：GPL 代码一行不进；rCore-Tutorial（GPL）只读思路，zCore（MIT）可读可抄结构。
8. **关卡归属**：它进 G0–G5 哪一关验证？**找不到关卡 = 范围泄漏，往后拖正确性，先不拿。**（ADR #42 判例：band/intent 的正确性归属 = **G3–G5 附加断言 + `测试策略.md` §9 模型检查扩展**，不进任何关卡通过条件——「既有关卡 + 附加断言」是新不变量的范式答案，不是新开关卡）

> 第 8 条是范围泄漏的最强哨兵：一个「增强」找不到正确性关卡归属，往往就是杂糅的入口。

## 5. 三个「分层借用」的解（看似矛盾，实可调和）

这三处是参考们**最像冲突、但其实可分层调和**的地方——也是本文的精华：

| 看似冲突 | 解（分层） |
|---------|-----------|
| **Theseus 单 AS** vs BerryOS 每进程 AS | Theseus 的 spill-free / intralingual 思想 **收缩到单进程内部**（每个服务进程本就是一个「Rust 地址空间内的 intralingual 世界」）；进程间仍保留 HW + 能力隔离。进程内吃 Theseus 红利，进程间吃 Zircon 隔离。 |
| **hubris 静态任务图 / 零分配** vs BerryOS 运行时动态 | hubris 的 **generation 协议是协议不是静态**——保留 `handle=(obj, gen)` + DEAD 语义；「重启资源可用保证」分层：boot 静态服务集用 hubris 式保证，动态进程由能力树监督，demand paging 与重启正交。 |
| **seL4 全栈证明** vs BerryOS 富对象 + AI | 形式化**只锁不可委托核心机制**（cap 派生/撤销原子性、IPC 状态机、调度护栏不变量），用 TLA+/loom/shuttle；**内存安全交给 Rust 类型 + unsafe 收敛**（Rust 已是比 C 高得多的基线）。各司其职，留空间给富对象与 AI。 |

## 6. 第一步行进（v1 落地骨架，对照 `路线图.md` Phase 0）

研究落地到**第一行可构建代码**该怎么搭（这是「最好的方案」的工程起点）：

- **crate 骨架 = zCore 三层 1:1 平移**：`arch/aarch64/`(HAL) + `kernel/`(zircon-object 等价) + `kernel/`(zircon-syscall 等价) + `user/berry-sys`(FFI 镜像)。MIT，可读可抄**结构**。
- **boot 入口**：`global_asm!` 第一行 `mrs CurrentEL` EL2→EL1 降级（关 MMU/cache、写 `sctlr`、`eret`）→ 早期 Rust → UART(PL011 @0x09000000) 打 "BerryOS boot"。骨架用 rCore-Tutorial 模板（**平移不照抄 GPL 代码**）。
- **`unsafe` 基线**：HAL 之上收敛到 ~20 块（对齐 zCore），code review 卡这条；外层包安全 API（CLAUDE.md「安全 Rust 外壳 + 小 unsafe 核」）。
- **ABI 生成**：用 Idol 思路从单一 IDL 源生成 `berry_*` 原型 + `berry-sys` Rust 镜像，CI bindgen 双向校对（消灭 `syscalls.h` 与 `berry-sys` 手写不同步）。
- **服务监督底座**：从 v1 就埋 `handle=(obj, gen)` + DEAD 错误码的协议形状（哪怕 v1 还没真重启），为 v3 AI/PM 崩→降级保活铺路（hubris）。
- **调度自写**：v1 先 round-robin + 一个 fair 类桩 + tickless idle(WFI)；**不抄** Redox RR 实现也不抄 zCore 协程——trait 留好，M0 共基座。
- **进程内审计尺**：写每个 IPC 端点 / 服务时，过 Theseus 的「state-spill」一问（它在缓存客户端进度吗？）——这是设计 review 的固定检查项。

## 7. 一页速查（贴在墙上）

```
中心：可注入的「机制/策略分离」+ 硬件信任边界。删掉就不是 BerryOS。

矛盾矩阵 10 轴的 PICK：
 1 信任边界 → 硬件（非编译器）
 2 内核粒度 → 富对象 v1~26（非 seL4 极简）
 3 地址空间 → 每进程 ASID（非 Theseus 单 AS）
 4 IPC → 分层：channel/event/VMO 通用 + 共享环独占热路径（不统管）
 5 调度 → 可插拔 trait + 全可抢占 + capacity + EEVDF 底座 + intent 两段式(#42) + EAS + tickless
 6 动态性 → 运行时动态（hubris 静态只借 boot 层）
 7 隔离恢复 → hubris generation/DEAD（监督）+ seL4 mint/revoke（权限）融合
 8 syscall 边界 → C-ABI 约定（非 Rust 原生）
 9 安全手段 → TLA+/loom 锁机制不变量 + Rust 类型锁内存安全（非全栈证明）
10 内存后备 → Redox 5 类 grant 细化 VMO

排除 8 问：轴PICK？冲突中心？Theseus仅进程内？IPC不统管？seL4只锁不变量？
         hubris静态只借boot层？GPL不进？哪关G0-G5验证？

分层借用 3 解：Theseus 进程内 / hubris 协议非静态 / seL4 锁机制非极简。

v1 起点：zCore 三层 crate + aarch64 EL2→EL1 boot + unsafe≤20 + IDL 生成 berry_* + handle=(obj,gen) + 调度自写。
```
