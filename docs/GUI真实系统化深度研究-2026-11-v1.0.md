# GUI 真实系统化深度研究（多窗口 / 输入 / CJK / 应用壳）——v1.0

> 版本：1.0（2026-11-07）
> 基线：`/tmp/gui-main` @ `023c96a`（官方 Browser/中文标签/GUI8 真链收官）
> 性质：深度研究报告 + 下一阶段实施裁决。本文只研究，不声称未实现功能已完成。

## 0. 结论摘要

1. **桌面本体不是静态 mock**：QEMU/virtio-tablet → `gui-inputd` →
   `berry-launcher` → `berry-ui` → APP_SPAWN → 真实用户进程 → fs RPC →
   FAT `LAYOUT.JSN` → 宿主读回，这条链已经由 GUI8 机器验收闭环。
2. **当前最大假绿面不在桌面，而在 app 语义**：官方图标与中文名下面的
   `appstub` 只消费 env 后立即 `exit(0)`；`views/main.bui` 只是注释文本，
   没有任何运行时 UI 消费。因此“看起来像 Browser/Photos”不等于业务可用。
3. **多窗口尚未真实并发**：WM 表协议存在，`gfxdemo` 能 CREATE/SET/TABLE_GET，
   但没有调用 DESTROY；`gui-wmd` 明确按单 wm 客户端串行假设设计；
   `guifbd` 忽略 `surface_id` 并假定提交 buffer 与全屏同几何；inputd 的
  窗口命中只做内存计数旁注，不改 wire、不路由。
4. **输入链真实但有队列压力缺口**：eventq 深 16，服务空闲 tick 100ms；
   pump 内部队列 32；INPUT_POLL 每响应最多 3 个事件。空闲期超过 16 个
   设备事件会尾部静默丢弃，press/release 不完整时可能留下接触态。
5. **3500 常用 CJK 当前 91,292B rootfs 余量装不下**；但先把两个 std 测试
   app（APPDEMO 332,008B + APPQUIET 318,760B ELF）改 no_std，预计可释放
   约 580–610KB，足以放下 **32×48 / 4 级抗锯齿 / 64 字随机页压缩**全量
   3500 字包（估算约 470–485KB 含索引与解码代码），无需降低壁纸分辨率。
6. **下一刀建议**：先做“真实窗口生命周期 + 输入压力 + rootfs 回收”三件，
   再做 Browser honest shell。不要先做网页引擎，也不要用静态截图冒充 app。

## 0b. Phase 1 session/owner 执行结果（2026-11-07 同日落地）

- **协议**：新增 `WM_CONNECT(0x66)` 与 `ST_DENIED(7)`。客户端在 broker
  通道随行迁移 `[per-session channel endpoint, self Process handle]`，
  后续 WM/present/hdi 全走专通道；wmd 静态 session 表 v1 帽 4。
- **所有权**：窗口表项新增 owner session；CREATE 绑定 owner，
  SET/DESTROY 非 owner 精确 `ST_DENIED`。GETINFO/TABLE 快照仍全局只读。
- **死亡清理**：wmd 同时 wait session 通道 READABLE 与 Process
  TERMINATED；进程退出时 `destroy_owned(owner)` 一次摘除全部 owned 窗。
- **真链负例/正例**：gfxdemo 开两个 session。session 2 修改 session 1
  窗口必须 `WMDENY ok`；session 1 显式 DESTROY 后表回空 `WMDTY ok n=0`；
  session 2 再建孤儿窗并直接退出，wmd 必须打出
  `WMDEAD ok id=2 wins=1`。launcher 为 session 3。
- **验收**：smoke-image 85/85 PASS；GUI8 基础标记扩到 14，三 Boot 与
  normal boot 均要求 WM session 生命周期族；host/ABI/docs 门全绿。

## 0c. Phase 2 两真实窗口合成执行结果（2026-11-07 同日落地）

- **合成面**：gui-wmd 创建全屏 XRGB8888 composition VMO，并成为 guifbd
  唯一 present client。session SUBMIT 不再直透 guifbd，而是先按 owner
  window 拷入合成 VMO，再以 `surface_id=0` 聚合提交。
- **surface 语义**：`surface_id=0` 为全局桌面；非 0 必须是当前 session
  拥有的可见窗口 id。窗口 buffer 为窗口局部 tight stride，damage 为
  window-local 坐标；wmd 裁剪后平移到全局 composition。
- **真实双窗**：gfxdemo session 1 创建左半屏窗口，session 2 创建右半屏
  窗口，二者分别渲染、分别 SUBMIT/FRAME_CALLBACK/RELEASE，并获得两个
  不同 guifbd token，打 `WM2FRAME ok n=2`。
- **反 mock 负例**：session 2 用 session 1 的窗口 id 提交 surface 必须
  `WMSDENY ok`（present surface owner 面）；此前 WM 域已有 `WMDENY ok`。
- **视觉证据**：QEMU 在 `WM2FRAME` 后截图，左窗顶带 `(127,0,0)`、右窗
  顶带 `(0,127,255)`，右底条 `(191,90,0)`；截图：
  `https://h.uguu.se/CRjzjKEo.png`。
- **验收**：smoke-image 87/87 PASS；GUI8 三 Boot + normal boot PASS；
  host/ABI/docs 门全绿。rootfs 32,837,444B，余 716,988B。

## 0d. Phase 3 输入 owner 路由执行结果（2026-11-07 同日落地）

- **协议**：新增内部 `INPUT_ROUTE(0x22)`（inputd→wmd 原始全局坐标事件
  批）；`WM_CONNECT` 随行 handle 扩为 `[WM endpoint, input endpoint,
  self Process]`，WM RPC 与输入分通道，避免异步 poll 与 present 响应错配。
- **wmd 权威路由**：DOWN 用 WM 表 hit-test 选 owner；MOVE/UP/CANCEL 按
  pointer 粘滞锁；无窗命中落 SYSTEM 桌面 session；窗口事件坐标/历史采样
  全部平移为 window-local；锁定窗失踪合成 CANCEL。
- **队列与死亡**：每 session 16 深输入环，溢出打 `WMIDROP bad`；Process
  TERMINATED 清窗同时清输入锁/队列/专通道。
- **真链验收**：launcher 为 session 3（桌面）；仅在 GUI8 哨兵模式另开
  APP session 4，在右下角建可见窗（常态 boot 不留隐形输入占位）。GUI8 先验桌面 CLICK/SWIPE 均出
  `WMROUTE ok sid=3 window=0`；再 QMP 点入 APP 窗，必须出
  `WMROUTE ok sid=4 window=<id>`，APP 输入端收到 `WMROUTEWIN` 且坐标
  在窗口内（实测 100×64 窗中 (49,31)）。
- **验收**：GUI8 三 Boot + normal boot PASS；smoke-image 87/87 PASS；
  host/ABI/docs 门全绿。rootfs 32,846,420B，余 708,012B。

  → berry-gfx DisplayList

  → ramfb

## 3. 多窗口深度分析

### 3.1 现有能力

`gui-wmd/src/table.rs` 已有：

- `WM_GETINFO`
- `WM_CREATE`
- `WM_DESTROY`
- `WM_SET`
- `WM_TABLE_GET`
- `WM_TABLE_WAIT`
- 两层窗 / Z / parent / group
- AVOID_SYS 有效几何裁剪
- focus 接管与归还
- version 单调与 snapshot

### 3.2 硬缺口

#### G1：没有客户端身份与所有权

`WmTable::Win` 没有 owner/client/session。任何能打到 wm_srv 的客户端理论上
都能按 id SET/DESTROY 别人的窗口。单客户端时代可接受，多 GUI app 时代不可接受。

#### G2：gui-wmd 明确单客户端假设

`main.rs` 头注写明：

- wm 客户端恰一个；
- serve 单线程；
- present 中继阻塞期间不可能处理另一 CREATE/SET；
- 后刀第二客户端需评估 per-request 快照戳或拆线程。

当前 wm_srv/push_srv 两路 wait_many 不能直接扩展成多个 app 客户端。

#### G3：gfxdemo 没有 WM_DESTROY

`encode_wm_destroy_req` 只有协议测试调用，生产消费者没有调用。
gfxdemo 正常退出后，WM 表里可能残留窗口。当前不炸是因为输入命中只做旁注、
launcher 没注册窗口，不代表生命周期正确。

#### G4：guifbd 是全屏单 surface

`PresentReq::Submit { surface_id: _ }` 在 `guifbd` 中被忽略。
`submit` 强制：

```text
buffer size >= fullscreen stride * height
```

并把 damage 直写全屏 framebuffer。两个客户端直接 relay 到 guifbd 会互相覆盖。

#### G5：wmd 只是 present 透传，不合成

`gui-wmd/src/relay.rs` 原样转发 SUBMIT。它没有：

- per-window buffer 元数据；
- clipping；
- Z-order composition；
- damage union；
- per-client credits；
- client death buffer release。

#### G6：inputd 命中不路由

`wm_annotate`：

- DOWN 做窗口命中；
- MOVE 粘滞锁定；
- UP/CANCEL 解锁；
- 但“不改 wire 事件”，只累计 `n_hit/n_stale/n_gone/n_miss`。

因此目前没有多客户端事件路由。

### 3.3 推荐多窗口路线

不要一步做通用 Android 式合成器。分四刀。

#### M1：生命周期正确化（小刀，先行）

1. `gfxdemo` 在成功建窗、呈现、hdi mini 序后显式 `WM_DESTROY`。
2. 新增 smoke 标记：
   - `WMDTY ok n=0`：gfxdemo 退出后 WM 表必须回空；
   - 或 `WMDESTROY ok id=N`。
3. launcher 创建自己的全屏 APP 窗口，退出/监督重启路径 destroy。
4. GUI8 断言：
   - gfxdemo destroy 在 exit 前；
   - launcher `WM_CREATE` 成功；
   - snapshot count 不残留旧窗口。

这一刀不解决并发，但先把“表项不会泄漏”变成机器不变量。

#### M2：WM session broker

使用现有 wm_srv 作为连接入口，避免新增 gift 槽（当前 env gift 已满 8/8）。

新协议建议：

```text
WM_CONNECT v2
request: op + client_type + reserved
attach:
  [0] session server end（客户端自建 channel pair 后迁入）
  [1] self process handle（用于 TERMINATED 死亡观察）
reply: session_id + caps/version
```

wmd 内部维护 session 表：

```text
session_id
session channel
process handle
owned window ids
last version
input queue / present state
```

所有权规则：

- CREATE 绑定 owner session；
- SET/DESTROY 默认只允许 owner；
- launcher/desktop 可有 privileged 系统位；
- session process TERMINATED → auto destroy owned windows + release aliases。

这不是通用动态线程模型，仍是单线程 wmd；只是把“多个客户端身份”
先收进协议与表。

#### M3：最小两窗口呈现（不重叠、不同步 resize）

第一版约束：

- 最多 2 个真实窗口；
- 窗口不重叠；
- buffer 几何等于当前窗口有效几何；
- 不支持呈现期间 resize；
- `surface_id` 解释为 window_id；
- wmd 成为 guifbd 唯一 present 客户端。

wmd 内部流程：

1. app SUBMIT 附 window buffer VMO；
2. wmd 校验 owner、window、damage；
3. clip 到有效几何；
4. 写入 wmd 拥有的全屏 composition VMO；
5. damage union 转发 guifbd；
6. FRAME_CALLBACK 后把 app buffer alias 归还 app；
7. guifbd credits 只属于 wmd，不被 app 争抢。

好处：

- guifbd 全屏协议可零改；
- app 不需要 8.3MB 全屏 buffer；
- 第一版不处理遮挡重合成；
- 能先机器验证两个真实进程同时呈现。

后续重叠窗口再引入 per-window backbuffer 或限制“移动时整屏 recomposition”。

#### M4：事件路由

长期正确形态：

```text
gui-inputd
  → wmd 是唯一 INPUT 客户端
  → wmd 根据 WM 表 pointer lock / focus
  → per-session input queue
  → launcher 或 app 消费
```

优点：

- app 不直接拿全局输入，避免输入泄露；
- wmd 是窗口与焦点权威；
- stale snapshot 问题集中在一个服务；
- 与桌面/应用窗口语义一致。

短期不建议的替代方案：

- inputd 在 PointerEvent 里加 `target_window_id`，所有 app 都订阅全量输入
  再自行过滤。这能快速测试，但输入泄露与乱序竞争会变成协议债。

## 4. 输入压力深度分析

### 4.1 当前参数

`drivers/bins/gui-inputd/src/main.rs`：

- virtio eventq `QSIZE=16`
- DMA ring/buffer 共 8KiB
- 空闲 `SVC_TICK_NS=100ms`
- INPUT_POLL 内部步进 `1ms`
- poll 阻塞帽 `30s`
- pump `QUEUE_CAP=32`
- 协议每次最多 `INPUT_EVENTS_MAX=3`
- wmd snapshot stale 帽 `10s`

### 4.2 已知问题

注释已明确：

```text
eventq 预投 QSIZE=16；QEMU 逐事件取描述符；
空闲期超过 16 事件/tick 时尾部静默丢弃；
press 送达而 release 丢弃可致接触态滞留；
```

INPUT_POLL pending 时，`serve_poll` 每 1ms harvest，压力窗口小；
但 launcher 在渲染/重启/无 pending 时仍有 100ms 空闲收割间隔。

### 4.3 第一刀

1. eventq 目标深提到 64（若 QEMU `QueueNumMax` 允许）：
   - ring：desc 1024B + avail ~132B + used ~518B，仍 <4KiB；
   - buffers：64×8B = 512B；
   - DMA 仍可保持 8KiB。
2. pump `QUEUE_CAP` 提到 128 或 256。
3. 暴露 dropped 计数：
   - 启动诊断；
   - INPUT_POLL EAGAIN/subscribe ack 可选 telemetry；
   - GUI8 burst 标记。
4. GUI8 新增 burst 相：
   - 无 INPUT_POLL pending 时注入 20/64/128 个 move；
   - 后续 click 必须恢复；
   - UP/CANCEL 后无 stuck contact；
   - 断言 dropped 计数与宿主注入数对账。
5. 若 QueueNumMax < 64，动态取 min(qmax,64)，不能硬编。

结构性根治是 virtio IRQ 唤醒，但应作为独立刀，避免与本轮 GUI app 生命周期混做。

## 5. CJK 字库量化研究

### 5.1 实测样本

宿主用 Noto Sans CJK SC 136px 4× 光栅化，再 box filter 到目标 cell。
样本为 U+4E00 起连续 3500 个汉字，代表复杂度偏保守。

### 5.2 压缩实测

| cell / 格式 | 原始大小 | zlib -9 | 结论 |
|---|---:|---:|---|
| 32×48 A8 | 5,376,000B | 1,197,681B | 当前预算不可能 |
| 32×48 A4 | 2,688,000B | 310,430B | 需 rootfs 回收后可行，质量较好 |
| 32×48 A2 | 1,344,000B | 436,957B | 推荐第一阶段全量格式 |
| 32×48 1-bit | 672,000B | 204,419B | 体积小但失去 AA |
| 16×32 A8 | 1,792,000B | 425,117B | 小字号仍偏贵 |
| 16×32 A4 | 896,000B | 248,428B | 小屏可考虑 |
| 16×32 A2 | 448,000B | 175,609B | 极省，1080p 标签偏糊 |
| 16×32 1-bit | 224,000B | 61,174B | 当前余量可容纳但硬边回归 |

随机页开销很小：64 字/页 zlib 只比整流 zlib 多约 0.2–1%。

### 5.3 推荐格式

**32×48 A2 + 64 字页 zlib/deflate + page cache**

估算：

- 3500 字 A2 page64 压缩：约 438KB
- codepoint 排序表：3500×3B ≈ 10.5KB
- page offset/index：<1KB
- inflate/取 nibble 代码与测试：约 20–35KB
- 合计：约 470–485KB

运行时：

- 每页解压后大小 `64 × 32×48 / 2 = 49,152B`
- 只缓存 1 页即可；
- coverage 值域 0/85/170/255；
- 不需要 FreeType、浮点或整表展开。

### 5.4 为什么先回收 APPDEMO/APPQUIET

当前两个 GUI8 测试 app 是 std ELF：

- `APPDEMO bin/appdemo`：332,008B
- `APPQUIET bin/appquiet`：318,760B
- 合计：650,768B

功能很少：

- APPQUIET：argv 自检后退出；
- APPDEMO：argv 自检、console 两行、读 `/etc/mtab`、退出。

改 no_std / berry-libc direct syscall 后估算：

- APPQUIET ≈5KB；
- APPDEMO ≈40–60KB（需 fs RPC）；
- 可释放约 **580–610KB**。

于是：

```text
当前余量 91KB + 测试 app 回收 ~600KB
≈ 691KB
> 32×48 A2 全量 3500 字包 ~485KB
```

还余约 200KB，不需要降低壁纸分辨率或把 ASCII 降成硬边。

### 5.5 实施注意

1. 常用字表应采用真实频率表，不能用 U+4E00 顺序替代；本报告只测压缩率。
2. 字体页须有 SHA-256 与生成器 guard。
3. `GlyphA8` 需要扩展为 coverage enum 或 A2 atlas：
   - painter 不能假设每像素一字节；
   - raster 直接读 high/low nibble。
4. `TextMetrics` 目前全码点等宽；CJK/ASCII 混排后续可改为 per-codepoint width。
5. 先做 golden：
   - 每页首/中/尾字 bbox；
   - coverage 金丝雀；
   - 缺字 U+FFFD；
   - 中文标签截图像素对拍。

## 12. 终局判断

当前 BerryOS 桌面已经是“真系统桌面”，不是图片；但系统 app 还处在
“官方资产 + 真进程空壳”阶段。下一阶段的核心不是继续调视觉，而是把
**WM session、真实 app frame、输入路由、client death cleanup** 变成机器
验收。与此同时，先回收 APPDEMO/APPQUIET 的 600KB 测试 app 预算，为
3500 常用 CJK A2 字库打开空间。
