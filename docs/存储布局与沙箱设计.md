# 存储布局与沙箱设计（分区 · 目录布局 · 应用沙箱 · 程序形态）

> 回答三件事：**盘怎么切（零分区）、目录怎么摆（四棵树）、程序怎么管（一个本质 + 三个轴，树即登记簿）**。
> 核心论点：**分区不进词典——「卷」= 命名空间挂载点，不是块设备切肉；每字节文件都有唯一的主人——归属=位置，反查 O(1)；沙箱是能力不是承诺——没申请的 handle 根本不存在**。
> 挂钩：`架构决策.md` #45（本文索引）+ #6（路径命名空间 = 卷的语义来源）+ #27（FS 引擎）+ #43/#44（应用模型——app 树的协议面）。`文件系统设计.md` 讲 FS 引擎（盘上格式 / VFS / pager），本文是它的**上层布局**；`兼容子系统设计.md` 的存储面在 §5 收口。

## 0. 病根诊断：老系统乱在三个「混」

| 系统 | 病灶 | 归类 |
|---|---|---|
| Linux 分区（/boot /home /var /usr swap EFI…） | 每个分区一段历史：/boot 因老 bootloader 读不了大盘、swap 因类型不同、/home 为重装不丢数据、/var 防日志塞爆 / | **机制混**：块层概念（固定大小切盘）泄漏进用户视野 |
| Unix 目录（/bin /sbin /usr/bin /usr/local /opt…） | 1973 年一块盘满了把 /usr 挪第二块盘——临时应急变 50 年标准，usrmerge 补 40 年 | **所有权混**：按历史时期分目录，不按「归谁」分 |
| Windows（Program Files ×3 + AppData 三兄弟 + ProgramData + 注册表） | 同一应用的设置散四处，卸载永远残留 | **所有权混 + 权限混**：应用「可以」到处写（ACL 事后检查）而非结构性拿不到 |
| macOS（/System /Library ~/Library 五套并存） | 方向对了（bundle + Containers），新旧两代叠着没清场 | 机制混 |
| Android（十几块分区 + /sdcard 后补 scoped storage） | A/B OTA 与 verified boot 的实现细节泄漏成用户概念；「先放开后收紧」补课代价极大 | 机制混 + 权限混 |
| iOS（沙箱树 + 用户数据区 + picker 授权） | 最接近正确答案——验证了本文的主路线 | —— |

三个「混」各挨一刀（§1–§3）：**所有权混→四棵树按归属分；机制混→零分区、卷是划线不是切肉；权限混→能力结构性缺席**。

## 1. 第一刀：零分区（「分区」这个词不进词典）

**一个存储池，整个 flash = 一个文件系统。** 分区当年解决的每件事我们都有更好的非分区解法：

| 当年分区解决的事 | 我们的解法 |
|---|---|
| /boot 单独（bootloader 读不了大盘） | boot ROM 按固定偏移加载——SoC 契约不是 OS 分区（真机上那块区域由芯片决定，我们不管它叫分区） |
| swap 单独（文件系统类型不同） | **无 swap**：MB 级手表上 swap 伤闪存又慢；内存不够用**墓碑**（`应用模型设计.md` §4.1——杀进程留状态）。墓碑就是我们的 swap：粗粒度、app 感知、省电版 |
| /home 单独（重装不丢数据） | 系统更新 = 只读系统卷原子换，用户卷根本不动——效果相同不用切盘 |
| /var 单独（防日志塞爆 /） | 容量配额 + `cache/` 可驱逐；CoW FS（#27）快照回滚兜底 |
| Android 十几块（A/B OTA + verified boot） | 系统卷只读 + 双目录切换（`sys/boot/` 指针）或 v2 快照；度量链（#24）不依赖分区 |

**「卷」= 命名空间挂载点，不是块设备**——决策 #6（路径式命名空间）的兑现：FS 是用户态服务，「卷」就是挂在路径上的服务实例。物理上零切分，逻辑上想挂几棵挂几棵。**分区是拿刀切肉，我们是拿笔划线**——划错擦掉重来，肉完好无损（macOS APFS 多卷共享池空间是这个思路的块层版；我们把「卷」升到命名空间层，连块层都不用动）。

## 2. 第二刀：四棵树（谁拥有，谁树下）

按**所有权**分目录，不按「什么类型的文件」分：

```
/                        ← 命名空间根（挂载与服务发现统一，决策 #6）
├── sys/                 ← 【系统拥有】
│   ├── kernel/          ← 内核镜像（度量启动锚点，决策 #24）
│   ├── svc/             ← 系统服务本体（appd/display/fs/net/pmu…，各自也是 manifest）
│   ├── bin/             ← 系统工具（bsh/hexyl 家族——rootfs cpio 的演化归宿）
│   └── boot/            ← boot 指针 / A-B 目录（系统更新用）
├── apps/                ← 【应用拥有】一 app 一棵树：安装=建树，卸载=删树
│   └── com.example.notes/
│       ├── manifest.toml   ← ADR #44 能力申请表（树根唯一必选项）
│       ├── bin/            ← 代码（对 app 自己只读——升级走 appd 原子换树）
│       ├── res/            ← 资源（图标/字体/布局）
│       ├── data/           ← 私有数据（可写）= manifest 里 $appdata 指的就是这里
│       └── cache/          ← 私有缓存（可写、可驱逐、卸载带走）
├── user/                ← 【人拥有】照片/docs/表盘/下载——不属于任何 app
│   └── main/            ← v1 单用户；多用户 = 加目录不加机制
│       ├── media/  docs/  watchfaces/  downloads/
├── tmp/                 ← 【没人拥有】重启即空（tmpfs 语义，唯一全局可写区）
└── svc/                 ← 服务发现挂载点：/svc/fs /svc/net…（决策 #6）
                           路径皮，底下是 channel，不占磁盘
```

口诀：**sys 系统的、apps 应用的、user 人的、tmp 没人的**。规范：目录名全小写、大小写敏感（不继承 macOS/Windows 的大小写混淆病）。

几个「不存在」——每条砍掉一坨历史包袱：

| 不存在的东西 | 替代 |
|---|---|
| `/etc`（系统+应用配置大杂烩，卸载必残留） | 系统配置 = `sys/` 下声明式 TOML；应用配置 = 它自己 `data/` 里的事，系统不管内容 |
| 注册表 | manifest（安装时翻译成 handle 授权集，ADR #44）；设置类走设置服务（v2） |
| `/usr/lib` 共享库 + DLL hell / soname | 工具包随应用静态链接（应用模型已定）——MB 级手表承受得起，简单性白赚 |
| `/dev` `/proc`（把内核状态伪装成文件的补丁） | 内核对象经 handle 不经路径；遥测经 berryctl `--json`（总原则 2） |
| `.sock` `.pid` 文件 | channel 是 handle 不是文件；pid 文件是「锁」的文件模拟，能力模型无此需求 |
| 盘符（C: D:） | 命名空间挂载；v2 外置存储挂 `/media/<卷名>`，沙箱规则照旧 |

rootfs（cpio + berry-loader，现役）是**装载机制**的雏形：现役装的是系统件（未来归 `sys/`），`.bap` 应用进 `apps/`——同一机制、两棵树（`应用模型设计.md` §2「rootfs 与 /apps 同构」的具体化）。

## 3. 第三刀：沙箱 = 能力，不是承诺

纠「权限混」的一刀，也是与 iOS 拉开差距的地方——iOS 沙箱仍是权限检查，我们是**结构性缺席**：

- **`$appdata` 不是路径，是 handle**。appd 授给应用的 fs 能力是指向它自己 `data/` 树根的 handle；fsmgr 的路径解析从树根出发，`..` 到根即止（chroot 语义，但按能力授）。应用没有「绝对路径」可逃逸——它持有的每一个 fs handle 都圈死了范围。
- **没申请的能力，表里就没有 handle**。不是「有权限位但运行时拦」，是物理上不存在（能力模型 vs ACL 的本质区别，决策 #2 在文件面的兑现）。
- **想碰用户的数据？凭票进场**。用户经系统 picker（display 的 UI 面 / v1 的 bsh `>` 面）把 `user/main/` 下某目录或文件授成 handle——应用拿到的还是一个树根 handle，同一机制零特判。iOS document picker 的能力版。
- **升级 = 原子换树**：appd 装新 `.bap` 到 `apps/<id>.new/` → rename 原子交换 → 删旧树。掉电安全由 rename 原子性保证（v2 由 CoW 快照加强）；回滚 = 指回旧树，不碰分区表。

**「拉屎区」的统一裁定**（每字节文件都有唯一的主人；主人在文件在，主人删文件走）：

| 需求 | 去处 |
|---|---|
| 私有缓存（数据库缓存/网络图片/解码中间件） | 自己树里的 `cache/`——可驱逐（容量压力先清）、卸载带走 |
| 产出归用户的文件（下载/导出） | `user/main/` 下对应目录，**凭用户授权的 handle 写**——拉完归用户所有，app 卸载不清除 |
| 进程间短暂交接 | `tmp/`——唯一全局可写区，活不过重启所以永远积不了垃圾 |
| ~~公共任意写盘~~ | **不存在**。Windows `%TEMP%` / 长期堆积的 `/tmp` 是反面教材：人人可写 = 没人负责 |

## 4. 常见问题的唯一答案（裁定表）

| 问题 | 答案 |
|---|---|
| 应用能在自己树下建子文件夹吗 | 能——`data/` 是它的领地，随便建 |
| 用户数据存哪 | `user/`——**不在任何 app 树下**（否则卸载 app 带走用户照片，安卓早期第三方相册的真实事故模型）；app 是经授权的访客不是主人 |
| 卸载 | 删树。私有数据/缓存随之而去；它写进 `user/` 的文件留下（已是用户的） |
| 系统更新 | `sys/` 只读 + 双目录/快照原子换；`user/`、`apps/` 不动 |
| 内存不够 | 墓碑（appd 线），不是 swap |
| 外置存储（v2） | 挂 `/media/<卷名>`，沙箱规则照旧 |

## 5. 外来生态的存储面（兼容层怎么住）

**破一个根本误会：任何软件都不需要「某种分区」，它需要的是「一棵路径长得对的文件树」。** Wine 跑在 Linux 和 macOS 上（ext4/APFS 完全不同）照样工作——它只是在用户目录建一个普通文件夹当伪 C 盘；真 Linux 上可以拿普通目录 chroot 跑整个发行版。文件系统类型在 syscall 层之上不可见——软件看到的是路径，不是盘。决策 #6 的 per-process 命名空间恰好是干这个的料：**给外来进程一面哈哈镜**——它照镜子以为自己站在标准的 Linux 街道上，镜子后面还是我们统一管理的柜子。

| 层（兼容子系统 T1–T3） | 需要什么 | 在我们盘上的形状 |
|---|---|---|
| T1 原生重编译 | 什么都不需要 | 原生程序：`sys/` 或 `.bap` 进 `apps/` |
| T2 翻译层（Linux 人格 / Wine / APK 容器） | 一棵「Linux 根」文件树 | **目录子树**：人格扩展包的 `data/` 里放 Linux 基础 rootfs（对我们就是数据文件），S3 路径命名空间把它挂成外来进程眼中的 `/`（`/proc` `/sys` 由人格合成） |
| T3 虚机（WSL2 式兜底） | 一块「虚拟硬盘」 | **一个大文件**（磁盘镜像 blob），放虚机应用的 `data/` 或用户指定处；镜像内部爱分几个区是其**文件内容**，与我们的布局零关系 |

Wine 的具体形状（扩展包 = 应用包同源 manifest，ADR #43）：

```
/apps/org.berry.compat.wine/     ← Wine 扩展包自己，一个普通"应用"
├── manifest.toml                ← type=daemon；申请 display/net 等能力
├── bin/                         ← Wine 本体 ELF（Linux 二进制，经 T2 跑）
├── res/                         ← 自带的 Windows DLL 替代品
└── data/                        ← 运行数据
```

外来应用的两种情况，**都统一在 /apps 管理下**：

- **正经「安装」**（Bottles/CrossOver 的现代实践）：兼容层给每个外来应用开**独立 prefix**（一棵专属伪 C 盘）并生成 manifest——`apps/com.foo.gamex/{manifest.toml, bin/gamex.exe, data/drive_c/…}`。卸载 = 删树，与原生应用一字不差。
- **散装二进制**（用户随手下载的 .exe / 裸 ELF）：**用户的文件**，住 `user/main/downloads/`，主人是用户。「打开方式 → Wine」运行；想变被管理的应用就「安装」——兼容层建树生成 manifest，升格为上一条。

APK 同理（T2 + bionic + ART + Binder 翻译，每个安卓应用一棵树）。**v1 手表端零涉及**——按端安装矩阵（`兼容子系统设计.md` §2）写死手表只装 T1，这些是手机/PC 端（v2+）的事。

## 6. 程序形态：一个本质 + 三个正交轴

**内核眼里的程序只有一种：一个 ELF + 一组 handle 的进程**（「应用/窗口」内核根本不认识——ADR #43）。所有「种类」都是三个正交属性的组合，跟集装箱和货物的关系一样：

- **轴一·形态**（文件格式，对 OS 只是数据）：原生 ELF / 外来 Linux ELF / Windows PE / APK / 脚本 / 字节码。
- **轴二·来源**（怎么进的系统，决定住哪）：

| 来源 | 住哪 | 谁管 |
|---|---|---|
| 系统自带（kernel/服务/工具） | `sys/` | 系统 |
| `.bap` 安装 | `apps/<反域名id>/` | appd |
| 兼容层安装（生成 manifest） | `apps/<id>/` | appd（与上同构） |
| 用户手动放的散装文件 | `user/main/` 任何地方 | 用户自己 |

- **轴三·身份**（manifest 的 type，决定待遇）：daemon（服务）/ gui（应用）/ headless（工具）/ 一次性命令。

**`.bap` 不是执行格式，是运输/安装容器**（cpio 信封 + manifest 说明书）——ELF 永远原样躺在 `bin/` 里，解开信封后与裸二进制无异（hexyl 今天就是无 manifest 裸跑的现役证据）。**有 manifest、在 `/apps`（或 `/sys`）= 被系统管理（生命周期/墓碑/卸载）；没有 = 只是用户的文件，手动跑**。能跑只需要 ELF + handle；被管理才需要形式。

## 7. 树即登记簿（没有第二本账）

| 系统 | 登记簿 | 病 |
|---|---|---|
| Linux | dpkg/rpmdb 各一套独立数据库 | 手动拷入的文件永远成孤儿（无文件→主人反查表）；两套包管理互不认账 |
| Windows | 注册表卸载项 + 各安装器 log | 卸载残留是常态 |
| macOS | pkg receipts + App bundle 两套体系 | 同上 |

**我们的登记簿 = `/apps` 目录本身**：`ls /apps` = 已安装列表；每个 `manifest.toml` = 元数据（版本/能力/intent）——自描述、无冗余。归属反查 = 看路径前缀，O(1)。删树 = 卸载，**不可能与任何数据库失同步——因为没有数据库**（归属就是位置，§3「每字节唯一主人」的存储面）。

## 8. 阶段化目标（诚实差距）

| 时点 | 内容 |
|---|---|
| v1（现状） | 布局是**设计先行**：fsmgr RAM overlay（tmpfs 语义）+ FAT12 卷——四棵树的目录形状 v1 还摆不了——fsmgr RAM 层是平名线性表（FILE_COUNT_MAX=8，名无 `/` 语义，bsh `>` 白名单排除 `/`），FAT 面仅根目录 16 项（子目录项解析侧 Skip），层级待 v2 S3 路径语义落地后再摆；`svc/` 是 handle 直连还没有路径皮；FAT 无权限位、8.3 短名，per-handle 圈地/驱逐/原子换树不可表达 |
| v2 | S3 路径命名空间落地（决策 #6 实施面）+ appd 装树/删树/换树（app-0）+ 现代 FS 起（CoW 快照 = 系统更新的分区替代）+ 多用户（加目录不加机制） |
| v2+ | 外置存储 `/media`；兼容层存储面（T2 per-app prefix / T3 镜像文件）随 `兼容子系统设计.md` 窗口 |
