## 1. iOS 机制拆解：预播放 = 事件即渲 + vsync 只锁呈现

iOS 触摸响应的架构核心是**把「渲染何时开始」与「帧何时上屏」解耦成两个独立时钟**：

- **事件即渲**：触摸事件由系统（backboardd）到达即送入应用 run loop，应用在该轮迭代内同步完成事件处理 → UI 更新 → 渲染提交——处理与渲染不被任何显示节拍对齐或推迟。离散交互的感知阈值是硬数字：主线程卡顿 <100ms 难察觉、几百 ms 即感无响应，且几乎总是主线程长任务（Apple 官方 hang 文档口径，`.agents/research/2026-11-15-survey-ios-swiftui-hig-ui-14dims.md` §性能两节）。
- **vsync 只锁呈现**：渲染完成的作品提交给独立 render server 进程，显示驱动在**下一 vsync 沿**取帧上屏（latch）——vsync 是呈现闩锁，不是渲染闸门。render loop 多阶段并行多帧（120Hz 即每阶段 8.3ms 预算），commit deadline 从 presentation time 反推，通常对齐 vsync；查 hitch 必须同时看主线程与 render server 两条时间线。
- **预播放（pre-roll/pre-spin）**：触摸落下的瞬间、应用还没开始画之前，系统就预先拉起渲染管线（预热 render server、提频）——首反馈帧不为冷启动成本买单。这是「预播放」的准确语义：**事件到达即开动整链，vsync 只负责收尾闩锁**。

**Android Choreographer 反例**：输入事件先进队列，等下一个 vsync 拍的 doFrame 回调序（INPUT→ANIMATION→TRAVERSAL）才被消费——输入处理被节拍对齐，最坏多吃整整一拍（16.7ms）内在延迟；Butter 工程的相位化回调、之后的 unbuffered dispatch 都是对这个结构性延迟的补救（`docs/GUI渲染调研-2026-10-v1.0.md` §定案与 §三安卓教训清单；`research/GUI-01-安卓渲染响应慢教训.md`）。

**对 BerryOS 的取舍结论**：输入到达即处理（iOS 形），vsync 只做呈现时基与遥测口径（iOS 形的软实现）；不引入 Choreographer 形的输入节拍对齐。这与 GUI 渲染调研的 vsync 帧调度定案（vsync 单一时钟源 + 相位化回调序用于**呈现侧**节奏，而非输入消费门）一致。

## 2. BerryOS 现状分析：已经是事件驱动——vsync 等待恒 0ms

整链逐段核现状（行号 = 2026-11-15 工作树）：

```
virtio-tablet IRQ ─► gui-inputd serve_poll（常备 armed POLL，1ms 步进收割）
                   ─► channel send_rep（input 域应答）
                   ─► launcher wait_many 醒（hi READABLE——睡事件不睡拍）
                   ─► recv 应答 → push_pointer 入缓冲 → wake()（Idle→Run 起振）
                   ─► pump_input（referee + press_react 标脏 + 重采样）
                   ─► render_frame（anim → relayout → paint——damage 空集跳过）
                   ─► SUBMIT（fresh READ dup 别名随行）
                   ─► guifbd blit-at-SUBMIT（damage 裁剪 CPU blit 直写 fb——应答即呈现）
                   ─► 光子
```

**已经是事件驱动的证据**：

- **帧循环不睡 vsync**：launcher 稳态等待 = `wait_many`（[wm 通道, 条件入列 input 通道] + deadline = min(next_wakeup, now+10s)）——醒来靠事件 READABLE 或自身动画/停帧期限，**从不为等一个 vsync 拍而睡**（`user/bins/berry-launcher/src/frameloop.rs:617-641`）。vsync 等待恒 0ms。
- **呈现不等 vsync**：guifbd v1 钉死 blit-at-SUBMIT——SUBMIT 处理内同步 damage 裁剪 CPU blit 写 fb，应答即 latch（`user/bins/guifbd/src/guest.rs:595-724`）；软 vsync（SOFT_VSYNC_NS≈60Hz）只服务 hdi VBLANK_WAIT 客户与 serve 循环自身醒睡节拍（guest.rs:127,344-376），不挡任何渲染与提交。
- **vsync 数值的全部现行用途** = 帧节奏与遥测：next_vsync_tick 推 expected_present（jank 判定超半周期 deadline_miss）、next_wakeup 的 Run 相拍点、停帧三态（RUN/SETTLE/IDLE）推进——即「呈现闩锁 + 时基」，无一处理渲染闸门。
- **调度侧唤醒即时**：显示链同步面全走 IPC channel，signal 唤醒 + G3 全抢占（preempt-on-wake 通用化）——guifbd/launcher 被消息唤醒可抢占在跑的后台任务（`docs/显示管线调度集成指南-v1.0.md` §信号唤醒即时）。

**结论**：iOS「事件即渲 + vsync 只锁呈现」的形态，BerryOS 架构上**已经是**——不需要引入新机制，剩下的差距全在成本面（§3/§4）与三个局部形状（§5）。

## 3. 延迟分解表：逐段预算

触摸→光子全预算 ≤1 帧（16.7ms @ 60Hz）；各段预算与承载机制：

| # | 段 | 预算 | 承载机制（现状锚点） |
|---|---|---|---|
| 1 | 设备→inputd 收割入泵 | ≤1ms | 常备 armed INPUT_POLL 的 serve_poll 1ms 步进收割（POLL_STEP_NS=1ms，`drivers/bins/gui-inputd/src/main.rs:78,799-848`；launcher 恒保持一轮 poll 在途——arm/收/重臂三段，frameloop.rs:326-391） |
| 2 | channel 传递（inputd→消费端） | ≤0.5ms | send_rep → channel READABLE 唤醒消费端 wait_many（内核 wake 路径即时） |
| 3 | pump + 标脏 | ≤0.1ms | referee + press_react/widget_react 表驱动直查，零闭包零分配（`user/berry-ui/src/lib.rs:2183-2260`） |
| 4 | 渲染 + SUBMIT（小 damage） | ≤10ms | 增量 paint（damage 裁剪）+ SUBMIT 随行别名 + blit-at-SUBMIT 裁剪 blit（frameloop.rs:426-473；guifbd guest.rs:595） |
| — | 合计（触摸→呈现） | ≤11.6ms | 余 ≥5.1ms 扫出/光子余量 @60Hz |

预算的用法：违反 ≤1 帧总预算时逐段对表定位；段 1–3 是 µs 级机制面，**段 4 是唯一毫秒级弹性段**——这就是 §4 的瓶颈结论。

## 4. 真瓶颈识别：呈现路径成本，不是调度等待

调度等待已被三件事清零：事件驱动帧循环（§2）、G3 全抢占 + preempt-on-wake、常备 armed poll 的收割形状。剩余延迟全部是**呈现路径的 CPU 成本**，按危害排序：

1. **首触 damage 放大（现状最大浪费）**：launcher 帧循环现状序 = `push_pointer → wake() → pump_input`——wake() 时输入还在缓冲里、damage 必空，条件化 FULL 兜底被触发；随后 pump_input 里 press_react 标出的**精确按压矩形**（几十 KB 像素级）被 FULL 的整屏语义吞掉（FULL 后 add no-op，`user/berry-ui/src/damage.rs:16`）。800×600×4B ≈ 1.92MB 整屏 blit 顶替了 ~36KB（96×96 图标格）级增量——段 4 预算被放大数十倍。TCG 仿真下整屏像素拷贝是毫秒级大头。
2. **阻塞 RPC 挡在 SUBMIT 前**：Msg::Click 分发在渲染之前同迭代执行，spawn_by_id_inner 的 APP_SPAWN RPC 严格串行阻塞（send→等回执，`frameloop.rs:397-408,848-872`）——按压反馈帧（PRESSED_BG）要等 spawn 回执到达后才渲染提交，首触反馈被几十 ms 级 RPC 直接顶穿预算。
3. **呈现路径固有成本**：px() 7 点抽样对拍（每点 vmo_read）、SUBMIT→FRAME_CALLBACK→RELEASE 严格内联串行三次 RPC 往返（在途恒 ≤1，frameloop.rs:28-34）——这些是正确性/背压设计的有价成本，优化空间在 damage 收敛（1）而非砍断链。

**裁决**：预算违例的排查顺序 = 先呈现路径成本（damage 是否 FULL、blit 像素量、RPC 是否挡路），后一切调度怀疑——与铁律 2 口径一致。

## 5. A′/B′/C′ 优化方案详细设计

三刀对准 §4 三个病灶，编号加撇与 GUI 规划的裁决 A–I 区分；A′/B′/C′ 分别 = 铁律 3/4/5 的落地刀。三刀互不依赖，均不动协议 wire、不动内核。

### 5.1 A′：首触 damage 收敛（铁律 3 落地）

- **问题**：wake() 先于 pump_input 执行，首触必走 FULL 兜底，精确按压矩形被吞（§4-1）。
- **方案**：embedder 帧循环把 `ui.wake(now())` 从输入接收段（frameloop.rs:363）**后置到 pump_input 之前**——终序 = `push_pointer → pump_input（press_react 标精确矩形）→ wake()（damage 非空则保矩形；空集才兜底 FULL）→ Msg 分发 → render_frame → SUBMIT`。一行搬家，引擎零改动。
- **引擎侧配套**：berry-ui `wake()` 契约注记补「输入驱动 wake 不放大 damage」条款（条件化 FULL 是现状——lib.rs:2511-2516 finding 9 修复的语义收尾）；「确无任何 damage 才兜底 FULL」保住「不欠拍」节奏契约（点壁纸等无视觉变化面仍出一帧，起振遥测口径不漂）。
- **否决备选**：给 wake 加 cause 参数分流——不如搬序干净（搬序后 FULL 兜底自然只命中空集，无需第二套语义）。
- **验收线**：launcher 首触帧遥测 damage_rects>0 且 damage_full=false（FrameRec 现成字段）；既有 smoke 标记全零漂移（CLICK ok n=1 照打）。
- **风险与回滚**：wake 晚于 pump 不破坏 pump 无相位前提（pump_input 不读 phase）；回滚 = 搬回一行。

### 5.2 B′：视觉优先于动作——spawn 后置（铁律 4 落地）

- **问题**：APP_SPAWN 阻塞 RPC 挡在 SUBMIT 前，按压反馈被顶穿（§4-2）。
- **方案**：Msg::Click 分发处只记账待办（`pending_spawn: Option<RecentsApp 形 id>`——连续点击取最新覆盖，旧的语义本就幂等重拉）；本迭代照常渲染 + SUBMIT + FRAME_CALLBACK；**呈现完成后**（RELEASE 归还后、稳态 wait_many 前）再执行 spawn RPC。多任务键重拉（spawn_by_id）同路并轨。回执记账、`CLICK ok n=1` 恰一次门、失败 eprintln 诊断面全部保持。
- **时序保证**：按压反馈帧在 spawn RPC 发起前已呈现（SUBMIT 应答即 latch）；spawn 在后台进行，成功后新应用建窗 → wmd 表变更 → 下轮迭代自然出反馈面。
- **否决备选**：spawn 转独立线程——launcher 单线程帧循环是现状架构契约（S1 判词），RPC 阻塞点后置已够，不引线程面。
- **验收线**：日志序断言「按压帧呈现打点先于 spawn 回执行」；CLICK ok n=1 恰一次零漂移；click_ready 门（presented > snap_frame）不受影响。
- **风险与回滚**：pending_spawn 逃逸面 = 帧循环退出路径无需清理（进程级生命周期）；回滚 = 恢复分发处直调。

### 5.3 C′：重采样目标保持新鲜（铁律 5 落地）

- **问题**：`ui.pump_input(last_expected)` 用上一帧 expected 轨（frameloop.rs:264,394）——稳态最多陈旧一个 period；idle 长睡（10s 帽）醒来后是远古值：重采样跨度帽 >20ms 直接拒采（RESAMPLE_MAX_DELTA_MS，`user/berry-guiproto/src/lib.rs:359`）→ 拖跟预测整体静默失效，外推帽（8ms）同样失义。
- **方案**：目标改为**本帧渲染时刻推出的拍点**——launcher 侧 `pump_input(next_vsync_tick(t_now, VSYNC_NS, 0))`（frame::next_vsync_tick 已 pub(crate)，随刀升 pub）；或引擎新面 `pump_input_at(now_ns)` 内部推导（target = next_vsync_tick(now) − RESAMPLE_LATENCY_MS，target_from_expected 单源不双轨）。取后者：推导单源进引擎，launcher 一处调用点换名，pump_input(expected) 旧签名退役（全系统唯一消费面 = launcher，无兼容包袱）。
- **正确性论证**：pump 与 render 同迭代 µs 级相邻，next_vsync_tick(t_now) 与 render_frame 内部自算 expected 恒同拍（含沿不欠拍语义同源 frame.rs:79-94）；陈旧上界从「不定」收敛到「<1 period」。
- **验收线**：berry-ui host 测补「idle 后首帧 pump 目标 = 当前拍推导」用例（构造 idle 时差 >20ms 的历史窗，断言不再拒采）；launcher 手验拖动手感（snap 翻页跟手）。
- **风险与回滚**：纯目标时刻换源，重采样算法零改动（resample.rs 冻结语义不动）；回滚 = 换回旧签名传 last_expected。

## 6. 与 iOS/Android 的架构对比

| 维度 | iOS | Android（Choreographer 形） | BerryOS（现状 + 本设计） |
|---|---|---|---|
| 输入到达→开始处理 | 事件即处理（runloop 即醒） | 排队到下一 vsync 拍 doFrame INPUT 相（+最多一拍） | 事件即处理（channel 唤醒 wait_many） |
| 渲染发起 | 事件驱动，同迭代提交 | vsync 对齐回调驱动 | 事件驱动，同迭代渲染 + SUBMIT |
| vsync 角色 | 呈现闩锁（render server latch） | 渲染闸门（帧回调节拍） | 呈现时基/闩锁（软 vsync + blit-at-SUBMIT 应答即呈现），不挡渲染 |
| 预播放/预热 | 触摸预热渲染链 + 提频 | 无（Butter 后靠相位/频率补救） | Idle→Run 即时起振（wake 起振遥测 spinup_late 现成）；touch-boost 走策略注入（`docs/应用模型设计-v1.0.md` §5） |
| 首触增量 | CA 增量提交，无放大问题 | — | A′：精确按压矩形直用，FULL 仅空集兜底 |
| 动作 vs 视觉 | 后台化（GCD 等） | — | B′：阻塞 RPC 排 SUBMIT 后 |
| 重采样 | 系统侧聚合预测 | vsync 对齐重采样 | 消费侧最终一跳重采样（Flutter #73286 教训）+ C′ 目标新鲜化 |
| 触摸→光子上界 | ~1 帧 | 1–2 帧（含排队拍） | ≤1 帧（预算 11.6ms + 扫出余量，§3） |

对比结论：BerryOS 不照搬任何一家——取 iOS 的「事件即渲 + vsync 呈现闩锁」形态（架构上已具备），避开 Android 的输入节拍对齐；Android 值得保留的只有消费侧重采样（已按最终一跳语义落地，C′ 修其目标新鲜度）。
