# 兼容子系统设计（扩展生态槽位）

> 回答三件事：**外来生态怎么跑**（Linux 程序 / Windows 程序（Wine）/ APK——以「装一个扩展」的形式，内核零 Linux 语义——新增面 = S1–S4 槽位，v2+ 预 ADR）、**系统要预埋哪些槽位**（四个，S1–S4）、**什么时候做**（v2+ 分期，v1 无代码面）。
> 核心论点：**兼容能力不是内核功能，是一个可卸载的用户态扩展包**。内核只卖地皮（原语 + 槽位），生态盖楼（兼容子系统装进来）；楼塌砸不着地皮（子系统崩 = 该容器死，内核与原生服务无恙），拆楼不留坑（能力回收干净）。
> 挂钩：`应用模型设计.md`（**扩展包 = 应用包同源 manifest，ADR #43——无新格式**）、`能力模型设计.md`（容器 = 能力沙箱）、`IPC设计.md`（路径命名空间决策 #6；channel↔Binder 映射见本文 §4.3）、`安全与硬件隔离设计.md`（IOMMU = 设备直通后盾）、`优化议程.md` ②生态税的外来生态延伸（§0 总表；本文 T2/T3 面 §2 未列，§2 动作 = T1 层）、`存储布局与沙箱设计.md`（外来客存储面：路径视图非分区 + per-app prefix，ADR #45）；端定位 ADR #39–#41。**本文是设计先行**（`路线图.md` 明文允许设计文档与任意 Phase 并行产出），槽位 S1–S4 为**预 ADR 候选**——正式 ADR 随 v2 立项逐条落 `架构决策.md`。

## 0. 与既有决策的对账（收紧，不是推翻）

| 既有决策 | 表面张力 | 本设计的解读 |
|---|---|---|
| 「自有 ABI + POSIX 兼容库（**不跑 Linux 二进制**）」 | 不是说不跑吗？ | 内核不认识 Linux syscall 的底线不变（拒 Linuxulator；S1 只是转发原语、语义全在被转发侧，≠ 一票否决的『内核 syscall 翻译层』）。**条件重开**：T2/T3 恰为 #14 反转触发器预授权的两形态（用户态兼容服务 / VM 内嵌真内核，`架构决策.md` 重议触发器表 + `系统调用ABI设计.md` §8.0），**立项须过证据门**——G-eco 第三方样例持续因『非 POSIX / 非 Linux』不可移植且用户态薄库确无解；现状：G-eco 已收官、hexyl 经 musl + 薄库移植成功（2026-10），重开证据未现，#14 维持。 |
| 微内核原则 5（失败隔离） | — | 直接适用：兼容子系统是普通服务进程家族，崩 = 该容器死，监督重启走 appd 线（ADR #43）。 |
| ADR #43（应用 = 纯用户态协议约定，内核不识「应用」） | — | 无缝衔接：**扩展包就是一种应用包**（cpio + manifest + 能力授予 + 生命周期），同一套 appd 安装/监督/墓碑机制，零新格式。 |
| 协议洁净（CLAUDE.md 工作方式 #4） | Wine 是 LGPL、AOSP 是 Apache | 我们**不搬任何兼容层代码**：Starnix（Fuchsia，宽松许可）只借模式；Wine/bionic/ART 是**被运行的普通程序**，随扩展包分发，不与kernel/原生服务链接。GPL 隔离面照旧成立。 |

## 1. 先例盘点（博采众长，逐个过 `架构综合纲领.md` 排除 8 问）

| 先例 | 做法 | 取 / 避 |
|---|---|---|
| **Fuchsia Starnix** | Linux 二进制跑在受限进程，syscall/异常被 Zircon **转发**给进程内的用户态运行时翻译（restricted mode） | ✅ **主参考**：内核只加「转发 + 受限态切换」原语族（zx_restricted_enter/kick 等），人格全在用户态；已演示跑 Android 生态组件。借模式（Fuchsia 宽松许可可对照）。 |
| Windows **WSL1** | 内核态翻译层（lxcore.sys + pico 进程） | ⚠️ 教训：~300+ syscall 的内核态维护面拖死了它——翻译层**别塞内核、别贪全覆盖**。 |
| Windows **WSL2 / WSA** | 真 Linux 内核进虚机；文件经 9P 桥 | ✅ 兜底路线：虚机也是「一个受能力管理的服务」。⚠️ WSA 2024 宣布弃维——**虚机线的持续维护成本同样真实**，别当免费午餐。 |
| macOS **Rosetta 2** | 用户态二进制翻译（跨 ISA） | ✅ 证明翻译层可做到「用户无感」；技术路线与 T2 正交（我们同 ISA，省指令翻译只留语义映射）。 |
| FreeBSD **Linuxulator** | 内核子系统实现 Linux syscall | ❌ 反例：就算可加载，Linux 语义还是进了内核——正是「不跑 Linux 二进制」决策要防的形态。 |
| **Wine 本体** | 纯用户态 Win32→POSIX 翻译，连 macOS 都能跑 | ✅ 证明「兼容层 = 普通程序」；且 Wine 是**普通 Linux 程序**——T2 立住它自动跟进。 |
| ChromeOS **ARC++** / **Anbox** | 容器/用户态跑 Android（共享宿主内核） | ✅ APK 容器的两条先验；图形栈对接（输入路由/合成）是最大工作量来源。⚠️ 均未延续：Google 已将 ARC++ 整体换代为 ARCVM（Android 进 crosvm 虚机，官方动机 = 安全隔离 + 版本独立升级，2022 年起新设备全面虚机形态、容器实现退役）；Anbox 停维归档（社区延续为 Waydroid，仍容器形态）——当事者从共享内核容器退到虚机，是 §4.5/§5「APK 容器降级 T3」kill criteria 被真实触发过的最强旁证。 |
| 早期鸿蒙跑 APK（后 NEXT 全砍） | 初期兼容 APK，生态自立后整体移除 | ⚠️ 教训：**半心半意的兼容面会被砍**。要做就做成一等公民扩展（可安装/可卸载/可演进），不做「内核特例」。 |

**综合**：T2 翻译子系统管体验（Starnix 式），T3 虚机管兜底（WSL2 式），内核态人格（Linuxulator 式）排除——两条腿都踩在「Linux 语义零进内核」这一侧：内核新增面收敛在 S1–S4 槽位（派发分支/异常通道/EL2 面等原语），不含任何 Linux 语义。

## 2. 三层扩展模型（T1–T3；与应用模型的 L1–L3 命名区分）

- **T1 原生层**：自有 ABI + POSIX 兼容库（`shell设计.md` 命令三梯队第一梯队同源），源码级兼容——简单程序重编译即跑（uutils/MIT 家族）。零运行时兼容成本，代价是每个程序要重编译。
- **T2 翻译层（兼容子系统，「装一个扩展」的本体）**：一个扩展包 = **Linux 人格**（syscall 翻译 + binfmt 式加载注册 + 私有路径命名空间 + 自管 fd 表/信号合成）。Wine 是跑在 T2 上的普通程序；**APK 容器 = T2 + bionic + ART + Binder 翻译**（Binder 的「句柄随消息传递」与 channel 语义几乎同构，§4.3）。
- **T3 虚机层（保底）**：真 Linux/AOSP 内核进 VM（EL2），设备经 IOMMU 直通。有了它，「任何 Linux 软件必然能跑」从工程承诺变成事实；代价是内存与维护（WSA 弃维的教训）。

**按端安装矩阵**（扩展 = 应用商店里的生态包，用户侧「装一个扩展」）：

| 端（ADR #39–#41） | T1 | T2 | T3 |
|---|---|---|---|
| 手表 rich 档（MB 级） | ✅ | ❌（装不下也无场景） | ❌ |
| 手机 / 工业 RT（GB 级） | ✅ | ✅ Linux 人格 + APK 容器 | 视 SoC（EL2 + 内存余量） |
| PC 高性能 | ✅ | ✅ + Wine | ✅ |

T2 与 T3 同时在装时，运行器按程序 manifest 与实测覆盖自动选择（T2 优先：集成体验 + 省内存；覆盖不了转 T3）。T3 就绪依赖 S4 落地（§6）。

## 3. 槽位对账：已有 vs 欠的

### 3.1 已有的（v1 原语即槽位——回头看设计文档早就埋了钩子）

| v1 原语（现状） | 在扩展里的角色 |
|---|---|
| `process_create` 双出参（父拿子 root Vmar）+ VMO 全量操作 | **用户态 fork** 的全部材料（§4.2）；Zircon 无 fork 而 Starnix 照样跑 = 先例保证 |
| channel + handle 随消息迁移 + `wait_many` | pipe / eventfd / 信号量 / **Binder** 的映射底座（§4.3） |
| Process 可等待（TERMINATED + `get_exit_code`，Plan B v0.5） | `wait()`/SIGCHLD 合成的原料 |
| 能力模型（权限在 handle） | 容器只拿被授权的 handle——访问面上**比 Linux namespace 更干净的隔离**（no ambient authority：对既有对象的操作全量 handle+rights 门控）。**v1 诚实豁口**：`process_create` job 恒 0、进程创建权未设防（`能力模型设计.md` 在案），Job v2 真门控收口后「授权即全貌」才在创建面成立。能力模型不承诺无 covert channel——共享调度器/服务的时序隐蔽通道非其执法面。 |
| MMIO 窗口 VMO + `vmo_get_phys`（P6 A-2/A-3）+ IOMMU 设计（决策 #22） | T3 设备直通；未来 vGPU 直通给 Wine 游戏 |
| berry-loader（cpio/ELF 纯函数解析）+ musl target 生态（G-eco-d） | T2 的加载器与首批被兼容对象（静态 musl 二进制是天然第一里程碑） |

### 3.2 欠的四个（预 ADR 候选，S1–S4）

| 槽位 | 解决什么 | 形态草案 | 为什么「小而正交」 |
|---|---|---|---|
| **S1 syscall 人格注册/转发** | Linux 二进制的 `svc`（NR 在 x8、参在 x0..x5）与 berry 派发约定（NR 在 x0、参在 x1..x6）全面错位——派发器把 Linux 第一参数当号解读：指针/未实现号才得 -ENOTSUP，fd/flags 等小整数首参撞进 berry 稠密号段（0x11–0x1B/0x31–0x37/0x51–0x54）即**误派发**——从 -EBADF/-EINVAL、误建 channel/VMO 到误触 `process_exit`(0x33)/`thread_exit`(0x36)（`-> !` 不返）直接杀进程，不可预测。需要入口，且 S1 必须在 berry 表派发之前按线程人格态截流；人格未注册前 Linux 二进制不可裸跑 | 线程级受限/正常双模式（Starnix restricted-mode 原义）：受限态 `svc` 触发转发——寄存器组落到共享页、切回正常态入口由翻译运行时接管；运行时自身以正常态运行、syscall 照走 berry 表（channel/vmo/process 全系） | 内核新增受限态转发原语 + 出入口/切换面（enter/kick + 状态页），不含任何 Linux 语义；语义全在被转发侧（用户态） |
| **S2 异常通道** | 信号语义：SIGSEGV/SIGBUS/SIGFPE/SIGTRAP 要从 trap 变消息 | 进程的异常事件以 channel 消息递给持监督 handle 者（Zircon exception channel 同形）；人格收后合成 Linux 信号投递（含打断阻塞 syscall 的唤醒） | 异常走向本就要出内核（appd 监督线也需要，ADR #43）；兼容只是第二消费者。**kill 他者的终止原语**同样由 appd 线先行，兼容复用不另立槽 |
| **S3 路径命名空间落地** | 决策 #6 的实施面：mount 模型 + per-process 根 | namespace 服务（IPC 设计既有规划）+ 进程持根 handle；人格为容器自造 `/proc` `/sys` 视图 | 本来就在路线图（决策 #6 对策：先能力传递、namespace 分阶段加）——兼容只是最强消费方 |
| **S4 EL2 虚机化面** | T3：VM 建立/运行/设备直通 | EL2 面（vcpu 上下文 + 二段页表编程 + 虚拟定时器/中断注入）+ 设备直通走 SMMU（决策 #22） | 与 ADR #41 x86 线同款纪律：范围盒子 + kill criteria（§5）；不达标自动冻结、主线无损 |

## 4. 关键机制草案

### 4.1 Linux 人格的运行形状
扩展包装入 = appd 经 manifest 拉起**人格服务家族**（加载注册 + 命名空间提供 + 翻译运行时分发）。Linux 二进制 = **受限进程**：S1 转发面 + 人格自管 fd 表；binfmt 式加载注册即强制绑定人格——不存在「未注册裸跑 Linux 二进制」的合法态，加载链须在 `process_start` 前完成人格绑定（否则误派发，§3.2 S1）。翻译运行时两种部署形态（v2 立项时 ADR 拍板）：

- **进程内库（Starnix 形，主选）**：翻译层以库映射进受限进程，syscall 转发即进程内调用——快；文件/网络等系统资源仍经 channel 回到真服务（fs/net）。
- **代理服务（备选）**：syscall 经 channel 发给集中式人格服务——隔离最强、最慢；留作多容器共享翻译状态的形态。

### 4.2 用户态 fork（无内核 fork 的先例路径）
人格持有子进程的全部材料：ELF 的 VMO（加载时即持有）+ root Vmar handle。fork = VMO 复制 → `process_create` → 映射 → **弹床恢复寄存器**（子进程从栈上 VMO 恢复寄存器影像后跳回，模拟「fork 返回两次」）。`thread_create(entry, sp)` 的现有签名就够——不需要新的「设寄存器」syscall。代价：v1 无 COW，fork = 整副本（gcc/make 负载可容忍）；G4 demand paging 后按 VMO 写时复制优化。

### 4.3 Binder over channel（我们的天然优势）
Binder 语义 ≈「带句柄对象寻址的消息 IPC」：handle 随消息跨进程迁移、对象身份稳定、死亡通知。与 channel + `ObjRef` 迁移几乎同构——映射表：Binder 句柄 ↔ channel handle、`BC_TRANSACTION` ↔ send/recv、死亡通知 ↔ 对端关闭检测（v3 收口面）。APK 容器最深的一条沟因此变最浅。

### 4.4 Wine 的位置
Wine = 普通（重量级）Linux 程序 → T2 跑通 gcc 级程序后自然跟进；其图形输出对接未来 display 服务（ADR #43 的 display 合成线）或 vGPU 直通（性能档）。**里程碑级验收建议**：`WINE ok`（notepad 级小程序渲染 + 输入回路）。

### 4.5 APK 容器（工程量最大，排最后）
= T2 + bionic（BSD）+ ART（Apache-2.0）+ Binder 翻译 + SurfaceFlinger ↔ display 对接 + zygote 预热模型对 fork 面的压力测试。前置：T2 稳定 + display 服务在位。若 Binder/ART 跟进成本 > Linux 人格 2× → 降级为 T3 跑整 AOSP（kill criteria §5）。

### 4.6 T3 虚机层形状
VM = 受能力管理的服务：持 EL2 面 handle（S4）+ 直通设备窗口（SMMU）。文件桥走 9P/virtio 面族（成熟参考多）。**定位是兜底保险，不是主体验**——覆盖 T2 没翻译到的长尾（稀有 syscall、内核模块、ptrace 级调试工具）。

### 4.7 epoll 面（诚实的坑）
`wait_many` n≤16，epoll 可监听数千 fd——T2 需自建**聚合器**（分批重验 + 就绪缓存，或专用多路等待服务升级 n 上限）。这是 T2 真实工程量的一部分，先记后还。

## 5. 工程边界与 kill criteria（诚实面）

- **syscall 面**：Linux arm64 ~300+ 在册。T2 允许「90% 常用覆盖」（按占用率排序的前一百）+ 长尾交 T3——WSL1 死因的制度化回避。
- **内存量级**（粗账）：T2 Linux 人格 ≈ 数十 MB 级；Wine 每应用数百 MB 起；APK/ART ≈ GB 级；T3 VM ≈ 1–2GB 起。——这就是按端安装矩阵的物理依据（手表端永远不装，与 ADR #39 无张力）。
- **性能**：T2 翻译开销目标 = 常用路径 < 2× 原生 syscall 成本（真机 G 卡实测口径，TCG 不做数）；T3 计算近原生、IO 桥有税。
- **kill criteria（建议，随各槽位 ADR 正式化）**：
  - T2：连续两个里程碑常用面覆盖率停滞，或维护工时 > 当期主线 30% → 冻结增量、转 T3-only（保留已落地面不拆）；S4 未落地期间本条款退化为「冻结增量」（转轨待 T3 就绪，§6）。
  - S4（EL2 面）：对齐 ADR #41 条款——连续两提交周期 >20% 主线工时 → 自动冻结。
  - APK 容器：跟进成本 > Linux 人格 2× → 降级 T3-only 路径；S4 未落地期间本条款退化为「搁置 APK 跟进线」（bionic/ART/Binder 不再投入，T3 就绪后再评估跑整 AOSP）。业界先例：Google 自身即从容器形态（ARC++）换代到虚机（ARCVM），共享内核容器的防御面与耦合维护成本是官方动机（§1）。
- **测试面**（AI 测试友好化照旧）：每层扩展带确定性验收标记——`LNX ok`（静态 musl busybox 输出与宿主基准逐字节对拍，hexyl 同款）→ `GCC ok`（**T2 内 gcc 编译 hello.c、产物再跑——兼容层自举闭环**）→ `WINE ok` / `APK ok`。

## 7. 开放问题

- **Q1**：S1 转发 ABI 的形状——共享页寄存器块（Starnix restricted-mode 式）vs 薄 syscall 转接号？模式切换原语族（进出入口/状态页布局/kick 语义）与 `svc #0` immediate 撞号取舍（berry-sys 现发 `svc #0` 与 Linux 惯例同号——改 immediate = ABI §8 修订存量重编，或按注册线程作用域解释）一并随 v2 ADR 定。
