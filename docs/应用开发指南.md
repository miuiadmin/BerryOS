## 1. 全链一览

BerryOS 应用 = 一个 `.bap` 包（berry application package，cpio newc 容器），内核对
「应用」零概念——装载、授权、监督全在用户态 appd 服务。从源码到跑起来：

```
你的工程（Cargo.toml + src/main.rs + manifest.toml）
  │ cargo build --release --target aarch64-unknown-linux-musl
  │   （musl target + berry-libc shim + berry-ld 链，见 §4 构建咒语）
  ▼
ELF 本体 → staging 组装 {manifest.toml, bin/<名>}
  │ python3 $ROOT/tools/mkapp.py <ID>.bap <staging-dir>
  ▼
<ID>.bap（cpio newc：manifest.toml + bin/<名> + SHA256SUMS 三条目）
  │ （集成面）mkcpio 打进 rootfs.cpio 的 app/<ID>.bap 条目
  ▼
系统启动 → appd 扫描 app/*.bap → manifest 门禁 → 按 capabilities 授能 spawn
```

## 2. 环境前置

```bash
# Rust stable 即可（免 nightly、免 custom target）。
rustup target add aarch64-unknown-linux-musl    # 应用面唯一必需的 target

# 只想本地打包/复验（不跑系统）：另需 Python >= 3.11（mkapp 的 tomllib 门）。
# 想在 QEMU 里真跑起来：另需仓库完整前置（qemu + just +
# aarch64-unknown-none），见仓库 README「Quick start」。
```

另需一份 BerryOS 仓库 checkout（v1 现实约束，见文首）。下文 `$ROOT` = 仓库根的
绝对路径（示例：`ROOT=$(cd /path/to/berryos && pwd)`）。

## 3. 最小应用工程（三件）

### 3.1 manifest.toml（规范形模板——字节级钉板）

`<slug>` 换成你的应用名（小写，与 `bin/` 下 ELF 同名；`<ID>` 为其大写形）：

```toml
[app]
id = "<ID>"
version = "0.1.0"
entry = "bin/<slug>"
type = "app"
intent = "utility"

[compat]
min = "0.1.0"
target = "0.1.0"
compile = "0.1.0"

[capabilities]
console = true

[runtime]
stack_pages = 8
```

**这是唯一合法形态的模板**：mkapp 门禁第 2 道「规范形重序列化逐字节相等」——
节/键定序、双引号串、纯十进制整数、LF only、拒 tab/注释/单引号/hex 整数/多余
空白。手写漂一点 = 打包 loud 拒（一行理由 + 非零退，不猜不改）。各字段语义见
§6 速查。

### 3.2 Cargo.toml（appdemo 同构）

```toml
[package]
name = "<slug>"
version = "0.1.0"
edition = "2021"

[workspace]

[dependencies]
# v1：path 依赖指向仓库内 berry-libc。脚手架默认按 in-tree 位置
# user/bins/<id>/ 生成 "../../berry-libc"——仓外工程自行改成绝对/相对
# 指向你 checkout 里的 $ROOT/user/berry-libc。
# （crates.io 发布后的 version 依赖形态见 §9）
berry-libc = { path = "<指向 $ROOT/user/berry-libc 的路径>" }

[profile.release]
opt-level = "z"
lto = true
codegen-units = 1
panic = "abort"
strip = true
```

（`[workspace]` 空表 = 独立小工作区，防被外层 workspace 吞并；release 五参是
musl + berry-libc 链的既定组合，动之前先跑通一次再说。）

### 3.3 src/main.rs（CRT0_SEED 是链接命脉，一字不减）

```rust
//! <ID> —— BerryOS 应用（契约见本指南 §7）。
use std::process::ExitCode;

// 链接种子（stdhello/appdemo 同款）：无引用则 berry-libc 的 crt0（含
// `_start`）不进链接；`#[used]` 防死码消除。
#[used]
static CRT0_SEED: unsafe extern "C" fn() = berry_libc::berry_crt0_anchor;

fn main() -> ExitCode {
    // argv0 契约：spawn name = manifest entry（§7 第 1 条）。
    assert_eq!(
        std::env::args().next().as_deref(),
        Some("bin/<slug>"),
        "argv0 should be manifest entry"
    );
    println!("app <ID> up");
    ExitCode::from(0)
}
```

### 3.4 或者：脚手架一键产四件

```bash
python3 $ROOT/tools/mkapp.py --new <dir> --id <ID>
```

- 约束：`basename(<dir>)` 必须等于 `<ID>` 的小写形（id 大写惯例，如
  `MYAPP` ↔ `myapp`）；目录已存在且非空 = 拒（防覆写）；**id 勿含点号**——
  slug 直接成为 Cargo.toml 包名，cargo 包名词法拒 `.`（用 `-` 或 `_`）。
- 产出四件：`manifest.toml`（= §3.1 模板）、`src/main.rs`（§3.3 同构）、
  `Cargo.toml`、`README.md`——**不含 bin/ 内容**（两步流：你构建 ELF 放进
  `bin/` 后才可打包；空 bin/ 会被「恰一个文件」门禁拒，这是有意的）。

## 4. 构建咒语（参数勿动）

justfile 原文（build-user 的 appdemo 构建行——以
`--manifest-path bins/appdemo/Cargo.toml` 锚文本定位，行号随刀漂移不引；
cwd = `user/`，`ROOT=$(cd .. && pwd)` 在同 recipe 首块）：

```bash
ROOT=$(cd .. && pwd)
CARGO_TARGET_DIR=cargo-target RUSTFLAGS="-C linker=$ROOT/tools/berry-ld -C linker-flavor=ld.lld -C link-arg=-zmax-page-size=4096" \
    cargo build --release --manifest-path bins/appdemo/Cargo.toml \
    --target aarch64-unknown-linux-musl
```

仓外工程照抄同一行，只换两处路径：`--manifest-path` 指向你的工程、`$ROOT`
指向你的 BerryOS checkout。**其余参数一个都不要动**：

| 参数 | 为什么 |
|---|---|
| `--target aarch64-unknown-linux-musl` | 用户态 std 面目标——musl ABI + berry-libc shim 承接 std 的 libc 调用 |
| `-C linker=$ROOT/tools/berry-ld` | 链接器包装：剥 musl crt（crt1.o 的 `_start` 与 berry-libc crt0 冲突）+ 剥 `-lc`（零 musl 字节——图里缺的符号一律 berry-libc 补桩），转交 rust-lld |
| `-C linker-flavor=ld.lld` | berry-ld 以 lld 驱动形态被 rustc 调用 |
| `-C link-arg=-zmax-page-size=4096` | rust-lld 默认 64K max-page 会把 PT_LOAD 对齐抬到 0x10000，装载器吃不下 |
| `CARGO_TARGET_DIR=cargo-target` | 显式钉产物目录，防全局 `~/.cargo/config.toml` 的 target-dir 覆盖把产物漂走 |

产物：`cargo-target/aarch64-unknown-linux-musl/release/<slug>`。

## 5. 打包与复验

### 5.1 staging 组装 + mkapp 打包（justfile build-user 尾段 staging+mkapp 原文——以 `rm -rf userbins/app-stage` 锚文本定位，行号随刀漂移不引；cwd = `user/`）

```bash
mkdir -p userbins/app-stage/APPDEMO/bin userbins/app
cp bins/appdemo/manifest.toml userbins/app-stage/APPDEMO/
cp cargo-target/aarch64-unknown-linux-musl/release/appdemo userbins/app-stage/APPDEMO/bin/
python3 ../tools/mkapp.py userbins/app/APPDEMO.bap userbins/app-stage/APPDEMO
```

要点：staging 目录内容必须**恰** `{manifest.toml, bin/}`，`bin/` 恰一个常规文件
（= ELF 本体，名字 = manifest `entry` 去掉 `bin/` 前缀）；输出文件名必须 =
`<id>.bap`。mkapp 自动生成第三条目 `SHA256SUMS`（manifest 与 ELF 两行的 sha256
清单）——**这不是你可以手写的文件**，staging 里出现同名文件 = `未知内容` 拒。

成功输出一行：`mkapp: <path> <n>B <ID> v… console=… stack=… intent=…`。

### 5.2 复验既有包

```bash
python3 $ROOT/tools/mkapp.py --check <path.bap>
```

只验不写：形状断言（恰 2 或 3 条目，第三条目名恰 `SHA256SUMS`；2 条目 =
SDK-1a 前历史包，同样可验）+ manifest 全量门禁复跑（含规范形逐字节）+
SHA256SUMS 在场则逐文件重算比对 + ELF 魔数。通过 =
`mkapp: <path> OK <n>B entries=<k> digests=<ok|n/a>`。

### 5.3 mkapp 用法速查

```bash
python3 $ROOT/tools/mkapp.py <out.bap> <app-dir>   # 打包（app-dir = {manifest.toml, bin/}）
python3 $ROOT/tools/mkapp.py --check <path.bap>    # 复验既有包（只验不写）
python3 $ROOT/tools/mkapp.py --new <dir> --id <ID> # 脚手架（§3.4）
python3 $ROOT/tools/mkapp.py --selftest            # 门禁自检（零依赖）
```

门禁五道（任一失败 = 一行理由 + 非零退）：① manifest 可解析且结构/值域过检；
② 规范形重序列化逐字节相等；③ `entry` == 包内 bin/ 唯一文件的完整路径；
④ 输出文件名 == `<id>.bap`；⑤ bin 文件头 4 字节 == `\x7fELF`。

## 6. manifest v1 字段速查

| 节.键 | 值域 | 缺省 | 语义 |
|---|---|---|---|
| `app.id` | `[A-Za-z0-9._-]`、首字符字母数字、≤24B | 必填 | 包身份；输出文件名 `<id>.bap` |
| `app.version` | ≤16B 自由串 | 必填 | 应用自述版本（与 `[compat]` 的 SDK 版本无关） |
| `app.entry` | `bin/` 前缀完整路径、≤32B | 必填 | == 包内唯一 bin 文件路径；= spawn argv0（§7） |
| `app.type` | v1 恰 `"app"` | 必填 | gui/headless/daemon 词表 v2 add-only |
| `app.intent` | 六词：unspecified/latency_critical/interactive/utility/background/maintenance | 必填 | 调度 intent 声明（叠加于公平，不替代） |
| `compat.min` | `x.y.z`（每段 1–3 位十进制、无前导零、0..=999） | 三键齐备或齐缺 | 运行下界：appd 装载时 `min > SDK_CURRENT` 即拒 |
| `compat.target` | 同上 | 同上 | 按哪一级平台行为契约测试（v1 占位契约） |
| `compat.compile` | 同上，且 `min ≤ target ≤ compile ≤ SDK_CURRENT(0.1.0)` | 同上 | 打包所用工具链级——mkapp 闸「不能面向未来 SDK 编译」 |
| `capabilities.console` | bool | 必填 | true → stdout 授 console handle（println! 落串口）；false → appd 私有采集对（EOF-only 收集） |
| `capabilities.fs` | 恰 `["rootfs"]`（v1 词表闭集） | 缺 | 声明即真授能：appd 装 fs 四元 gift，libc open/read 等文件面立即可用；**v1 = 与 bsh 同权的全卷读写删**（含写/删 op，无 per-app 隔离——私有目录是 v2 `$appdata` 词，v1 硬拒） |
| `capabilities.net` | 恰 `["client"]`（v1 词表闭集） | 缺 | **v1 勿声明**：schema/打包收，装载时 appd loud 拒（`eco: app <id> net unserved`）——net 服务面挂账中 |
| `runtime.stack_pages` | 整数 1..=64 | 整节可省（省 = 8） | 主栈页数；栈深需求大的应用显式抬（hexyl 32 页先例）——栈穿 = 干净 D-abort |
| `security.profile`/`key_lineage` | `[a-z0-9-]{1,16}`，两键齐备或齐缺 | 整节可省 | 纯占位（v2 签名预留壳）；v1 解析过即忽略，零行为 |

未知节/未知键一律硬拒（loud 失败优于半工作）。`[compat]` 整节缺席 ≡ 按
SDK_CURRENT 处理（旧包路径，零行为漂移）。

## 7. 应用侧契约清单（写代码前必读）

立法原文：`docs/应用模型设计.md` §3（「安装 = 翻译、启动 = 授能」）、§0.1
（一格式一扇门——GUI/CLI/服务/驱动不是四种包，是同格式里的数据字段）。

1. **argv0 = entry**。appd 以 manifest `entry` 串作 spawn name——`argv[0]` 恒为
   `"bin/<slug>"`（不是裸文件名）。§3.3 模板里的 assert 是契约活证：错值 = 断言
   炸 → abort → 装载失败 loud。
2. **EOF 先行**。经 libc `exit` 族退出（std 的 `main` 返回 / `ExitCode` /
   `process::exit` 都走这条面）时，berry-libc 先向 stdout 发零长 EOF 再真退——
   收集方（appd 或管道对端）以此认终点。别绕过 libc 直接退（EOF 永不到达，
   收集方挂到超时）。
3. **退出码语义**。退出码真码传回（appd reap 收码；非 0 = 装载降级行）。
   `panic` 在 release `panic = "abort"` 下 = libc abort → EOF 先行 + 退出码
   134。失败就 panic 是可接受的 loud 形态，但退出码请按语义给。
4. **能力 = handle，没申请就没有**。manifest 是唯一授权入口：你没写的能力键，
   spawn 交给你的 handle 表里就没有对应 handle——不是「有权限位但被运行时
   检查」，是**根本拿不到**（能力模型与 ACL 的本质区别）。调用对应 syscall/
   libc 面拿到的是 `-EBADF`/`ENOENT` 类错，不是权限弹窗。
5. **console 两态**。`console = true`：stdout = console 发端别名，`println!`
   直落串口（调试首选）。`console = false`：stdout 由 appd 私有采集对收集
   （EOF-only），串口上看不见你的输出。
6. **fs 词 = 镜子**。`fs = ["rootfs"]` 声明了、装载才会装 fs gift；声明了且
   授能失败 = loud 降级行（绝不静默少装）。文件面用法与宿主 Rust 一致
   （`std::fs::read` / `File::open` …），底层经 fsclient → fsmgr RPC。
   v1 边界如实：`rootfs` 词 = 与 bsh 同权的**全卷读写删**（fs 通道双向
   dup，含 MPUT/TRUNC/UNLINK 等写删 op，作用于挂载卷全卷），无 per-app
   隔离——per-app 私有目录是 v2 `$appdata` 词（v1 词表硬拒），勿按 v2
   语义理解 v1 词面。
7. **net v1 勿声明**（§6 表）。词表先行 ≠ 无服务硬授——诚实 loud 拒好过空头
   支票。
8. **`SHA256SUMS` 不是你的文件**（§5.1）。mkapp 产包期自动生成，开发者侧
   不可写、不需知。

## 8. 跑起来（集成面）

`.bap` 进系统的现行接线 = 仓库 `justfile build-user`：mkcpio 把
`app/<ID>.bap` 作为单条目打进 `rootfs.cpio`（mkcpio 调用的 `name=path`
对列表——以 `app/APPDEMO.bap=userbins/app/APPDEMO.bap` 锚文本定位），随后 `just run-rootfs` 起系统——appd 扫描 `app/*.bap`、过门禁、
按 capabilities 授能 spawn。期望串口证据行（appdemo 为例）：`app APPDEMO up`
（应用打的）与 `APP ok n=`（appd 装载谓词）。

**仓外应用 v1 尚无自动接线位**（build-user 条目表挂账中）——把你的 `<ID>.bap`
交给系统集成者，或临时在 in-tree 仿 §5.1 的 staging + mkcpio 行手工进包。
`--check` 过 = 包本身合规，与接线无关。

## 9. 发布与获取（SDK-1b：crates.io 面）

SDK 八 crate 与依赖序（叶子在前）：`berry-sys` / `berry-tls` /
`berry-netdproto` / `berry-fsproto` / `berry-mmap` / `berry-signal`
（六叶子，互不依赖）→ `berry-fsclient`（→ sys+fsproto+netdproto）→
`berry-libc`（→ 六叶子全量直赖）。仓内开发走 path 依赖（§3.2）；八件发布到
crates.io 后，仓外工程的依赖形态：

    [dependencies]
    berry-libc = "0.1.0"        # 取代 §3.2 的 path 形（其余七件同理）

（v1 边界见文首双态声明：构建链工具仍在仓内。）

### 9.1 维护者发布手顺（八连 publish——需 crates.io 账号）

    # 一次性：
    #   crates.io 账号（GitHub 登录）→ Account Settings → API Tokens
    #   创建 token（publish-new-update scope），然后：
    cargo login                # 粘贴 token（存 ~/.cargo/credentials.json）
    #   发布机前提（双镜头审查 F5）：根 .cargo/config.toml 锁
    #   build.target=aarch64-unknown-none 且 config 发现跨 workspace 边界
    #   命中——八连 publish 的 verification build 即对该 target，目标不在册
    #   会炸在 verification（报错形态 E0463 can't find crate for `core`，
    #   与「代码坏了」难分）：
    rustup target add aarch64-unknown-none
    #   钉版陷阱（2026-11-01 实抓）：仓根 rust-toolchain.toml 钉 1.97.0 后，
    #   rustup 把「stable」与「1.97.0」当两个独立工具链（同版本号也是两个
    #   安装目录）——target 装在 stable 名下救不了 1.97.0 的 verification。
    #   上面这条 add 在仓库内跑会自动落钉版名下（rustup 按目录上下文解析）；
    #   保险形态是显式 --toolchain 1.97.0。抬版 = 改 rust-toolchain.toml +
    #   重装 target + ci.yml/sdk-publish.yml 的 toolchain 行三同步。
    #   发布前提（F4）：从**已提交**的工作树发布——八份 README.md 必须
    #   已随 Cargo.toml 入 commit；干净 clone/`git clean` 后缺
    #   README 的树上跑 publish 会在 readme 解析步直接炸。

    # 名占预检（八行应全 404；非 404 = 名被占，停下议事——2026-10-30 七名全
    # 空闲复核 + 2026-11-01 九名含 berry-signal 复核均 404；注意必须带
    # User-Agent，裸 curl 得 403 反爬不是 404）：
    for c in berry-sys berry-tls berry-netdproto berry-fsproto berry-mmap berry-signal berry-fsclient berry-libc; do
      curl -s -A "berryos-release-check" -o /dev/null -w "$c %{http_code}\n" \
        "https://crates.io/api/v1/crates/$c"
    done

    # 发布前必做：八份 user/berry-*/Cargo.toml 的 repository 字段与八份
    # README.md 内仓库链接，从占位 https://github.com/berryos/berryos 换成
    # 公开镜像真地址（占位上线 = crates.io 页面死链，且该字段只在下一版
    # 发布时才刷新——0.1.0 存续期内恒死链）。换完自检（应零输出；有输出
    # = 占位残留，勿发——双镜头审查 F3）：
    #   【已完成 2026-11-01（821a0e5）】：23 处全量换装 + MSRV
    #   rust-version="1.93"（1.93.0 实测 check 过 berry-libc 全依赖树）+
    #   仓级 rust-toolchain.toml 钉 1.97.0。自检命令留作回归守卫：
    grep -rn 'github.com/berryos/berryos' user/berry-*/Cargo.toml user/berry-*/README.md

    # 八连 publish（叶子序；顺序错了当场 "no matching package" 报错——
    # tarball 生成即剥 path、打包期就要 registry 可解析。工作树脏则每条
    # 加 --allow-dirty）：
    cd user/
    cargo publish -p berry-sys
    cargo publish -p berry-tls
    cargo publish -p berry-netdproto
    cargo publish -p berry-fsproto
    cargo publish -p berry-mmap
    cargo publish -p berry-signal
    cargo publish -p berry-fsclient        # 六叶子在册后才可解析
    cargo publish -p berry-libc            # fsclient 在册后才可解析

注意事项：

- **index 传播延迟**：连发中偶发 `no matching package named berry-sys` =
  crates.io sparse index 尚未收录上一发（秒级到分钟级）——等 30–60s 重试
  **当前这条**；已发成功的那条重试会报「already exists」，看到即跳过继续。
- **不可逆**：版本一旦上传不可删除（只能 yank——yank 只阻止新依赖解析，
  已锁定版本照常可用）。发布 = ADR #57 语义版本纪律生效起点（0.x 阶段
  minor 即 breaking）。
- 八件 version 统一 0.1.0；抬级时八份 Cargo.toml + 内部依赖 version req
  联动同抬——流程归版本纪律另刀，本指南不展开。

### 9.2 发布性预验与 Trusted Publishing 接管（SDK-02 拍板①，2026-11-01）

**dry-run 预验实态**（2026-11-01 干净树实测，821a0e5 后）：

- 六叶子（sys/tls/netdproto/fsproto/mmap/signal）`cargo publish --dry-run`
  全链绿（打包 → verification build 对 aarch64-unknown-none → 停在 upload）。
- fsclient/libc 的 dry-run **结构性不可预验**：打包期就要 registry 可解析
  路依赖（tarball 生成即剥 path），叶子未上册前必报 `no matching package
  named berry-*`——这不是包缺陷；两件在真发布序内的自身 publish 步完成
  verification。
- 本地预验 = `cd user && cargo publish --dry-run -p berry-sys`（余五叶同）。

**CI 通道**：`.github/workflows/sdk-publish.yml`（休眠骨架）——手动
workflow_dispatch，默认空跑：六叶子 dry-run 严格守卫 + 两依赖件降级
warning（八件全上册后自然转绿）。

**Trusted Publishing 接管三步**（RFC 3691；首版手动发布后才可开始）：

1. 八件首版按本节手顺手动 publish（一次性 `cargo login` 起步）。
2. crates.io 每个 crate → Settings → Trusted Publishing：owner=`miuiadmin`
   repo=`BerryOS` workflow=`sdk-publish.yml` environment=`publish`（与
   workflow job 的 environment 字段一致，错名 = OIDC 交换对不上）。
3. 把 sdk-publish.yml 的「OIDC 交换」占位步（exit 1 锁死态）替换为
   crates.io 当时文档的官方交换方式——RFC 3691 示例 action
   （rust-lang/crates-io-auth-action）官方标注「当前不存在」，故骨架里
   是文档化占位而非可用实现。替换后 workflow_dispatch 空跑切真发，
   发布序/重试语义与本节同源。
