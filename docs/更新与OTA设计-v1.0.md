# 更新与 OTA 设计（四层刀法 · 掉电安全 · 固件随包）

> 版本：**1.0**（v1.0）｜2026-11-06

> 回答三件事：**四层东西（boot / 系统 / 应用 / 固件）各自怎么更新、每层怎么掉电安全、按端怎么差异**。
> 核心论点：**升级分四层、每层一把刀。「双分区」只是 L0 块层的版本，我们的主刀在命名空间层——sys 目录级 A/B + 指针原子翻。换家具，不换房子：user/ 数据从来不动**。手机厂换系统是换发动机（整机重刷、恢复模式、变砖恐惧）；我们是换家具，房子（存储布局与归属语义）从来不动。

> **2026-10-30 追记**（SEC-01 day-one 缝冻结 2026-10-30——件 20；SEC-02 A3 文档冻结）：§2.1 L0 slot 状态三字段（Android A/B 同型）+ 「SUCCESSFUL 先于 rollback index 更新」次序 + RPMB 归属裁定（帧驱动=持证应用 / HMAC=keystored / 计数统一走 CounterBackend）+ `berry.verifiedbootstate` 四态验证标记。

## 0. 病根：整机重刷文化

- **恢复模式 / fastboot / 线刷**：把「换系统」做成「换发动机」——用户数据跟着搬家，失败 = 变砖恐惧。
- **分区级 A/B**（Android seamless）：方向对（掉电安全、无变砖），但把块层实现抬成用户概念——十几块分区、空间翻倍、分区名泄漏进论坛帖。
- **固件散放**（/lib/firmware 大杂烩）：无版本归属、无签名链、与驱动版本脱钩——「驱动装了新版但固件还是旧的」是常年病。
- **更新恐惧的代价**：用户拖延更新 → 安全补丁覆盖率低 → 厂商强推重启 → 信任进一步崩坏。**更新体验是安全性的直接影响因子，不是体验加分项**。

## 1. 四层刀法总表

| 层 | 更新对象 | 刀 | 掉电安全 | 机制现状 |
|---|---|---|---|---|
| **L0 boot/SoC** | boot ROM 之后的最早级载荷 | SoC 契约的 slot A/B（若芯片强制）+ **启动计数回退**（ChromeOS 式） | slot 指针单字原子写 + 回退保底 | 真机面（P8）；QEMU `-kernel` 直加载无此层 |
| **L1 系统** | `sys/` 整棵（内核+服务+工具） | **目录级 A/B**：两棵系统树 + 指针单字原子翻 | 指针原子 + 新系统自证健康（失败自动回指旧槽） | 设计（#45 四棵树的直接红利，本文 §3） |
| **L2 应用** | 单个 app 树 | appd 换树：`.new` 装好 → rename 原子交换 → 删旧树 | rename 原子性（v2 CoW 快照加强） | 已设计（`应用模型设计-v1.0.md` §3 升级=原子换树） |
| **L3 固件** | 设备固件（wifi/BT/触摸控制器…） | **随驱动包**：`fw/` 在驱动包内，版本与驱动绑定；更新固件 = 更新驱动包 | 同 L2（树原子换） | 设计（`驱动模型设计-v1.0.md` §1/§5 L3） |

**user/ 不动是四层共同的底线**——系统换了、应用换了、固件换了，照片文档表盘一个字节不动（四棵树按所有权分的直接兑现，#45）。

## 2. L0：boot 层是「SoC 契约」，不是我们的分区

- boot ROM 按固定偏移加载下一级——这是**芯片契约**（每颗 SoC 不一样），不是 OS 的分区决策（`存储布局与沙箱设计-v1.0.md` §1 已裁定）。
- 若 SoC 引导链强制双槽（多数手机 SoC 如此）：L0 老老实实做物理 A/B——但它是**实现细节**，用户可见语义仍是「翻指针」。#45 重议触发器已预埋此后门：真机强制多分区 → **块层**适配，用户可见布局与归属语义不变（分区永远不升用户概念）。
- **启动计数回退**（ChromeOS verified boot 同款）：新槽启动计数 +1，新系统须在限定窗口内写「健康」标记（关键服务全起 + 自检过）才清零；连续 N 次未健康 → boot 自行回指旧槽。**变砖在机制上不可能**。
- QEMU / 无双槽 SoC（部分手表）没有 L0 概念——单载荷直加载，L1 直接顶到最前。

### 2.1 L0 slot 三字段 + 反回滚次序 + RPMB 归属 + 验证态标记（SEC-01 day-one 缝冻结 2026-10-30——件 20）

四件设计冻结（真机窗口 P8 实板，设计位现在定死；与 `安全与硬件隔离设计-v1.0.md` §4/§4.1/§6 对齐）：

1. **slot 状态三字段**（Android A/B boot_control 同型，字段名照抄）：`priority`（优先级，>0 = 可启动；「active 槽」= 高 priority 槽的派生态，不单独存）、`tries_remaining`（剩余尝试次数）、`successful_boot`（成功标记）。落盘形态 = **镜像内固定偏移小文件或专用扇区**，BerryBoot 读它选槽——本节上方「启动计数 + 健康标记」机制的机器可读化。状态机对齐 Android：更新引擎写备槽 → 激活（priority 高 + tries_remaining=N）→ 重启 → bootloader 选高 priority 槽 → 新系统自检 → `markBootSuccessful` 等价面清 tries 落 successful → 失败每 boot 消耗一次 tries、归零 bootloader 自行回旧槽（变砖在机制上不可能，§2 结论不变）。
2. **「SUCCESSFUL 先于 rollback index 更新」次序纪律**：槽标 SUCCESSFUL **之后**才允许更新反回滚计数元数据——否则先写回滚计数 = 旧槽（版本号更低）再也回不去，**回退机制被防回滚机制反噬**（AOSP 明文规则）。此序写进更新引擎状态机，与 §3「防降级」bullet 构成完整次序契约：回退自由（SUCCESSFUL 前）→ 防降级生效（SUCCESSFUL 后）。
3. **RPMB 归属裁定**（对齐 `安全与硬件隔离设计-v1.0.md` §4.1 TEE 客户端定位；`驱动模型设计-v1.0.md` §1/§2 既有面不为此改）：
   - **帧驱动 = 持证应用**（devmgr 面，vblk 同族——RPMB 是 eMMC/UFS 块设备的子协议，走块设备授权链）；
   - **auth key 持有者与 HMAC 计算 = keystored**（BerryOS 无 TEE，keystored = 安全侧进程级隔离最小近似——同 Linux RPMB 子系统「内核只透传帧、密钥在安全世界」拓扑；帧驱动永不接触 auth key）；
   - **计数统一走 CounterBackend**（read / increment / compare_and_set 抽象，SEC-01 §4.5 件 16）——L0 启动计数、rollback index、未来认证限速计数同一接口；后端 QEMU 软件桩 → 真机 RPMB/eFuse 换芯零协议改。**内核零 RPMB 知识**。
4. **`berry.verifiedbootstate` 验证态标记**：`androidboot.verifiedbootstate` 的等价物，进 handoff/boot 标记面——四态对齐 Android RootOfTrust 枚举与颜色态：`verified`（GREEN，厂根验签）/ `self-signed`（YELLOW，用户根）/ `unverified`（ORANGE，解锁未验）/ `failed`（RED，验签失败——真机路拒跳或警告屏，QEMU 路占位）。下游（keystored 证明、盘加密密钥绑定、遥测）第一天就能消费「当前验证态」，不需要内核 ABI 再开洞。

> 来源：SEC-01 §4.5 件 20；`research/sec-notes/SEC-1-引导链安全与VerifiedBoot.md` §3.5（A/B 三字段 + SUCCESSFUL/rollback 耦合）、day-one 留缝 3/5、`research/sec-notes/SEC-4-密钥管理与加密芯片.md` §3.4（RPMB 协议）、§5-3（RPMB 归属裁定原文）。

## 3. L1：系统层主刀 = 目录级 A/B（零分区的更新面兑现）

`存储布局与沙箱设计-v1.0.md` §2 预留的 `sys/boot/` 槽位展开：

```
sys/
└── boot/            ← 更新面（sys 树内的保留目录）
    ├── a/           ← 活动系统树（kernel/ + svc/ + bin/…）
    ├── b/           ← 备用槽（更新落这里；不用时可清空回收空间）
    └── ptr          ← 指针（单字：'a' | 'b'）+ 健康标记/启动计数
```

运行视图把活动槽挂成 `/sys`（命名空间挂载——「卷 = 挂载点」的直接应用，决策 #6）；b 槽与 ptr 是普通文件，对用户不可见。

流程：**下载**（net 服务，落 `tmp/`）→ **验签**（度量链 #24 延伸：整树 hash 清单逐项核）→ **备槽**（逐文件落 `sys/boot/b/`——落一半也无妨，b 不是活动槽）→ **翻指针**（单字原子写）→ 重启 → 新系统自检 → **写健康标记**。任一步掉电：指针未翻 = 一切照旧；指针已翻 = 计数回退接管。

- **与分区级 A/B 的对账**：同样掉电安全；我们不翻倍整盘空间（b 槽按需全量或差量，弹性是文件树的、分区没有）、不把块层概念抬进用户视野、不需要改分区表的专用 bootloader。
- **防降级**（安全面）：回退只许回到「未被安全公告否决」的版本——反回滚计数挂度量链（#24，防 downgrade 攻击），实板时落地。
- **内核镜像**在系统树内（`sys/…/kernel/`，存储布局 §2 的 `sys/kernel/` 槽）——L0 只管「从哪棵树起」。

## 4. L2：应用层 = appd 换树（已设计，零新增）

`应用模型设计-v1.0.md` §3：`.new` 装树 → rename 原子交换 → 删旧。更新的调度策略（错峰/闲时/Wi-Fi only/电量门槛）是 appd 策略面；**墓碑应用更新连进程都不用杀**——下次复活自然读新树（§4.1 的免费红利）。

## 5. L3：固件随驱动包（收编 /lib/firmware）

- 驱动包内 `fw/` 目录 = 该设备固件的唯一合法住址；manifest 声明版本；签名随包（#24）。
- 「更新 wifi 固件」=「更新 wifi 驱动包」——一个动作、一条版本线、一次回滚面（回滚驱动树 = 回滚固件）。Linux「驱动与固件分别装、版本矩阵靠运气」病从结构上消失。
- 加载协议：devmgr 拉起驱动 → 驱动从自己包内读 `fw/` → 经设备协议下发（驱动自治 + appd 监督，与 vblk 启动自验同款形状）。

## 7.5 签名槽生命周期吸收议程（借 swift-os，调研 22 号 §⑤）

swift-os 签名双槽「安装—激活—确认—回退」生命周期实读出的五条可借鉴点（调研 22 号 §5），对照 BerryBoot 现状逐条落地。
与 `存储布局与沙箱设计-v1.0.md` §8.5 互链：那边管槽的存储分层形态（签名只读 base 双槽怎么住，调研 16 号成果），
这边管槽的签名与安装生命周期（怎么签、怎么装、怎么确认、怎么回退）——一事实一归属，两侧衔接即完整更新安全面。

- **① 每槽独立签名，槽身份绑进签名消息**（ADR #77 R1a 随裁补注 2026-11-11：段身份白名单案落册——OEM 段绑段身份、平台段绑组合式树身份并枚举段 hash 白名单；lane 语义按 L1 累积强制——本句 L1 半边以 #77 裁定为准）：差距——BerryBoot 现为纯装载器，验签面停在 §2 设计位；
  槽条目若只签内容哈希，跨槽重放（A 槽签名条目挪进 B 槽）签名拦不住。swift-os——SWOSKERN v4 manifest 每槽
  独立条目，52 字节签名消息把 slot_index 绑进签名域（魔数‖索引‖长度‖哈希），重放条目验签即死；v3 单签名盖
  两槽改 v4 的动机正是「新内核只装备槽、无需重签另一槽」（调研 22 号 §3）。落地——L0 slot 条目（§2.1）与
  L1 树清单（§3）的签名消息设计时即绑槽与树身份；对抗测试照抄其夹具范式「错误索引配正确签名的条目必须被拒」
  （调研 22 号 §5 ①）。挂 v2+（L1 随真机窗口，L0 随 P8 SoC 选型）。

- **② 选择器非信任锚**：差距——L1 指针 `sys/boot/ptr`（§3）将来翻写时绕不开「谁有权写指针」。swift-os——
  active、attempt、state 等可变状态全走不签名的 CRC／SHA 完整性通道：内核只持公钥，不能自签运行时要写的状态；
  签名对象只有镜像本体与 manifest 元数据，指针指向物自认证，篡改指针最坏 = 换选另一个仍有效签名的旧槽或
  boot loop（可用性面，永不升级为代码完整性绕过，调研 22 号 §3）。落地——ptr、健康标记、启动计数只做完整性
  保护，密码学强度全压在两棵树各自整树验签（§3 验签步）；BerryOS 铁律 FS 用户态，指针写者 = 持证更新服务。
  挂 v2+（随 L1 双目录与指针实板）。

- **③ 安装三段式＋commit 全量重验＋落盘先于指认**：差距——§3 流程「备槽 → 翻指针」有掉电安全论证（b 槽落
  一半无妨），但缺「递交前独立复核」一层（写完即信）。swift-os——stage begin、write、commit 三段：begin 即查
  版本地板、槽容量、能力位、单 owner（fail 早）；commit 侧全量重验四件事（写满、长度对拍、盘上重哈希、验签），
  FLUSH 落盘先于任何 manifest 指认（调研 22 号 §3）。落地——更新引擎在翻指针前加独立复核步：对备槽整树重算
  hash 清单对拍签名 manifest，全绿才允许写 ptr；掉电次序纪律 = 树数据全量落盘 flush 先于 ptr 写。挂 v2+
  （随 L1 实板刀）；断电暴力验收随真机台阶二（真板可真实切电，台阶状态随裸机提案复评）。

- **④ confirm 先于抬反回滚地板**：非差距而是佐证——§2.1 第 2 条已冻结「SUCCESSFUL 先于 rollback index 更新」。
  swift-os——confirm 成功才把 minSystemVersion 抬到该槽版本，确认前回退自由存在；两项目独立收敛到 AOSP 同一条
  规则，且给了该次序的一个可测实现（调研 22 号 §3）。落地——P8 实板时以其 confirm 与地板抬升的次序断言为
  验收参照；本条零新增议程，纯外部佐证入账。挂 P8（随 §2.1 既有冻结兑现）。

- **⑤ 格式单源共享（I/O-free 格式核心）**：差距——v1 无槽与镜像签名格式，未来宿主打包工具与机上验证面各自
  实现格式必有漂移面。swift-os——swosboot.swift 同一 I/O-free 文件编进内核、宿主工具、宿主测试三处，宿主写的
  字节就是内核解析的字节，格式永不漂移（调研 22 号 §5 ⑤）。落地——槽 manifest 与更新包格式做成无 I/O 纯库
  （进字节切片、出判定），单源编进 berry-boot 工具链与持证更新服务两侧，宿主测试同源。挂 v2（随首个签名
  格式落地，度量链 #24 实板同期）。

**诚实边界（减弱面记入）**：swift-os 的反回滚地板 minSystemVersion 住在不签名的可写 manifest 里——持整块
store 盘的离线攻击者理论上可清零地板后配旧签名镜像降级；其信任边界论证只覆盖 active 指针面，未覆盖地板被磁盘
篡改降低的面（调研 22 号 §3 末减弱面记录，§6 预期四呼应）。BerryOS 规避：反回滚计数走 CounterBackend 落
RPMB／eFuse（§2.1 第 3 条结构性选择，对离线磁盘攻击者更强）——本议程落地时，地板永不落进不签名的可写文件。
