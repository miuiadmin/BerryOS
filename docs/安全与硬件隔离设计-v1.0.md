## 1. 为什么能力模型不够

纯能力只校验"你有没有这个 handle 的权限"。但三类攻击它管不住：

1. **DMA 攻击**：用户态驱动能指挥设备 DMA，绕过 CPU 页表，直接读写任意物理内存——能力形同虚设。
2. **运行期内存破坏**：内核 `unsafe` 区（页表/上下文切换）一旦被 ROP/JOP/UAF 打穿，能力检查可被绕过。
3. **启动期篡改**：内核镜像/bootloader 被换，运行期能力规则全是空中楼阁。

→ 分别由 SMMU、ARM 安全扩展、度量启动兜住。

## 2. IOMMU / SMMU（能力安全的硬件后盾，决策 #22）

- **每个设备一个 SMMU domain**，绑定其被授权的物理区间（= 它能 DMA 进的那些 VMO 的物理页）。
- 用户态驱动经 Resource handle 拿到设备 MMIO + 一个**锁页/连续的 DMA VMO**；SMMU 只放行该 VMO 区间，越界 DMA 被 SMMU 拦截并上报（ faults → 异常通道）。
- 与内存管理（`内存管理设计-v1.1.md` §6 DMA VMO）联动：DMA VMO 带 `CONTIGUOUS` + 锁页（不可换出），物理地址交给设备；SMMU domain 由内核在 map_device_memory 时建。（v1 已落形态 = 纯 VMO 无 IOMMU：vmo_get_phys 查页后备、无 IOMMU 披露面 v1 接受——`驱动模型设计-v1.0.md` §2；CONTIGUOUS+锁页+SMMU 绑定仍 v2/v3）
- **热插拔/解绑**：驱动崩 → Job 回收其 handle → 内核拆 SMMU domain → 设备无法再 DMA。
- **编排方 = devmgr**（`驱动模型设计-v1.0.md` §2，ADR #46——IOMMU DMA 圈是三铸件之一）：给哪个设备铸/拆 domain 由 devmgr 走应用链编排；本文件只管内核侧 domain 机制。

> 没有 SMMU，"用户态驱动 + 纯能力"就是不成立的；这是 Zircon/seL4 都重度依赖的件。

## 3. ARM 安全扩展（运行期，决策 #23）

| 扩展 | 防什么 | day-one 怎么用 |
|------|--------|----------------|
| **PAC**（指针认证，ARMv8.3） | ROP（返回地址/函数指针被篡改） | 内核指针签名/校验，target feature 开 |
| **BTI**（分支目标识别，ARMv8.5） | JOP（跳到非法落点） | 代码段标记合法落点 |
| **MTE**（内存标签，ARMv8.5） | UAF / 越界 / 双释放 | 内核堆 slab 打标签，访问校验 |

- **目标 day-one 开**（`-Z target-feature=+pauth,+bti,+mte` 或 target.json），`unsafe` 区显式管理。**Phase 0/1 推迟**：QEMU `-cpu cortex-a72` 是 ARMv8.0、无此三扩展（开了也只是 NOP/陷入），Phase 1 仍保持 cortex-a72；待 **v2** 切 `-cpu max`（ARMv8.5+）时**三档分刀**（2026-10-29 C4 拍板——三扩展不是同一个开关，旧文「一次性开，源码零改动」仅对 BTI 严格成立，已废）：
  - **BTI ≈ 零改动**——代码段标记 + target feature，开即生效，先开；
  - **PAC = key 管理小刀**——启动期生成/装载 PAC key 的编排，次之；
  - **MTE = 分配器中心点刀**——需 `-machine virt,mte=on` 机器级选项 + 内核 slab/buddy 分配器单一入口打标签（async 先行 ~93% UAF 检出、最坏 6.64x 减速，性能帽对 bench 基线），最后落。

  （切换点见 `路线图-v1.1.md` v2、`tools/`。）
- MTE 对内核堆（slab 分配器）尤其值钱（深度打标签见 §6 v2）：每块分配一个标签，越界/UAF 立即触发。
- 这些是**硬件加速的运行期安全网**，与 Rust 编译期安全互补（Rust 管 borrow，PAC/BTI/MTE 管 unsafe 区与攻击面）。

## 4. 安全 / 度量启动（启动期信任，决策 #24）

```
ROM(根) ─度量─▶ bootloader ─度量─▶ kernel ─度量─▶ 关键服务
                    │               │              │
              每级把下级 hash 累加记入 secure element / TPM
```

- **度量链双路选主**（2026-10-29 C2 拍板——旧文「QEMU 用虚拟 TPM；真机用硬件」隐含 TPM 单路，已修订）：**手机 = TPM 2.0 兼容面**（QEMU 用 swtpm 起步，真机用硬件 TPM/融合安全芯片）；**手表/穿戴 = DICE**（UDS→CDI 逐层派生：每级从上一级密钥 + 本级度量派生下一级，无 TPM 依赖——ADR #39 手表线定位下结构性必要）。**测量清单 TLV 单一事实源**：两条路消费同一份逐级 hash 清单（bootloader/kernel/关键服务，TLV 编码 + 槽位编号表），仅派生引擎不同（PCR 扩展 vs DICE 派生链）——两路一套语义，不许漂移出两套测量面。
- **信任根派生自度量**：初始能力包（`能力模型设计-v1.0.md` §5 bootstrap channel）的合法性由"度量结果符合预期"保证，**不是硬编码"init 是特权进程"**。
- **远程证明**（v3+）：设备可向验证方出示度量摘要，证明运行的是未被篡改的内核 + 服务集；token 采 **EAT (RFC 9334)/CBOR**（业界收敛格式，两路同用）。
- **回滚保护**：secure element 存单调计数器 / 反回滚计数，防刷入旧（已知漏洞）镜像。

### 4.1 TEE 定位：客户端，不自建（C3 拍板 2026-10-29）

BerryOS 是 TEE 的**客户端**，不是 TEE 的业主——负面清单成文：

- **不自建 TEE OS**——全 Rust TEE OS 仅列 v4+ 实验轨道，不作主线依赖。
- **不占 EL3**——内核止步 EL1/EL2，EL3 属平台固件（TF-A 类）；引 Fuchsia 参考不引申为业主立场。
- **用户态不得直发 SMC**——内核只给 **OEN allowlist 受控桥**：keystored 等持证服务经 syscall 面请求，内核按 Trusted-OS OEN/Function-ID 白名单放行特定调用，其余一律拒。
- **keystored = 进程级隔离起步**——密钥服务先是普通用户态服务（进程边界 + 能力约束 + QEMU 软桩后端）；真机对接厂商 TEE（KeyMint/Trusty 类）时 **wire 面不变、后端换真件**。

### 4.2 测量槽位编号表（SEC-01 day-one 缝冻结 2026-10-30——件 12）

§4「测量清单 TLV 单一事实源」的槽位号分配**现在定死**。PCR 分配与 bank 激活是平台契约、必须平台期定死——TPG 教训：事后协商无门（`research/sec-notes/SEC-3-度量启动与远程证明.md` §4 教训 5）；槽位表对齐同型纪律：**add-only——新槽只追加、永不重分配改义**（ABI「在册模式」同款立法）。对照 TCG PC Client PCR 段位哲学（0–7 固件特权 / 8–15 OS 自用 / 16–23 debug·动态），BerryOS 度量链自引导器起算（QEMU 路无固件度量者，真机路由 SoC 引导链上一级补位）：

| 槽位 | 度量对象 | 度量者 | 段 |
|---|---|---|---|
| 0 | 引导器（BOOTAA64.EFI / 真机 BL 等价载荷） | 平台上一级（QEMU 路无上游度量者，恒零占位；swtpm 相启用时固件侧补） | 固定 |
| 1 | 内核 KERNEL.ELF | BerryBoot（`br entry` 跳转前——kfile 读段顺手累积 hash，SEC-3 启示 2「引导器读段即度量点」） | 固定 |
| 2 | initrd（INITRD.BIN 整 blob） | BerryBoot（init 读段同点累积） | 固定 |
| 3 | rootfs（fw_cfg/cpio 路与槽 2 同源字节；盘路 = 挂载卷内容清单摘要——rootfs 迁盘后两槽自然分叉） | BerryBoot（cpio 路）/ 内核首服务（盘路） | 固定 |
| 4 | `.bap` manifest 集（全部 app manifest，**按 app id 升序**逐条累加——IMA 单槽累加同型） | appd（收集/装载时） | 固定（累加） |
| 5–15 | 预留（未来固定分配：现代 FS 超块、devmgr 设备授权表、关键服务逐个（§4 度量链第四级）等——启用时逐个定死入本表） | — | 预留固定 |
| 16–23 | 动态/调试（v2 遥测环 append-only 测量事件流——TCG PC Client 16–23 debug/dynamic 段同位） | 运行期按需 | 动态 |

- **累加语义**：每槽一个累加器 `slot_new = Hash(slot_old ‖ entry_digest)`（PCR extend 同式）；TLV 清单逐条目记录（槽位号 + 算法 ID + digest + 描述串），**重放清单即重建全部累加器**——清单是单一事实源，累加器只是派生态。槽 4 取 id 升序 = 度量可复现且与装卸序无关（AI 测试友好化：同输入同输出）。
- **双路映射**（§4 双路选主的接口位）：TPM 路 extend 时固定槽落 **OS 自用 PCR 段（8–15）**——0–7 是固件特权段、OS 改不动（PC Client 惯例）；具体 PCR 号 v3 实现期定死回填本表。DICE 路槽位号直接作逐层 CDI 派生 label。两路一套槽位语义，不许漂移出两套测量面。
- **解封绑定纪律**：密钥解封只绑 0–3 且必须**前向密封**（OTA 前预封到下一 slot 预期度量——Apple SKP 教训，`SEC-7` §3.5：否则每次升级毁钥匙）；槽 4 随 app 装卸翻面、恒不绑；16–23 恒不绑（BitLocker PCR7 运维事件的教训：绑会因合法更新翻面的位 = 每次更新都是恢复事件）。
- 与 handoff 留缝（SEC-01 §4.5 A 组件 1/2，兄弟刀）衔接：TLV 清单与度量锚 `meas_root` 落 BerryHandoff reserved 区具名槽；**本表管清单内条目的槽位号分配**——两刀接口位互补。

> 来源：SEC-01 §4.5 件 12；`research/sec-notes/SEC-3-度量启动与远程证明.md` §3.1（PCR 编号分配表）/§4 教训 5、`research/sec-notes/SEC-5-微内核安全体系.md` §3.8/§5（测量槽位编号表现定死）。

## 5. 与其它子系统接口

- **能力模型**：SMMU domain、度量信任根 = 能力的硬件后盾。
- **内存管理**：DMA VMO（CONTIGUOUS/锁页）+ SMMU；MTE 给 slab 打标签。
- **驱动**：用户态驱动经 Resource + SMMU 安全用 DMA。
- **引导加载器**：度量链落在此。
- **AI 调度**：无关——AI 只在 fair 类内调策略，不碰安全隔离。

## 6. 阶段化目标（对照 `架构决策.md` #20）

- **v1**：PAC/BTI/MTE **暂关**（cortex-a72 无扩展，见 §3；v2 按 §3 三档分刀开）；SMMU **探测**（识别有无）；度量启动留桩。
- **v2**（2026-10-29 C1 拍板扩盒）：原盒（切 `-cpu max`、三扩展按 §3 三档 BTI→PAC→MTE；SMMU domain 建立 + DMA VMO 绑定）**+ keystored 软桩**（用户态密钥服务：ksproto wire 面 + 软桩后端 + RPMB/vTPM 计数后端 trait，定位见 §4.1）**+ 认证绑定链**（锁屏口令 → scrypt → CE/DE 双域密钥解锁——不做 FDE，文件域密钥绑用户认证）。密钥服务是三段论缺的第四段，越晚立越贵。
- **v2.5**：FAT 阶段整卷元数据加密层（自 v2 降档——盘格式 first-format-only：每文件 nonce + class 域随盘格式演进先埋位，加密执法随后补；不可 OTA 改的域现在埋）。
- **v3**：度量链完整（bootloader 度量 kernel，双路按 §4）；远程证明探索（EAT/CBOR）。
- **v4+**：安全启动闭环（签名 + 反回滚）；全 Rust TEE OS 实验轨道（§4.1）。
