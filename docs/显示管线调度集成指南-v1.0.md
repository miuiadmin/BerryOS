# 显示管线调度集成指南

> 版本：1.0 ｜ 日期：2026-11-14 ｜ 定位：显示加速团队（guifbd / gui-wmd / berry-launcher / gfxdemo）把显示管线接入调度器 intent / policy / EAS 体系的使用面指南——每条路线标注「当前可用」或「需调度器改造」，代码可直接抄。机制与 API 全貌归 [调度器API参考-v1.11.md](调度器API参考-v1.11.md)（sched/ 影抄）与 [策略服务用户指南-v1.0.md](策略服务用户指南-v1.0.md)（0x83 六 op），本文只写显示管线怎么接，不双写。

## 〇、速查表：接什么、现在能得到什么

| 路线 | 动作 | 效果现状 |
|------|------|----------|
| Intent 声明 | 创建者在 spawn 前设 `SchedAttr.intent = 0x02` | 声明通道**当前可用**；调度消费大半**需调度器改造**（v2 EEVDF 消费点，见 §一） |
| Policy 注入 | `policy_bind` 给 guifbd 的 key 提 `weight +32` + EPP Perf | **当前可用**（0x83 已落地，weight/EPP 消费在席，见 §二） |
| EAS 大核路由 | 策略表条目 `placement = 2`（偏 big） | 表通道与 TCB 落点**当前可用**；唤醒选核真路由**需调度器改造**（见 §三） |
| 帧率保障 | 提 `sched_slice_hz` 启动参数 + policy 加权 | **当前可用**；intent 直通权重是 v2 蓝图（见 §四） |
| 实测验证 | `tele: intent_tally` / `BENCHRWAKE` / `bench.py --lat` / shadow A/B | **当前可用**（见 §五） |

## 一、Intent 接入（最简——一行代码）

### 1.1 六档值域（编码冻结，u8 越小档越高）

单源 = `intface/src/lib.rs`（`sched/src/intent.rs` re-export）；映射表 = `iprofile/src/lib.rs` `WATCH_PROFILE_TABLE`（v1 绑定表，消费点见 1.4）。

| 值 | 档 | boot-params / manifest 词 | latency_nice | weight 包络 | EPP | timer slack |
|----|----|--------------------------|--------------|-------------|-----|-------------|
| 0x00 | UNSPECIFIED | `unspecified` | 0 | 1..1024 | Efficiency | 50ms |
| 0x01 | LATENCY_CRITICAL | `latency_critical` | -20 | 512..1024 | Perf | 0（exact 铁律） |
| 0x02 | INTERACTIVE | `interactive` | -8 | 256..1024 | Perf | 10ms |
| 0x03 | UTILITY | `utility` | 6 | 64..512 | Efficiency | 50ms |
| 0x04 | BACKGROUND | `background` | 19 | 1..64 | Efficiency | 500ms |
| 0x05 | MAINTENANCE | `maintenance` | 19 | 1..16 | Efficiency | 10s |

显示管线任务（guifbd / gui-wmd / berry-launcher / gfxdemo）应标 `INTENT_INTERACTIVE (0x02)`；若某条链路是闹钟级同步上屏（如未来 vsync 硬同步），才考虑 0x01（该档 slack=0 绝不顺延）。

### 1.2 声明通道（当前可用）——创建者 setattr，spawn 时消费

系统里没有 `spawn_opts.intent` 这个字段；用户态任务的 intent 经 `SchedAttr`（ABI 0x3C `berry_sched_setattr`）声明，语义是「**S1 只存，spawn 时消费**」：`kernel/src/syscall.rs` 的 `apply_sched_attr_to_task` 在 `process_start` / `thread_start` 把 effective 属性（Process 默认 ∪ Thread 覆盖，`SchedAttr::merge`）写进刚装配的 Task（`intent_declared` / `intent_effective` 双写）。因此接线点是**创建者的 spawn 链**——svcmgr / launcher 在 `thread_create` 之后、`process_start`（首线程）或 `thread_start`（后续线程）之前，对 **Thread handle** 设一次（thread handle 创建时即授 `RIGHT_SET_POLICY` / `RIGHT_INSPECT`；Process handle 不带此权，别对它 setattr）：

```rust
use berry_sys::*;

// svcmgr / launcher 的 spawn 链：thread_create 之后、process_start 之前
let mut attr = SchedAttr {
    size: core::mem::size_of::<SchedAttr>() as u32,
    version: 1,                 // size/version 必填（ABI §7.2）
    flags: SCHED_FLAG_INTENT,   // 只置 intent 位，别的字段不动
    intent: 0x02,               // INTERACTIVE
    ..SchedAttr::default()
};
let s = berry_sched_setattr(thread_handle, &attr); // Thread handle 已授 SET_POLICY
debug_assert!(berry_sys::is_ok(s));
```

对已运行任务 setattr 只改存储不生效——intent 想换档须在下一次 spawn（新线程）时兑现。读回验证用 `berry_sched_getattr`（0x3D，`RIGHT_INSPECT`），返回 effective 属性含 `intent` 字段。

### 1.3 两条免代码的伴随通道（当前可用）

- **消息借入（自动生效，无需声明）**：intent 随 IPC 消息传播——server 收消息结算 `intent_effective = min(declared, msg_intent)`（数值越小档越高，min = 语义更强者胜），每条消息重导、下条弱消息自然回落。guifbd 作为显示 server，声明 0x02 后处理消息期间**只可能被借得更高**：UNSPECIFIED（0x00）客户端发 flush 消息会让 guifbd 结算到 0x00 顶档；BACKGROUND（0x04）客户端消息也让它保持 0x02。借入有双帽（`INTENT_HOP_MAX` 8 跳 / 链预算 400ms），超帽回落 declared。
- **产品级缺省档**：`product.toml` `[platform.boot.params]` 写 `intent_default = interactive`（G5；kernel `bootparams.rs` 词表，berry-assemble 投放）——所有新任务缺省 INTERACTIVE。它是全局开关、粒度粗，适合整机调试期，不适合长期替代逐服务声明。

### 1.4 声明之后今天会发生什么（诚实面）

intent v1 语义面 = 传播机制（TCB 双字段 + send 快照 / recv 结算 + 三道帽），**无 pick 序消费点**——`sched/src/intent.rs` 模块头与 svcmgr spawn 注记（「intent v1 解析面记录、调度零消费，消费点随 v2 EEVDF，ADR #42 两段式」）是现行口径。今天的硬消费与在途消费：

- **当前可用**：band 带键（`sched/src/band.rs`——intent 即带键的带级预算包络，默认全关，见 §4.3 第 4 层）；遥测直方（`tele: intent_tally`，见 §5.1）；消息借入链。
- **需调度器改造（v2，表已冻结）**：IntentProfile 的 latency_nice（更早虚拟截止期）/ weight 包络 / EPP / uclamp 列接入 EEVDF 消费点；timer slack 列的定时器聚合消费。声明通道先行 = 档位数据今天就在 TCB 与遥测里，v2 消费点落地即受益，无需返工。

## 二、Policy 注入（中——策略表条目，当前可用）

0x83 `berry_policy_bind` 已全量落地（六 op + 工具链 + A/B 升级工作流，详参 [策略服务用户指南-v1.0.md](策略服务用户指南-v1.0.md)）。给显示服务注入权重与 EPP 三步：

```rust
use berry_sys::*;

fn boost_guifbd() -> Status {
    // ① 对账：活跃世代 + guifbd 自身策略键（v1 key = Task::proc_tag）
    let mut packed = 0u64;
    let mut key = 0u64;
    let s = berry_policy_status(&mut packed, &mut key);
    if !is_ok(s) { return s; }
    let active_gen = packed & 0xFFFF_FFFF;

    // ② 构造 16B 条目：weight +32（INTERACTIVE 档增强）+ EPP=Perf
    let tbl = [PolicyEntry {
        key,                       // guifbd 内跑 = 自身键；别处注入须经遥测拿 key
        weight: 32,                // 内核夹紧 [-64, +64]
        placement: 0,              // 放置意见见 §三
        epp_flags: POLICY_EPP_HAS | POLICY_EPP_VAL, // Perf 档
        _rsv: 0,
    }];

    // ③ COMMIT：gen 须严格大于活跃世代，-EAGAIN = 重读 STATUS 携新 gen 重试
    berry_policy_bind(0, POLICY_OP_COMMIT, tbl.as_ptr(), 1, active_gen + 1, 0)
}
```

注入语义与效果（消费点 `sched/src/policy.rs` `apply`——每次 pick 出选后按 key 查表，命中改写 TCB）：

- **权重数学**：`prio_effective = max(prio_base + weight, pi_inherited)`，而 EEVDF 权重 = `1024 + prio_effective × 64`（`sliceface` `weight_of_prio`，封顶 1<<20）。`weight +16` → EEVDF 权重 2048 = 基线 ×2，**虚拟片减半**；`weight +32` → 3072 = ×3，虚拟片 1/3。注意 §四的「INTERACTIVE → 权重 ×2」是 v2 intent 直通蓝图；**今天的 ×2 / ×3 由 policy 表兑现**。
- **EPP 二值**：`POLICY_EPP_HAS | POLICY_EPP_VAL` = Perf，写 `Task.epp`（能效倾向，指引大小核放置与改频的软参数面）。
- **关键边界**：v1 key = `Task::proc_tag`，不可合成——guifbd 之外的服务（如 svcmgr 代注入整表）要从串口遥测行或 STATUS 对账拿 key；`key = 0`（内核任务）注入即弃；单表 ≤ 128 条；整表提交是全量换快照，不是增量合并。
- **护栏**：±64 包络内核三点执法；deadline 档（policy=3）任务被 RT 屏蔽不进表。完整错误码速查见[策略服务用户指南](策略服务用户指南-v1.0.md) §2.1。

## 三、EAS 能效与放置（高级——表通道可用，真路由需调度器改造）

放置词汇表是**策略表条目字段**（不是 intent 的自动推导）：`placement` 三值——0 = 无意见（默认）、1 = 偏 little（省电核 CPU0）、2 = 偏 big（性能核 CPU1）。显示服务条目置 2 即表达「上大核」：

```rust
let tbl = [PolicyEntry {
    key, weight: 32,
    placement: 2,                 // 偏 big——EAS 放置意见
    epp_flags: POLICY_EPP_HAS | POLICY_EPP_VAL,
    _rsv: 0,
}];
```

现实接线（`sched/src/policy.rs`，调点调度 v1.3 EAS 线）：

- **当前可用**：`apply` 顺带消费——`placement ≠ 0` 且 SMP 参与门开时写 `Task::placement_hint`（TCB 落点）；`placement_hint(key)` O(1) 读出口（唤醒路径核选择的读面）。EM 能量表形状（`sched/src/em.rs`）与 util EWMA + overutilized 门（`sched/src/util.rs`）在席。
- **需调度器改造**：**只存不路由**——唤醒选核的真消费面随 SMP 路由刀接（smoke-smp 三相 LB 稳定后）；单核 QEMU 形态（`par_enabled()` 关）连 TCB 都不写，零行为变化。今天 `placement = 2` 的可观察效果只有 ktest 断言面（`placement_hint` 键透传断言），不是实际大核迁移。
- **overutilized 回退**（EAS 永远机会主义）：任一核 util 超域容量 80% → `placement_hint` 恒 0（回退无 hint 的默认负载均衡）——饱和系统里放置意见失真，这是 Linux EAS 同款纪律。1080P@60 满载相位下别指望放置意见生效，先靠 §二权重与 §四 slice 频率。

## 四、帧率保障（调度器面现状）

### 4.1 「INTERACTIVE → EEVDF 权重 ×2」的现行等价物

intent 档直通 EEVDF 权重是 v2 蓝图（IntentProfile weight 包络列消费点未接，见 §1.4）。今天拿同样的效果走 policy 表：`weight +16` = 权重 ×2 / 虚拟片减半，`weight +32` = ×3（§二）。对 0.117ms 级 per-rect flush 的 guifbd，`+32` 是当前可用的最强档（±64 包络内，advisor 对交互族建议值 +16，叠加高唤醒 +8）。

### 4.2 60fps 帧预算与调度机会

- **信号唤醒即时**：显示管线的同步面是 IPC（flush / present 消息），signal 唤醒走 wake 路径 + 全抢占（G3 关卡已过：preempt-on-wake 通用化 + preempt 点加密）——guifbd 被消息唤醒后可抢占在跑的后台任务，不等 slice 到期。
- **超时唤醒粒度 = 1 slice**：定时器路径的超时扫描只在 tick 跑。编译期缺省 `SLICE_HZ = 10`（100ms 片）——**缺省配置下一个 16.6ms 帧预算内连 1 次超时调度机会都不保**。当前可用解法：`product.toml` `[platform.boot.params]` 写 `sched_slice_hz = 128`（值域 [16,1024]，`bootparams.rs` 词表执法）→ 片长约 7.8ms，帧预算内 ≥2 次超时唤醒机会。boot 串口有 `bootparams slice_hz=128 ...` eco 行可验（§5.1）。
- **帧循环负载画像已入册**：GUI 帧循环是 fair 类主力负载、1080P@60 帧预算是 M4 ×4 带实例化的第一批真实场景（[调度彻底计划-v1.2.md](调度彻底计划-v1.2.md) CP-12 验收线）——显示团队的实测数据（§五）直接喂这条线。

### 4.3 交互不被后台饿死：现行机制栈

从强到弱四层，全部当前可用：

1. **带序 + 带内 EEVDF**（`sched/src/class.rs`，`PURE_EEVDF = false`）：`prio_effective` 是带序，高带整带压制低带。policy `+32` 把 guifbd 抬到带 32——默认 0 带（未加权进程 / 后台）整带让位，这是「不被饿死」的第一承重墙。
2. **EEVDF 权重与 eligible**：权重 ×3 → vruntime 前进速度 1/3 → 长期处于 `vruntime <= avg` 的 eligible 态（出选优先），虚拟截止期更早（片重算 `slice_virtual`）。
3. **freeze 硬隔离**：后台整进程 `berry_process_suspend`（0x3E）退出 pick 面，窗口结束 close token 解冻——重负载相位（批量贴图 / 字体烘焙）一冻一提，对称解除（[策略服务用户指南](策略服务用户指南-v1.0.md) §6.2 联合示例）。
4. **band 带级预算**：BACKGROUND 档配 quota/period 限流（`band.rs` `configure`，带键 = intent_effective）——机制在席、**默认全关**（v1.2 §7 入场券未过），启用属调度器侧排刀，显示侧先当预留能力。

### 4.4 deadline 档不建议用于帧循环

`sched_setattr` policy=3（EDF + 预算 + ΣU ≤ 0.95 admission）语义上是硬实时通道：帧循环是软实时负载（丢帧可降档），且 deadline 任务被 RT 屏蔽出策略微调射程、`slack` 语义全变。用 §二 policy 加权 + §4.2 slice 频率组合即可。

## 五、实测建议

### 5.1 验证 intent 生效（当前可用）

- **串口档位直方**：`tele: intent_tally u2=N/M ...`（boot `tele_dump`，`itally` 单源装配）——uN 桶 = recv 结算后 `intent_effective` 落 N 档的次数。guifbd 声明 0x02 后跑 GUI 负载：与已声明 INTERACTIVE 的客户端对话时 u2 增长；UNSPECIFIED（0x00）客户端的 flush 消息把结算借到顶档，落 u0 且 `borrowed=` 同步增长——两桶都在动 = 借入链在干活。同行 `infl=` / `hop_cap=` / `bud_cap=` 是通胀与超帽遥测。
- **自查回读**：spawn 链里 `berry_sched_getattr` 读 effective 属性的 `intent` 字段（§1.2）；boot-params 路径看 eco 行 `bootparams ... intent=interactive`。
- **ktest 面**：内核 ktest 已有 INTENT 结算律 / BP bootparams / G5 缺省档断言（`kernel/src/ktest.rs`，`INTENT：` / `BP：` 前缀）——改 spawn 链后跑 `just smoke`（ktest 随 boot 自跑）确认零回归。
- 注意：v1 没有 per-task `tele:` 行带 intent 字段——intent 遥测是**档位直方**不是逐任务行；逐任务的 key 对账用 `berry_policy_status` self_key。

### 5.2 测帧延迟（HDR 唤醒直方图，当前可用）

- **超时唤醒路径**：`BENCHRWAKE p50=... p99=... n=...`（64 样本真睡 SLEEPQ → tick 唤醒 → `record_wake_lat` 灌 HDR → 合并分位；CNTVCT 周期口径，QEMU virt 62.5MHz 除之得 ns）。它是 slice 频率的直接函数——`sched_slice_hz` 前后各跑一遍，p50 塌缩幅度就是帧循环定时器面的收益。
- **IPC 唤醒路径（更贴 flush 链）**：`python3 tools/bench.py --lat`（G3-4 bench-lat，`-smp 2`）收割 `BENCHLAT,lane=ipc,n=,min=,p50=,p90=,p99=,max=`——wake→run 延迟，正是「提交线程 send flush → guifbd 上 CPU」的形态。policy 注入前后各跑，ipc lane p99 差值即权重档收益。
- **调度开销回归**：`python3 tools/sched_perf_analyze.py` 对拍 pick < 5µs 验收线（策略表命中路径计入 pick 开销——注入前后必须各测一遍，防「加权了但 pick 炸了」）。

### 5.3 基线对比方法（A/B 工作流，当前可用）

候选策略表（显示服务条目）先上 shadow 轨道双轨观测再转正，四步与判定阈值全在 [策略服务用户指南-v1.0.md](策略服务用户指南-v1.0.md) §三/§四：① SHADOW_COMMIT 候选表 → ② 跑 GUI 代表负载（1080P@60 满帧 + 后台噪声任务并跑）累积对账 → ③ `policy_ab_eval.py` 判 PROMOTE / HOLD / DEMOTE → ④ PROMOTE 转正。确定性对拍加 `just bench-icount`（B-2 通道，verdict=exact 才可比），帧率口径用 berry CLI 的 `--json` / shot 标记面（[显示与加速体系设计-v1.1.md](显示与加速体系设计-v1.1.md) 目标一的验收口径）。
